# 权限体系：设计与实现

> 日期：2026-10-23
> 范围：`app/core/permissions.py`、`app/deps.py`、全部 `app/api/*.py`、`frontend/src/lib/{auth,routes}.ts`、`AppShell`、`RequirePermission`

## 0. 一句话

**把"谁能做什么"从散落各处的 `role == "admin"` 收敛成一张权限点表；后端逐接口声明、前端只负责按清单显示。**

改造前只有两档：`CurrentUser`（登录即可）和 `AdminUser`（管理员）。两个角色时它够用，但它表达的是"你是不是管理员"，而不是"这个接口需要什么能力"——加第三种角色的那天，几十处判断会同时失效，且不会报错。

## 1. 三个维度，不要混在一起

| 维度 | 回答的问题 | 载体 |
|---|---|---|
| **认证** | 你是谁 | JWT + `users` 表 |
| **权限** | 你能用哪些功能 | 权限点 + `ROLE_PERMISSIONS` |
| **数据归属** | 你能看哪几行 | `owner_id` + `tenant.owner_filter()` |

它们**不能互相替代**：

- 只有 `owner_id` 没有权限点 → 普通用户能给自己建一条 `role=admin` 吗？不能，但他能调管理接口改别人的 `is_active`。
- 只有权限点没有 `owner_id` → 有 `doc.read` 的人会看到全公司的文档。

本项目的做法：**权限点管"功能"，owner_id 管"行"**。两个都要有。

## 2. 权限点目录

`app/core/permissions.py`，命名 `<资源>.<动作>`：

| 权限点 | 含义 | user | admin |

| `chat.use` | 对话（含会话列表/历史） | ✓ | ✓ |
| `doc.read` | 看知识库文档 | ✓ | ✓ |

## 3. 后端：三件事

### 3.1 角色 → 权限（唯一映射）

```python
ROLE_PERMISSIONS = {
    "user": frozenset({...}),
    "admin": frozenset(ALL_PERMISSIONS),
}

def permissions_for_role(role: str | None) -> frozenset[str]:
    return ROLE_PERMISSIONS.get((role or "").strip().lower(), frozenset())
```

### 3.2 每个接口声明权限点

```python
from app.core.permissions import PERM_EVAL_READ
from app.deps import require_permission

async def get_eval_run(
    run_id: int,
    user: Annotated[User, Depends(require_permission(PERM_EVAL_READ))],
) -> EvalRunDetailOut:
    ...
```

`require_permission` 返回一个闭包依赖，**按权限点缓存**（`lru_cache`）。不缓存的话每次请求都会新建闭包，`Depends` 的缓存随之失效，同一权限点在一个请求里被检查多次，日志里还全是不同的函数对象。

`CurrentUser` 仍保留，但只用于**登录者的基本权利**：`/auth/me`、改密、登出。这类接口不该被权限点挡住——角色映射配错时，用户至少要还能改密码。

### 3.3 下发清单（前端只消费，不推导）

`UserOut` 增加 `permissions`，由 `UserOut.from_user(user)` 填充：

```python
out = cls.model_validate(user)
out.permissions = sorted(permissions_for_role(user.role))
```

三个出口都走它：`issue_tokens`（登录 + 刷新复用）、`/auth/me`、管理员用户列表。

⚠ **不能靠 Pydantic 从 ORM 自动转换**：`User` 没有 `permissions` 属性，自动转换只会给默认空列表。表现是"登录 200 但菜单全没了"，后端日志一切正常。

## 4. 前端：三层

### 4.1 页面 → 权限点（唯一真源）

`lib/routes.ts`：

```ts
export const PAGE_PERMISSIONS: Record<PageKey, string> = {
  chat: 'chat.use', knowledge: 'doc.read', profile: 'profile.read',
  eval: 'eval.read', tools: 'tools.manage', trace: 'trace.read',
  retriever: 'retriever.use', admin: 'admin.users',
};
```

侧栏过滤与路由守卫**都读这张表**。分两份写，就会出现"菜单藏了但地址栏能进"或反过来，而这两种不一致都不会报错。

### 4.2 侧栏

```ts
const visibleNav = navItems.filter((item) =>
  hasPermissionOf(user, PAGE_PERMISSIONS[item.key]),
);
```

`adminOnly: true` 已被删除——那等于前端也维护了一份 role→能看什么的映射。

### 4.3 路由守卫

```tsx
function guarded(key: PageKey, element: ReactNode) {
  return <RequirePermission permission={PAGE_PERMISSIONS[key]}>{element}</RequirePermission>;
}

<Route path="/admin" element={guarded('admin', <AdminPage />)} />
```

`RequirePermission` 用 `useSyncExternalStore(subscribeSession, getSession, getSession)`，**不是**渲染时读一次 `getSession()`。否则管理员被降级后，页面会一直停在管理页直到手动刷新。

无权限时渲染 `ForbiddenPage`（403 说明 + 缺哪项权限 + 回对话台），而不是静默重定向——用户点了入口却"什么都没发生"会被理解成页面坏了。

## 5. 四个容易写错的边界

### 5.1 `tools.list` 与 `tools.manage` 必须分开

- `tools.list`：对话时 LLM 要拿工具清单，**普通用户必须有**，否则对话直接废掉。
- `tools.manage`：工具注册表管理页，管理员专属。

合成一个权限点，就必然逼出"要么普通用户能改全局工具配置，要么他不能对话"。

### 5.2 「缺失」与「空数组」是两件事

```ts
if (!user) return false;                        // 未登录：确定没有
if (!Array.isArray(user.permissions)) return true;  // 旧 session：还不知道
return user.permissions.includes(permission);   // 后端明确说了
```

- 旧 session（账号体系升级前存的）没有 `permissions` 字段 → 先放行，由启动时 `/auth/me` 补齐。返回 `false` 会让侧栏瞬间全空（连对话台都没了），比多显示几个入口更难理解。
- 空数组 = 后端明确说"这个人没有任何权限" → 必须拦住。合并成一个兜底，就会在"角色配错"时静默放行整个应用。

### 5.3 未知角色 fail-closed

`permissions_for_role("superuser")` → 空集。默认放行的后果是"新角色在配好之前就能访问一切，且没有报错"；空集是"立刻不能用"，会被当场发现。

### 5.4 权限判定不看 token claims

`get_current_user` 每请求回查 `users` 表，`require_permission` 用的是这次查出来的 `user.role`。若改成读 token 里的 role，管理员点了"降级"后对方还能用 2 小时，用户只会觉得"点了没用"。

已有用例 `test_role_change_takes_effect_on_next_request` 钉住这一点。

## 6. 关键取舍

| 决定 | 为什么不选另一个 |
|---|---|
| 权限点用**代码常量** | 放 DB 里意味着代码可以引用一个不存在的权限点，拼错字符串也不报错；且需要额外一张表 + 管理界面 + 缓存一致性。将来真要做自定义角色，改 `permissions_for_role` 的内部实现即可，调用点不动 |
| admin **显式列出**全部 | 通配 `*` 会让新增权限点自动给 admin（没人 review），且审计时无法回答"admin 到底能干什么" |
| 403 detail **带权限点** | "权限不足"无法定位；内部平台，权限点名不是机密。可排障优先 |
| 前端**不推导** role→权限 | 两份表必然漂移，漂移那天不会报错，只会"菜单显示了但点进去 403" |
| 保留 `AdminUser` | 存量兼容；新接口一律 `require_permission`。两者在只有两个角色时等价 |

## 7. 模块级自检

`permissions.py` 在 import 时跑三条检查，配错就炸（而不是等到某次请求）：

1. `ALL_PERMISSIONS` 无重复
2. 每个角色引用的权限点都在目录里（防拼错）
3. 每个权限点至少被一个角色拥有（防孤儿）

第 3 条同时保证"新增权限点忘了给 admin"变成**启动失败**，而不是"管理员莫名少一个入口"这种要用户来报的 bug。

## 9. 自测题

**Q1** 为什么普通用户必须拥有 `tools.list` 却不能拥有 `tools.manage`？

**A** 前者是对话的运行时依赖（LLM 要据此决定调什么工具），后者是平台级配置能力。合成一个权限点会逼出"能对话就能改全局工具配置"或"不能对话"的二选一。

**Q2** 前端已经有 `PAGE_PERMISSIONS` 了，为什么还要后端每个接口声明一次？

**A** 前端那份只决定"显示什么"，可以绕过（改 localStorage、直接 curl）。后端那份是真正的边界。两者职责不同，不是重复。

**Q3** `permissions` 缺失时返回 `true`，这不是 fail-open 吗？为什么可以接受？

**A** 因为它只影响"显示什么"，真实操作仍会被后端 403。而返回 `false` 的代价是侧栏全空——用户会以为系统坏了。同时它有明确的收敛路径：启动时 `/auth/me` 一定会把清单补齐。

**Q4** 把权限点放进数据库表不是更灵活吗？

**A** 灵活的前提是有人维护。现阶段角色固定，DB 表带来的只有"不发版就能改"，代价是代码可引用不存在的权限点（拼错不报错）+ 一张表 + 管理界面 + 缓存。等真有运营需求再换，`permissions_for_role` 的内部实现换掉即可。

**Q5** 为什么 `require_permission` 要按权限点缓存闭包？

**A** 不缓存则每次请求新建闭包 → `Depends` 的依赖缓存失效 → 同请求内重复检查，且 OpenAPI/调试器里一堆同名函数看不出一条规则在哪。
