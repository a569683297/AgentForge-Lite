## 〇、先统一几个词

后面反复用到，第一次出现时给准确定义，**不是"大概知道"就行**：

| 名词 | 含义（本项目里的具体所指） |
|---|---|
| **哈希（hash）** | 单向函数：`明文 → 定长串`，无法反推。密码只存哈希，永不存明文。本项目用 **bcrypt**（专门为密码设计，故意很慢）。 |
| **加盐（salt）** | 每个密码配一段随机串一起哈希。同一密码两次注册得到**不同**哈希，防"彩虹表"（预先算好的 明文→哈希 对照表）。bcrypt 自动带盐。 |
| **成本因子（cost / rounds）** | bcrypt 的"迭代次数"以 2 的幂表示。`rounds=12` = 迭代 2¹² 次。它是**唯一可调的"慢"旋钮**：越大越抗暴力破解，也越慢。 |
| **JWT** | 一段 `base64(header).base64(payload).签名` 的字符串。服务端**不存**它，靠签名验证真伪。代价：签出去就撤不回来。 |
| **claims** | JWT 里的字段。本项目用 `sub`(用户id) / `typ`(access或refresh) / `jti`(唯一id) / `role` / `iat`(签发时刻) / `exp`(过期时刻)。 |
| **access token** | 短期凭证，**每个 API 请求**都带。2 小时。 |
| **refresh token** | 长期凭证，**只用来换新的 access**。7 天。它是唯一能吊销的那一份。 |
| **轮换（rotation）** | 每次用 refresh 换新时，**旧的立刻作废**。用来让"被盗的 refresh 只能用一次"。 |
| **多租户（multi-tenant）** | 一套代码/一个数据库服务多个用户，数据互相不可见。本项目是"行级隔离"：同一张表，用 `owner_id` 分家。 |
| **owner** | 数据归属人。`sessions` / `documents` / `llm_models` 等表都有一列 `owner_id`。 |
| **审计日志（audit log）** | 「谁、在什么时候、对什么、做了什么」的结构化记录。与"应用日志"不同：它不轮转、可查询、是**事实记录**。 |

## 一、边界：做了什么，没做什么

### 做了

| 能力 | 具体行为 |
|---|---|
| 注册 / 登录 / 登出 | 邮箱 + 密码；登录失败 5 次锁 5 分钟 |
| 令牌 | access 2h + refresh 7d；refresh **轮换**；登出即吊销 refresh |
| 改密 | 校验旧密码；改完**作废所有改密前签发的 refresh** |
| 找回密码 | 一次性令牌（30 分钟），走邮件；本地无 SMTP 时把链接写日志 + 回 `dev_link` |
| 数据隔离 | 5 张表加 `owner_id`；检索（向量 + BM25）、会话、文档、模型全链路按人过滤 |
| 权限分层 | `user` / `admin` 两个角色；工具管理、评测、Trace、指标、用户管理**仅管理员** |
| 用户管理 | 列表、搜索、启用/禁用、改角色；三条"不能自锁"硬规则 |
| 审计 | 12 个动作；管理员页面可查、可按动作前缀/操作者过滤 |
| 迁移 | `scripts/auth_migrate.py` 幂等，含结构自查 + 行为自查 |

### 没做（是设计边界，不是漏了）

| 没做 | 原因 |
|---|---|
| OAuth / 第三方登录 | 需要回调域名、应用注册、状态校验，与本项目的"自建账号"是两条路 |
| 邮箱验证（注册即用） | 需要真实 SMTP + 验证令牌流。当前只有**找回密码**用了邮件通道 |
| 团队 / 组织 / 共享 | 现在是"每人一亩三分地"。共享要引入 `grants` 表与"谁能看谁"的判定，是另一个量级 |
| access token 立刻吊销 | 无状态 JWT 的固有代价。要立刻踢人只能维护黑名单（每请求查一次 Redis）或把 TTL 缩到几分钟。本项目选的是"2 小时"这个折中，并**如实写进文档**而不是假装实现了 |
| 工具按人隔离 | `ToolRegistry` 是**进程级全局**，两人上传同名工具会撞。已在 `ToolServer.owner_id` 的注释里登记 |
| `X-Forwarded-For` 信任 | 审计的 `ip` 字段在 nginx 反代后恒为 `127.0.0.1`。信任这个头需要先有"可信代理列表"，否则谁都能伪造 |

## 二、端到端：两条链路

理解这套东西最快的路径，是把两条链路从头到尾走一遍。

### 2.1 一次登录

```
浏览器 POST /api/auth/login {email, password}
  │
  ▼ [1] 限流检查      Redis GET auth:fail:{email}
  │                  └─ ≥5 → 直接 401（不等校验，也不告诉"你被锁了"）
  ▼ [2] 查用户        SELECT * FROM users WHERE email = ?
  │                  └─ 查不到 → 跑一次假哈希（见 §四.3）→ 401
  ▼ [3] 校验密码      bcrypt.checkpw(明文, 库里的哈希)   ← 166ms，故意慢
  │                  └─ 不匹配 → 失败计数 +1 → 401
  ▼ [4] 查账号状态    is_active=false → 401（同一条文案）
  │
  ▼ [5] 清理 + 升级   删失败计数；last_login_at=now；
  │                  哈希强度不足则顺手重算（见 §四.4）
  ▼ [6] 签一对 token  access(2h) + refresh(7d)
  │                  refresh 的 jti 写进 Redis 白名单，TTL 7 天
  ▼ [7] 写审计        audit_logs: auth.login
  ▼
200 {access_token, refresh_token, expires_in, user}
```

**为什么第 [3] 步必须慢**：如果校验只要 1ms，攻击者就能拿字典每秒试几千个密码。166ms 意味着单核每秒只能试 6 个 —— 这才是 bcrypt 存在的全部意义。

### 2.2 一次带鉴权的对话（跨用户的部分在哪）

```
浏览器 POST /api/chat  Authorization: Bearer <access>
  │
  ▼ [1] 验签 + 查库    deps.get_current_user
  │                   ├─ 签名/过期/类型不对 → 401
  │                   └─ 回查 users：被禁用 → 401（**立即生效**，不等 2 小时）
  ▼ [2] 会话归属       ensure_session(session_id, owner_id=user.id)
  │                   ├─ 不存在 → 建一条，归属我
  │                   ├─ 存在且是我的 → 继续
  │                   └─ 存在且是别人的 → 404（不是 403）
  ▼ [3] 进入 Agent 图  owner_scope(user.id)  ← ContextVar，见 §六
  │     ├─ 检索：SQL 三处 CTE 都带 owner 条件
  │     ├─ 记忆：Redis key 带 session_id（会话本身已按 owner 校验过）
  │     └─ 写 messages：session_id 已确认归属
  ▼
200 {answer, sources, ...}
```

## 三、数据模型

### 3.1 两张新表

**`users`**：`id` / `email`(唯一，小写) / `password_hash` / `display_name` / `role` / `is_active` / `created_at` / `updated_at` / `last_login_at` / `password_changed_at`

两个字段值得单独说：

- `is_active` 而不是"删用户"：账号要能**停用**而不是消失 —— 停用不破坏引用它的审计记录、会话、文档。
- `password_changed_at`：改密后用它和 refresh token 的 `iat` 比对，把"改密前签发的 refresh"全部判死。**没有它就只能靠 7 天自然过期**。

`__repr__` 特意不打印 `password_hash` —— 一句 `print(user)` 就能把哈希送进日志的事故，比想象中常见。

**`audit_logs`**：`id` / `actor_id`(FK, `ON DELETE SET NULL`) / `actor_email`(快照) / `action` / `target_type` / `target_id` / `detail`(JSONB) / `ip` / `created_at`

索引两条：`(created_at)` 服务"按时间倒序"，`(actor_id, created_at)` 服务"这个人做过什么"。

### 3.2 五张表加 `owner_id`

```
documents      owner_id → users.id  ON DELETE CASCADE   ← 参与过滤
sessions       owner_id → users.id  ON DELETE CASCADE   ← 参与过滤
llm_models     owner_id → users.id  ON DELETE CASCADE   ← 参与过滤
tool_servers   owner_id → users.id  ON DELETE CASCADE   ← **只作审计，不参与过滤**
eval_runs      owner_id → users.id  ON DELETE SET NULL  ← **不参与过滤**
```

后两张为什么不参与过滤，必须说清楚，否则下一个人会以为漏了：

- **`tool_servers`**：工具是**平台能力**，注册表是进程级的。A 上传的工具 B 也能在对话里被 LLM 调用 —— 因为 LLM 看到的是同一个注册表。既然"能用"是共享的，"管理"就统一收给管理员（`AdminUser`）。`owner_id` 留着是为了回答"这个工具是谁传的"。
- **`eval_runs`**：评测是**平台级**任务，跑的是同一套语料、同一批用例，产出要能横向对比。按人切开会让"上一次跑的分"和"这一次"没法比。

**`nullable=True` 是刻意的**：迁移前的老数据没有归属，回填给引导管理员（迁移脚本第 5 步）；但"没有归属"这个状态本身要允许存在，否则迁移会失败。

### 3.3 一条约束必须收窄

```sql
-- 改造前：全库唯一
CREATE UNIQUE INDEX uq_documents_content_hash ON documents (content_hash);
-- 改造后：每人唯一
CREATE UNIQUE INDEX uq_documents_owner_hash ON documents (owner_id, content_hash);
```

不收窄会发生什么：B 上传一份 A 已经传过的《员工手册》，哈希相同 → 被判定为"重复文档" → **复用 A 的那一行**。B 拿到的是 A 的文档 id、A 的切片、A 的引用。这不是"去重命中"，这是数据泄露。

去重这件事本身没变，变的只是"判重的作用域"。

## 四、密码：bcrypt 的四个坑

全部集中在 `app/core/security.py`（**密码学的唯一出口**，别的地方不许出现 `bcrypt.` 或 `jwt.`）。

### 4.1 成本因子要用实测选，不是抄

本机（Apple Silicon / bcrypt 5.0.0）实测：

| rounds | 单次耗时 | 每秒可试（单核） | 用途 |
|---|---|---|---|
| 4 | ~0.7 ms | ~1400 | **仅测试**（建账号不拖慢用例） |
| 10 | ~42 ms | ~24 | 老库的常见默认值 |
| **12** | **~166 ms** | **~6** | **本项目生产值** |
| 14 | ~663 ms | ~1.5 | 登录明显变卡，用户会抱怨 |

`BCRYPT_ROUNDS = 12`。注意代码注释里早期写的是"250ms"——那个数字是猜的，实测是 166ms。**这类数字必须实测后写，抄来的数字会让后续所有性能判断都偏**。

### 4.2 72 字节是硬上限，必须显式拒绝

bcrypt 在设计上只看前 **72 字节**。超长密码的处理有两种：

```python
# ❌ 静默截断：密码 A 的前 72 字节若与密码 B 相同，两者等价
raw = plain.encode()[:72]

# ✅ 本项目：明确拒绝
if len(raw) > BCRYPT_MAX_BYTES:
    raise ValueError("密码过长（bcrypt 上限 72 字节）")
```

为什么截断很糟：用户以为自己设了 100 位的强密码，实际只有前 72 位生效。更麻烦的是**事后无法发现**——库里存的哈希看不出它来自一个被截断的密码。

⚠ 还有一个容易错的细节：**`max_length` 数的是字符，bcrypt 限的是字节**。中文密码 72 个字符 = 216 字节，仍会超。所以 pydantic 层的 `max_length=72` 只挡明显过长的输入，真正的拒绝在 `hash_password` 里按字节判。

### 4.3 用户不存在时也要跑一次 bcrypt（陪跑）

```python
if user is None:
    verify_password(password, _DUMMY_HASH)   # 目的只有一个：消耗 166ms
    raise InvalidCredentials("邮箱或密码错误")
```

不这么做的话：不存在的邮箱 **1ms** 返回，存在的邮箱 **166ms** 返回。响应时间本身就是"这个账号存不存在"的答案，比任何错误文案泄露得都多。

`_DUMMY_HASH` 必须是一个**格式合法、成本因子 12** 的真 bcrypt 串：

```
$2b$12$4xjuRglf2rrm7W5ZL9cO.u3VbIHz.AyuO2d2iP7DfyZNahMZrI/RW
```

如果随便写个 `"dummy"`，bcrypt 在**解析阶段**就报错并立刻返回 —— 反而把"不存在"变成 1ms、"密码错"变成 166ms，比不陪跑更糟。`tests/unit/test_security.py` 里有一条用例专门守这个不变量（断言它以 `$2b$12$` 开头，且跑一次 > 50ms）。

### 4.4 `needs_rehash`：格式不合法也算"需要重算"

登录成功时顺手把低强度哈希升级到 12 —— 用户无感，全库强度随时间收敛。

```python
def needs_rehash(hashed: str) -> bool:
    parts = (hashed or "").split("$")
    if len(parts) < 4:          # ← 结构必须先独立判断
        return True
    try:
        return int(parts[2]) < BCRYPT_ROUNDS
    except ValueError:
        return True
```

**这里踩过一个真坑**，第一版写的是：

```python
return len(parts) >= 4 and int(parts[2]) < BCRYPT_ROUNDS   # ❌
```

`"garbage".split("$")` 只有 1 段 → `and` 短路成 `False` → 函数返回"不需要升级"。而 docstring 明明写着"解析不了的串按需要升级处理"。`except` 那支**永远进不去**，因为短路发生在抛异常之前。

教训：**`and` 的短路会吃掉异常分支**。校验类的函数，结构判断要独立 `if` + 独立 `return`。

## 五、JWT：为什么 access 和 refresh 待遇不同

### 5.1 一个刻意的不对称

| | access | refresh |
|---|---|---|
| 有效期 | 2 小时 | 7 天 |
| 用在哪 | 每个 API 请求的 `Authorization` 头 | 只在 `/api/auth/refresh` |
| 是否查 Redis | **不查** | **必须查**（白名单） |
| 能否吊销 | 不能（只能等过期） | 能（删白名单即失效） |
| 存哪 | 前端 localStorage | 前端 localStorage |

**为什么 access 不查 Redis**：它是每个请求都要验的东西。查一次 Redis 就是给每个请求 +1 次网络往返；对话接口本身要跑几秒，多 1ms 确实看不出来，但这是"用可避免的成本换可避免的耦合"。2 小时的窗口是可接受的取舍 —— 前提是**这个取舍被写进文档**，而不是让人误以为"登出就立刻踢下线"。

**为什么 refresh 必须查**：它是长凭证，必须能吊销。JWT 本身撤不回来，所以把 `jti` 落 Redis 做白名单 —— 不在名单里就是不认。

### 5.2 轮换：旧的那份用完即废

```python
async def refresh_tokens(refresh_token: str) -> dict:
    payload = decode_token(refresh_token, expected_type=TOKEN_TYPE_REFRESH)
    key = _REFRESH_KEY.format(jti=payload["jti"])
    owner = await _redis_get(key)
    if owner is None or owner != str(user_id):
        raise InvalidCredentials("登录已失效，请重新登录")
    ...
    await _redis_delete(key)          # 先删旧
    return await issue_tokens(user)   # 再签新
```

顺序不能反：先签新再删旧，万一签新失败，旧 token 还在 —— 用户手里就有两份有效凭证。

轮换的实际价值：refresh 被盗后，攻击者用一次，真实用户的下一次刷新就失败 —— **异常被暴露出来**。没有轮换的话，两边可以并行用 7 天，谁都不知道。

### 5.3 fail-closed vs fail-open：两种 Redis 故障，两种处理

同一个项目里，两处对 Redis 故障的处理**故意相反**：

| 模块 | Redis 挂了 | 理由 |
|---|---|---|
| `memory_service`（对话记忆） | **降级**继续 | 丢了只是"忘了上文"，对话还能继续 |
| `auth_service`（认证） | **失败**（503） | 读不到白名单的 refresh，可能是抖动，也可能是有人在刷 —— 两种在服务端长得一样，唯一安全的处理是都不放行 |

这就是 fail-closed（出错就拒绝）与 fail-open（出错就放行）的分界：**它取决于"放行的后果"**。授权相关的必须 fail-closed，体验相关的可以 fail-open。

### 5.4 禁用账号要"立即"生效

access token 里有 `role` 快照，本来可以不查库。但 `get_current_user` 仍然**每个请求回查一次 users**：

```python
user = await session.get(User, user_id)
if user is None or not user.is_active:
    raise HTTPException(401, "登录状态无效，请重新登录")
```

代价是每请求一次主键查询（毫秒级、走索引）。收益是"禁用"这个动作**立刻**生效，而不是等 2 小时。禁用一个正在滥用系统的账号时，这个差别就是"当下止血"和"两小时后止血"。

同理，`require_admin` **认库里的 role，不认 token 里的 role** —— 降级一个管理员也应该立刻生效。

## 六、多租户：为什么用 ContextVar 而不是参数

### 6.1 问题的形状

要给检索加 owner 过滤，最自然的写法是把 `owner_id` 一路当参数传：

```
api/chat.py → agent_service.run_agent → 图节点 → 工具 → retrieval_service.search
```

这条路有 5~6 跳。但真正的问题不是"跳数多"，而是：

> **检索那一跳的调用者是 LLM。**

LLM 只会填一个 `query` 字符串。它不知道也不该知道"当前是谁在问"。身份必须是**环境信息**（ambient），不是**参数**。硬塞进工具 schema 里还会让模型有机会自己编一个 owner。

### 6.2 用 ContextVar 承载"当前请求是谁"

```python
_current_owner: ContextVar[uuid.UUID | None] = ContextVar("current_owner", default=None)

@contextmanager
def owner_scope(owner_id):
    token = _current_owner.set(owner_id)
    try:
        yield
    finally:
        _current_owner.reset(token)      # ← 必须 reset(token) 而不是 set(None)
```

**为什么必须 `reset(token)` 而不是 `set(None)`**：`set(None)` 看起来等价，但会丢掉"上一层原来的值"。嵌套 `owner_scope` 真实存在（接口层设一次、某个内部调用再设一次），`reset(token)` 精确还原到上一层，`set(None)` 会把外层也清掉 —— 症状是"某些路径突然能查到全库"，而且**只在嵌套时出现**。

### 6.3 `owner_filter()`：把判断收进一个函数

```python
def owner_filter(column, owner_id=None):
    target = owner_id if owner_id is not None else current_owner()
    if target is None:
        return true()          # 系统内部调用（评测/脚本）：不过滤
    return column == target
```

两个设计点：

- 返回 `true()` 而不是让调用处写 `if owner is not None:`。**调用处一旦要写 if，就一定有地方会忘**。SQLAlchemy 的 `where(true())` 是合法的无操作条件。
- `target is None` 表示"系统内部调用"，**不是**"没有权限"。这个分支存在是必要的（离线评测要跑全库），但它必须只有一个入口 —— 想拿到它只能不设 `owner_id`，而不是"设错一个值"。

### 6.4 BM25 的 SQL：三个 CTE 都要加

这是本节最值得记的一条。`_BM25_SQL` 里有三段参与计算：

| CTE | 算什么 | 漏了会怎样 |
|---|---|---|
| `corpus` | 全库文档数 `N`、平均长度 `avgdl` | 长度归一化基准被别人的语料拉偏 |
| `candidates` | 谁被召回 | **召回别人的文档**（最明显的一种） |
| `df` | 每个查询词的文档频率 | IDF 被压低 |

IDF 的公式是：

```
IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
```

`df` 变大 → 分母变大 → IDF 变小 → 这个词的区分度被认为更低。

**只给 `candidates` 加 owner 是最典型的错法**：召回范围对了，排序却是错的。症状是"我搜同一个词，排序和库里别人有多少相关文档有关"。它不报错、不越权，只是**结果悄悄变差** —— 这类问题在数据隔离里叫**统计量侧信道**。

`tests/integration/test_isolation.py::test_bm25_statistics_do_not_leak_across_owners` 就是守它的：先只放我自己的文档测一个分，再往别人名下塞 5 份含同一个词的文档，**分数必须一模一样**。

> 这条用例写完我特意验证过它"有牙齿"：把 `corpus` 与 `df` 两处的 owner 条件删掉，分数从 `17.072` 掉到 `14.7682`，用例当场变红。**没验证过会红的测试，往往是不会红的测试。**

### 6.5 一个容易漏的坑：`str(None)` 是 `"None"`

```python
"owner": str(scoped) if scoped is not None else None    # ✅
"owner": str(scoped or "")                              # ❌ 得到 "None" / ""
```

SQL 里是 `CAST(:owner AS uuid) IS NULL`。如果传进去的是字符串 `"None"`，PG 会尝试把它转成 uuid 并**直接报错**（`invalid input syntax for type uuid`）。而且 `str(scoped or "")` 还有第二个坑：当 `scoped` 是合法 uuid 时它没问题，但这个写法让人以为"空值会变成 None"，实际变成空串。

### 6.6 越权一律 404，不是 403

| 场景 | 状态码 | 为什么 |
|---|---|---|
| 访问**别人的** document / session / model | **404** | 403 等于承认"这个 id 确实存在"。攻击者可以用 404/403 的差别枚举出有效 id |
| 普通用户访问**平台级**接口（评测/工具/指标） | **403** | 这些资源确实存在，只是你无权用。这里不存在"枚举"问题（谁都猜得到 `/api/metrics`） |
| 没带凭证 | **401** + `WWW-Authenticate: Bearer` | 前端据此知道"该去登录了"，而不是"你没权限" |

三种码对应三个不同的问题，混用会让前端没法处理，也会泄露信息。

### 6.7 `ON CONFLICT DO NOTHING` 之后必须再查一次归属

```python
created = (await db.execute(stmt)).scalar() is not None   # 只有真插进去才有返回行
if not created and owner_id is not None:
    existing_owner = ...
    if existing_owner != owner_id:       # None 也算不通过
        raise SessionOwnershipError("会话不存在")
```

`ON CONFLICT DO NOTHING` 有两种来源：**「我新建的」** 和 **「别人早就建好的」**。两者返回的都是"没有行"，所以冲突之后必须再查一次归属。

漏了这一步的后果不是"看到不该看的"，而是**写进别人的上下文** —— 最危险的一类越权。`existing_owner is None`（迁移前遗留的无主会话）也算不通过：让它被谁"顺手接管"比让它闲着更危险。

### 6.8 流式接口：两条时序，错一条就失效

```python
# ❌ 错：接口层设 owner_scope
with owner_scope(user.id):
    return StreamingResponse(event_stream())

# ✅ 对：生成器内部设
async def event_stream():
    with owner_scope(user.id):
        async for event in run_agent_stream(...):
            yield event
```

接口层设的 `with` 在**函数返回时**就退出了，而生成器是在返回**之后**才被逐个 `yield` 消费的 —— 那时候 ContextVar 早就还原了。症状是"流式对话检索不到任何东西"（owner 变回 None 之前其实会查全库，更糟）。

第二条时序：**归属校验必须在开流之前**。

```python
session_id = req.session_id or uuid.uuid4()
await ensure_session(session_id, owner_id=user.id)   # ← 先校验
return StreamingResponse(event_stream())             # ← 再开流
```

开流之后 HTTP 状态码已经是 200，越权只能表现为一条 error 帧 —— 前端得先判断"这是不是权限问题"，而它本该是一个干净的 404。

### 7.1 一张表说清谁能调什么

| `/api/eval/*` | **管理员** | `AdminUser` |
| `/api/traces/*` | **管理员** | `AdminUser` |
| `/api/metrics/*` | **管理员** | `AdminUser` |
| `/api/admin/*` | **管理员** | `AdminUser` |

`/api/tools` 原先**没有任何凭证依赖**（D27 时期的诊断接口）。账号体系上线后，它成了唯一一个"匿名就能列出全部工具名、参数、MCP server 连接状态"的口子。现在收到登录之后（普通用户即可 —— 对话页要用它）。

### 7.2 权限判断写在依赖里，不写在函数体里

```python
AdminUser = Annotated[User, Depends(require_admin)]
```

写在依赖里的效果是：**新增接口时不写 `admin: AdminUser` 就等于没有权限**（FastAPI 会因为缺参数报错，或者被代码审查抓到）。写在函数体里判断则是"新增接口时记得判断" —— 而"记得"这件事，在第十个接口上一定会失效。

### 7.3 三条自锁防护（都在接口层，不依赖前端）

| 规则 | 不加会怎样 |
|---|---|
| **不能禁用自己** | 管理员一怒之下把自己禁用，就再没人能改回来。`scripts/auth_set_password.py` 只改密码，不改 `is_active` |
| **不能把最后一个管理员降级** | 系统里没 admin 之后，用户管理接口全 403，平台进入"只能改库"状态 |
| **改自己的角色也走第 2 条** | "让另一个 admin 顶上，再把自己降级"是合法操作 —— 只要降级后还剩至少一个 |

校验顺序很重要：**先算清楚"改完之后还剩几个 admin"，再决定要不要拒绝**。反过来的话（先写库再检查）就得回滚，而回滚窗口里别人可能已经读到中间状态。

## 八、审计

### 8.1 与 Langfuse 的分工（最容易混的一对）

| | Langfuse（`observability.py`） | 审计（`audit_logs`） |
|---|---|---|
| 记的是 | **一次运行的内部过程**：span 树、耗时、token | **一次状态变更**：谁、对谁、从什么变成什么 |
| 面向 | 排障、性能 | 合规、追责 |
| 量级 | 一次对话几十条 | 一次对话通常 0 条 |
| 能删吗 | 会轮转、会过期 | **不轮转、不提供删除入口** |

两者都叫"记录"，但回答的是不同的问题。把"禁用一个账号"记进 Langfuse 是错的（它不是一次运行）；把"检索耗时 2.4s"记进审计也是错的（它不是状态变更）。

### 8.2 四个设计取舍

1. **`actor_email` 冗余存快照**：账号可能被删、邮箱可能被改，而"当时是谁干的"必须保持当时的模样。审计表的语义是**事实记录**，不是"当前状态的视图"。
2. **`actor_id` 用 `ON DELETE SET NULL`，不用 `CASCADE`**：级联删除会让"删号"变成"抹掉痕迹"——那正好成了滥用的出口。
3. **`detail` 用 JSONB**："把 `{role: user → admin}` 记成一句话"之后就再也查不了了。JSONB 既能给人看，也能 `WHERE detail->>'from' = 'user'` 地查。
4. **写审计永不抛异常**：审计是旁证，不是前置条件。审计表写不进去就让"登录"失败，是本末倒置。失败只记一条 warning（用 warning 不用 exception：它不该出现在"服务在报错"的信号里，但必须留下"这次审计丢了"的痕迹）。

### 8.3 对外不区分，对内必须区分

这看起来矛盾，其实是两条不同的边界：

| | 登录失败的**响应** | 登录失败的**审计** |
|---|---|---|
| 内容 | 永远"邮箱或密码错误" | `reason: user_not_found / bad_password / inactive` |
| 防的是 | **枚举**（攻击者靠响应判断账号存在性） | 给**运维**看 |

三种 reason 的处置完全不同：一堆 `bad_password` 是撞库，一堆 `user_not_found` 是有人在扫邮箱，一堆 `inactive` 是有人拿已禁用的号在试。混成一条，运营就没法判断该封 IP 还是该排查泄露。

### 8.4 12 个动作

```
auth.login              admin.user_disabled        document.deleted
auth.login_failed       admin.user_enabled         tool_server.uploaded
auth.logout             admin.user_role_changed    tool_server.deleted
auth.register
auth.password_changed

```

命名用 `领域.动作` 而不是零散字符串：查询时能按前缀分组（`auth.*` 全是认证类）。`GET /api/admin/audit/actions` 把清单吐给前端，**新增动作时不用改前端**。

## 九、前端

### 9.1 双拦截器（axios）

```
请求拦截：/auth/ 之外的接口 → 先看本地 expiresAt（提前 60s 视为过期）
                            └─ 过期 → 先刷新，再带上新 token 发出去
响应拦截：401 且不是 /auth/ 且没重试过
                            └─ 单飞刷新 → 重放原请求
```

**为什么要提前 60 秒**：`expiresAt` 是按服务端返回的 `expires_in` 算的，但客户端的时钟、网络往返、服务端的判定时刻之间有几秒抖动。卡在最后一秒刷新，会出现"我以为还有效，但服务端已经判过期"。

**为什么必须"单飞"（single-flight）**：

```typescript
let refreshing: Promise<string | null> | null = null;
function refreshOnce() {
  refreshing ??= refreshAccessToken().finally(() => { refreshing = null; });
  return refreshing;
}
```

页面加载时常常并发 3~5 个请求。如果每个 401 都各自触发一次刷新，会有严重后果：**refresh 是轮换的** —— 第一个请求刷新成功（旧 refresh 作废），第二个请求还在用旧 refresh，于是 401，然后可能把刚拿到的新 token 也判死。最后用户被莫名其妙踢出登录。共享同一个 Promise 就只有一个真正在刷。

`_retried` 标志防的是另一种死循环：刷新成功但接口仍然 401（比如账号被禁用），不能无限重放。

### 9.2 `safeNext`：防开放重定向

```typescript
function safeNext(raw: string | null): string {
  if (!raw || !raw.startsWith('/') || raw.startsWith('//')) return '/';
  return raw;
}
```

`?next=` 是"登录后回到原页面"必需的。但不校验的话，`/login?next=https://evil.com` 会变成一个**用我们域名做的钓鱼跳板** —— 用户看到的是我们的登录页，登录成功后跳到攻击者的站点。

必须同时挡 `//evil.com`（协议相对 URL，浏览器会当成外站）。

### 9.3 localStorage 存 token 的取舍

| | localStorage | HttpOnly Cookie |
|---|---|---|
| XSS 能否读到 | **能** | 不能 |
| CSRF | 不受影响（要靠手动带 header） | 需要 CSRF token |
| 多标签页同步 | 天然一致 | 天然一致 |

选 localStorage 是**明确的取舍**：换来"不用处理 CSRF、前后端分离部署简单"，代价是"一旦有 XSS，token 直接可读"。要真正解决 XSS 只能靠 CSP + 输出转义，而不是换个存储位置 —— HttpOnly 只是让 XSS **偷不到 token**，攻击者仍然可以在页面里替用户发请求。

### 9.4 前端藏入口 ≠ 有权限

`AppShell` 里按 `isAdmin` 过滤导航项，只是**体验**：不让普通用户点进一个必然 403 的页面。真正的边界在后端。

对应的测试写法：`test_normal_user_gets_403_on_admin_only` 用普通用户的 token **真的打一次**每个管理员接口。断言 403，而不是断言"菜单里没有这个入口"。

### 9.5 真实 bug ①：登录后不跳转，F5 才进得去

**这是上线验收时用户实测报出来的**（2026-10-21），单测和接口探针全都通过的那一版。

现象：

```
输入正确密码 → 点"登录" → 页面毫无反应，还停在登录页
按 F5 刷新     → 直接进了 /chat
```

根因不在后端。登录**成功了**，`saveSession()` 把 token 写进了模块变量和 localStorage。问题出在视图层：

```typescript
// ❌ 有 bug 的写法
const [authSession, setAuthSession] = useState<StoredSession | null>(() => getSession());
```

`useState` 的初始值函数**只在首次挂载时执行一次**。之后 `saveSession()` 改的是 `lib/auth` 里的 `current`，App 组件完全不知道 —— `authSession` 还是 `null`，`authenticated` 还是 `false`，路由守卫把刚跳过去的 `/chat` 又推回 `/login`。

用户看到的是"点了没反应"，实际发生的是：

```
saveSession() → localStorage 有 token
navigate('/chat') → 路由变成 /chat
渲染 → authenticated === false → 早返回 → <Navigate to="/login?next=/chat">
```

刷新为什么能好：整个 App 重新挂载，`useState` 的初始值函数重新跑一次，这次从 localStorage 读到了 token。

**修法：把"读一次快照"换成"订阅数据源"**

```typescript
const authSession = useSyncExternalStore(subscribeSession, getSession, getSession);
```

`lib/auth.ts` 里为此加了一个极简的订阅器：5 个写入点（登录 / 注册 / 刷新 token / 改密 / 退出）统一调 `emit()`，视图自动跟上。之所以必须做成"订阅"而不能在登录页 `setState` 往上抛，是因为**其中两个写入点发生在组件树之外** —— axios 拦截器里的静默刷新和强制下线，那里根本调不到 `setState`。

**一个必须知道的硬约束**：`useSyncExternalStore` 的 `getSnapshot` 在"值没变"时必须返回**同一个对象**（`Object.is` 比较）。每次 `JSON.parse` 出新对象会让 React 判定"每次渲染都变了"，轻则无限重渲染，重则 `Maximum update depth exceeded` 白屏。本项目的 `current` 是模块级变量、只在写入时换引用，满足这个条件；`src/lib/auth.test.ts` 里有两条用例专门钉住它。

**顺手修掉的第二个隐患**：`emit()` 原本是裸的 `for (const l of listeners) l()`。一个订阅者抛错会 ① 中断后续订阅者的通知 ② 把异常冒泡给 `saveSession()` 的调用方。而 `emit()` 是在**存储已经写完**之后调用的 —— 登录页的 `catch` 会误判"登录失败"并弹错误提示，可实际上凭证已落盘。现在逐个 `try/catch`，一个组件坏掉不影响其它人，也不污染调用方。

**回归测试**：`src/lib/authStore.test.tsx` 用真实渲染复现了这条路径 —— 把 `Probe` 换回 `useState` 写法，3 条用例全红（`expected '未登录' to be '已登录:...'`）。这正是当初用户看到的那句话。

### 9.6 真实 bug ②：能看页面，不能发消息

同一个版本里的第二个现象：

```
登录后所有页面正常（知识库、模型列表、分析页都能打开）
唯独发消息失败
```

根因是**鉴权漏了一条通道**。流式对话没法用 axios —— 浏览器端 XHR 拿不到流式响应体（`responseType: 'stream'` 只在 Node 有效），必须用 `fetch` + `ReadableStream` 手写 SSE 解析。而：

> **`fetch` 不经过 axios 拦截器。**

所以请求拦截器加的 `Authorization` 头、响应拦截器做的 401 自动刷新，在流式接口上**全都不生效**。后端按规则回 `401 {"detail":"请先登录"}`，前端把这句话原样弹给用户 —— 看起来像"登录坏了"，实际是"这条链路没带证件"。

这类 bug 的迷惑性在于：轮询类接口（axios）全部正常，只有一条通道是坏的，而且报错文案指向的是"身份"而不是"通道"。

**修法：补一个与拦截器行为逐条对齐的 `authedFetch`**

```typescript
export async function authedFetch(input: string, init: RequestInit = {}): Promise<Response> {
  // ① 发之前先主动刷新（本地判定过期时）
  await ensureFreshToken();
  const first = await send();               // 每次重新取 token，重放时才能拿到新值
  if (first.status !== 401) return first;

  void first.body?.cancel();                // 重放前丢弃旧响应体，否则连接不释放
  const token = await refreshOnce();        // ② 与 axios 拦截器共用同一个单飞 Promise
  if (!token) { forceLogout(); return first; }

  const second = await send();
  if (second.status === 401) forceLogout(); // 新 token 也被拒 = 账号被禁用/密钥轮换
  return second;
}
```

三个细节值得记住：

1. **`refreshOnce()` 必须复用，不能另写一份**。refresh 是轮换的，两条通道各刷一次会把对方的 token 打废。
2. **重放前要 `cancel()` 第一个响应体**。不取消的话浏览器会一直占着这条连接。
3. **每次重发都重新读 token**，不能把第一次的 header 对象拿来复用。

**验证**（真实链路，不是单测推断）：

```
不带 token → HTTP 401  {"detail":"请先登录"}
带 token   → HTTP 200  data: {"type":"meta",...}  → data: {"type":"token","text":"收到"} → done
```

**回归测试**：`src/api/client.test.ts` 5 条。把 `Authorization` 注入换成别的 header 重跑，2 条立刻红。

**两个 bug 合起来看，是一条通用教训**：

> 状态管理里，"写进了存储"和"视图知道了"是两件事；鉴权里，"某个 HTTP 客户端配了拦截器"和"所有出站请求都带了凭证"也是两件事。
> 两者都属于**看起来自动、其实是显式**的地方 —— 只在多通道/多写入点的情况下才暴露。

## 十、迁移：7 步与两个坑

`scripts/auth_migrate.py` 幂等（跑 3 次：第一次执行、后两次全部 `[--] 已迁移过`）。

| 步 | 做什么 |
|---|---|
| 1 | 建 `users` + `audit_logs`（`__table__.create(checkfirst=True)`，不用 `create_all`） |
| 2 | 5 张表加 `owner_id` + 索引 + 显式命名外键 `fk_{table}_owner`（`DO $$` 块兜底） |
| 3 | `DROP INDEX uq_documents_content_hash` → `CREATE UNIQUE INDEX uq_documents_owner_hash` |
| 4 | 引导管理员（密码**就地打印**） |
| 5 | 回填 `owner_id IS NULL` → admin |
| 6 | 结构自查（列/类型/nullable/FK CASCADE/索引/ORM 交叉核对） |
| 7 | 行为自查（savepoint 内造两个用户验证互不可见，然后回滚） |

### 坑 1：asyncpg 把 PG 的 `"char"` 读成 `bytes`

第 6 步的结构自查会读 `pg_constraint.confdeltype` 判断外键的删除行为。PG 里它是 `"char"` 类型，值是 `'c'`(cascade) / `'n'`(set null) / `'a'`(no action)。

但 **asyncpg 返回的是 `b'c'`（bytes）**，于是 `b'c' != "c"` 恒真 → 自查报"外键删除行为应为 CASCADE，实际 b'c'"，而实际上完全正确。

```python
if isinstance(deltype, (bytes, bytearray)):
    deltype = deltype.decode()
```

**这类"自查脚本自己报假警"的坑特别值得记**：它让你怀疑已经正确的代码，浪费的时间比真 bug 还多。

### 坑 2：凭证类输出必须在**产生的那一刻**交给人

第一次跑迁移时，引导管理员的密码是随机生成的，打印在"最后的汇总"里。结果脚本第 6 步就崩了 —— 密码永远丢失，只能写一个 `scripts/auth_set_password.py` 重新设。

修法两条：
1. 在 `bootstrap_admin()` 里**就地打印**，不等汇总；
2. 提供 `scripts/auth_set_password.py`（`--password` / `--from-env` / 交互式 `getpass`），同时刷 `password_changed_at`。

原则：**脚本后半段随时可能失败。凭证、URL、一次性令牌这类"只出现一次"的东西，一产生就交出去。**

## 十三、面试可能问到的六个问题

**Q1：为什么不用 session + Cookie？**
A：两者都能做对。JWT 的收益是"验签不需要存储"（水平扩展不用共享 session 存储），代价是"撤不回来"。本项目用**短 access + 可吊销的 refresh 白名单**取中间态。如果只有一个实例、且需要"立刻踢人"，session + Redis 反而更简单。

**Q2：refresh token 为什么必须轮换？**
A：不轮换的话，被盗的 refresh 可以并行用 7 天，用户和服务端都发现不了。轮换之后，攻击者用一次，真实用户的下一次刷新就失败 —— 异常被暴露。配合"旧 jti 立刻从白名单删除"，重放必然失败。

**Q3：为什么 access token 不查 Redis？**
A：它是每请求都要验的，查一次就 +1 次往返。2 小时的窗口是可接受的取舍。反过来说，如果业务要求"封号立即生效"，那就必须每请求回查（本项目正是这么做的，只是回查的是 users 表的主键，而不是 Redis 白名单）。

**Q4：多租户用参数传 owner 不行吗？**
A：在检索这条链路上不行。那一跳的调用者是 LLM，它只会填 query，不知道也不该知道当前是谁 —— 身份是环境信息。参数化的另一个问题是"总有一个调用点会忘传"，而 ContextVar + 一个 `owner_filter()` 让"忘"变成不可能（不传就走默认的 `true()`，那个分支只有系统内部调用会走到）。

**Q5：为什么越权返回 404 而不是 403？**
A：403 等于承认"这个 id 存在"。用 404/403 的差别可以枚举有效 id。但平台级资源（`/api/metrics`）用 403 —— 那些地址谁都猜得到，不存在枚举问题，用 403 语义更准。

**Q6：审计为什么不用 Langfuse？**
A：Langfuse 记的是"一次运行的内部过程"，会轮转、会过期，且没有"谁对谁做了什么"的结构化字段。审计要的是**事实记录**：账号被删了、邮箱改了，当时那条记录仍然要读得懂 —— 所以 `actor_email` 存快照、`actor_id` 用 `SET NULL` 而不是 `CASCADE`。

## 十四、自测题（先自己答，再看下面的参考答案）

**1.** 有人说"我们把 bcrypt rounds 调到 14 更安全"。这句话缺了什么？
**2.** 用户不存在时为什么要跑一次假哈希？不跑会泄露什么，泄露得比错误文案更严重吗？
**3.** `needs_rehash("garbage")` 应该返回什么？第一版实现为什么返回了相反的值？
**4.** BM25 的 SQL 有三处 owner 条件。只加在 `candidates` 上，会不会"越权"？不会的话，问题是什么？
**5.** 流式对话接口里，`owner_scope` 为什么不能设在接口层？
**6.** 前端并发 5 个请求同时 401，为什么必须"单飞"刷新？各自刷新会发生什么？
**7.** 迁移脚本为什么要在"最后的汇总"之前就把引导管理员密码打出来？
**8.** `actor_id` 为什么用 `ON DELETE SET NULL` 而不是 `CASCADE`？

---

### 参考答案

**1.** 缺"代价"这一半。rounds 每 +1 是耗时翻倍：12→166ms，14→663ms。登录会明显变卡，用户会抱怨甚至改用短密码。安全性从来不是单目标的，**"更安全"必须给出成本**才是一个可决策的说法。另外它没说要重算全库已有哈希 —— 调了常量但老用户还是旧强度（这正是 `needs_rehash` 存在的原因）。

**2.** 防**时序侧信道**。不跑假哈希时：邮箱不存在 1ms 返回，存在但密码错 166ms 返回。响应时间就是"这个账号存不存在"的答案。比错误文案更严重 —— 文案是可以统一的，耗时是**物理事实**，改不掉。而且假哈希必须是格式合法、成本因子正确的真 bcrypt 串，否则 bcrypt 在解析阶段就报错，反而把差距拉得更大。

**3.** 应该返回 `True`（"这个串不合法，下次登录成功时顺手换掉"）。第一版写成 `len(parts) >= 4 and int(parts[2]) < ROUNDS`，`"garbage"` 只有 1 段 → `and` 短路成 `False` → 返回"不需要升级"，`except` 那支永远进不去。教训：**`and` 的短路会吃掉异常分支**，校验类函数的结构判断要独立 `if` + 独立 `return`。

**4.** 不会越权（召回范围是对的），但**排序是错的**。`corpus`（N、avgdl）与 `df`（文档频率）是统计量，只加 `candidates` 会让 IDF 按全库算 —— "别人文档里这个词很常见"会压低我的候选分。不报错、不越权，只是结果悄悄变差，叫**统计量侧信道**。

**5.** 因为接口层返回的是 `StreamingResponse`，`with owner_scope(...)` 在**函数返回时**就退出了；生成器是在返回**之后**才被逐个 `yield` 消费的，那时 ContextVar 已经还原。必须把 `with` 放进生成器内部，让它的生命周期覆盖整个 `async for` 的迭代期。

**6.** 因为 refresh 是**轮换**的。各自刷新时：第一个成功（旧 refresh 作废、发新），第二个还在用旧 refresh → 401，甚至可能把刚拿到的新 token 也判死。最后用户被莫名其妙踢出登录。共享同一个 Promise 就只有一个真正在刷，其余请求等它的结果。

**7.** 因为**脚本后半段随时可能失败**。第一次跑迁移时密码打印在最后汇总里，而第 6 步结构自查就崩了 —— 密码永久丢失，只能另写一个重置脚本救回来。原则：凭证、URL、一次性令牌这类"只出现一次"的东西，**一产生就交出去**。

**8.** 因为 `CASCADE` 会让"删号"变成"抹掉痕迹"——那正好成了滥用的出口。审计表的语义是事实记录：账号被删之后，它做过的**事**仍然要留在账上，所以 `actor_id` 置空、`actor_email` 快照仍在。
