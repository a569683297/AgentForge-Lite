## 1. 三题标准答案

### 题 1：`--network none` 之后，容器内 `curl db:5432` 报什么错？为什么不是 `connection refused`？

**答案**：报的是 **`Could not resolve host: db`**（DNS 解析失败）。
若绕过域名直接用 IP（如 `curl 172.18.0.2:5432`），报的是 **`Network is unreachable`**。

**为什么不是 `connection refused`** —— 这三个错误分别发生在**三个不同的层**：

| 错误 | 发生在哪 | 含义 |
|---|---|---|
| `Could not resolve host` | DNS 解析 | 连名字都换不成 IP |
| `Network is unreachable` | 内核路由 | 有 IP，但本机没有一条通往它的路由 |
| `Connection refused` | TCP 握手 | 包**已经到了**对方主机，但那个端口没有程序在听（对方回 RST） |

`--network none` 给沙箱的是一张**只有 `lo`（回环口，只能自己跟自己说话）的网络栈**：
没有网卡、没有路由表、也没有 Docker 内置 DNS（那个 127.0.0.11 的解析器只在自定义
bridge 网络里才会被注入）。包**根本出不去**，所以永远走不到"端口拒绝"那一步。

**这条差别为什么重要**：`connection refused` 意味着"目标主机活着、我们被允许发起连接，
只是没人接"；而 `network unreachable` 意味着"物理上没有路"。
前者是**策略**的结果（改个防火墙规则就能通），后者是**拓扑**的结果（改策略没用）。

### 题 2：`--memory 256m` 是谁、在什么时刻动手杀进程？api 那边会收到什么？

**答案**：动手的是**内核的 OOM killer**（Out-Of-Memory killer —— 内存耗尽时由内核
强制终止进程的机制），不是 Docker，也不是我们的代码。

**触发时刻**：沙箱这个 **cgroup**（control group —— 内核的资源记账与限额机制，
把一组进程归进一个账本并对账本设上限）的内存用量触到 256MB，且内核无法通过回收
页缓存腾出空间时，立即杀。

**api 侧收到的完整链条**（这也是"错误变文本"契约的价值所在）：

1. 容器内进程被杀 → 容器退出，退出码 **137**（128 + 9，即被 SIGKILL 终止）
2. 容器 stdout 关闭 → `docker` CLI 进程读到 EOF、退出
3. MCP SDK 的读循环结束 → `call_tool()` 抛异常 / 连接已关闭
4. `MCPClient.call()` 的 `except Exception` 分支兜住
5. 返回一段**字符串**：`工具 X 执行失败：MCP server「…」调用异常 …`
6. 这段文本以 tool 消息写回，LLM 看得见，可以自己改口

**关键**：api 不会崩、这一轮对话不会 500。一个沙箱被 OOM 杀掉，
用户看到的是"这个工具暂时用不了"，而不是"整个平台挂了"。

### 题 3：既然已经用 env 白名单不给子进程传密钥了，为什么 `--user 10001` 仍然必需？

**答案**：env 白名单控制的是**投递**，`--user` 控制的是**能力**。

`_base_env()` 只给子进程 `PATH / HOME / TMPDIR` 三个变量 —— 它保证"我们没把密钥
递过去"。但沙箱进程若能以 root 身份运行，它根本不需要我们递：

- 读 `/proc/1/environ`：**PID 1 的完整环境变量**。compose 里 `env_file: .env`
  把 DeepSeek key、Langfuse secret、Harness PAT 全注进了 api 容器环境，
  这份数据就摆在那个文件里，root 随时可取。
- 读 `/app/.env`、`data/` 下的任何文件
- 连 `db:5432`（如果网络没断）、连 `docker.sock`（如果挂进来了）

所以两道防线职责不同：

| 防线 | 挡住什么 | 挡不住什么 |
|---|---|---|
| env 白名单 | 被动继承（"我递给它"） | 主动读取（"它自己去拿"） |
| `--user 10001` | 主动读取（uid 不匹配，`/proc/<pid>/environ` 读不了） | — |
| `--network none` | 横向移动到 db/redis | — |

**一句话**：白名单是**策略**，uid 是**能力**。策略可以被绕过，能力不能。

## 2. 两个机制的分工（速查）

| | namespace（命名空间） | cgroup（控制组） |
|---|---|---|
| 管什么 | **看得见什么、碰不碰得到** | **能用多少** |
| 本项目用到的 | PID / NET / MNT / USER / UTS / IPC | memory / cpu / pids |
| 对应参数 | `--network none`、`--read-only`、`-v …:ro`、`--user` | `--memory`、`--cpus`、`--pids-limit` |
| 缺了会怎样 | 能看见不该看见的东西（密钥、其他进程、宿主文件） | 一个死循环吃满整机 |

**两者互补，缺一个都不叫沙箱**：只有 namespace → 资源被吃光；只有 cgroup → 什么都看得见。

## 3. 本次实际落地的隔离参数

`app/mcp/sandbox.py`（增量 2）会拼出这样一条命令：

```text
docker run -i --rm
  --name agentforge-tool-<id8>
  --label agentforge.tool=<id>
  --network none
  --read-only
  --tmpfs /tmp:rw,noexec,nosuid,size=16m
  --user 10001:10001
  --cap-drop ALL
  --security-opt no-new-privileges
  --memory 256m --cpus 0.5 --pids-limit 64
  -v tool_code:/tool:ro
  agentforge-tool-sandbox:local
  /tool/<id>/server.py
```

| 参数 | 挡住的具体事故 |
|---|---|
| `-i`（不加 `-t`） | 保住 stdio 管道；加 `-t` 会引入 TTY 行尾转换，把 JSON-RPC 报文弄坏 |
| `--network none` | 连不上 `db` / `redis`；无法把数据外传 |
| `--read-only` | 改不了自己的代码；写不了持久文件 |
| `--tmpfs /tmp` | 给一个**可写但易失**的小目录（体积上限 16m，`noexec` 禁止在挂载点执行二进制） |
| `--user 10001` | 读不到 `/proc/1/environ`（题 3） |
| `--cap-drop ALL` | 没有任何内核特权（不能 mount、不能改网络、不能 ptrace） |
| `no-new-privileges` | 不能通过 setuid 程序提权 |
| `--memory / --cpus / --pids-limit` | 内存耗尽、CPU 吃满、fork 炸弹 |
| `-v …:/tool:ro` | 代码只读挂载，容器内改不了自己 |
| **不给任何 `-e`** | `docker run` 不像 `subprocess` 那样继承宿主环境 → 沙箱内 environ 是空的 |

## 4. 这套方案防不住什么（诚实边界）

1. **api 自身被攻破 = 宿主被攻破**。api 挂了 `/var/run/docker.sock`，
   谁能跟这个 socket 说话，谁就拥有宿主 root 权限。沙箱保护的是"用户上传的工具代码"，
   不保护 api。彻底解耦要拆独立 runner 服务（P2-b），当前版本不做。
2. **内核 / runc 逃逸**。容器不是虚拟机，共享同一个内核。内核漏洞层面的逃逸防不了，
   只能靠升级 Docker。
3. **没有出网白名单**。`--network none` 是"完全断网"。若将来要允许工具联网，
   只给网卡是不够的 —— **egress 白名单**（出网白名单，只允许访问指定域名/IP）
   得靠 iptables 或代理实现，不是 `docker run` 一个参数能给的。
4. **不限制磁盘写入总量**。`--read-only` + `--tmpfs size=16m` 已经限制了可写面，
   但 tmpfs 是内存，写满会算进 `--memory` 配额 —— 这条由增量 3 的验收脚本实测确认。

### 一处当场更正的决策

原计划入口用 `python -I`（隔离模式），实测后改为 `-E -s -B`：

- Python 3.11 起，`-I` **隐含 `-P`** —— 不把脚本所在目录放进 `sys.path`
- 实测（3.13.15）：`-I /tmp/ptest/x.py` 的 `sys.path` 里没有 `/tmp/ptest`；
  `-E -s` 有
- 单文件工具不受影响，但增量 6 的 zip 多文件形态**必须**能同目录 import
- 结论：用 `-E -s -B`，隔离目的（忽略 PYTHON* 环境变量、不加载 user site、不写 pyc）
  一个不少，同时不给后续留坑

`Network is unreachable` 而不是 `Connection refused`，与题 1 的答案一致 ——
包**根本没有出口**。

**⑥ 架构验证：`docker run -i` 能否承载 MCP 握手**（增量 0 之外额外做的一次，
因为它若不成立，整个方案要重来）

用一个最小 MCP server + 官方 SDK 的 `stdio_client`，`command` 设成 `docker`：

```text
tools  = ['echo_word']
result = ['沙箱通了 | uid=10001']
耗时   = 2.05s（含容器冷启动）
```

`uid=10001` 就是证据：这次工具调用**真的在另一个容器里执行**，不是宿主进程。
`MCPClient` 只需要把 `command` 从 `sys.executable` 换成 `docker`、`args` 换成隔离参数，
**代码零改动**。增量 2 可以照此推进。
