# Trace 时间线：改为「以提问为单位」

**日期**：2026-10-20
**触发**：使用反馈 —— "他把所有的提问都融合成一个时间线，不能明确去获取某一次提问的具体时间线"
**结论**：改造完成，左侧每次提问一行（带提问原文），右侧是该次的瀑布图，可按类型筛选。

---

## 1. 先澄清一个事实：分组本来就是对的

先说清楚，免得后续动作建立在错误前提上。

后端 `list_traces()` 一直是**按 `traceId` 分组**的，而 `traceId` 的生成规则是
「一次 `run_agent` 调用 = 一条 trace」。实测 7 天窗口 raw 数据的结构：

```
trace 738cbe936fb6   run_agent > agent-plan > tool:demo_tools_days_until > tool:inventory_query_inventory > tool:current_time > agent-answer
trace 181abe54e839   run_agent > agent-plan > tool:inventory_query_inventory > agent-answer
trace bea3867b7fd4   run_agent > agent-plan > tool:demo_tools_days_until > agent-answer
```

三次提问、三条 trace、三个 `sessionId` 各自独立 —— **数据层没有"融合"**。

那"看起来融合"是怎么来的？三个原因叠在一起：

### 根因 ①：列表里没有"身份"，20 行长得一模一样

改造前是一个下拉框，每行只有 `时刻 · run_agent · 耗时`：

```
17:24 · run_agent · 4100ms
15:29 · run_agent · 2624ms
15:11 · run_agent · 1216ms
```

`run_agent` 是根 span 的**固定名字**，每次调用都一样。7 天里 20 次提问在下拉里
除了时间没有任何区别 —— 用户无法回答"哪一条是我问年假那次"。
这不是排版问题，是**缺少身份标识**。

### 根因 ②：对话被调试运行淹没了

同一个 Langfuse 项目里混着三类运行。实测 7 天窗口的分布：

| 类型 | 根 span 名 | 条数 |
|---|---|---|
| 真实对话 | `run_agent` | 42 |
| 评测判分 | `eval-judge` | 120 |
| 检索检查器手工查询 | `retriever_inspect` | 49 |

按时间取前 20 条，`run_agent` 会被 `eval-judge` 和 `retriever_inspect` 挤出去。
更极端的实测：某次在检索检查器上连点几次之后，最近 200 个 span 组成了
**77 条 trace，全部是 `retriever_inspect`**，一条对话都没有（见 §7 的验证记录）。

### 根因 ③：拿不到提问原文（最硬的一条）

这是三个里唯一无法在展示层解决的，单独展开。

## 2. 硬约束：Langfuse 的实时接口不返回 input

Trace 页走的是 `GET /api/public/v2/observations`（选它的理由：实时、无紧配额、
支持 `?traceId=` 精确过滤）。实测它返回的**完整键集**：

```
bookmarked, endTime, environment, id, inputPrice, isRootObservation, latency,
level, modelId, name, outputPrice, parentObservationId, projectId, public,
sessionId, startTime, statusMessage, timeToFirstToken, totalPrice, traceId,
type, userId, version
```

**没有 `input`，没有 `output`，也没有 `metadata`。** 提问文本不在里面。

三条备选路线都实测过：

| 路线 | 实测结果 | 为什么不用 |
|---|---|---|
| v2 `/observations/{id}` 单条详情 | **404**（端点不存在） | — |
| v2 `/traces/{id}` | **404**（端点不存在） | — |
| v1 `/public/traces/{id}` | 200，`input = {"user_input": "距离2027年10月1日还有几天？..."}` | `_deprecation` 写明 **2026-11-16 下线**；且一次只能查一条（20 条 trace = 20 次请求） |

> 关于 v1：它确实带 input，用它能让历史对话立刻显示提问。但这是
> **把功能建在一个 27 天后必然消失的端点上**。届时要推倒重做，而且中间
> 那段时间还得为"每条 trace 多打一次 HTTP"付账。

**第四条路：自己的库本来就有提问原文。** 只是一直没和 trace 对上号。

## 3. 方案：messages 表加 trace_id

一次提问 = 一条 trace = 一条 `role='user'` 的消息。把 Langfuse 的 trace id
写到那条 user 消息上，Trace 页一次 SQL 批量反查即可。

```
用户发送
  → run_agent 开 span，current_trace_id() 拿到 7d217eef...
  → 跑图（LLM + 工具 + 检索，子 span 自动挂着）
  → 落库：append_messages(..., trace_id=7d217eef...)
            ↓ 只写在那条 user 消息上
  [messages] 2359 | user      | 7d217eef... | 员工累计工作满 2 年的，年假有几天？
             2360 | assistant | NULL        | （空，带 tool_calls）
             2361 | tool      | NULL        | [1] 来源：FAQ-常见问题.md ...
             2362 | assistant | NULL        | 累计工作满 2 年的员工，年假为 5 天。
```

Trace 页读的时候反过来：

```
list_traces(kind="dialog")
  → v2 observations（拿 span 明细）
  → 按 traceId 分组，算 kind / 耗时 / span 数
  → 按 kind 过滤 → 按时间倒序 → 截断
  → SELECT trace_id, content FROM messages
      WHERE trace_id = ANY(这几十个 id) AND role = 'user'
  → 每行补上 question
```

### 三个刻意的决定

**① 只有 user 消息带 trace_id。**
同一轮的 assistant / tool 消息若也挂同一个 id，`WHERE trace_id IN (...)` 会
查出 3~4 行，把"一次提问"变成"三条记录"，上层还得按 role 去重一次。
让 user 消息独占，语义最干净。

**② 取 `current_trace_id()` 的位置在 span 内部、落库在 span 外部。**
它读的是"当前上下文里的活动 span"，出了 `with` 就是 None；而落库是副作用，
刻意排在 span 之外（不占"用户等待"的延迟，与原有设计一致）。所以中间用一个
局部变量传递。

**③ 不回填历史数据，也不编造。**
改造前的消息写入时根本没取过 trace id，无从回填。老 trace 显示「（未记录提问）」
斜体灰字 —— 这是**如实呈现**。若用 `name` 或 session 标题顶替，用户会以为
看到了提问原文，而实际上看到的是别的东西。

## 4. 顺带修掉的一处误导：降级被染成红色

改造过程中截图发现：某次真实对话的 `rerank` 条是**红色**的，看起来像故障。

查下去发现原因：那次重排 3006ms，超过 `rerank_timeout_s=3.0` → 降级，
Langfuse 记的是 `level="WARNING"` + `status_message="重排超时降级（返回融合序）"`。
而旧逻辑是：

```python
"error" if level == "ERROR" or span.get("statusMessage") else "ok"
```

**"有 statusMessage 就算 error"** —— 于是一次**降级**被染成和 500 错误一样的红。

这两件事的处置完全不同：降级要调超时 / 缩候选池；错误要去看堆栈。
混在一起既让人排查不存在的故障，又让真正的错误失去区分度。

改成三态（`ok` / `warning` / `error`），并把 `status_message` 透传到前端
（鼠标悬停可见原因）。同时 `_has_error()` 只认 `level == "ERROR"` ——
否则列表上几乎每条都带红点（重排降级在容器里是常态）。

> 注意：这**不是**本次改造引入的问题，是一直存在的既有误导，只是以前
> 一次只显示一条 trace、且大家都盯着 rerank 的数字看，没人注意到颜色。
> 重排超时这个问题本身（容器内 2.4~3.0s 贴着 3s 线）仍未解决，见 memory 里的三条待选方案。

## 6. 怎么用

1. 打开「Trace 时间线」，默认就是「对话」类型 + 最近 24 小时。
2. 左列每次提问一行：`10-20 17:50:06 · 6.17s · 9 span` + 提问原文（最多两行）。
3. 点任意一行 → 右栏显示这一次运行的瀑布图，横轴是**这一次内部**的相对毫秒。
4. 想看检索检查器/评测的运行，切左上角类型下拉（带各类条数）。
5. 黄色条 = 降级（悬停看原因），红色条 = 真错误。

## 8. 已知限制（如实列出，不是待办）

**① 改造前的历史对话没有提问原文。**
`messages` 里那些行的 `trace_id` 是 NULL，无从反查。页面上显示「（未记录提问）」。
这是**永久状态**，不会因为时间推移变好 —— 除非手工把历史 trace 和消息对上
（时间就近匹配），而那是猜，不做。

**② 列表可能不完整（已截断）。**
单次最多拉 200 条 observation。24 小时窗口里搜检检查器点几次就能占满
（每次 5 个 span）。截断时会显示「（已截断）」，悬停说明"较早的运行可能不在列表里"。
**没有擅自调大上限**：这是"刷新更快"与"历史更全"的取舍，影响 Langfuse 带宽，
需要时再定。

**③ 评测运行可能出现在「对话」里。**
评测也会调 `run_agent`（`persist=False` 不落库），它的根 span 名同样是
`run_agent`，所以会被归到 `dialog`。区别是 `question` 为 `None`。
没有按 `metadata.persist` 细分 —— v2 不返回 metadata，硬分会引入猜测。

**④ 重排超时降级仍然存在。**
本次只是把它**显示对了**（黄色 + 原因），没有解决性能问题。
容器内 2.4~3.0s 贴着 3s 超时线，8 次采样 2 次降级。三条备选方案
（调 `RERANK_TIMEOUT_S` / 缩小候选池 / 加 CPU 或换小模型）仍待拍板。
