# 用户上传本地工具（MCP Server）：功能设计与实现

> 日期：2026-10-20　状态：**已实现并验收通过**
> 前置文档：`docs/工具沙箱-隔离原理与自测答案-2026-10-20.md`（隔离原理与六题答案）
>
> **一句话**：用户可以上传一个 `.py` 写的 MCP Server，平台把它跑在隔离容器里，
> 自动发现它的工具并接进注册表 —— 下一轮对话 LLM 就能调用，**Agent 引擎零改动**。

---

## 一、先说边界：这个功能能做什么、不能做什么

### 能

- 上传**单个 Python 文件**（≤256KB），它必须符合 MCP Server 形态
- 自动发现其中全部工具，注册进 `ToolRegistry`，工具名带 `<名字>_` 前缀
- 试跑任意一个工具（走与 Agent 完全相同的调用路径）
- 启用 / 停用 / 重连 / 删除
- **重启不丢**：api 重启或容器重建后，按库里的状态自动拉起
- 全程跑在隔离容器里：无网络、非 root、只读根文件系统、有内存/CPU/进程数上限

### 不能（这些是设计边界，不是缺陷）

| 不能 | 原因 |
|---|---|
| 依赖第三方 pip 包 | 沙箱镜像里只有标准库 + `mcp`。装包需要联网与构建期介入，属后续形态 |
| 访问本机的文件/服务 | 沙箱 `--network none`、只读文件系统 —— "你机器上的东西"到不了容器里 |
| 多文件 / zip 上传 | 当前只接受单文件；zip 要额外防**路径穿越**（zip slip：压缩包内 `../` 逃出解压目录），属增量 6 |
| 联网调外部 API | 同上。真要联网得给出网白名单（egress），不是一个参数能解决的 |
| 多租户隔离 | 本平台无鉴权、单用户。谁的 API 谁的工具，没有"用户 A 看不到 B"这层 |

## 二、端到端流程

### 2.1 上传（一次 HTTP 请求做完 6 件事）

```
用户浏览器
  │  POST /api/tool-servers   (multipart: file + name + display_name + description)
  ▼
[1] 开关检查     settings.tool_sandbox_enabled=false → 503（在读请求体之前拒绝）
[2] 读文件       await file.read(MAX+1) —— 多读 1 字节即可判超限，避免整个大文件进内存
[3] 校验         validate_name / validate_code（纯函数，语法用 compile 解析但不执行）
[4] 落盘         <工具根>/<uuid>/server.py（先写 .tmp 再 replace，原子替换）
[5] 卷可见性预检  docker run --rm <隔离参数> -c "exists('/tool/<uuid>/server.py')"
[6] 入库 + 拉起   INSERT tool_servers → MCPManager.add_server_held(spec)
                 → docker run -i（长驻任务持有）→ 握手 → tools/list → register(stub)
  ▼
202 { status, connected, tools[], tool_count, last_error }
```

### 2.2 调用（与 Agent 完全同一条路径）

```
POST /api/chat  →  plan 节点：get_tools_schema()   ← 每轮现取，不是启动时缓存
                →  LLM 决定调 demo_tools_text_stats
                →  execute 节点：execute_tool(name, args)
                →  注册表查到 stub（本进程内的一个 async 函数）
                ── 边界 1：写进 docker CLI 的 stdin ──
                →  [dockerd] → 容器内 python 读 stdin → 执行工具 → 写 stdout
                ── 边界 2：同一个 id 的响应回到 stub ──
                →  字符串 → tool 消息 → 回到 plan 节点
```

**为什么 Agent 引擎不用改**：`MCPClient` 只认 `MCPServerSpec(command, args, ...)`。
D27 时 `command=python`，现在 `command=docker`，对它来说都是"起个子进程聊 JSON-RPC"。

### 2.3 重启恢复

```
api 启动
  → sweep_orphans()        清掉上次残留的容器（按 --label agentforge.tool 精确匹配）
  → restore_active()       SELECT * FROM tool_servers WHERE status='active'
        ├─ 代码文件缺失 → 标 failed + 写明原因（卷被清过）
        └─ 逐台 add_server_held()，单台失败只影响自己
```

## 三、数据模型：`tool_servers`

| 列 | 类型 | 作用 | 为什么需要（不是"顺手加的"） |
|---|---|---|---|
| `id` | uuid | 主键 + 磁盘目录名 | 与用户起的名字解耦：改名不影响文件位置 |
| `name` | varchar(32) **唯一** | 机器名 / 工具名前缀 / 注册表 source | 唯一约束必须在**库上**：应用层"先查再插"挡不住并发，而两条同名会让 `unregister_source` 一次摘掉两台 |
| `display_name` | varchar(100) | 给人看的名字 | 用户不该被迫用 `demo_tools` 这种名字 |
| `description` | text | 说明 | 只给人看。**不发给 LLM** —— 工具描述在代码里，由 `tools/list` 现取 |
| `entry_file` | varchar(255) | 相对路径 `<uuid>/server.py` | 存绝对路径换机器就失效（本机/容器两种形态路径不同） |
| `sha256` | varchar(64) | 代码指纹 | 同名重传时，回答"容器里跑的是不是刚传的那份"。日志里唯一的线索 |
| `size_bytes` | integer | 字节数 | 排障与展示 |
| `status` | varchar(16) | active / disabled / failed | **重启恢复的唯一依据**；也是"该不该跑"的意图 |
| `last_error` | text | 最近失败原因 | 失败必须能看见，否则用户只能对着空列表猜 |
| `created_at` / `updated_at` | timestamptz | 时间 | 排序与排查 |

**运行态不入库**：`connected` / `tools` / `tool_count` 来自 `MCPManager` 的实时状态。
库里的是"意图"，内存里的是"事实" —— 两者不一致正是要看见的信号（见 §6）。

## 四、接口契约

| 方法 | 路径 | 语义 | 主要返回 |
|---|---|---|---|
| GET | `/api/tool-servers` | 列表（持久 + 运行态） | `{total, servers[]}` |
| POST | `/api/tool-servers` | 上传并接入 | **202** + 对象（`connected` 可能为 false） |
| POST | `/api/tool-servers/{id}/reconnect` | 重新拉起 | 对象 |
| PATCH | `/api/tool-servers/{id}` | `{"status":"active"\|"disabled"}` | 对象 |
| POST | `/api/tool-servers/{id}/call` | 试跑某工具 | `{tool, output}` |
| DELETE | `/api/tool-servers/{id}` | 删除（断开+摘工具+删代码+删记录） | 204 |

### 错误码约定

| 码 | 含义 | 触发 |
|---|---|---|
| 400 | 用户输入问题 | 名字不合法、非 `.py`、超 256KB、非 UTF-8、含 NUL、语法错、参数非 JSON |
| 404 | 没有这条记录 / 工具不属于这台 server | 含"越权调用内置工具" |
| 409 | 名字被占 | 与文档去重同一语义：不是错误，是状态冲突 |
| 503 | 部署没配好 | 沙箱未启用、docker 不可用、镜像缺失、卷映射错 |

### 为什么上传返回 202 而不是 201

"已接受" ≠ "已可用"。202 的真实含义是：**记录和文件都落好了，但它可能没连上**
（用户代码里没写 `server.run()`、或者 import 挂了）。

此时用户能在列表里看到它、能看到 `last_error`、能改能删。
如果返回 201，前端会以为"成了"，然后对着一个空工具列表发懵 —— 更容易走错路。

## 五、隔离：参数与威胁模型

完整参数清单是 `app/mcp/sandbox.py:isolation_flags()`，**验收脚本用的是同一份**。

| 参数 | 挡住的具体事故 |
|---|---|
| `-i`（不加 `-t`） | 保住 stdio 管道；`-t` 会引入行尾转换，弄坏 JSON-RPC |
| `--network none` | 连不上 `db`/`redis`；无法外传。错误是 `Network is unreachable`，不是 `refused` |
| `--read-only` | 改不了自己的代码、留不下持久文件 |
| `--tmpfs /tmp:rw,noexec,nosuid,size=16m` | 唯一可写处，且不可执行、上限 16MB（算进内存配额） |
| `--user 10001:10001` | 读不到 `/proc/1/environ`（那里有全部密钥） |
| `--cap-drop ALL` + `no-new-privileges` | 无内核特权、不能提权 |
| `--memory 256m --cpus 0.5 --pids-limit 64` | 内存耗尽、死循环、fork 炸弹 |
| `-v <卷>:/tool:ro` | 代码只读挂载 |
| 不给任何 `-e` | `docker run` 不继承宿主环境 → 沙箱内 environ 是空的（11 个基础变量，零密钥） |

### 明确的剩余风险

1. **api 挂了 `/var/run/docker.sock`** → api 被攻破 = 宿主被攻破。
   沙箱保护"用户上传的工具"，不保护 api 自身。彻底解耦要拆独立 runner 服务（P2-b）。
2. 容器共享宿主内核，内核/runc 逃逸防不了。
3. 没有出网白名单（现在是"完全断网"）。

## 六、状态语义：三个字段，六个组合

`status`（库里：该不该跑）× `connected`（运行态：跑没跑）的组合，各自含义不同：

| status | connected | 含义 | 前端显示 | 用户该做什么 |
|---|---|---|---|---|
| active | true | 正常 | 运行中 | 无 |
| active | false | **该跑但没跑**（容器崩了/重启失败） | 该跑但没连上 | 点重连 |
| failed | false | 拉起失败（代码有错/镜像缺失） | 启动失败 | 看 `last_error` 改代码后重连 |
| disabled | false | 用户主动停用 | 已停用 | 无（需要时再启用） |
| failed | true | 理论上不出现（重连成功会写回 active） | — | — |
| disabled | true | 理论上不出现（停用会先断开） | — | — |

**为什么不合并成一个 status**：合并之后"该跑却没跑"和"用户主动停了"长得一样，
而这两个的处置方式完全相反 —— 前者要修，后者不要动。

## 七、六个关键设计决策（含踩坑记录）

### 1. 用 sibling 容器，不用 `subprocess`

沙箱的必要条件是"代码不能跑在本进程的文件系统与网络里"。subprocess 做不到。
`docker run -i` 把 docker CLI 变成一根管道，`MCPClient` 零改动复用。
（验证见前置文档 §5 第 ⑥ 条：`uid=10001` 证明调用真的进了另一个容器。）

### 2. 命名卷，不能用 `./data` 那种 bind mount

**踩到了**：`docker run -v` 的左边由**宿主 daemon** 解析，不是 api 容器里的路径。
更隐蔽的是 **compose 会给卷加项目前缀**（`agentforge-lite_tool_code`），
而 api 容器内写的是 `-v tool_code:/tool` —— docker 找不到这个卷，
就**静默新建了一个空卷**挂进去。

症状：容器起得来，握手立刻断（`MCPError: Connection closed`），
日志里没有任何"找不到文件"的提示（因为 python 在容器里报的错进的是 stderr 日志，而客户端只看到连接关闭）。

修法两层：
- `docker-compose.yml` 里给卷写死 `name: agentforge_tool_code`，与 `TOOL_CODE_VOLUME` 一致
- `sandbox.can_see()`：上传时用**同一个沙箱镜像**探一下文件是否可见，
  把"卷映射错"从"用户代码有问题"里分出来，返回 503 + 明确原因

### 3. 接入必须发生在一个长驻任务里（anyio cancel scope）

**踩到了**：第一版在 HTTP 请求里直接 `await add_server(spec)`。
上传成功、工具注册成功，但**下一调用就 `Connection closed`**，容器却还活着。

根因：MCP SDK 内部用 anyio 的任务组 + **取消作用域**，而 anyio 有一条硬规则 ——
**取消作用域必须由进入它的那个任务退出**。在请求任务里进入，请求一结束任务被取消，
传输随之被拆。收尾时还会抛
`RuntimeError: Attempted to exit a cancel scope that isn't the current task's`。

修法：`MCPManager.add_server_held()` 起一个**只为这台 server 存在**的任务，
在任务里 connect，然后 `await stop.wait()` 挂住；停止时只置事件，让它自己收尾。
（D27 的静态 server 没这个问题，因为它们在 lifespan 里接入 —— lifespan 是一个活到进程结束的任务。）

### 4. 上传返回 202，失败也是"成功"

见 §4。核心：把"用户代码的问题"留在用户能看见、能改的位置，而不是变成 500。

### 5. 工具名必须加前缀 + 保留名必须拒绝

- 前缀：两台 server 都可能叫 `search`，而 `register` 撞名会 `raise ValueError`
- 保留名（`local`/`inventory`/`harness`）：`unregister_source(source)` 是**按 source 整批摘工具**的，
  用户叫 `local` 的话，删他的工具会把项目内置工具一起摘干净

### 6. 沙箱入口用 `-E -s -B`，不用 `-I`

Python 3.11 起 `-I` **隐含 `-P`**（不把脚本所在目录放进 `sys.path`），
会堵死后续 zip 多文件形态的同目录 import。实测：`-I` 下 `/tmp/ptest` 不在 `sys.path`，`-E -s` 在。

## 八、运维手册

```bash
make sandbox                 # 首次必跑：构建沙箱镜像（联网装 mcp SDK）
docker compose up -d --build # 起全栈
uv run python -m scripts.tool_server_migrate   # 建表（幂等）
uv run python -m scripts.tool_sandbox_verify   # 六项隔离验收
```

**部署前置条件**（缺一个都会有明确报错，不会静默降级）：
1. `agentforge-tool-sandbox:local` 镜像存在
2. api 容器挂到 `/var/run/docker.sock`
3. `TOOL_SANDBOX_ENABLED=true`
4. 卷名三处一致：`docker-compose.yml` 的 `volumes.tool_code.name`、`TOOL_CODE_VOLUME`、config 默认值

### 排障表

| 症状 | 最可能的原因 | 怎么确认 |
|---|---|---|
| 上传返回 503「镜像不存在」 | 没跑 `make sandbox` | `docker image ls \| grep tool-sandbox` |
| 上传返回 503「卷映射不正确」 | 卷名三处不一致 | `docker volume ls \| grep tool_code` |
| `connected=false` + `Connection closed` | 代码没写 `server.run(transport="stdio")`，或 import 挂了 | `docker compose exec api cat <stderr_log 路径>` |
| `failed` + `RuntimeError ... cancel scope` | 用了 `add_server` 而不是 `add_server_held` | 看 `manager.py` 的调用点 |
| 容器残留一堆 | api 被 `kill -9` | `docker ps -a --filter label=agentforge.tool`，重启会自动清扫 |
| 工具在 `/api/tools` 里但调用总失败 | server 已断但工具还在（半截状态） | 看 `/api/tool-servers` 的 `connected` |
