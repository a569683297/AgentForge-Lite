## Q1 · 组件选型：为什么不用 antd Select？

> 背景名词：**Popover** = 点一下某个元素、在它旁边浮出一块自定义内容的面板
> （antd 组件；Select 的展开列表其实就是它的特化形态）。
> **dropdownRender** = antd Select 的逃生舱口：允许你用自定义内容**替换**整个下拉面板。

**L1**：我们最终的面板里有四样东西：分组标题、每项双行（显示名 + 模型标识小字）、
右侧类型标签、**底部固定一行**「配置自定义模型」。这四样里，哪一样是 Select 的
默认 option 模型**表达不了**的？为什么？

**L2**：其实 antd Select 也有 `dropdownRender`，可以用它硬做出任意面板——
所以"Select 做不到"这个说法**不准确**。那我们最终选 Popover + 自定义面板的理由
更准确的说法是什么？（提示：想想 Select 的 `value` / `options` / 搜索 / 键盘导航
这些能力里，我们真正用到了几个。）

**L3**：这个选择有代价：Popover 的自定义面板**失去了 Select 自带的键盘导航**
（方向键上下移动、回车选中）。当前实现里"键盘可达"到什么程度？（提示：看每行的
DOM 标签）如果要补齐方向键导航，改造点在哪？

<details><summary>参考答案</summary>

**L1**：底部固定行（以及分组标题、双行结构、标签）——Select 的 `options` 数据模型是
"一组可选项"，天然没有"与选项并列的非选项内容"的概念。分组虽然可以用 `options`
的 group 结构表达，但双行 + 标签 + 底部固定行都超出了它的表达能力。

**L2**：准确的说法是**语义借壳**问题：用 Select + dropdownRender 时，Select 的
`value`/`options`/搜索/allowClear/键盘导航**几乎全部作废**（我们不需要搜索、
不需要多选），实际是"借 Select 的壳装一个完全自定义的面板"。而 Popover 的语义
就是"按钮 + 浮层"，与我们的交互**一一对应**——组件语义匹配是最诚实的选型理由。
（此题的用意：结论不变，但理由必须站得住——"做不到"是错的，"语义不匹配"是对的。）

**L3**：每行是原生 `<button>`（代码里 `ModelRow` 用的是 `<button>`），所以
**Tab 键能逐行聚焦、回车/空格能触发**——"键盘可达"已经满足（无障碍的底线）。
缺的是"方向键导航"（↑↓ 移动焦点 + Esc 关闭）这类**富交互**。
补齐的改造点：Popover 面板上挂 `onKeyDown`，维护"当前高亮行"的索引 state，
在行上做 `tabIndex`/`ref.focus()` 管理。（当前不做的原因：这是鼠标为主的
桌面工具，成本收益不划算——但要知道代价是什么。）

代码定位：`frontend/src/components/ModelSwitcher.tsx`（面板与 ModelRow）。
</details>

## Q2 · 会话级记忆的三个语义

> 背景名词：**会话级记忆** = 模型选择"按会话各记各的"（拍板方案，§4.2）——
> 每个会话记住自己用的模型；新会话继承最近一次选择；存储在前端 localStorage。

**L1**：`resolveModelForSession(sessionId)` 的优先级链是什么？"没有记录"时会落回哪一级？

**L2**：为什么 `null`（默认通道）必须是一个**合法状态**，而不是"删掉记录"来代
表"默认"？构造一个操作序列，展示两者混同后会出什么错。

**L3**：done 时 `onModelUsed(session_id, requestModelId)` 的"补记"解决的是哪个
具体场景？如果不补记，用户会看到下拉框显示"错误的模型"——把这个操作序列写出来。

<details><summary>参考答案</summary>

**L1**：三级——① 该会话自己的记录（by-session 表）→ ② 最近选择（last）→
③ 都没有则 `null`（默认，= 不传 model_id 走主备链路）。
`sessionId` 为 undefined（/chat 新会话页）时直接看 ②。

**L2**：关键区别：**"用户显式选择了默认"** 与 **"用户没做过选择"** 是两种事实，
行为不同（前者要让"最近选择"也变成默认，后者要保持原最近选择）。
混同（用"删记录"表示切回默认）会出的错：
> 用户在会话 A 选了 X（last=X）→ 在 A 里切回"自动降级"（若实现成删记录，
> last 仍是 X）→ 打开**新会话** → 继承 last=X（**错**：用户最近做的选择明明是
> "默认"，新会话应当继承默认）。
我们的实现：`rememberModel(sid, null)` 删除该会话记录 **并且**把 last 置 null ——
两个动作都做，因为"最近选择"服务的是另一条路径（新会话继承）。

**L3**：场景——**/chat 新会话页里选 X**（此时没有 sessionId，只写进了 last）→
发问 → 服务端建会话 S → 之后用户在别的会话里把模型切成 Y（last=Y）→ 回到 S：
resolve(S) 时 S 没有自己的记录 → 落回 last=**Y** → 下拉显示 Y，
但 S 这一轮明明是用 X 发的问。
补记（done 时把"发问用过的 X"写进 bySession[S]）把 S 的选择**钉住**，
从此不随 last 漂移。注意补记只对**显式选择**做（`if (requestModelId)`）——
"默认"不补记，否则会把"默认"钉死成某个具体模型，丧失继承语义。

代码定位：`frontend/src/lib/modelMemory.ts` + `frontend/src/App.tsx`（handleModelUsed）
+ `frontend/src/pages/ChatPage.tsx`（done 分支）。
</details>

## Q3 · 归因覆盖 bug（本阶段最有价值的一题）

> 背景：归因"本轮由 XX 回答"的数据 `model_used` 只在**响应/done 帧**里，
> **不落库**（messages 表没有这一列）。

**L1**：首轮问答时，"本轮由 XX 回答"一开始在屏幕上**出现不了**——描述完整的
事件链（从 done 帧到达开始），指出哪一步把归因弄丢了。

**L2**：修复为什么是"接力"（pendingAttributionRef），而不是"done 后不再重读历史"？
重读有什么**不可替代**的价值？

**L3**：这个 bug 的通用模式是什么？（提示：什么属性的信息会撞上这个坑）
未来再加"只存在于实时事件流里"的信息时，你的检查清单第一项是什么？

<details><summary>参考答案</summary>

**L1**：事件链——
① done 帧到达：`patchAssistant({ modelUsed })` 给**占位气泡**写上归因（此刻内存里是对的）；
② 同一处理器里 `navigate('/chat/:id')`（首轮建立新会话，URL 要切换）；
③ URL 变化 → 组件的 `useEffect([sessionId])` 触发 → `getSessionMessages()` **重读 PG**；
④ `setMessages(fromHistory(history))` —— **全量替换**消息列表：占位气泡（临时 id）
被 PG 版消息（真实 id）替换，而 PG 里没有归因列 → **modelUsed 丢失**。
所以屏幕上永远只显示重读后的"无归因版"。

**L2**：重读的价值：让**屏幕 == 落库**（S2 的核心承诺："done 后哪怕立刻刷新，
看到的也是完整落库版本"）。重读还兜住了流式过程中的丢帧/reset 边界——
以 PG 的存储版本为准是最终一致性锚点。取消重读 = 为了一个显示字段放弃一致性，
是拿大目标换小目标。而接力只补一个字段，两个目标都保住。

**L3**：通用模式——**"只存在于实时事件流、不在持久层"的信息，都会撞上
"navigate → 历史重读 → 全量替换"这一关**（本例：modelUsed；将来的例子：
token 用量、耗时、重试次数……）。检查清单第一项：
**"这个信息存进 PG 了吗？没有 → 它是怎么活着穿过重读的？"**
（如果连"穿过"都不需要——比如它本就该只在当前气泡上闪现——那也要显式写下这个决定，
而不是让它静默消失。）

代码定位：`frontend/src/pages/ChatPage.tsx` 的 `pendingAttributionRef`（写入在 done、
消费在 history effect）+ `frontend/src/components/MessageList.tsx`（渲染）。
</details>

## Q4 · 配置弹窗的两个设计与验收方法

**L1**：编辑模型时，API Key 输入框是**空的**（连打码值都不回显）——为什么这是
最不容易出错的形态？（提示：从 PATCH 契约"留空=不修改"倒推。）

**L2**：编辑态点「测试连接」时，**什么时候测表单值、什么时候测已保存的配置**？
为什么必须分叉？如果不分叉（一律测表单值），用户会遇到什么**误导性**的失败？

**L3**：怎么**证明**"请求真的带着 `model=fake-model` 打到了假端点"，而不是只看
UI 上的归因文字？脚本还断言了 `stream=true`——这一条在防什么？

<details><summary>参考答案</summary>

**L1**：因为表单提交语义是"**留空 = 不修改 key**"。如果回显任何值（哪怕打码值
`sk-***c4`），用户误改一下再提交就会造成灾难（要么把打码值当新 key 存进去，
要么以为自己在改 key 实际没改）。空输入框 + 一句提示"当前：sk-***c4（留空 = 保持
原 key 不变）"是最不会出错的形态：**key 的修改必须是用户的明确动作**（重新输入），
而不是"编辑别的字段时的副作用"。

**L2**：分叉条件 `editing && !form.api_key`：
- 编辑态且 key 留空 → 测**已保存配置**（`testSavedModel`）。因为"留空=不修改"
  下**表单值 ≠ 真实配置**（真实 key 在库里）；拿空 key 的表单值去测，
  对需要 key 的端点必然 401 → 用户看到"连接失败"，但配置其实是好的——**这是
  系统在撒谎**（用了一个不等于真实配置的输入去代表真实配置）；
- 填了新 key（想换 key）或新建态 → 测表单值（测的正是用户要保存的那一份）。
测试按钮的信条：**"测的东西必须是用户将要使用/正在使用的那一份配置"**。

**L3**：假端点 v2 在**另一个进程**里记录"最后收到的请求"（`GET /last` 返回
`{model, stream}`）——这是**独立第三方视角**的网络层证据，和 UI 上后端的
`model_used` 是两个互相独立的来源。两源互证才排除"UI 自说自话"。
`stream=true` 断言的是**链路的形态**：证明这次走的是流式端点（如果哪天链路
悄悄退化成非流式，这个断言会红——它是"悄悄退化"的守卫）。

代码定位：`frontend/src/components/ModelConfigModal.tsx`（handleTest 的分叉）
+ `/tmp/fake_openai_endpoint.py`（/last）
+ `/Users/779369901qq.com/.workbuddy/binaries/node/workspace/af-model-switch-verify.mjs`（⑪）。
</details>
