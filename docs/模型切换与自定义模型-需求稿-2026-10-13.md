## 一、需求描述（用户视角）

### 1.1 一句话

把右上角那个"只读假下拉"变成**真正的模型选择器**：能看到有哪些模型、能选、能自己添加/管理模型（含自定义的任意模型）。

### 1.2 参考图逐元素拆解

对你给的截图逐元素过一遍——**哪些照做、哪些换一种表达、哪些不做**（诚实标注，不做假的）：

| 参考图元素 | 我们的处理 | 说明 |
|---|---|---|
| 模型列表 + 当前选中打勾 | ✅ **照做**（核心） | 下拉展开列出可选模型，当前项打勾 |
| 「配置自定义模型」底部入口 | ✅ **照做**（核心） | 点开配置弹窗，管理自定义模型 |
| 免费 / 折扣 / 订阅标签 | 🔁 **换表达**：改为**类型标签**（内置 / 本地 / 自定义） | 图里这些是**计费营销**概念。本项目自托管、无计费体系，"限时免费"这类标签**没有数据源，做就是编**。类型标签有真实依据（这个模型从哪来） |
| 倍率（0.29x / 0.11x…） | ❌ **不做** | **倍率** = 该平台按 token 计费时"消耗算力额度"的系数，是**商业计费概念**。本项目直连各家 API（或本地推理），没有"额度"这个东西——显示一个数是编的 |
| 顶部「Max 模式」开关 | ❌ **不做**（非目标） | 图里它是该平台"自动选最强模型"的商业策略开关。我们的对应物是**失败自动降级**（已有），但语义完全不同，不硬蹭 |
| 模型 logo 图标 | 🔁 **降级**：类型色点/统一图标 | 我们没有各模型的 logo 素材与授权；用类型色点区分即可（细节留实现） |

### 1.3 两个典型使用场景（验收时就按这两个走）

**场景 A · 切换模型**：我想对比「同一个问题，deepseek 和另一个模型分别怎么答」——
右上角点开列表 → 选中另一个模型 → 发问 → 回答由新模型产出，且消息上能看到"本轮由 XX 回答"（归因）。

**场景 B · 添加自定义模型**：朋友给了我一个某云厂商的 OpenAI 兼容端点（网址 + key + 模型名）——
下拉底部点「配置自定义模型」→ 填 4 个字段（显示名 / Base URL / API Key / 模型标识）→ 点「测试连接」当场验证通不通 → 保存 → 列表里出现、选中即用。

## 二、现状盘点（为什么这不是"换个 UI 组件"）

### 2.1 前端现状

`frontend/src/components/AppShell.tsx` 第 85 行，右上角是一个**只读占位**：

```tsx
<Tooltip title="模型由后端环境变量决定，当前仅展示">
  <Select size="small" value="configured runtime" options={[{ value: 'configured runtime', ... }]} />
</Tooltip>
```

它写死了一个选项、连点都点不动。它诚实地反映了后端现状（模型由 `.env` 决定），但需求就是**让它不再诚实、而是真正能干活**。

### 2.2 后端现状

| 层 | 现状 | 位置 |
|---|---|---|
| 配置 | 模型由 `.env` **静态决定**（`LLM_PROVIDER=deepseek/openai` 二选一），运行时不可切 | `app/config.py` |
| 通道 | 硬编码两通道 `LLM_CHANNELS = ("deepseek", "openai")`，每通道 = `{api_key, base_url, model}` 三件套 | `app/config.py` |
| 网关 | 主通道失败→自动降级备通道；`provider=` 可**锁定通道不降级**（D22 judge 在用）；发请求就是标准的 `{base_url}/chat/completions` + Bearer 头 | `app/services/llm_gateway.py` |
| 对话链路 | 请求体**没有**任何模型字段——用哪个模型这件事，请求方连提都提不了 | `app/schemas/chat.py` |

**两个有利条件**（决定了这需求是"接线"而不是"重构"）：
① 网关本就是多通道抽象，且是纯粹的 OpenAI 兼容协议客户端——**任何 OpenAI 兼容端点（云 API / 中转站 / Ollama 本地）都能零改动对接**；
> **注解 · OpenAI 兼容协议**：OpenAI 的对话接口（`POST /v1/chat/completions` + `{api_key, base_url, model}` 这套用法）事实上的行业通用格式。各家服务（含本地 Ollama、各类中转站）都提供"兼容模式"来模仿它，于是**同一份客户端代码能通吃所有家**——这正是本项目网关能"零改动接入任意模型"的地基。
② "锁定通道"能力 D22 已有，语义正好是本次要的"用户显式选择 = 不偷偷换"。

### 2.3 与两份既有文档的关系（**重要，避免三份文档打架**）

| 文档 | 与本次的关系 |
|---|---|
| PRD F9.4「侧边栏：模型选择（deepseek/openai）」 | 本次是它的**扩展实现**：不止两个固定选项，而是"内置 + 自定义"的完整模型列表 |
| 《本地模型接入方案-2026-10-12》（评审稿） | **高度重叠、建议合并实施**。它解决"云端/本地二选一切换"，本次解决"多模型列表 + 自定义"。它的实测成果（Ollama 可用、`host.docker.internal` 通、provider 透传链路设计）**全部继续有效**；仅 UI 位置从它的「输入区」改为本次用户指定的「右上角」 |

## 四、设计决策点（已拍板 · 理由存档）

### 4.1 自定义模型配置**必须存后端**（硬约束，不是选择题）

推导：LLM 调用发生在**后端**（网关红线：业务代码/前端不得直连 SDK）。前端 localStorage 里的 key，后端的网关**用不到**。所以：

- **自定义模型的三件套（base_url / api_key / model）必须存后端**（本项目 PostgreSQL，新表）；
- 前端只存"**选中了哪个**"（一个 id）——这是 UI 偏好，不是机密数据。

### 4.2 切换的生效范围与持久化（**已拍板：会话级记忆**）

**结论**：模型选择按**会话**记忆——每个会话记住自己用的模型；新建会话**继承最近一次选择**；记忆存浏览器 localStorage（`{会话 id → 模型 id}` 映射表 + 最近选择）。发问时把**当前会话的** `model_id` 放进请求。

**为什么是它（对照主流 AI 软件的行为定的）**：
- 主流 AI 软件（ChatGPT / Claude 类）的用户可观察行为是：**会话内随时切、历史完整保留、各会话各记各的、新会话继承上次选择**——切模型只决定"下一句由谁写"，**从不清空历史**（历史与模型解耦：历史属于会话，模型只影响未来的回复）；
- "切模型 = 自动开新会话"是少数第三方聚合工具的省事做法，非主流——不采用（它恰恰会造成"没法接着聊"）。

与其他候选的对比：

| 方案 | 不采用的原因 |
|---|---|
| 服务端存"当前模型"（全局） | ⚠ **评测脚本会被误伤**（脚本不传模型却被全局状态影响）；且"服务端全局"归属哪个客户端，语义混乱 |
| 前端全局一个选择 | 不像主流软件——A 会话切了模型，B 会话跟着变 |
| **会话级（采用）** | 最贴近主流行为；实现代价同样小（localStorage 一张映射表） |

**传输方式（不变，无争议）**：始终请求级（发问携带 `model_id`）→ 后端无状态、**不传 = 现有行为**（评测/回归零影响）。

**诚实边界**：localStorage 是"这个浏览器"的记忆——换设备/换浏览器不同步。单机项目可接受；将来要跨设备，把记忆升级为后端存储（如 sessions 表加列），列未来增强。

### 4.3 降级语义：显式选择 = 锁定不降级（已拍板，沿用昨日方案 §5.2）

- **不传 `model_id`**（默认）→ 现有行为：主通道 + 失败降级备用（**逐字节不变**）；
- **显式选了模型** → 锁定该通道，失败就报错，**不静默切别的**。理由：
  1. 用户的动机是"我就要用这个"（省钱/隐私/对比测试）——静默换模型既违背意图，还让"归因"变成谎话；
  2. 与 judge 锁定通道同一哲学：**显式选择即承诺，不偷偷换**。

### 4.4 API Key 的存储与出口（已拍板：明文入库 + 出口打码 + 日志纪律）

| 环节 | 规则 |
|---|---|
| 存储 | 明文存本机 PostgreSQL（自托管单机项目，DB 就在本机；**标注为已知限制**，加密存储列为可选增强） |
| 读取出口 | API **永不返回完整 key**：返回打码值（如 `sk-***c4`）或 `has_key: bool` |
| 日志 | key 不进任何日志/异常消息（把自定义模型 key 加入现有 `SENSITIVE_FIELDS` 屏蔽机制的适用范围） |

### 4.5 模型标识方式：统一 `model_id`（已拍板）

对话请求里新增字段 **`model_id`**（语义：你选的哪个模型），取值两种：

- **内置模型**：用通道名（`deepseek` / `openai` / 未来可能的 `ollama`）；
- **自定义模型**：用 DB 里的 UUID。

网关内部仍按现有的 `{api_key, base_url, model}` 三件套工作——`model_id` → 三件套的解析是新增的一小层（`_resolve_channels` 扩展），**不改变网关对"通道"的核心抽象**。

## 五、接口与数据设计（草案，实现时以代码为准）

### 5.1 新增表 `llm_models`（仅存自定义模型）

> **为什么内置模型不入库**：内置模型由 `.env` 驱动（现状不动）。`.env` 是"我信任的默认通道"，DB 是"用户自己加的"——两处职责分明，且内置模型**零迁移风险**。
> **建表方式**：沿用项目惯例 `scripts/dXX_migrate.py`（`create_all` + 回读库结构自查）。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID 主键 | 对外即 `model_id` |
| `name` | varchar(255) | 显示名（必填） |
| `base_url` | varchar(500) | 如 `https://api.example.com/v1` |
| `api_key` | varchar(500)，可空 | 本地端点常不需要 |
| `model` | varchar(255) | 模型标识，如 `qwen-max` |
| `enabled` | bool，默认 true | 置灰而不删 |
| `created_at` / `updated_at` | timestamptz | 与既有表同风格 |

### 5.2 新增 REST 接口

| 接口 | 用途 |
|---|---|
| `GET /api/models` | 列表：内置（`.env` 有 key 的）+ 自定义（DB）。每项：`{id, name, model, kind: "builtin"\|"local"\|"custom", enabled, base_url, api_key_masked}` |
| `POST /api/models` | 新建自定义模型（4 字段） |
| `PATCH /api/models/{id}` | 编辑（key 留空 = 不修改） |
| `DELETE /api/models/{id}` | 删除（连带处理：若某会话正选中它，该会话回退默认并提示） |
| `POST /api/models/{id}/test` | 连通性测试（对**已保存**的模型） |
| `POST /api/models/test` | 连通性测试（对**表单未保存**的值，供 §3.2 C4 用） |

### 5.3 对话接口扩展（**非流式与流式两条链路同步**）

```
POST /api/chat          { message, session_id, model_id? }
POST /api/chat/stream   { message, session_id, model_id? }
```

- `model_id` 缺省 = 现有行为（零回归）；
- 非法/找不到的 `model_id`：**非流式**返回 422（pydantic 层或路由层校验）；**流式**在 `error` 帧里返回明确原因（HTTP 200 已先行，见现有帧协议约定）；
- 响应/done 帧新增 `model_used`（实际执行模型，供 §3.3 归因）。

### 5.4 端到端链路（入口 → 步骤 → 返回）

```
[前端] 右上角选中模型（按会话记忆：localStorage 存 {会话 id → 模型} 映射）
   │  发问时携带 model_id
   ▼
[HTTP] POST /api/chat(/stream)  { message, session_id, model_id? }
   ▼
[服务层] run_agent / run_agent_stream  → AgentState 携带 model_id
   ▼
[编排层] plan_node → chat_with_tools(_stream)(..., model_id=...)
   ▼
[网关] _resolve_channels(model_id)：
        ① 空        → 现有主备降级（零回归）
        ② 内置通道名 → settings.llm_channel(name)，锁定
        ③ UUID      → 查 llm_models 表 → 组三件套，锁定
        ④ 查不到    → 明确报错（422 / error 帧）
   ▼
[LLM] 该模型对应端点（云 API / 中转 / 本地）
   ▼
[返回] 回答 + model_used（流式在 done 帧）
```

## 六、边界与非目标（明确不做，防止范围蔓延）

1. ❌ **倍率 / 免费 / 折扣标签**——无数据源，做就是编（§1.2）；
2. ❌ **Max 模式开关**——商业概念，语义不对应；
3. ❌ **自动分流**（后端判断"简单题用便宜模型"）——不可靠，沿用昨日方案结论；
4. ❌ **非 OpenAI 兼容协议**（Anthropic / Gemini 原生协议端点）——网关是 OpenAI 协议客户端，只描 OpenAI 兼容端点；遇到其他协议**明确报错**而不是碰运气；
5. ❌ **per-model 参数面板**（温度 / max_tokens 逐模型配置）——本次不做（温度是场景参数，项目已有自己的语义）；
6. ❌ **后端存储的跨设备模型记忆**——localStorage 仅本浏览器；后端同步（如 sessions 表加列）列为未来增强；
7. ⛔ **不动的部分（零回归红线）**：评测 judge（继续锁 deepseek）、对话摘要（走默认通道）、评测/回归脚本（不传 `model_id` 行为完全不变）。

## 七、验收标准

1. 右上角下拉列出：内置模型（`.env` 已配 key 的）+ 自定义模型；当前项打勾；**同一会话切换后刷新保持、可来回切；新会话继承最近选择**（§4.2 会话级记忆）；
2. 【零回归】不切模型（默认项）发问 → 行为与改动前**逐字节一致**（Langfuse 里 model 名不变）；
3. 【场景 A】切换到另一模型发问 → 回答由该模型产出（Langfuse trace 模型名可见），消息显示"本轮由 XX 回答"；
4. 【场景 B】添加自定义模型（故意填错 base_url）→ 测试连接给出明确失败原因；改正后 → 测试通过 → 发问成功；
5. 【流式兼容】上述 3/4 在**流式与非流式两条链路**都成立（流式错误走 error 帧、信息明确）；
6. 【安全】任何接口响应、日志中**不出现完整 api_key**；删除自定义模型后列表即时消失；被删除模型若为某会话当前选中，该会话回退默认并提示；
7. 【零影响】现有 pytest 全量绿；评测脚本、回归脚本输出与改动前一致；
8. 文档同步：IMPL-SPEC 附录 B"模型切换"条目、README 相应段落更新。
