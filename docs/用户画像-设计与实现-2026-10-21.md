> 关联：`docs/账号体系-设计与实现-2026-10-21.md`（本功能的地基）

## 一、先解决一个定义问题：什么叫"用户画像"

**用户画像**（user profile）：一组**跨会话稳定**的、关于"这个用户是谁"的事实与偏好。

判据只有一条，但很硬：

> **换一个新会话，它还必须成立。**

| 用户说过的话 | 是不是画像 | 为什么 |
|---|---|---|
| "我叫老郭，在一家电商公司做前端" | ✅ 是 | 下周开新会话仍然成立 |
| "我最近在准备面试" | ✅ 是 | 是个持续数周的目标 |
| "帮我看看这个 useEffect 为什么会死循环" | ❌ 不是 | 一次性的任务 |
| "这个报错怎么修" | ❌ 不是 | 同上 |
| "我平时更习惯用函数组件" | ✅ 是 | 长期偏好 |

这条判据不只是分类标准，它同时决定了三件事：

1. **它不能放 `sessions.summary`** —— 那张表一行对应一个会话，天生是会话级作用域。
2. **它不能每轮都重新算** —— "关于我是谁"在一生中只会被说几次，而对话有几千轮。
3. **它必须能被用户删** —— 模型猜错时，只有用户知道"这条不对"。

### 一个容易混淆的术语

代码注释里 `get_summary()` 写的是"读**长期**摘要"。这里的"长期"指的是**跨轮次**
（超出 8 轮滑窗的那部分），不是跨会话。两个词相差一个字，含义完全不同：

- **会话内的"长期"** = 超出热窗口、被压缩进摘要的那些轮次 → 仍属于**一个** session
- **用户级的"长期"** = 换会话仍然成立的画像 → 属于**一个** user

这正是这个功能立项的直接原因：A 会话说"我叫老郭"，新建 B 会话问"我叫什么"，Agent 一无所知。

## 二、四层记忆的完整版图

做之前只有前三层，第四层是这次补的：

| 层 | 存什么 | 作用域 | 生命周期 | 载体 |
|---|---|---|---|---|
| 单轮上下文 | 本次请求的 messages | 一次请求 | 请求结束即丢 | 内存 |
| 会话热窗口 | 最近 8 轮对话 | **一个 session** | 24h TTL | Redis |
| 会话摘要 | 更早轮次的压缩 | **一个 session** | 随会话 | `sessions.summary` |
| **用户画像** | **跨会话的稳定属性** | **一个 user** | **长期** | **`user_profiles` + `user_profile_facts`** |

四层的组装顺序（`build_system_prompt`）：

```
人设（PLAN_SYSTEM_PROMPT）
  ↓
用户画像        ← 跨会话稳定（"你是谁"）
  ↓
会话摘要        ← 本会话临时（"刚才聊了什么"）
  ↓
本轮对话（messages）
```

**为什么画像排在摘要之前**：先稳定后临时。反过来（摘要在前）模型更容易用一段临时上下文盖掉长期设定 —— 这种漂移不报错，只是画像时灵时不灵。

## 三、三条链路

### 写入链路 A：用户显式填写

```
我的画像页（/profile）
  → PATCH /api/profile
  → user_profiles.explicit（JSONB）
```

**JSONB** 是 PostgreSQL 的二进制 JSON 类型：语义上就是你熟悉的 `JSON.parse` 那套，
但它可以在建索引后按字段查询（`WHERE explicit->>'nickname' = '老郭'`）。

### 写入链路 B：对话后隐式抽取

```
一次对话结束（persist=True）
  → 触发检查：新增 ≥6 条用户发言 且 距上次 ≥10 分钟
  → asyncio.create_task（后台）
      → 读该用户游标之后的发言
      → LLM 抽取「跨会话仍成立」的事实
      → 规范化 + 哈希 + ON CONFLICT DO NOTHING 入库
```

### 读取链路：拼进 system prompt

```
POST /api/chat
  → 接口层已有 user 对象
  → run_agent(owner_id=user.id)
  → 组装 state 前：render_for_prompt(owner_id, 本轮问题)
       ├─ 显式字段：**全量**
       └─ 隐式事实：关键词匹配取 **top-k（默认 4 条）**
  → build_system_prompt(人设, 画像, 摘要)
```

**top-k** = 取匹配度最高的前 k 条。为什么隐式事实不能全量注入，见第五节。

## 四、数据模型：为什么拆成两张表

### `user_profiles`（一人一行，显式字段）

| 列 | 类型 | 说明 |
|---|---|---|
| `owner_id` | UUID PK, FK→users CASCADE | 一人一行，所以直接做主键 |
| `explicit` | JSONB | 用户自填，键取自 `EXPLICIT_KEYS` |
| `updated_at` | timestamptz | |

### `user_profile_facts`（一条一行，隐式事实）

| 列 | 说明 |
|---|---|
| `id` / `owner_id` | 主键 / 归属（FK→users CASCADE） |
| `kind` | `preference` / `fact` / `goal` |
| `text` | 一句话陈述 |
| `text_hash` | 规范化文本的 sha256（去重依据） |
| `source_session_id` | 从哪次会话抽出来的（FK→sessions **SET NULL**） |
| `confidence` | 模型自评可信度（仅用于排序与展示，**不参与任何自动删除**） |
| 唯一约束 | `(owner_id, text_hash)` |

### 拆表的理由

两边的**信任等级、编辑方式、注入配额**全都不同：

| 维度 | 显式（用户自己填） | 隐式（LLM 抽的） |
|---|---|---|
| 谁说的算 | 用户 | 模型 |
| 改的方式 | 表单保存，改了就生效 | **只能删**，改要重新抽 |
| 注入策略 | 全量 | top-k |
| 出错后果 | 他自己填错的，他能改 | 他会觉得"这系统坏了" |

挤在一张表里，早晚要按"来源"字段到处分支 —— 那正是该拆的信号。

### 为什么 `source_session_id` 是 SET NULL 而不是 CASCADE

删掉一个会话，**不该**连带删掉从它抽出来的画像。

画像的语义是"关于这个人的长期事实"，它一旦成立就独立于来源存在。
用 CASCADE 会有个很难发现的事故：用户清理历史会话 → 画像悄悄清空 →
他会以为"这系统记不住我"，而实际是被级联删了。

（对比：`user_profiles.owner_id` 用 CASCADE 是对的 —— 人没了，画像没有独立意义。）

## 五、三个关键设计

### 5.1 显式全量 / 隐式 top-k

**显式为什么全量**：它是用户主动声明的，总共 4 个字段、几十个字，任何场景都相关。

**隐式为什么不能全量**：两个问题。

1. **token 线性增长**：画像是越积越长的（每 6 轮抽一次），全量塞进去就是无底洞。
2. **无关事实会干扰当前问题**（更要命）：你问代码规范，它把你的"喜欢喝美式"也带上，
   模型可能真的往回答里带。

所以：显式全量 + 隐式 top-4。

### 5.2 抽取为什么不能挂在请求路径上

一轮对话已经串了：读记忆 → LLM 多轮工具调用 → 摘要检查。
再同步加一次 LLM 抽取，每轮多 1~2 秒，而**绝大多数轮次根本不含画像信息**
（"我叫老郭"这种话一生可能只说一次）。

与摘要的对照，这个差异值得记住：

| | 摘要（`maybe_summarize`） | 画像抽取（`maybe_extract`） |
|---|---|---|
| 谁等它 | **下一轮对话要读它** | 没人等 |
| 延迟敏感 | 是（同步 `await`） | 否（`asyncio.create_task`） |
| 失败后果 | 记忆断档 | 个性化晚一点生效 |

判据不是"哪个更高级"，而是**这个结果会不会被下一步立刻读到**。

### 5.3 "可见可删"不是体验问题，是正确性问题

**画像写错比没有画像更糟**：Agent 会一口咬定一个错误事实，而用户找不到地方纠正，
只能怀疑系统坏了。

所以每一条事实都必须：

- **看得见**：列在 `/profile` 页上
- **标来源**：来自哪次会话（可以点进去看当时说了什么）
- **删得掉**：一条一个删除按钮，删完下一轮就不再带

这也是为什么接口**不提供"编辑事实"**：用户编辑会引出"改完之后算显式还是隐式"的无解问题。
用户想说的事实，让他填到显式字段里 —— 那才是他"说了算"的地方。

于是两张表的边界始终清楚：**显式的用户负责，隐式的模型负责、用户可否决。**

## 六、实现细节

### 6.1 规范化：去重的地基

`normalize_fact_text()` 做四件事，都不改变语义：

1. **NFKC 归一**（Unicode 的一种标准归一形式，把全角字符映射到半角）：
   `Ｔｙｐｅ` → `Type`
2. 压缩连续空白
3. 去掉首尾空白
4. 去掉句末标点（`。．.!！?？；;，,、`）

然后用 `sha256(规范化文本)` 作为 `text_hash`。

**为什么必须先规范化再哈希**：抽取器每次输出措辞会有细微差别，
`"偏好 TypeScript。"` 与 `"偏好 TypeScript"` 直接哈希是两个不同的串 —— 等于没去重。

**不做的事**（有意为之）：不做同义词替换、不做大小写折叠。
宁可多留一条，不要合并掉两条意思不同的事实。

### 6.2 关键词匹配：一个实测出来的坑

匹配用**布尔余弦**：

```
score = 命中词数 / sqrt(查询词数 × 事实词数)
```

分母带 `|fact|` 是在惩罚"靠长度蹭分"，用 sqrt 而不是并集（Jaccard）是为了不惩罚长查询。

**关键坑**（写测试时发现的）：用查询 `前端` 去匹配事实 `前端开发相关的第 N 条事实`，
一条都没命中 —— 因为 **jieba**（中文分词库）把「前端开发」切成了**一个词**，
与「前端」不相等。

这类"词表里有复合词"的情况在中文里非常普遍（前端开发 / 机器学习 / 大模型应用），
只做完全相等匹配会让画像在最常见的问法上**静默失效**。

修法是加一层包含关系兜底：

```python
if token in fact_tokens or _contains_any(token, fact_tokens):
    hits += 1

def _contains_any(token, others):
    if len(token) < 2:          # ← 这条限制不能省
        return False
    ...
```

**为什么限制 `len >= 2`**：单字（"的""和""写"）是任何词的子串，
放进来会让所有事实都"命中" —— 那等于匹配失效，而且**看不出任何异常**（分数都 > 0，排序近似随机）。

### 6.3 无匹配时的兜底：取满 top_k（**2026-10-21 线上故障后修正**）

一条都不相关时，按 `confidence` 降序取到 **top_k 条**（不超过事实总数）。

- 不带任何事实 → 画像在**最需要它的时候（泛泛的提问）恰好消失**
- **只带 1 条 → 事实总量小于 top_k 时，等于无理由丢弃大半个画像**

#### 原来的写法与它错在哪

初版写的是"只带 1 条"，理由（写进 docstring 的）：

> 相关性为零，多带一条只是噪音。

这个推理有一步是错的：**零相关只说明「匹配没有给出信号」，不等于「每条事实都同样相关/同样无关」**。
没有信号的时候，唯一可用的排序依据就是 `confidence`，正确动作是**用它填满预算**，
而不是在没有依据的情况下只挑一条。

#### 真实故障

用户的画像只有 2 条（`是开发工程师` / `希望被称呼为梦`，confidence 都是 0.95）。

| 步骤 | 实际发生 |
|---|---|
| 问「我叫什么？」 | 分词 `['我','叫','什么']` |
| 与两条事实的布尔余弦 | 都是 **0.000**（"称呼"≠"叫"，"梦"≠"什么"） |
| 进兜底分支 | 按 `(-confidence, id)` 排序，取 1 条 |
| 结果 | 取到 id 小的 `是开发工程师`，**名字那条被丢弃** |
| Agent 回答 | 「我这边没有你的名字信息，无法直接说出」 |

用户看到的现象是"新开窗口画像没被召回"，但**注入其实是成功的** —— 只是注入了无关的那一条。
这类"看起来没生效、其实是生效了一半"的故障最难查，因为日志里一切正常。

修法与回归守卫：

```python
def _by_confidence(limit: int) -> list[FactItem]:
    return sorted(facts, key=lambda f: (-f.confidence, f.id))[:limit]

if not scored:
    return _by_confidence(top_k)
```

`tests/unit/test_profile_service.py::test_name_fact_survives_zero_relevance_query`
直接复刻上面这张表（两条 0.95 的事实 + 查询「我叫什么？」），断言名字那条必须在结果里。
把兜底改回 `_by_confidence(1)`，三条用例同时变红。

#### 代价核算

多带 3 条事实 ≈ 60~100 tokens，且仍受 `FACT_TOP_K = 4` 硬上限约束。
相对"画像在最该出现的时刻整条消失"，这个代价可以接受。

### 6.4 渲染：那句"不要主动复述"是行为约束

```text
【用户档案】（用户本人填写）
- 称呼：老郭
- 职业 / 身份：前端工程师

【过往对话中了解到的信息】（可能不准确或已过时）
- 正在准备 React 技术面

使用这些信息时：
1. 只用来调整举例、措辞与深浅，不要在回答里主动复述（不要说「我记得你……」）。
2. 【用户档案】是用户本人填写的，可信度更高；【过往对话中了解到的信息】由系统自动提取，
   可能过时或有误。两者冲突时，以【用户档案】为准。
3. 与用户当前的说法冲突时，以当前说法为准。
```

**第 1 条**不加，模型会开始说"记得你上次提到……"，而画像里**根本没有"上次"的时序** ——
它只是在复述一段背景文本，听起来像编造（实际是提示词诱导出来的行为）。

**第 2 条是验收时撞出来的真实问题，不是预防性设计。**
容器内首次抽取把最近 30 条历史一起抽了，抽出一条「名字是小王」（来自更早的测试对话），
而用户显式填的是「称呼：老郭」—— 同一份 prompt 里两句话互相矛盾，模型只会挑一个信。

两条事实的**可信度天然不同**（用户亲口填的 vs 模型猜的），但模型不知道这件事，
除非你告诉它。所以优先级必须写进 prompt，不能指望它自己判断。

> 顺带记一笔这个案例的后续处理：那条错误事实被删掉了 ——
> 这正是"可见可删"存在的理由。**如果画像不可删，这次就只能改代码去修数据。**

### 6.5 后台任务必须持有强引用

```python
_BACKGROUND: set[asyncio.Task] = set()

task = loop.create_task(_safe_extract(owner_id, session_id))
_BACKGROUND.add(task)
task.add_done_callback(_BACKGROUND.discard)
```

**asyncio 的 task 如果没人引用，可能在跑完之前被 GC 回收**（Python 文档明确要求保存引用）。
这个坑的症状极隐蔽：日志里没有错误、没有 traceback，只是"有时抽有时不抽"。

另外 `_safe_extract` 内部必须吞掉所有异常。不吞的话，
异常会在事件循环层记成 `Task exception was never retrieved`，
而那条日志出现在**请求结束之后**，跟用户看到的任何现象都对不上 —— 排障时几乎无法归因。

### 6.6 游标与冷却放 Redis

- `profile:{owner_id}:extract_upto` —— 已抽到哪条 message id
- `profile:{owner_id}:extract_at` —— 上次抽取的 unix 时间

都是**可丢失状态**：游标丢了 → 抽最近的 30 条（不是全量重抽）；冷却丢了 → 最多多抽一次
（去重约束保证不会重复入库）。

判断"一份数据能不能放缓存"的标准：**先问丢了会怎样。**
答"只会多做一次无害的重复劳动"就能放。

⚠ 游标缺失时**取最近 30 条**而不是"从头取全部"：
从头取意味着老用户第一次跑抽取会把几百条历史一次性喂给 LLM —— token 爆炸、
延迟几十秒，抽出来的还都是早就过时的东西。

**但它有一个必须说清楚的副作用**：对**已有历史数据**的老用户（或新部署上线的时刻），
第一次对话就会触发一次"最近 30 条"的抽取 —— 因为 `len(rows) >= 6` 这个条件
对历史消息同样成立。也就是说 `PROFILE_TRIGGER_MESSAGES` 的语义在首次运行时会从
"新增 6 条"变成"历史里有 6 条"。

这是**有意的取舍**（否则老用户永远没有画像，功能上线即空），代价是首次可能抽到
过时的、甚至与显式字段冲突的内容。处置靠两条：
① 渲染时声明优先级（见 6.4 第 2 条）；
② 用户能看见并删除。

验收时就真撞上了：首次抽取抽出一条「名字是小王」，与显式字段「称呼：老郭」冲突。

### 6.7 两个时间差：有些"没召回"是正常现象

用户最容易误判的两个时刻，都不是 bug：

| 时刻 | 当轮表现 | 原因 |
|---|---|---|
| 本轮说「以后叫我阿梦」，**同一轮**问「我叫什么」 | 答不出 | 抽取排在**回答之后**（不占对话延迟），本轮 system prompt 已经发出去且无法追加 |
| 在 `/profile` 改完显式字段，立刻回到**已经打开**的那轮对话追问 | 旧值 | 同上：画像在本轮开始前读一次，改完从**下一轮**生效 |

所以排查"画像没生效"的第一步永远是：**换一个新会话再问一次**。
如果新会话仍然答不出，才去看 `render_for_prompt(owner_id, query)` 返回了什么（见下一节的探针）。

## 七、失败模式与降级方向

| 失败 | 影响 | 处理 | 方向 |
|---|---|---|---|
| 对话中读画像失败 | 本轮没有画像 | 返回空，对话照常 | **fail-open** |
| 抽取 LLM 超时 | 本轮不产生新事实 | 记 warning + **写冷却时间** | 下轮再试 |
| 抽取输出不是 JSON | 同上 | 记 warning + 写冷却时间 | 下轮再试 |
| 写库失败 | 事实没入库 | 只记 warning | 下次重抽 |
| 用户删光画像 | 回到"没有画像" | 正常状态 | 不是错误 |

### fail-open 与 fail-closed 的分界（这一条要记牢）

| 场景 | 失败时 | 理由 |
|---|---|---|
| 认证读 Redis 白名单 | **拒绝**（fail-closed） | 读不到 → 不能确定你是谁 |
| 读用户画像 | **放行**（fail-open） | 读不到 → 这次没有个性化，不是不能对话 |

判据是**这一层是不是业务的前置条件**。认证是（不知道你是谁就不能放行），
画像是（不知道你是谁也能回答，只是没那么贴心）。

### 为什么 LLM 失败要写冷却时间

不写的话，下一轮对话会立刻再试一次 —— 于是一次模型故障会变成
"每一轮对话都多一次失败调用"，把一次性故障放大成持续雪崩。

## 八、踩过的四个坑

### 1. `text` 字段遮蔽了 `sqlalchemy.text`

```python
class UserProfileFact(Base):
    text: Mapped[str] = mapped_column(Text)          # ← 这一行执行完，
    confidence: Mapped[float] = mapped_column(Float,
        server_default=text("0.7"))                  # ← 这里的 text 已经不是函数了
```

报错：`TypeError: 'MappedColumn' object is not callable`。

Python 的**类体是一个普通作用域**：字段名叫 `text`，类体里的名字 `text` 就被绑定成了
`MappedColumn` 对象。起别名 `from sqlalchemy import text as sa_text` 是唯一彻底的解法
（换个字段名只是把这个坑推给下一个改代码的人）。

### 2. `SAWarning: nested transaction already deassociated`

迁移脚本里手写 `nested = await conn.begin_nested()` + `commit()`，
插入失败后那个嵌套事务被 SQLAlchemy 标记为 deassociated，最外层 rollback 时冒警告。

改用 `async with conn.begin_nested():`（上下文管理器自己负责回滚与释放）。

警告本身无害 —— 但"每次迁移都冒一行警告"会训练人忽略警告，那才是真代价。

### 3. jieba 复合词导致匹配失效

见 6.2。这个是**测试抓出来的**，不是看代码看出来的。

### 4. 测试期望 vs 实现漏洞：怎么判断

`needs_rehash("garbage")` 返回 `False`（上一轮账号体系的收尾）。判断依据是 **docstring 的意图**：
它写的是"解析不了的串按需要升级"，而代码没做到 → **改实现，不改测试**。

判据可以概括成一句：**测试描述的是"应该怎样"，实现描述的是"现在怎样"。两者不一致时，
先问哪一个是想要的。**

## 十一、遗留（没做，不藏着）

1. **关键词匹配的精度上限**：同义改写（"做前端的" vs "前端工程师"）匹配不上。
   换向量检索更准，代价是多一张 embedding 表 + 一次调用 + 索引重建约束。
   **现在不做的理由**：画像事实都很短，关键词重合的召回已经够用；
   等出现"答得不贴"的真实反馈再换，不提前为一个没观测到的问题付复杂度。
2. **抽取没有人工确认环节**：抽出即生效。缓解手段是"可见可删"，不是"先审后用"。
3. **没有"清除全部画像"按钮**：只能逐条删。加一个整页清空是 20 行代码，
   但它会让"误点"的代价从"少一条"变成"全没了" —— 需要二次确认，属于下一轮的产品决策。
4. **抽取触发是固定阈值**（6 条 / 10 分钟），没有按"这段话是否像在说自己"来判定。
   后者更省调用，但会漏（用户可能用一句话说完所有信息）。
5. **跨用户画像对比 / 管理员查看**：刻意没做。画像是最私密的一类数据，
   "管理员能看"这个能力本身就不该存在。

## 十二、面试问答

**Q1：为什么画像不放在 sessions.summary 里？**

`summary` 的主键语义是 session —— 一行对应一个会话。画像的判据是"换会话仍然成立"，
把它塞进会话级表，跨会话就必然读不到。这不是实现问题，是**作用域错配**。

**Q2：显式字段和隐式事实为什么要拆两张表？**

信任等级不同（用户说的 vs 模型猜的）、编辑方式不同（能改 vs 只能删）、
注入策略不同（全量 vs top-k）。挤在一张表里，每个使用点都要按"来源"分支 ——
那是该拆的信号。

**Q3：抽取为什么放后台？失败了怎么办？**

它在请求路径上会每轮多 1~2 秒，而绝大多数轮次不含画像信息。
失败时只记 warning + 写冷却时间，下轮再试 —— 绝不能因为抽画像让对话 500。
冷却时间那一步是关键：不写的话一次故障会被放大成"每轮一次失败调用"。

**Q4：画像读不到时为什么放行，而认证读不到时拒绝？**

判据是"这一层是不是业务的前置条件"。认证是（不知道你是谁就不能放行），
画像是（不知道你是谁也能回答，只是没那么贴心）。这就是 fail-closed 与 fail-open 的分界。

**Q5：怎么防止画像重复累积？**

三层：① prompt 里把已有事实喂回去，让模型在生成阶段避开；
② 规范化（NFKC + 去空白 + 去句末标点）后算 sha256；
③ 数据库唯一约束 `(owner_id, text_hash)`。
前两层是效率，第三层是正确性 —— 抽取是后台任务，可能并发跑两份，
应用层"先查再插"挡不住。

**Q6：为什么画像必须给用户一个能删的页面？**

因为画像写错比没有更糟。用户看到 Agent 一口咬定一个错误事实，又找不到地方纠正，
只会怀疑系统坏了。而且**删不掉 = 无法纠错 = 这个功能反而有害**。

**Q7：top-k 匹配为什么先上关键词，不上向量？**

向量更准，但要多一张 embedding 表、一次调用（+30ms）、以及"画像更新要重建索引"的运维约束。
画像事实很短（20~40 字），关键词重合的召回已经够用。
**不提前为一个尚未观测到的问题付复杂度代价。**

## 十三、自测题

**1. 一条信息满足什么条件才算"画像"？举一个反例。**
答：换一个新会话它还必须成立。
反例："帮我看看这个 useEffect 为什么会死循环" —— 一次性任务，下周不会仍然成立。

**2. `sessions.summary` 和 `user_profile_facts` 的作用域分别是什么？**
答：前者一个 session，后者一个 user。前者换会话就没了，后者换会话仍然带上。

**3. 显式字段为什么全量注入，隐式事实为什么只取 top-k？**
答：显式只有 4 个字段、几十个字，任何场景都相关；
隐式会越积越长（token 线性增长），且无关事实会干扰当前问题。

**4. 一条事实都不匹配本轮问题时，注入几条？为什么不是 0 条？为什么不是 1 条？**
答：按 confidence 取满 top_k（不超过事实总数）。
0 条会让画像在最需要它的时候（泛泛的提问）恰好消失；
1 条则是在"匹配没有给出信号"的情况下凭空只挑一条 —— 事实总量小于 top_k 时等于丢弃大半个画像，
真实故障就是这么发生的（2 条事实问「我叫什么」，只带上"是开发工程师"，名字被丢掉）。

**5. 抽取失败时为什么要写冷却时间？**
答：不写的话下一轮对话会立刻再试一次，一次模型故障会被放大成"每轮一次失败调用"。

**6. 画像是 fail-open 还是 fail-closed？和谁相反？**
答：fail-open（读不到就返回空，对话继续）。与认证的 refresh 白名单（fail-closed）相反。
判据是"这层是不是业务的前置条件"。

**7. 为什么 `source_session_id` 用 SET NULL 而 `owner_id` 用 CASCADE？**
答：删会话不该删画像（画像独立于来源存在，否则用户清理历史会以为"系统记不住我"）；
用户被删则画像没有独立意义，一起删。

**8. 为什么 `text` 字段会让 `server_default=text("0.7")` 报错？怎么修？**
答：类体是普通作用域，字段声明后名字 `text` 被绑定成 `MappedColumn`，遮蔽了模块级的
`sqlalchemy.text` 函数。用 `from sqlalchemy import text as sa_text` 起别名。

**9. 关键词匹配为什么需要"包含关系"兜底？为什么又限制长度 ≥ 2？**
答：jieba 把「前端开发」切成一个词，与查询「前端」不相等 → 匹配失效。
限制 ≥2 是因为单字是任何词的子串，放进来会让所有事实都"命中"（匹配退化且无异常可查）。

**10. 为什么要给后台任务保存强引用？**
答：`asyncio.create_task` 返回的 task 若没人引用，可能在跑完之前被 GC 回收。
症状是"有时抽有时不抽"，日志里什么都没有。
