## 一、结论摘要：能不能用

| 技术 | 能否融入 | 接入位置 | 含金量类型 | 前置条件 |
|---|---|---|---|---|
| **Harness.io** | ✅ 能（低摩擦） | AgentForge 的 **MCP 客户端 → Harness 官方 MCP Server** | 真实外部企业系统 + AI-for-DevOps 场景 | Harness 账号 + 一条真实流水线 + PAT |
| | ⚠️ 能但摩擦高 | 用 Harness pipeline 承载**评测门禁**（Eval as a gate） | 前沿度最高的一个用法 | 需先解决 codebase connector / Gitee / 执行环境 |
| **Dify** | ✅ 能（源码已证实） | AgentForge 的 **MCP 客户端 → Dify App MCP Server** | 平台互操作 + 企业主流平台实操经验 | 一个已发布的 Dify 应用（你已有） |
| | ✅ 能（零代码） | **对照基线**：同题对比评测 | "为什么自建"从话术变数据 | 评测体系先落地（PRD D20–D24） |
| **Agentic BI** | ✅ 能 | Tool Registry 加分析工具 + 轻量语义层 + 前端图表 | 结构化数据问答 + 多步自主分析 + 可视化 | 语义层文件 + 一个查询工具 + 前端图表组件 |

**一句话**：三个技术**都能融入**，且**都不需要推翻现有架构**——因为 AgentForge 的分层（Gateway / Tool Registry / Agent 引擎 / RAG / Eval / 可观测）本来就是为了"加东西不返工"设计的。真正决定含金量的不是"加了几样"，而是**每一项能不能被讲成一个设计决策**。

> **具体怎么接（可执行步骤）见 §六**。其中 Harness 走 PRD 已有的 `POST /api/mcp/register`；Agentic BI 走 Tool Registry + `metrics.yaml` 语义层 + 前端图表。

## 二、关键杠杆：为什么 MCP 决定了一切

### 2.1 一个客户端，接通两个外部系统

```
AgentForge（MCP Client —— PRD D25–D27 / F6.3–F6.5，本来就是 P0）
    │
    ├──→ Harness MCP Server   官方开源（github.com/harness/mcp-server）
    │                          11 工具 × 252 资源类型 × 41 toolset（2026-09 口径）
    │
    └──→ Dify App MCP Server  你本地已有（Dify 1.17 内置服务端实现）
```

**MCP 客户端无论如何都要写**（PRD 里是 P0，D25–D27）。所以：
- 接 Harness：**边际成本 ≈ 0 架构改动**，只多一个工具源
- 接 Dify：同上，而且你那边已经有跑通的应用

**含金量机制**：你交付的不再是"一个会查文档的机器人"，而是**一个能与企业级系统互操作的 Agent Runtime**。这是从"应用层"跨到"运行时层"的差别。

### 2.2 这为什么是 2026 年的前沿

| 信号 | 事实 |
|---|---|
| 协议层面 | MCP 已是智能体与外部系统交互的事实标准；JD 中 2 份（JD2/JD7）明确点名 |
| 平台层面 | Harness 2026 版把 MCP 写进产品能力（"apply bulk updates using APIs or **MCP**"），并开源了自己的 MCP server |
| 应用层面 | Dify 1.17 内置 MCP 服务端，能把应用反向暴露给外部 Agent |
| 语义层面 | 厂商已开始"把自己变成别人的工具"——**互操作本身就是这一代平台竞争的主战场** |

**你的项目如果做成"AgentForge 能同时驱动两个主流平台"，讲的就是这件事。**

## 三、Harness.io

### 3.1 它是什么

**企业级软件交付平台**（官网定位 "One platform for the autonomous SDLC"）。模块：CI / CD(含 GitOps) / IaC 管理 / 数据库 DevOps / 制品仓 / 代码仓 / AI 代码评审 / 安全测试(SAST·SCA·供应链) / 运行时防护(API·AI) / 云与 AI 成本 / 特性开关 / 混沌工程 / 内部开发者门户 / AI SRE。

其 2026 AI 层值得注意的设计——**"Agents act. You draw the boundaries."**：
- Delegate 常驻**你自己的 VPC / 集群内**，密钥不出边界
- OPA 策略即代码 + RBAC + 审批 + 审计签名，**同一套策略同时管 AI 和管人**
- **验证失败自动回滚**
- 自主度三档：Autonomous / Human-in-the-loop / Deterministic

> 这套"让 Agent 能干活但被管住"的设计，与 AgentForge 附录 A 里缺失的「权限 / 沙箱 / 预算护栏」是同一类问题——**可作为阶段 3 的设计参考**。

### 3.2 路径 A：当 Agent 的 MCP 操作对象 ✅ 可行（低摩擦）

**接法**：AgentForge 的 `app/tools/mcp_client.py`（MCP Client）连 `harness-mcp-v2`（MCP Server），动态发现工具 → 注册进 ToolRegistry → Agent 可调用。

**官方 MCP Server 事实**（来源：`github.com/harness/mcp-server` README，2026-09-22 读取）

| 项 | 内容 |
|---|---|
| 仓库 / 包 | `github.com/harness/mcp-server`（MIT 许可）；npm **`harness-mcp-v2`** |
| 规模 | **11 个工具 × 252 种资源类型**，**41 个默认 toolsets**，**35 个 prompt 模板**（该项目迭代极快，数字以 README 当日为准） |
| 工具（官方文档表述为 11 个通用动词） | `harness_list` / `get` / `create` / `update` / `delete` / `execute` / `search` / **`diagnose`** / **`status`** / `describe` / `schema` |
| MCP 资源 | `pipeline:///{pipelineId}`、`executions:///recent`、`schema:///pipeline` 等，以 URI 寻址 |
| 认证 | Harness **PAT**（`pat.<accountId>.<tokenId>.<secret>`，account id 自动提取）；HTTP 模式亦支持 `sat` 与 HarnessID OAuth |
| 起法 | `HARNESS_API_KEY=pat.xxx npx harness-mcp-v2@latest`（stdio 默认）；HTTP：`npx harness-mcp-v2 http --port 8080` |
| 传输 | stdio（本地客户端）/ HTTP（远程共享，session-based + SSE）；另有托管端点 `https://mcp.harness.io/mcp`（需账号开通，走 OAuth，不用 PAT） |
| 写操作护栏 | **`HARNESS_AUTO_APPROVE_RISK`** = `none` / `low_write` / `medium_write` / `high_write` / `all`，可按 session 用 `x-harness-auto-approve-risk` **收紧**（只能降不能升）；高风险操作走 elicitation 请求用户确认 |
| 上下文控制 | 支持 **toolset 过滤**（只暴露需要的工具集）；官方理由：工具数膨胀会降低 LLM 选工具的准确率 |
| 诊断能力 | `harness_diagnose` 附**失败分类**：`infra_flake` / `test_failure` / `config_error` / `dependency_failure` / `permission_error` / `timeout` 六类（有 TypeSafe API 时启用，属 advisory，失败静默省略） |
| 语义检索 | 可选本地语义搜索（ONNX embedding，模型约 23MB 首次下载）；`HARNESS_SEARCH_PROVIDER` 控制开关 |

> ⚠️ **规模数字会变**：该仓库 commit 频率接近每日，v3 写的 139 / 30 / 27 在数日内即已过期。引用前请以 README 为准。

**含金量**
1. **真实外部企业系统**：把 PRD S7「≥1 个**真实外部**工具可用」从内存 mock 升级为真实平台（PRD 自带的 `inventory_server` 是 mock 数据）
2. **场景前沿**：`harness_diagnose` 让 Agent 能**诊断失败流水线**——"AI 辅助 DevOps"是 2026 年最热的 Agent 落地场景之一
3. **工具定义质量差异**：Harness 刻意采用"少数通用动词 + resource_type 路由"而不是"一接口一工具"，理由是**工具数膨胀会掉 LLM 选型准确率**——这个设计取舍本身就是一个可讲的架构观点（也是你 Tool Registry 的对照组）
4. **JD 覆盖**：一次动作同时对应 高端第 2 项（企业级工程化）与 MCP（JD2/JD7）

**前置**
- Harness 账号（免费档 $0）+ 一个项目 + **至少一条真实流水线**
- PAT 权限最小化（建议 pipeline 只读 + execute）
- Node（`npx`）——对纯 Python 项目是一次小引入

### 3.3 路径 B：用 Harness 承载"评测门禁"（Eval as a gate）⚠️ 可行但摩擦高

**想法**：把"跑 50 条评测集 + LLM-as-judge 打分 + 消融实验"做成一条 pipeline，**评测不达标不放行**。这是"Agent 效果持续评估"进 CI/CD 的做法，前沿度很高。

**摩擦点（实测级）**
1. Harness CI 的 Build stage 需要 **codebase connector** 拉代码，而**仓库在 Gitee，不在其官方集成清单**（GitHub / GitLab / Bitbucket / Kubernetes / Docker / AWS / Azure / GCP / Jira / Slack / ServiceNow / Terraform）
2. CD 目标环境是 **K8s / ECS / Helm / Serverless / SSH**，而 AgentForge 跑在**本机 docker-compose**
3. 需要**常驻 Delegate** 进程
4. 免费档限额在 **2026-08-28 被记录到一次削减**（此前 2,000 build credits/月 → 现为 ≤60 并发执行、250GB 存储、1 org 等；**云构建额度的新口径未公开明示，需实测**）

**可绕开的方式**（供参考，未验证）
- Pipeline 支持 **Inline 存储模式**（YAML 存在 Harness 里，**不需要 Git**）——但 CI 构建仍需 codebase
- 可用 **Custom stage + Delegate** 直接跑脚本（Delegate 跑在本机时能访问本地目录）——可行但偏 hack
- 或把代码镜像到 GitHub 再接入

**判定**：**技术可行，但前置成本明显高于收益**。若目标只是"每次 push 自动跑 pytest"，GitHub Actions / Gitee Go 摩擦小一个数量级；若目标是"评测门禁"，可以先用轻量 CI 实现同样的东西，把 Harness 留给路径 A。

## 四、Dify

### 4.1 关键发现：Dify 应用可被暴露为 MCP Server（源码实证）

> 以下均为**本地 Dify 1.17 源码实读**，非文档推测

| 证据 | 位置 | 内容 |
|---|---|---|
| MCP 服务端路由 | `api/controllers/mcp/mcp.py` | `POST /mcp/server/<server_code>/mcp`，JSON-RPC 2.0；协议版本由 `MCP-Protocol-Version` 头协商；支持结构化输出需协议 ≥ `2025-06-18` |
| 服务端实现 | `api/core/mcp/server/streamable_http.py`（379 行） | `handle_mcp_request` 分发 `Initialize` / `ListTools` 等；`handle_list_tools(app.name, app.mode, user_input_form, ...)` |
| 工具入参形态 | 同文件 `ToolArgumentsDict` | `query` + `inputs`（由应用的 user_input_form 决定）→ **一个 App ≈ 一个 MCP 工具** |
| 控制台管理 | `api/controllers/console/app/mcp_server.py` + `AppMCPServer` 模型 | 可为 App 创建/更新/启停 MCP Server（`server_code` / `status` / `parameters`） |
| 数据迁移 | `2025_06_25_..._add_mcp_server_tool_and_app_server.py` | 同时引入「MCP server 作为工具」与「App 作为 server」两条能力 |
| 客户端能力 | `api/core/mcp/mcp_client.py`、`client/`（streamable / sse） | Dify 自身也能作 MCP Client |

**结论**：AgentForge 的 MCP 客户端可以连 Dify 的 `/mcp/server/<server_code>/mcp`，把「调用陪跑应用」当成一个工具。

### 4.2 路径 A：当工具挂进 AgentForge ✅ 可行

**接法**：同 §3.2，只是目标端点换成 Dify 的 MCP server。你已发布的 `陪跑` 应用可直接用。

**含金量**
1. **平台互操作的真实案例**：一个自研 Agent Runtime 驱动一个企业主流平台的应用
2. **架构红线不破**：走的仍是 PRD 的 Tool Registry + MCP 客户端，**不违反"业务代码不得绕过 Gateway"**
3. 顺带证明你**两边都摸过**——这比"我只用过 Dify"或"我只自研过"都强

**前置**：几乎为零（应用已有，MCP server 在控制台开启即可）。⚠️ 待实测：Dify 控制台开启 App MCP Server 的具体步骤与鉴权方式（我只读到代码，没走通 UI 流程）。

### 4.3 路径 B：当对照基线 ✅ 可行（零代码）

同一批问题分别喂给 Dify 应用与 AgentForge，用 AgentForge 的 judge 给两边打分，产出对比报告。

**含金量**：把 `PRD §2.3`「为什么自建而非用 Dify」从一张**论证表**变成**实测数据**。面试官最难反驳的就是这种。JD 中有 3 份（JD1/JD2/JD7）点名 Dify，这个实操经验本身也值钱。

**前置**：评测体系先落地（PRD D20–D24）。Dify 侧接口已全验证通（`X-App-Code` → `GET /api/passport` → `X-App-Passport` → `POST /api/chat-messages`）。

**注意**：Dify 侧每题消耗 DeepSeek token（含推理过程），题目量建议 ≤30。

## 五、Agentic BI

### 5.1 定义（已查证）

Agent 自主规划多步分析、跨（多）系统取数、执行中间分析、自我校验，交付**带引用、可审计**的结论。**关键区别是"自主多步"**（单次问答属于上一代 ChatBI）。参考框架：连接 → 语义理解 → 规划查询 → 交付行动 → 审计（语义层是公认前置）。

### 5.2 与 AgentForge 的关系：结构同构

| 维度 | AgentForge 现状 | Agentic BI |
|---|---|---|
| 输入 | 非结构化文档 | 结构化数据表 |
| 流程 | 规划 → 检索 → 综合 → **带引用输出** | 规划 → 查数 → 多步分析 → **带引用结论** |
| 共同骨架 | **规划 → 取数 → 综合 → 引用/审计** | 同 |

**AgentForge 的场景 B（库存表查询）本质就是一个三行的 Agentic BI。**

### 5.3 三个接入点（都不推翻架构）

| # | 接入点 | 具体做法 | 复用现有 |
|---|---|---|---|
| 1 | **分析工具** | Tool Registry 注册 `analytics_query`（或按业务拆多个），Agent 自主决定何时调用 | Tool Registry（D8）零改动 |
| 2 | **轻量语义层** ★ | `data/metrics.yaml` 定义指标名 / 口径 / 维度 / SQL 模板；Agent **先查语义层再生成 SQL** | 新增约 1 个模块（前沿点所在） |
| 3 | **前端图表** ★ | React + ECharts 渲染查询结果（你现有前端栈） | 你的主场，UI 阶段（D29–D31） |

### 5.4 含金量

1. **"自主多步"是真正的前沿点**：单次 NL2SQL 已不新鲜，**多步自主分析 + 自我校验**才是 2026 年 Agentic BI 的定义
2. **语义层是稀缺能力**：能讲清"为什么不能直接让 LLM 生成 SQL、指标口径为什么必须先治理"——这是**设计判断**，不是调库
3. **演示冲击力最强**：从"问文档答文档"升级为"问业务问题 → 多步查数 → 出图 → 给结论"。**且恰好用上你的前端能力**，别人抄不了
4. **审计闭环现成**：Langfuse 已经能承载"每一步分析了什么"的轨迹

**前置**：语义层文件 + 一个查询工具 + 前端图表组件。**不含**完整 BI 平台（权限、调度、订阅那套）。

## 六、具体接入路径（v4 新增）

> 本章回答"**怎么接**"——每一步落到可执行动作。原则：**不新写模块，只往已有扩展点上挂东西。**

### 6.1 两条路的本质差异

| | Harness.io | Agentic BI |
|---|---|---|
| 接的是什么 | **别人写好的 server 进程**（Harness 官方代码） | **你自己的工具函数**（项目内代码） |
| 走什么协议 | MCP（需要写 client） | 无协议，复用现有 Tool Registry |
| 新增代码 | 一段 server 注册配置 + `.env` 一行 | 工具函数 + `metrics.yaml` + 前端图表组件 |
| 新增概念 | 无（MCP 协议本就在 PRD 计划内） | **指标语义层**（唯一的新概念） |
| 难点在 | 子进程生命周期、PAT 安全、首次启动预热、工具集裁剪 | 指标口径设计、SQL 注入防护、多步编排的提示词 |
| 跑的是谁的代码 | Harness 官方（迭代极快） | 你的 |
| 加的含金量类型 | **协议层**：能与企业系统互操作 | **能力层**：能自主多步分析 + 用上前端主力 |
| 面试会问 | "你做过 MCP 互操作吗？" | "你怎么保证 Agent 写的 SQL 是对的？" |

**一句话区分**：Harness 证明"我的 Agent **能接进别人的系统**"；Agentic BI 证明"我的 Agent **能自己分析数据并讲出结论**"。

### 6.2 Harness.io：怎么接入（五步）

#### 🔑 起点：PRD 已经定义好了接入点

`PRD §11 API 设计` 中已有：

| 方法 | 路径 | 说明 | 请求 | 响应 |
|---|---|---|---|---|
| POST | `/api/mcp/register` | 注册 MCP 服务 | `{command, args}` | `{tools:[...]}` |

**这个接口就是为接 Harness 这类外部 server 准备的。** 接 Harness **不需要新写模块**，只需要让这个接口实例化出来（D27）、然后往里发一段配置。

#### 第 1 步：拿 PAT

`app.harness.io` → My Profile → API Keys → + New API Key → 在其下创建 Token。
得到形如 `pat.<accountId>.<tokenId>.<secret>` 的凭证。**account id 内嵌于 PAT，无需单独配置**。

#### 第 2 步：写入 `.env`（项目铁律 6：绝不入库）

```
HARNESS_API_KEY=pat.xxx.yyy.zzz
```

`.gitignore` 必须已包含 `.env`。建议 PAT 权限最小化（pipeline 只读 + execute）。

#### 第 3 步：调用自有注册接口

```bash
curl -X POST http://localhost:8000/api/mcp/register \
  -H 'Content-Type: application/json' \
  -d '{"command":"npx",
       "args":["-y","harness-mcp-v2@latest"],
       "env":{"HARNESS_API_KEY":"pat.xxx.yyy.zzz"}}'
```

返回 11 个工具的名字 + 描述 + 参数 schema。

#### 第 4 步：`mcp_client.py` 的动作（**这段是 D27 原计划内容，不是为 Harness 新写**）

1. `subprocess` 启动 `npx -y harness-mcp-v2@latest` 子进程
2. 走 **stdio** 发 `initialize` 握手（协议版本协商）
3. 发 `tools/list` 取回工具清单
4. 逐个 `ToolRegistry.register(name, description, schema, handler)`
5. 子进程**常驻**；Agent 触发调用时，把 LangGraph 的 `tool_call` 翻译成 JSON-RPC 的 `tools/call`

#### 第 5 步：验证

问一句"我最近有哪些流水线失败了" → 观察 Agent 是否选中 `harness_list(resource_type="execution")` → 打开 **Langfuse** 确认这次工具调用被完整追踪。

#### ⚠️ 四个必须提前知道的工程细节

| # | 细节 | 影响与对策 |
|---|---|---|
| 1 | **stdio 模式 = 常驻 Node 子进程**，不是 HTTP 调用 | client 必须实现生命周期管理（启动 / 健康检查 / 崩溃重启 / 退出清理），否则会泄漏 Node 进程。这也是 PRD F6.3 的真实分量 |
| 2 | **首次启动慢**：`npx` 要拉包；若开启语义检索还要下载约 23MB 的 ONNX 模型 | **演示前必须预热**，否则第一问会卡十几秒。同时应**锁定版本号**（该仓库近乎每日提交） |
| 3 | **写操作有风险分级**：`HARNESS_AUTO_APPROVE_RISK`（none / low_write / medium_write / high_write / all），可按 session 收紧（只能降不能升） | 初期用 `none` 或 `low_write` 只读。**这套机制是 PRD「权限 / 护栏」缺失项的现成参考**，可讲成"我参考 Harness 的 auto-approve risk 分级，为工具层设计了写操作确认门" |
| 4 | **41 个 toolset 全开会塞满上下文** | 按需开启（只开 CI/CD 相关）。官方明确取舍：**工具数膨胀会降低 LLM 选工具的准确率**——与你 Tool Registry 未来会撞到的问题同一个 |

#### 含金量的准确表述

- PRD **S7「≥1 个真实外部工具」**从"内存 mock 库存"升级为"真实企业平台"。**注意**：不是说不写 D26 的 `inventory_server` 了——**自己写 server（理解协议两端）+ 接别人的 server（证明互操作）两件事都做，才是完整的 MCP 能力证明**。
- `harness_diagnose` 自带**失败分类**（六类），Agent 可直接做"诊断 + 给建议"，是 AI-for-DevOps 的典型落地（2026 年最热场景之一）。
- 一次动作覆盖两项 JD 要求：高端第 2 项（企业级工程化）+ MCP 协议（JD2 / JD7）。

### 6.3 Agentic BI：怎么接入（三样东西）

**与 Harness 的本质不同**：Harness 接别人写好的 server；Agentic BI 是**你自己写三样东西**。

#### 第 1 样：工具函数（`app/tools/analytics.py`）

```python
@tool
def query_metric(metric: str, dimension: str | None = None,
                 start_date: str = "", end_date: str = "") -> dict:
    """按口径查询业务指标。可用指标名与维度见 metrics.yaml。"""
    spec = METRIC_REGISTRY[metric]                      # 从 metrics.yaml 加载
    if dimension and dimension not in spec.dimensions:
        raise ValueError(f"不支持的维度: {dimension}")   # 白名单校验
    sql = render(spec.sql_template, dimension=dimension)  # 模板渲染，非自由生成
    return {"metric": metric, "rows": db.fetch_all(sql, start_date, end_date)}
```

> ### 🎯 这是整件事的技术核心
> **LLM 不写 SQL。LLM 只选三样：指标名、维度、时间范围。SQL 由 `metrics.yaml` 的模板渲染。**
>
> 这一条直接消掉了 Agentic BI 最大的翻车点（模型生成的 SQL 跑错 / 跑废）。面试被问"你怎么保证 NL2SQL 不出错"，最强答案不是"我加了校验"，而是"**我没让它写 SQL**"。

#### 第 2 样：指标语义层 `metrics.yaml`（约 20 行，唯一的新概念）

```yaml
metrics:
  inventory_turnover:
    label: 库存周转率
    description: 出库量 / 平均库存，衡量库存健康度
    table: inventory_movements
    time_column: occurred_at
    dimensions: [warehouse, sku, category]     # 白名单：注入防护的依据
    sql_template: |
      SELECT {dimension} AS dim,
             SUM(qty_out)::float / NULLIF(AVG(qty_on_hand), 0) AS value
      FROM inventory_movements
      WHERE occurred_at >= :start AND occurred_at < :end
      GROUP BY {dimension}
      ORDER BY value DESC
```

`{dimension}` 只能取 `dimensions` 白名单内的值，日期走参数绑定 → **SQL 注入防护顺带就有了**。语义层是 Agentic BI 公认的前置条件，这 20 行就是它。

#### 第 3 样：前端图表（`frontend/` React + ECharts）

关键设计：`query_metric` 返回的是 **dict 而非字符串**。工具吐结构化数据 → 前端直接把 `rows` 喂给 ECharts。
**这是你前端主力唯一能用上的技术路径**，也是演示冲击力最强的部分。

#### "自主多步"实际长什么样（与上一代 ChatBI 的分界线）

```
用户："上个月哪个仓库周转最慢？为什么？"
 ① Agent 调 query_metric(metric="inventory_turnover", dimension="warehouse")
     → 西安 1.2 / 上海 3.8 / 成都 4.1  →  Agent 自行判断西安最慢
 ② Agent 自己决定再深入一步：
     query_metric(metric="inventory_turnover", dimension="sku")
     → 定位到西安某 SKU 出库量骤降
 ③ 出图 + 结论 + 数据出处
```

①②之间**没有人类介入**，是 Agent 自己决定"要再查一步"——**这就是"自主多步"，也是 Agentic BI 与单次问答（ChatBI）的真正分界**。

#### 前置与边界

- 前置：一个查询工具 + 一张事实表（PRD 场景 B 的库存表可用）+ `metrics.yaml`
- 不做的：完整 BI 平台（多步校验、审计轨迹、复杂图表体系属于一个阶段的工作量）
- 评测接入：PRD 评测集类型 C（工具调用 10 条）中放 2–3 条多步分析题即可覆盖

## 附录 A：术语撞名说明 —— 两个 "Harness"

> **保留原因**：`JD/Agent开发岗位JD总结.md` 中 JD2 所写的「Agent Runtime / Agent Harness 能力」指的是**智能体侧**能力（会话管理、上下文管理、记忆、状态持久化、可观测、LLM Gateway），**与 Harness.io 无关**。两部分都有用，但**不可混用**。

**Agent Harness** = 包在语言模型外面的**运行时外壳**，把"文本生成器"变成"能行动的 agent"。职责：执行循环、工具执行、上下文管理、记忆与状态持久化、护栏/权限、错误恢复、可观测。

关键区分：
- **框架 ≠ harness**：LangGraph 是"写 agent 的工具箱"；harness 是**生产里跑起来的装配系统**
- **四层不同**：framework（怎么写）→ harness（怎么跑得可靠）→ orchestrator（多个怎么协作）→ gateway（什么能过界）
- **能力比例**：同模型 SWE-bench，基础脚手架 ~23% vs 优化 harness 45%+ → **能力差异一半来自 harness**

逐条对照（AgentForge 现状）：

| # | 职责 | 现状 | 判定 |
|---|---|---|---|
| 1 | 执行循环 | D6 ReAct，5 步上限 | 完成 |
| 2 | 工具执行与路由 | D8 Registry 已通；MCP 未接 | 部分 |
| 3 | 上下文管理（压缩/摘要） | 滑窗有，摘要无 | 部分 |
| 4 | 状态持久化 | `sessions`/`messages` **0 行**，Redis 重启即丢 | **缺失** |
| 5 | 权限 / 沙箱 / 预算 | 完全没有 | **缺失** |
| 6 | 错误恢复 | 重试 1 次，无 checkpoint | 部分 |
| 7 | 可观测 | LLM 埋点通，三层未核实 | 部分 |
| 8 | 统一模型入口 | Gateway 双通道 | 完成 |

**核心发现**：缺失的第 4 项 + 部分的第 3 项，**恰好就是 PRD D10 那一整天的欠账**。

⚠️ **话术风险**：不要写"我造了一个 Agent Harness"（第 4、5 项是空的，会被打穿）。准确说法：「我在做 Agent Runtime 的核心组件：ReAct 循环、工具注册、上下文与状态管理、LLM Gateway、全链路追踪；安全和预算是下一步」。
