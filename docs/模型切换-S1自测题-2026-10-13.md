## 第二部分：参考答案（建议先自答再看）

### Q1

**L1**：运行环境设了 `HTTP_PROXY`（本机代理，如 `127.0.0.1:56908`）；httpx 默认 `trust_env=True`——"信任环境变量里的代理设置"。于是对 `127.0.0.1:9` 的请求被交给代理；代理连不上 9 端口，**自己回了一个 502**。错误翻译看到 5xx → 走"端点内部错误（端点服务方的问题）"分支。真实原因（端口没开 = 连不上）被改写成了**误导性的方向**。

**L2**：因为"走代理"是用户所在网络环境的真实策略——很多网络（尤其外网访问）必须走代理才能出去；全局禁掉会把**外网**探测/调用搞坏。而"本机/内网地址走公网代理"本身毫无意义，且必然产生假错误。所以按目标地址分叉：`localhost / 127.0.0.1 / host.docker.internal / *.local` → `trust_env=False`（直连）；外网 → 保持跟随环境。

**L3**：先怀疑"代理拦截/改写"。验证三步：① 同一端点，直连 vs 走代理对比（`curl --noproxy '*'`，或代码里临时 `trust_env=False`）；② 看 502 是谁回的——检查响应特征（代理返回的 502 与真实端点错误不同，比如响应头、连接时序）；③ 换一个网络环境（或不设代理）复测。若直连正常、走代理 502 → 是网络策略问题，不是端点配置问题。现在的 502 文案已提示"可能是代理/网关拦截"。

### Q2

**L1**：后端**跳过 `api_key` 列的更新**——service 层 `if payload.api_key:` 为假（None 和 "" 都算），就不写这一列；其余字段（name / base_url / model 等）照常更新。库里的 key 原样保留。

**L2**：编辑弹窗回显的 key 是**打码值**，用户拿不回明文。如果"提交空 = 清空 key"，那么用户**只是改个名字**就会把自己的 key 抹掉 → 下一次调用直接 401；而用户通常没有留底，等于要回去重新申请/翻找 key。也就是说，"编辑"这个动作本身会破坏数据。

**L3**：因果链：出口必须打码（安全底线）→ 前端回显只能拿到打码值（明文拿不回来）→ 用户提交的 key 字段天然只有两种内容："空"或"打码值"（不可能提交原文）→ 因此后端必须把"空"定义为"不修改"（若定义为清空，则"编辑"与"打码"互相掐死：要么为了能编辑而回显明文——泄露；要么一编辑就毁 key——事故）。两条规则是一套闭环，缺一条另一条就变成 bug。

### Q3

**L1**：规则：保留**前 3 位 + 后 4 位**，中间替换为 `***`（例：`sk-***f855`）；长度 ≤ 8 的 key 整体打掉。为什么前 3 后 4：**后 4 位是常见的"辨识位"**（用户习惯靠尾巴认 key），前 3 位如 `sk-` 前缀能帮助识别类型；而真正的随机熵在中间——打掉中间就无法复原，兼顾"能辨认"与"不能复原"。

**L2**：SQLAlchemy 模型默认的 `__repr__` 会**打印所有列的实际值**。只要代码里任何地方写了 `logger.info("row=%s", row)` 这类"看似无害"的调试日志，**明文 key 就会随日志流出去**（日志常被采集、转发、长期留存）。在 `__repr__` 里打码 = 把泄露点焊死在出口，不依赖"每个人都记得别 log 它"。

**L3**：断言要打在**原始响应文本**上：拿整个 HTTP 响应的原文（raw text），断言"明文 key 子串不在其中"（如 `assert "sk-verify-12345678" not in raw`），而不仅检查规定的打码字段格式——因为泄露可能发生在**任何**字段或多余输出里。S1 的集成测试就是这样写的（"列表响应原文里不得出现任何明文 key"）。更严格：用一个**唯一**的 key 构造模型，对 list / create / patch / test 所有接口的原始响应逐一做 not-in 检查。

### Q4

**L1**：① **观测噪音**：探测是运维诊断动作，不是业务调用；走网关会在 Langfuse 里每次点按钮都留下一条 generation，污染真实业务调用的观测数据。② **语义被改写**："测试连接"要回答的是"**我这个配置**通不通"；而网关带降级链——主通道失败会静默切到备用通道，最终测到的可能已经不是这个配置，答非所问。

**L2**：被网关的**主备降级链**（`_call_with_failover`）改写。不可接受的原因：探测的价值几乎全在**失败分支**（帮用户定位配置问题）；如果备用通道"救活"了请求，用户会收到一个"成功"，拿着**坏的配置**去保存/使用，真实对话失败时更摸不着头脑。测试必须如实报告"这个配置"的结果。

**L3**：因为"通或不通"正是这个接口要回答的**问题本身**——"不通"是一个**成功的诊断结果**，不是协议层错误。若用 4xx/5xx：① 同一件事要在两个地方处理（HTTP 层 + 响应体），前端得写两套分支；② 失败诊断的结构化信息（ok / error / 耗时 / 具体原因）没有一个统一错误码能自然承载——401、404、超时、连不上语义各异；③ 会把"调用我们接口本身失败"（网络断、服务崩）与"被测端点不通"混淆——后者 HTTP 应为 200（**我们的系统是正常的**，是探测对象不通）。
