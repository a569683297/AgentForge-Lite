## 一、为什么"分析自己"而不是"分析业务"

原 PRD 定位是**企业知识库问答平台**，它的数据模型（`sessions` / `messages` / `documents` / `document_chunks`）**全部围绕 RAG 场景**，`app/models/` 实测也只有这 4 张表。

因此 Agentic BI 的数据源不能外挂一套虚构的业务库（库存等），否则业务语境断裂——"一个知识库问答项目为什么管库存"这句话面试必须答得出。

**正确切入点是：这个系统自己就在源源不断地生产结构化数据。** Agent 平台的使用者（运营者/开发者）需要知道自己系统跑得怎么样，这是自洽的真实需求，也恰好是 AI 平台团队的真实日常工作。

## 三、第①层逐表：字段 → 可分析问题

### 3.1 `sessions` ✅ 已建
字段：`id` / `title` / `summary` / `created_at` / `updated_at`

| 可分析问题 |
|---|
| 会话总量与按天趋势 |
| **摘要触发率** = `count(summary IS NOT NULL) / count(*)` —— 验证摘要记忆是否真的被触发 |
| 会话平均时长 = `avg(updated_at - created_at)` |
| 活跃度分布（长会话 vs 单问单答） |

> ⚠️ **当前实测 0 行**（D10 欠账未补，摘要记忆整块没做）。这张表要产出数据，前提是先补 D10。

### 3.2 `messages` ✅ 已建
字段：`id` / `session_id` / `role(user/assistant/tool)` / `content` / `tool_calls` JSONB / `tool_results` JSONB / `created_at`

| 可分析问题 |
|---|
| 消息量趋势、角色分布 |
| **对话轮次分布**（每会话消息数）→ 验证"8 轮滑窗"这个参数设得对不对 |
| **工具调用频次**（`tool_calls` 非空占比、按工具名聚合）→ 哪个工具最常被调 |
| 平均回答长度、超长回答占比 |

> ⚠️ `tool_calls` 是 JSONB，聚合需 `jsonb_array_elements` 展开。**这会让语义层模板复杂一档**——见 §五 的工程注意。

### 3.3 `documents` ✅ 已建
字段：`id` / `filename` / `file_type(pdf/docx/md/txt)` / `status(processing/ready/failed)` / `chunk_count` / `error_message` / `created_at`

| 可分析问题 |
|---|
| 文档数与类型分布 |
| **处理成功率** = `count(status='ready') / count(*)` |
| **失败原因分布**（`error_message` 聚类） |
| 平均切片数 / 文档；找出异常值（某文档 1000 切片 = 分块异常） |

### 3.4 `document_chunks` ✅ 已建 ← **分析价值最高**
字段：`id` / `document_id` / `content` / `page_ref` / `title_path` / `embedding` / `content_tokens` / `content_tsv`

| 可分析问题 |
|---|
| 切片总量 |
| **切片质量：长度分布 / 空切片 / 超短切片（< 50 字）占比** |
| 每文档切片数分布，识别异常分块 |
| `title_path` 覆盖率（标题层级是否解析成功） |
| `page_ref` 覆盖率（引用可定位性的前置，直接关系 S5 引用覆盖率 ≥ 90%） |

> **这张表是根因层。** 检索效果差的答案通常不在检索算法里，在切片质量里。

### 3.5 `eval_cases` ⬜ 未建（PRD 已定义）
字段：`id` / `category(doc_qa|cross_doc|tool_call|multi_step)` / `question` / `reference` / `doc_ids UUID[]` / `expected_tool` / `expected_call_sequence`(v4 新增) / `created_at`

| 可分析问题 |
|---|
| 题库构成（4 类分布）、覆盖度是否均衡 |
| 各题目关联文档数分布 |

### 3.6 `eval_runs` ⬜ 未建（PRD 已定义）← **最自然的图表数据源**
字段：`id` / `config_name(pure_vector|hybrid|hybrid_rerank)` / `score_correctness` / `score_faithfulness` / `score_completeness` / `accuracy` / `report_path` / `created_at`

| 可分析问题 |
|---|
| **准确率趋势**（按时序折线） |
| **三配置横向对比**（消融实验 A/B/C）→ 直接支撑 S2「混合+重排 vs 纯向量 ≥ +10%」 |
| **三维度得分对比** → 定位最弱维度（通常是 faithfulness） |
| 配置 × 维度交叉（哪个配置在哪个维度收益最大） |

### 3.7 `mcp_servers` ⬜ 未建（v4.0 新增）
字段：`name` / `is_builtin` / `command` / `args` / `env_keys` / `toolsets` / `risk_policy` / `status` / `tool_count` / `last_error` / `created_at` / `updated_at`

| 可分析问题 |
|---|
| MCP server 连接成功率（`status='connected'` 占比） |
| 工具数量分布：自研 vs 外部 |
| 错误率与 `last_error` 聚类 |
| `risk_policy` 分布（写操作防护的配置覆盖情况） |

## 四、第②层：Langfuse（⚠️ 不在项目库里）

Langfuse 有**自己的数据库**。以下数据项目会产生，但**不在项目 PostgreSQL 中**：

| 数据 | 能回答的问题 | 对应验收指标 |
|---|---|---|
| LLM 调用 | 延迟 P95、token 消耗与成本 | S4（P95 < 5s） |
| 检索与重排 | 召回数、**各段耗时拆解**（embedding / 向量检索 / BM25 / rerank / 生成，哪一段最慢） | 性能优化依据 |
| 工具与轨迹 | MCP 调用链路（含 `mcp_server_name` / `tool_name`，F8.4） | S6、S10 |

> **⚠️ PRD 缺口**：F8 只写了"埋点 + 面板展示"，**没有写"Langfuse 数据回流给 Agent 分析"**。
> 要让 Agent 回答"我最近的延迟为什么涨了"，必须先有一条 **Langfuse REST API 取数通道**。这是 v4.1 需要补的一句话。

## 五、第③层：缺口清单

| 缺口 | 影响 | 补齐成本 | 现状 |
|---|---|---|---|
| **`eval_case_results`**（单用例得分明细） | 没有它，"哪类用例失分最多""哪个维度最弱的原因"**全答不出来**——`eval_runs` 只有汇总分 | 1 张表 + 评测写入逻辑 | **v4.0 PRD 中不存在** |
| **Langfuse 取数通道** | 延迟/token/成本类问题答不出 | 1 个 API client | PRD 未设计 |
| **`tool_call_log`**（工具调用独立表） | "工具调用排行/成功率"只能从 `messages.tool_calls` JSONB 挖，或查 Langfuse | 1 张表 | PRD 未定义 |

> `eval_case_results` **不是为 BI 硬加的**——PRD §9.5 的报告结构本来就要求"失败案例各取 3 条"，这张表是评测功能自身就该有的，之前漏了。

### 语义层的工程注意（重要）

`messages.tool_calls` 是 JSONB，聚合需 `jsonb_array_elements` 展开。**建议首版语义层不纳入 JSONB 指标**——语义层的价值在于"模板固定、只换维度"，JSONB 展开会让模板变得难读且易错。工具调用排行优先走 `tool_call_log`（若补）或 Langfuse。

## 六、跨表下钻链（这才是"多步分析"的真场景）

单表聚合是简单指标，**跨表下钻才是 Agentic BI 与普通问答的分界**。

> ⚠️ **以下三条链中的具体数值（82→85→88%、62% 等）均为示意，不是实测数据。** 它们描述的是"这条链跑通后会得到什么形态的结论"，用于验证可行性；真实数值需项目跑完评测后才产生。

### 链 1：评测质量自诊断（4 跳，跨 4 张表）

```
① eval_runs          → 近三次准确率 82 → 85 → 88%，但 faithfulness 恒为三维度最低
② eval_case_results  → 按 category 聚合，cross_doc 类得分最低     ← ⚠️ 依赖缺口表
③ eval_cases         → 取出 cross_doc 原题，失分集中在 5 条
④ document_chunks    → 这 5 条题引用的文档，超短切片占比 62%
                       结论：问题在分块策略，不在检索算法
```
**跳过第②跳，第③④跳就无法收敛** —— 这是补 `eval_case_results` 的最强论据。

### 链 2：文档入库质量 → 检索效果归因（3 跳）

```
① documents        → 处理成功率 95%，但 3 篇文档 chunk_count 异常偏高
② document_chunks  → 这 3 篇的超短切片占比 > 50%
③ eval_runs        → 这 3 篇恰好是 cross_doc 类题目失分最多的引用来源
                       结论：重做这 3 篇的分块参数，预期 cross_doc 类提升
```

### 链 3：外部工具健康度（2 跳）

```
① mcp_servers      → harness 状态 connected，tool_count 11
② Langfuse（需通道）→ 该 server 的工具调用成功率 92%，2 次超时
```

## 七、`metrics.yaml` 指标候选（v4.1 的直接输入）

首批建议 **6 个指标**，全部来自系统自身数据、全部可 SQL 直查：

```yaml
metrics:
  retrieval_accuracy:          # 检索准确率趋势
    label: 检索准确率
    table: eval_runs
    time_column: created_at
    dimensions: [config_name]  # 白名单 = 枚举列
    # 支撑 S2 消融对比 + 趋势折线

  eval_dimension_scores:       # 三维度得分（需 UNION 三列转行）
    label: 评测维度得分
    table: eval_runs
    time_column: created_at
    dimensions: [score_type]   # correctness / faithfulness / completeness
    # 定位最弱维度

  eval_failures_by_category:   # ★ 明细指标，用于下钻
    label: 分类失分
    table: eval_case_results   # ⚠️ 依赖缺口表
    time_column: created_at
    dimensions: [category]
    # 链 1 的第②跳

  doc_processing_success:      # 文档处理成功率
    label: 文档处理成功率
    table: documents
    time_column: created_at
    dimensions: [file_type, status]

  chunk_quality:               # ★ 明细指标，用于下钻
    label: 切片质量
    table: document_chunks
    time_column: (需 join documents.created_at)
    dimensions: [document_id]
    # 长度分桶：空切片 / <50 字 / 正常

  conversation_volume:         # 对话量
    label: 对话量
    table: sessions
    time_column: created_at
    dimensions: [title]        # 粒度待定，可能改为按天分桶
```

**关键观察**：`dimensions` 白名单对系统数据**比业务数据更自然**——维度就是表里的枚举列（`config_name` / `status` / `file_type` / `category` / `role`），白名单边界清晰、无需人为设计。

**指标数**：4 个单表聚合 + **2 个明细下钻指标**（`eval_failures_by_category` / `chunk_quality`）—— 后者是 PRD F11.1 要求的"≥ 1 个用于下钻的明细指标"，本方案给了 2 个。

## 八、诚实的限制

| 限制 | 说明 | 应对 |
|---|---|---|
| **数据量小** | demo 级规模，评测跑 3 次只有 3 个点，会话数十个。时序趋势说服力弱 | 强调**对比**（三配置横比）而非**时序**；消融矩阵 A/B/C + 复跑可造出 3–6 个点。面试被问"数据量够吗"就用这个答 |
| **数据靠"跑"出来** | 没有真实用户，数据靠主动跑评测/传文档积累 | 演示前必须**先跑 ≥ 2 次评测**、上传 ≥ 10 篇文档（已写入 v4.0 §17.3 清单） |
| **D10 欠账** | `sessions`/`messages` 实测 0 行，对话类分析**当前无数据** | 补 D10（摘要记忆 + 落库）是所有对话类指标的前置 |
| **Langfuse 不互通** | 延迟/成本类数据在外部系统，Agent 当前拿不到 | 补 Langfuse API 取数通道（v4.1 待定） |
| **无用户反馈数据** | PRD 没有点赞/点踩功能，"答案满意度"无数据源 | 明确不做；评测分作为质量代理指标 |
