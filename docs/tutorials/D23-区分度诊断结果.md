## §1 怎么跑的

> **名词先注解**：**消融**（ablation）指"只改一个变量、其余全部锁死，跑两次以上看差异"。
> 本项目要消融的**唯一自变量**是 `settings.retriever_config`（检索配置），三档分别是：
> - **A `pure_vector`** —— 只用向量相似度检索（"意思像"就命中）
> - **B `hybrid`** —— 向量 + BM25 关键词检索，两路结果融合
> - **C `hybrid_rerank`** —— 在 B 的基础上再加重排（用交叉编码器把候选重新排序）

| 项 | 值 |
|---|---|
| 配置 | A / B / C 各跑一轮（`generation_runs=1`、`judge_runs=3`） |
| 题量 | 50 条（`doc_qa` 30 + `cross_doc` 10 + `tool_call` 10） |
| 评测集指纹 | `a7797b06e2fa8f824a2db3f1254fbebc01c7e4cf3b117ad793677706c0b90afe` |
| 语料指纹 | `5783a666517cae4a6327f24823e8df4bfd6d9c42b836bc04194ad96df6bbdcc9` |
| 实测耗时 | A 2 分 37 秒 · B 2 分 33 秒 · C 3 分 25 秒（**合计 8 分 37 秒**） |
| 实测成本 | 742 次 LLM 调用 / **158.3 万 token**（比预估 200 万略低） |
| run_id | A=**4** · B=**5** · C=**6**（表里 id=1 是 D22 的小规模实跑，`generation_runs=2`，已按 `generation_runs=1` 过滤排除） |

> **为什么三配置都要跑**：C 已在天花板，位置无法再高 → 若"重排带来提升"要能体现，只能靠 **A 更低**。
> 只跑 C 一个配置，等于**没有对照组**，什么也证明不了。

## §4 核心发现：13/15 条失败是评测集自身的缺陷

### 4.1 现象

`tool_call` 类题（C 类，考"该不该调工具"）的失败率高得不正常：**30 条明细里 13 条失败**，
而 `doc_qa` 类 **90 条明细全部通过**。

### 4.2 根因

翻出 C 类题的 `reference`（**参考答案**——judge 打分时拿它当"标准答案"逐点比对）：

```
C01~C04 :  应当调用 search_documents 工具完成该请求。理由：答案在知识库制度文档里，必须先检索
C05~C07 :  应当调用 current_time 工具完成该请求。理由：问的是当前时刻，属于实时信息，知识库里没有
C08~C10 :  不应当调用任何工具，直接回答即可。理由：闲聊兼能力询问，没有需要外部信息的成分，调工具反而多余
```

**这 10 条题的 `reference` 全部是"给评测者看的元说明"**（说明"这题考什么"），
**没有一条写了答案内容**。

而 judge 看到的是一句话："**以下是这道题的标准答案**"，然后收到"应当调用 current_time 工具完成该请求"。
→ 它会要求**候选答案本身去声明/执行工具调用**。
→ 但候选答案是一段**回答内容**（"现在是 2026 年 9 月 29 日 09:33:27。"），不含"我调用了工具"这句话。
→ **judge 判定"未按要求执行" → 正确性 0 分、完整性 0 分。**

### 4.3 证据链（C05 完整对照）

| 项 | 内容 |
|---|---|
| 题面 | 「现在几点了？」 |
| `expected_tool` | `current_time` ← **"要不要调工具"这个约束本来就在这里**（结构化字段） |
| `reference` | "应当调用 current_time 工具完成该请求。理由：…" |
| **系统实际行为** | 调用了 `current_time` 工具 ✅，回答"现在是 2026 年 9 月 29 日 09:33:27。" ✅ |
| **judge 判定** | **correctness = 0**（理由原文："参考答案要求调用检索工具，待评答案直接给出了…，未按要求执行"） |

**系统完全做对了，却被判失败。**

### 4.4 关键细节：为什么 C01~C04 反而过了？

同一句"应当调用 search_documents 工具…"，C01~C04 在三配置下全部得 5 分，C05~C08 全部得 0 分。
C02 更极端：**A 配置下 0 分、B/C 配置下 5 分，而三份答案的内容几乎相同**（三次打分两次 0 一次 5）。

→ **judge 在这类歧义输入上的判定是随机的**：
它有时把"答案里带 `[1]` 标注 / 内容有据可查"理解为"确实按要求检索了"（给 5），
有时把"答案没声明调用工具"理解为"没按要求执行"（给 0）。

**这就是 `C02` 那条"配置差异"的真相——它是抽签，不是配置的效果。**

### 4.5 影响面

| 类别 | 明细数 | 失败 | **其中假失败** |
|---|---|---|---|
| `doc_qa` | 90 | 0 | 0 |
| `cross_doc` | 30 | 2 | **0** |
| **`tool_call`** | 30 | **13** | **13（100%）** |

**受影响的是 C 类全部 10 条题的 30 条明细**（其中 13 条实际踩中、17 条侥幸得 5 分）。

## §6 这个 bug 为什么一直没被发现

这是本文档最该记住的部分 —— **它不是运气问题，是三个结构性原因**：

| # | 原因 | 说明 |
|---|---|---|
| ① | **"稳定的假失败"比随机噪声更难发现** | C05~C08 在**三个配置下一致失败**，看起来像一个可靠的信号（"系统在这 4 类问题上确实不行"）。**随机噪声至少会自己抖出来**，而稳定的假信号会被当成结论收下 |
| ② | **D22 的小规模实跑恰好避开了它** | 那次只跑 4 题，其中 C 类题是 C01/C02 —— 而那一次 judge **全部给了 5 分**。**样本小 → 恰好全好 → bug 隐藏**（同 D20「第 1 轮 100% 是幸存者偏差」） |
| ③ | **从数据形状上看不出异常** | C 类题 `reference` 平均 48 字，`doc_qa` 36 字、`cross_doc` 72 字 —— **长度完全正常**。这个 bug 只能靠**读 reference 的内容**发现，任何统计检查都抓不到 |

> **一句话教训**：**`reference` 不是给人看的文档，是给 judge 吃的标准答案。**
> 写它的时候必须站在 judge 的视角：*"这段文字会被当成正确答案，我的答案跟它比对会得到什么判定？"*

## §8 方法论收获（面试可讲）

1. **"测不出差异"要先怀疑尺子，而不是急着下"没有差异"的结论。**
   本轮如果只看表面数字（88/92/90），很容易写成"重排对答案准确率无明显提升" ——
   而真实原因有两个，且**都不是重排本身**。
2. **稳定的假失败是评测系统里最危险的一类错误。** 它有三个特征：跨配置一致、理由听起来很合理、数据形状正常。
   唯一的防线是**读原始判定理由**（judge 的 `reason` 字段），而不是只读汇总分数。
3. **给 judge 的标准答案，是"接口"不是"文档"。** 约束类信息（要不要调工具）必须走**结构化字段**
   （`expected_tool`），**不能写进自然语言的参考答案** —— 后者会被 judge 当成内容要求。
   > 这与本项目反复踩的那条同族：**同一件事写两处，两处会各自演化**。
4. **小样本通过 ≠ 没问题**。D22 那次 4 题实跑全绿，恰恰因为抽到的题"运气好"。
   样本小的时候，"全绿"的信息量远低于直觉。
