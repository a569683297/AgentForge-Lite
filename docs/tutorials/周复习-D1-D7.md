## 1. 项目全链路（用户提问 → 最终回答）

```
用户提问
  → FastAPI API 层（接收请求，三层解耦）
  → services 层（业务逻辑）→ models 层（操作数据库）
  → Agent 引擎（LangGraph 状态机）
      plan（LLM 决策，chat_with_tools + 官方 function calling）
        → 条件边判断：有 tool_calls？→ execute / answer
      execute（执行工具，tool 消息带 tool_call_id 写回）
        → 回 plan（再决策）
      answer（无工具调用时生成最终回答，用 chat）
  → 全程走 LLM Gateway（双通道降级 + Langfuse 追踪）
  → 返回用户
```

## 5. 面试叙事（升级版，可背）

> "我的项目核心链路是：用户提问 → FastAPI 三层架构（API 收请求 / services 处理逻辑 / models 操作数据库）→ Agent 引擎用 **LangGraph 状态机**做流程管理，LLM 按 **ReAct + 官方 function calling** 决策是否调用工具，执行完结果写回再决策，直到回答。全程走 **LLM Gateway**，统一加 **Langfuse 追踪**——每个节点的 token、耗时、失败点都可见；同时为高可用做了**双通道降级**，主模型挂了自动切备用。这套架构可观测、流程可控，后续能平滑接入 RAG 检索和多 Agent 协作。"

**关键词清单**（面试必带）：三层解耦 / LangGraph 状态机 / ReAct / 官方 function calling / LLM Gateway / Langfuse 可观测 / 双通道降级 / 平滑扩展

## 6. 面试追问防御（高频问题速答）

| 追问 | 速答 |
|---|---|
| 为什么用 LangGraph 不手写循环？ | 可追踪、可扩展、recursion_limit 控制、可可视化 |
| 什么触发降级？ | 任何异常：超时/非 2xx/连接错误（raise_for_status 触发） |
| tool 消息为什么带 id？ | OpenAI 协议要求结果对应调用，缺失 400 |
| 数据存哪？ | 全量 PostgreSQL（持久），热数据 Redis（快） |
| 怎么保证不贴错 id？ | 执行和贴票在同一循环迭代，或并发时 id 与结果绑定返回 |
