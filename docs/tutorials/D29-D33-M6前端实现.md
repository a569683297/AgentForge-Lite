## §2 名词先注解

### 2.1 本阶段新出现的（先注解，再往下用）

**Vite** = 前端**构建工具 + 开发服务器**（替代老一代的 Webpack）。
两个身份要分开：`vite`（dev，不打包、按需编译、改代码几乎即时热更）与 `vite build`（产生产物）。
本项目用它的 **`server.proxy`** 解决开发期跨域（见下条）。

**dev proxy（开发代理）** = 让**开发服务器**把指定前缀的请求转发到另一个地址。
本项目配置是 `/api` → `http://localhost:8000`（`frontend/vite.config.ts`）。
**为什么需要**：浏览器有同源策略，前端跑在 `:5173`、后端在 `:8000`，直连就是跨域。
⚠ **它只在 `npm run dev` 时存在** —— 生产环境靠 nginx（Docker 的 `web` 服务）做同样的事。

**AntD（Ant Design）** = 一套 React 组件库。**本项目选它是因为 PRD 定死了**（2026-10-03 拍板「不换 Tailwind/shadcn」）。

**token（设计令牌）** = AntD 的**原子设计变量**（色值 / 字号 / 圆角 / 行高 / 控件高度）。
理解它的关键是**三层派生**：**Seed Token**（源头，如 `colorPrimary`）→ AntD 的算法自动推出整条色阶 →
**Map Token**（派生值，如 `colorPrimaryHover`）→ **Alias Token**（语义别名，如 `colorTextDisabled`）。
**改一个 Seed 会连锁改一大片** —— 这是"为什么改一个颜色，某些组件看着也变了"的原因。

**`<ConfigProvider>`** = AntD 的**全局主题注入口**。用 `<ConfigProvider theme={...}>` 包住整个应用，
所有 AntD 组件从它取 token。**本项目里它只有一个**（`src/theme/ThemeProvider.tsx`），
组件里**禁止**再套局部 `<ConfigProvider>` —— 那会造成"两个真相"。

**CSS Modules** = 「类名自动加哈希、只在当前文件生效」的 CSS。
文件名写 `xxx.module.css`，组件里 `import s from './xxx.module.css'`，然后 `className={s.sidebar}`。
**为什么用它而不是 Tailwind**：① 与 AntD 的样式体系不冲突；② AntD 覆盖不到的"自绘区域"
（Trace 瀑布图、细条进度条）需要一个能写普通 CSS 的地方。

**`data-theme` 属性** = 挂在 `<html>` 上的一个自定义属性，值取 `light` / `dark`。
本项目用它承载**"当前是哪套主题"这个唯一事实**，CSS 变量（`tokens.css`）按它切换。

**FOUC（Flash of Unstyled Content，样式闪白）** = 页面先按默认（浅色）画出来、
然后 JS 才把主题切成深色，用户看到**一瞬间的白闪**。
本项目的对策是在 `index.html` **`<head>` 里塞一段同步脚本**，在页面渲染前就把 `data-theme` 设好（见 §3.1-③）。

**ECharts** = 百度开源的图表库。**本项目的坑在于它"不吃" AntD 的 token** ——
ECharts 要的是**具体色值**，不认 AntD 的 JS token 体系。所以色值必须**显式传进图表配置**，
并且切主题时**重建实例**（`MetricChart.tsx` 用 `key={mode}` 做到）。

**骨架屏（skeleton）** = 数据还没到时先画的"灰色占位块"，形状模仿真实内容。
比转圈好在**不会让布局跳一下**。本项目用 AntD 的 `<Skeleton.Input>` 拼了个 `TableSkeleton`。

**mock（模拟数据）** = 手工编的假数据。
**本项目的纪律**：mock 只允许存在于**一个出口** `src/mock/index.ts`，
且承载它的页面**必须在页头挂「示例数据」徽标** —— 不然演示时会被人当成真实运行结果。

**命名空间前缀** = 同一个名字空间里给来自不同来源的东西加前缀区分。
本项目里 MCP 工具的注册名是 `<server 名>_<工具名>`（如 `harness_list` 来自 `harness` 这台 server），
**前缀由服务端在注册时加上，前端原样显示即可，不要自己再拼一遍**。

#### ③ ★ 双主题同源：本日技术含量最高的一处

需求原文（DESIGN §9）：**主题状态必须同时驱动 AntD 的 `<ConfigProvider theme>` 和 `<html data-theme>`，两者同源**。
两件事都要做，且**不能各写一套**：

```tsx
// src/theme/ThemeProvider.tsx（全文 45 行）
function initialTheme(): ThemeMode {                 // ① 首帧怎么定
  const saved = localStorage.getItem(STORAGE_KEY);   //   优先用户上次的选择
  if (saved === 'dark' || saved === 'light') return saved;
  return matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';  // 否则跟随系统
}

useEffect(() => {                                    // ② 切换时两边一起动
  document.documentElement.setAttribute('data-theme', mode);   // → CSS 变量
  document.documentElement.style.colorScheme = mode;           // → 原生控件（滚动条/表单）
  localStorage.setItem(STORAGE_KEY, mode);                     // → 持久化
}, [mode]);

return <ThemeContext.Provider value={value}>
  <ConfigProvider theme={mode === 'dark' ? darkTheme : lightTheme}>   {/* → AntD token */}
    {children}
  </ConfigProvider>
</ThemeContext.Provider>;
```

**三段分别解决三个不同的问题，少一段就坏一处**：

| 段 | 解决什么 | 少掉它会怎样 |
|---|---|---|
| `initialTheme()` | **首帧**用哪套 | 刷新后主题回到默认（用户选择丢失） |
| `useEffect` 里三行 | **切换时**同步 | `data-theme` 与 AntD 各自为政 → 自绘区域和组件区域**颜色不一致** |
| `index.html` 内联脚本 | **防 FOUC** | 深色用户每次刷新看到**一闪的白** |

★ **`index.html` 的内联脚本是必需的**（不是冗余）：`useEffect` 在**渲染之后**才跑，
而内联脚本在**渲染之前**就执行 —— 时序不同，不能互相替代。

```
<!-- index.html <head> 里 -->
<script>
  const savedTheme = localStorage.getItem('af-theme');
  if (savedTheme === 'dark' || (!savedTheme && matchMedia('(prefers-color-scheme: dark)').matches)) {
    document.documentElement.setAttribute('data-theme', 'dark');
  }
</script>
```

#### ④ API client：错误信息要"能直接给用户看"

`src/api/client.ts` 是一个 axios 实例 + 一个**响应拦截器**：

```ts
export const client = axios.create({ baseURL: '/api', timeout: 20_000, ... });

client.interceptors.response.use(
  (response) => response,
  (error: unknown) => {
    if (axios.isAxiosError(error)) {
      // ★ 优先取后端 FastAPI 的 `detail` 字段 —— 它本来就是写给用户看的
      const message = typeof error.response?.data?.detail === 'string'
        ? error.response.data.detail
        : error.message;
      return Promise.reject(new Error(message));
    }
    return Promise.reject(error);
  },
);
```

**为什么值得单独讲**：FastAPI 的错误响应体是 `{"detail": "..."}`，
axios 默认只给一个 `Request failed with status code 400` —— **把后端精心写的错因丢了**。
拦截器把它捞回来，于是所有页面都能直接 `setError(reason.message)` 显示人话，不用各页各写一遍。
⚠ 注意它的**边界**：`detail` 不是字符串时（FastAPI 的校验错误里 `detail` 是一个**数组**）会退回 axios 原文。

`src/api/*.ts` 是 7 个薄封装（`health` / `chat` / `sessions` / `documents` / `eval` / `tools`），
每个函数只做"拼路径 + 给类型"，**不做业务判断** —— 这一层保持薄，页面才好改。

#### ① 数据流：一次提问从按下回车到渲染

```
用户按 Enter
  → submit()                     ChatPage.tsx
  → sendMessage(msg, sessionId)  api/chat.ts → POST /api/chat

  → 工具名数组经 toolCallFactory 变成 ToolCallCard
```

**关键点：`/api/chat` 是"一问一答"的**（返回完整 JSON），不是流式。所以：
- 提交到返回之间，界面只能显示**「Agent 正在处理请求…」**（`<Alert type="info">`）
- **绝不能做假打字机**（把整段答案用 setInterval 一段段吐出来）——
  那是**用动画掩盖接口能力不足**，演示时会被人问穿

#### ② 引用高亮：切分逻辑在 `lib/format.ts`

```ts
// extractCitationParts('答案 [1] 和 [9]。', [1])
// → [{text:'答案 '}, {citation:'1',valid:true}, {text:' 和 '},
//    {citation:'9',valid:false}, {text:'。'}]
```

`renderAnswer()`（`MessageList.tsx`）把片段分别渲染成：普通文字 / **可点的引用按钮** /
**灰色失效引用**。**"失效"有两个来源，要一起判**：

```tsx
const isInvalid = invalid.includes(Number(part.value)) || !part.valid;
```

- `!part.valid` = 这个 `[n]` 在 `sources[]` 里**找不到对应来源**（模型编了一个引用）
- `invalid.includes(...)` = 后端的 `invalid_citations` 数组点名了它（后端已经校验过一轮）

**为什么要两处一起判**：一个查的是"我手上有没有这条来源"，一个查的是"后端认为它合不合法"。
**用一个代表另一个就会漏** —— 这是本页最容易写漏的一行。

#### ③ ★ 工具卡片：本次收尾修掉的地方（重要）

`/api/chat` 返回的 `tool_calls` 是 **`string[]`，只有工具名** —— 没有入参、没有返回、没有耗时。
而卡片设计上要显示入参和返回摘要。**这个缺口怎么处理，是"诚实"与"好看"的分界点。**

**修之前**（外部执行方的写法）：

```ts
// ❌ 编造：入参写死成空对象，返回写死成一句读起来像结论的话
names.map((name) => ({ name, arguments: {}, result: '本轮工具调用已完成；详细参数请从会话历史查看。', failed: false }))
```

**两个问题**：① `arguments: {}` 会被渲染成 `{}`，读者以为"这个工具真的没传参"；
② 那句 result 是**我编的**，可它长得像真实返回。而在**会话历史回放**路径上（`pairToolMessages`），
入参与返回**是真的**（从 `tool_calls[].function.arguments` 和一个 `role:'tool'` 的消息里取）
→ **同一个组件，两条路径，一半真一半假，且界面上分不出来**。这正是 铁律 12 说的"静默失效"。

**修之后**：把「不知道」变成类型系统里的一等公民。

```ts
// src/lib/format.ts
export interface PairedToolCall {
  name: string;
  /** null = 数据源根本没给入参（≠ 入参是空对象 {}） */
  arguments: Record<string, unknown> | null;
  /** null = 数据源没给返回摘要 */
  result: string | null;
  /** 只在 result 存在时可判定；result 为 null 时恒为 false（未知 ≠ 成功） */
  failed: boolean;
}
```

配套三处：`parseArguments()` 解析失败**返回 `null` 而不是 `{}`**；
`ToolCallCard` 用**三态**（成功 / 失败 / **未知**）渲染；`ChatPage` 的 factory 如实落 `null`。

```tsx
// ToolCallCard.tsx 核心三行
const known = tool.result != null;
const tone  = !known ? 'muted' : tool.failed ? 'danger' : 'success';
const argsText = tool.arguments == null ? null : JSON.stringify(tool.arguments, null, 2);
// 渲染：无数据时显示「本轮接口未返回入参」而不是一条像结论的假文案
```

★ **这条改动的价值不在界面，在类型**：现在"缺数据"是**编译期可查**的，
以后谁想再编一个假返回值，type 上就说不通。

#### ④ 会话侧栏与"新建会话"

侧栏（`AppShell.tsx`）的「最近会话」取 `listSessions()` 的前 6 条；点一条 → `App` 把 `page` 切到 `chat`

**★ 四个指标卡的分母各不相同，这是 D23 踩过的坑的延续**：

```tsx
<MetricCard label="正确性均分" value={formatScore(detail?.score_correctness)} note={`按行计算，分母是 ${detail?.scored_rows} 行`} />
<MetricCard label="完整性"     value={formatScore(detail?.score_completeness)} note={`明细总行数 ${detail?.rows}`} />
```

`rows`（明细总行数）与 `scored_rows`（**参与打分的**行数）**必须分开显示** ——
因为**工具类题不送 judge、分数为 NULL**，所以 `scored_rows < rows`。

**失败模式条的归一化**：

```tsx
const maxFailure = Math.max(1, ...Object.values(detail?.failure_breakdown ?? {}));
// ...
<span style={{ width: `${(count / maxFailure) * 100}%` }} />
```

两个细节：① `Math.max(1, ...)` 的 **`1`** 是防空兜底（全 0 时不做除零）；
② 归一化**按最大值**而不是按总数 —— 失败模式条之间是**独立比较**关系，不是"占总量比例"。

### §3.4 D32 —— Trace 时间线

**计划交付**：自绘横向 span 瀑布图（DESIGN 说这页最难）。**实际：UI 做完整了，数据是 mock。**

**文件**：`pages/TracePage.tsx`(24) + `mock/index.ts` 的 `MOCK_TRACES`（`mock/index.ts` 共 141 行）

#### ① 它画的是什么

一条横向**瀑布条**：左边是 span 名（按 `depth` 缩进），右边是时间轴上的**色条**，
条的位置与宽度**按该 span 在整条 trace 里的时间比例算**：

```tsx
const left  = (span.start_ms / trace.total_ms) * 100;                          // 起点 %
const width = Math.max(1.5, ((span.end_ms - span.start_ms) / trace.total_ms) * 100);  // 宽度 %
//                                    ↑ 1.5 是下限：极短的 span 也要看得见
```

**`Math.max(1.5, ...)` 是必须的**：像 `tool:current_time` 这种 8ms 的 span，
按比例算宽度只有 0.9% —— 在 1000px 宽的容器里不到 10px，会看不见。

#### ② ★ 本次收尾把 mock 的 span 名全部改成"真实口径"

外部执行方原来编的 span 名与 D28 **真实埋的常量对不上**。这是一处很危险的错：
**它不会报错、界面照样好看，但演示时会说出错的名字。**

| 原 mock 里写的 | D28 真实常量（`app/services/observability.py`） |
|---|---|
| `vector-search` | **`vector_search`**（下划线） |
| `bm25-search` | **`bm25`** |
| `bge-reranker` | **`rerank`**（**模型名 ≠ span 名**） |
| `search_documents`（工具） | **`tool:search_documents`**（带 `tool:` 前缀） |
| （缺 `retrieval` 父 span） | **有**：`retrieval` 是**检索的父 span** |

**真实的 span 树形状**（照抄 `observability.py` 的模块 docstring）：

```
run_agent                  ← 根，一整轮对话（as_type=agent，带 session_id）
├─ agent-plan              ← generation
├─ tool:search_documents   ← tool
│   └─ retrieval           ← retriever 父（★ 嵌套计时：它的耗时包含子段）
│       ├─ vector_search   ← retriever
│       │   └─ embedding   ← embedding（只有它能带 model 名）
│       ├─ bm25            ← retriever
│       └─ rerank          ← retriever
├─ tool:harness_list / tool:harness_get / tool:current_time
└─ agent-answer            ← generation
```

**为什么 `tool:` 前缀不能省**（这是 D28 讲过、这里要复用的理由）：
**工具名是用户可自定义的**，完全可能出现一个叫 `vector_search` 的工具；
那时它和检索那格在 Langfuse 上同名，`group by name` 会把两者混成一组 —— 而 D35 的
`latency_p95` 正好按 name 分组，**混组不报错，只是那一行的数字错了**。

#### ③ ⚠ 这一页的数据源缺口（最重要的知识点）

**Trace 页在后端完全没有接口。** span 数据在 **Langfuse** 里，而本项目**没有做 Langfuse 的 trace 查询出口**。
D28 建的读通道（`langfuse_client.py`）只拉 `/api/public/observations`（**扁平的 observation 列表**），
**不是**"按 trace 取整棵树"。

所以这一页的性质是：**一个完整的界面 + 一份 mock 数据 + 一个明确的待办**。
页头挂 **「示例数据」徽标**（`PageHeader` 的 `badge` 属性），这是**纪律**不是装饰 ——
**没有数据源的页面必须自己承认**。

> **接线时会遇到的真问题**（先记下来，将来做的时候省一次返工）：
> Langfuse 的 observations 是**平铺**的，要还原成树得靠 `parent_span_id` 自己组装；
> 而且它**不返回 `depth`** —— 前端要自己按父子关系算缩进层级。

### §3.5 D33 —— 工具注册表 + RAG 检索检查器（+ 分析页提前落地）

#### ① ToolsPage：接真实 API，且要处理"server 断了但工具还在表里"

**文件**：`pages/ToolsPage.tsx`(42)

`getTools()` 返回的对象有**两部分信息，不要混**：

```jsonc
{
  "total": 14,
  "by_source": { "local": [...], "inventory": [...], "harness": [...11 个...] },
  "servers": [ { "name": "harness", "connected": true, "tool_count": 11, "error": null } ],
  "tools":   [ { "name": "harness_list", "description": "...", "parameters": {...}, "source": "harness" } ]
}
```

★ **`tools[]` 与 `servers[]` 是两个不同的问题**：
`tools[]` 说"注册表里有什么"，`servers[]` 说"那台 server 现在还活着吗"。
**工具还在表里、server 已经断了**是完全可能的状态（注册发生在启动时，之后 server 可能挂掉）。
所以卡片上的状态点要**查 server 表**：

```tsx
function toolStatus(tool: ToolItem) {
  const connected = tool.source === 'local' || serverConnected.get(tool.source) !== false;
  return connected ? { tone: 'success', label: '可用' } : { tone: 'warning', label: '未连接' };
}
```

`source === 'local'` 的短路是必需的 —— 本地工具**不在 `servers[]` 里**，
不短路就会因为"查不到"而误判成"未连接"。

⚠ **`servers[]` 有两种形态**（源码 `app/mcp/manager.py`）：**连接失败时没有 `tool_count` 字段**。
所以 TS 类型里它必须声明成可选（`tool_count?: number`），否则连接失败那天前端会崩在类型上。

**筛选 pill 的计数来自 `by_source` 的数组长度**，不是自己数 `tools[]` ——
**同一份数据不数两遍**（数两遍就会出现"pill 显示 3、列表里 4 条"的怪状）。

#### ② RetrieverPage：把"重排前后的取舍"摆出来

## §4 类比迁移表

用户是 **Vue → React 的中级前端**（PRD 红线 4 说 UI 复用既有经验），所以这张表的左列是**你已有的经验**：

| 本项目的东西 | 对应你熟悉的 | 关键差别 |
|---|---|---|
| `palette.ts` + `antdTheme.ts` | Vue 的 **scss 变量** + Element Plus 的主题定制 | AntD 是 **JS token**（运行时对象），不是 CSS 变量；两者要**各管一半**（组件走 token、自绘走 CSS 变量） |
| `ThemeProvider` + `data-theme` | Vue 里的 `useDark()` | 这里要**同时**驱动两套（AntD token 与 CSS 变量），不能只改一套 |
| `useState` 切页（7 页） | `vue-router` | **本阶段刻意没引路由库** —— 7 页、无深链接需求，`useState` 够用。⚠ 代价：刷新会回到第一页、无 URL 分享 |
| `src/api/*.ts` 薄封装 + axios 拦截器 | 你在 Hono/Next 项目里的 `api/` 目录 | 一样的分层，**唯一新增的是"把 FastAPI 的 `detail` 捞回来当错误消息"** |
| CSS Modules | Vue 的 `<style scoped>` | 同样的"类名不乱跑"效果，写法是 `import s from './x.module.css'` |
| `ToolCallCard` 的**三态**渲染 | 你写过的 loading/error/success 三态 | 这里多了一个**第四态：`unknown`** —— 数据源没给就是没给，不许用空值冒充 |
| `mock/index.ts` 单一出口 | 前端的 `__mocks__/` 约定 | 这里的纪律更硬：**mock 只准在一个文件里，且承载页必须挂徽标** |
| `MetricChart` 的 `key={mode}` | React 里"用 key 强制重建" | 这里不是性能技巧，是**功能必需**（ECharts 实例状态） |

## §5 面试考点

M6 在面试里的定位：**"前端我不只是会写，我知道它跟后端的数据边界在哪。"**
下面 5 问按"会被问到的可能性"排序。

**Q1：这个前端的数据都是真的吗？**
> 分两组。**对话 / 知识库 / 评测 / 工具注册表**这四页打的是真实后端接口 —— 比如工具注册表
> 现在真能列出 14 个工具，其中 harness 那 11 个是外部 MCP server 动态发现的。
> 另外**三页（Trace / 检索检查器 / 分析）是示例数据**，因为后端**确实没有**这三个数据源：
> Trace 的数据在 Langfuse 里没有查询出口；检索片段现在只有一段拼接字符串、没有名次和 score；
> 分析页要的 `/api/metrics` 排在语义层那几天做。
> 这三页的页头都挂着「示例数据」徽标，mock 数据也集中在一个文件里 —— **不编接口，是我给自己定的规矩。**

★ **这题是本阶段最能加分的一题**：绝大多数人会说"都做完了"，而你能说出**"哪几页是假的、为什么假、什么时候能真"**。

**Q2：主题切换怎么做的？AntD 和自定义 CSS 怎么统一？**
> 一个 `ThemeProvider` 同时驱动两套：`<html data-theme>` 驱动 CSS 变量（给自绘区域和 ECharts 用），
> `<ConfigProvider theme>` 驱动 AntD 的 token（给组件用）。
> 色板只有一个真源 `palette.ts`，两套都从它取，所以不可能出现"改了颜色但有一半没变"。
> 另外 `index.html` 里有一段**同步执行的**内联脚本，在首帧渲染前就把 `data-theme` 设好 ——
> 不然深色主题用户每次刷新都会看到一闪的白（FOUC）。

**追问：那 ECharts 呢？** → 它不吃 AntD 的 token，所以色值要显式传；
而且切主题时用 `key={mode}` 重建实例，因为有些 ECharts 配置是初始化期读的。

**Q3：你说"不许编造数据"，具体怎么在代码里防的？**
> 靠类型。工具卡片在实时路径上**拿不到入参和返回**（`/api/chat` 只回工具名），
> 一开始的写法是塞一个空对象和一句"已完成"的文案 —— 界面看着完整，但**一半真一半假，界面上分不出来**。
> 改成 `arguments: Record<string, unknown> | null`、`result: string | null`，
> 解析失败也返回 `null` 而不是 `{}`，组件按**三态**渲染。
> 这样"缺数据"从**运行时才看得见**变成**编译期就能查** —— 以后谁想再编一个假值，type 上就说不通。

**Q4：后端是非流式的，你怎么处理"没有打字机"？**
> 不假装。后端 `/api/chat` 返回完整 JSON，**没有 SSE 端点**，
> 所以提交后显示一个明确的"处理中"状态，不做 setInterval 假动画。
> 假打字机的问题不是"不好看"，是**用动画掩盖了接口能力** —— 演示时被问"这是真流式吗"就答不上来。
> 真要做流式，得后端先上 SSE。

**Q5：前端工程化上有哪些已知不足？**
> 三个我自己知道的：① **构建产物 2.35MB 没有代码分割**（AntD + ECharts 打成一个包）；
> ② **测试只有 5 条**，且都集中在纯函数（`format.ts`），组件与接口层没有测试；
> ③ **没引路由库**，7 页用 `useState` 切，代价是刷新回第一页、URL 不可分享。
> 这三条都是"当前规模下可接受、规模一涨就必须补"的取舍。

### 7.3 一条工具/环境坑：`npm` 在资源竞争下会被 SIGTERM，构建还会偶发 `write EPIPE`

本次 `typecheck` 单跑 **4 分 22 秒**、`test` 71 秒（平时都是秒级）。
期间有两条命令**直接被杀掉**（退出码 **137 = SIGTERM**），当时后端（uvicorn）
与前端 dev server **都在跑**。
→ **判据**：**退出码 137 不是"代码错"**，先看机器上还有谁在抢资源；
`npm` 这类命令**放后台跑**（本次就是转后台后跑通的）。
> 与铁律 9 的"报错要先定性"同源：**`SIGTERM` 是环境信号，不是断言失败。**

**同一个坑的第二种表现**：有一次 `npm run build` 报

```
[commonjs--resolver] Could not load .../node_modules/antd/es/descriptions/hooks/useItems.js: write EPIPE
```

**怎么定性**：`EPIPE` = "管道另一头已经关了"；而且**堆栈落在构建工具链的 IPC 桥接层**
（本机编辑器自带的 node shim），**不在 vite / tsc 的业务逻辑里** → 判为**环境层**。

★ **但"判为环境问题"不能直接当结论用 —— 必须补一次复跑才算数。** 复跑结果：
**`BUILD_RC=0`，`✓ built in 2m 19s`，4070 模块 / 2.53 MB** → 这才敢下结论「**环境抖动，非回归**」。
→ **规矩**：**遇到"看起来像环境问题"的失败，不复跑就直接写"环境问题"，等于用一句话把可能的真回归盖掉。**
区分的方法只有一个：**在同一个 commit 上复跑，看它是否可复现。**


### 7.4 一条认知坑：**"一次性交付"会被误读成"按天做了五天"**

本阶段最需要警惕的不是代码，是**文档的口径**。M6 是一个提交交付的，
但如果照着计划写成五份"当天总结"，就会**凭空造出五个不存在的工作日** ——
而且这种错**没有症状**，读的人只会以为"哦，是分五天做的"。
→ **处理**：本文件 §0 用一张表把这件事写死（实现是一次性的 / 组织按天序 / 不是五次工作日）。
→ **规矩**：**交付形态与计划形态不一致时，必须在文档开头显式声明**，不能靠读者自己推。

### 7.5 ★ 收尾期新发现的口径偏差：预览功能与「D19 冻结后端」红线冲突

**事实**：收尾期并行加入的「文档预览」功能**新增了一个后端只读接口**
`GET /api/documents/{id}/preview`，并改了 `app/api/documents.py` / `app/schemas/document.py` / `app/services/document_service.py` **三个后端文件**。

而 **PRD 红线 #3** 写的是：**「D19 后冻结后端新功能（P1 全部砍掉，保底 P0）」**（`docs/PRD-v4.1-含前沿技术.md:1514`）。
**按字面，这就是"D19 之后的又一个后端新功能"，应当被砍。**

**我判定"保留并如实登记"的理由（三条，都可以复核）**：
1. **它是只读的、且不新增任何暴露面** —— 接口 docstring 写死「不暴露原始文件或任何凭据」，没有下载路由、没有新凭据、没有新的外部调用；它读的是**库里已经存好的切片**。
2. **它不动既有契约** —— 没有改任何已有接口的签名或字段，纯粹是"同一资源（documents）上的第 4 个操作"（上传 / 列表 / 删除 之外多一个读），**删掉它对其它模块零影响**。
3. **可回退成本极低** —— 若 D34–D37 出现超支，**第一顺位可回退项就是它**：前端摘掉 `onRow` 与 `<DocumentPreviewModal>` 即可（后端接口留着不接、不产生副作用）。

**但必须诚实说清另一半**：**严格按红线字面，它就是违反了。**
标记为「**已知偏差 · 已接受**」，**不是"不算违规"** —— 如果将来有人拿这条红线来质疑，正确的回答是
「它是一次**有意接受的偏差**，理由见上，且已登记为第一顺位回退项」，**而不是**「它不算新功能」。

**★ 由此得到一条工程教训**：**并行工作流会绕过"当天验收"这道闸。**
M6 本体是走流程的（有 PLAN、有验收），但这批改动是**在收尾期由另一条并行线直接写进工作区**的 ——
它**没经过红线条目检查**，所以在收尾检视时**必须专门为它补一次"红线对照"**，否则这类偏差会**悄无声息地活下来**。
→ **规矩（建议纳入收尾清单）：收尾时必须把"这一轮的增量"逐条对一遍 PRD 红线清单，而不是只检查"功能对不对"。**
