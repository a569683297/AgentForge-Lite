## §0 收纳边界

### 0.1 一句话判据

> **同一句话只说一次。**
> **数字与结论 → 本文档；过程与代码 → 各日教程；原始数据 → 探针结果文件；词义深度 → 术语卡。**

**「吸收」的具体含义**（2026-09-29 用户拍板）：**不是把原段落搬走，而是本文档按「为什么这么设计」的线索重写一遍**，
原文件正文原样保留。靠**粒度**分工，而不是靠"内容不重叠"：

| | 落点 | 例子 |
|---|---|---|
| **本文档** | **为什么这么设计**（决策链 / 取舍 / 反例） | 「判分器为什么要显式锁通道」+「不锁会怎样，且不会报错」 |
| **各日教程** | **当天怎么做的**（函数名 / 参数 / 命令 / 验收 / 踩坑现场） | 「`_resolve_channels` 的签名是…，跑了 60 项断言」 |

> 粒度分工是第三条路：**讲的东西不同名，就不构成两处权威。**

# 第一部分 · 问题：为什么要这套评测

## §1 要回答的三个层次

评测要回答的不是一个问题，是**三个不同的问题**，而它们**必须用三套不同的量具**（量具 = 测量的工具/指标）。

| # | 问题 | 谁来答 | 量具 | 成本 | 噪声 |
|---|---|---|---|---|---|
| ① | **检索有没有捞对？** | 检索层 | `Hit@k` / `MRR` | **零 token**（确定性，同输入同输出） | 无 |
| ② | **端到端答得对不对？** | 生成层 | 准确率（按题） | 每题调 LLM | **生成侧抖动 10.0%** |
| ③ | **我这次的改动到底有没有用？** | 判定层 + 归因 | 消融对比 + `failure_reason` | judge 每题 3 次 | **裁判侧抖动 ε=0.95%** |

**术语注解**：
- **量具**：测量用的工具与刻度。同一个数字用不同量具量出来**不可比**，这是本项目的头号口径纪律。
- **`Hit@k`**：正确文档出现在检索结果**前 k 名**里的比例（命中率）。**`MRR`**（Mean Reciprocal Rank，平均倒数排名）：
  正确文档第一次出现的名次取倒数再平均 —— 第 1 名得 1.0，第 2 名得 0.5，第 3 名得 0.33，**越小越靠后、越接近 0**。
- **消融（ablation）**：**一次只改一个变量**、其余全锁死，看这个变量到底带来什么差异。
  本项目唯一自变量 = `settings.retriever_config`（`pure_vector` / `hybrid` / `hybrid_rerank` 三档）。
- **抖动（jitter）**：同样的输入，跑两次结果不一样的程度。分三层，**应对方式完全不同**（见 §6）。
- **ε（epsilon）**：judge 对**同一份答案**重复判定的**不一致率**（单次口径）—— 判定层的噪声地板。

**为什么必须分三层**：三层噪声**叠加**之后剩下的那点差异，才是「配置差异」。
如果不知道每层噪声多大，就**分不清「真差异」和「抽样抽出来的差异」**（§3、§6 展开）。

**反例（不这么做会怎样，且不报错）**：D23 早期拿 **run 1（只跑了 C01~C04，共 8 行）** 与 run 4/5/6 对比 ——
**两次跑的题集不同**，对照根本没有含义；而**表格照排、脚本正常退出、数字看着还挺像**。
→ 覆盖率型静默失效：**断言全绿 ≠ 覆盖到了**。

> 出处：`D24-总结.md §2.1/§2.2` · `D23-检索层指标.md §2.1` · `D20-总结.md §3`

## §2 为什么「看几个例子觉得挺好」不行

拿几个问题手测、觉得答得不错 —— 这个做法**有三个独立的失效点**，每一个都能单独毁掉结论：

| # | 失效点 | 会怎样 | 为什么**不报错** |
|---|---|---|---|
| ① | **抽样随缘** | 「感觉挺好」= 你自己挑的题，**专挑会的** | 样本少、又自选，**没有任何机制告诉你漏了什么** |
| ② | **没有噪声概念** | 不知道 judge 抖多大，就不知道「提升 X%」**算不算数** | 差异可能全来自抖动，但**数字看起来总是有值的** |
| ③ | **改动后无法归因** | 同时变两个变量 → 差异**归不到任何一个** | 表格照排，**读者会自行脑补成"是新变量带来的"** |

**由此定下三条硬纪律**：

1. **评测集是地基，不是随手找的 50 个问题**（§4）。
2. **先校准量具，再测系统**（§3）—— 顺序反了就会得到「假 0」（§3 有实例）。
3. **绝不拿评测集调参**：看了一眼哪条挂了就改 prompt 再重跑 = **过拟合评测集**（相当于把答案背下来了）。
4. **分母必须一致**，否则三个百分比**不可比**。

**反例（本项目实踩）**：
- 若图省事**直接把重排塞进** `search()`，B 配置就**永久消失** —— 此后「重排到底有没有用」**再也答不出来**，
  而且**没有任何地方会报错**。
- 分母不一致：某配置少算几条题，分母一变，**三个百分比根本不可比**，但表格依旧整齐。
- 探针 **relay-gpt 的失败率在 1%~37% 之间飘**（上一轮 37.1%）—— 这就是「不先量化噪声」的现场：
  你拿到的任何一个数，**不知道它落在抖动区间的哪里**。

> 出处：`D20-总结.md §1/§4/§6.2/§6.3` · `D20-评测方法论.md 一/四` · `D20-术语卡.md §1/§5`

# 第二部分 · 设计：每个决策的取舍

## §3 量具先行

**规则：先校准 judge，再测系统。**

**为什么**：judge（判分器 = 用 LLM 按 rubric 给答案打分的那个模型）本身**有噪声**。
不知道它抖多大，就不知道「A 比 B 高 2%」到底是真差异还是抽样抽出来的。

**怎么校准**：让 judge 对**同一份答案**重复打分，看不一致率 ε。

**本项目的两轮校准（关键：第 1 轮是「假 0」）**：

| 轮次 | ε（实测） | 真相 |
|---|---|---|
| 第 1 轮 | **0** | ⚠ **假数**：judge 只用了 `{0,2,3,5}` 四档，**4 分档一条都没有**；而通过门槛是 `correctness ≥ 4` → **阈值带（3.5~4.5）为空** → 翻转概率**结构性锁死为 0**，**与 judge 稳不稳无关** |
| 第 2 轮 | `deepseek` **0.95%** / `relay` **1.90%** | 阈值带占比 16.2% / 21.0%（**不再为空**），才是真实的单次不一致率 |

**第 1 轮错在哪**：与 D18「拿 12 token 的句子测出 2.8ms」**同族** —— **测量对象选错**。
（12 token 的句子太短，测不出真实吞吐；阈值带空，测不出真实抖动。）

**D21 又测出一次 ε=0.0000，但成因完全不同**：这次阈值带不空（5/50 = 10%），
是**样本太简单**（50 次判定里 45 次满分）→ **修法方向相反**（不是加密阈值带，是加难题）。
→ **同一个数字 0，两个截然不同的原因**：这就是「数字必须带口径」的原因。

**报 ε 的规矩**：

1. **点估计必须连区间一起报**。ε=0.95% 的 95% Wilson 区间是 **0.17%~5.20%**。
   （**Wilson 区间**：给小比例做的置信区间，比"正态近似"在小样本下更可靠。）
2. **比例型指标的"分母是否有效"要一起写**（阈值带为空 → 分母无效 → 数字无意义）。
3. **门槛要用保守口径复算一遍**：点估计算出门槛 2.9 条，Wilson 上界 7.14% 算出 **11.42 条** ——
   **不是矛盾，是两把尺子**。

**门槛链条（怎么从 ε 推出「提升几条题才算数」）**：

```
ε = 1/105 = 0.95%（判定级）
→ 50 题下的噪声地板 = 50 × 2ε(1−ε) ≈ 0.94 条
→ 加 2σ（σ≈0.96）→ 门槛 ≈ 2.9 条
```
→ 也就是说：**在 50 题的规模上，「差别不到 3 条题」的结论不该当成差异。**
（PRD S2 的「+10%」在 50 题上 ≈ **4 条题** —— 刚好比门槛高一点，这是个巧合但很有用。）

**3 次投票能把裁判侧抖动降到多少**：`P(翻转) = 3ε²(1−ε) + ε³`；
deepseek 点估计 0.95% → 门槛 **0.36 条**；Wilson 上界 5.20% → **2.5 条**。

**跨 judge 一致率**：第 1 轮 12/12 = 100%（**假象**，阈值带空）；
第 2 轮 19/21 = 90.5%，**分歧全部落在阈值带**（说明分歧不是随机的，是集中在"边界题"上）。

**反例**：D20 有一次**计时起点写在并发锁外面** → 单次耗时报成 **11.74s**（真实 0.84s，**差 14 倍**），
**不报错、断言全绿**。→ 量具的**使用方法**本身也会静默出错。

## §4 评测集设计

### 4.1 三类题 = 三种能力

| 类别 | 条数 | 考什么 | 备注 |
|---|---|---|---|
| `doc_qa` | **30** | 单文档问答 | **含 5 条负例**（「文档中并无答案」）→ 测**幻觉控制** |
| `cross_doc` | **10** | 跨文档推理（答案要点分散在两篇及以上） | 本批数据里**唯一还有梯度**的维度 |
| `tool_call` | **10** | **该不该调工具**（不判答案内容） | 判定只走 `tool_call_ok`（§7） |
| **合计** | **50** | —— | 满足 PRD S1「≥ 50 条（3 类）」 |

**难度分布**：`easy` 21 / `medium` 22 / `hard` 7；**覆盖 8 个主题文档**。

### 4.2 `evidence`（判定依据）的四种形态

把参考答案写成**可机检**的形式，而不是一段散文：

| 形态 | 写法 | 用在 |
|---|---|---|
| 正向原文片段 | 原文句子 | `doc_qa` / `cross_doc` |
| 跨文档 | `片段一 \| 片段二` | `cross_doc` |
| 负例 | `[不存在] 关键词` | 5 条负例 |
| 工具 | `[工具] 工具名` | `tool_call` |

### 4.3 `doc_ids` 纪律（**最容易违反的一条**）

> **gold（金标准 = 正确答案所在的那篇文档）只用于判分统计，绝不能当检索过滤条件。**
> 否则就是「**开卷考试还给页码**」—— 分数会虚高，而且**看不出任何异常**。

配套细节：**指纹里用 `doc_slugs`（文档的语义化短名）而不是 `doc_ids`（数据库 UUID）**。
理由见 §9 取舍 ②。

### 4.4 指纹冻结（两张网）

**指纹（fingerprint）** = 把「会影响判分的内容」拼起来做一次 `sha256`，用来证明**输入没被换过**。

- **两张独立指纹**：**题**（50 条的题干/参考答案/evidence）+ **语料**（知识库正文）。
  必须**独立成列** —— 合在一起时，"变了"这件事**无法归因**（是题变了还是语料变了？）。
- **指纹里只放影响判分的内容**：不放 `id` / `created_at` / `doc_ids`（原因见 §9 取舍 ①）。
- **`evidence` 不做归一化**：**顺序即内容**。
- **负例的 `reference` 不能留空**，要写成可判定的陈述（空着就没法机检）。

## §5 两阶段

**把评测拆成「先生成落库、再重复打分」两段，而不是「跑一条打一条」。**

### 5.1 两个旋钮，各对抗一层噪声（**不可混**）

| 旋钮 | 含义 | 对抗哪一层 | 本项目取值 |
|---|---|---|---|
| `generation_runs` | **每题让被测系统跑几次** | **生成侧**抖动 | 正式消融 = **3**（诊断轮 = 1） |
| `runs_per_case` | **每份答案让 judge 打几次** | **裁判侧**抖动 | **3** |

⚠ **这两个旋钮最常被混为一谈**：「跑 3 次」到底指系统跑 3 次还是 judge 打 3 次？**必须写明主语**。

### 5.2 为什么拆开：**钱花在裁判上**

| 做法 | 成本（50 题 × 3 配置） |
|---|---|
| ✅ 拆开（生成 1 次 + 打分 3 次） | 生成 150 次（5~10s/次）≈ 15~25 分钟 + 打分 450 次（~1s/次）≈ 6 分钟 |
| ❌ 不拆（3 次重复套整条链） | **450 次生成** ≈ 45~75 分钟（**3 倍**） |

→ 而且不拆还会把**生成抖动混进 judge 抖动**，**两个噪声源再也分不开**。

### 5.3 两个前提

1. **每条题用全新 session**。注意：`persist=False` 只保证**不写**，**不保证读不到别人写的** ——
   两者是两件事，别用 `persist=False` 冒充"隔离"。
2. **生成串行、打分并发**（`judge_max_concurrency = 4`）。

### 5.4 聚合等价性（一个省事但必须写明的等价）

「**中位数 ≥ 4**」 ⟺ 「**多数投票通过**」—— 所以 3 次打分可以用中位数一句话概括。

**反例**：若生成也 ×3，**成本翻三倍**，且把「生成抖动」混进「judge 抖动」，
**两个噪声源再也分不开**，而**没有任何报错**。

> 出处：`D22-评测器与明细落库.md §1/§5` · `D22-决策材料.md §1.6` · `D20-总结.md §7`

## §6 抖动三层（**本项目的招牌结论**）

### 6.1 三层是什么

| 层 | 本质 | 应对 | **投票有用吗** |
|---|---|---|---|
| ① **裁判侧** | 重复测**同一个值** | 重复打分取多数 | ✅ **有用** |
| ② **生成侧** | 给一个**随机变量**抽样 | 只能**重复生成** | ❌ **没用** |
| ③ **输入被换过** | **不是抖动**，是输入变了 | **指纹前置拦截**（不做统计） | ❌ 统计手段全失效 |

**一句话自检**：**「我重复的是裁判，还是输入？」**

### 6.2 三层应对方式完全不同（为什么混了会错）

把②当成①处理（多打几次分取多数）→ **对生成侧抖动完全无效**：
你重复的只是"给同一份答案打分"，而答案本身每次都不一样。
把③当成①或②处理 → 更糟：**平均两个不同系统的结果，没有含义，但看起来更稳**。

### 6.3 诊断流程（五步）

1. **先冻结指纹**（排除第③层）；
2. **测裁判侧**（同一份答案重复打分）；
3. **测生成侧**（⚠ **每份答案先打分取多数、再互相比较 —— 这一步不能省**）；
4. **比大小**（哪一层更大，就该先治哪一层）；
5. **定 N**（跑几次才够）。

### 6.4 实测数字

| 项 | 值 | 口径 |
|---|---|---|
| 生成侧不一致题数 | **1/10 = 10.0%**（Wilson 上界 **40.4%**） | `cross_doc` 全部 10 题，`generation_runs=5`、judge 3 次/份 |
| 裁判侧翻转 | **0/10** | 同上 |
| 折算到 50 题 | **5.0 条**（点估计）~ **20.2 条**（Wilson 上界） | —— |
| PRD S2 的「+10%」 | ≈ **4 条题** | 50 题规模 |

→ **结论**：生成侧抖动（5.0~20.2 条）**大于** PRD 要的 +10%（4 条）。
→ **所以用 `generation_runs=1` 的数据下「配置 A 比 B 好 N 条」，结论是不成立的。**

### 6.5 单题实例（B01）

- 5 次生成判定 `✓✗✗✗✗`（通过 **1/5**），字数 572/552/583/499/523（极差 84），
  1/5 的 95% Wilson 区间 **0.5%~71.6%**。
- ⚠ **反例（别用字数当抖动代理指标）**：`B02` 字数极差 **237（全场最大）** 却 **5/5 全过**；
  而真正会翻的 `B01` 排在**中下游**。→ **字数抖 ≠ 结论抖**。

### 6.6 ⚠ 第②层会伪装成「配置差异」（D24 新增实例）

D24 报告初稿把三配置的 `failure_reason` **并列成表**，读者自然读成
「配置不同 → **失败模式不同**」。真相是：**同一条题（B01）三份生成逐字不同**
（`pure_vector` `32d4d63c`(651 字) / `hybrid` `448154b3`(484 字) / `hybrid_rerank` `5c040524`(529 字)）
→ **「归因不同」这件事本身也不可归因于配置。**

**反例（③层被当成②层）**：改 `d21_corpus.py` 正文、**不带 `--force`** 跑 seed
→ 语料没更新、指纹不变、**三处都不出声** → 你以为在测新语料，其实还在测旧的。

> 出处：`D22-决策材料.md §1` · `D24-总结.md §2.5/§7④` · `D22-生成抖动探针结果.md §3–§6` · `D21-评测集与语料.md §2.10`

## §7 归因可机械复算

**规则：`failure_reason`（失败归因）必须由「纯函数」从分数推导，不让模型再生成一遍。**

**术语注解**：
- **纯函数** = 同样输入永远给同样输出、不调外部服务的函数。
- **判据**：**能用纯函数从已有数字推出来的东西，不要让模型再生成一遍。**

**6 个取值**：

| 取值 | 触发条件 |
|---|---|
| `system_error` | 系统/网络故障（**上游原因优先**） |
| `tool_miss` | `tool_call` 类题的 `expected_tool` 明确、但**实际没调或调了别的** |
| `hallucination` | `faithfulness ≤ 2`（编造） |
| `incomplete` | `completeness ≤ 2`（漏答） |
| `wrong_answer` | `correctness ≤ 2` 或有遗漏 |
| `None` | 通过 |

**优先级**：`system_error → tool_miss → hallucination → incomplete → wrong_answer`。
两条理由：**① 上游原因优先于下游表现**；**② `tool_miss` 有否决权**；
**③ 先判 faithfulness 再判 completeness** —— **编造比漏答严重**。

**可执行自检**：**同一份答案重复推导 10 次，结果必须完全相同**（`d22_verify.py` 的 B1 断言）。

**反例（为什么不能让模型吐自由文本）**：

| 病 | 后果 |
|---|---|
| **同义异形** | 5 次写成 4 种说法 → 聚成 4 类 → **失败模式分布是假的** |
| **不可复现** | 同一份答案两次跑出不同归因 |
| **不可测** | **写不出断言 → 永远不会红** |

→ 三项任一独立出现就足以否决这个设计。

**同族先例（D14）**：`messages.tool_calls` 被存成 **JSON 字面量 `null`** 而非 SQL `NULL`
→ `IS NULL` **恒为假** → 整片逻辑**静默失效**。
→ 与 §9 取舍 ⑤ 的「分母被隐式化」是同一类病：**看起来有值，其实不是那个意思。**

> 出处：`D22-决策材料.md §2` · `D22-评测器与明细落库.md §4` · `D23-工具类题判定路径修复.md §5`

## §8 可复现的四个前提

| # | 前提 | 具体做法 | **不这么做会怎样（且不报错）** |
|---|---|---|---|
| ① | **judge 显式锁通道、失败不降级** | `chat(..., provider="deepseek")` / `allow_failover=False`；锁定模式**不包装异常**（保留原始 `httpx.HTTPStatusError`） | **网关静默降级** → 「一部分样本 deepseek 打、一部分 relay 打」，报告里**只写了一个 judge 名** → **抖动测量被污染** |
| ② | **两张指纹（题 / 语料）独立成列** | §4.4 | 合在一起 → 「变了」**无法归因** |
| ③ | **配置切换可校验、可恢复** | 显式校验配置名 + `try/finally` 恢复 | `validate_assignment=False` → `"hybrid_rerankk"`（**多打一个 k**）**不报错**，检索静默走默认分支 → **那一列配置是假的**；跑完不恢复 → 后续手动对话莫名用最后一档配置 |
| ④ | **明细逐条落库** | 粒度 = **一次生成 = N 行** | 只有汇总分 → **不可再下钻** → 「分数低」但**不知道为什么** |

**为什么①要「不包装异常」**：`429/503/超时` **该重试**；`401/400` **不该重试**。
包成统一的 `RuntimeError` 后，**四种情况长得一样，信息就丢了**。

**检索层可以零 token 复算**（确定性、同输入同输出）：

| 配置 | 35 题耗时 | 备注 |
|---|---|---|
| `pure_vector` | 2.6s | 零 LLM 调用、**零 token** |
| `hybrid` | 1.4s | 同上 |
| `hybrid_rerank` | **35.1s** | 重排是**大头**（占绝大部分） |

对照：`d22_run` 跑一轮三配置约 **158 万 token / 8 分半**。
→ **检索层指标是本项目"最便宜的那把尺子"**，这是它优先被补的原因（§12）。

**`report_path` 回写（D24 新增）**：把生成出的报告路径写回 `eval_runs.report_path`
→ **指纹从前置约定变成代码强制**（可校验、可恢复）。

# 第三部分 · 为什么这么设计（决策链 + 反例）

## §9 六个关键取舍

> **每个取舍的价值，只能由「不这么做会怎样、且不会报错」证明。**
> （这是本项目踩坑最多的一类：**静默**失效。）

### 取舍 ① — 指纹只归一化「影响判分的内容」

- **怎么做**：不直接 `json.dumps` ORM 对象，只挑出题干/参考答案/evidence。
- **不这么做**：带上 `id` / `created_at` / `doc_ids` → 一旦重建语料，**UUID 全变** → **假报警**
  → **报警疲劳** → **冻结机制名存实亡**。

### 取舍 ② — 用 `doc_slugs` 而不用 `doc_ids`

- **怎么做**：指纹里用**语义化短名**（`annual-leave`）而不是数据库 UUID。
- **实测**：重建语料后 **8 个 UUID 全变**，而指纹**仍等于** `a7797b06…90afe` ✅
  → 证明"换了 UUID 但内容没变"这件事**不会误报**。
- **不这么做**：同 ①。

### 取舍 ③ — C 类题只判工具调用（方案乙），**不改写 `reference`（方案甲）**

| 维度 | 乙（已选） | 甲 |
|---|---|---|
| 贴合 C 类题考点 | ✅ 考的就是"会不会选对工具" | ✗ C05~C07 问「现在几点」，答案不固定，**写不出可核对的标准答案** |
| 与已有设计对称 | ✅ 原本就写了「`tool_miss` 有否决权」，乙补上**对称的通过权** | ✗ |
| **评测集指纹** | **不变** → D21 校准的 ε **继续有效** | **变** → **ε 作废，要重走一遍校准** |
| judge 成本 | 省掉 30 行 × 3 次 = **90 次调用/轮**（约 28 万 token） | 不变 |

- **背景（这段很重要）**：`tool_call` 类题的 `reference` 原本写的是**给评测人的元说明**
  （如「应当调用 search_documents 工具完成该请求」），被 judge 当成**标准答案**逐字比对
  → 判定"答案没按要求执行" → **给 0 分**。
  铁证：C05 题面「现在几点了？」，**系统调对了 `current_time`、答出了正确时间，judge 给 0 分**。
- **完整机制有三条，叠加生效**：
  ① judge 的 prompt 里**没有**工具调用记录 → judge 只能靠"无片段依据"**反推成编造**；
  ② C05~C07 的 `current_time` **不产生检索片段**，而 faithfulness 的 0 档正是
     "整段答案找不到任何片段依据" → **这一维结构性必 0**；
  ③ `reference` 一列同时承担"出题说明"与"标准答案"**两种含义** → judge 逐字比 → 冲突。
- → **分水岭不是"有没有调工具"，是"答案背后有没有 judge 认得的那种依据"。**
- **修法（方案乙）**：判据封成**唯一函数** `failure_taxonomy.is_tool_only()`，runner 与判定函数**共用它**。
- **验收**：`d22_verify` **77/77 全绿**（原 60 + 新增 17）。
- **数据作废规则**：`run_id=4/5/6` 的 `tool_call` 类题判定**全部作废**（**不重算、不删除**，
  留作"量具不合格时量出什么"的现场证据）。

### 取舍 ④ — 判据只写一次（`is_tool_only()`）

- **不这么做**：两处各写一份 `expected_tool is not None`，某处被改成 `category == "tool_call"`
  → **静默分裂**：runner **照常花钱打分**、判定函数**不看那批分数** ——
  **花了钱、落了库、一个都没用上，无报错**。

### 取舍 ⑤ — 三维度均分的分母**显式化**为 `scored_rows`

- **怎么做**：分母 = **有分数的明细行数**（`tool_call` 类题不判内容 → `score_*` 是 `NULL` → 不计入）。
- **不这么做**：
  - 诊断脚本印成 `39/50 = 78%`（**拿总行数当分母**）→ 改 `n_scored` 后才是 `39/40 = 98%`；
  - 「逐题并排」只比 `score_correctness` → 工具类题分数**恒为 `None`** → 被自动算成
    「**三配置一致**」→ **10 条题被悄悄豁免**，**不报错**（覆盖面型静默失效）。

### 取舍 ⑥ — 边界守卫**抛异常**（独立 `ReportGuardError`），不是打警告

- **不这么做**：这类错**无症状**（表格照排、脚本正常退出）；打警告的结局是「**没人看**」
  或「**被当噪音关掉**」。→ 所以 `scripts/d24_report.py` 里守卫不过时**退出码非 0**。

### 补充取舍（同类，一并列出）

| # | 取舍 | 不这么做（且不报错） |
|---|---|---|
| ⑦ | 历史数据「**作废但不重算不删**」 | 只改明细不改汇总 → **一个 run 两份数字，两份都"有来源"**，最难发现 |
| ⑧ | 结构断言拆成「**子集（永久有效）+ 总数（故意易红）**」 | 硬编码总列数 → `A8` **从 D22 一直红到 D24 无人察觉** |
| ⑨ | **不留死代码 + 不写撒谎的注释** | 注释描述了一个不存在的实现 → 后来人以为已经做了 |
| ⑩ | **计时起点口径要对齐** | D20 起点在锁外（0.84s 报成 **11.74s**）；D22 起点在 `gather` 之后（24 次 HTTP 耗时算成 **0.0s**）—— **两种都不报错** |

> 出处：`D22-决策材料.md §2/§3` · `D23-工具类题判定路径修复.md §3/§4/§11/§14` · `D24-总结.md §2.4/§7` · `D21-评测集与语料.md 附录B`

# 第四部分 · 结果：最终得到什么提升

## §10 消融结果

**数据来源**：[`../eval-report-2026-10-10.md`](../eval-report-2026-10-10.md)（**D36 正式消融**）。
`generation_runs = 3` · `runs_per_case = 3` · judge `deepseek`。

| 配置 | run | 检索 | 重排 | 准确率（按题） | 通过/总题数 | 正确性均分（按行） | 均分分母 |
|---|---|---|---|---|---|---|---|
| `pure_vector` | 26 | 向量 top5 | — | **98.00%** | 49/50 | 4.925 | 120（共 150 行） |
| `hybrid` | 27 | BM25+向量 RRF top5 | — | **98.00%** | 49/50 | 4.933 | 120（共 150 行） |
| `hybrid_rerank` | 28 | BM25+向量 RRF top20 | bge-reranker top5 | **98.00%** | 49/50 | **4.942** | 120（共 150 行） |

> ★ **两个口径不要互相印证（本轮最好的一个实例）**：
> **按题**看，三配置**完全相同**（98.00% / 逐题判定 50/50 一致）；
> **按行**看，正确性均分**略有差异**（4.925 → 4.933 → **4.942**，单调递增）。
> → 如果拿"按行均分一路上升"去讲「重排略好」，就是**把行级抽样差异当成了题级结论** ——
> 而题级判定**一个都没变**。**两个口径各自都对，互相印证就错。**

**术语注解**：**RRF**（Reciprocal Rank Fusion，倒数排名融合）= 把多路检索结果**按名次**融合成一路
（看名次不看分数，所以不同来源的分数不可比也没关系）。

**结论**：

- **三配置准确率完全相同（98.00%）→ 本轮消融未测出配置差异。**
- **PRD S2 验收点「混合+重排 vs 纯向量 ≥ +10 个百分点」→ 实测 +0.00 → ❌ 未达标。**
- **PRD S3「最终准确率 ≥ 88%」→ 98.00% → ✅ 达标。**

**⚠ 这个 0 差异不能解读成「重排无用」** —— 三条理由（全部可复核）：

1. **检索层已撞天花板**：三配置的 `Hit@1 / Hit@5 / Hit@10` 全 **100%**、`MRR` 恒 **1.000**（35 道可算题里
   **每一道的首篇 gold 都排第 1 名**）→ **不是重排没起作用，是没有一道题给过它发挥机会**。
2. **评测集区分能力不足**（结构性）：题由制度条款**轻度改写**，语料中**每个主题只有一篇文档**
   → 「找对文档」对三种配置都不构成挑战。
3. **「量具坏了」这种可能已排除**：随机基线 `Hit@5` 只有 **4.5%~9.4%**，
   而真实 gold 的 `Hit@5` 是 100%；`d23_metrics_verify.py` **33/33 全绿**。

→ **正确的说法**：「在**当前这份**评测集上，三个检索配置**无法区分**；**瓶颈是任务难度，不是检索配置**。」

**逐题并排（口径最严的一列）**：三配置**逐题判定 50/50 完全一致**（100%）。
唯一失败题 `B01`（`cross_doc`）在三个配置下**都失败**。

## §11 量具指标

**三层量具的实测现状**：

| 层 | 指标 | 实测 | 口径（分母） |
|---|---|---|---|
| **检索层** | `Hit@1 / Hit@5 / Hit@10` | **全 100%** | **35 道可算题**（单文档 25 + 跨文档 10），**文档级去重**后（同篇多片只算最早名次） |
| 检索层 | `MRR` | **恒 1.000** | 同上（35/35 题的首篇 gold 都排第 1 名） |
| 检索层 | 随机基线 `Hit@5` | **4.5%~9.4%** | **负对照**（随机撞上非 gold 文档的概率）→ 证明量具没坏 |
| **生成层** | 准确率（按题） | **98.00%（49/50）** | 分母 = **题数** |
| **裁判层** | 行级通过率（`正确性 ≥ 4` 的行 / 有分数的行） | **353/360 = 98.06%**（run 26/27/28） | 分母 = **有分数的明细行数**（工具类题不判内容）。⚠ 旧口径名「满分判定 \(39/40 = 97.5\%\)」指的是**同一件事**（已交叉验证：run 9/10/11 各为 `39/40`），只是 `gr=3` 后分母从 40 变成 120 |

**单次抖动与门槛**：

| 项 | 值 | 口径 |
|---|---|---|
| 裁判侧 ε（单次不一致率） | **0.95%**（点估计） · **0.17%~5.20%**（95% Wilson） | 判定次数 |
| 裁判侧 ε（保守口径 B） | **7.14%** | 题数 |
| 单次门槛 | **2.9 条**（点估计） / **11.42 条**（保守） | 题数（50 题规模） |
| 3 次投票后门槛 | **0.36 条**（点估计） / **2.5~3.79 条**（保守） | 题数 |
| 生成侧抖动率 | **10.0%**（Wilson 上界 40.4%） | 题数（10 条 `cross_doc` × 5 次生成） |
| 生成侧折算 50 题 | **5.0 ~ 20.2 条** | 题数 |

**⚠ 三个必须记住的口径陷阱**：

1. **别引「90% 满分」**：D21 那句 "45/50" 的分母是**判定次数**
   （10 条分层抽样 × 5 次打分），**不是题数**；样本级真相是 **10 条里 9 条满分**。
   把"次数"读成"题数"会把证据基础**夸大 5 倍**。
2. **ε 的两个值不是同一把尺子**：`0.95%` 是点估计、`7.14%` 是保守口径 → **并列比较即出错**。
3. **「行级」指标的分母是「有分数的行」、不是总行数**：`gr=1` 时代每配置有分数 40 行（**不是 50**）
   → `39/40 = 98%`，**不是** `39/50 = 78%`；`gr=3` 时代是 **120 行**（**不是 150**）
   → 逐配置 `117/120 = 97.50%` · `118/120 = 98.33%` · `118/120 = 98.33%`。

**检索层指标的边际信息（很关键的一句）**：
**三层全在（或接近）天花板 → 配置之间没有可改进的空间。**
这不是"没差异"，是**尺子没有分辨力**。

## §12 诚实记录：没测出什么、为什么

> 这一节的写法本身就是设计的一部分：**差异不显著时，要写明归因，而不是含糊过去。**
> 作废的实验、没测出的差异、判断错的地方**一律保留并写明原因** ——
> 它们是本项目最有说服力的部分。

| 项 | 内容 |
|---|---|
| **没测出什么** | 三个检索配置之间的**任何**差异（**0.00 个百分点**，逐题判定 **50/50 一致**） |
| **归因 1 · 检索层天花板** | 三配置 `Hit@k` 全 100%、`MRR` 恒 1.000 —— 不是重排没用，是**没有一道题给过它发挥机会** |
| **归因 2 · 评测集区分能力不足** | 题由制度条款轻度改写，语料中**每个主题只有一篇文档** → 「找对文档」对三种配置都不构成挑战 |
| **归因 3 · 排除项：量具没坏** | 随机基线只有 4.5%~9.4%；`d23_metrics_verify.py` **33/33 全绿** |
| **可量化的改进判据** | 让 gold 文档在**融合序**里的名次落进 **6~20** 区间（唯一能区分「融合 top5(B)」与「重排窗口 20(C)」的区间）→ **实测当前 0/35** |
| **本轮新发现** | 唯一失败题 `B01` 在三个配置下**答案 sha256 各不相同**（651/484/529 字）→ 那是**生成侧抖动**，「归因不同」**不能归因于配置** → **失败模式无法比较** |

**已经做过的「把任务变难」两条路线（剂量-反应实测）**：

| 路线 | 做法 | 结果 |
|---|---|---|
| 甲 · 改问法 | 把问题问得更难 | 10 条里 **9 条仍天花板** → 剂量不够 |
| 乙 · 加干扰文档 | 往语料里塞干扰项 | **只推得动向量路**（平均 1.25 位，8/8 单调）；**融合路平均 0.38 位且饱和**；**重排路 35/35 全在 top5** |

→ 这两条路线的价值在于**否证**：它们说明「加难题」不是简单调参数能解决的，
**必须改评测集的构造方式（主题冗余度）**，而不是加大力度。

**反例（如果只看表面数字会写成什么）**：若只看 D23 第一轮的表面数字 `88/92/90`，
会顺手写成「重排对答案准确率无明显提升」——
而真实原因有**两个**（**评测集缺陷** + **天花板效应**），**都不是重排本身**。
→ 这就是「**先修尺子、再看刻度**」的意义。

## §13 成本账

**正式消融（D36，`generation_runs=3` · `runs_per_case=3` · 50 题）实测**：

| 配置 | 生成阶段 | 打分阶段 | 该轮总墙钟 | LLM 调用次数 | token 合计 |
|---|---|---|---|---|---|
| `pure_vector` | 150 条 / **379.0s** | 360 次 / **91.3s** | **7 分 51 秒** | 651 | 1,473,018 |
| `hybrid` | 150 条 / **371.6s** | 360 次 / **91.9s** | **7 分 43 秒** | 651 | 1,454,391 |
| `hybrid_rerank` | 150 条 / **599.6s** | 360 次 / **91.9s** | **11 分 32 秒** | 652 | 1,482,597 |
| **三配置合计** | 450 条 | 1080 次 | **27 分 10 秒**（13:48:16 → 14:15:26） | **1,954** | **4,410,006** |

**三条可直接引用的观察**：

1. **打分阶段三配置几乎一样**（91.3 / 91.9 / 91.9 s）—— 因为 judge 与检索无关（打分只看答案文本）。
2. **重排把生成阶段拖慢了 1.6 倍**（371.6s → **599.6s**）：`hybrid_rerank` 每次检索都要过一遍
   **bge-reranker**（模型加载 1371ms 一次），**代价全在生成阶段**。
   → 与 `D23-检索层指标` 的离线结论一致（35 题：A 2.6s / B 1.4s / **C 35.1s**，重排是大头）。
3. **打分 360 次 ≠ 450 次**：150 份答案 × 3 次 = 450，**减去 30 份工具类题 × 3 = 90** → 360。
   ⚠ **「期望 450 次」这句话本身是有意的对账项** —— 它逼你解释那 90 次去哪了（§9 取舍 ⑤ 同一件事）。

**为什么日志必须全留**：D23 有一次用 `| tail -N` 截断日志，**事后无法复核 token 成本**
—— 这是本项目的一条硬纪律（同时记住：`cmd | tail -N` 会把**汇总行吃掉**，只剩表头）。

**成本结构（3 配置 × 50 题的预估，与实测对照）**：

| 项 | 预估（`d22_run.py` 文档头） | 实测 |
|---|---|---|
| 单配置生成 | 5~9 分钟 | `pure_vector` **6.32** · `hybrid` **6.19** · `hybrid_rerank` **9.99** 分钟 |
| 单配置打分 | ~2 分钟 | **1.52~1.53 分钟** ✅ |
| 单配置合计 | —— | **7 分 43 秒 ~ 11 分 32 秒** |
| 三配置合计 | —— | **27 分 10 秒** |

> ⚠ **预估被打破了**：`hybrid_rerank` 的生成阶段 **9.99 分钟**，**超出预估的 5~9 分钟上限** ——
> 原因是**重排没有被算进那个预估**。这是一个**低估**，如实记下来（不是"大概在区间内"就糊过去）。

**「重复 3 次」买到了什么**：

| 重复的对象 | 买到 | 代价 |
|---|---|---|
| judge 打 3 次（`runs_per_case=3`） | 裁判侧抖动从 **0.95% 降到 0.36% 门槛**（≈ 2.6 倍更稳） | 打分调用 ×3（约 +6 分钟/配置） |
| 系统跑 3 次（`generation_runs=3`） | 把生成侧抖动从"单次抽样"变成"多数投票" | **生成调用 ×3**（+12~13 分钟/配置） |

**值不值**：
- **本轮 `generation_runs=3` 的实测价值 = 证伪**：三配置在 `gr=1` 和 `gr=3` 下**都是 98.00%**
  → 说明「测不出差异」**不是跑得不够多**，而是**评测集本身没有分辨力**。**这个否定结论值这 24 分钟。**
- **检索层指标零 token 可复算**（§8）：**最便宜的那把尺子** → 应该**优先跑**它，而不是先堆生成次数。

## §14 五分钟讲述稿

**30 秒电梯陈述（可直接背）**：

> 「我给一个 RAG Agent 搭了一套评测体系。核心不是"跑个分"，是**先把尺子校准、再量东西**——
> 我用重复判定量出判分器自己的噪声（ε=0.95%），算出门槛：50 题上**差别不到 3 条题就不算差异**。
> 消融要**只改一个变量**，我做了纯向量 / 混合 / 混合+重排三档。
> 结果是**三档完全同分（98%）**；**这个 0 差异我没有含糊过去**，
> 而是定位到原因是**检索层已经撞天花板 + 评测集区分度不足**，并给出了**可量化的改进判据**。」

**五分钟主线（五段）**：

| 段 | 讲什么 | 关键句 |
|---|---|---|
| ① **为什么要有评测** | 直觉评测的三个失效点 | 「看几个例子觉得挺好」有三个独立的坑：抽样随缘 / 没有噪声概念 / 改动后无法归因 |
| ② **尺子怎么校准** | 量具先行 + ε + 门槛 | 「第 1 轮我测出 ε=0，**那是假数** —— judge 根本没用到阈值带，是**结构性锁死**，不是它稳」 |
| ③ **怎么量** | 两阶段 + 两个旋钮 + 抖动三层 | 「系统跑 3 次 vs judge 打 3 次，**是两件事**：一个对抗生成侧，一个对抗裁判侧；**投票对生成侧无效**」 |
| ④ **量出什么** | 三配置 98% 同分 + 归因 | 「0 差异**不等于重排无用**：`Hit@k` 全 100%、`MRR` 恒 1.0 —— **没有一道题给过重排机会**」 |
| ⑤ **怎么保证没写错** | 报告可仲裁 + 三条守卫 + 独立验证 | 「报告带 run_id、两张指纹、judge 与次数，路径回写 `eval_runs`；守卫不过**退出码非 0**；还有 60 条断言的独立验证脚本」 |

**演示脚本的七段（PRD §16.2）与降级顺序** → 见 `scripts/demo.sh` 与 D35 教程。

**⚠ PRD §16.4 明列的「不要说」**：❌「我和 Dify 比的是**检索算法**」——
对照只到**答案层**，说比了检索就是编。

### D.2 写作规则（**写本文档时仍在遵守**）

1. **同一句话只说一次**：数字与结论在本文档给一次；其他文件**引用它**，不得各写一份。
2. **每个数字必须标口径**：ε 有「点估计 0.95%」与「保守口径 7.14%」两种，**不是同一把尺子**。
3. **每个设计决策配反例**：必须写「不这么做会怎样」，且优先写**不报错的失败**。
4. **名词首次出现即注解**（本项目铁律）：判据是「**读者有没有定义过**」，不是"这词难不难"。
5. **失败要留档**：作废的实验、没测出的差异、判断错的地方一律保留并写明原因。
6. **不贴长代码**：代码归教程，本文档最多给**片段 + 指向**。
