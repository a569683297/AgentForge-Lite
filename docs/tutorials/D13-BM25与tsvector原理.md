## 2. 核心概念讲解

### 2.1 为什么向量检索之外还需要一条腿

D9 做的是**向量检索（稠密检索）**：把文本编码成向量，比谁的向量更近。它擅长"**意思相近但用词不同**"——问"报销怎么走"能命中写着"费用申请流程"的段落。

它有个结构性弱点：**精确符号**。

> 知识库里有这么一句：「**E104** 报警表示伺服过载，需检查 **SN-2024-087** 型号的驱动板」
>
> - 用户问"E104 是什么报警" → 向量模型把 `E104` 编进 1024 维里，这几个字符在语义空间里信息量极低，真正那一句很可能**进不了 Top-K**
> - BM25 做**词面精确匹配**：`E104` 只在那一篇出现 → IDF 极高 → 一击命中

|  | 稀疏（BM25 / 关键词） | 稠密（向量） |
|---|---|---|
| 表示 | 词表维度，绝大多数位置是 0 | 固定维数，每一维都有值 |
| 匹配依据 | **词面重合** | **语义距离** |
| 强项 | 编号、型号、缩写、罕见专名 | 同义改写、"换个说法" |
| 弱项 | 换个说法就找不到 | 精确符号容易丢 |

**两条腿的弱点几乎不重叠，这就是要混合的原因**（融合算法 RRF 在 D17）。

⚠️ 一个必须说准的机制：**同一条查询并行跑两条腿，各出一个榜单，再融合**——不是"把查询拆两半，分别喂给两条腿"。（这个误解在 D13 验收时出现过一次。）

### 2.2 BM25 的三个部件

```
score(D, Q) = Σ  IDF(q) ×  f(q,D) × (k1 + 1)
                        ──────────────────────────────────
                         f(q,D) + k1 × (1 - b + b × |D|/avgdl)

IDF(q) = ln(1 + (N - df(q) + 0.5) / (df(q) + 0.5))
```

| 部件 | 干什么 | 参数 |
|---|---|---|
| **TF（词频）** | 出现越多越相关，但**要饱和**：不是线性加分，有天花板 `k1+1` | `k1`（常用 1.2~2.0） |
| **IDF（逆文档频率）** | 越稀有的词越有区分度。"的/是/我们" IDF≈0，`E104` IDF 极高 | — |
| **长度归一化** | 压掉长文档的天然优势：把"出现 5 次"换成"密度" | `b`（0=不归一化，0.75 常用，1=完全归一化） |

**两个参数压的是两种不同的偏置，这是最容易混的一处：**

| 参数 | 压的偏置 | 场景 |
|---|---|---|
| **k1** | **文档内**偏置 | 同一个词在同一篇里反复刷（防关键词堆砌） |
| **b** | **文档间**偏置 | 文档长度差异（防长文档白占便宜） |

**和 TF-IDF 的关系（面试常问）**：
> **BM25 = TF-IDF + TF 饱和 + 文档长度归一化。** 后两条是它的全部改进，也是它比 TF-IDF 明显更准的原因。

⚠️ 工程上的要害：**IDF 和 avgdl 是全局统计量**——需要"多少篇文档包含这个词""平均文档多长"。这意味着 **BM25 必须能看到整个语料，语料一变分数全变**；而向量检索每篇文档独立编码、互不影响。**这是两者在工程上最根本的差别。**

### 2.3 tsvector 是什么

- **`tsvector`** = 预处理后的**词位列表**，形如 `'智能':2 '机器':3 '学习':4,7`（词 + 出现位置）
- **`tsquery`** = 查询表达式，形如 `'智能' & '机器'`
- **`@@`** = 匹配操作符
- **GIN 索引** = 倒排索引（term → 文档 id 列表），这就是"稀疏检索"的物理形态
- 入口函数：`to_tsvector('配置名', 原文)`

**类比你的前端经验**：这东西本质就是 `Map<token, Set<docId>>` 的数据库持久化版，多了位置信息。区别是由数据库维护，带事务和并发。

### 2.4 ⚠️ 本日最大的坑：`tsvector` ≠ BM25

检索链路其实是**三层**，而"路线"只在前两层分岔：

| 层 | 干什么 | 三种做法 |
|---|---|---|
| ① 切词 | 原文 → 词序列 | A 应用层 jieba / B 库内 zhparser / C 不切 |
| ② 索引 | 词 → 倒排表 | A、B 都是 `tsvector + GIN`；C 是 trigram |
| ③ **打分** | 候选 → 相关性分数 | **三条路线默认全落到 `ts_rank` / `similarity`——都不是 BM25** |

**PRD 第 144 行的原文是错的（或者说，把两层写成了一个词）：**

> **F3.4** 混合检索：BM25（PostgreSQL tsvector）+ 向量（cosine）→ RRF 融合（k=60）

`tsvector` 是**索引结构**，BM25 是**打分公式**。PostgreSQL 给了你索引，也给了你一条打分函数（`ts_rank`）——**但 `ts_rank` 不是 BM25**（原因见 §3 探针③）。

**面试话术要么不说，要么说准**：

> ❌ "我们用 PostgreSQL 的 tsvector 做 BM25"
> ✅ "倒排索引用 `tsvector + GIN`，**BM25 打分是我们自己用 SQL 实现的**"

### 2.5 三条路线，以及为什么选 A

| | A 应用层分词 | B 库内 zhparser | C pg_trgm |
|---|---|---|---|
| 装什么 | `jieba`（纯 Python，1 个包） | 装 deb（PIGSTY 提供 pg14–18） | 无（`CREATE EXTENSION`） |
| 动镜像 | 不用 | **要，自写 Dockerfile** | 不用 |
| 加 token 列 | 要（+ 迁移 + GIN 索引） | 不用 | 不用 |
| 分词一致性 | **靠代码保证**（有错配风险） | 库内天然一致 | 不涉及 |
| 自定义词典 | 改 jieba 词典 | 库内表，可动态加 | 无 |
| 打分 | `ts_rank` | `ts_rank` | `similarity` |
| 能不能做真 BM25 | ✅ 配合自算公式 | ❌ 仍要自算 | ❌ |

**选定 A**，理由四条：

1. **不动部署形态**（不用自建镜像、不改 compose）
2. **一天能做完**（D16 的工程量可控）
3. **分词器在应用层 = 换分词方案只需改一处**
4. **它让"自算 BM25"变成一条 SQL**——因为 token 被存成了空格分隔的纯文本，tf 可以直接数出来（见 §3 探针④）

它的真实风险是第 3 列第一条"分词一致性靠代码保证"，**兜法照抄 D12 的教训：加结构自检断言**。

### 3.1 顶部常量

```python
K1 = 1.2     # 词频饱和：控制"同一个词在同一篇里重复出现"的边际收益上限
B = 0.75     # 长度归一化：控制"长文档天然占优"要被压掉多少（0=不管，1=全按长度压）

PROBE_DOCS = [
    ("智能 智能 智能 智能 智能 " + " ".join(["其他"] * 15), "关键词堆砌：tf=5，但文档长（20 词）"),
    ("智能 学习", "短而精：tf=1，文档仅 2 词"),
    ("学习 学习 学习", "不含查询词"),
    ("智能 学习 学习 学习", "tf=1，文档 4 词"),
]
```

- 语料是**刻意构造的对撞**：第 1 篇 TF 最高但文档最长，第 2 篇 TF 最低但文档最短。**只有这种构造才能看出 `k1`/`b` 到底有没有生效。**
- token 用**空格连接**存成纯文本 —— 这正是路线 A 的存储形态，也是后面 tf 能直接数出来的原因。

### 3.2 `_idf()` —— 一个函数的三个输入

```python
def _idf(n: float, df: float) -> float:
    """IDF = ln(1 + (N - df + 0.5) / (df + 0.5))。越稀有的词分越高。"""
    return math.log(1 + (n - df + 0.5) / (df + 0.5))
```

`+0.5` 是平滑项：避免 `df=0` 时除零、也避免 `df=N` 时 IDF 变成 0 或负数。**注意它需要 `N`（全库文档数）和 `df`（含该词的文档数）——这两个量都不在单篇文档里，这就是"BM25 是语料级算法"的字面含义。**

### 3.3 `BM25_SQL` —— 逐 CTE 说明

这是本日的核心资产，**D16 的正式实现基本就是它的工程化版本**。

| CTE | 作用 | 关键点 |
|---|---|---|
| `docs` | 取 token 串 + 算文档长度 `dl` | `array_length(string_to_array(tokens,' '),1)`；`::float` 避免整数除法 |
| `q` | 查询拆成词序列 | D16 里这一步换成 jieba 分词输出 |
| `corpus` | 语料统计 `N` / `avgdl` | **两个全局量**，需扫全表 |
| `tf` | 每个 (文档, 查询词) 的 `f` | 直接数 token 串里出现了几次 |
| `df` | 每个查询词的 `df` | `WHERE f > 0` 只数命中的文档 |
| `scored` | 套公式求和 | 逐词算 `IDF × 饱和后的 TF`，再 `sum()` |

**⚠️ 那两处 `CAST(... AS double precision)` 不是多余的**，原因见 §7 坑 1——不加它，`k1` 会变成 `1`、`b` 会变成 `0`，**`b=0` 等于把长度归一化整个关掉**，而脚本不会报任何错。

**看 id=1 与 id=2 这两行——这就是 `k1` 和 `b` 到底在干什么的实证：**

- `ts_rank` 把**刷了 5 遍关键词的长文档排第 1**（被堆砌骗了）

## 4. 类比迁移表

| 今天的新东西 | 你已经会的东西 |
|---|---|
| `tsvector` + GIN 倒排索引 | 手写的 `Map<token, Set<docId>>`，只是由数据库持久化 + 带事务 |
| `tsquery` + `@@` | 结构化查询表达式（像 Mongo 的查询对象） |
| `ts_rank` vs BM25 | 简单排序函数 vs 带权重、饱和、归一化的排序函数 |
| `k1` 饱和参数 | 评分封顶 / `Math.min(score, cap)` |
| `b` 长度归一化 | 把"绝对次数"换成"占比/密度"（如按总请求数归一化） |
| `N` / `avgdl` / `df` 全局统计量 | 需要全量数据的聚合派生状态（不能只看单条记录） |
| 应用层分词 | 写库前的 ETL transform——**在进数据库之前把数据变形** |
| 索引侧/查询侧分词器必须一致 | 序列化与反序列化必须用同一套 schema |
| 绑定参数被推断成 integer | TS 里类型推断失误导致的静默截断（不报错，结果错） |

## 5. 面试考点

**Q1：BM25 和向量检索各擅长什么？为什么要混合？**
> BM25 做词面精确匹配，擅长编号/型号/缩写这类罕见专名；向量做语义匹配，擅长得同义改写。**两者弱点几乎不重叠**：问"E104 报警"时向量的那几个字符在语义空间信息量极低，真正那一句可能进不了 Top-K；而"报销怎么走"这种换个说法的问法，BM25 找不到。所以**同一条查询并行跑两条腿、各出一个榜单，再用 RRF 融合**。

**Q2：`k1` 和 `b` 分别控制什么？**
> `k1` 控制**文档内**的词频饱和——防同一篇里把关键词刷几十遍；贡献上限是 `k1+1`，边际收益递减。`b` 控制**文档间**的长度归一化——把"出现次数"换算成"密度"，用全库平均长度当标尺。**一个管文档内，一个管文档间**，这是两个不同的偏置，不能混。
> 追问 `b=0` 会怎样：长度项完全失效，同 TF 下长短文档得分相同 —— 实测过，长 5 倍的文档拿到**完全一样**的分数。

**Q3：`ts_rank` 的公式是 BM25 吗？**
> 不是。**`ts_rank` 默认没有长度归一化**（实测：短文档与 16 词长文档同分 `0.060793`；它另有 `normalization` 开关可以加长度惩罚，但公式整体仍不是 BM25）；更根本的是**它算不出 IDF**——`ts_rank(tsvector, tsquery)` 只接收这两个入参，拿不到 `df`/`N`/`avgdl`，**IDF 在数学上就不可能算出来**。

**Q4：你们的知识库怎么实现 BM25 的？**
> **倒排索引用 PostgreSQL 的 `tsvector` + GIN**：入库时把切片分词后的 token 串转成 `tsvector` 存一列并建 GIN 索引，做词面匹配和候选召回。**BM25 打分是自己用 SQL 实现的**（因为 PostgreSQL 没有内置 BM25）：`N`/`df`/`avgdl` 三个语料统计量现算，逐查询词算 `IDF × 饱和 TF` 再求和排序。
> 追问代价/规模：现算是全表扫，数据量大要改成维护统计表或缓存——这正是专门的 BM25 扩展（如 `pg_textsearch`）要自建专用索引存语料统计的原因。

**Q5：中文怎么办？**（PostgreSQL 内置分词器不支持中文，这是必被追问的点）
> 有三条路：① **应用层预分词**——用 jieba 切好词、空格连接存一列，再用 `to_tsvector('simple', 那一列)`（**本项目选的这条**，零扩展依赖、不动部署）；② 库内装中文分词扩展 zhparser（分词在数据库内闭环，但要自建镜像）；③ 用 `pg_trgm` 做字级三元组模糊匹配（适合短字段补全，做段落级相关性排序不合适）。
> 无论哪条，**索引侧和查询侧必须用同一个分词器**——粒度不一致 token 就对不上。实测：预分词后查整词「人工智能」返回 False，因为索引侧已经被切成 `人工/智能`。

**Q6：异步/性能相关追问**（复用 D12 的话术）
> 关键词检索和向量检索分别是一次 SQL 一次向量化，都跑在 `BackgroundTasks` 那条异步入库链路之外；检索本身是同步查询，量大了靠 GIN + pgvector 索引，不靠加大线程。

## 6. 自测题（先自己做，再看参考答案）

1. BM25 的三个部件各在解决什么偏置？`k1=0`、`b=0` 分别会退化成什么样？
2. 从函数签名出发说明：为什么 `ts_rank` 算不出 IDF？
3. PRD 写「BM25（PostgreSQL tsvector）」错在哪？正确表述应该是什么？
4. 预分词方案里，如果**入库侧**用 jieba 默认词典、**查询侧**误用了另一份词典，会发生什么？怎么防？
5. 自算 BM25 需要 `N`、`df`、`avgdl` 三个全局量，当前实现是每次查询现算，代价是什么？量大了怎么办？

<details>
<summary>参考答案</summary>

**1.** TF 解决"出现越多越相关"（但必须饱和，否则关键词堆砌刷分）；IDF 解决"越稀有的词越有区分度"（"的/是"没有区分度）；长度归一化解决"长文档天然占便宜"。`k1=0` → TF 二值化（只问出现与否，重复无效）；`b=0` → 长度归一化完全关闭，同 TF 下长短文档同分（实测：`b=0` 时 3 词与 16 词文档都是 `1.7742`）。

**2.** `ts_rank(tsvector, tsquery)` —— 两个入参里，`tsvector` 只描述**这一篇文档自己**的词位，`tsquery` 只描述查询，**语料级信息（`df`/`N`/`avgdl`）压根没进函数**。IDF 需要"全库有多少篇文档含这个词"，所以不是"实现得不好"，而是**信息不足，算不出来**。

**3.** 错在把**索引结构**（`tsvector`）和**打分公式**（BM25）写成了一个东西。PostgreSQL 提供 `tsvector` + `ts_rank`，**没有内置 BM25**。正确表述：**"倒排索引用 `tsvector + GIN`，BM25 打分自己实现"**。

**4.** token 对不上：入库时存的是 `人工/智能`，查询时若切出 `人工智能`（或反之），`@@` 就匹配不到，**检索结果静默变差、不报错**。防法两条：① 分词器实例与词典配置**只有一处定义**，入库/查询共用同一个函数；② 加**结构自检断言**（如验证 `to_tsvector('simple', tokenize(样例)) @@ to_tsquery('simple', tokenize(样例))` 必为真），把静默失效变成显式失败——这正是 D12 外键坑的教训。

**5.** 代价是**每次查询都要扫全表**算 `N`/`df`/`avgdl`，查询量上来后线性变慢。三条出路：① 维护统计表（定期或入库时增量更新 `N`/`avgdl`/每个词的 `df`）；② 缓存统计结果；③ 换用自带专用索引、把语料统计存在索引里的扩展（`pg_textsearch` 的 memtable 就是这么干的，但它要求 PG17/18）。

## 7. 踩坑记录

### 坑 1（真实，写探针时踩的）：SQL 浮点参数被静默截断成整数

**现象**：探针第一版跑出来 `BM25 顺序 = [1,2,4,3]`、`ts_rank 顺序 = [1,2,4,3]`——**两列完全一样**，而这正好推翻了探针要证明的结论。同时 BM25 值也对手算不上（`0.59446` vs 手算 `0.50412`）。

**根因**（实测确认）：

```
SELECT :k1 + 1  →  2      ← 1.2 被推断成 integer 后截断为 1
SELECT 1 - :b   →  1      ← 0.75 被截断为 0
加 CAST 之后： 2.2 / 0.25  ✓
```

`:k1` 在表达式 `:k1 + 1` 里被 PostgreSQL 推断为 **integer**，Python 传的 `1.2` 被截断成 `1`；`:b` 同理 `0.75 → 0`。**`b=0` 意味着长度归一化被完全关闭**——探针要测的东西整个失效了，而脚本照样跑完、不报任何错。

**修法**（两层，缺一不可）：

1. **SQL 里浮点参数一律显式 CAST**：`CAST(:k1 AS double precision)`
2. **加两道防线**：
   - 参数自检：查一次 `CAST(:k1 AS double precision) + 1`，断言等于 `K1+1`
   - 属性断言：`assert bm25_order[0] == 2`（"短而精"必须胜过"堆砌的长文"）——**参数一旦失效，这条断言就会失败**

**三条教训**：

- **SQL 的浮点参数不要指望类型推断**，一律 CAST。这类坑的可怕之处是**不报错**。
- **脚本不能把结论硬编码在 `print` 里**。我第一版就是这样：明明打印出的数据和结论相反，脚本还是把"BM25 把它压下去了"照念一遍。**结论必须由数据驱动**（改成 `if bm25_order == ts_order` 分支输出）。
- **"能跑通"不等于"跑对了"**——和 D12 的 `create_all` 跳过、`.gitignore` 吞目录是同一类：**你以为某个操作按你的意图生效了，实际它的判断标准不是你想的那个。**

### 坑 2（表述错，被实测纠正）：`ts_rank` 有没有长度归一化

我先前的说法是"`ts_rank` 没有长度归一化"。**不准确**：它有 `normalization` 参数，只是**默认是 0（关闭）**。准确说法是"**默认参数下没有长度归一化**；开了会有长度惩罚，但公式整体仍不是 BM25"。**结论性表述必须带上前提条件**——这类"绝对化表述"在面试里同样会被追穿。

### 坑 3（实验设计错）：我自己设计的 IDF 探针不成立

为了"实测证明 `ts_rank` 没有 IDF"，我构造了一张表：`common` 出现在 3 篇、`rare` 只出现在 1 篇，查询写 `common | rare`，结果含 `rare` 的那篇分数更高。**这个实验不能证明任何事**——它分数高是因为**命中了 2 个词位**，不是因为 IDF 生效。

**正确做法**：IDF 缺失的论证走**结构性**路线（见自测题 2），**不要**把那个探针当证据引用。

**教训**：**不要用一个自己设计的、变量没控干净的实验去"证明"一个结论。** 实验证不了的东西，就用逻辑推。

### 坑 4（认知层，本日最大价值）：三条路线全都没有 BM25

我最初介绍路线 A/B/C 时，只讲了"谁切词、用什么索引"，把**打分**这一层默认带过。结果读完的印象是"选了 A 就有 BM25 了"——**直到你直接问"那这样来说的话，你三条路线都没有走 BM25?"**

**你是对的，三条路线一条都没有。** 根因在我：**把方案按"打包"讲（一条路线 = 一个完整方案），而不是按"层"讲。** 三层里 A/B/C 只在前两层分岔，打分层是独立的第三维——这一维默认值是 `ts_rank`，**它不是 BM25**。

**教训**：讲方案要**先分层、再说每层选什么**；用"方案"打包讲，会让读者以为"选了方案就拿到了全部能力"。

### 坑 5（资料核实）：zhparser 是不是必须从源码编译

网上大量教程说"zhparser 必须手动编译 SCWS + `make install`"。**查证结果：不必然**——PIGSTY 提供 pg14–pg18 的 deb 包（`apt install -y postgresql-16-zhparser`，2.3 版）；那些"必须手编"的教程，根因是 **PGDG 官方源不提供这个包**，不代表别的发行渠道也没有。

**教训**：查"某个东西能不能装"，要去看**发行方/仓库**，别信教程里的经验之谈。这条同样适用于评估"要不要换镜像"这类成本判断。
