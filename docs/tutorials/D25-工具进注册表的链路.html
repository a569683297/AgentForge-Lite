工具是怎么进到 Tool Registry 里的

D25 · 左边「本地工具」是已在跑的代码（`app/tools/`）；右边「MCP」是 D26/D27 要补的那一段 · 结论由真机 grep 与源码取证，非示意
一句话结论

Agent 引擎只依赖注册表的两个接口（get_tools_schema() 取工具目录、 execute_tool(name, args) 按名字执行），它自己一个工具名都不出现。 所以「工具从哪来」对它是不可见的 —— 只要是有人往注册表里写条目，它就照用。 MCP 干的事就是成为注册表的第二个写入者。

看图的关键：① 和 ①′ 是两个完全不同的来源（一个在你进程内的函数，一个在别的进程里）， 但 ③ 往下看过去没有差别 —— 引擎那一格拿到的永远只是「一张工具目录 + 一个按名字执行的入口」。

二、现有链路：本地工具的五步（全部可指认到行）

步在哪发生发生了什么
1 app/tools/current_time.py 工具函数上面加一个装饰器：@register(name="current_time", description="…", parameters={…})
2 app/tools/registry.py 的 decorator() 把 {function, description, parameters} 塞进模块级字典 _registry。
重名会当场 raise ValueError("工具名重复")。
3 app/tools/__init__.py 副作用导入（只为触发注册、不为使用）：from app.tools import current_time。
⚠️ 少了这一行，第 2 步就不会执行 —— 注册表是空的，且不报任何错。
4 agent_service.py 第 117 行 get_tools_schema() 把注册表渲染成 OpenAI function calling 的 tools 数组，随请求发给 LLM。
5 agent_service.py 第 145 行 LLM 回 tool_calls → execute_tool(名字, 参数) → 查字典、执行、str() 成字符串 → 包成 role:"tool" 消息回灌。

注册表里那一条到底长什么样

本地工具写进去的条目（键名来自 registry.py 源码）：

_registry["current_time"] = {
    "function":    <function current_time>,      # 真正的可调用对象
    "description": "获取当前时间…",                # 给 LLM 看，决定它会不会被选中
    "parameters":  {"type":"object", "properties":{}, "required":[]},   # JSON Schema
}

MCP 工具从 tools/list 拿回来的条目：

Tool(name="harness_diagnose", description="…", inputSchema={"type":"object", …})
                                       ↑
            两边都是 JSON Schema —— 这就是"能被同一张表装下"的前提
形状一一对应表（这是 MCP 能"零改动接入"的技术前提）：
语义本地工具（@register 参数）MCP（tools/list 返回）
叫什么namename
干什么用的descriptiondescription
参数长什么样parameters（JSON Schema）inputSchema（JSON Schema）
怎么执行function（本进程函数）没有对应物 → 要改成"记住它属于哪个 Server"
最后一行就是 MCP Client 存在的理由：前三项 MCP 已经给全了，只有"怎么执行"这一项必须由你的适配层补上。

三、所以 MCP Client 只要补三件事

动作什么时候做做什么
发现 Server 启动 / 重连时（一次性） 发 tools/list，拿回这台 Server 的全部工具（名字 + description + inputSchema）
适配 拿到清单后 把 inputSchema 原样当 parameters 用（同一套 JSON Schema，几乎不用转）， 再补一个"这条归哪个 Server"的标记，然后写进 _registry
分派 每次 execute_tool(name, args) 查这条名字属于哪个 Server → 往那个子进程发 tools/call → 把返回的 content 拼成字符串返回（execute_tool 的契约是返回 str）
三件事做完，注册表里就多了一批来源不同、形状相同的条目。Agent 引擎那一格 一个字都不用改 —— 它本来就不知道、也不需要知道工具在哪。

它从注册表导入的只有两个名字（第 37 行）：

自证要求：这条"命中数 0"必须能在文件外复现 —— 即任何人拿到这份仓库， 跑一遍同样的搜索都能得到 0。判据是这个 0 不是我填进去的， 否则就成了循环证据（自己写下"没有"，再拿它当"没有"的证明）。

五、三条边界 —— 「不改 Agent 代码」不等于「什么都好」

容易说过头的地方准确说法
"零改动" 改的不是代码，是数据：注册一台 Server 要给它 {name, command, args, env}（PRD F6.6 的 POST /api/mcp/register）。 → 准确说法是 「改注册表的内容，不改读注册表的代码」， 而且运行时就能加，不用重新部署。
"工具名会撞车" 两台 Server 都可能提供一个叫 search 的工具，而 register() 里 raise ValueError("工具名重复") 会在运行时直接炸。 → 所以 MCP 工具进表要带命名空间（PRD 里那个 harness_diagnose 就是"Server 名 + 工具名"的形态），并且注册表要额外记住归属哪个 Server。
"接口一致 ≠ 行为一致" 代码不改，但Agent 的行为会变：① 工具变多 → LLM 选择空间变大，可能选错、可能多花 token； ② 工具描述由别人写，写得差就选不中；③ 多了一整个进程生命周期 （子进程崩溃 / 泄漏 / 退出清理，PRD F6.7 专门写了这条）；④ 多了传输失败面 （stdio 断了、超时，而本地函数调用不会"连不上"）。 → MCP 降的是接入成本，不是运行风险。
还有一个细节：MCP 的返回值是双层的 —— content（给人/模型读的自然语言）+ structuredContent（给程序读的结构化值）。 而本项目 execute_tool 的契约是只返回一个字符串。 所以适配层必须做一次取舍：取 content，还是用 structuredContent？ → 适配层不是零成本的，它只是把成本从 Agent 挪到了 MCP Client： 一处改动，换整条引擎零改动。

六、为什么这条路走得通 —— 它是 D8 就铺好的扩展点

阶段"加一个工具"要做什么Agent 引擎改动
D6在 agent_service.py 里内联工具定义要改（工具与引擎耦合）
D8新建一个文件 + 加 @register，并在 __init__.py 里 import 一次零改动
D26/D27注册一台外部 MCP Server（给 command/args/env）仍然零改动
所以准确的说法是：MCP 本身并不"提供"零改动能力 —— 它填进了 D8 那个注册制设计早就留好的插槽。 用软件工程的词说，这叫 依赖倒置（引擎依赖"注册表接口"这个抽象， 而不是依赖具体工具）＋ 开闭原则（对新增 Server 开放，对修改引擎封闭）。
