## 1. 今日目标

1. 说清**为什么不能把 BM25 分数和 cosine 相似度直接相加**（用真实数字，不用"量纲不同"四个字糊过去）
2. 掌握 **RRF 公式** `score(d) = Σ 1/(k + rank_i(d))`，能徒手算两条文档的分数并比大小
3. 理解 **k=60 的取向**：奖励"被多路共同认可"，而不是"单路分数特别高"
4. 落地 `fuse_rrf()`（纯函数）+ `hybrid_search()`（两路并发 → 融合）
5. 认识 **RRF 的平局是结构性的**（名次交换的两条文档分数精确相等），并给出确定策略
6. 诚实界定验收边界：**能证明什么**（召回覆盖 ≥ 任一路）、**不能证明什么**（排序质量更高）

## 2. 核心概念讲解

### 2.1 问题的起点：两个排序，怎么合成一个

D16 之后我们手里有两个**互不相干**的排序：

| 路 | 排序依据 | 命中集合特征 |
|---|---|---|
| 向量（`search`） | cosine 相似度 | 广 —— 语义近的都进来，**字面无关也可能排前面** |
| BM25（`search_keywords`） | 词频 + IDF + 长度归一化 | 窄 —— **字面不命中就是 0 分，压根不进候选** |

最直觉的合体方式是加权求和：`α × cosine + (1-α) × BM25`。本项目实测数据直接把它否掉了：

| 查询 | 向量路实测分数区间 | BM25 路实测分数 |
|---|---|---|
| 「年假有几天」 | 0.1896 ~ **0.6637** | **2.4554** |
| 「E104型号参数」 | 0.3320 ~ **0.6342** | **3.3495** |
| 「报销单要谁审批」 | 0.3088 ~ **0.7074** | **2.5901** |

两个问题，都是数据摆出来的：

1. **量纲不同**：cosine ∈ [0,1]，BM25 无上界（本次 2~3，换个语料 10+ 也正常）。
   直接相加时 BM25 那一项完全主导，α 变成摆设。
2. **分布随查询漂移**：BM25 的 IDF 依赖全库 `df`，**语料一变所有分数都变**（D16 §2.4 的结论）。
   想用一个固定 α 摆平，等于假设"所有查询的分数分布一样"，而它必然不一样。

要治它得先把两路分数归一化（min-max / z-score…），而归一化本身要调参、还要**按查询**重算一
——绕了一大圈，还是回到"怎么调参"。

### 2.2 RRF：把分数扔掉，只留名次

```
score(d) = Σ   1 / (k + rank_i(d))          k = 60
           i
```

`rank_i(d)` 是文档 d 在第 i 路里的名次（**从 1 开始**）。**分数完全没有出现。**

- 出处：Cormack / Clarke / Buettcher, *Reciprocal Rank Fusion outperforms Condorcet and
  individual Rank Learning Methods*, SIGIR 2009（University of Waterloo）。
- k=60 是该论文的经验取值，Elasticsearch 等实现沿用。
- ⚠ **诚实标注**：和 D16 的 `b=0.75` 一样，**没有为本项目语料调过参**。
  真正调参要等 D20-D24 的评测体系。

为什么这样就好了：**名次是序数量，天然同量纲**；名次也不受分数分布影响。
两个问题同时消失，代价是丢掉"分差有多大"这个信息。

### 2.3 RRF 到底奖励什么（这是全篇最关键的一处）

| 文档 | 向量路 | BM25 路 | RRF 分 |
|---|---|---|---|
| A | rank1 | 缺席 | 1/61 = **0.016393** |
| B | rank5 | rank5 | 2/65 = **0.030769** |

**B 赢，赢 1.877 倍。** 而且注意 B 在 BM25 里是那批里的**最后一名**（该路只返回 5 条），
A 在 BM25 里**根本不存在**。

所以：

| 判据 | 会选谁 |
|---|---|
| 谁在单路的名次高 | **A**（向量第 1 名） |
| 谁被两条列表同时提到 | **B**（哪怕在两条里都垫底） |

RRF 选后者 —— 它奖励"**共识**"，不奖励"单路爆发"。

**代价（双刃剑）**：真有文档只在单路相关时，会被"两路都中等"的压过去。
净收益必须靠评测量化，实现上不做任何承诺。

### 2.4 k 在控制什么

k 越大 → 名次越"平等"，越只看"被几路提到"。实测（A5）：

| rank | k=1 | k=60 | k=600 |
|---|---|---|---|
| 1 | 0.5000 | 0.016393 | 0.001664 |
| 20 | 0.0476 | 0.012500 | 0.001613 |
| **rank1 ÷ rank20** | **10.500×** | **1.311×** | **1.032×** |

k=600 时 rank1 和 rank20 只差 3% —— 融合基本退化成"**按被提名次数排序**"，名次信息报废。
所以 k 不是越大越好；k=60 的位置是"rank1 与 rank2 只差 1.6%，但被两路提到直接翻倍"。

**一条能背下来的推论**：两路都 rank_r 的分数 `2/(k+r)`，要压过单路第一 `1/61`，只需
`2/(k+r) > 1/61 → r < 62`。即 **k=60 下，只要两路名次都进前 62，就胜过任何单路第一名**。
（k=1 时这个门槛是"两路都进前 3"。）

### 2.5 一个我原先没预料到的性质：平局是**结构性**的，不是偶发

融合分是 `1/(k+a) + 1/(k+b)`。只要两条文档在两路里的名次是**交换的**
（一条 v1/b2、另一条 v2/b1），和就**精确相等**。

本项目实测就撞上了：查「年假有几天」时

```
policy = (向量 rank2, BM25 rank1) → 1/62 + 1/61 = 0.032522
hr     = (向量 rank1, BM25 rank2) → 1/61 + 1/62 = 0.032522   ← 精确相等
```

第一次跑时，先后是由 `chunk_id`（UUID）大小决定的 —— 而 UUID 没有任何语义。
这是个**真问题**，不是理论洁癖：两路名次相邻的文档越多，交换型平局就越多。

解法是给 `sort_key` 定五档，把"必须有人拍板"的地方显式拍板：

| 档 | 规则 | 性质 |
|---|---|---|
| ① | `rrf_score` 降序 | RRF 主判据 |
| ② | 被几条列表提名（多者优先） | "两路都认可" > "单路认可" |
| ③ | 最好名次升序 | 同为两路提名时，名次靠前优先 |
| ④ | **向量名次升序（无则排后）** | ⚠ **这是策略，不是实测结论** |
| ⑤ | `chunk_id` 升序 | 终极兜底：保证两次跑出同一顺序 |

第 ④ 档为什么选"信向量"：本项目检索主路是向量（D9-D12 先建，PRD 的 hybrid 定义也是
"向量为主 + BM25 补字面"），且向量路对改写 / 近义查询更稳。
**这不是调参调出来的，等 D20-D24 有评测集后应回头验证。**

### 2.6 两路要并发发起

```python
vector_hits, keyword_hits = await asyncio.gather(
    search(query, top_k=HYBRID_CANDIDATE_K),
    search_keywords(query, top_k=HYBRID_CANDIDATE_K),
)
```

两路互不依赖：一路是"embedding 网络调用 + 向量排序"，另一路是"jieba 切词 + 倒排 + BM25 自算"。
顺序 `await` 的总耗时是两者**之和**，`gather` 是两者**最大值**。各拿各的 session，不共享连接。

`HYBRID_CANDIDATE_K = 20`（PRD §9.3：两路各 top20 → RRF → top20 → D19 重排 top5）。
为什么不沿用默认的 3：融合的价值在"给两路名次做仲裁"，窗口太窄会把
"单路第 8 名但另一路也认可"的文档直接砍掉 —— 而它恰恰是 RRF 想捞的。

### 2.7 融合需要"身份"，这是昨天埋下的伏笔

融合要判断"两路返回的这两条是不是**同一片**"。靠 `content` 字符串比对是脆的
（空白 / 截断差异都会静默配对失败，表现为"本该合并的一条变成两条并列"）。

所以 D17 第一步是给两路都补 `chunk_id`（切片主键）—— 见 §3.1。

### 3.4 `fuse_rrf()` —— 逐行

```python
merged: dict[str, dict] = {}
```

用 `dict` 而不是 `list` 作为累加容器：**key = chunk_id 天然去重**，
"同一片被两路命中"这件事就自动变成"往同一个 entry 上加分"，不需要任何去重代码。

```python
def absorb(hits: list[dict], leg: str) -> None:
    for rank, hit in enumerate(hits, start=1):
```

内层函数之所以抽出来，是因为两路的处理**只差 leg 名字和取哪个分数字段** ——
写两遍就是两份要同步维护的代码。`enumerate(..., start=1)` 里的 `start=1` 是硬性要求：
RRF 公式的 rank 从 1 开始，从 0 开始会让第 1 名拿到 1/60 而不是 1/61。

```python
        chunk_id = hit.get("chunk_id")
        if not chunk_id:
            logger.warning("融合跳过无 chunk_id 的结果 leg=%s rank=%d", leg, rank)
            continue
```

**跳过而不是抛错**：宁可少一条结果，也不要因为一条脏数据让整个检索 500。
（`.get()` 而不是 `[...]`：两路都保证有，但融合函数是纯函数、
验证脚本会喂手工构造的 dict，用 `.get()` 更稳。）

```python
        entry = merged.setdefault(chunk_id, {...})
        entry["rrf_score"] += 1.0 / (k + rank)
```

`setdefault` 的语义正是这里需要的："有就取出来、没有就先塞一份初始值再取出来"，
于是第二次命中的同一个 chunk 会**复用同一个 dict**，`+=` 就落在同一处。

```python
        if leg == "vector":
            entry["vector_rank"] = rank
            entry["similarity"] = hit.get("similarity")
        else:
            entry["bm25_rank"] = rank
            entry["bm25_score"] = hit.get("score")
```

**记名次 + 记原始分，但原始分不参与排序。** 记原始分的用途有二：
① 出问题时能一眼看出"这条是向量排第几、BM25 排第几"；
② D23 消融实验要展示两路差异时直接可取，不用再回查。

```python
        ranks = [r for r in (entry["vector_rank"], entry["bm25_rank"]) if r is not None]
        return (-entry["rrf_score"], -len(ranks), min(ranks),
                entry["vector_rank"] if entry["vector_rank"] is not None else 10**9,
                entry["chunk_id"])
```

排序键见 §2.5。两处细节：
- `-len(ranks)` 用**负号**把"多者优先"塞进升序 `sorted`；后两档同理用负号 / 正号控制方向。
- `10**9` 是"无向量名次则排到最后"的哨兵值。**不能写 0**：0 会被当成"比 rank1 还靠前"。

```python
    ordered = sorted(merged.values(), key=sort_key)
    for entry in ordered:
        entry["rrf_score"] = round(entry["rrf_score"], 6)
```

**先排序、后 round**：round 只影响展示，不能让它参与比较（否则两个相差 1e-9 的分数
会被 round 成同一个值、排序失去区分度）。

### 3.5 `hybrid_search()` —— 逐行

```python
    vector_hits, keyword_hits = await asyncio.gather(
        search(query, top_k=HYBRID_CANDIDATE_K),
        search_keywords(query, top_k=HYBRID_CANDIDATE_K),
    )
    fused = fuse_rrf(vector_hits, keyword_hits, top_k=top_k)
```

**服务层薄、纯函数厚**：这个函数只做三件事（并发取数 → 调纯函数 → 记日志）。
好处是**融合逻辑可以脱离数据库单测** —— 验证脚本 A 段 11 条断言
一条数据库都不用连。

```python
    overlap = len({h["chunk_id"] for h in vector_hits} & {h["chunk_id"] for h in keyword_hits})
    logger.info("混合检索完成 query=%r 向量=%d BM25=%d 交集=%d → 融合返回=%d", ...)
```

**交集数是这条日志里最值钱的量**：它是"两路是否真的互补"的体温计。
交集≈并集说明两路高度一致（RRF 无事可做）；交集=0 说明两路完全无关（结果会各占一半）。

```python
    if not keyword_hits:
        logger.info("混合检索降级：BM25 路无结果，本次等效纯向量检索 query=%r", query[:20])
```

最常见的触发场景是"查询全是标点"（清洗后无 token）。此时**融合自动退化成向量单路**
（实测 D1b：融合结果与向量路顺序完全一致），不报错、不丢结果，只是丢了关键词那一路的仲裁。

### 3.6 `scripts/d17_hybrid_verify.py` —— 6 段断言

| 段 | 测什么 | 关键断言 |
|---|---|---|
| A | RRF 纯函数（不连库） | A2 逐条复算分数一致；**A4 原始相似度 0.99 的 A 被 B 反超**；A10 交集条目必胜"名次更差"的单路条目 |
| B | 真实两路融合 | B3 融合结果 == 两路**并集**；B4 分数可由记录的 rank 反推 |
| C | 抽样对比（验收点） | C1 覆盖两路前三名；C1b 有交集时融合首位来自交集 |
| D | 边界 | D1b BM25 为空时融合与向量路**顺序完全一致**（降级而非打乱） |
| E | 契约 | E1b 字段精确集合；E2 两次调用顺序完全一致 |

**A4 为什么是判决性的**：它给 A 的 `similarity` 喂了 **0.99**、B 只给 **0.10**，
如果实现里偷看了分数，A 会赢；实测 B 赢（0.030769 > 0.016393）。
这条断言直接测"分数有没有被真正扔掉"，不是测公式算得对不对。

**A10 是可证明的性质，不是观察**：

```
a 在内容路名次 r1 < b 的唯一名次 r
→ score(a) ≥ 1/(k+r1) + 1/(k+r2) > 1/(k+r1) > 1/(k+r) = score(b)
推论：交集非空且交集中最大名次 ≤ k 时，2/(k+m) ≥ 2/(2k) = 1/k > 1/(k+1)
     → 融合第一名必定来自交集
```

验证脚本对全部条目做了 O(n²) 的暴力检查，0 违例。

## 4. 类比迁移表

| 今天的概念 | 你已会的（React / TS / Node） |
|---|---|
| RRF 只取名次、扔掉分数 | 排行榜合并时用 `rank` 而不是原始票数 —— **序数量不需要统一量纲** |
| 两路 `asyncio.gather` | `Promise.all([a(), b()])`：两个互不依赖的请求并发而不是串行 |
| `merged` 用 dict 按 key 累加 | `reduce` 成 `Map<id, item>` 做归并，key 天然去重 |
| `sort_key` 返回多档元组 | JS 的 `arr.sort((a,b) => a.x - b.x || a.y - b.y || ...)` 链式比较 |
| `setdefault` | `Map` 的 `if (!map.has(k)) map.set(k, init)` 惯用法 |
| 融合需要稳定 `chunk_id` | React `key` 必须用稳定 id、不能用数组下标 —— 同样是"身份"问题 |
| 平局要有确定策略 | 排序算法不稳定会让 UI 出现"每次渲染顺序不同" |

## 5. 面试考点

**Q1：为什么用 RRF 而不是加权求和？**
> 分数不可比：cosine 有界 [0,1]，BM25 无上界（实测本语料 2~3），直接相加时 BM25 完全主导；
> 而且 BM25 的 IDF 依赖全库 df，语料一变所有分数都变，固定权重等于假设"所有查询分布一样"。
> RRF 只取名次 —— 名次是序数量，同量纲，也不受分布影响。
> 代价是丢掉"分差"信息，收益是不用调权重、可跨检索器组合。

**Q2：RRF 会推什么样的文档到前面？**
> 被多路共同认可的。极端对照：一条"两路都排第 5"的文档（2/65=0.0308）
> 会压过一条"向量第 1 但 BM25 完全没召回"的文档（1/61=0.0164）。
> 代价是"只在单路相关"的文档会被牺牲，净收益要用评测量化。

**Q3：k=60 是怎么定的？**
> Cormack 2009 的经验取值，业界沿用。我们**没有**为本项目语料调过参（诚实标注）。
> 它控制"头部有多集中"：k 越大名次越平等（k=600 时 rank1/rank20 只差 3%，
> 融合退化成按提名次数排序）；k 越小越看重单路名次（k=1 时差 10.5 倍）。

**Q4：融合要解决什么工程问题？**
> 身份对齐。两路返回的是两套 dict，必须能判断"是不是同一片"。
> 用内容字符串比对很脆（空白 / 截断差异会静默配对失败，两条本该合并的变成并列），
> 所以两路都要带 `chunk_id`。
> 另外融合后是**并集**、不是交集 —— 不丢任一路的结果，这也是可断言的（B3）。

**Q5：怎么验证融合是对的？**
> 三条结构性断言：① 融合结果 == 两路并集；② 每条融合分可由记录的 rank 反推；
> ③ 交集条目必胜"名次更差"的单路条目（可证明的性质，0 违例）。
> 至于"排序质量是否更高"—— 那要评测集，一天 4 篇语料证明不了，如实说。

**Q6（追问，容易翻车）：RRF 有没有平局？怎么办？**
> 有，而且是**结构性**的：名次交换的两条文档（v1/b2 与 v2/b1）分数精确相等，实测撞到过
> 0.032522 == 0.032522。所以要有一套确定的排序键：分数 → 被提名路数 → 最好名次 →
> 向量名次（**策略选择，非实测结论**）→ chunk_id 兜底。

## 6. 自测题（先自己做，再看参考答案）

1. 文档 A：向量 rank2、BM25 缺席；文档 B：向量 rank9、BM25 rank9。谁高？高多少倍？
2. k 从 60 调到 5，融合会往哪个方向变？给出 rank1 与 rank20 的贡献比。
3. 「融合的召回覆盖面 ≥ 任一路」这句话，为什么是**结构性保证**而不是"经验观察"？
4. 如果两路返回的结果里都没带 `chunk_id`，融合会怎么坏？坏的时候会不会报错？
5. 为什么融合分相同的时候，`sort_key` 第 ② 档（被几条列表提名）要排在第 ③ 档（最好名次）前面？
   举一个能体现差别的例子。

<details>
<summary>参考答案</summary>

1. A = 1/62 ≈ 0.016129；B = 2/69 ≈ 0.028986。B 高 0.028986 / 0.016129 ≈ **1.797 倍**。
   算法：① 单路贡献 `1/(k+rank)`；② 缺席 = 0；③ 求和；④ 比值用交叉相乘避免除不尽。
2. k 变小 → 越看重"单路名次靠前"。rank1/rank20：k=5 时 (1/6)/(1/25) = **4.167×**
   （k=60 是 1.311×）。方向：头部更集中，单路第一名更容易夺回主导权。
3. 因为融合是**在并集上做排序**，不是"在交集上做排序"：`absorb` 把两路每一条都塞进 `merged`，
   `top_k` 只是在最后截断。B3 断言的就是 `set(fused) == set(vector) | set(keyword)`。
   （注意：这句话的前提是 **top_k ≥ 并集大小**；top_k 截断时当然会"少"，那是设计要求不是丢失。）
4. 会静默坏：同一片在两路被当成两条不同文档，各自计分、并列出现在结果里（重复片段占满 top_k，
   真正该排第一的反而被挤下去）。**不报错、不崩** —— 典型的静默失效，
   所以实现里对"缺 chunk_id"显式 `logger.warning` 跳过，验证脚本也有专门断言（A6）。
5. ② 管"被几条列表提名"，③ 管"名次多靠前"；RRF 的核心取向是**共识优先**，所以 ② 必须在 ③ 前。
   例子：X = 向量 rank2、BM25 rank2 → 2/62 = 0.032258；
   Y = 向量 rank1、BM25 缺席 → 1/61 = 0.016393。
   如果先看名次，Y（第 1 名）该赢；但 RRF 判 X 赢 —— 分数本身已经体现了这一点，
   ② 档是为了那些**分数恰好相等**的情形（如两路各 rank1 vs 单路 rank1）。

## 附录 A：端到端运行链路（实测）

### A.1 一次 `hybrid_search()` 的完整过程

```
hybrid_search("灰度回滚", top_k=5)
  → asyncio.gather(
        search("灰度回滚", 20)          → jieba 不用；embedding → pgvector 距离排序
        search_keywords("灰度回滚", 20) → jieba 切词 → tsquery → GIN 倒排 → 自算 BM25
    )
  → fuse_rrf(两路结果, top_k=5)
        absorb(vector, "vector") / absorb(keyword, "bm25")
        → merged（按 chunk_id 合并、累加 1/(60+rank)）
        → sort_key 五档排序 → round(6) → 截断 top_k
  → 返回 [{chunk_id, content, source, page_ref, rrf_score,
            vector_rank, bm25_rank, similarity, bm25_score, retriever}, ...]
```
