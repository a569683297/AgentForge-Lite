## 2. 核心概念讲解

**本节新名词先注解**（第一次出现即注，不堆到文末）：

| 名词 | 一句话注解（它是什么 / 解决什么问题） |
|---|---|
| **幂等**（idempotent） | 同一个操作**跑一次和跑 N 次结果相同**。解决"脚本重跑会不会把数据搞乱"。本项目里 = 已入库的文档再跑一次不改动、不报错 |
| **播种**（seed） | 给一个空系统**预置一批基础数据**，让它开箱就有东西可看。本项目 = 上传 3 份示例文档 |
| **前置检查**（preflight） | 正式动作**之前**先跑一遍"条件够不够"，不满足就早退并说明原因 —— 避免跑到一半才炸 |
| **退出码**（exit code） | 进程结束时交给调用方的一个整数，0 = 成功。本项目定**三档**：0 成功 / 1 真坏了 / 2 前置没满足 |
| **冒烟测试**（smoke test） | 只验证"主链路通不通"的**最少量**检查（通了不代表全对，但堵了就一定有问题）。名字来自"通电看冒不冒烟" |
| **ToUnicode 映射表** | PDF 里的一张**字符对照表**：告诉提取工具"这个字形对应哪个 Unicode 码点"。它错了，PDF 看着正常但**机器提取出的字是错的** |
| **字体子集**（font subset） | 生成 PDF 时**只嵌入用到的那些字**（不嵌整个字体文件），为的是把文件压小。副作用是子集里的字要另建 ToUnicode 映射，错就错在这里 |
| **Kangxi 部首区** | Unicode 里的一片区域（U+2E80–U+2FDF），存的是"部首"这种独立字符 —— 例如 `⼿`(U+2F3F) 与汉字 `手`(U+624B) **长得几乎一样、码点完全不同** |
| **NFKC 归一化** | 一种字符标准化：把"兼容形态"折叠回常用形态（如全角 `Ａ` → 半角 `A`）。跑一次 `unicodedata.normalize("NFKC", s)` 即可 |
| **文本层**（text layer） | PDF 里**可被搜索/复制的文字数据**（区别于"只是画出来的图形"）。扫描件没有文本层，本项目要求必须有 |
| **`page_ref`** | 本项目给 PDF 切片挂的**来源页码**（`p.1`…`p.5`），让引用能定位回具体页 |
| **降级**（graceful degradation） | 某个依赖挂了时**主动退到一个弱一点但仍可用的形态**，而不是整体崩掉。本项目 = 外部工具下线后，Agent 退回纯知识库问答 |
| **同源**（same-origin） | 页面与它请求的接口**协议 + 域名 + 端口三者全同**。后端没开 CORS 时，前端必须与它同源才能调通 |
| **`headless` 模式** | 让浏览器**不开窗口**地跑（用来截图、导 PDF）。本项目用它把 HTML 变成 PDF |
| **Arial Unicode MS** | macOS 自带的一个**大字符集字体**（`/Library/Fonts/Arial Unicode.ttf`）。今天它被用作 PDF 生成字体，因为**只有它的 ToUnicode 是对的** |

### 2.1 为什么偏偏是这三件 —— 验收线在要求什么

PRD `F10.3` 原文只有一行：

> **F10.3** README（架构图 + 启动指南 + 演示脚本）

而 `F10` 那一行的**验收原话**（`docs/PRD-v4.1-含前沿技术.md` L462）是：

> **验收**：全新环境 docker compose up 后 **10 分钟可演示**

这句话拆开就是三件事，一件对应一件：

| 验收要求 | 靠谁满足 | 落到哪个文件 |
|---|---|---|
| **能起**（10 分钟内起得来，不用问人） | **启动指南** | `README.md` §3 |
| **能看明白**（30 秒建立心智模型） | **架构图** | `docs/架构图.md`（+ README §2 指过去） |
| **能用**（有固定动作，不靠临场发挥） | **演示脚本** | `scripts/demo.sh`（+ README §4） |

→ **关键认知**：这三件**不是"补文档"，而是验收本身**。缺一件，"10 分钟可演示"就不成立。

⚠ 一个容易搞混的点（本轮复述判定时纠正过）：**`README.md` 是总入口**，F10.3 里它被括号括住的那三个词
是"它要装订的东西"，不是"它的全部职责"；它的**专属职责**是**启动指南**那一格。

### 2.2 「可复现」比「可执行」难在哪 —— 三个硬条件

"脚本能跑"容易，"**换个环境还能跑**"难。三个硬条件，缺一个都会让人卡住：

| # | 条件 | 不做的后果 |
|---|---|---|
| ① | **凭据分级**：`.env` 每一项从哪来、哪些**必填**、哪些**可空** | 别人 clone 下来起得来，但**一调用就报错**，且报错指向不明 |
| ② | **预热**：`npx` 拉包 + ONNX 模型（**分钟级**，只在首次用外部工具时触发） | 演示**第一次提问必卡** |
| ③ | **外部依赖的可复现边界**：明确写出"Langfuse 走云、Harness 走云 + 需要你自己的 PAT" | README 会**承诺一个做不到的"10 分钟"** |

★ 第 ③ 条最容易漏，而且它和本项目反复出现的一条纪律同源 ——
**别把"特定条件下的观测"写成"默认"**（D26 的协议版本、D25 的"规范新增了一代"都是同一个错型）。
**你必须主动划出"哪些能复现、哪些依赖你个人凭据"，而不是含糊地写"配置好环境变量即可"。**

### 2.3 为什么"预热"必须写进**启动指南**（时间账）

PRD `F10.4（v4.0 补充）` L464 是明文要求，不是我的设计：

> 同时**首次启动预热**必须写入启动脚本（`npx` 拉包 + 可选下载约 23MB ONNX 模型），**否则演示首问会卡顿**。

**时间账怎么算**（数字全来自 D34 §5.1 / §5.6 的实测）：

| 项 | 实际成本 | 什么时候发生 |
|---|---|---|
| `npx` 首次拉 `harness-mcp-v2` 包 | **2 分 31 秒**（直连 npmjs 超时，走国内镜像才拉到） | 第一次要用外部工具时 |
| 下载 ONNX 模型（`harness` 的语义检索用它） | **约 23 MB** | 同上 |

两个阶段卡住的**性质不同**：

- **部署阶段超时** = 慢，还能补救（重跑、等一会）
- **演示阶段卡住** = 卡在**第 4 段「外部系统互操作」**，而这一段对应验收表里的 **S10（必须级）**
  → 5 分钟演示里卡 2 分半 = **当场翻车**

还有两层，是这题真正的考点：

1. **"口头提醒"这个方案本身不成立** —— 它依赖**你在场**。而 F10 的验收场景恰恰是**别人 clone 下来自己起**，
   "没人提醒"才是默认状态。
2. **本项目已经把预热降级过一次** —— PRD §9.8 原文要"串入 compose 启动链"，因为 api 容器不装 Node，
   只能走它后半句 `make warmup`（**已登记的已知偏差**，见 §附录 C）。既然它**不在**启动链里，
   就**必须**在启动指南里显式列出来 —— 否则这个偏差就从"已知"变成"没人知道要跑"的**静默破洞**。

### 2.5 没有 Harness PAT 的人，断在第几步（分级 + 可判定信号 + 降级路径）

**PAT** = Harness 平台上生成的**个人访问令牌**（Personal Access Token），服务端靠它认人。
本项目的环境变量名是 `HARNESS_API_KEY`。

**先破一个直觉**：他**不会起不来**。两重原因 ——

1. `docker compose up` 起的四个服务跟 Harness 无关；
2. MCP 连不上会**降级**（PRD §16.3 明文：「连续失败时该工具下线，**Agent 降级为纯 RAG 回答，不阻断主流程**」）。

**真正的断点在第 4 段**：

| 段 | 需要 PAT？ | 没 PAT 时 |
|---|---|---|
| 1 开场 | 否 | 正常 |
| 2 知识库 | 否 | 正常 |
| 3 RAG 问答 | 否 | 正常 |
| **4 外部系统互操作** | **是** | **🔴 断在这里** —— 工具不在注册表 → Agent 降级为纯 RAG → S10（必须级）演示不出来 |
| 5 Agentic BI | 否 | 正常（但本版本该段整体未实现） |
| 6 评测 | 否（需先跑过评测） | 正常 |
| 7 Langfuse 回流 | 需 **Langfuse** key（另一个凭据） | 无 key 则断 |

**最坏的地方不是"断"，是"静默"**：他看到的只是"答案有点答非所问"，**看不到"你缺 PAT"**。

所以 README 给了他三样东西（不是写一句"配置好环境变量即可"）：

### 2.7 素材**不能随便写**：必须与 D21 的评测语料对齐

这是今天抓到的**最严重的一个坑**，它不是"文档写错"，而是**会污染历史结论**。

- 库里已有一篇 D21 的评测语料：**`员工带薪年休假与考勤管理办法.md`**（D21 的 50 道题里，
  「年假 5 天」这类数字的答案就出自它）
- 我第一版素材写的是「工作时间 **9:00–18:00**、迟到 **15 分钟**计违纪」
- 而 D21 那篇写的是「工时段 **9:00–12:00 / 13:30–18:00**、迟到**超过 30 分钟**计旷工半天」

→ **两份口径矛盾**。后果有两条，第二条更严重：

1. demo 提问会召回到**互相矛盾**的答案（用户体验层面）
2. **D21–D24 的评测结论会被污染** —— 评测题检索的是**整个知识库**，
   多一份同主题、口径不同的文档进来，命中集就变了（**成绩不可解释，且没人会想到去查它**）

**修法**：把新素材改成「**实施细则**」定位 ——

- 数字**全部对齐上位制度**，一个字不新造
- 只补上位制度**没覆盖的空白**（补卡流程 / 加班费 150-200-300% / 各类假期天数 / 九篇制度速查表）
- 显式**声明主从关系**（"天数出自上位《员工带薪年休假与考勤管理办法》，本细则不另作规定"）

**实测验证**（`logs/d35-demo.log` 第 3 段）：提问「一年有多少天带薪年休假」→
答出 **5/10/15 天分档 + 结转 5 天 + 换算公式**，来源 5 条跨 3 份文档
（`员工带薪年休假与考勤管理办法.md` ×2 / `公司考勤制度.md` ×2 / `FAQ-常见问题.md` ×1），
**没有矛盾**。详细对齐表见 §附录 B。

### 2.8 PDF 的 ToUnicode 陷阱（肉眼看不出、关键词检索静默失败）

演示素材里必须有一份 **PDF**（PRD §17.2 指定 `产品手册.pdf`），而本项目**没有 PDF 生成库**
（`pypdf` 只能读）。所以走的是：**写 HTML → 用 Chrome `--headless` 导 PDF**。然后踩了坑。

**第一版结果**：`pypdf` 提取出的文字里，`手册` 变成了 `⼿册`。定性后发现：

| 事实 | 数据 |
|---|---|
| 被替换的字符数 | **36 个**（去重后一批），全落在 **Kangxi 部首区**（U+2E80–U+2FDF） |
| 例 | `⼿`(U+2F3F) ← 本应是 `手`(U+624B) · `⻔`(U+2ED4) ← 本应是 `门`(U+95E8) |
| **NFKC 能不能还原** | ❌ **不能** —— `⻔` 这类字符 NFKC 归一化后**仍然不是** `门` |

**为什么这个故障特别坏**：肉眼看 PDF**完全正常**（字形一样），但
**关键词检索会静默匹配失败** —— 你搜"手册"搜不到，而这个失败**不报错**。

**为什么"入库时归一化"这条退路不成立**：因为 `⻔` 这种 NFKC 都还原不了，
所以**在入库侧修不干净**，只能**从源头（生成时）解决**。

**做法**：做一次**字体对照实验** —— 用同一个 HTML、只换 `font-family`，跑 6 种 macOS 中文字体：

| 字体 | 部首区字符数 | 结论 |
|---|---|---|
| PingFang SC | 8–9 个 | ❌ ToUnicode 错 |
| Songti SC / STSong / Heiti SC / Hiragino Sans GB | 8–9 个 | ❌ 同上 |
| **Arial Unicode MS** | **0** | ✅ **正确** |

→ 固定用 `Arial Unicode MS` 重新生成，并加**全篇字符机检**（不只看头几行）：
实测危险区字符 **0**，5 页 → 走项目解析器得到 `page_ref = p.1…p.5`。

⚠ **一条纪律**：这个字体**必须确认它真实存在**（`/Library/Fonts/Arial Unicode.ttf`）——
否则 Chrome 会**静默 fallback** 回错误的字体，实验结论就不成立。
（同型：D26「转述未经自己验证的故障」——**没验证过的东西不能当前提**。）
