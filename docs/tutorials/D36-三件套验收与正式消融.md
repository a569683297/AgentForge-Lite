## 2. 核心概念讲解

### 2.1 三件套的验收线在要求什么（原文拆解）

**三件套的权威定义**（`docs/PRD-RAGPlus.md:275` 原文）：

> 「产出『**评测报告 + Langfuse 追踪演示 + MCP 工具演示**』三件套，简历可写、面试可讲。」

**验收行**（`docs/PRD-v4.1-含前沿技术.md:1514` 原文）：

> 「D34 \| 面试三件套验收（评测报告/追踪/MCP） \| **全达标**（🆕 S7 由 S10 的真实外部工具满足）」

**拆开看，三件套各自挂在哪条指标上**：

| 件 | 挂的指标 | 验证方式（PRD 原话） |
|---|---|---|
| ① 评测报告 | **S1** 评测集规模 · **S2** 消融提升 · **S3** 准确率 · **S5** 引用覆盖率 | 「评测集入库文件」「评测报告」「LLM-as-judge 自动评分」 |
| ② Langfuse 追踪 | **S6** 100% 对话可追踪 | 「**面板抽查**」 |
| ③ MCP 工具演示 | **S7** · **S10** | 「**演示脚本** + Langfuse 追踪」 |

★ **一句话**：**验收不是"有没有这三样东西"，是"这三样东西各自挂的指标有没有达标"**。
→ 所以逐条对指标是**必做动作**，不能拿"三件套都在"当结论。

### 2.2 S7 与 S10 是同一件事的两面（口径澄清）

`docs/PRD-v4.1:189` 原文：

> 「v3.0 中 S7 的『真实外部工具』由自研的 `inventory_server`（**内存 mock 数据**）承担，
> **严格讲不满足「真实外部」**。v4.0 后 S7 由 **S10 的 Harness 外部 Server** 真实满足，
> 而 `inventory_server` 转为『自研 server（理解协议两端）』的教学与测试用途。
> **两者都需要保留**——自己写 server 证明懂协议，接别人的 server 证明能互操作。」

**读出来的关键**：

- S7 问「**有没有一个真实外部工具能用**」；S10 问「**那个工具是不是来自非自研 Server、且能被发现并调用**」。
- **PRD 自己承认 v3.0 的 S7 是"凑的"** —— 自研 server 的 mock 数据不算"真实外部"。
  这是一处**被文档主动登记的降级**，而不是等别人挑出来。
- **`inventory_server` 不能删** —— 它的价值从"满足 S7"变成了"**证明会写协议两端**"。

★ **面试可讲**：这条口径澄清本身就是个亮点 —— **知道自己的指标当初是怎么被"凑"上的，并且主动改正**。

### 2.3 「全达标」里藏着两个不达标 / 未取证 —— 为什么必须逐条对

验收行写的是「**全达标**」。逐条实测之后，真相是：

| 指标 | 实测 | 与"全达标"的关系 |
|---|---|---|
| S2 消融提升 | **+0.00**（要求 ≥ +10） | ❌ **不达标** —— 登记为「**已知偏差 · 已接受**」 |
| S6 「100%」可追踪 | 通道 + 结构 + 实时写入均已取证 | ⚠ **部分取证** —— Langfuse 不可达时的行为**未验证** |

**为什么必须这么较真**：如果照抄「全达标」三个字，那**不是乐观，是假账**。
本项目的纪律是：**不达标就写不达标，未验证就写未验证**。
→ S2 的归因（**评测集区分度不足 + 检索层天花板**）与证据在
[`../面试三件套验收-2026-10-10.md`](../面试三件套验收-2026-10-10.md) §2.3 / §6.1；
其中一条可量化判据是：**让 gold 文档在融合序里的名次落进 6~20 区间 → 实测当前 0/35**。

### 2.4 正式消融 = `generation_runs=3`：为什么它值得 27 分钟

**背景**：`评测总纲` §3 待办 ③ 挂着「正式消融（`gr=3`）⚠ **未跑**」已经 11 天
（D24 就查出：现有数据是 `gr=1` 的**修复后诊断轮**）。
而 **§10/§11/§13 三节的唯一数据源就是它** —— 所以总纲一直只能停在骨架。

**为什么 `gr=3` 不是"多跑两遍"那么随意**：

- **生成侧抖动的实测值是 10.0%**（`cross_doc` 10 题 × 5 次生成，`D22-生成抖动探针结果`）
  → 折算 50 题 = **5.0 ~ 20.2 条**（点估计 ~ Wilson 上界）；
- 而 PRD S2 要的「+10%」在 50 题上 ≈ **4 条**；
- → **`gr=1` 时，抖动（5.0~20.2 条）比要检出的差异（4 条）还大** → **任何"A 比 B 好 N 条"都不成立**。

**所以 `gr=3` 的实测价值不是"提升"，是"证伪"**：
三配置在 `gr=1` 与 `gr=3` 下**都是 98.00%** → 说明「测不出差异」**不是跑得不够多**，
而是**评测集本身没有分辨力**。**这个否定结论值这 27 分钟。**

**两个旋钮的分工（最常被混）**：

| 旋钮 | 本项目取值 | 对抗哪一层 |
|---|---|---|
| `generation_runs`（**系统**跑几次） | **3** | **生成侧**抖动 |
| `runs_per_case`（**judge** 打几次） | **3** | **裁判侧**抖动 |

### 2.5 一个真 bug 的形状：漏传字段 + 默认值 = 静默

**症状**：`POST /api/chat` 的响应里 `tool_calls` **恒为 `[]`** —— 而同一轮 Langfuse 上有 TOOL span、
PG 的 `messages` 里明明记着工具调用。

**根因**（`app/api/chat.py`）：构造 `ChatResponse(...)` 时**漏传** `tool_calls=result.tool_calls`，
而该字段在 `ChatResult` 里是 `default_factory=list` → **pydantic 静默补 `[]`**
→ **不报错、不崩溃、键还在**，只是**值永远是空的**。

**这类 bug 的形状（记住它）**：

```
「加了字段」+ 「字段有默认值」+ 「有一层忘了搬」 = 静默失效
```

**为什么它特别毒**：

1. **接口形状是对的** —— 键名、类型、文档看起来都没问题；
2. **不报错** —— 没有异常、没有日志、断言也不红；
3. **表现伪装** —— 前端「工具卡片」实时不显示，**但刷新后从 PG 重读又有了**
   → 看起来像**前端 bug**；
4. **污染验收证据** —— 演示脚本第 4 段（S10 的演示路径）**读不到工具调用**。

**它的来源是铁律 10**（「改了返回类型要改所有调用点」）：D22 把字段加进 `ChatResult` 时，
**API 这一层没同步**；而且 `chat.py` 的 docstring 里**本来就没写这个字段** ——
**文档跟着一起漏，所以读代码的人也不会起疑**。

### 2.6 为什么「键集合比对」抓不到这个 bug（哨兵值法）

**直觉的防回归写法**（❌ **无效**）：

```python
assert set(resp.json()) == set(ChatResponse.model_fields)   # 对这个 bug 恒真
```

**为什么无效**：**pydantic / FastAPI 序列化会带上默认值** —— 漏传的字段**在 JSON 里照样出现**，
只是值为默认。所以「键集合」永远是齐的。**它对这个 bug 恒真，永远抓不到。**

**正确做法：哨兵值法（sentinel）**

1. 把 `run_agent` 换成一个**返回"每个字段都带哨兵值"的 `ChatResult`** 的桩；
2. 请求 `/api/chat`，**断言哨兵能原样读回**。

```python
fake = ChatResult(answer="哨兵回答", sources=[SourceItem(index=7, ...)],
                  invalid_citations=[13], tool_calls=["SENTINEL_TOOL"])
monkeypatch.setattr(chat_module, "run_agent", lambda *a, **k: fake)
...
assert body["tool_calls"] == ["SENTINEL_TOOL"]   # ← 漏传哪个字段，哪个就退回默认值
```

**★ 还要加一条「元断言」**（防**将来**）：桩覆盖的字段集合 == `ChatResult.model_fields` 的键集合。
→ 以后**再给 `ChatResult` 加字段**，这条会**主动变红**，逼你回来补哨兵。
这是「**覆盖面型失效 → 修法永远是新增维度**」的直接应用。

### 2.7 假绿的两种形态（本次一次抓到两种）

| # | 形态 | 本次实例 |
|---|---|---|
| ① | **判据只看前置、不看结果** | `demo.sh` 第 4 段只查 `HAS_HARNESS`（**前置有没有装载**），不查本轮 `tool_calls` 是否非空 → **打 ✅ 却显示「（无）」** |
| ② | **断言恒真** | 「响应键集合 == 模型字段集合」（§2.6）—— **看似在验，实际永远过** |

**两者的共同点**：**都在验"东西在不在"，而不是"事情发生没发生"。**
→ 修法都是：**把判据从"存在性"改成"结果性"**。

**本次的修法（分层判据）**：

| 条件 | 退出码 | 输出 |
|---|---|---|
| `tool_calls` 含 `harness*` | 0 | ✅ 强证据 |
| 有工具调用但无 harness | 2 | ⚠ 弱证据（**未触达外部**） |
| 一个工具都没调 / 解析失败 | 3 / 1 | ❌ **无证据** —— **绝不打 ✅** |

### 2.8 语料指纹：一张「没人登记过的账」

**发现过程**：核对三件套时顺手比对指纹，发现旧报告声明的是
`5783a666…`（**8 篇 / 51 片**），而**当前库**是 `d1c88a2f…`（**11 篇 / 82 片**）。

**差额 31 片**正好等于 **D35 补的三份演示素材**（9+9+13）。

**为什么这很严重**：

- `eval_report_service.check_comparable()` 的三条守卫里，**第二条就是「语料指纹逐字相同」**；
- 但它只保证「**三个 run 之间**一致」，**管不到「报告与当前库是否同源」**；
- → 指纹变了而没人登记 = **教材换了一本、考卷没换**：分数差里混进了"教材变了"，
  **归因不成立，而且不会报错**。

**它是怎么漏掉的**：D35 教程、10-09 工作日志、项目记忆里「**指纹**」一词 **零命中**。
→ **改动的那个"面"和记账的那个"面"不是同一个面。**
→ 修法不是"下次记得"，是**让新消融跑在新库上**（→ 报告与库自动同源），
并**在三个地方登记**（`评测总纲` §4.5 · 验收文档 §2.5 · `README.md` 过时点表）。

## 5. 面试考点

1. **「三件套验收，你怎么保证不是走过场？」**
   → 逐条对指标（§2.1），并且**主动写出不达标项**（S2）与未取证项（S6 的不可达行为）。
2. **「你说全达标，但 S2 明明是 +0.00？」**
   → 坦承不达标，给出**归因 + 可量化改进判据**（gold 名次落进 6~20 区间，实测 0/35），
   并强调「**0 差异 ≠ 重排无用**」（三段证据：`Hit@k` 100% / 评测集区分度 / 随机基线负对照）。
3. **「S7 和 S10 有什么区别？」**
   → S7 问「有没有真实外部工具」，S10 问「是不是**非自研** Server 且可被发现并调用」；
   **v3.0 的 S7 是自研 mock 凑的**，v4.0 才由 Harness 真实满足（§2.2）。
4. **「你怎么证明外部工具真被调用了？」**
   → 三处独立证据 + **最强旁证**：对话答出「260 种资源类型 / 42 个工具集」
   —— **该数字不可能来自本地语料**（知识库里没有 Harness 文档），**只能来自外部工具**。
