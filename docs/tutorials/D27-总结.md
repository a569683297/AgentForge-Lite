  上一轮对话里模型"知道有哪些工具"，靠的就是它。
- **替身（stub）** = 一个住在**本进程**里的假函数，它的唯一工作是"把参数转发给子进程里那个真函数，再把结果搬回来"。
  它和真函数的**差别只有一行代码**（调用的是转发，不是真逻辑），但模型完全看不出来。
- **库存 server**（代码 `mcp_servers/inventory_server.py`，来源名 `inventory`）= **D26 里你自己写**的一台 MCP server，
  唯一功能是查库存（工具名 `query_inventory`）。数据写死在进程内、**零外部依赖**（不用网络、不用凭证）→ **常开**。
  它存在的用途是当"**自研 server**"这一侧的活证据：证明昨天那套客户端接入是**通用的**，不是只对 Harness 特调。
- **Harness**（来源名 `harness`）= **外部企业系统**（Harness 平台）**官方提供**的 MCP server，用 `npx -y harness-mcp-v2@latest` 起。
  数据在**网络那头**的企业系统里，要 PAT 才能读 → **默认关**（`MCP_HARNESS_ENABLED=false`），按需开。
- **`source`（来源）** = 今天给注册表**新加的一个字段**，记"这个工具是谁给的"。
  今天接完之后，同一张表里住着**三个来源**：`local`（项目自己写的 2 个）、`inventory`（D26 那台库存 server 的 1 个）、

## §2 名词先注解（全部在此，不外链）

这一节的存在理由同 D26：下面 §3 起会连续用到这些词。**不先定义就用，等于用一堆我不确定你熟不熟的东西解释新东西。**

### 2.1 今天新出现的

| 名词 | 它是什么 | 它解决什么问题 |
|---|---|---|
| **MCP Client（客户端）** | 发起连接、调用工具的那一方（本项目里 = `app/mcp/` 这个模块） | 它不需要知道工具**怎么实现**，只要知道**有哪些工具、参数长什么样**。这正是"工具可以离开主程序"的前提 |
| **注册表 / `ToolRegistry` / `_registry`** | 进程内的一个内存字典 `dict[str, dict]`：键=工具名，值=`{function, description, parameters, source}` | 它是**唯一的工具入口**：模型看到的工具清单、`execute_tool` 能找到谁，都来自它。**它不在数据库里，重启即重建**（这一点在 §5 里是关键） |
| **`source`（来源）** | 今天给注册表加的一个字段："这个工具从哪来"（`local` / `inventory` / `harness`） | 没有它，出故障时只能靠工具名猜是哪台 server（§4.3） |
| **路径 A（静态注册）** | **import 期**由 `@register(...)` 装饰器完成登记；函数体在**本进程** | 项目自己写的工具走这条 |
| **路径 B（动态发现）** | **运行期**由客户端连上 server、问出清单后**现造替身**再登记；函数体在**子进程** | 外部 server 的工具走这条。今天新增的就是它 |
| **动态发现（dynamic discovery）** | "先问 server『你有什么工具』，再按它报的清单登记" | 让"接新 server"变成**改配置**，而不是改代码 |
| **替身 / stub / 代理** | 一个住在本进程、冒充远端工具的 `async def` 函数；它只负责转发与搬运 | 让"函数体在别的进程"这件事对下游**完全不可见**（§4） |
| **`tools/list` / `tools/call`** | 两条 JSON-RPC（一种极简远程调用协议：一个 JSON 对象 = 一次请求或一次响应）方法名：「列工具」与「调工具」 | 前者是**注册期**用的，后者是**调用期**用的 |
| **命名空间 / 前缀（namespace / prefix）** | 登记时给工具名加的一段前缀（如 `inventory_` + `query_inventory`） | 防两台 server 的工具**撞名**。⚠ 它**只动名字一个字段**（§4.3） |
| **`AsyncExitStack`** | 标准库里的一个"攒箱"：把多个 `async with` 逐个塞进去，事后再一起关掉 | 官方 `Client` 是 `async with` 形态（只能活在那个代码块里），而我们要在**任意时刻**才用它 → 必须把"进入/退出"拆开手动控制 |
| **上下文管理器（context manager）** | 带 `__enter__/__exit__`（异步版是 `__aenter__/__aexit__`）的对象，`with` / `async with` 用它管资源的开与关 | 保证"开了就一定关"，哪怕中途抛异常 |
| **协程（coroutine）** | `async def` 函数**调用后**返回的那个对象；要 `await` 它才真的开始跑 | 它和"函数已经执行完"是两回事 —— 忘了 await 会得到一个"什么都没干"的对象（§8 的错误就是它的变体） |
| **事件循环（event loop）** | asyncio 里驱动所有协程的那个调度器。**一个线程一个** | "跨事件循环操作"是本项目反复踩的坑（§10 第 2 条） |
| **anyio** | 一个跨 asyncio / trio 的异步抽象库；MCP 官方 SDK **内部**用它 | 它的并发原语（task group / cancel scope）有"必须从同一个 task 进出"的硬约束 |
| **task / cancel scope** | anyio 的并发单位与"取消范围" | 它们决定了"什么时候能安全地关连接"（§10 第 2 条） |
| **`ExceptionGroup`** | Python 3.11+ 的"一组异常"；anyio 的 task group 会把子异常**打包**成它 | 直接 `str()` 它只会得到 `unhandled errors in a TaskGroup (1 sub-exception)` —— **真因藏在里面**，所以必须"摊平"（§7.2） |
| **`TestClient`** | FastAPI / Starlette 提供的测试客户端：不起真服务器也能发请求，并会**完整跑一遍 lifespan**（启动/关闭钩子） | 用它才能验"应用启动时真的接上了 server"（§7.7 E 段） |
| **超时（timeout）** | "最多等多久，超过就当失败" | 它防的不是"慢"，是**卡死**（§5.3） |
| **快速失败（fail fast）** | 一出错**立刻**报出来，而不是等满超时才报 | 与"静默挂住"相对（§5.2） |
| **卡死（hang）** | 进程**还活着**、但永远不回答 | 比"进程死了"危险得多（§5.3） |
| **白名单（whitelist）** | 明确列出"允许传过去的东西"，清单外的**一律不给** | 今天用它给子进程配环境变量（§7.2、§10 第 1 条） |
| **`npx`** | Node 的命令：**临时下载并运行**一个 npm 包（包会缓存） | Harness 官方 MCP server 就是这么分发的，所以"首次启动慢"（§7.2 的 `spec_timeout`） |
| **npm registry / 镜像** | 下载 npm 包的服务器地址；国内要换镜像，否则直连**超时** | 直连 `registry.npmjs.org` 实测超时（curl 12s 返回 000） |
| **PAT** | Personal Access Token，Harness 的个人访问令牌。**只从 `.env` 读，绝不入库、绝不打印** | 接 Harness server 要它；TRIAL 账号 **2026-10-06 07:59:59 到期** |
| **`serverInfo`** | 握手（正式对话前互相报身份、报能力的那几封开场报文）时 server **自报**的身份（名字 + 版本） | 排障时第一眼要看的东西。今天读到 `harness-mcp-server 3.2.31` |
| **`dataclass`** | Python 标准库的装饰器：自动生成 `__init__` / `__repr__` 这些样板 | `MCPServerSpec` 用它，使"启动说明书"是一份**纯数据**（§7.1） |
| **单例（singleton）** | 全局唯一的那一个实例 | `get_manager()` 返回的就是它 —— lifespan 启停它、接口层查它的状态 |
| **副作用 import** | 只为"执行模块顶层的代码"而 import，不为取名字 | 路径 A 的注册靠它（D26 讲过，今天 `# noqa: F401` 就是给它留的记号） |
| **`inspect.isawaitable`** | 判断一个对象"能不能被 await" | 注册表用它区分"同步函数 / 协程"；写错会导致模型收到 `<coroutine object ...>` 这种垃圾（§8） |

## §3 只有一件事是新的：第二条进注册表的路

### 3.1 路径 A（静态注册）—— 一句话回顾

D10 起就是这个机制，今天没有改动：

```
写工具文件 → @register(name, description, parameters) → 在 app/tools/__init__.py 里 import 一次
        → 装饰器在 import 期执行 → 进 _registry → 函数体就在本进程里，微秒级直调
```

⚠ 最容易漏的一步：**只在 `__init__.py` 里 import 一次**。忘了不会报错，只是"这个工具不存在"。

### 3.2 路径 B（动态发现）—— 今天的全部内容

```
① 起子进程（command + args + 一份白名单 env）
② async with Client(stdio_client(...))  →  握手完成，谈定协议版本
③ await list_tools()                    →  server 报出它的工具清单（名字 / 描述 / schema）
④ for tool in 清单:  造一个替身 _stub   →  ⑤ register(name=前缀+名字, description=原描述, parameters=原 schema,
                                                              source=这台 server 的名字)(_stub)
⑥ 连接**不关**（常驻），留待用户某轮对话真的调工具
```

**只有第 ④⑤ 步是"新"的**。前三步和最后一步都是"照官方 SDK 用"。

### 3.3 ★ 支点是「契约够窄」，不是「函数体在别处」

这是今天**最容易被讲错、也确实差点被讲错**的一句（§9.3 会交代它怎么错、怎么修）。

**错的说法**（原理图 §1 初稿的原句）：

> 路径 B 的全部价值，都建立在"函数体不在我这个进程里"这一件事上。

这句话的毛病：**它把"现象"说成了"理由"。** 函数体在别处，是**结果**（因为它要连的是别人的进程），
不是"为什么能不改代码"的理由。顺着它推，就会推出一句错的结论 ——
"因为函数体都不在 Agent 代码中，所以接新 server 只要接进来就行"（用户 Q1-L2 就是这么答的）。

**对的说法**：支点是**契约够窄**。把三件事摆出来看：

| 问 | 答案 |
|---|---|
| `register` 要求调用方给什么？ | **三样描述信息**（名字 / 描述 / 参数 schema）+ **一个可调用对象**。就这些 |
| 下游（`get_tools_schema` / `execute_tool`）只认哪几个签名？ | 两个：`get_tools_schema()` 与 `execute_tool(name, arguments)` |
| 它**检查了什么**？ | 只查"名字重不重"（重了 `raise ValueError`） |
| ★ 它**没检查什么**？ | **它从不检查这个 callable 是真函数还是代理** —— 不看 `__module__`、不看它跑在哪个进程、不看它是怎么实现的 |

★ **"它没检查什么"才是可扩展性的来源。** 只要新东西能满足那两句话，就能接进来 ——
新增一台 server 要做的，只是在**配置层**多写一份 `MCPServerSpec`（§7.1 的那份"启动说明书"）。

> 判据（可以拿去面试说）：**问"为什么能 X"，理由必须落在「接口的窄度」上，
> 不能落在「现象」上。** 现象读起来像论证，所以最容易骗过"对 / 错"判定。

## §4 一次调用，在客户端这一侧怎么走

### 4.1 完整时间线（11 步，两条进程边界）

```
[本进程 = AgentForge]                                   [子进程 = MCP Server]
 1 execute_node 决定调 "inventory_query_inventory"
 2 execute_tool(name, args)              ← 注册表查表，拿到的是**替身**
 3 替身: asyncio.wait_for( call_tool(remote, args), timeout=call_timeout_s )
 4   ──── 边界 1：把参数包成一条 tools/call（带一个**自己生成的 id**）写进子进程 stdin ────→
                                                        5  读 stdin
                                                        6  按名字查自己的工具表
                                                        7  （路由：一次字典查表）
                                                        8  Pydantic 校验参数
                                                        9  执行真函数
                                                       10  打包结果（带**同一个 id**）
 11  ←──── 边界 2：同一个 id 的响应回到替身，取出 content 文本层 ────
    → 返回**字符串** → 以 tool 消息写回 → 回 plan 节点
```

### 4.2 替身（stub）只做三件事

| # | 做什么 | 关键点 |
|---|---|---|
| ① **冒充** | 用 server 给的**名字 + 描述 + schema** 去登记 | ⚠ 用的是**描述信息**，不是"参数" —— 参数是**调用期**才有的，登记期还没有 |
| ② **打包** | 把参数包成一条 `tools/call` 报文写进子进程 stdin | ⚠ 必须**自己生成一个 id**（后面要靠它对上号） |
| ③ **等回** | 在 stdout 上等**同一个 id** 的响应，取 `content` 文本层 | 认 id，不认顺序 |

### 4.3 命名空间：前缀只动「名字」这一个字段

**实测（D 段 D2）**：远端名 `query_inventory` → 登记名 `inventory_query_inventory`；
**描述与 schema 与远端原文逐字相同**（原样透传）。

★ 顺带钉一个口径（今天必须说清，否则会被读错）：

> **加前缀只动「名字」一个字段。「在描述里补上来源」是另一个独立动作 ——
> 这两件事是两步，不是加前缀的必然结果。**

（这条口径就是 Q3-L2 的答案，上图 §4 里也专门写了。用户当时答成"名字和描述都会改变"。）

**为什么不加前缀很危险** —— 图上给了四层后果，前提是**假设实现改成"后注册覆盖先注册"**：

| 层 | 真正会发生什么 |
|---|---|
| ① **能力静默消失**（最根本） | 键相同 → 整条记录被顶掉 → `get_tools_schema()` 只报存活的那一个 → **模型连它存在都不知道**。第一层后果不是"调了返回错"，而是"这个能力不存在了，而且没人告诉你" |
| ② 调了拿到语义不搭的东西 | 两边名字同、语义不同（A 的 `get` = 查物料 / B 的 `get` = 查资源）→ 拿 A 域的问题调 B 域的工具 |
| ③ **谁活下来由顺序决定**（最毒） | import 顺序 / 启动顺序 / 连接快慢（动态发现还受网络影响）→ 同一份代码换台机器结果不同 → **本地复现不了** |
| ④ 为什么"无法排查" | 日志里只有（相同的）工具名 → 分不清这次调用打到哪台 server |

⚠ **但当前的实现不是"覆盖"，是"抛错"**：`register` 重名直接 `raise ValueError`，且发生在启动时 ——
**这是快速失败，问题会自己喊出来。** 上面四层是**对照用的假设世界**，
差别不在"有没有 bug"，而在「**bug 会不会自己喊出来**」。

### 4.4 `source` 字段：让注册表记住来源

`register()` 今天多了一个参数 `source`（默认 `"local"`，**现有两个工具零改动**）。
它是 `/api/tools` 与排障的依据，也是 `unregister_source()` 的抓手（§7.4）。

**⚠ 这里有个最容易被误读的地方，单独说清：**

`source` 的取值是「**`local` + 每台 server 的名字**」，**不是「本地 / 远端」的二选一**。
`local` 只有**一个**，它是"来源类别"；`inventory` 和 `harness` 是**具体的 server 名**（实例）。
再接一台新 server → 多一个新取值；**它不是把"远端"又切成两半。**

**为什么不能只记"本地 / 远端"**：因为"远端"不是一台。出故障时你要回答的是
**"该重启谁 / 任务是在哪个进程里烧掉的"** —— 写 `remote` 说不清是 inventory 还是 harness。
（这也是为什么 `unregister_source(name)` 的入参是 **server 名**，而不是 `"remote"`。）

**更反直觉的一点**：这两台 server 在**传输层其实是同一类** —— 都是
`StdioServerParameters` + `stdio_client` 起的**本机子进程**（`client.py:117/134`），
一台是 `sys.executable mcp_servers/inventory_server.py`，一台是 `npx -y harness-mcp-v2@latest`。
所以 MCP 语义上那个"本地（stdio）/ 远端（SSE / streamable HTTP）"的二分，**在这个项目里根本切不开它们**。

**真正把它们分开的是"数据从哪来 / 谁维护"：**

| | 库存 `inventory` | Harness `harness` |
|---|---|---|
| 谁写的 | **你**（D26 产物） | **外部厂商** |
| 数据在哪 | 写死在 server **进程内** | **网络那头的企业系统** |
| 要网络吗 | 不要 | 要 |
| 要凭证吗 | 不要 | 要 **PAT**（`HARNESS_API_KEY`） |
| 默认 | **常开** | **默认关**（`MCP_HARNESS_ENABLED=false`） |
| 代表 | "我自研的 server 也能被同一套客户端接入" | "真实的第三方企业系统" |

→ 所以"本地 2 + 库存 1 + Harness 11"里的**"库存 1"和"Harness 11"是并列的两台 server**，
**不是两个分类层级**；真正的层级只有一层：`local`（进程内真函数）vs **各台 server**（函数体在别的进程里）。

## §5 ★ 取证一：两种「挂了」，形状完全不同

> 出处：图上 §4「补一条机制」那一块。原话是：
> **"以上全部是源码推演，尚未实测。今天编码时会用真实场景验一次（杀掉子进程再调），验完才升格为结论。"**
> 今天把它兑现了 —— 这就是验证脚本的 **G 段**。

### 5.1 为什么要分两种

「server 挂了」不是一件事，是**形状完全不同的两件事**：

| 怎么挂的 | 调用时会发生什么 | 谁接住 |
|---|---|---|
| ① **进程没了**（崩溃 / 被 kill） | 往已死的子进程 stdin 写 → **写失败**（管道已断） | `execute_tool` 的 `except` → 变成一段错误**字符串** |
| ② **进程还活着但卡住** | 写入**成功**，但**等不到响应** → **超时才是命门** | 只有超时机制能接住；不写超时 → **整轮对话被挂住** |

### 5.2 G-① 进程被 SIGKILL

**怎么拿到"内核给的 pid"**（不是让 server 自报，D26 讲过的手法）：
让 shell 先写 `$$` 再 `exec` 顶替 —— `exec` 之后 shell 的进程号就是 server 的进程号。
本次拿到 `pid=25791`（G3 通过）。

| 断言 | 实测 |
|---|---|
| G1 用 `sh + exec` 包装的 server 也能正常接入 | ✅ |
| G2 杀之前调用正常 | ✅ 返回 1641 字符 |
| G3 从内核拿到了真 pid | ✅ `pid=25791` |
| **G4 ★** 杀掉后再调用 → **返回错误文本**（不抛异常、不挂死） | ✅ **0ms**，返回 `工具 query_inventory 执行失败：MCP server「killme」调用异常 MCPError: Connection closed` |
| **G5 ★** 而且它是**快速失败** | ✅ 0ms（超时阈值 5000ms） |

### 5.3 G-② 进程活着但卡住

做法：写一个 `/tmp/d27_probe/hanging_server.py`，它有一个 `freeze` 工具**故意阻塞**。
把 `call_timeout_s` 设成 2 秒（故意设小，别让验证脚本自己等 30 秒）。

| 断言 | 实测 |
|---|---|
| G6 卡死的 server 仍能被正常接入（握手与 `tools/list` 是好的） | ✅ |
| **G7 ★** 调用卡住的 server → **在超时内返回错误文本** | ✅ **2.00s**，返回 `工具 freeze 执行失败：MCP server「hangme」响应超时（超过 2s），该 server 可能已卡死` |
| **G8 ★** 超时 ≈ **配置值**（不是别的东西在起作用） | ✅ 实测 2.00s / 配置 2.0s |
| **G9 ★** 断开一台卡死的 server 能在限时内完成（关闭流程不被拖住） | ✅ 2.02s / 限时 8.0s |

⚠ **G9 这一条是今天现场才想到的场景**：卡死的子进程正阻塞在 `time.sleep` 里，
**它不读 stdin，也就不会因为 EOF 而退出** → 一台卡住的 server **能拖住整个关闭流程**。
这是生产里真实存在的场景（"应用关不掉了"），今天顺带把它钉住了。

### 5.4 结论与边界（不许省）

1. **两种"挂了"都能被收敛成字符串喂回模型**，不会把整轮对话弄崩 —— **前提是有超时**。
2. **超时的那一支才是真正的命门**：`wait_for` 会 cancel 掉内部那个 task，
   所以"超时之后这条连接还能不能继续用"**不能想当然**。今天的做法：
   **实测后再调一次并只作记录、不断言好坏**（G 段里那行 `↳`），
   并在 `app/mcp/client.py` 的注释里写明"这一点由 G 段实测，不靠推理"。
3. **边界**：本次只覆盖"工具执行路径"的失败（写管道失败 / 不响应），
   **协议层错误（JSON-RPC 的 `error` 对象）这一支没单独测**。结论不许外推到它。
4. ★ 这条与 D24 那条「**覆盖面型静默失效**」同源：
   注册表声称的能力 ≠ 真实能调通的能力。所以**修法是"新增一个维度"**（来源标注 + 主动摘除），
   不是把原有断言收紧。

## §6 ★ 取证二：协议版本是**双向**的（修正原理图 §5①）

### 6.1 图上原本写的是

> ① 本项目落在哪一代协议 —— 走高层 `Client`，它默认 `mode="auto"`：先探 `server/discover`，
> 成功就不再发 `initialize` → **谈定 Modern（`2026-07-28`）**。

这句话**方向是对的**（D26 已经用抓包证过：`auto` 不发握手），但它把结论写成了一个**单值**：
好像"本项目 = 2026-07-28"。

### 6.2 实测：同一个 `auto` 模式，两台 server 谈出两个版本

今天接了两台 server，日志里是这样的（`--with-harness` 那次运行的原文）：

```
MCP 已连接 server=inventory 自报=inventory           版本=       协议=2026-07-28
MCP 已连接 server=harness   自报=harness-mcp-server  版本=3.2.31 协议=2025-11-25
```

| server | 自报身份 | 谈定协议 |
|---|---|---|
| `inventory`（D26 自研，走本机 python） | `inventory` | **`2026-07-28`**（Modern） |
| `harness`（官方 npm 包 `harness-mcp-v2@3.2.31`） | `harness-mcp-server` `3.2.31` | **`2025-11-25`**（Legacy 代） |

**客户端那一侧完全没有区别** —— 同一份 `MCPClient`、同一个 `mode="auto"`。

### 6.3 所以正确的说法是什么

> **谈定哪一代，是双方各自支持范围的交集** ——
> **不只看"用哪一层客户端"（D26 的结论），也看"对方 server 最高支持到哪一代"（今天的新事实）。**

D26 那句话（「默认走哪一代，取决于用哪一层客户端」）**依然成立，但它是必要条件、不是充分条件**。
今天补上的这一半是：**同一层客户端，换个 server 也会落在不同代上。**

### 6.4 这条为什么值钱

因为它是一个**"看起来已经很严谨的结论"又被收窄了一次**：
D26 已经从"默认走握手代"（无主语）修到"取决于用哪一层客户端"（带主语），
今天发现**主语还不够全** —— 还要带上"对方是谁"。

⚠ 还有一个**副产物**：`harness` 落在 `2025-11-25`，意味着**它的握手/报文形状与自研 server 不同**。
今天没有对 harness 做抓包，所以**"它到底发不发 `initialize`"这件事今天没测**（不许写成结论）。

## §7 代码逐行解读

> 这一节的密度标准 = 铁律 2 第 3 条的「边写边讲」。
> 组织方式：新增文件逐个讲（在干嘛 / 为什么这么写 / 哪里最容易错）。

### 7.1 `app/mcp/client.py`（311 行，D27 核心）

**它是什么**：一台 server 的连接。负责：起进程 → 发现工具 → 造替身 → 登记 → 回收。

#### `MCPServerSpec`（一份"启动说明书"）

```python
@dataclass
class MCPServerSpec:
    name: str                                  # 这台 server 的名字，也是 source 字段的值
    command: str                               # 可执行文件（python / npx）
    args: list[str] = field(default_factory=list)
    env: dict[str, str] = field(default_factory=dict)   # ⚠ 必须显式白名单
    namespace: str = ""                        # 登记时加的前缀；空串 = 不加
    cwd: str | None = None
    call_timeout_s: float = 30.0               # 单次调用的超时
```

**为什么单独抽成一份数据**：让"连什么"与"怎么连"分开 ——
以后加一台 server 只需要多写一份 spec，`MCPClient` 一个字都不用动。
**这正是「接新 server 不改 Agent 代码」在配置层的形态**（§3.3）。

三个字段的注释里各藏了一个坑，都不是凑数的：

| 字段 | 注释原文（要点） |
|---|---|
| `env` | "⚠ env 必须是**显式白名单**，不能 `{**os.environ}` 全透传：实测踩过 —— 本机 `.env` 里的 `LOG_LEVEL=INFO`（大写）透传进去后，harness server 启动瞬间 Fatal error 自杀（它只认小写枚举）。**一个"看起来无关"的宿主环境变量，足以让子进程起不来。**" |
| `call_timeout_s` | "⚠ 它防的不是'慢'，是 **server 卡死**：子进程没了会立刻写失败（能捕获），子进程还活着但不应答则会**永远挂着** —— 而这是 `execute_tool` → `execute_node` 里的一个 await，挂住一次就是挂住**整轮对话**（比报错严重得多）。" |
| `namespace` | "inventory：远端叫 `query_inventory` → 加前缀 → `inventory_query_inventory`；harness：远端**自带** `harness_` 前缀 → 传空串，避免 `harness_harness_list`" |

#### `MCPClient.__init__` / `connect` / `_capture_handshake`

```python
self._stack: AsyncExitStack | None = None   # 让 async with 的上下文**跨请求常驻**
```

**为什么用 `AsyncExitStack` 而不直接 `async with`**：官方 `Client` 是 async context manager，
直接 `async with` 只能活在 with 块里；而我们要在**任意时刻**（用户某轮对话决定调工具时）才用它。
→ 必须把"进入 / 退出"拆开手动控制。

```python
params = StdioServerParameters(
    command=self.spec.command,
    args=list(self.spec.args),
    env=dict(self.spec.env),   # ← 白名单，不继承宿主环境
    cwd=self.spec.cwd,
)
```

**子进程 stderr 落盘**：`tempfile.mkstemp(...)` 建一个临时文件给它。
理由（注释原文）："子进程 stderr 跟协议流是两根不同的管子，里面放的是**给人看的**日志。
出问题时这是唯一有原文的地方。" 路径记在 `self.stderr_path`，会出现在 `/api/tools` 的 `servers` 块里。

```python
self._client = await asyncio.wait_for(
    self._stack.enter_async_context(Client(stdio_client(params, errlog=self._errlog_file))),
    timeout=timeout_s,
)
except Exception:
    await self._force_cleanup()   # 起不来就把已开的东西收干净（子进程 + 文件句柄）
    raise
```

`_capture_handshake()` 做的事：把握手结果（`server_info` / `protocol_version`）记下来。
**"尽力而为，取不到不算失败"** —— 它是排障情报，不是功能依赖。
今天 §6 那个"两台 server 谈出两个版本"的事实，就是从这个函数记下来的值里读到的。

#### `discover_and_register` —— 路径 B 的全部心脏（14 行）

```python
listed = await self._client.list_tools()
names: list[str] = []
for tool in listed.tools:
    remote = tool.name                       # ← 名字来自 server，不是我写的
    full = self._qualify(remote)
    register(
        name=full,
        description=tool.description or "",
        parameters=tool.input_schema or {"type": "object", "properties": {}, "required": []},
        source=self.spec.name,               # ← 记出处
    )(self._make_stub(remote, full))
    names.append(full)
```

三个值得停一下的地方：

1. **`register(...)(...)` 这个双括号**：`register(name=..., ...)` 先返回内层函数 `decorator`，
   Python 再把 `_make_stub(...)` 的结果传进去。这和 `@register(...)` 装饰器写法**完全等价**
   （装饰器只是语法糖）。因为工具名是运行期才知道的，所以不能用 `@` 写法。
2. **`tool.input_schema or {...}`**：schema 缺省时给一个"空对象 schema"，
   与 registry 内部的默认值保持一致 —— 不然下游要处理 `None`。
3. **`description or ""`**：同理，不让 `None` 漏下去（B5 断言钉的就是"每个工具都带描述"）。

#### `_make_stub` —— 替身工厂

```python
async def _stub(**kwargs: Any) -> str:
    return await self.call(remote, kwargs)

_stub.__name__ = full
_stub.__qualname__ = f"MCPClient[{self.spec.name}].{full}"
_stub.__doc__ = f"MCP stub → {self.spec.name}.{remote}"
```

⚠ **必须是 `async def`**（注释里专门写了）：`execute_tool` 里有一句 `inspect.isawaitable(result)`，
**同步函数会被原样 `str()` 掉** → 模型收到的是 `"<coroutine object ...>"` 这种垃圾，
而 **Python 只发个 RuntimeWarning、不报错**。D10 踩过这个坑，这里不能再犯。

后三行改的 `__name__` / `__qualname__` / `__doc__` 只影响**排障可读性**
（`_registry` 用的键是完整的 `full`），但出事时这几行能省很多时间。

#### `call` —— **永远返回字符串**

```python
try:
    result = await asyncio.wait_for(
        self._client.call_tool(remote, arguments),
        timeout=self.spec.call_timeout_s,
    )
except (TimeoutError, asyncio.TimeoutError):
    return f"工具 {remote} 执行失败：MCP server「{self.spec.name}」响应超时（超过 {...:.0f}s），该 server 可能已卡死"
except Exception as e:
    return f"工具 {remote} 执行失败：MCP server「{self.spec.name}」调用异常 {type(e).__name__}: {e}"
return self._render(remote, result)
```

**为什么错误也变成文本而不抛异常**（注释原文）：
"调用方是 `execute_tool` → `execute_node` → 写回 tool 消息给 LLM。抛出去会被 `run_agent`
的通用 except 变成 500，用户这一轮直接白跑；变成文本则**模型看得见**，能自己改口。"

**两个 `except` 的顺序是有意的**：先抓超时（最严重、且 `TimeoutError` 在 3.11+ 就是 `asyncio.TimeoutError`），
再抓宽泛的。写反了超时会被当成普通异常，错误文本就丢了"可能已卡死"这句最有用的话。

#### `_render` —— 取哪一层

```python
blocks = getattr(result, "content", None) or []
texts = [b.text for b in blocks if getattr(b, "text", None)]
```

**为什么取 `content` 而不是 `structuredContent`**（注释原文）：
"server 返回 12 条物料时，`content` 是**每条一个 block**（12 个），那正是 LLM 习惯的'碎片'粒度；
`structuredContent` 是给程序用的。两者是同一批数据的两个视角，**喂模型的走 content**。"

`is_error=True` 也**照样返回文本**（前面加一句 `工具 X 返回错误：`），不在这里再抛一遍 ——
契约是"到了调用方手上一定是字符串"。

### 7.2 `app/mcp/manager.py`（214 行）

**它管什么**：`MCPClient` 管**一台**，`MCPManager` 管**一批** + 生死。三件职责，每件对应一个真实的坑：

| 职责 | 对应的坑 |
|---|---|
| 批量启动、**单个失败不拖垮全局** | 外部 server 我们控制不了（要网络 / npm / PAT）。它起不来，我们的 API 也必须能起来 → 失败记 `status=failed` + 原因，继续下一个 |
| 断开时**把工具一起摘掉** | `unregister_source` 存在的理由（§5.4 那条"调用不通的工具"） |
| 提供**可观测状态** | `/api/tools` 要能回答"这台 server 现在什么情况" |

**给子进程的环境**：

```python
_BASE_ENV_KEYS = ("PATH", "HOME", "TMPDIR")

def _base_env() -> dict[str, str]:
    return {k: os.environ[k] for k in _BASE_ENV_KEYS if k in os.environ}
```

⚠ 注释原文："绝不用 `{**os.environ}`：宿主环境里任何一个同名变量都可能让子进程读错配置
（实测：`.env` 的 `LOG_LEVEL=INFO` 让 harness 启动即 Fatal error）。"
`if k in os.environ` 这一句也别省：**缺了就不放**，避免塞空串覆盖对方的默认值。

**`add_server` 里那个必须吞掉的异常**：

```python
except Exception as e:
    detail = _explain_connect_failure(spec, e)   # ← 摊平异常组
    self._status[spec.name] = {... "error": detail ...}
    logger.warning("MCP server「%s」接入失败：%s", spec.name, detail)
    await client.close()
    return self._status[spec.name]
```

"**必须**吞掉异常，只记状态" —— 同 lifespan 里 Redis 自检"只告警不崩溃"的口径。
但**不能静默**：状态里留 `reason`，`/api/tools` 一眼看到是哪台、为什么没上来。

**`_explain_connect_failure` —— 把异常组摊平**：

```python
leaf = exc
while getattr(leaf, "exceptions", None):     # ExceptionGroup / BaseExceptionGroup
    leaf = leaf.exceptions[0]
return f"{type(leaf).__name__}: {leaf}"
```

为什么不摊平不行（注释原文）："anyio 的 TaskGroup 会把子异常包成 `ExceptionGroup`，
直接 `str()` 只会得到 `unhandled errors in a TaskGroup (1 sub-exception)` ——
真正的原因藏在里面，排障时**等于没有信息**。"

**`spec_timeout` —— 为什么不同 server 给不同超时**：

```python
return 240.0 if spec.command.endswith("npx") else 20.0
```

理由（注释原文）："`npx` 这类命令**可能现下载依赖**（实测：直连 npm 官方源会挂住 5 分钟以上，
加国内镜像后 2 分 31 秒），而下文自研 server 是本机 python 起进程、毫秒级。
用同一个超时值必然二选一：要么拖死本机 server 的启动，要么杀了 npx。"

**`remove_server` —— 断连与摘除是一件事**：

```python
client = self._clients.pop(name, None)
removed = unregister_source(name)      # ← 摘除**不依赖** client 是否存在
if client is not None:
    await client.close()
self._status.pop(name, None)
```

顺序有意：先摘工具（内存操作、必然成功），再关连接（可能慢/可能卡 —— 见 §5.3 的 G9）。

**`build_specs` —— 两台 server，各代表一类真实形态**：

| server | command | env | namespace | 代表 |
|---|---|---|---|---|
| `inventory` | `sys.executable`（**与主进程同一解释器** → 一定 import 得到 `mcp`） | `_base_env()` + `LOG_LEVEL=info` | `inventory` | 本机自研、零外部依赖 → **永远该在** |
| `harness` | `npx` | `_base_env()` + 5 个**显式**键（`HARNESS_API_KEY` / `HARNESS_READ_ONLY` / `HARNESS_AUTO_APPROVE_RISK` / `npm_config_registry` / `LOG_LEVEL`） | `""`（**自带前缀，不再叠加**） | 真实外部企业系统 → **默认关，按需开** |

⚠ `harness` 分支先判断 `if not settings.harness_api_key: logger.warning(...)`：
"没有凭证就别起了 —— 起了也会在第一次调用时 401，不如在这里明确说清'为什么没接上'。"

## §8 错误语义：为什么 MCP 的错误也必须变成字符串

D10 定下的注册表契约是：**`execute_tool` 永远返回字符串**。今天客户端层完整继承了它，
并在三个不同的失败点上把它落实：

| 失败点 | 返回的文本 |
|---|---|
| server 未连接 | `工具 X 执行失败：MCP server「Y」当前未连接` |
| 进程已死（写管道失败） | `工具 X 执行失败：MCP server「Y」调用异常 MCPError: Connection closed` |
| 卡死（超时） | `工具 X 执行失败：MCP server「Y」响应超时（超过 Ns），该 server 可能已卡死` |
| 远端业务失败（`is_error`） | `工具 X 返回错误：<server 给的原文>` |
| 参数类型错（Pydantic 拦下） | `工具 X 返回错误：Error executing tool ... 1 validation error`（**实测 C3**） |

**两条理由**（都不是"风格问题"）：

1. **抛异常 → 用户这一轮白跑**：异常会被 `run_agent` 的通用 `except` 变成 500。
2. **文本 → 模型能自己改口**：模型看得见"这个工具暂时不可用"，可以换说法、换工具，把这一轮救回来。

★ 判据（可以拿去面试说）：**"让模型看见失败"比"让程序优雅失败"更值钱** ——
因为这一层的消费者是**模型**，不是程序员。

## §10 踩坑记录

### ① `start()` 返回 dict，被当成 list 迭代（**今天唯一一个"崩掉进程"的 bug**）

```python
ok = [s["name"] for s in status if s["connected"]]        # ❌ TypeError: string indices must be integers
ok = [name for name, s in status.items() if s["connected"]]  # ✅
```

`start()` 返回 `dict[str, dict]`，直接迭代 dict 拿到的是**键**（字符串）。
危害：**lifespan 崩掉 → `TestClient` 起不来**，而且被 anyio 的次生错误
（`Attempted to exit cancel scope in a different task`）**掩盖了一层** ——
是 `d27_verify` 的 E 段把它抓出来的。已把这段教训写进 `main.py` 的注释里。

### ② 验证脚本挂死 12 分钟（**本项目已知坑的第 2 次命中**）

跑到 E 段时死住，**无任何报错、无任何输出**。
真因：`TestClient` 会**另起线程 + 另起事件循环**，在它那个 loop 里 `aclose()`
一个在**主 loop** 上创建的 `AsyncExitStack` → **永久挂起**。
修法：E 段之前先 `await get_manager().stop()`（在**主循环里**关掉前面几段建的连接）。
→ 与 D12 / D21 记过的"跨事件循环操作要在自己的 loop 里做"是**同一条**。

### ③ C3 断言假阴性：`anyOf` 之下的"什么都没测到"

`min_stock: int | None` 生成的 schema **不是** `{"type": "integer"}`，而是
`{"anyOf": [{"type": "integer"}, {"type": "null"}]}`。
只查 `spec.get("type") == "integer"` → **一条都找不到** → 走近 `if int_param is None` 那一支 →
报 `[FAIL] schema 里找不到 integer 参数，跳过`。

⚠ 它**不报错、不崩溃**，只是"过滤条件永远匹配 0 条" —— **安静地什么都没测到**。
修法：加 `_schema_has_type()` 兼容 `anyOf`。
→ 这是 D26「**位置 ≠ 语义**」的升级版：当时栽在"按下标认参数"，这次栽在"按 `type` 字段认参数"。

### ④ `| tail -80` 的管道缓冲：12 分钟看不到任何进度

后台跑 `uv run python -m scripts.d27_verify 2>&1 | tail -80`，输出全被**块缓冲**在管道里。
**排查成本比故障本身还高。**
修法：输出重定向到文件 + `sys.stdout.reconfigure(line_buffering=True)`。

### ⑤ Harness 启动即 Fatal error —— **不是 PAT 失效**

第一版 PAT 验证脚本写 `env={**os.environ, ...}` 全透传宿主环境，harness 启动瞬间自杀：

```
Fatal error: Error: Invalid configuration: LOG_LEVEL: Invalid option: expected one of "debug"|"info"|"warn"|"error"
```

真因：本机 `.env` 的 `LOG_LEVEL=INFO`（**大写**）撞上 harness 只认的**小写**枚举。
→ 改成显式白名单后 **1.70s 连上**。
★ **一个"看起来无关"的宿主环境变量，足以让子进程起不来。**
这条已经固化进 `MCPServerSpec.env` 的注释、`manager.py`、`.env.example` 三处。

### ⑥ `uv` 不在非交互 shell 的 PATH 里

定位：`uv` 实际在 `~/.local/bin/uv`。
→ 规矩：脚本里用**绝对路径** `~/.local/bin/uv`；**"同一命令两次结果不同"先怀疑 shell 环境（PATH）**，
不是命令本身坏了（同 D26「命令错冒充依赖坏」那条）。

### A.1 第一组（原理环节）

**Q1**
- **L1**：路径 A 的注册发生在 **import 期**（模块被导入的那一刻），函数体在**本进程**；
  路径 B 的注册发生在**运行期**（我主动 `connect()` 之后），**注册动作仍然发生在我的进程**里，函数体在**子进程**。
  拆三层：**内容谁提供 = 子进程；注册动作谁执行 = 我；注册进哪张表 = 我进程里的 `_registry`**。
- **L2**：支点是**契约够窄** —— `register` 只要求"三样描述信息 + 一个可调用对象"；
  下游只认 `get_tools_schema()` / `execute_tool(name, args)` 两个签名；**它从不检查这个 callable 是真函数还是代理**。
  所以新增 server 只需在**配置层**多写一份 `MCPServerSpec`。**"函数体在别处"是结果，不是理由。**
- **L3**：`_registry` 是进程内的内存字典，**没有回收逻辑** → 键值对**原样留着** → 必须**主动摘**（`unregister_source`）。
  而且"挂了"有两种形态：① 进程没了 → 写管道失败 → **0ms 快速失败**；
  ② 进程活着但卡住 → 写入成功、等不到响应 → **超时才是命门**（不加超时会挂死整轮对话）。

**Q2**
- **L1**：① **冒充**（用 server 给的**名字 / 描述 / schema 三样描述信息**登记）
  ② **打包**（**自己生成一个 id**，把参数包成一条 `tools/call` 写进子进程 stdin）
  ③ **等回**（在 stdout 上等**同一个 id** 的响应，取 `content` 文本层）。
- **L2**：Python 的**函数对象不跨进程** —— 函数对象 = 代码 + 内存状态，只存在于那个进程的地址空间；
  两个进程之间只有 stdin/stdout **传字节**。**不是 Python 不行，任何语言都不行。**
  → 所以只能"在本地放一个只会转发的替身"。
- **L3**：**返回字符串**。契约是"到了调用方手上一定是字符串"（D10）；
  抛出去会被 `run_agent` 的通用 `except` 变成 500、用户这轮白跑；变成文本则**模型看得见**，能自己改口。

**Q3**
- **L1**：`register` 重名**直接 `raise ValueError`**，且发生在**启动时** → 这是**快速失败**，问题会自己喊出来。
- **L2**：**只动「名字」一个字段**。`description` 与 `parameters` 是 server 给的原文、**原样透传**。

- **L3**：四层 —— ① **能力静默消失**（整条记录被顶掉；**这是第一层**）

### A.2 第二组（编码环节）

**Q1**
- **L1**：① 进程没了 → `工具 X 执行失败：MCP server「Y」调用异常 MCPError: Connection closed`，实测 **0ms**；
  ② 进程卡住 → `工具 X 执行失败：MCP server「Y」响应超时（超过 2s），该 server 可能已卡死`，实测 **2.00s**（≈配置值）。
- **L2**：卡住时**写入是成功的**，所以没有异常可抓 —— 它会**永远等下去**。
  而这条路是 `execute_tool` → `execute_node` 里的一个 `await`，**挂住一次 = 挂住整轮对话**（用户只看到转圈），
  比"报个错"严重得多。不写超时不会崩、不会报错，**只会静默挂死**。
- **L3**：0.1s 会让**正常但稍慢**的调用也被判超时（Harness 首次调用要拉包、网络往返都 > 0.1s）→ 误报；
  而且 `wait_for` 会 cancel 内部 task，频繁取消可能把 SDK 的请求 / 响应配对搞乱。
  **不是越小越好** —— 要按"这台 server 最慢的正常响应"来定（本机 python 20s / `npx` 240s，见 `spec_timeout`）。

**Q2**
- **L1**：`tools` 说"**现在有哪些工具**"，`servers` 说"**这些工具的主人现在什么情况**"。
  分开是因为两者**可以不一致** —— server 断了但工具还在注册表里 = 会调不通，**这种不一致本身就是要看见的信息**。
- **L2**：因为 `function` 对象**不可 JSON 序列化**。混进去这个函数就只能在 Python 里用、接口层没法直接调。
  （另一个分工：`get_tools_schema()` 是发给 LLM 的，格式必须严格是 OpenAI function calling 的形状，不能多加字段。）
- **L3**：因为 `"local"` 是**进程内的真函数**（`current_time` / `search_documents`），
  它们**与任何外部 server 的生死无关**。摘掉它们 = 把自己项目的能力删了，而且**不会报错**
  （F2 断言钉的就是"`local` 前后一致"）。

**Q3**
- **L1**：**显式白名单** —— 只从宿主环境里挑 `("PATH", "HOME", "TMPDIR")` 三个（缺了就不放）；
  harness 那台再**显式**加 5 个它自己要的键。
- **L2**：因为宿主环境里任何一个同名变量都可能让子进程读错配置。
  **实测例子**：本机 `.env` 的 `LOG_LEVEL=INFO`（大写）透传进去后，harness 启动瞬间
  `Fatal error: Invalid configuration: LOG_LEVEL: Invalid option: expected one of "debug"|"info"|"warn"|"error"` 自杀。
- **L3**：会变成 `harness_harness_list`（前缀叠加）—— 因为 **harness 的工具名自带 `harness_` 前缀**，
  远端就叫 `harness_list`。所以配置成 `""`，**避免叠加**。
