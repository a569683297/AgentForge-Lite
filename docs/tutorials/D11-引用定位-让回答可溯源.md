**PRD 验收标准**：答案含 `[1]` 引用**且可定位原文**。

D10 完成了前半句——`[1]` 确实出现在回答里了。

- D10：**看起来像引用**（角标有了，但指不到任何地方）

## 2. 核心概念讲解

### 2.1 可溯源需要两条通道，缺一条都不成立

这是 D11 最重要的认知。很多人只想到其中一条。

| 通道 | 做什么 | 缺了会怎样 |
|---|---|---|
| **A. prompt 通道** | 改 `answer_node` 的 system，要求 LLM 标注 `[1] [2]` | 回答里根本没有编号，sources 收了一堆也没人引用 |
| **B. 数据通道** | 收集结构化片段，随 `run_agent` 一起返回 | 用户看到 `[1]` 却点不开，纯装饰 |

**两条通道的交汇点，只有那个编号。**

```
            ┌─ A 文本通道 ─→ LLM ─→ 回答「…报销需 5 个工作日 [1]」
检索结果 ───┤                                        ↕ 靠 [1] 对齐
            └─ B 结构通道 ─→ sources 表 ─→ 前端把 [1] 渲染成可点击来源
```

D10 已经铺好了地基（编号进了 LLM 上下文），D11 把两条通道都接通。

### 2.2 prompt 通道：给了材料 ≠ 会标注

D10 结束时有个现象让人以为"引用还没做"：回答里没有 `[1]`。

但真相是——**`[1]` 早就在 LLM 的上下文里了**。工具返回的文本长这样，它作为 `role: "tool"` 消息进入上下文：

```
[1] 来源：finance_policy.md（相关度 0.78）
员工出差产生的交通费、住宿费需在行程结束后十个工作日内提交报销单……
```

**LLM 看得到 `[1]`，但没被要求写出来。** 看 D10 版本的 `answer_node` prompt：

```python
system = (
    "你是 AI 助手。如果上面有工具执行结果，请基于结果回答用户；"
    "否则直接回答。不要提及内部工具调用细节。"
)
```

两个问题：

1. 没有任何一句要求标注来源。LLM 的默认倾向是"综合材料，用自己的话答"
2. 最后那句"不要提及内部工具调用细节"很可能在**主动抑制**它——模型完全有理由把 `[1]` 理解成"内部细节"而回避

**结论：上下文里有 ≠ 输出里有。中间隔着一道指令。**

D11 的新 prompt 把两件事拆开说：

```python
system = (
    "你是 AI 助手。\n"
    "如果上面有工具执行结果，请严格基于结果回答用户，"
    "并在每条来自资料的论断后标注来源编号，格式为 [1]、[2]（对应工具结果里的 [n]）。\n"
    "只允许使用工具结果中确实存在的编号，不要编造编号；"
    "也不要写出工具结果里没有的内容。\n"
    "如果工具结果不足以回答，就直接说明资料中没有相关信息，不要自行推测。\n"
    "不要提及工具调用的技术细节（函数名、参数、数据库等）。\n"
    "如果上面没有工具执行结果，直接回答用户。"
)
```

逐句的作用：

| 句子 | 作用 |
|---|---|
| 「严格基于结果回答」 | 把模型约束在给定材料内 |
| 「标注来源编号 [1][2]」 | 通道 A 本体 |
| 「只允许使用确实存在的编号，不要编造」 | 提前压住幻觉引用（对应 2.4 的校验） |
| 「不足以回答就直说没有」 | 允许它说"不知道"，而不是硬编 |
| 「不要提技术细节（函数名、参数、数据库）」 | 保留原意图，但**与标编号区分开** |
| 「没有工具结果就直接回答」 | 闲聊路径不受影响 |

### 2.3 数据通道：为什么不能用正则从文本里反解

结构化数据要跟着回答一起返回，但**工具契约规定只能返回 `str`**。三条路：

| 方案 | 做法 | 判定 |
|---|---|---|
| A. 正则反解 tool 消息 | Agent 跑完后，用正则从 `messages` 里抠 `[1] 来源：xxx` | ❌ 格式耦合（文案改一个字就崩）、换行边界难判、**本质是把刚序列化的东西再反序列化回来** |
| B. 工具返回 dict | 让 `search_documents` 返回结构化对象 | ❌ 破坏 D10 契约。LLM 读不了 Python 字面量，还要改注册表和所有工具 |
| **C. 请求级收集器** | 工具仍返回 `str`，但**额外**把格式化之前的原始结构登记到请求级上下文 | ✅ 契约不变、零文本解析 |

选 C。代价是引入**隐式状态**——工具函数不再是纯函数，多了个看不见的副作用。这个代价用一个命名清晰的文件（`app/core/citation.py`）来钉住。

**关键细节：收集器存的是"格式化之前"的原始数据。**

```
路 1（给 LLM）："[1] 来源：finance_policy.md（相关度 0.78）\n员工出差…"  ← 拼好的文本
路 2（给前端）：{source: "finance_policy.md", similarity: 0.78, content: "员工出差…"}
                 ↑ 前端要的是这三个字段，不是"来源："这个前缀
```

如果路 2 也存拼接文本，前端就得再解析一遍字符串——绕回方案 A 那条脆弱的老路。

### 2.4 越界校验：要求引用会带来新风险

一旦要求 LLM 标编号，它会**为了"显得有依据"而乱标**——写出 `sources` 里根本不存在的 `[5]`。

所以 D11 必须有校验：

```python
_CITATION_RE = re.compile(r"\[(\d+)\]")   # 只匹配纯数字方括号，不误伤 [文字](url)

def check_citations(answer: str, total: int) -> list[int]:
    used = {int(n) for n in _CITATION_RE.findall(answer)}
    return sorted(n for n in used if n < 1 or n > total)
```

**只检测、不改写。** 改写回答会引入新的不确定性（改错了更难查），先记录 + 日志告警，等 D17 评测体系量化之后再定策略。

### 2.5 contextvar：请求级隔离，以及一条必须记住的铁律

收集器需要"每个请求一份、互不污染"。Python 标准库 `contextvars.ContextVar` 正是干这个的，等价于 Node.js 的 `AsyncLocalStorage`。

直觉上会这么写：

```python
_sources = contextvars.ContextVar("sources", default=[])
```

**实测证明这是错的。** 原因是 ContextVar 的一条核心语义：

> **ContextVar 复制的是「绑定」，不是「对象内容」。**

- `asyncio.create_task` / `gather` 会给子任务**复制一份 context**
- 但复制的是"变量名 → 对象"的映射，**两个任务指向同一个 list 对象**
- 于是两个请求 `append` 到**同一个 list** → 数据互相串

实测现象（两个并发请求各自登记 2 条）：

```
请求E 看到 = ['E-片段1', 'F-片段1', 'E-片段2', 'F-片段2']
请求F 看到 = ['E-片段1', 'F-片段1', 'E-片段2', 'F-片段2']   ← 完全一样，串了
```

**正确写法：绑定动作必须发生在每个请求自己的 task 内部。**

```python
def reset_sources() -> None:
    _sources.set([])     # 在当前 task 内重新绑定一个全新 list
```

`run_agent` 开头调用它，每个请求就各持一份。实测：

```
请求A 看到 = ['A-片段1', 'A-片段2']
请求B 看到 = ['B-片段1', 'B-片段2']     ← 互不污染 ✅
```

另外用 `default=None` + 惰性绑定做双保险：即使某个调用方忘了 `reset`（比如工具被单独测试），也不会抛 `LookupError`，只是那一份数据只在当前 task 内可见。

### 2.6 多轮检索的编号必须全局递增

一次对话里 Agent 可能查两次库（先查"报销流程"，再查"报销时限"）。

如果每次都 `enumerate(results, start=1)`，两批结果都是 `[1][2][3]`——**LLM 写"根据 [2]"时，指哪一批？**

解决：收集器维护全局偏移。

```python
def record_sources(results) -> int:
    buf = _sources.get() or ...   # 当前已登记的条数
    offset = len(buf)              # 本批第一条编号 = offset + 1
    ...
```

工具侧用 `enumerate(results, start=offset + 1)`。实测两批检索后编号是 `[1,2,3,4,5,6]`，不是 `[1,2,3,1,2,3]`。

## 3. 代码逐行解读

### 3.1 `app/core/citation.py`（新建，今日核心）

```python
_sources: contextvars.ContextVar[list[dict[str, Any]] | None] = contextvars.ContextVar(
    "citation_sources", default=None
)
```

- 类型注解 `ContextVar[X]` 是给读者看的，**ContextVar 本身不做类型校验**
- `default=None`：没绑定过时取到 `None`，而不是抛 `LookupError`
- 参数 `"citation_sources"` 是给调试用的名字

```python
def reset_sources() -> None:
    _sources.set([])
```

**一行函数，但它是并发正确性的全部。** 必须在每个请求入口（`run_agent` 开头）调用。
省掉它的后果不是"偶尔慢"，是**跨请求数据串**——A 用户看到 B 用户的检索来源。

```python
def record_sources(results: list[dict[str, Any]]) -> int:
    buf = _sources.get()
    if buf is None:                 # 本 task 还没绑定 → 惰性绑定
        buf = []
        _sources.set(buf)

    offset = len(buf)               # 已有条数 = 本批第一条编号 - 1
    for item in results:
        buf.append(
            {
                "index": len(buf) + 1,
                "source": item.get("source") or "未知来源",
                "content": item.get("content") or "",
                "similarity": item.get("similarity"),
            }
        )
    return offset
```

- `buf.append(...)` 是**原地修改**，不是重新绑定 —— 这一点在 LangGraph 场景下至关重要（见 3.4）
- `index` 用 `len(buf) + 1` 逐条递增，天然全局连续
- `item.get("source") or "未知来源"`：`.get` 避免 `KeyError`，`or` 同时兜住 `None` 和空字符串
- 返回 `offset` 给调用方算起始编号

```python
def get_sources() -> list[dict[str, Any]]:
    return list(_sources.get() or [])
```

**`list(...)` 包一层是防御性拷贝**：调用方拿到的是副本，误改它不会污染收集器内部。

### 3.2 `app/schemas/chat.py`（新建）

```python
class SourceItem(BaseModel):
    index: int
    source: str
    content: str
    similarity: float | None = None


class ChatResult(BaseModel):
    answer: str
    sources: list[SourceItem] = Field(default_factory=list)
    invalid_citations: list[int] = Field(default_factory=list)
```

用 pydantic 而不是裸 dict 的三个理由：

1. **字段有类型校验**——来源数据缺字段会在构造时立刻报错，而不是悄悄传下去
2. **未来接 HTTP 接口可直接做 response_model**，FastAPI 自动序列化
3. **等于可执行的接口文档**，比注释可靠

`default_factory=list` 而不是 `= []`：**可变默认值必须是工厂**，否则所有实例共享同一个列表（这是 Python 的经典坑，和函数默认参数是同一个问题）。

### 3.3 `app/tools/retrieval.py`（改动 2 处）

```python
from app.core.citation import record_sources
```

```python
    results = await search(query)

    if not results:
        return f"未在知识库中找到与「{query}」相关的内容。"

    # ① 先登记结构化结果（结构通道）
    offset = record_sources(results)

    # ② 再格式化成文本（文本通道）
    blocks: list[str] = []
    for index, item in enumerate(results, start=offset + 1):
        source = item.get("source") or "未知来源"
        blocks.append(
            f"[{index}] 来源：{source}（相关度 {item['similarity']}）\n{item['content']}"
        )

    return "\n\n".join(blocks)
```

**顺序是关键**：① 必须在 ② 之前，更必须在 `return` 之前。

原因：`results` 这个结构化对象**只在函数内部存在**。一旦 `return` 出去的是拼接文本，结构信息就永远出不了这个函数了。这就是"双通道"的物理位置——**在数据还结构化着的那一刻，分出一份给另一条路**。

`enumerate(results, start=offset + 1)`：编号从本批的全局位置开始，而不是永远从 1。

### 3.4 `app/services/agent_service.py`（改动 3 处）

**① `answer_node` 的 system prompt** —— 见 2.2，通道 A。

**② `run_agent` 开头加 reset**

```python
    # ⓪ 引用收集器必须在跑图之前重新绑定。
    #    ContextVar 复制的是「绑定」不是「对象内容」，不重新绑定会读到上个请求的残留。
    reset_sources()
```

为什么"在跑图之前"就够：LangGraph 执行节点时会**继承**当前 task 的 context 绑定（实测确认，见 3.5）。所以父 task 绑好，节点里 `append` 就能被外层读到。

**③ `run_agent` 出口改结构**

```python
    # ⑤ 取出本请求累计的来源（结构通道）
    raw_sources = get_sources()
    sources = [SourceItem(**item) for item in raw_sources]

    # ⑥ 校验引用编号有没有越界
    invalid = check_citations(final_answer, len(sources))
    if invalid:
        logger.warning(...)

    # ⑦ 写回记忆
    await append_turn(session_id, user_input, final_answer)

    # ⑧ 返回结构化结果
    return ChatResult(answer=final_answer, sources=sources, invalid_citations=invalid)
```

`SourceItem(**item)` 是**字典解包构造**：`item` 的键名必须和 pydantic 字段名逐字一致，否则 `ValidationError`。这个约束是好事——收集器字段名改了而 schema 没跟上，会当场报错而不是静默丢数据。

### 3.5 LangGraph 场景下的 contextvar（实测数据）

**这个必须实测，不能推理**——如果 LangGraph 把节点丢进全新 context 执行，方案 C 直接不成立。

| 场景 | 节点内能否读到父 task 的绑定 | 外层能否读到节点内的登记 |
|---|---|---|
| 父 task 先 `reset`，再 `ainvoke` | ✅ 继承到（id 相同） | ✅ 能读到 |
| **不 reset**，直接 `ainvoke` | ❌ 拿到 `None` | ❌ 读不到（节点内新建的绑定出不来） |
| 父 task `reset` 后 `gather` 并发 | ✅ 两个都继承 | ✅ 能读到 |
| 父 task `reset` 后 `create_task` | ✅ 继承 | ✅ 能读到 |

两个结论：

1. **`reset_sources()` 不能省**——第二行就是省掉它的后果（静默丢数据）
2. 节点内**只能 `append` 不能 `set`**——`set` 会建立当前 task 专属的绑定，外层读不到（实测确认）

## 4. 类比迁移表

| 这套链路 | 前端等价物 |
|---|---|
| `contextvars.ContextVar` | Node.js `AsyncLocalStorage`（请求作用域存储） |
| `reset_sources()` | 请求中间件里初始化 `req.locals` |
| `record_sources()` | 往 `req.locals.sources` 里 push |
| `get_sources()` | 请求结束时读 `req.locals` |
| 工具返回 `str` | 接口返回 HTML 字符串 |
| `sources` 表 | 接口另外返回的 JSON 数据 |
| 回答里的 `[1]` | 页面里的 `<sup>[1]</sup>` 角标 |
| `check_citations()` | 校验模板里引用的图片 ID 是否真实存在 |
| pydantic `BaseModel` | TypeScript `interface` + 运行时校验（zod） |

## 5. 面试考点

**Q1：你们 RAG 的引用是怎么做的？**
> 双通道。文本通道把带编号的片段给 LLM，prompt 里明确要求它标注 `[n]`；结构通道用 contextvar 收集原始结构化片段，随回答一起返回给前端。两条通道只靠编号对齐。前端拿 sources 表把 `[n]` 渲染成可点击来源。

**Q2：为什么不直接从工具返回的文本里正则解析出结构化数据？**
> 三个问题：格式耦合（文案改一个字就崩）、内容含换行/特殊字符时边界难判、本质是把刚序列化的东西再反序列化回来。收集器在格式化**之前**存原始结构，零解析。

**Q3：为什么用 contextvar 而不是把 sources 挂在 AgentState 上？**
> 工具层只拿得到 `name` 和 `arguments`，拿不到 state —— 工具是注册表统一调度的，签名里没有 state 通道。contextvar 是"不改变工具签名又能携带请求级数据"的折中，代价是引入隐式状态。

**Q4：contextvar 有什么坑？**
> ContextVar 复制的是**绑定**不是**对象内容**。如果在父层级绑定一个 list 再并发子任务，子任务会继承**同一个 list 对象**，append 互相串。必须在每个请求自己的 task 内部重新绑定。

**Q5：要求 LLM 标注引用会带来什么新问题？**
> 幻觉引用——为了显得有依据而标出 sources 里不存在的 `[n]`。所以要校验：正则提取所有编号，比对 sources 范围，越界的记录并告警。我们只检测不改写，改写会引入新的不确定性。

**Q6：你们怎么保证并发请求之间的引用数据不串？**
> contextvar 按 task 隔离 + 每个请求入口显式重新绑定。实测两个并发会话各自的来源编号都从 1 连续，无翻倍。

### 参考答案要点

1. A 通道（prompt）让回答里有编号；B 通道（收集器）让编号能映射回原文。缺 A：回答里没编号，sources 白收；缺 B：有编号但点不开，纯装饰。
2. 因为 prompt 没要求，而且"不要提及内部工具调用细节"可能在主动抑制。D11 明确要求标注 `[n]`，并把"技术细节"与"来源编号"分开说。
3. 前端要的是 `source/content/similarity` 三个字段，不是拼好的文本。存文本还得再解析一遍，绕回正则反解那条脆弱路线。
4. **复制的是绑定，不是对象内容。** 错误写法（父层级绑定后并发子任务）会让两个请求共用同一个 list，看到对方的数据，条数翻倍。
5. 会读到上一个请求的残留来源，或者与其他请求共享同一个 list（取决于绑定发生在哪一层）。并发下会串数据。
6. 两批都是 `[1][2][3]`，LLM 写"根据 [2]"分不清指哪批。`record_sources` 返回本批之前的已有条数（offset），工具用 `start=offset+1` 编号，使编号全局递增。
7. 因为要求引用会诱发"为凑引用而乱标"的幻觉引用。只记录不改写，是因为改写会引入新的不确定性，改错了更难查；等有评测体系量化后再定策略。
8. `append` 是原地修改，`set` 是重新绑定。在 LangGraph 节点里 `set` 会建立当前 task 专属的绑定，外层 `get_sources()` 读不到——静默丢数据。
9. 会话 ID 写死会让第二次运行读到 Redis 里上一轮的问答历史，LLM 直接从历史作答、不再调用工具，于是 sources 为空——看起来像"收集器坏了"，实际是记忆层的影响。

## 7. 踩坑记录

### 坑 1：contextvar 用 `default=[]` 会跨请求串数据

原本打算写 `ContextVar("sources", default=[])`。实测两个并发请求各自登记 2 条时：

```
请求E 看到 = ['E-片段1', 'F-片段1', 'E-片段2', 'F-片段2']
请求F 看到 = ['E-片段1', 'F-片段1', 'E-片段2', 'F-片段2']
```

**根因**：`default=[]` 里那个 list 在**模块导入时创建一次**，所有 task 共享。即使换成"父 task 先 `set([])` 再并发"，子 task 继承的仍是**同一个 list 对象**——`set` 只隔离"绑定"，不隔离"对象"。

**修法**：`default=None` + 必须由每个请求在自己的 task 内 `set([])`。实测并发互不污染。

### 坑 2：节点的"继承"依赖入口先绑定

实测：不调 `reset_sources()` 直接 `ainvoke`，节点内 `_sources.get()` 返回 `None`，节点里惰性绑定的那份数据**外层读不到**（`get_sources()` 返回 `[]`）。

现象是"回答里有 `[1]`、来源表却是空的"，看起来完全像收集器坏了。

### 坑 3：验证脚本的断言"空列表也能通过"

B3 的原始断言是"编号从 1 连续"：

```python
a_ok = a_idx == list(range(1, len(a_idx) + 1))
```

**空列表 `[] == []` 恒为真** —— 来源一条都没收到时，断言照样打 ✅。

**修法**：把"非空"写进条件。

```python
a_ok = len(a.sources) > 0 and a_idx == list(range(1, len(a_idx) + 1))
```

**教训**：写断言时要问一句"什么情况下这个断言会假通过"。

### 坑 4：会话 ID 写死导致"第二次运行就坏"

第一次跑 B1 成功（来源 3 条），第二次跑同一脚本却来源 0 条、越界 `[1]`。看起来像非确定性 bug。

**真因**：会话 ID 写死成 `d11-e2e-1`，第二次运行时 Redis 里已经存着上一轮的问答（含 `[1]`），LLM **直接从历史作答、不再调用工具** → 来源为空，而回答里的 `[1]` 是从历史带过来的。

这个假象很容易被误判成"收集器坏了"，实际是记忆层的影响。

**修法**：验证脚本用带 uuid 的会话 ID；同时把这个场景单独立成 B4 用例。

### 坑 5（已知缺陷，D11 未修）：历史里的引用没有来源表

B4 暴露的真实问题——**同一会话重复提问时**：

```
第 1 轮：来源 3 条  越界 无
第 2 轮：来源 0 条  越界 [1, 2, 3]   ← 沿用历史作答，未调用工具
```

第 2 轮回答里的 `[1]` 是上一轮的记忆带过来的，但**本次请求的收集器里没有对应来源**，前端点不开。

D11 的处理：`invalid_citations` 已经把这个情况报出来了，前端可据此降级显示（比如整段标灰、提示"来源请见上一轮"）。

彻底解决需要把来源一起存进记忆（涉及记忆存储结构改动），或改用"不做检索就不标引用"的 prompt 约束。**留到 D17 评测体系量化后再定策略**。这类"先检测、后治理"的处理方式，在企业项目里是常见且合理的节奏。

## 附录 A：端到端运行链路（实测）

### A.1 一次问答的完整数据流

```
用户："「琥珀」这个项目是哪个组负责的？"
  │
  ├─ run_agent：reset_sources()          ← 绑定本请求的收集器
  │
  ├─ plan 节点：LLM 决定调工具
  │     tool_calls = {name: "search_documents", arguments: '{"query": "琥珀 项目 负责团队"}'}
  │
  ├─ execute 节点 → search_documents 工具
  │     ├─ results = await search(query)          ← list[dict]，只活在函数内部
  │     ├─ offset = record_sources(results)       ← 通道 B：登记结构化数据
  │     └─ return "[1] 来源：…\n…"                 ← 通道 A：文本给 LLM
  │
  ├─ plan 节点（第二次）：LLM 判断信息够了
  │
  ├─ answer 节点：生成回答
  │     "「琥珀」项目由**星河算法组**负责，项目周期两年……[1]"
  │                                          ↑ 编号是 LLM 自己写的
  │
  └─ run_agent 出口
        sources = get_sources()                  ← 取出通道 B 的数据
        invalid = check_citations(answer, len(sources))
        return ChatResult(answer=..., sources=..., invalid_citations=[])
```

**LLM 全程没见过向量、没见过数据库、没见过 `list[dict]`**——它只见过那段带编号的文本。所有"RAG 的魔法"发生在工具把文本交出去的那一刻。

### A.2 实测输出（B1）

```

越界引用：无
---- 来源映射表（前端拿到的就是这份）----
  [1] d11-alpha.md  相关度 0.7547  「公司内部项目管理规定：代号为「琥珀」的项目由星河算法组负责…」
```

前端拿到这份 JSON 后渲染成：

>

**这就是"可定位原文"。**

### A.3 一次请求内多次检索（B2）

```
第一批工具返回：[1] 来源：d11-alpha.md（相关度 0.7704）
```

### A.4 并发不串（B3）


## 附录 B：HTTP 出口——把 Agent 挂上接口

### B.1 为什么先做非流式

PRD 规划的是 SSE（逐字返回），但那要求前端用 EventSource 接收、还要处理断线重连，是一块独立的工作量。项目现在还没有前端，先用非流式 JSON 把「服务层 → HTTP 出口」这段接通——好处是能用 curl 直接看到完整的 `{answer, sources}`，确认 D11 的引用定位在**真实 HTTP 边界**上是否完整。

将来上流式时，前端本来就要把 `fetch` 改写成 `EventSource`，所以现在用 JSON 不构成额外的技术债。

### B.2 接口契约

```
请求   POST /api/chat
       {"message": "问题", "session_id": "可选"}

响应   200
       {"session_id": "...", "answer": "...", "sources": [...], "invalid_citations": [...]}

错误   422  请求体不合法（pydantic 拦下，不进入业务逻辑）
       500  未处理异常（main.py 的全局异常处理器统一兜底）
```

### B.3 三个文件的改动

| 文件 | 改动 |
|---|---|
| `app/schemas/chat.py` | 新增 `ChatRequest` / `ChatResponse` |
| `app/api/chat.py` | **新建** —— `POST /api/chat` |
| `app/main.py` | 注册 chat 路由 |

**① `session_id` 是可选的，且带格式校验**

```python
session_id: str | None = Field(default=None, pattern=r"^[A-Za-z0-9_-]{1,64}$")
```

不传就由服务端新建（`uuid.uuid4().hex`）并在响应里回传。好处是 curl 裸测一个请求也能跑通；前端要延续上下文时，把响应里的 session_id 存下来、下一轮回传即可。

`pattern` 不是形式主义：**session_id 会直接进 Redis 的 key**。不校验的话，用户传个带空格或换行的字符串进来，key 就脏了。

**② `ChatResponse` 用继承，而不是把 session_id 塞进 `ChatResult`**

```python
class ChatResponse(ChatResult):
    session_id: str = Field(description="...")
```

`session_id` 是**传输层**概念（HTTP 请求之间靠它串起同一个会话），而 `ChatResult` 是**服务层**返回值——`run_agent` 已经通过入参拿到它了，不需要在自己的结果里再回带一份。分层别串味。

**③ 路由函数只做三件事**

```python
session_id = req.session_id or uuid.uuid4().hex     # ① 补全 session_id
result = await run_agent(session_id, req.message)   # ② 调服务层（业务全在那边）
return ChatResponse(...)                            # ③ 转换返回结构
```

不在这里写业务判断（检索、组 prompt、校验引用都在服务层），也不写参数校验——后者交给 pydantic + FastAPI，非法请求直接 422。

### B.4 HTTP 边界上"多出来"的东西

服务层能跑通 ≠ 接口能跑通。挂上 HTTP 之后，新增了四件服务层不用管的事：

| 新增的东西 | 谁负责 |
|---|---|
| 请求体形状与取值校验 | pydantic（`Field` 约束）→ FastAPI 自动 422 |
| `session_id` 的生命周期（谁生成、谁保存、谁回传） | 路由层 |
| 错误码语义（422 / 500 各代表什么） | FastAPI + main.py 的全局异常处理器 |
| 序列化（pydantic 模型 → JSON） | FastAPI（`response_model`） |

这也是为什么路由函数可以写得这么薄——**边界上的活都被框架和 schema 声明式地接管了**。

### B.5 实测（`scripts/d11_http_verify.py`，4/4 通过）

```
H1. 不传 session_id → 服务端新建会话 + 引用可定位
  HTTP 状态 = 200
  session_id = 144a07a122f34a3db88fb272e7f44f9c  (长度 32)
  answer = 「琥珀」项目由**星河算法组**负责，项目周期两年，负责人为林工，该项目组直接向 CTO 汇报。[1]
  ---- sources（前端拿到的映射表）----

    [2] d11-beta.md   相关度 0.5753  「公司内部项目管理规定：代号为「翡翠」的项目由山海基础组负责…」
  invalid_citations = []

H3. 参数校验（非法输入 422）
  ✅ 空 message           → HTTP 422  loc=body.message
  ✅ 缺 message           → HTTP 422  loc=body.message
  ✅ message 超长(2001)    → HTTP 422  loc=body.message
  ✅ session_id 非法字符   → HTTP 422  loc=body.session_id
  ✅ session_id 超长(65)   → HTTP 422  loc=body.session_id

```

**H2 顺带在 HTTP 边界上复现了 §7 坑 5 的已知缺陷**：

```
第 1 轮  状态=200  answer=根据资料，「翡翠」项目由**山海基础组**负责，负责人为**周工**…[1]

```

两个信息同时成立：

- 第 2 轮能答出"周工"（这个信息第 1 轮的文档里才有）→ **记忆确实生效了**，说明 `session_id` 正确串起了两轮
- 但第 2 轮 `sources=0`、`[1]` 被判越界 → **沿用历史作答时没有新的来源表**

同一个现象，在 D11 服务层测试里看起来像"收集器坏了"，挂上 HTTP 之后有了 `invalid_citations` 这个字段，前端就能明确知道"这轮的引用没有来源可映射"并降级显示。
