该不该把工具包成 MCP —— 把「代价」量出来

D25 · 全部数字来自 2026-10-01 本机实测（mcp SDK 2.2.0 / Python 3.13 / 10 逻辑核）· 探测脚本在 /tmp/d25_demo/，非示意
一句话结论

你的三条判断 全部成立：MCP 的价值不在「调用更快」，在接入更省事、更规范、能共享； 本地工具本地定义最好；包成 MCP 会多出复杂度和延迟。

要掰正的只有一处 —— 代价的排序：实测每次往返只多 0.56 ms， 本项目里一次重排（780 ms）就相当于 1,385 次 MCP 往返。 所以延迟不是主要代价（虽然相对倍数很吓人）； 主要代价是复杂度，而复杂度里真正咬人的是失败模式变多（下一节展开）。

一、你的答案，逐条判定

你说的判定说明
「MCP 的意义不是在于调用更好」 对 协议不承诺更快。实测往返是直调的 1.7 万倍 —— 它压根不是为性能设计的。
「而是叫工具的接入更加方便和规范化，可以进行工具共享」 对 这正是它的全部价值主张：把 N 个应用 × M 个工具 的适配矩阵，压成 N + M 份实现。
术语：适配矩阵 = 每个应用都要为每个工具各写一次对接代码，应用或工具任意一方增加，组合数就乘上去。
「这种本地工具在本地定义最好」 对 这就是判据本身。下一节的「三问」是它的可执行版本。
「改成 MCP 的代价是，复杂度和延迟都会增加」 对，但要排序 两条都真。但量级差了三个数量级：主项是复杂度，不是延迟（第二节给出数字）。

二、实测①：一次往返到底多贵

实验设计：让工具什么都不干（noop() 返回空串），这样量到的全是通道开销，不是工具本身的计算。 对照组是同一个进程里直接调函数（最理想情况）。

测量项第一次第二次怎么读
直调函数（median） 0.0419 µs 0.0419 µs 同一进程内，编译器/解释器层面的一次函数调用
MCP 往返一次（median） 0.5634 ms 0.5628 ms 完整包含：序列化 → 写管道 → 子进程执行 → 读管道 → 反序列化
→ 相对倍数 17,203× 17,435× 比例吓人但这个倍数说明不了「贵不贵」
→ 绝对差值 +0.56 ms +0.56 ms 这才是要看的数
传输成本（1 KB 返回值） 0.5690 ms 0.5737 ms 和空返回值几乎一样 → 说明固定开销占绝对主导
传输成本（100 KB 返回值） 0.8280 ms 0.8251 ms 传了 100 KB 才多 0.26 ms
→ 拟合出的斜率 0.0027 ms/KB 0.0026 ms/KB 数据量几乎不是成本；贵的是「往返」这个动作本身
两次独立测量几乎完全重合（往返差 0.1%、斜率差 4%），说明这组数字是稳的。 （按项目规矩：关键性能数字必须独立测两次 —— D18 就是这么发现同一份代码两次跑差 1.8 倍的。）
「比例」和「绝对值」在这里讲了两个相反的故事，要分开说。 直调 0.042 µs vs 往返 0.56 ms，比例上是天文数字；但绝对差只有 0.56 毫秒 —— 人眨一次眼是它的 200 倍以上。 面试里如果只说「慢了 1.7 万倍」会误导人，只说「才 0.56 毫秒」又显得像在洗地；两个一起说才是完整的。

对照锚点：本项目自己的耗时

一次重排（20 篇 × 300 字切片）实测中位数 780 ms —— D18/D19 受控复测 754.5 / 812.2 ms（load 6.94~9.20），不是本轮测的，此处只作参照。

一次重排 780 ms  ÷  一次 MCP 往返 0.5634 ms  ≈  1,385 次

也就是说：把一次重排的时间拿去付 MCP 往返，够你来回调 1,385 次工具。 在这个量级差面前，通道延迟不可能成为选型理由。

一个必须说清的边界：这 0.56 ms 量的是同机 stdio（宿主直接读子进程的标准输入输出）。 Harness 那个 Server 是本地 Node 子进程，它内部再发 HTTPS 去 Harness 云端 —— 那段网络往返不在这 0.56 ms 里，它属于工具的执行成本，不是 MCP 通道的成本。

三、实测②：起一个 Server 进程要付多少（这个比往返更值得关心）

往返便宜，但进程本身不便宜。四段放在同一次运行里测（load 3.02 / 10 核，每段 5 次取中位与最小）：

分段中位最小比上一段（按最小）
① 裸 Python 进程能起来25.0 ms24.9 ms—
② import mcp259.2 ms257.7 ms+232.8 ms
③ import mcp.server256.8 ms255.1 ms≈ 0
④ 建好 MCPServer 对象265.3 ms253.9 ms≈ 0
⑤ ★ 真 MCP 启动（spawn + initialize）222.8 ms220.9 ms算出来是负的
能下的结论（①→④ 内部同口径、可加）： 起一个 MCP Server 进程的时间几乎全花在「把依赖 import 进来」（约 233 ms）， 裸解释器只要 25 ms，而协议握手与建对象几乎不额外花时间。 → 换句话说：你付的是 Python 生态的启动税，不是 MCP 协议的开销。
⚠ ⑤ 比 ② 还小 —— 这组关系不可加，所以我不做减法。 ⑤（220.9 ms）竟然小于「裸进程 + import mcp」（257.7 ms）， 但 ⑤ 严格多做了事。 原因是这两类测量的区间不一样：①~④ 用 subprocess.run 量的是「起→跑完→退出」的全程， ⑤ 只量到「initialize() 返回为止」（此时子进程还活着，退出与析构的成本没算进去）。 我怀疑差异来自这个口径差，但没有验证（比如没去把两种口径统一后重测）， 所以这里只做「同一量级」的判断，不做减法。
★ 更正（我本轮自己犯的）：第一版分解，我拿「本批新测的 250.5 ms」去减「上一轮跑的 232.6 ms」， 脚本照直印出 占 108%，剩下约 -18.2 ms —— 一个负数，自相矛盾，而我让它印出来了。 两次运行之间负载不同（同一次启动：232.6 → 262.7 ms，差 13%），数字根本不能相减。 → 修法：把四段全部放进同一次运行（本表格就是这么来的）。 → 这条与项目里那条老规矩同源：不同口径 / 不同批次的数字禁止相减或并列比较。 （那次脚本的输出只打在屏幕上、没落盘 —— 本页其余数字的来源都在 /tmp/d25_demo/*.log，唯独这条错误的现场只在对话里，它的价值也正是"作为一个反例"。）

这组数两轮差约 10%：import mcp 累计第一次 224.5 ms、第二次 200.9 ms。 导入耗时受磁盘缓存与机器负载影响，看量级（两百毫秒）即可，别抠到小数点。 （第一轮那两段当初只打在屏幕上、没落盘，所以此处引用的是已存文件的第二轮；两轮结论一致。）

五、结论：代价排序

代价实测量级在本项目里意味着什么
复杂度 主项 多一个要你管的进程：启动、健康、崩溃重启、退出清理。全是你自己写。
└ 失败模式变多 — 子进程起不来 / 跑一半崩了 / 工具清单悄悄变了（tools/list_changed 你不订阅就收不到）。 这三类都不报错、只是行为变了 —— 属于典型的静默失效。
延迟（每次往返） +0.56 ms 一次重排 ≈ 1,385 次往返。不是选型理由。
延迟（一次性启动） ≈ 0.22~0.26 s 常驻只付一次；若是 CLI 形态，每次都要付。这才是延迟里唯一值得算的一项。
数据量带来的成本 0.0026 ms/KB 基本可以不管。但如果工具返回巨大结果（几十 MB），要单独想。

六、判据：三问

  1. 这个数据（或能力）在不在我的进程里？ 在 → 套 MCP 只是给自己加一层进程边界。
  2. 除了我，还有没有第二个消费者？ 只有我 → 共享这个好处拿不到；多个 Host / 多人 / 跨语言 → 才值。
  3. 它会不会成套地变？我需要运行时发现吗？ 工具集固定且我知道 → 直接调；工具集由别人维护、会变 → 动态发现才有意义。

第 1 问是硬条件，后两问决定「值不值」，三问全中才该套。

用三问体检本项目每一个候选

候选①在进程里②多个消费者③会变且需发现结论
current_time（D9 那个） 是否否 不该套 三问全否 —— 你的判断是对的
知识库检索 retrieve() 是（同进程 + 同库）否否 不该套 语料是我们自己入库的，没有那条边界
自研库存服务（D26） 是（内存 mock）否否 判据说不该套 见下方「诚实一条」
Harness（D27） 不在（别人云端的系统） 是（官方 Server，多 Host 共用） 是（别人维护、会变） 该套 三问全中，这才是 MCP 的正战场

七、诚实一条：D26 那个自研 server，不满足我自己写的判据

按上面三问，自研库存服务应该不该套 MCP。这个结论我不绕开，直接摆出来。 它仍然要做，理由是另一个维度的 —— PRD §4.2 自己写了（原文）：

所以准确的讲法是：D26 的价值是「证明我懂协议两端」，不是「工程上应该这么做」。 面试时这两句要分开说 —— 混在一起说，反而暴露没想清楚。

八、面试怎么讲

被问「你们为什么接 MCP？它有什么好处」

「省钱不是它的卖点。MCP 解决的是适配矩阵：没有它，N 个应用 × M 个工具要写 N×M 份对接； 有了它变成 N+M —— 应用侧只要一次动态发现。所以它的好处在接入成本和互操作， 不在调用性能。我自己量过：一次 stdio 往返 0.56 毫秒，是这个量的通道开销。」

反追问：「那你为什么还接 Harness？你自己的知识库为什么不套 MCP？」

「判据是数据在不在我的进程里。知识库是我自己入库的、跟 Agent 同进程， 套上去只多一层进程边界和一次往返。Harness 正好相反 —— 数据在别人的云端系统里， 由别人维护、还天天变，那才是 MCP 的主场。」

再追问：「那代价是什么？」

「复杂度，不是性能。多一个进程要管生命周期，而且失败模式变多还都很隐蔽： 子进程起不来、跑一半崩了、工具清单变了但你没订阅通知所以不知道 —— 这几类都不报错，只是行为变了。 延迟反而可以忽略：每次往返 0.56 毫秒，而链路里一次重排要 780 毫秒，差三个数量级。」

九、本轮的边界（没测到的不下结论）

  • Harness 的启动成本没测（还没接）。它是 Node 写的，不能照搬这里的 Python 数字。
  • Streamable HTTP 传输的延迟没测（本项目只用 stdio）。跨机/跨进程的 RTT 不在上面的数字里。
  • 高并发下没测。上面全部是「一次一个请求」的顺序测量；多个工具并发调同一个 Server 的表现是另一回事。
  • 「子进程 stderr 不被读会阻塞」这条经典坑没实测。读 SDK 源码可见 stdio_client(server, errlog=sys.stderr) —— 默认就替你排掉 stderr（所以默认配置下这条坑不触发， 代价是子进程日志会混进宿主自己的终端）。这是读源码得出的，不是实测。
