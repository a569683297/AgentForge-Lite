MCP 的 Server 到底是什么

D25 · 全部结论来自 2026-10-01 本机实测（mcp SDK 2.2.0）· 报文为真实抓取，非示意
一句话结论

Server 不是「一个工具」，Server 是「一个装着工具的独立进程」。 两者的差别不在"能干多少活"，而在它是不是一个需要被启动、被连接、被询问、还能自己崩掉的东西。 哪怕一个 Server 里只装 1 个工具，它俩也仍然是两种东西 —— 本文就是为证明这一句。

一、先看对照：同一个 current_time，两种活法

你项目里 D9 写的 app/tools/current_time.py，和一个 MCP Server 里的 current_time 工具， 函数体的代码可以一模一样。区别全在外面那层壳。

宿主进程内 你的 current_time

# app/tools/current_time.py
def current_time() -> str:
    return datetime.now(...).isoformat()

# registry 里手写一行登记：
registry.register("current_time", current_time)
  • 住在 Agent 后端自己的进程里（同进程、同内存）
  • 调用 = 直接函数调用，没有网络、没有序列化
  • 没有"启动"这回事 —— 它随 FastAPI 一起活、一起死
  • 要加第 2 个工具 → 再手写一行 register
  • "有哪些工具"这件事只存在于我脑子里和代码里，机器问不出来

独立进程 MCP Server 里的 current_time

# 先有一个 Server（盒子）
server = MCPServer("demo", version="0.0.1")

# 再把函数挂进去（内容物）
@server.tool(name="current_time", ...)
def current_time() -> str:
    return datetime.now(...).isoformat()

server.run("stdio")   # ← 常驻，等请求
  • 住在 另一个操作系统进程里（子进程）
  • 调用 = 序列化 → 写管道 → 等回包
  • 必须先"启动"，还可能启动失败 / 中途崩掉
  • 加第 2 个工具 → 只多一个装饰器，宿主一行不改
  • "有哪些工具"机器能问出来（tools/list）

二、实测：一个 Server 装 3 个工具，一次 tools/list 全拿到

如果 Server 就是工具，那"1 个 Server → 3 个工具"这句话就无法成立。实测：

  一次 tools/list 拿到 : 3 个工具
      - current_time   入参 schema = {'properties': {}, 'type': 'object', ...}
      - add            入参 schema = {'properties': {'a': {'type': 'integer'},
                                                     'b': {'type': 'integer'}},
                                       'required': ['a', 'b'], 'type': 'object', ...}
      - echo           入参 schema = {'properties': {'text': {'type': 'string'}},
                                       'required': ['text'], 'type': 'object', ...}
注意这三个 inputSchema 是自动生成的。 我只是写了 def add(a: int, b: int) -> int， Server 就把 Python 的类型标注翻译成了 JSON Schema 挂在网上。 这一层翻译工作，就是一个"普通函数"永远不做的事 —— 因为没人问它。

三、Server 到底做了什么：四件事

职责它在干什么对照：一个普通函数
① 启动
与常驻		 被宿主作为子进程拉起，之后就活着等消息；宿主退出它才退出 没有进程，谈不上启动
② 接线 起一个循环：从 stdin 读一行 JSON-RPC → 处理 → 往 stdout 写一行结果。
（stdio 传输的全部内容就是这个）		 没有通道，它只存在于调用栈上那一瞬
③ 报目录 被问"你有哪些工具"时，回一张清单：名字 + 描述 + 参数 JSON Schema 问不了。"有哪些工具"只在代码里
④ 校验 + 调度 收到 tools/call 后：按名字找到函数 → 校验参数类型 → 真正执行 → 把返回值包装成 MCP 的结果结构 只有最后一步（执行）

②③④ 都可以在下面的真实报文里逐条对上。

四、真实报文：一次完整的 stdio 会话（原样抓取）

下面是 Client（宿主侧）和 Server（子进程）之间来回的每一行。 中间插了一层透明监听，所以看到的是协议原文，不是我重写的示意。

① client → server   请求 method=initialize id=1
   {"jsonrpc":"2.0","id":1,"method":"initialize","params":{
      "protocolVersion":"2025-11-25","capabilities":{},
      "clientInfo":{"name":"mcp","version":"0.1.0"},"_meta":{}}}

② [SERVER 进程] 进程已启动，本进程内装了 3 个工具        ← 它是另一个进程

③ server → client   响应 OK id=1
   {"jsonrpc":"2.0","id":1,"result":{
      "capabilities":{"tools":{},"resources":{},"prompts":{},"experimental":{}},
      "protocolVersion":"2025-11-25",
      "serverInfo":{"name":"demo-three-tools","version":"0.0.1"}}}   ← Server 自报家门

④ client → server   通知 method=notifications/initialized
   {"jsonrpc":"2.0","method":"notifications/initialized"}            ← 没有 id，不需要回

⑤ client → server   请求 method=tools/list id=2                      ← ③ 报目录
⑥ server → client   响应 OK id=2  → 3 个工具的清单 + JSON Schema

⑦ client → server   请求 method=tools/call id=3
   {"jsonrpc":"2.0","id":3,"method":"tools/call",
    "params":{"name":"current_time","arguments":{},"_meta":{}}}

⑧ [SERVER 进程] 执行 current_time()                                  ← ④ 真的在它那边跑

⑨ server → client   响应 OK id=3
   {"jsonrpc":"2.0","id":3,"result":{
      "content":[{"text":"2026-10-01T19:24:00+08:00","type":"text"}],
      "isError":false,
      "structuredContent":{"result":"2026-10-01T19:24:00+08:00"}}}   ← 双层返回
第 ⑨ 行那个"双层返回"值得单独记一笔：同一个值出现了两次 —— content 里是给人/模型读的自然语言，structuredContent 里是给程序读的结构化值。 协议同时给两种读者准备了字段。（本次实测原本只预期一种，这是顺手发现。）

五、两种"出错"，实测下来长得一样

我本来以为"工具报错"和"协议层出错"会是两种形态。实测：两种都装在"成功的响应"里返回， 用 result.isError = true 标记，客户端不抛异常。

⑩ client → server   tools/call  name="echo"  arguments={"text":123}   ← 故意传错类型
   [SERVER 进程] Tool 'echo' rejected arguments: ['text']              ← Server 校验了
⑪ server → client   响应 OK id=5
   result.content[0].text = "Error executing tool echo: 1 validation error for
                             echoArguments / text / Input should be a valid string"
   result.isError = true                                       ← 客户端侧：is_error=True

⑫ client → server   tools/call  name="not_exist_tool"                  ← 调不存在的工具
   [SERVER 进程] Tool 'not_exist_tool' failed: 'Unknown tool: not_exist_tool'
⑬ server → client   响应 OK id=6
   result.content[0].text = "Unknown tool: not_exist_tool"
   result.isError = true                                       ← 同样不抛异常
这个设计是有意的：错误要能被模型看见。 如果把它做成"连接级异常"，那模型看到的就是"工具断了"，没法自己改成正确参数再试一次； 装进 result 里，模型读得到那句 Input should be a valid string， 就能自我修正 —— 这是 Agent 循环里很关键的一环。

⚠ 附带一句：本次没有测到"协议层错误"（JSON-RPC error 对象）的分支， 上面结论只覆盖工具被调用之后的错。别外推。

六、判据：一句话分清楚

问一句「需要被启动吗？需要被连接吗？需要被问『你有什么』吗？」

  • 三个都要 → 它是 Server
  • 只要"被调用" → 它是 Tool

换一种说法：current_time 的入口是 def current_time(...)； MCP Server 的入口是 server.run("stdio")。 一个是函数，一个是常驻进程。

七、那"多一层"到底换来了什么

换来的说明本项目对应
动态发现 工具清单是运行时问出来的，不是编译期写死的 → 接入新 server 不用改 Agent 代码 PRD §9.9 那条面试叙事
语言/技术栈无关 Server 用什么语言写都行，只要说 MCP。我们是 Python，Harness 官方 Server 是 Node D27 连 Harness
故障隔离 Server 崩了是它自己崩，宿主进程还活着 → 可以重启它、可以降级 D27 要写的健康检查 / 重启退避
独立部署与权限 单独升级、单独发凭据（Harness 的 PAT 只给 Server 那一侧用） D25 的 PAT

代价也要说清：多一次进程间往返、多一个要管生命周期的东西 （启动、健康检查、崩溃重启、退出清理）。所以判据是 「数据在不在我的进程里？不在，才有 MCP 的价值。」 —— 我们自己的知识库是入库的、同进程的，就不需要给它套一层 MCP。

八、⚠ 今天这轮实测纠正的两处说法

纠正 1（较重要）：stdio 的默认路径就是「握手式」。
昨天我说的原话：「PRD §9.6.2 那句『stdio 发 initialize 握手』被推翻了，现在只是 legacy 路径。」
实测事实：SDK 2.2.0 同时支持两代，但走 stdio 时客户端默认发 initialize， 谈定的版本是 2025-11-25（= LATEST_HANDSHAKE_VERSION）， 而不是同样存在于 mcp.types.LATEST_PROTOCOL_VERSION 里的 2026-07-28。
所以：PRD 那句话对默认路径仍然成立，我昨天把它说成"被推翻"是过度外推 —— 把"规范里新出现了一代"读成了"实现已经切换过去了"。
SDK 常量实测：LATEST_PROTOCOL_VERSION=2026-07-28 · LATEST_HANDSHAKE_VERSION=2025-11-25 · LATEST_MODERN_VERSION=2026-07-28 · HANDSHAKE_PROTOCOL_VERSIONS=(2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25) · MODERN_PROTOCOL_VERSIONS=(2026-07-28,) · MCP_PROTOCOL_VERSION_HEADER=mcp-protocol-version
纠正 2（我自己的脚本硬编码了错结论）
第一版脚本里我写了 print("调 echo(123): 未报错（Server 接受了错类型）")， 而它上一行打印的报文明明白白写着 Tool 'echo' rejected arguments。 数据说"拒绝了"，脚本照念"没拒绝"。这是本项目第 4 次同一个坑 （D13 → D16 → D18 → 今天）：结论文本必须由数据分支决定，不能硬编码。
