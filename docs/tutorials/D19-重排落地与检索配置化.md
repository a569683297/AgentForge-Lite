## 2. 核心概念讲解

### 2.1 配置化的目的：让「消融」这个东西能成立

这是今天最容易被讲歪的一点。

**错误理解**：`RETRIEVER_CONFIG` 是个 feature flag，为了灰度上线时能切换。
**正确理解**：它是**实验矩阵的开关**。

PRD §9.5 / F3.6 / F7.3 要求**同一个评测集跑三遍**：

| 配置 | 链路 | 要回答的问题 |
|---|---|---|
| A `pure_vector` | 向量 top5 | 基线 |
| B `hybrid` | 两路 top20 → RRF → top5 | 加关键词那一路有没有用 |
| C `hybrid_rerank` | 两路 top20 → RRF → **20** → 重排 → top5 | 加交叉编码器有没有用 |

验收点是 **S2：C 相对 A ≥ +10%**。要做出这个对比，三条链路必须**同时存在、可切、且可归因**。

> **反例（必须记住）**：如果今天图省事，直接拿重排**替换**掉 `search()`，
> 那么 B 配置就**永久消失**了 —— "重排到底有没有用"这个问题**以后再也答不出来**，
> 因为没有一个"不加重排"的对照。
>
> 类比前端：这不是为了灰度的 feature flag，而是**同一份测试用例要能跑 3 个 build** ——
> 测试矩阵必须能同时构建出三个版本，缺一个就少一组数据。

### 2.2 三条链路的形状

```
                    ┌─ 向量 search(top20) ─┐
用户问题 ─→ retrieve ├─ BM25 search_keywords(top20) ─→ RRF(k=60) ─┬→ 直接取 top5      【B: hybrid】
                    └──────────────────────┘                      │
                                                                   └→ top20 ─→ rerank ─→ top5  【C: hybrid_rerank】

                    ┌─ 向量 search(top5) ─────────────────────────────────→ 返回          【A: pure_vector】
```

三条链路的差别**只在哪一步截断**：

| | 检索 | 融合 | 重排 | 返回 |
|---|---|---|---|---|
| **A** `pure_vector` | 向量 top_k | — | — | top_k |
| **B** `hybrid` | 向量 top_k + BM25 top_k | RRF | — | top_k |
| **C** `hybrid_rerank` | 向量 20 + BM25 20 | RRF | ✅ | top_k |

📌 **最容易写错的一处**：B 的融合窗口是 `top_k`（5），**C 的融合窗口是 20**。
因为重排要吃的就是这 20 条 —— 只给重排 5 条，等于让它在融合已经砍完的结果里重排，
能纠正的空间几乎为零。写代码时这里最容易顺手写成"两处都传 `top_k`"。

### 2.3 判据：这段代码是「等外部」还是「自己算」

先看熟悉的场景：React 里 `fetch` 一个接口，页面不会卡死 —— 因为它在**等外部**。

| | BM25 查询 | 重排推理 |
|---|---|---|
| 干什么 | 把 SQL 发给 PG | 用 CPU 跑 20 次前向 |
| 等待期间事件循环 | **空闲**（可以去处理别的请求） | **被钉住**（没有 await 点） |
| 要 `to_thread` 吗 | **不需要**，`await` 就够 | **必须** |
| 耗时量级 | 毫秒 | **750~820ms** |

一句话判据：

> **这段代码是在"等外部"，还是在"自己算"？**
> **等外部** → `await` 就够；**自己算** → 丢线程池（`asyncio.to_thread`）。

`await session.execute(...)` 的本质是"把 SQL 发出去，然后**等它回来**"，等待期间事件循环
是空闲的，这是 asyncpg 提供的异步能力。而 ONNX 推理里面**一个 await 都没有** ——
它不是在等谁，它在**用 CPU 算**。直接写进 async 函数，事件循环就被这一坨计算钉住 750ms。

### 2.4 超时的真相：保护请求延迟，不保护 CPU

```python
scores = await asyncio.wait_for(
    asyncio.to_thread(_rerank_sync, query, documents),
    timeout=settings.rerank_timeout_s,
)
```

这两层含义**完全不同**，组合起来才既"不卡循环"又"不无限等"：

- `to_thread` —— 把同步计算挪出事件循环
- `wait_for` —— 给这次等待加一个截止时间

⚠ **关键**：超时触发后，**请求会立刻返回，但那个工作线程不会停**。
Python 线程无法被强制中断，它会把这次推理**算完再丢弃结果**。

所以：

> **超时保护的是「请求延迟」，不是「CPU」。**
> 高并发下持续超时，线程池里的线程会越积越多，CPU 反而**更满**。

这一点是面试可讲的：很多人以为 `wait_for` 是"取消任务"，在 asyncio 协程里
确实能取消（`CancelledError` 会在 await 点抛出），但**线程里的同步代码没有 await 点**，
取消无处可抛。

### 2.5 单例 + 双重检查锁

`TextCrossEncoder(...)` 构造时就要加载 1GB 的 ONNX（实测 **751ms**，D18 探针测过 634~789ms）。
不能每个请求加载一次 → **懒加载 + 进程级单例**。

```python
if _model is not None:          # ① 快路径：已加载，不进锁
    return _model

with _model_lock:
    if _model is not None:      # ② 双重检查：等锁期间别人可能已经加载好了
        return _model
    ...
```

**为什么两层都要**：

- 外层那次（①）是为了**性能** —— 加载完成后每次检索都抢一次锁毫无必要
- 内层那次（②）是为了**正确性** —— 等锁的这段时间里，别人可能已经加载好了

**为什么必须加锁**：`if _model is None: _model = load()` 是**复合操作**。
GIL 只保证单条字节码原子，不保证"检查 + 赋值"连起来原子。两个请求同时首次到达时，
两边都会看到 `None`，于是**各加载一份**，内存直接翻倍到 **2GB**。

> 📌 顺带指出：本项目 embedding 那个单例（`get_embedding_provider()`）**没有加锁**。
> 它同样有这个隐患，只是 embedding 只有 90MB、加载快，撞上的概率低。
> 今天这里补上了，那边留着 —— **这是有意为之的取舍，不是遗漏**（等 D20+ 有空再收敛）。

**为什么是 `threading.Lock` 而不是 `asyncio.Lock`**（用户 Q2 的答案）：

`asyncio.Lock` 的获取是 `await lock.acquire()`，要能成立，前提是**脚下有一个正在运行的事件循环**。
而 `_load_model()` 是在 `asyncio.to_thread` 的**工作线程**里被调用的 ——
那里 `asyncio.get_running_loop()` 会直接抛 `RuntimeError: no running event loop`。

选锁的判据可以固化成一句话：**选锁看"谁在哪个执行单元里抢这个资源"** ——
这里竞争 `_model` 的两拨人都是普通 OS 线程，所以用 `threading.Lock`。

**为什么要有失败冷却**（`LOAD_RETRY_COOLDOWN_S = 60.0`）：

模型文件损坏 / 内存不足这类失败，重试基本治不好；而"每个请求都重试一次加载"
等于把一次 751ms 的失败成本**乘以 QPS**，还会把日志刷爆。冷却期内直接快速失败 → 走降级路径。

⚠ **反面也写在注释里**：冷却期内即使问题已被修好（比如你把模型文件补上了），
也要等满 60s 才会恢复。这是"半开自愈"的代价。

### 2.6 降级：降成什么，以及「降级必须可归因」

**降级条件**：模型加载失败 / 推理抛异常 / 推理超时 / 分数条数与候选数不符。
**降级动作**：返回**融合序的前 top_k**（当前最接近可用的序）。

真正重要的是第二句：**降级必须能被观察到**。

```python
for item in results:
    item["retriever"] = "hybrid_rerank" if reranked else "hybrid"
```

`retriever` 由**实际走通的路径**决定，不是由配置名决定 —— 降级时全部标 `hybrid`。

**为什么这条不能省**：如果降级样本被当成 C 配置的成绩算进评测，**C 的分数会被拉向 B**
（因为那批结果的排序本来就是 B 的排序），重排看起来"没用甚至有害"。
评测报告会得到错误结论，**而代码不会有任何报错**。

有了这个标记，评测脚本只要 `group by retriever` 就能看出"这次跑 C 时有多少条其实来自融合序"，
这正是 §6 自测题 Q1 的落点。

### 2.7 三个量纲：`similarity` / `bm25_score` / `rerank_score`

工具层要往文本里写 `（相关度 0.87）`，引用收集器要给前端一个 `similarity` 字段。
这个字段**三条路各有各的来源，口径完全不同**：

| 来源 | 是什么 | 取值范围 | 能跨 query 比吗 |
|---|---|---|---|
| 向量路 | `1 - 余弦距离` | 真·相似度，∈ [0,1] | 能（同量纲） |
| BM25 路 | BM25 分 | **无上界**（本语料 2~3，换语料能到 10+） | 不能（依赖语料统计量） |
| 重排 | cross-encoder 输出的 **logit** | 实测 **+6.47 ~ −9.61**（同一批候选内） | **不能**（D18 实测） |

融合之后，一条结果**可能只被 BM25 命中**（向量路没召回到它），这时它的 `similarity` 就是 `None`。

⚠ 而 `app/tools/retrieval.py` 原来是**直接下标** `item['similarity']`，不是 `.get` ——
所以它会渲染成"**相关度 None**"交给 LLM 看。D19 修了这个：

```python
similarity = item.get("similarity")
score = f"（相关度 {similarity}）" if similarity is not None else ""
blocks.append(f"[{index}] 来源：{source}{page}{score}\n{item['content']}")
```

**整段括号一起省略**，而不是渲染出 "相关度 None"。

**同时刻意不把重排分填进 `similarity`** —— 它是第三个量纲，理由是：
① logit 不可跨 query 比较；② 量纲与 cosine 不同；③ 塞进"相关度"这个位置会让 LLM
**拿不同尺子的数字互相比较**。正确做法是**另开一个键** `rerank_score`。

## 3. 代码逐行解读

### 3.1 `app/config.py`（+44 行）

**① `RETRIEVER_CONFIGS` 放在 config 层，不放 service 层**

```python
RETRIEVER_CONFIGS: tuple[str, ...] = ("pure_vector", "hybrid", "hybrid_rerank")
```

放这里的理由：它是**唯一合法取值清单**，需要被两处消费 ——
settings 的校验器（**启动时**拦）和 `retrieve()` 的显式传参校验（运行时拦）。
放 service 层就拿不到"启动时"这个时机。

**② 三个新字段**

```python
retriever_config: str = "hybrid_rerank"   # 默认走链路最全的一档
rerank_model: str = "BAAI/bge-reranker-base"
rerank_timeout_s: float = 3.0
```

`3.0` 的依据写在注释里：实测 750~820ms（load≤10），忙时 1.4s → 约 3.7 倍余量。
**并明确标注这是"拍的"不是调出来的** —— 不标就等于假装它经过调优（铁律 11 的同族）。

**③ 校验器**

```python
@field_validator("retriever_config")
@classmethod
def _validate_retriever_config(cls, value: str) -> str:
    normalized = value.strip().lower()
    if normalized not in RETRIEVER_CONFIGS:
        raise ValueError(f"retriever_config 只能是 {RETRIEVER_CONFIGS} 之一，收到 {value!r}")
    return normalized
```

`field_validator` 是 pydantic v2 的装饰器（v1 叫 `validator`）：字段赋值后、模型构造完成前
再跑一道自定义逻辑。`@classmethod` 是必须的 —— 校验阶段还没有实例，只能给类。

**为什么必须在这里拦，而不是在 `retrieve()` 里兜底回退**：`.env` 写成 `hybrid_rerankk`
时，兜底回退会让系统**照常启动、静默用另一个策略跑** —— 于是消融实验里那一列的配置是假的，
而且没有任何报错。这与 PRD §3.4 要防的"静默失效"是同一族。

**为什么先 `strip().lower()`**：`Hybrid ` 这种写法该被接受，不值得让人因为大小写去翻日志。
（验证脚本 A4 就是断言这条。）

### 3.2 `app/services/rerank_service.py`（新增 215 行）

**① 三个模块级状态**

```python
_model = None                         # 已加载的模型（None = 还没加载 / 加载失败）
_model_lock = threading.Lock()        # 保护"判断 None + 构造"这个复合操作
_load_failed_at: float | None = None  # 上次失败时刻（用于冷却判断）
```

`float | None` 是 Python 3.10+ 的联合类型写法（等价于 `Optional[float]`）。

**② `_load_model()`** —— 已在 §2.5 讲透。补两点：

- 用 `time.monotonic()` 而不是 `time.time()`：单调时钟不受系统时间调整（NTP 校时、手动改时间）影响，**算时间差必须用它**
- `from fastembed.rerank.cross_encoder import TextCrossEncoder` 是**函数内延迟 import**：D18 实测该子模块**顶层未导出**，不检索就不该加载它

**③ `_rerank_sync()`**

```python
def _rerank_sync(query: str, documents: list[str]) -> list[float]:
    model = _load_model()
    return list(model.rerank(query, documents))
```

`list(...)` **不是可有可无的**：`rerank()` 返回的是**生成器**，不消费它就一次前向都不会跑。
（D18 的探针踩过这个坑 —— 当时测出接近 0 的数，就是因为没消费生成器。）

**④ `rerank()` 的三个分支**

```python
if not candidates:
    return [], False        # 空候选不加载模型：不白付 751ms 的加载成本
```

超时分支与异常分支都返回 `[dict(item) for item in candidates[:top_n]], False`。
`dict(item)` 是**浅拷贝**，目的是**对调用方零副作用** —— 成功和降级两条路径都不会改到
调用方传进来的融合结果，调用方可以放心复用原列表。

异常分支的日志**刻意不带 `exc_info=True`**：

```python
logger.warning("重排失败降级 err=%s 候选=%d query=%r", e, len(candidates), query[:20])
```

降级是**高频可预期事件**（模型没起来时每个请求都走这里），带堆栈会把真正的故障埋进噪音。

**⑤ 排序与打标**

```python
paired = sorted(
    zip(scores, candidates),
    key=lambda pair: (-pair[0], pair[1].get("chunk_id") or ""),
)
...
enriched = dict(item)
enriched["rerank_score"] = round(float(score), 4)
```

排序键第二档 `chunk_id` 的理由和 D17 一样：保证同一份数据两次跑出**同一顺序**，
不让并列的先后交给排序算法碰运气。

**⑥ 分数条数校验**

```python
if len(scores) != len(candidates):
    logger.warning("重排分数条数不匹配 scores=%d candidates=%d，降级", ...)
    return [dict(item) for item in candidates[:top_n]], False
```

⚠ 这是**防御性断言**，防的是"内容 A 配上分数 B"这种**静默错位**：
`zip` 遇到长度不等会按短的截断，不报错，排序就悄悄错了。
宁可降级也不出错误结果。

### 3.3 `app/services/retrieval_service.py`（+121 行）

**① `DEFAULT_TOP_K` 3 → 5**

```python
DEFAULT_TOP_K = 5   # D19 从 3 改成 5：PRD §9.5 消融矩阵 A/B/C 写的都是 top5
```

三条链路口径必须一致，否则"A 用 3 条、C 用 5 条"的对比没有意义。

**② `search()` 补 `retriever` 标记**

```python
"retriever": "pure_vector",
```

D17 只给 BM25 与融合打了标记，**向量路漏了** —— 于是 A 配置在消融里**无法归因**。
三配置都要能自报家门。

**③ `RERANK_CANDIDATE_K = 20`**

为什么是 20 不是 5：见 §2.2。代价也写在注释里：20 条 ≈ 750~820ms，
top10 约省一半 —— **这个数字就是 D19 唯一的延迟旋钮**（D18 已实测：线程数、CoreML
都救不了，唯一的办法是减少候选数）。

**④ `retrieve()` —— 今天的核心**

```python
name = (config or settings.retriever_config).strip().lower()
if name not in RETRIEVER_CONFIGS:
    raise ValueError(f"未知检索配置：{name!r}，可选 {RETRIEVER_CONFIGS}")
```

`config or settings.retriever_config`：`config` 为 None 时取 settings。

后面的 `raise` 是**补 settings 那条路的漏**：pydantic 已经拦住了 `.env` 的写法，
但**评测脚本显式传参**这条路径没被拦 —— 一次手滑就会把某行实验数据记成另一个配置。

三个分支：

```python
if name == "pure_vector":
    results = await search(query, top_k=top_k)
elif name == "hybrid":
    results = await hybrid_search(query, top_k=top_k)
else:  # hybrid_rerank
    fused = await hybrid_search(query, top_k=RERANK_CANDIDATE_K)   # ← 20，不是 top_k
    results, reranked = await rerank(query, fused, top_n=top_k)
    for item in results:
        item["retriever"] = "hybrid_rerank" if reranked else "hybrid"
        item.setdefault("rerank_score", None)
```

`setdefault` 是 **dict 的方法（Python 内置，不用 import）**：键不存在就设成 None，
存在就保留原值。这里的作用是让 **C 配置的键集恒定** ——
降级时结果来自融合（本来没有 `rerank_score`），补一个 None
可以让上层做直接下标时不会 `KeyError`。

**返回结构三态一致**（这是"配置化"能成立的前提）：

| 键 | A | B | C |
|---|---|---|---|
| `chunk_id` / `content` / `source` / `page_ref` / `similarity` / `retriever` | ✅ | ✅ | ✅ |
| `rrf_score` / `vector_rank` / `bm25_rank` / `bm25_score` | — | ✅ | ✅ |

```python
    raise RuntimeError("注入的推理故障")

finally:

```

`finally` 里的还原不能省：E 段后面还有 F/G/H 三段，不还原就全被污染。

真实数据这次**没撞到** `similarity=None`（24 片语料下向量 top20 恰好覆盖了
BM25 命中的那 3 片）。所以脚本把一条 `similarity=None` 的结果**直接注进工具层**：

```python
    return [{"chunk_id": "fake-1", "content": "伪造片段：仅被 BM25 命中…",

             "similarity": None, "retriever": "hybrid", "bm25_score": 3.2}]
```

在工具层模块里 `retrieve` 已经是一个独立的名字，改源模块的不会影响它。
这是 Python 打补丁最常见的坑。

"抖动无意义"，而不是打印一个看起来很吓人的数字。

## 5. 面试考点

**Q：你们检索链路的架构是什么？**
> 三配置可切的混合检索：向量 + BM25 双路各取 20 候选 → RRF(k=60) 按**名次**融合 → 交叉编码器
> 对这 20 条精排 → top5 喂 LLM。配置化不是为了灰度，是为了做消融实验 ——
> A/B/C 同一评测集跑三遍，才能回答"重排到底有没有用"。

**Q：RRF 已经融合了，为什么还要重排？**
> 因为 RRF **只吃名次、完全看不到内容**。它能仲裁"两路意见不一致"，
> 却纠正不了"两路一致但都错了" —— 两边都把某条排前面时，RRF 只会顺着它。
> cross-encoder 把 `[query, 文档]` 拼成一条序列逐层交叉，能读出内容层面的相关性。

**Q：重排为什么用 `to_thread`？**
> 判据是"等外部还是自己算"。ONNX 推理里**一个 await 都没有**，它是用 CPU 算 750ms，
> 留在事件循环里会把整个进程的请求都钉住。BM25 不需要，因为 `await session.execute`
> 是"等 PG 回来"，等的时候事件循环是空闲的。

**Q：超时了任务会被取消吗？**
> 请求会提前返回，但**线程不会停** —— Python 线程无法被强制中断，它会算完再丢弃结果。
> 所以超时保护的是**请求延迟**，不是 CPU。持续超时会让线程池越堆越多。

**Q：重排失败了怎么办？**
> 降级返回 RRF 融合序的前 5，不让请求 500。关键是**降级必须可归因** ——
> 打标走"实际路径"而不是"配置名"，降级时标 `hybrid` 而不是 `hybrid_rerank`。
> 否则评测时降级样本被算进 C 的成绩，C 会被拉向 B，得出"重排没用甚至有害"的错误结论，
> **而代码不会有任何报错**。

**Q：重排模型加锁了吗？**
> 加了，双重检查 `threading.Lock`。不加锁的话并发首次加载会**加载两份 1GB 模型**，
> 内存翻倍。用 `threading.Lock` 而不是 `asyncio.Lock`，是因为它在 `to_thread`
> 的工作线程里执行 —— 那里没有事件循环，`await` 不了。

**Q：重排的成本是多少？**
> 20 候选 @300 字/片 ≈ **750~820ms**（load≤10，本机实测）。这是链路里最大的一块串行成本。
> 而且没有免费的提速开关：线程数 4→1.09×、10→1.12×；开 CoreML 反而 **5.06s，慢约 7 倍**
> （首次编译开销）。**唯一的旋钮是减少候选数**（top20→top10 约省一半）。

## 6. 自测题（先自己做，再看参考答案）

### Q0（本日三问 · 已答）

**Q0-1 降级归因**：重排超时降级后返回 RRF 融合序前 5。评测脚本若**不知道降级发生了**，
把这批结果算作 C 的成绩 —— 会得出什么错误结论？分数往哪偏？
**Q0-2 线程模型**：BM25 也是同步的，为什么不需要 `to_thread`，重排必须？
**Q0-3 similarity**：`hybrid_rerank` 返回的 `similarity` 该给什么？能填重排分吗？

<details><summary>答案</summary>

**Q0-2（用户答对）**：`_load_model` 在 `to_thread` 的工作线程里执行，那里没有事件循环，
`asyncio.Lock` 需要 `await` 才能获取，根本跑不起来。
更完整的表述见 §2.3 判据（等外部 vs 自己算）+ §2.5。

**Q0-1**：会得到"重排让效果变差"的错误结论，分数**往 B 的方向偏**（偏差方向是让重排显得有害）。
两层原因：① **不可比** —— A/B 是在全部查询上算的，C 只统计了"重排成功"的子集，分子分母都换了；
② **选择性偏差** —— 降级主要是超时引起的，而超时概率跟候选文档长度走
（D18 实测近线性：75字 203ms / 300字 785ms / 450字 1247ms），所以被排除的恰恰是"文档长/候选重"
的查询，剩下 70% 是**被筛过的轻量样本**，C 在它们身上反而**偏高** —— 而如果脚本反过来
**只信降级样本**（把它们当 C 的成绩），C 就被拉向 B。
正确口径：**端到端口径**（分母固定为全部查询，降级按降级后实际结果计分）用于回答
"系统表现"；**条件口径**（只算重排成功批次）用于回答"重排器本身多好"，
且必须报成"重排成功率 × 条件准确率"两个数，不能叫"系统的准确率"。

**Q0-3**：`similarity` **只能给真的相似度**（向量路的 `1 - 余弦距离`），融合后
"只被 BM25 命中"的条目给 `None`（工具层此时整段省略，见 §2.7）。
**不能填重排分**：重排分是 logit，① 不可跨 query 比较 ② 与 cosine 不同量纲
③ 会让 LLM 拿不同尺子的数字互相比较。重排分走**单独的键** `rerank_score`。

</details>

### Q1（推演 · 更刁的一层）
真实评测里 C 配置有 30% 的查询走降级。如果评测脚本 `group by retriever` 之后
**只统计 `retriever == "hybrid_rerank"` 的那些**，会得出什么新问题？这个成绩和 A/B 还能直接比吗？

<details><summary>答案</summary>

**不能直接比。** 这是"条件口径"冒充"端到端口径"。

① **分母变了**：A/B 是在全部查询上算的，C 只算了 70%。分子分母都换了。
② **偏差不是随机的**：降级主因是超时，而超时概率随候选长度增长 → 被排除的偏向"长文档/重候选"
的查询 → 剩下的 70% 是轻量样本，C 的成绩会**偏高**（让重排显得有用）。
③ **成绩拼接不了**：不能把"70% 成功批次的成绩"和"30% 降级批次的成绩"加权平均后
当成 C 的成绩 —— 那两个数回答的是不同问题。

正确做法：C 的成绩用**全部查询**算（降级样本按实际返回结果计分），这样才和 A/B 同分母。
"只算成功批次"的数**另有价值**（衡量重排上限），但要**单独报**，并且明确标注
"重排成功率 = 70%，重排条件准确率 = X"。

</details>

### Q2（术语/接口）
`setdefault` 是什么？为什么 `retrieve()` 要给 C 分支的结果补 `rerank_score = None`？

<details><summary>答案</summary>

`setdefault(key, default)` 是 **dict 的内置方法**（不用 import）：键不存在就设为 `default`，
存在则**保留原值**并返回它。

这里的作用是**让 C 配置的键集恒定**：降级时结果来自融合结果（本来没有 `rerank_score`），
补一个 `None` 保证上层做**直接下标** `item["rerank_score"]` 时不会 `KeyError`。
这和工具层用 `.get("similarity")` 而不是 `item["similarity"]` 是同一个防御思路 ——
只不过这里选择"补齐键"而不是"改调用方"。

</details>

### Q3（对比）
如果把重排从"本地 ONNX"换成"调远程 rerank API"，`_rerank_sync` 的哪一条性质会消失？
`to_thread` 还要不要包？降级设计要不要改？

<details><summary>答案</summary>

**消失的性质**："**自己算**"（同步 CPU 密集、无 await）→ 变成"**等外部**"（网络 IO）。

**`to_thread` 不要了**（包了是反模式）：应该用 `httpx.AsyncClient` 直接 `await`。
唯一例外是坚持用同步的 `requests` 库 —— 那**必须**继续包，但那是拿线程池换并发度。
判据：库自带 await 能力 → 不包；只有同步 API → 包。

**降级要改，五处**：
| 项 | 变化 | 后果 |
|---|---|---|
| 失败模式 | **+ 429 / 5xx / 网络抖动 / 鉴权失败** | 降级条件要扩，动作不变 |
| 超时语义 | httpx 支持 cancellation，**连接能真取消** | "线程停不下来"那句要重写 |
| 重试 | 需要退避重试 | 与"超时保护延迟预算"**冲突**，要划一条线 |
| 成本 | 固定 → **按请求计费** | 候选数 20 从"延迟旋钮"变成"**延迟+成本双旋钮**" |
| 顺序 | 远程**常常不保证返回顺序** | `zip(scores, candidates)` 会**静默错配**（分数贴到别的片段上）→ 必须按 `chunk_id` 对齐 |

单例与锁的位置也变：不再需要模型单例，但需要 `httpx.AsyncClient` 单例（连接池复用），
锁的语义从"防止加载两份"变成"防止建两个连接池"。

</details>

### Q4（数值推演）
`RERANK_CANDIDATE_K` 从 20 改成 10，按 D18 的实测比例估算 C 的净成本变成多少？为什么这个改动**不能**顺手做？

<details><summary>答案</summary>

D18 实测：候选数 4× → 耗时 4.38×（近似线性）。所以候选从 20 → 10，
净成本约从 **759ms → ≈380ms**（省一半）。

**不能顺手做**，因为它是**精度与延迟的权衡**，必须由 D20 的评测数据决定：
重排的价值就在"从一批候选里挑出更好的 5 条"，候选窗口越小，**召回上限**越低 ——
正确答案如果没被 RRF 排进前 10，重排再准也救不回来。
所以"省一半延迟"的代价是"可能丢掉正确答案"，这是一个**需要用评测集量化**的决定，
不是拍脑袋的数。**改动前必须先把 `RERANK_CANDIDATE_K` 造成的精度损失测出来。**

</details>

### Q5（排障）
验证脚本退出时打出 `RuntimeError: greenlet is being finalized` + `non-checked-in connection`，
但**所有断言通过、退出码 0**。你怀疑两个方向：① 超时丢弃的工作线程 ② 重排模型。
怎么最快定位？

<details><summary>答案</summary>

**造两个最小探针，把变量隔离。**

探针 1（测"超时丢弃线程"假设）：一条最少代码的 `asyncio.wait_for(to_thread(sleep), timeout=0.1)`
+ `engine.dispose()` + `asyncio.run()`。跑出来**没有** greenlet 错误 → 假设 ① 排除。

探针 2（测"重排模型"假设）：什么都不做，只跑一次真实 DB 查询 + 一次重排，再
`engine.dispose()`。跑出来**没有**错误 → 假设 ② 排除。

两个都排除后，剩下的唯一解释就是**脚本自身的资源管理**。回去看缩进 ——
清理段的第二条 `count` 查询**缩进少了一层**，写在 `async with async_session_factory() as session:`
**块外**面 → session 已 close，再 `execute` 会从池子里**重新借一条连接且没人归还** →
退出时连接池检查发现非签入连接。

**教训**：告警与断言是两条独立的信号通道 —— 断言全绿 + 退出码 0 **不代表**没有资源泄漏。
而且注意"缩进少一层"在 Python 里**不是语法错**，它只是把语句挪到了另一个作用域，
静态检查也抓不住。

</details>

### Q6（诚实边界）
今天的验证用了**合成语料**（脚本自己造的、8 篇 × 3 片）。这个验证**不能**证明什么？

<details><summary>答案</summary>

**不能证明"重排提升了效果"。**

合成语料是固定模板 + 固定 seed 拼出来的，它的语义分布是**人造的**：
同一主题的句子重复、关键词分布可控。它只能证明：

① 链路**通**（三配置能跑、能产出结果）
② 口径**对**（字段契约、`retriever` 标记、降级可归因）
③ 成本**真实**（延迟是真在 CPU 上跑的，与语料语义无关）

但它**不能**回答"重排到底有没有用" —— 那需要 D20 的评测集（真实语料 + 标注答案 + 指标）。
这一点必须主动写出来，否则"50/50 通过"会被误读成"重排有效"。

另外还有一个**更细的边界**：合成语料的 8 篇里关键词是**刻意分布**的，
所以"BM25 命中集合可预期"这个性质**是我们设计出来的**，真实语料里
关键词命中集合会随文档数增长而快速膨胀。

</details>

### Q7（回看 D17 的平局问题）
D17 的 `fuse_rrf` 用了**五档** `sort_key`（分数 → 提名路数 → 最好名次 → 向量名次 → `chunk_id`）。
今天的重排排序只用了**两档**（分数 → `chunk_id`）。为什么少了几档？

<details><summary>答案</summary>

因为**分数的结构不一样**。

RRF 的分数是 `Σ 1/(k+rank)`，取值来自一个**极小的离散集合** ——
名次交换的两条文档（`1/61+1/63` 与 `1/62+1/60`）会算出**精确相等**的浮点数
（D17 实测撞到 `0.032522 == 0.032522`）。所以平局是**结构性**的，必须靠后面三档
（提名路数 / 最好名次 / 向量名次）表达"两条分数相同的，谁更该在前面"。

重排的分数是 cross-encoder 输出的**连续 logit**，20 条里精确撞分的概率极低。
所以第二档 `chunk_id` 只需要保证**确定性**（同一份数据两次跑出同一顺序），
不需要表达"谁更该在前面"。**档数不同是因为要解决的问题不同**，不是简化。

</details>

### Q8（设计判断）
为什么 `_load_model()` 的失败冷却设成 60 秒，而不是"失败后永久不重试"？
反过来，为什么不设成"每次请求都重试一次"？

<details><summary>答案</summary>

**不能永久不重试**：模型文件损坏 / 内存不足这类原因**有可能被修好**
（补文件、释放内存、挂载磁盘），永久熔断意味着修好了也必须重启进程才能恢复。

**不能每请求重试**：把一次 751ms 的失败成本**乘以 QPS**，且日志被刷爆。

**60 秒 = 半开自愈**：冷却期内快速失败走降级，冷却期过后允许再试一次。

⚠ 注意反面：冷却期内即使问题已修好，也要等满 60s 才恢复 —— 这是这个设计的**代价**，
不是缺陷。D18/D19 都没有对这个值做过调优，它和 `rerank_timeout_s` 一样属于
"先给个保守值，等 D20+ 有数据再校正"。

</details>

## 7. 踩坑记录

### 坑 1：断言区间是我**估算错**，不是断言太严（差点放宽区间）

B2 原本断言每篇原文 `600 <= len <= 900`，实测只有 **561~631 字**，直接红了。

第一反应是"改成 `500 <= len`"。**这个改法错在**：B 段的全部意义就是
"必须用**生产尺寸**的输入测" —— 放宽区间等于默认"短一点也行"，
D18 已经在这里栽过一次（拿 12 token 的句子测出 2.8ms，低估约 15 倍）。

**正确修法**：改**生成器**（从"固定 26 句"改成"拼到 ≥700 字再停"），
让输出真的落在生产尺寸上，断言不动。
改完实测 703~726 字，恰好切成 3 片 300 字。

> 教训：断言红了先问"是数据错还是我算错"，**不要先动断言**。

### 坑 2：`async with` 块外复用 session —— 真 bug，但**断言全绿**

清理段的第二条 `count` 查询**缩进少了一层**，写在了 `async with ... as session:` **块外面**。

后果：session 已经 close，再 `execute` 会从池子里**重新借一条连接且无人归还** →
退出时打出 `RuntimeError: greenlet is being finalized` + `non-checked-in connection`。
**断言 50/50 全绿、退出码 0，只有告警。**

排障过程（用了两个最小探针，把变量隔离）：

1. 怀疑"超时丢弃的工作线程" → 写探针：最小 `wait_for(to_thread(sleep), timeout=0.1)` + `dispose()`
   → **无错误**，排除
2. 怀疑"重排模型" → 写探针：只跑真实 DB 查询 + 一次重排 → **无错误**，排除
3. 剩下唯一解释：脚本自身资源管理 → 回头看缩进，命中

> 教训：① 告警与断言是**两条独立信号**，全绿不代表没泄漏；
> ② "缩进少一层"在 Python 里**不是语法错**，静态检查抓不住；
> ③ 排障要**先隔离变量**（每个探针只变一个因素），不要一上来就读代码猜。

### 坑 3：库里只有 1 篇 / 3 片 / 62~73 字 —— 测不出链路

**3 个候选、60 多字**，根本测不出"top20 → 重排 → top5"，也测不出生产尺寸的延迟。

三个选项：**(a) 脚本自建自清** / (b) 手工造一批长期入库 / (c) 只在现有 3 片上做。

选 **(a)**，理由是：今天的目标是"链路接通"，评测语料是 D20 的事 ——
(a) 既不欠账也不污染全库。代价是**样本是造出来的**（见 Q6 的诚实边界）。

### 坑 4：`B 与 C 的融合窗口不同` 是本日最容易写错的一行

写 `retrieve()` 的 C 分支时，顺手写 `hybrid_search(query, top_k=top_k)` 是**最自然的错**——
而且它**不会报错**：链路照跑，重排照做，只是重排的输入从 20 条变成 5 条，
"能纠正的空间"几乎归零。表现为"重排看起来没什么用"。

所以专门加了断言 **C7「融合窗口可独立控制（C 用 20 进重排，B 只用 5）」**。
**凡是"错了也不报错、只是效果变差"的地方，都必须有断言钉住。**

### 坑 5：monkeypatch 打在「定义处」而不是「使用处」

F5/F6 要注入一条 `similarity=None` 的结果。第一反应是 patch
`retrieval_service.retrieve` —— **无效**。

原因：工具层写的是 `from app.services.retrieval_service import retrieve`，
这是**名字绑定**：工具层模块里 `retrieve` 已经是一个独立的名字，改源模块的不影响它。
正确做法是 patch **`tool_module.retrieve`**（工具层模块里的那个名字）。

> 这是 Python 打补丁最常见的坑，D17/D18 的注入也都遵守"打在使用处"。

### 坑 6：脚本 docstring 写"七段"，实际是八段

`A~G` 写了七段，但代码里有 `A~H` 八段（H 是清理段，漏在 docstring 里）。
**提交前修掉了。** 这类"文档与代码不同步"看着是小事，但下次有人按 docstring
判断"清理逻辑在哪一段"时会找不到。
