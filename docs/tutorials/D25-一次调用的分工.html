一次 MCP 调用里，谁干了哪一段

D25 · 全部结论来自 2026-10-01 本机实测（mcp SDK 2.2.0）· 报文与输出均为真实抓取，非示意
一句话结论

你的模型 —— 「Server 是装工具的盒子 → Client 传工具名和参数 → Server 按名字调对应工具 → 返回结果」 —— 主干完全正确。差的是三处：名字是谁给的、 Server 还会先校验一道参数、失败也走同一条回程。 另有一处措辞要松一下：「多个」不是必要条件 —— 只装 1 个工具的 Server 照样是 Server。

一、你的四步 → 真实的六步

你描述的实测真实情况差在哪
Server = 装了多个工具的工具箱 ✅ 本质正确 「多个」不是必要条件：server_one_tool.py 只装 1 个工具，照样完整跑通（见本文 §2）
（你没提到） Server 是被 Client 启动的子进程，启动后就常驻，等 stdin 上的下一行 少了生命周期：它会启动失败、会中途崩、退出时必须清理
（你没提到） Client 先发 tools/list 问清单 —— 工具名是从这里来的 ★ 少了「名字的来源」。这一条就是 MCP 的全部价值所在（§2 专门证它）
Client 传入要调的工具 + 参数 ✅ tools/call，参数是 {name, arguments} 机械上正确。但决定调哪个的不是 Client，是模型（§4 说清三者分工）
Server 按工具名和参数调对应工具 ✅ 内部就是一张 名字 → 函数 的字典（§3 把这张表打出来了） 只需补一个实现细节：查表前先校验参数
（你没提到） Server 按 JSON Schema 校验参数，类型不对当场拒 ★ 少了这一道。echo(text=123) 被拒即证据（§5）
返回正确结果 ✅ 但成功和失败都走同一封 result，失败只是把 isError 置真 回程只有一条，不是「成功走一条、失败走另一条」

注：tools/list / tools/call 是 MCP 定义的两种「方法名」； JSON Schema 是一种用 JSON 描述「这个函数该收什么参数」的格式，Server 用它把函数的参数类型告诉外部。

二、实验：一个「零硬编码」的客户端

先说为什么要补这个实验 —— 我上一轮的证据是不够的。

上一轮的抓包脚本 client_probe.py 第 44 行写的是 await session.call_tool("current_time", {}) —— 工具名是我写死在客户端代码里的。所以那一轮虽然打了 tools/list， 但并不能证明「名字是从 Server 来的」：名字本来就在我手上。

补的做法是写一个代码里不出现任何工具名的客户端，名字一律从 tools/list 的返回值里取；参数则按每个工具自报的 inputSchema 现造（只求合法，不关心语义）。

先自证：这个文件里真的没有工具名

$ grep -n "current_time\|add\|echo" client_zerocode.py
（无输出 —— 一次都没命中）

然后：同一份文件、一字未改，指向两个不同的 Server

指向 只装 1 个工具的 Server

### 本次连的 Server 文件：server_one_tool.py
  Server 自报家门 : demo-one-tool v0.0.1
  ① tools/list 拿到 1 个工具名：['current_time']
  ② call current_time  args={}
                       is_error=False
                       返回: 2026-10-01T19:34:27+08:00

指向 装 3 个工具的 Server

### 本次连的 Server 文件：server_three_tools.py
  Server 自报家门 : demo-three-tools v0.0.1
  ① tools/list 拿到 3 个工具名：
       ['current_time', 'add', 'echo']
  ② call current_time  args={}          -> 19:34:30
  ② call add           args={'a':7,'b':7} -> 14
  ② call echo          args={'text':'hello'} -> 收到：hello
这三行结论由数据直接给出：
  • 客户端脚本不知道 add 要两个整数、echo 要一个字符串 —— 它只是照 Server 给的 inputSchema 造了 {'a':7,'b':7} 和 {'text':'hello'}，就调通了。
  • 换一个 Server，客户端一行都不用改 —— 这正是 PRD §9.9 那句 「接入新 server 不需要修改 Agent 代码」的可运行证据，也是 PRD S10 要证明的能力。
  • 所以：工具名不是我写的，是 Server 在 tools/list 里告诉客户端的。

三、打开箱子：Server 内部那张「名字 → 函数」的表

「Server 根据工具名去调相应工具」这句话，落到实现上是什么？把 Server 对象的内部 工具登记表打印出来看（这一步叫内省：程序在运行时读取自己的结构）：

server 对象   : MCPServer  name='demo-three-tools'
tool_manager  : ToolManager
  公开方法   : ['add_tool', 'call_tool', 'get_tool', 'list_tools', 'remove_tool', ...]

_tools: dict，共 3 条
  'current_time' -> 登记项类型 Tool  里面挂的函数 = <function current_time at 0x10c2122a0>
  'add'          -> 登记项类型 Tool  里面挂的函数 = <function add at 0x10b618cc0>
  'echo'         -> 登记项类型 Tool  里面挂的函数 = <function echo at 0x10a7c54e0>

所以「路由」不是什么复杂机制，就是一次字典查表： 收到 {"name": "add", "arguments": {"a": 7, "b": 7}} → 用 "add" 查出那个函数对象 → 把 JSON 里的 {"a":7,"b":7} 反序列化成 Python 的 a=7, b=7 → 调用它 → 把返回值再序列化回 JSON。

那张表是装饰器写进去的：源码里每个函数上方的 @server.tool(...) 就是「把我登记进那张表」的意思。（装饰器 = Python 里包在函数定义上方的一行 @xxx， 它在函数被定义的那一刻就执行，用来改写或登记这个函数。）

四、四个角色各管哪一段（这是面试最容易被追问的一层）

角色在本项目里是谁它负责的那一段
模型
决定		 DeepSeek（经 LLM Gateway） 决定「调哪个工具、传什么参数」（选择权）。看到工具清单后自己选，这一步没有任何代码写死。
规范原文（Tools 页）："Tools in MCP are designed to be model-controlled, meaning that the language model can discover and invoke tools automatically"
Host（宿主）
放行 + 编排		 FastAPI 后端进程（app/）
不是 React 前端		 规范 Architecture 页列了 6 条：创建并管理多个 Client 实例 · 控制连接权限与生命周期 · 执行安全策略与「用户同意」要求 · 处理用户授权决定 · 协调 AI/LLM 与 sampling · 汇总跨 Client 的上下文。
→ 一句话：它不选题，但它决定「哪些工具能被模型看见」，并且能否决 （规范原文："there SHOULD always be a human in the loop with the ability to deny tool invocations"； Applications SHOULD: Provide UI that makes clear which tools are being exposed to the AI model）
本项目里它还管一件具体的事：启动并管理 Server 子进程的生命周期
Client（连接器）
搬运		 D27 要写的 app/services/mcp_client.py 1 个 Client 对象 ↔ 1 个 Server（规范原文 "Each client is created by the host and communicates with exactly one server"）。 职责：每个请求都带上协议版本与能力 · 双向转发消息 · 管理订阅与通知 · 维持 Server 之间的安全边界。
→ 一句话：它不判断，只管这一条通道：发 tools/list、 把模型的工具调用翻译成 JSON-RPC 发出去、把回包翻译回来。
D27 还要在这里把清单转成 LangGraph 能认的工具定义（生成存根 → 注册进 Tool Registry）
Server
执行		 D26 自研库存服务 / D27 的 Harness ① 启动后常驻，在 stdin 上读、往 stdout 上写； ② 报目录（tools/list）； ③ 按名字查表 → 校验参数 → 执行 → 包装结果
诚实边界：本次演示里没有接 LLM —— 那一跳是我用脚本按「把清单里的工具全调一遍」走的。 所以「模型决定调哪个」这一句是架构层面的说明，不是本文实测出来的。 真实链路里由 ReAct 循环中的模型决定，D27 接入时才会有实测。
本节 2026-10-01 修正：原版把 Host 与 Client 合成了一行 （「Host / Client · 搬运 + 管理」），结果是两层的职责边界被压平 —— 复述时很容易把「决定调哪个工具」挂到 Host 头上，而那是模型的活。 现按规范 Architecture 页把两者拆开。原版那四句（启动子进程 / 发 tools/list / 翻译成 JSON-RPC / 自己不判断）仍然成立，只是分属两层，已并入上表。

一句话记法：模型有选择权（调哪个）， Host 有放行权与否决权（哪些能被看见、能不能执行）， Client 只有搬运（不判断），Server 只管执行。

五、出错也走同一条回程

实测两种「出错」，没有一个抛异常给客户端：

tools/call {"name":"echo",  "arguments":{"text": 123}}     ← 参数类型错
  Tool 'echo' rejected arguments: ['text']
  → 响应 OK  isError=true   content.text =
       Error executing tool echo: 1 validation error for echoArguments
       text: Input should be a valid string [input_value=123, input_type=int]

tools/call {"name":"not_exist_tool", "arguments":{}}        ← 工具根本不存在
  Tool 'not_exist_tool' failed: 'Unknown tool: not_exist_tool'
  → 响应 OK  isError=true   content.text = "Unknown tool: not_exist_tool"

两种错都装在一封成功的 JSON-RPC 响应里返回，只是把 isError 置真。 这是有意的设计：错误要让模型看得见，模型才能读出 「参数该是字符串而不是数字」并改对重试 —— 这是 Agent 自修正循环的关键一环。

每条响应还带 structuredContent：同一个值印两遍 —— content 是给人/模型读的自然语言，structuredContent 是给程序读的结构化值。

边界：本次只测到「工具执行错误」这一支。 协议层错误（响应里带 JSON-RPC error 对象，例如协议版本不支持）没有测到， 此处不下结论。
