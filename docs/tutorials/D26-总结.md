## §2 名词先注解（全部在此，不外链）

这一节的存在理由：下面 §3 起会连续用到这些词。**不先定义就用，等于用一堆我不确定你熟不熟的东西解释新东西。**

| 名词 | 它是什么 | 它解决什么问题 |
|---|---|---|
| **MCP** | Model Context Protocol，一套**让模型能调用外部工具**的开放协议 | 在此之前，"给模型接一个工具"每家写法都不一样。MCP 把**客户端与工具服务之间的对话格式**统一了 |
| **Server（MCP 语境）** | **一个装着工具的独立进程**，通过 stdio / HTTP 对外提供工具 | 让工具可以**离开主程序**单独部署、单独升级，甚至由别人提供 |
| **Client（MCP 语境）** | 发起连接、调用工具的那一方（通常是 Agent 进程） | 它不需要知道工具怎么实现，只需要知道**有哪些工具、参数长什么样** |
| **Host** | 掌管 Client 与 Server 生命周期的那个程序（比如 IDE、Agent 主进程） | Server **不决定自己活多久**，谁起它就归谁管（§3 第 7 步、§7.3 G 段） |
| **JSON-RPC 2.0** | 一种**极简的远程调用协议**：一个 JSON 对象 = 一次请求或一次响应 | 它只规定"请求长什么样、响应长什么样"，不含传参风格、不含鉴权。MCP 在它上面加自己的规矩 |
| **stdio** | standard input/output，进程的标准输入输出 —— 即 stdin / stdout 两条管道 | 让两个进程**不需要网络**就能对话。MCP 的本地传输就走它 |
| **fd（文件描述符）** | 操作系统给每个进程维护的一张表，**下标 0/1/2 分别代表 stdin/stdout/stderr** | 进程读写"标准输入输出"其实是在读写这几个下标。**改这张表的下标指向，就能改变输出的实际去向**（§4 的关键） |
| **inode** | 文件系统里一个文件的唯一编号 | 判断"两个 fd 是不是指向同一个东西"最靠得住的依据就是比 inode（§4 就是这么取证的） |
| **管道（pipe）** | 一根单向的数据通道，写进一端、从另一端读出来 | 一个进程的 stdout 接到另一个进程的 stdin，两个进程就串起来了 |
| **EOF** | End Of File，"没有更多数据了"的信号；管道写端全关闭时读端会读到它 | Server 靠它知道"客户端走了"（§3 第 7 步） |
| **握手（handshake）** | 正式对话前先互相报身份、报能力、谈定规矩的那两封开场报文 | 让双方在开始干活前先对齐"我会什么、你支持什么" |
| **两代协议** | MCP 协议分了两代：**Legacy**（≤ `2025-11-25`，开场发 `initialize` **握手**）与 **Modern**（`2026-07-28` 起，**取消握手**）。同时支持两代的实现叫 **Dual-era** | Modern 把"版本 / 身份 / 能力"从开场握手改成**每次请求都自带**（见 §5.4 的 `_meta`），省掉一轮往返 |
| **`_meta`** | JSON-RPC 报文里一个**协议自己用的保留字段**（`params._meta`），业务数据不放这儿 | Modern 代用它携带协议版本、客户端身份、客户端能力 —— 每次请求都带 |
| **`inputSchema` / `outputSchema`** | 描述"这个工具要什么参数 / 返回什么结构"的 **JSON Schema**（一种用 JSON 写的"数据格式说明书"） | 让客户端**在调用前**就知道该怎么传参，不用靠猜或靠读服务端源码 |
| **`anyOf`** | JSON Schema 里的"满足其中之一即可"。本项目里 `int \| None` 生成的就是 `anyOf:[{integer},{null}]` | 用来表达"这个参数可省略" |
| **`content`（工具返回的第一层）** | 给**人 / 模型读**的一层：一个数组，里面是文本块 | 模型是靠这一层理解结果的 |
| **`structuredContent`（第二层）** | 给**程序读**的一层：干净的结构化数据 | 上层代码不用去解析自然语言文本 |
| **`isError`** | 工具返回里的一个布尔标记，`true` 表示"这次调用业务上失败了" | 它让失败**能被模型看见**，模型据此可以自己改参数重试（§8） |
| **装饰器（decorator）** | Python 里那个 `@` 开头的写法。它在**函数定义的那一刻**执行，用来"改造/登记"这个函数 | 本项目用它把函数注册进服务、并**自动生成**工具的描述与参数 schema（§6） |
| **docstring** | 函数体开头那个三引号字符串 | 在 MCP 里它**不只是注释** —— 它会被当成工具描述发给模型（§6） |
| **AST** | Abstract Syntax Tree，把源码解析成树形结构后的形态 | 用它可以精确地问"这个文件 import 了什么"，而不是用文字搜索（注释里出现同样的词就不算） |
| **Pydantic** | Python 的参数校验库。本项目用它做请求参数校验 | 参数类型不对会在**进入函数之前**就被拒掉（§8） |
| **pid** | 进程号。**由内核分配**，不是进程自己报的 | 验证"它是不是独立进程"时，必须用内核给的号，不能用对方自报的（§7.3 G 段） |
| **会话首领（session leader）** | 被单独放进一个新会话的那个进程（`os.getpgid(pid) == pid` 时成立） | 它是"这个进程是被独立放出来的、不是随便挂在谁底下"的证据 |

## §3 一次工具调用，在 Server 内部走七步

把 Server 想成**一个坐在管道边上的柜台**。它不主动做事，只对送进来的纸条作反应。一次 `tools/call` 进来，发生七件事：

| 步 | 做什么 | 为什么必须在这一步 |
|---|---|---|
| 1 | 从 **stdin 读一行**，解析成 JSON | 报文是**一行一个** JSON 对象（换行分隔），不是一个大 JSON 数组。所以"读一行"就是一个完整请求的边界 |
| 2 | 看 `method` 字段，决定走哪个分支 | 同一个通道要同时服务 `initialize` / `tools/list` / `tools/call` 等**好几种**请求。`method` 是唯一的分流依据 |
| 3 | 拿 `params.name`（工具名）**去查一张字典** | 见下方说明 —— **这一步是"路由"的全部内容** |
| 4 | 用该工具的 `inputSchema` **校验参数** | 参数不合规必须在**进函数之前**拦下，否则错误会以"函数内部的奇怪异常"形式冒出来，很难归因 |
| 5 | 调**真正的 Python 函数** | 到这步才执行你的业务代码 |
| 6 | 把返回值包成**两层**：`content`（给人/模型读） + `structuredContent`（给程序读） | 同一批数据、两个用途。见 §8 的空结果与 §7.3 的 D5 断言 |
| 7 | 把结果写回 **stdout**，**带上和请求相同的 `id`** | 因为 stdout 上可能同时有多条请求在飞，`id` 是唯一的配对依据 |

### 第 3 步展开：所谓"路由"，就是一次字典查表

Server 内部存着一张字典（`ToolManager._tools`）：**键 = 工具名，值 = 一个 Tool 对象**，Tool 对象上挂着真正的 Python 函数。

这张表**不是在运行时动态拼的**，而是由 `@server.tool()` 装饰器在**函数定义被解释到时**就写进去了。
所以"路由"这一步没有任何魔法 —— **一次 `dict` 查表**。

> ★ **这一步是整条链路里最容易被误解的地方。** 常见的想象是"Server 内部有个 if-else 判断工具名"，
> 或者"客户端知道自己要调哪个函数"。都不是。客户端只知道**名字**（而且这个名字是它从 `tools/list` 拿到的，不是写死的），
> Server 拿名字查表。**"名字 → 函数"的映射完完全全在 Server 这一侧。**

### 第 7 步展开：它为什么"不决定自己活多久"

`server.run(transport="stdio")` 这行会**一直阻塞**，直到 stdin 上读到 **EOF**（客户端断开）才返回。
实测（`/tmp/d26_probe/`）：Client 一断开，进程在 **0.94s / 0.08s** 内正常退出。

→ **生命周期归 Host。** 这不是设计缺陷，是刻意的：让 Server 成为可以被随时起停的**被调用方**，
而不是一个需要自己管自己的常驻服务。

## §4 ★ 取证一：`print` 到底会不会污染协议流？

### 4.1 我原本准备讲什么

原理环节我原本准备讲一条"经典坑"：**往 stdout 打印会污染协议流**。
理由听起来完全成立：stdout 是协议通道，你在上面打一行 `DEBUG: ...`，
客户端读到的就是一行非法 JSON，会话就毁了。

**这条说法在别处是对的**，所以我差点直接当成结论讲出去。按铁律（能跑一次给人看就别用嘴解释）**动手造对照实验**。

### 4.2 对照实验：两个逐字相同、只差一行 `print` 的 server

| 文件 | 差异 |
|---|---|
| `srv_clean.py` | 干净版 |
| `srv_noisy.py` | **逐字相同，只多一行 `print("DEBUG: ...")`** |

各跑一遍完整动作（`initialize` → `tools/list` → `tools/call`），中途用一个 **stdout 监听中继**把 server 的 stdout
逐行抄进日志（**不截断**），并对每一行判一次"是不是合法 JSON"。

### 4.3 结果：两者**全绿**，`print` 没有造成任何可观测故障

`tee_noisy.log` 里**只有 3 行、行行是合法 JSON**，那行 `DEBUG` **一行都没进去**。

于是追因 —— 换一种更硬的投法，**投三枚可区分的标记**（`srv_marker_probe.py`）：

| 标记 | 投法 | 落点（实测） |
|---|---|---|
| `MARKER-M1-PRINT` | `print(...)` | **终端**，协议流里无 |
| `MARKER-M2-SYS-STDOUT` | `sys.stdout.write(...)` | **终端**，协议流里无 |
| `MARKER-M3-OS-WRITE-FD1` | `os.write(1, ...)`（**绕过 Python，直接写 fd 1**） | **终端**，协议流里无 |

★ 连 **fd 层直写**都被改道 ⇒ 不是 Python 的包装在挡，是 **fd 本身的指向变了**。

同时刻量到的 fd 事实（原文）：

```json
{"fd1_ino": 845803477511856773, "fd1_mode": "0o10660",
 "fd2_ino": 845803477511856773, "fd2_mode": "0o10660",
 "fd1_same_as_fd2": true}
```

`fd1_ino == fd2_ino` ⇒ **fd 1 和 fd 2 指向同一个东西**（`0o10660` 是个管道）。
另一份探针还顺带确认了一个容易搞错的点：**Python 层的 `sys.stdout` 对象没被换掉**
（`sys_stdout_type: TextIOWrapper`、`sys_stdout_fileno: 1` 全程不变）——
**换的是 fd 1 这个下标指向谁，不是 `sys.stdout` 这个对象。**

### 4.4 ★ 结论与三条边界（不许省）

**结论**：`MCPServer.run()` 启动时把 **fd 1 改道到 fd 2**，所以用户代码往 stdout 写的东西实际流向 stderr，
**落不到协议通道上**。

三条边界，缺一条就会把这句话讲成错的：

1. **这是 SDK 给的保护，不是协议的许可。** 协议规定 stdio 通道上只能有协议消息；
   换 SDK / 换语言 / 自己手写 stdio server **就没有这层保护**，那时 `print` 真的会毁掉会话。
   → 所以本次的"不会坏"，**不能**外推成"用 MCP 可以随便 print"。
2. **"没坏" = "没测出坏"。** 本次只覆盖一种组合：`mcp 2.2.0` + `MCPServer` + 工具函数内打印 + 高层 `Client`。
   没测的组合不许说。
3. **副作用仍在**：fd 1 与 fd 2 已经合流 → server 的 stderr 变成
   **"业务噪音 + 真错误日志"混在一起**，排查时要能区分这两类。（本项目的规矩是：要打日志就**显式**写 stderr。）

### 4.5 由此固化的一条通用规矩

> **凡属"会导致 X 故障"这类断言，先问："我在这个版本上真见过它发生吗？"**
> 没见过的，就写成"风险存在，但当前实现有防护"，**不许当成结论复述**。
>
> ★ **转述一个未经自己验证的故障，比不转述更危险 —— 它带着别人的权威感。**
> （本次是"我差点把一条听起来完全合理的常识当成结论讲出去"。）

## §5 ★ 取证二：默认走哪一代协议？（纠正本项目自己的一条旧结论）

### 5.1 为什么必须抓包：两种说法都能自圆其说

写验证脚本的 F 段时，我要回答"client 和 server 开场到底说了什么"。
而"**stdio 默认发 `initialize` 握手**"与"**默认发 `server/discover`**"这两句话，
**在文档层面都能找到依据，而且指向完全不同的两代协议**。

→ **文档只告诉你"存在什么"，"默认用哪个"的唯一来源是跑一次、把报文抓下来看。**

### 5.2 抓包对照：同一个 server、同一个 Client，**只改一个参数**

| `mode` | 谈定版本 | Client → Server 的 method 序列 | 日志报文条数 |
|---|---|---|---|
| **`auto`**（高层 `Client` 的**默认值**） | **`2026-07-28`** | `server/discover` → `tools/list` | 4 |
| `legacy` | **`2025-11-25`** | `initialize` → `notifications/initialized` → `tools/list` | 5 |

**业务报文两边一模一样**（都发 `tools/list`，拿到同样多的工具）—— **差的只有开场那两封。**

### 5.3 报文原文（逐字，未截断）

> 读下面这几封信封时只需要认识两个字段：**`serverInfo`** = 服务自报的身份（名字 + 版本）；
> **`supportedVersions`** = 它声明支持的协议版本列表。其余字段看不懂不影响。

**`auto` 的第一封**（注意：**根本没有 `initialize`**）：

```json
{"jsonrpc":"2.0","id":1,"method":"server/discover","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"mcp","version":"0.1.0"},"io.modelcontextprotocol/clientCapabilities":{}}}}
```

**`auto` 的第一封响应**（注意这封信封的字段：`supportedVersions` / `resultType` / `ttlMs` / `cacheScope`）：

```json
{"jsonrpc":"2.0","id":1,"result":{"cacheScope":"private","capabilities":{"prompts":{"listChanged":true},"resources":{"listChanged":true,"subscribe":true},"tools":{"listChanged":true}},"resultType":"complete","supportedVersions":["2026-07-28"],"ttlMs":0,"_meta":{"io.modelcontextprotocol/serverInfo":{"name":"inventory","version":""}}}}
```

**`legacy` 的第一封**：

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"mcp","version":"0.1.0"},"_meta":{}}}
```

**`legacy` 的第一封响应**（这封信封里是 `protocolVersion`）：

```json
{"jsonrpc":"2.0","id":1,"result":{"capabilities":{"experimental":{},"prompts":{"listChanged":false},"resources":{"listChanged":false,"subscribe":false},"tools":{"listChanged":false}},"protocolVersion":"2025-11-25","serverInfo":{"name":"inventory","version":""}}}
```

### 5.4 ★ 报文字段差异清单（不只是"少了握手"）

抓包顺带把这些差别也摊开了 —— 这些是**光看"两代"这个标签看不出来的**：

| 维度 | `auto`（Modern） | `legacy`（Legacy） |
|---|---|---|
| 版本声明位置 | 响应里的 **`supportedVersions: ["2026-07-28"]`** | 响应里的 **`protocolVersion: "2025-11-25"`** |
| 版本 / 身份 / 能力 | **每个请求的 `params._meta` 里都带一遍** | 只在握手那一次谈定；后续请求的 `_meta` 是**空对象** |
| 响应的信封字段 | 有 `resultType: "complete"` · `ttlMs` · `cacheScope` | **没有**这三个 |
| 能力声明的标志位 | `listChanged` 三处**全 `true`**，且 `resources` 多一个 `subscribe: true` | `listChanged` 三处**全 `false`**，`resources.subscribe: false` |
| 服务器身份 | 放在 `_meta.io.modelcontextprotocol/serverInfo`（serverInfo = 服务自报的身份：名字 + 版本） | 放在顶层 `serverInfo` |
| 多出来的通知 | 无 | 多一条 `notifications/initialized` |

→ **版本 / 身份 / 能力"从开场一次谈定"变成"逐请求自带"** —— 这就是 Modern 代最本质的变化。
（顺带：Modern 少了 `notifications/initialized`，因为**没有握手就不需要"握手完毕"这个通知**。）

### 5.5 机理（源码级）

`mcp/client/_probe.py` 里的 `negotiate_auto`：

- **先** `send_discover(LATEST_MODERN_VERSION)`
- **成功**就 `adopt()`（走 Modern）
- **抛错才** `session.initialize()`（回退 Legacy）

→ **fallback（回退：这条路走不通就退回备选方案）方向是单向的**：Modern → Legacy，不会反过来。
这一点对 §11.2 的 Q3 很关键。

### 5.6 ★ 所以正确说法是什么，以及本项目错在哪

**正确说法**：**"默认走哪一代，取决于用哪一层客户端。"**

- 高层 `Client`（`mode="auto"`，默认）→ **Modern**（`2026-07-28`，无握手）
- 指定 `mode="legacy"` → Legacy
- 低层 `ClientSession` / 手写报文那条路 → Legacy

**本项目原本记的是**："stdio 默认走握手代 `2025-11-25`"。这句话**在特定路径上成立**，写成通例就是错的。

## §6 装饰器替我生成了什么

写一台 MCP Server，**理论上要手写**：工具名、工具描述、参数 schema、返回 schema。
实际上一行都不用 —— `@server.tool()` 从**函数签名 + docstring** 全生成了。逐个说清它生成了什么：

| 生成物 | 来源 | 实测样例（`query_inventory`） |
|---|---|---|
| 工具名 `name` | **函数名** | `query_inventory` |
| 工具描述 `description` | **`fn.__doc__`，且不做 dedent**（dedent = 把多行文本每行开头的公共缩进统一去掉） | 描述里**带着每行 4 个空格的缩进**（线上原文可见 `\n\n    当用户问...`） |
| 参数 schema `inputSchema` | **函数签名的类型注解** | `min_stock` → `anyOf:[{integer},{null}]` + `default: null` |
| 参数级 `title` | 参数名 → **Title Case**（每个词首字母大写） | `min_stock` → `"Min Stock"` |
| 工具级 `title` | 名字 → **直接拼接**（不转驼峰） | `query_inventoryArguments` / `query_inventoryOutput` |
| 返回 schema `outputSchema` | **返回类型注解** | `list[dict[str,Any]]` → `{"result":{"type":"array","items":{"type":"object",...}}}` |

**description 的取值优先级**（源码 `mcp/server/mcpserver/tools/base.py:84`）：
`显式传的 description` > `fn.__doc__` > `""`。同款写法在 tools / resources / prompts **三处**都有。

### 6.1 缩进这件事为什么值得记

它意味着：**我写的 docstring 会原样（含缩进）发给客户端、再转给 LLM**。
"要不要为 4 个空格做点什么"有三个选项：

- **甲：不动**（← **本项目用户拍板选了这个**）：docstring 就是描述，最标准、最省心；4 个空格对 LLM 无实质影响。
- 乙：显式传 `description=`：文本最干净，但描述与函数分离，失去"自动"这个卖点。
- 丙：自定义装饰器自动 dedent：单一来源 + 干净，但为 4 个空格引入非标准包装。

★ **它值得记的理由不是"缩进"，而是"我知道 SDK 直接取 `__doc__` 不清缩进"** —— 面试里这是个能讲出**验证过程**的细节。

### 6.2 `content` 是"每条记录一个 block"

顺手实测到的：返回 12 条物料 → `content` 数组里 **12 个 block**（每块是一段缩进 JSON 文本），
干净的结构化数组在 `structuredContent.result` 里。

**含义**：**返回值的规模直接决定喂给模型的碎片数**。返回 50 条就是 50 个 block。
（同族问题：工具**数量**膨胀会降低模型选工具的准确率 —— 这里说的是**返回值**侧的同类风险。）

## §7 代码逐行解读

### 7.1 `mcp_servers/inventory_server.py`（104 行，正式产物）

**文件头三条设计约束，是这份文件的"为什么"**（不是装饰性注释）：

1. **零项目依赖**：只 import 官方 `mcp` + 标准库，不 import `app.*`、不连 Postgres、不读 `.env`
   → 所以它能在**任意目录、任意 Python 环境**里单独跑起来。
   （反过来说：**如果它必须 import 项目的配置才能启动，那它就不叫"独立服务"，只是项目的一部分。**）
2. **数据在进程内**：`_INVENTORY` 是写死在文件里的内存 mock 数据（mock = 为了演示手工编的假数据）。
3. **绝不往 stdout 打业务日志**：要打日志就**显式写 stderr**。

**逐块**：

- `server = MCPServer("inventory")` —— 第一个位置参数是**这台 server 自己的名字**。
  实测结论：**传什么、`serverInfo.name` 就报什么**；不传 / 传空串落回 SDK 占位默认 `"mcp-server"`
  （源码那行是 `name=name or "mcp-server"`）。它**不参与工具名**（工具名来自函数名）。
  ⚠ 有个未深究的点：同文件里还有一行 `default_audience=self.name`，**作用本次没查，不许在面试里展开讲**。
- `_INVENTORY` 的 12 条**故意造出四档库存**（`0` 缺货 / `<50` 极低 / `<300` 偏低 / `>1000` 充足）。
  目的：让"过滤"有**可看的效果** —— 不做这个，"`min_stock=20` 的结果对不对"根本看不出来。
- `_CATEGORIES` 用 `dict.fromkeys(...)` 去重保序 —— 为的是**别在两处手写同一串品类名**（写两遍必然有一天不一致）。
- `@server.tool()` 下面的那个 docstring **不只是注释**（§6）。所以它写的是**"什么时候用"**，不是"内部怎么实现"。
- `query_inventory(min_stock, category)`：两个 `if` 都写成"**不传就不过滤**" → 两个参数可任意组合；
  最后 `sorted(key=lambda row: row["stock"])` 升序 —— 方便一眼看出该补货哪些。
- `server.run(transport="stdio")` **一直阻塞**，stdin EOF 才返回（§3 第 7 步）。
  这里**显式写出 `transport=`**（transport = 传输方式，即"用哪条通道对话"）是为了避免歧义（它默认就是 stdio）。

### 7.2 `scripts/d26_mitm.py`（124 行，透明抓包器，可复用）

**它是什么**：一段**双向管道**，它自己**不是** MCP 的任何一方。

```
Client 的 stdin  ──> 本进程 ──> 真正 Server 子进程的 stdin
Client 的 stdout <── 本进程 <── 真正 Server 子进程的 stdout
```

它把双方之间的**每一行 JSON-RPC 原样抄一份到 stderr**，然后**原样转发**。

**为什么必须有它**：MCP 的 stdio 传输里，协议流走 stdin/stdout —— **没有网络包可以抓**。
SDK 又把报文封在内部，业务代码只能拿到解析后的对象。
→ 要回答"它到底发了 `initialize` 还是 `server/discover`"，**只能在中间插一段管道**（§5.1）。

**逐块**：

- `describe(raw)`：把一行报文概括成人话，四个分支 —— 有 `method` 有 `id` = **请求**；
  有 `method` 无 `id` = **通知**；有 `result` = **响应 OK**；有 `error` = **响应报错**。
  （这四个分支正好就是 JSON-RPC 的全部消息种类 —— §5.4 里 `notifications/initialized` 走的就是第二个分支。）
- `pump(src, dst, tag)` 三个动作：**读一行 → 记一行 → 原样转发**。
  ★ **转发必须原样**，否则它就改变了被观测的系统（观测者不能扰动被观测对象）。
- ★ **打印不截断**是刻意的：早期版本用 `raw[:300]`，结果长响应（如整张工具清单）在日志里只剩前半截，
  而"原样落日志"这句表述就**失真**了。**要截断请在读日志的人那边做，别在记录时做。**
- 起子进程用 `sys.executable`：**保证它和被观测的 server 跑在同一套 Python 环境**里
  （否则换解释器会 import 不到 `mcp`，报的错还像是"server 坏了"）。
- 子进程的 `stderr=sys.stderr`：把 server 自己的 stderr **直接透出去**，不拦、不吞。

### 7.3 `scripts/d26_verify.py`（490 行 / **36 条断言** / 七段）

**设计原则**：**一段回答一个不同的问题**。这是它跟"一堆断言语句堆在一起"最大的区别 ——
失败时你能直接说出"是哪一类问题坏了"。

| 段 | 回答什么问题 | 条数 |
|---|---|---|
| A 前置静态检查 | 这份文件真的是"零项目依赖、能被单独启动"的吗（**只读源码，不连进程**） | 3 |
| B 连接与身份 | ★ **官方高层 `Client`** 能不能连上它 | 4 |
| C 工具目录 | `tools/list` 报出来的目录，字段是否齐全、schema 是否可用 | 7 |
| D 调用与返回 | ★ 名字从目录里取（**零硬编码**），业务结果对不对、双层返回对不对 | 7 |
| E 错误语义 | 出错时是**抛异常**还是**装进 `isError`** | 4 |
| F 两代协议对照 | ★ 同一个 server、同一个 Client，只改 `mode`，看**第一封报文**是什么 | 5 |
| G 进程独立性 | ★ 它是不是一个**真的独立进程**，生命周期归谁管 | 6 |

**几处关键设计（每处都有"不用它会怎样"）**：

- **`check()` 不用 `assert`**（`assert` = Python 的断言语句，条件不成立就当场抛异常）：让**全部断言都跑完**再给结论。
  用 `assert` 的话第一条失败就抛，后面几十条信息一起被吞掉 —— 排查时最需要的恰恰是"还有哪些也坏了"。
- **B 段必须用官方高层 `Client`**：自己写的客户端能连上，只证明"我按自己理解的协议写对了"；
  **官方客户端能连上，才证明"服务对外表现符合规范"**。
  （同 D25 的规矩：**实验脚本本身不能含有你要证明的东西**。）
- **C7 = 零硬编码自证**：用 `ast` 扫**本文件**的全部字符串常量，与工具名求交集，**必须为空**。
  理由见下。
- **D 段参数按 schema 声明的类型挑，不按位置猜**（`_param_by_json_type`）——
  见 §10 的踩坑①。
- **D2 的期望值用另一条独立路径算**：从"全部记录"里自己筛一遍，**不引用服务端的过滤逻辑**。
  用服务端的逻辑算期望值，等于**用被测量的东西验证它自己**。
- **F0 是守门断言**：抓包日志每条报文都必须以 `}` 结尾。
  **被截断过的"原始日志"是不能拿来论证的** —— 这条断言的存在理由就是 §7.2 那个教训。
- **G 段拿 pid 的手法**：`/bin/sh -c 'echo $$ > pidfile; exec "<python>" "<server>"'`。
  `exec` 让 shell **被 python 顶替**，所以写下的 `$$` 就是 server 的进程号。
  ★ **这个 pid 来自内核，不是 server 自报的。**
  再用 `os.kill(pid, 0)`（**不发信号，只问内核"这个 pid 还在不在"**）与
  `os.getpgid(pid) == pid`（getpgid = 取进程组号；两者相等说明它是**新会话的首领**）取证。
  断言链：连接前不存在 → 连接中存在且 ≠ 我 ≠ 我父 → **断开后自行退出**。

#### 为什么"零硬编码"是这份脚本的核心

若脚本里直接写死工具名去调用，那它只能证明"我写对了"，**证明不了名字来自 Server** ——
**名字本来就在我手上**，写进去再调通，这叫**循环证据**。

所以本文件里**一个工具名都不许出现**：名字一律从 `tools/list` 的返回值取，参数名从 `inputSchema` 取。

★ **而且自证要扫"这个脚本自己"，不是在命令行里 `grep` 一遍**：
`grep` 是**一次性的动作**（今天查了、明天改了没人再查），而 C7 是**每次跑都重查的断言**。
把规矩变成断言，它才不会腐烂。

### 7.4 负测试：证明"36/36 全绿"不是"永远全绿"

**一条永远通过的断言，比没有断言更危险** —— 它给的是虚假的安全感。
所以"全绿"这个结果本身**必须被验证**：故意注入破坏，看对应断言会不会红。

| 注入的破坏 | 期望红的断言 | 实测 |
|---|---|---|
| `inventory_server.py` 里加一行 `_INVENTORY.pop()`（少一条数据） | **D1**（12 → 11） | ✅ **如期报红**（11≠12） |
| `d26_verify.py` 里写进一个工具名常量 | **C7**（零硬编码自证） | ✅ **如期报红** |

其余 **34 条仍绿**；**还原后复跑 36/36**。

## §8 错误语义：两种错误走两条完全不同的路

这一节是**从 bash 手写报文**（零 Python、零 `mcp` 库）的对照实验里得到的 —— 也是补上 **D25 标着"未测"的那一项**。

三条报文原文（`raw_shell_errors.log`）：

| 情形 | 报文原貌 | 走哪条路 |
|---|---|---|
| 工具不存在 | `{"id":4,"result":{"content":[{"text":"Unknown tool: 这个工具不存在"}],"isError":true}}` | **工具层 → `result` + `isError`** |
| 参数类型错 | `{"id":5,"result":{"content":[{"text":"Error executing tool echo: 1 validation error for echoArguments … Input should be a valid string [type=string_type, input_value=12345, input_type=int] …"}],"isError":true}}` | 同上（Pydantic 全文塞进 `text`） |
| **方法名不认** | `{"id":6,"error":{"code":-32601,"message":"Method not found","data":"随便一个不存在的方法"}}` | ★ **协议层 → JSON-RPC 标准 `error` 对象** |

**所以边界不是"所有错误都走 result"，而是：**

> **工具层走 `result`（要让模型看得见，模型才能自己改）、协议层走 `error`（模型看不懂那一层）。**

**为什么这么设计**：`call_tool` **不抛异常**是刻意的 —— 错误如果以异常形式抛给调用方，
模型根本看不到；装进 `result` + `isError=true`，模型读到 `Input should be a valid string`
就能**自己把参数改对再试**。这是 **Agent 循环能自转的关键一环**。

另注：**成功响应里的 `isError:false` 是显式出现的**，不是省略 —— 显式和省略在协议里是两件事。

**空结果不是错误**（D4 断言）：`category` 传一个不存在的品类 → `content: []` + `structuredContent.result: []` + **`isError: false`**。
"查不到"是**正常结果**，不是失败。把它标成错误，模型会以为工具坏了。

### 9.2 本日两次自我推翻（**这才是今天的主要产出**）

| # | 推翻的说法 | 真实情况 | 性质 |
|---|---|---|---|
| 1 | 「`print` 会污染协议流」 | `MCPServer.run()` 把 **fd 1 改道到 fd 2**；且"没坏"="没测出坏"，换 SDK/语言就没这保护 | 推翻**流传很广的常识** |

### 9.3 复述验收状态

## §10 踩坑记录

### ① 位置 ≠ 语义（**本日最值得记的一个 bug**）

**现象**：D 段第一版写 `p_names = sorted(props)`、然后 `p_names[0]` 当成 `min_stock` 传 `20`。
**字母序靠前的是 `category`** → 服务端参数校验拒绝 → 下一步取 `structured_content["result"]`
**直接 `TypeError`，把整个脚本打挂**。

**根因**：**参数名的字母序和它的语义毫无关系**。我把"排列位置"当成了"身份"。

**修法**：从 `inputSchema` 里**按声明的类型**挑（`integer` → 数值参数，`string` → 文本参数）。
**参数名可以随便取，能稳定区分它们的只有类型。**

**连带修的第二处**：缺前提时**跳过并报红，不要崩**（`_rows()` 取不到就返回 `None` 交给 `check` 判红）。
崩掉会一次性丢掉后面所有断言的信息。

### ② Pydantic 模型在 Python 侧是 snake_case（**同族第 2、3 次**）

线路上看到的是 `inputSchema` / `isError` / `structuredContent`，
**Python 属性名是 `input_schema` / `is_error` / `structured_content`**。

→ 规矩：**写探测脚本前先 `model_fields` 看一眼**，别照抄抓包结果里的字段名。
（同族第一次是 `init.protocol_version`。同一个坑踩三遍，说明它不是我"手滑"，是我**没把它当规矩**。）

### ③ `Client(str)` 里的 `str` 是 URL，不是命令

想让它起子进程必须传 `StdioServerParameters(command=..., args=[...])`。
把命令字符串丢给 `Client` 是无效的。

### ④ 回归五个脚本全挂 —— **不是回归失败，是我用错了跑法**

**现象**：改完依赖后跑全量回归，五个脚本全报 `ModuleNotFoundError: No module named 'app'`。
**第一反应**（错的）："刚动依赖把 import 破坏了"。

**真相**：本项目脚本**必须用模块方式跑** —— `uv run python -m scripts.xxx`。

- `-m` 会把 **cwd（current working directory，当前工作目录 = 项目根）** 加进 `sys.path`
  （`sys.path` = Python 找模块时依次搜索的路径列表），`import app` 才找得到
- 直接给路径 `python scripts/xxx.py` **只会把 `scripts/` 加进 `sys.path`** → 必然 `No module named 'app'`

**改用模块方式后**：**260/260 全绿**（`d21_delete_scope 27 + d21_eval 63 + d22 77 + d23_metrics 33 + d24_report 60`）。

★ **而且当时静态证据本来就已经证明依赖没被动**：`uv.lock` 改动是 **+437 / −0（纯新增、零删除行）**，
装完 pydantic 仍是 `2.13.4`、uvicorn `0.52.4`、fastapi `0.141.1`、langgraph `1.2.11` **全部未变**。
**我手里有证据，却先去怀疑对象。**

→ **定性铁律**：`ModuleNotFoundError / ImportError / command not found` **先怀疑入口和环境**；
`AssertionError / 数字不对` **才怀疑对象**。

### ⑤ raw shell 第一版丢了一条 `tools/call`

写端（管道左边那个子 shell，它的任务是"把报文送进去"）关得太快，server 读到 stdin EOF 就退出了，**还没轮到处理第三条**。
**修法：每条报文之间加 `sleep`，最后一条写完再 `sleep` 才收尾。**
（副作用是好的：这成了"**生命周期由 Host 掌管**"的活体演示 —— 见 §3 第 7 步。）

### ⑥ 机检假阳性不许照修（**本项目反复出现**）

README 机检报 5 处、PRD 机检报 4 处，**逐条目视全是假阳性**：
原有转义竖线 `\|` 被算成列分隔符、跨行粗体、修正说明本身在引述原写法、对照表故意保留反面例子。

→ **照报错去修会把表格切断、把排版改坏。** 机检给的是"**候选**"，不是"结论"。

### ⑦ Bash `grep` 假阴性（本项目已知坑，第 N 次）

## 附录 A：Q1–Q3（第二组）参考答案 —— **先自己答完再翻**

> §11.1 第一组的判定结果已经写在正文里，不重复。这里是**第二组**的参考答案。

### A1 · 两代协议

**L1**：`auto` = `server/discover` → `tools/list`，谈定 **`2026-07-28`**；
`legacy` = `initialize` → `notifications/initialized` → `tools/list`，谈定 **`2025-11-25`**。
（业务报文两边一样，差的只有开场那两封 —— §5.2）

**L2**：出错在**"默认"这两个字少了主语**。正确说法是「**默认走哪一代取决于用哪一层客户端**」：
高层 `Client`（`mode="auto"`）默认走 Modern；`mode="legacy"` 或低层 `ClientSession` 走 Legacy。
（§5.6）

**L3**：会推出"**它现在就走 `2026-07-28`、不发握手了**"。而真实情况是：
- **规范里有这一代** ≠ **实现默认用这一代**；
- 而且**同一个常量还有另一个**：`LATEST_HANDSHAKE_VERSION = 2025-11-25`。
  两个常量分别是"最新的一代"和"握手代里最新的一版"，**看一个常量推不出默认路径**。

★ 这正是 10-01 那天犯过的错（把"规范新增了一代"读成"实现已经切过去"）—— **同一个错型的第一次**。

### A2 · 零硬编码自证

**L1**：它在检查"**这个脚本里没有出现任何工具名**"。
做法是用 `ast` 扫本文件的全部字符串常量，与 `tools/list` 报出来的工具名求交集，必须为空。（§7.3）

**L2**：
- **能证明**：**我按我理解的协议写对了**（路径通了、结果对不对）。
- **不能证明**：**那个名字是从 Server 拿到的**。因为名字**本来就在我手上** ——
  我写死它再调通，逻辑上完全可能是"恰好我写对了而已"，这叫**循环证据**。

**L3**：因为两者的**性质不同**：
- `grep` 是**一次性动作** —— 今天查了，明天有人加一个字没人再查；
- C7 是**断言** —— **每次跑都重查**，改了文件、重跑，它照样会红。

★ **把规矩变成断言，它才不会腐烂。** 这也是"实验纪律"和"今天小心一点"的区别。

### A3 · auto 探测失败怎么办

**L1**：**回退去发 `initialize` 握手**（源码 `negotiate_auto`：先 `send_discover(LATEST_MODERN_VERSION)`，
成功就 `adopt()`；**抛错才** `session.initialize()`）。（§5.5）

**L2**：`server/discover` 探测失败 → 回退 → **发 `initialize`（带 `2025-11-25`）** + `notifications/initialized`，
最终**谈定 `2025-11-25`（Legacy）**。
Server 侧回的是 `initialize` 的响应（带 `protocolVersion: "2025-11-25"`、`serverInfo`）。
→ 客户端**不需要知道**对面是哪一代，这正是"自带代际探测"的意义。

**L3**：**会直接失败，而且回退救不了。** 因为 fallback 方向是**单向的**（Modern 探测失败 → 回 Legacy），
**没有"Legacy 失败 → 试 Modern"这条路**。
一个只认 Modern 的 server 收到 `initialize` 会回 `-32022 UnsupportedProtocolVersionError`
（`data.supported` 里列它支持的版本），而**写死 `mode="legacy"` 就等于关掉了探测** ——
客户端不会再去试 `server/discover`。

→ 这条推演的实用含义：**除非有明确理由，别写死 `mode`。** 默认的 `auto` 是最宽的入口。

**三条教训**（写进 PRD §9.6.3）：

1. **同一份「规模」被三个来源写成三个数**（PRD 252 / 文档页 139 / 实测 259），三份都自称权威、**只有一份是实测**
   → 引用外部系统的规模，**必须标"读取日期 + 来源层级（文档 / 实测）"**。
2. **「只读」被挂在错误的层上**（凭证层 vs 服务端层）。这类"能力挂在哪个层"的错**不报错** ——
   拿全权 token 调只读接口，测试照样全绿
   → 写风控设计时，**每道护栏都要写明实施在哪个进程**。
3. **"会导致 X 故障"这类断言，必须先问"我在这版本上真见过吗"**（§4.5）。
