## 1. 从零讲容器：七层递进

> ⚠ 这一节是**地基**。D34 开工时跳过它直接讲"容器里的 localhost 不是你的 mac"，
> 结果讲完被要求从头重讲一遍。**后续所有 Docker 相关内容都从这里起步。**

### ① 容器 = 一台软件模拟的迷你电脑

它有自己**独立的**文件系统、网络、进程表。装了什么依赖、监听哪个端口，都是这台"电脑"自己的事，与你的 Mac 无关。

### ② 为什么需要它 —— 四个服务的依赖会打架

本项目有四个东西要跑：数据库（带向量扩展）、缓存、后端 API、前端静态站点。
它们要求不同、装法不同。如果都装在 Mac 上，会出现"这个要 Python 3.12、那个要 Node 22"的冲突，而且换一台电脑就重装一遍。

**容器把"每个服务的运行环境"打包成一个自包含的盒子** —— 于是换机器只需要有 Docker。

### ③ 镜像（image） vs 容器（container）

| 词 | 类比 | 说明 |
|---|---|---|
| **镜像** | 装系统的 **U 盘** | 只读的模板，一层层叠出来（**层 = layer**） |
| **容器** | 用 U 盘**装出来的那台电脑** | 镜像的一个运行实例，可以有好几个 |

**Dockerfile** = 描述"这个 U 盘怎么做"的配方文件。

### ④ 端口映射 = 你的 Mac 与容器之间的一扇门

容器有自己的网络，外面默认**看不见**它。`ports: "8080:80"` 的意思是：

```
宿主机的 8080 端口  →  转发到  容器的 80 端口
      ↑ 你在浏览器里敲的            ↑ 容器内服务真正监听的
```

**格式永远是「宿主:容器」**，写反了会得到一个"莫名其妙连不上"。

⚠ 本项目把 api 映射成 **18000**（而不是 8000）、web 映射成 **8080**（而不是 80），原因是**宿主机上这两个端口已经被占了**：8000 是本机 dev 的 uvicorn，80 是本地 Dify 的 nginx。**容器的端口是可以随便定的，因为它跟宿主机本来就没关系。**

### ⑤ ★ 容器里的 `localhost` 指"它自己"

这是最容易错、也最容易看懂的一条：

> `localhost` 的字面意思是"**正在说话的那台机器自己**"。
>
> 在 api 容器里写 `localhost:5432`，指的是 **api 容器自己的 5432** ——
> 而 api 容器上根本没有数据库，那儿没人监听。

**报错形态是判据**：

| 报错 | 含义 |
|---|---|
| `Connection refused` | **找到了那台机器**，但门后没人（端口没开） |
| `timeout` | **连机器都没找到**（地址不通 / 被防火墙吞了） |

这两个字面不同、原因不同，看到时不要混着说。

### ⑥ 服务名 = compose 建的局域网里的域名

compose 一上来会做两件事：

1. 建一张**虚拟局域网**（本项目实测叫 `agentforge-lite_default`）
2. 把每个服务在 YAML `services:` 下的**名字**注册成这张网里的域名

于是"连数据库"就写它的服务名 **`db`**，"连缓存"就写 **`redis`**。

### ⑦ 落到真实代码

`app/config.py` 里**没有** `DATABASE_URL` 这个环境变量（这是一个常见误记）。真实的字段是分开的：

```python
postgres_host: str = "localhost"   # ← 在 compose 里被覆盖成 "db"
redis_host: str = "localhost"      # ← 被覆盖成 "redis"
```

覆盖发生在 `docker-compose.yml`：

```yaml
api:
  env_file: [.env]                 # 密钥从这进（不进镜像）
  environment:
    POSTGRES_HOST: db              # ★ 服务名落地处
    REDIS_HOST: redis
```

**优先级**：compose 的 `environment` > `env_file`；pydantic 读 **操作系统环境变量** 的优先级 > 读 `.env` 文件 —— 所以覆盖成立。

### ⑧ ★ 同一行里的两个 `/api`

nginx 里这一行是"路径 vs 机器名"最容易混的地方：

```nginx
location /api/ { proxy_pass http://api:8000; }
```

| 片段 | 是什么 | 判据 |
|---|---|---|
| `location /api/` | **路径**（URL 里的一段，来自浏览器的请求地址） | 前面有斜杠 |
| `http://api:8000` | **机器名**（局域网里那台叫 api 的机器） | 在 `://` 和 `:端口` 之间 |

**位置决定角色**：`@`、`://` 后面到 `:端口` 之间那个位置，**只能填主机名**。
所以"把 `/api` 填进去"在语法上就不成立 —— 而且即使去掉斜杠写成 `api`，**它指的也是 api 自己**（而 api 上没有数据库）。

## 2. compose 的四个服务

| 服务 | 镜像 | 容器内端口 | 宿主端口 | 说明 |
|---|---|---|---|---|
| `db` | `pgvector/pgvector:pg16` | 5432 | 5432 | 复用 D1 起的老容器，**本次一行未动** |
| `redis` | `redis:7-alpine` | 6379 | 6379 | 同上 |
| `api` | 本地构建 `agentforge-api:local` | 8000 | **18000** | FastAPI + uvicorn |
| `web` | 本地构建 `agentforge-web:local` | 80 | **8080** | nginx 托管前端静态文件 |

### 2.1 为什么 db / redis "刻意不动"

加了 `restart:` 之类的配置 = **改了配置** → `compose up` 会判定"这个容器该重建" → 白白重启一次数据库。

**这是"最小 diff"判据的落地**：本次只需要它继续跑，那就一个字都不改。
实测证据：`docker compose ps` 里它们显示 `Up 4 days`（而 api/web 是 `Up 2 minutes`）。

### 2.2 `depends_on` + `healthcheck`：**"起来了" ≠ "能用了"**

```yaml
depends_on:
  db:    { condition: service_healthy }
  redis: { condition: service_healthy }
```

如果只写 `depends_on: [db]`，compose 只保证"**容器已启动**"—— 而 Postgres 从"进程起来"到"能接受连接"之间有几秒。

`healthcheck` 就是给这个"能用"下定义：

```yaml
healthcheck:
  test: ["CMD", "pg_isready", "-U", "agentforge"]
```

**本项目 api 的健康检查工具是刻意换过的**：镜像里**没有 curl**（slim 镜像很干净），所以用 Python 的 `urllib` 打自己的 `/api/health`；web 用 `wget`（nginx:alpine 基于 busybox，有 wget 没 curl）。

### 2.3 `start_period: 20s` 是怎么定的（不是拍脑袋）

读 `app/main.py` 的启动流程（`lifespan`）确认：启动期只做两件事 —— **Redis 自检** + **MCP 接入**，**不加载模型**（模型是首次使用时才加载）。

所以 20 秒足够；写成 40 秒就是编了一个不存在的理由。

### 2.4 一个容易漏的细节：`name:`

```yaml
name: agentforge-lite
```

不写的话，**项目名默认取目录名** —— 你把项目文件夹改个名，compose 就认为是另一个项目，会**重新建一套容器**，然后撞端口。

## 3. api 镜像（`Dockerfile`）

### 3.1 基础镜像为什么用 `python:3.12-slim` 而不是 alpine

alpine 更小，但它用 **musl libc**（而主流 Linux 是 glibc）。本项目依赖里的 `onnxruntime`、`asyncpg` 这些带**预编译二进制**的包，官方提供的轮子都是给 glibc 编的 —— 用 alpine 就得现场编译，又慢又容易缺系统库。

### 3.2 ★ 层缓存：先拷依赖清单，再拷代码

```dockerfile
COPY pyproject.toml uv.lock ./     # ← 先
RUN uv sync --frozen               # ← 装依赖
COPY app/ ./app/                   # ← 后
COPY scripts/ ./scripts/
COPY mcp_servers/ ./mcp_servers/
COPY tests/ ./tests/
```

**为什么顺序重要**：每一层都有一个"指纹"（由这一层的内容和上一层算出来）。**只要某一层的指纹没变，Docker 就跳过它、直接用缓存。**

所以把"改得最勤的代码"放在后面 —— 改了代码之后，前面"装依赖"那一层还是缓存命中的，构建秒过。反过来的话，每次改一行 `.py` 都要重装 102 个包。

**实测证据**：改 `nginx.conf` 后重建前端镜像，日志显示 `#12 RUN npm ci` 是 **CACHED**、`#13 RUN npm run build` 是 **CACHED**，**只有** `#15 COPY nginx.conf` 真的重跑了。

### 3.3 `--host 0.0.0.0` 必须写

uvicorn 默认绑 `127.0.0.1`，意思是"**只监听容器自己**"。这样宿主机通过 18000→8000 的转发**连不上**。

这和第 ① 节那个坑是**同一件事的两面**：
- 那边是"客户端把地址写错了"
- 这边是"服务端只肯听自己"

### 3.4 ★★ `.gitignore` 与 `.dockerignore` 是**两套独立机制**

这是今天最值得记的一条：

> `.env` 被 `.gitignore` 挡住 ⇒ **只说明它不会进 git**，**不代表它不会进镜像**。

`docker build` 会把上下文目录（build context）**整个发给 Docker 引擎**。不加 `.dockerignore`，`.env`（含所有 API key）、`.venv/`、`models/`（1.1 GB）**全都会被打包传过去**，其中有 COPY 指令的还会直接进镜像。

**实测证据**：本项目加了 `.dockerignore` 后，构建日志里上下文传输只有 **2.91 MB**；不加会是 **1 GB+**。

### 3.5 一个前导斜杠的坑

`.dockerignore` 里写 `/models/`（**带前导斜杠 = 只匹配仓库根的那个**）。

不写斜杠的话，`models/` 会**连 `app/models/` 一起排掉** —— 那里面有 ORM 模型定义，容器启动会直接 `ModuleNotFoundError`。这个坑项目里已经记过一次，今天没再踩。

## 4. web 镜像：多阶段构建

### 4.1 "含 Node" 到底指什么

前端构建需要 Node，但**运行**只需要 nginx。所以镜像分两段：

```dockerfile
FROM node:22-alpine AS builder       # ← 第一段：构建
RUN npm ci && npm run build

FROM nginx:1.27-alpine               # ← 第二段：运行（从这里重新开始）
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

**最终镜像里没有 Node、没有 npm、没有 `node_modules`。**

| | 大小 |
|---|---|
| builder 用的 `node:22-alpine` | 164 MB |
| **最终 `agentforge-web:local`** | **52.3 MB** |

实测证据：对最终镜像跑 `which node` / `which npm`，**都是空**。

### 4.2 nginx 配置的三件事

**① 静态资源：`/assets/` 长缓存 + `index.html` 不缓存**

Vite 产物的文件名带**内容哈希**（`index-a1b2c3.js`），内容变了文件名就变，所以可以放心让浏览器缓存一年。

但 `index.html` **绝不能缓存** —— 它里面写着"该去加载哪个 JS"。缓存了它，用户会拿旧的 HTML 去要一个已经被删掉的 JS 文件名 → **白屏**。

⚠ 今天在这里踩过一次：原先同时写了 `expires 1y` 和 `add_header Cache-Control`，实测**发出了两条 `Cache-Control` 头**。改成只用一条。

**② SPA 兜底**

```nginx
location / { try_files $uri $uri/ /index.html; }
```

前端路由（如 `/trace/abc`）在服务器上**并不存在这个文件**。不兜底的话刷新页面就 404。实测 `/trace/abc` → 200。

**③ 反向代理**

```nginx
location /api/ { proxy_pass http://api:8000; }
```

**为什么必须有这一层**：本项目后端**没有配 CORS**（跨域资源共享 —— 浏览器默认禁止一个源去请求另一个源的接口）。
前端 `baseURL` 是相对路径 `/api`，如果直接对 `18000` 发请求就是跨域，浏览器会拦。走 nginx 同源转发就不存在跨域问题。

**⚠⚠ 尾部斜杠的语义完全不同**：

| 写法 | 效果 |
|---|---|
| `proxy_pass http://api:8000;` | **透传**原始 URI → `/api/health` 原样转发 ✅ |
| `proxy_pass http://api:8000/;` | 用 `/` **替换** 掉 `location` 匹配的部分 → 变成 `/health` ❌ 404 |

本项目后端的路由**自带 `/api` 前缀**（`app/main.py` 里六处 `include_router(..., prefix="/api")`），所以必须**不能带尾部斜杠**。

### 4.3 ★★ 今天最有价值的实测发现：nginx 会把上游 IP **记死**

**背景**：`proxy_pass` 里写**字面主机名**时，nginx **只在配置加载那一刻解析一次 DNS**，之后**永不重查**。

**后果**：`docker compose up -d --build` 重建 api 容器后，新容器会拿到**新的 IP**，但 nginx 还在往旧 IP 打 → **web 会持续 502**，直到 web 自己也重启。

**对照实验**（这个过程本身值得学）：

1. 第一次实验：删掉 stub 容器重建 → 新 IP **复用了旧的那个** → **实验无法区分**（⚠ 第一版实验设计有缺陷，不算证据）
2. 改法：先起一个 `alpine sleep 300` **占位抢走旧 IP**，再起真正的 stub → 拿到新 IP
3. 结果：`curl` 得到 **502**，nginx 错误日志原文
   `connect() failed (111: Connection refused) ... upstream: "http://<旧IP>:8000/api/anything"`
   —— **证明它仍在打旧 IP**

**修法**：让 `proxy_pass` 里出现**变量**，nginx 就会改按 `resolver` 的间隔**重新解析**：

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;   # 127.0.0.11 = Docker 内置 DNS
location /api/ {
    set $api_upstream http://api:8000;
    proxy_pass $api_upstream;
}
```

- ⚠ 变量里**不带路径**，所以原始 URI（含 `/api` 前缀）仍原样透传，**语义没变**（这是"为了让 nginx 重解析"，不是"顺手改了转发规则"）
- ✅ 修复后重跑同一实验：IP `.3` → `.4`，等 11 秒（> `valid=10s`）后连续两次 `curl` 均 **404**（打到了），**错误日志零条**
- ★ **附带好处**：解析延后 → 单独跑 web 容器（没有 compose 网络）时 nginx **不再启动失败**（旧写法报 `[emerg] host not found in upstream "api"`，退出码 1）

## 5. MCP 预热脚本（`scripts/warmup_mcp.py`）

### 5.1 "预热"到底预热什么

**预热（warmup）** = 在正式用它之前先跑一遍那套"第一次特别慢"的流程，让慢的部分**提前发生**。

关键是：**慢的成因有好几层，只有一部分能靠"提前跑"消掉。**

| 层 | 慢在哪 | 一次性的？ |
|---|---|---|
| ① npm 包下载 | 首次要从 npm 仓库下载 `harness-mcp-v2`。实测直连超时，走国内镜像用了 **2 分 31 秒** | ✅ 一次性 |
| ② 版本的"再解析" | 配置若写 `@latest`，npx **每次启动都要联网问**"latest 现在是哪个版本" | ❌ **每次都发生** ← "锁版本"要解决的就是它 |
| ③ Node 进程 + 模块加载 | 起进程、把 535 MB 的包加载进内存 | ❌ 每次都发生，本次要**量出来** |
| ④ ONNX 模型（可选） | 语义检索要下载约 23 MB 模型 | ✅ 一次性 |

→ 所以预热的真正目标不是"让它变快"，而是：**把一次性成本提前付掉，把每次都发生的成本量出来**（好知道演示时会不会卡）。

### 5.2 为什么**不能**串进 compose 的启动链

PRD §9.8 原文写的是「compose 的 api 服务启动脚本中**串入** `warmup_mcp.py`（**或提供 `make warmup`**）」。

但用户已拍板 **api 容器不装 Node** → 容器内**根本起不了 harness**（它是 `npx` 启动的 Node 程序）→ 前半句走不通，只能走**后半句**。

⚠ **登记为对 PRD §9.8 的已知偏差**（见 §11）。

即便容器里有 Node，这样做也仍然不对：`npx` 冷启动是**分钟级**，串进启动链会把 `docker compose up`（也就是 D34 验收的"**一键起**"）一起卡住。

### 5.3 脚本的八段结构

| 段 | 做什么 | 关键设计 |
|---|---|---|
| A | 查 npm 缓存现状 | ★ **判据不是"缓存目录在不在"**，见下 |
| B | 打印当前生效配置 | PAT 只报"已配置/未配置"，**绝不打印内容** |
| C | 起进程 + 握手（**T1**） | 这是最慢的一步，单独计时 |

### 5.4 三个"判据"上的讲究

**A 段为什么不能用"本地存在缓存目录"当判据**

`~/.npm/_npx/<hash>` 的**目录名是命令字符串的哈希**。你把配置从 `@latest` 改成 `@3.2.33`，npx 就会去**另一个目录**。

所以"本地有一个 harness 目录"**证明不了**"这次启动会命中它"。

**真正的判据在 C 段的 T1 耗时**：几十秒起不来 = 在拉包；几百毫秒 = 缓存命中。

**F 段为什么用 `after - before` 而不是"扫到 0 个"**

起进程**之前**本机**已经有** 2 个命令行里含 `harness-mcp-v2` 的进程（来源不明）。所以"扫到 0 个"**永远不会成立**。

这段只能回答"**我起的这一台有没有留下**"—— 这是**覆盖面边界**，必须说出来，不能假装是"全机没有泄漏"。

**退出码为什么分三档**

| 码 | 含义 |
|---|---|
| `0` | 可演示 |
| `1` | **坏了** |
| `2` | **前置没满足**（开关关着 / 没配 PAT） |

"没开"和"坏了"是两件完全不同的事 —— 演示前的检查清单必须能区分它们。

### 5.5 ★★ 结清一笔挂起的死账

**背景**：Harness 的 TRIAL 账号 **2026-10-06 07:59:59 到期**。
2026-10-07 复查时只验了"**连接建立** + **`tools/list`**" —— 这两个都是**读**。
**工具执行（`tools/call`）从来没验过**，而 D27 验收②和 D37 都依赖它。

判据是：**「风险还没兑现」≠「风险已解除」**。

**本次结果**（`harness_list(resource_type="organization")` 真调成功）：

```json

```

→ **到期日（10-06）之后第 3 天，工具执行（只读路径）仍然可用。**

**⚠ 边界必须连着说**：只验了**一个只读工具**，**没验写操作**（create/update/delete/execute）。
正确说法是「**只读路径在到期后仍可用**」，**不是「账号没事了」**。

**mock 策略**（PRD 明确要求）：
- LLM 层用假模型测逻辑
- MCP 层用**本机自研的 `MCPServer`** 当"假 server"（真协议、真子进程，但**不依赖外网与 PAT**）
- Harness 侧标 `@pytest.mark.external`，**默认跳过**

**验收项**：`S8` 核心链路覆盖率 ≥ 60%（`pytest --cov`）。

### 6.2 三个关键设计

**① mock 替换的是"最内层"，不是"整个函数"**

`MockLLM` 替换的是 `llm_gateway._call_once`（**单通道调用点**），而**不是** `chat()`。

差别很关键：`_call_once` **之上**还有**降级循环**（主通道失败 → 切备用）。把那一段留着，"降级"这段真实逻辑才测得到；替换 `chat()` 的话，测的是 mock 自己。

**② 一条断言"没有区分度"的例子（今天真实踩到）**

验证"锁定通道失败时**异常不被包装**"这条：如果 mock 抛的就是 `RuntimeError`，而网关**包装后也是** `RuntimeError` —— 两边同一个类型，断言**恒真**。

**修法**：让 mock 抛一个**不可能被包装出来**的类型（`httpx.ConnectError`）。

> 一般规律：**写断言时先问"它能被打破吗"**。一个永远绿的断言比没有断言更糟 —— 它给人已经验过的错觉。

**③ `external` 标记怎么做到"默认跳过、点名才跑"**

不能用 `addopts = "-m 'not external'"` —— 那样命令行再写 `-m external` 会变成"既要 external 又要 not external"，自相矛盾，**永远收集不到用例而且不报错**（静默 0 条）。

正解：在 `conftest.py` 里判断"这次有没有显式点名 external"，没有才给这些用例挂 `skip`。

### 6.5 今天由测试驱动出来的**两个真修复**

**① `repr(settings)` 把 4 个密钥明文打印出来**

pydantic 的 `repr()` **默认会打印所有字段的实际值**。这意味着任何一句 `logger.info("config=%s", settings)`、任何一次把 settings 塞进异常消息、乃至调试时在终端敲一下变量名，都会把 API key 明文写出去 —— **而它完全不像"泄密"，看起来只是打了一行配置。**

**修法**：在 `app/config.py` 加一份 `SENSITIVE_FIELDS` 清单并覆盖 `__repr_args__`：

```python
def __repr_args__(self):
    for name, value in super().__repr_args__():
        yield (name, "***") if name in SENSITIVE_FIELDS else (name, value)
```

为什么用**集中清单**而不是给每个字段加 `Field(repr=False)`：
- 逐字段写会**漏**（新增密钥字段的人不会记得加，而漏了毫无症状）
- 集中一份让它有**唯一出处** —— 与 `RETRIEVER_CONFIGS` / `LLM_CHANNELS` / `HARNESS_RISK_LEVELS` 是**同一个设计手法**（"唯一合法取值清单必须有一个权威出处"，本项目反复在用）

**② NUL 字节（`%00`）导致 500**

`curl 'localhost:18000/api/eval/cases/%00'` → PostgreSQL 抛
`asyncpg.exceptions.CharacterNotInRepertoireError: invalid byte sequence for encoding "UTF8": 0x00`

**参数化查询救不了它** —— 这不是 SQL 注入（值没有被拼进 SQL），而是**这个字符本身非法**。不拦的话它会以 **500** 的形式冒出来，把一个"用户输入问题"**伪装成"服务端故障"**，污染错误监控。

**修法**：在 `app/main.py` 加一个中间件，路径里出现 NUL 字节直接 **400**（查 `request.url.path` 和 `scope["raw_path"]` **两处** —— 前者是解码后的，后者是原始字节，某些百分号写法会漏）。

## 7. ★ 今日问答落盘（步骤① 复述 · 三轮）

> **规则**：这份记录含**用户原答逐字**、判定、**错因**。
> 三轮都保留 —— 因为"错在哪、怎么改对的"比"最终答案"值钱。

### 7.1 题干（三个问题，来自原理环节）

1. **容器是什么？**
2. **为什么容器里连不上 `localhost`？**
3. **容器里要连数据库，那个位置该写什么？那个名字是从哪来的？**

### 7.2 第一轮

**用户原答（逐字）**：

> 1. 容器就是一个包裹所有服务的一个盒子，里面按照名字去区分，给每一个服务一个单独的空间，可以安装对应的依赖，不会相互影响，并且可以根据盒子的名称去进行具体的访问。
> 2. 因为localhost代表的是本电脑，但是容器相当于另外一个电脑，所以无法访问。
> 3. 应该写/api，这个名字从YAML文件里面写的服务名

**判定**：

| 题 | 判定 | 原因 |
|---|---|---|
| 1 | ⚠ **半对（模型装反了）** | 「给每个服务一个单独空间、装各自依赖、互不影响、按名字访问」**全对**；但开头「**一个包裹所有服务的盒子**」是错的 —— 用户**自己的句子里前后矛盾**。正确：**一个服务 = 一个容器 = 一台迷你电脑**（4 服务 = 4 台），把它们连起来的是 compose 建的**局域网**（公共的），不是盒子（各自的） |
| 2 | ✅ **对**（补一处精度） | 理由说对了。补：报错文本是 **`Connection refused`**（找到了地址但门后没人），**不是 `timeout`** |
| 3 | ❌ **错** | ① 答案应是 **`db`**；② `/api` 是**路径**不是**机器名**，那个位置只能填主机名；③ 「名字来自 YAML 服务名」**这半句是对的** |

**★ 错因分析（比答案值钱）**

用户不是凭空编的 —— `/api` **确实存在于这个项目里**，但在**另一个位置**：web 容器里 nginx 的转发规则 `location /api/ { proxy_pass http://api:8000; }` —— **同一行里 `/api` 是路径、`api` 是主机名**。用户把这两个角色**合并成了一个**。

这与他做前端的经验**直接相关**：`vite.config.ts` 的 `server.proxy` 里 `/api` 就是**路径前缀**。
→ **迁移式误解**：把前端「路径」的心智模型直接搬到了容器的「地址」位置上。

**教学对策**：讲 nginx 转发时**必须明确指出** `location /api/` 与 `proxy_pass http://api:8000` 里两个角色的差异（已在 §1.⑧ 落地）。

### 7.3 第二轮（修正后重答）

**用户原答（逐字）**：

> 1. 一个服务=一个容器=迷你电脑，是相互独立的，不能相互访问。而他们直接连接的局域网才是公共的。
> 2. 要连接数据库要写db，因为后面连接的是服务名称，所以不能使用/api，api是根据需要连接的服务名称自定义的

**判定**：

| 题 | 判定 | 原因 |
|---|---|---|
| 1 | ⚠ **基本对，一处必须修** | 「一个服务 = 一个容器 = 迷你电脑」✅（上轮核心错误已纠正）·「局域网才是公共的」✅ —— 但**「不能相互访问」是错的**，且**与自己后半句矛盾**（既然局域网是公共的，就能通过它互访）。正确：容器之间**独立**（各自文件系统/依赖/端口），但**能互相访问** —— 这正是写 `db:5432` 的**前提**。★ 若"不能互访"成立，第 2 题就不成立 |
| 2 | ✅ **基本对，一处需钉死** | 「要写 db」✅、「那个位置连的是服务名」✅、「不能用 `/api`」✅。**模糊处**：末句表述不清。需钉死：填的是**目标服务在 YAML `services:` 下的 key**。★ **关键补刀**：`api` **本身也是个服务名** —— 所以即使去掉斜杠写成 `api` **依然错**（那指的是 api 自己，而 api 上没有数据库） |

**★★ 同一错型（两轮都是）**：用户**两轮都把答案写成自相矛盾的两半**（上轮"一个盒子装所有服务"＋"每个服务单独空间"；本轮"相互独立不能互访"＋"局域网是公共的"）。

→ **教学对策**：遇到"半句对半句错"时，**优先抓自相矛盾**（用户手里其实已握有正确答案，只是没对齐），比重新讲一遍有效得多。

### 7.4 第三轮 ＝ 通过 ✅

**用户原答（逐字）**：

> 4个容器有各自独立的系统，但是他们可以互相访问，通过的是局域网，并服务名去进行访问

**判定**：✅ **三要素齐** —— **各自独立**（系统）＋ **可以互相访问** ＋ **靠局域网 / 服务名**。
前两轮的核心错误（"一个大盒子装所有服务"、"不能相互访问"）**均已纠正**。

**步骤① 共三轮**：1 轮（1 过 / 1 半对 / 1 错）→ 2 轮（1 基本对 / 1 过）→ 3 轮 **通过**。

| 3 | **端口"冲突"误判** | 用 `docker ps \| head -10` 把排在第 16、17 行的本项目容器**吃掉了**，误判成"别人占了端口"。**凡 head/tail 截断后下结论，必须先确认截断点之后没有关键行** |
| 4 | **`schema` 的 `required` ≠ 完整约束** | `harness_list` 的 `resource_type` **不在 `required` 里**，服务端却硬要。→ **schema 只声明了一部分** |
| 5 | **`enum[0]` ≠ "默认值"** | 补齐参数后仍红：挑了 enum 的**字母序第一个**，它需要额外上下文。★ **enum 的顺序不表达推荐程度** |
| 6 | **写了一条恒真断言** | C1 第一版写成 `check(..., True, ...)`（永远绿）。**"写了断言" ≠ "断言有用"** |
| 7 | **pytest 的"跨事件循环"** | `db.engine` 是模块级创建的，连接池绑定创建时的 loop；pytest 默认每个测试新 loop → 前一个结束后连接绑在**死 loop** 上。修法：`asyncio_default_test_loop_scope = "session"` |
| 8 | **`unregister_source` 参数写成了 namespace** | 注册时写进 `source` 的是 **`spec.name`**，不是 namespace（namespace 只影响工具**名前缀**）。写错会留下摘不掉的工具，下一个用例报"工具名重复" |
| 9 | **断言里用了"同一个类型"做对照** | 见 §6.2 → 修法是换一个**不可能被包装出来**的类型 |

> ★ **第 2、3 条同属一类**：**取证方式**出了问题，不是被检对象有问题。
> 本项目已第 7、8 次遇到"报警先怀疑检查器"——**修法永远是改检查器，不是改被检对象**。

## 11. 面试可以怎么讲

**Q1：你们项目的 Docker 是怎么组织的？**
四服务（db / redis / api / web）一条 compose 起。api 是 Python+uv 自建镜像，前端走**多阶段构建**（node 构建 → nginx 托管），最终镜像 52 MB 且**不含 Node**。db/redis 复用既有容器，本次**一行未改** —— 因为改了配置就会触发重建，白白重启一次数据库。

**Q2：前后端怎么打通的？为什么不是 CORS？**
后端**没有配 CORS**，前端 `baseURL` 是相对路径 `/api`，由 nginx 同源反代到 `api:8000`。这样既避免跨域，也让浏览器只看到一个源。★ 有个坑：`proxy_pass` 尾部**不能**带斜杠 —— 带了会用 `/` 替换掉 location 匹配的部分，把后端自带的 `/api` 前缀剥掉，直接 404。

**Q3：遇到过什么比较隐蔽的问题？**
nginx 把 `proxy_pass` 里的字面主机名**只在启动时解析一次**，之后永不重查。所以重建 api 容器（拿到新 IP）后，web 会**持续 502** 直到 web 自己也重启。我们用 `resolver + 变量` 让它按间隔重解析。
★ 而且第一次做对照实验时**实验本身是无效的** —— 新建容器**复用了旧 IP**，两种情况无法区分；后来先用一个占位容器把旧 IP 抢走，才拿到能区分的证据。

**Q4：测试怎么保证不依赖外部服务？**
LLM 层替换的是网关的**单通道调用点**而不是整个 `chat()` —— 这样"主通道失败→切备用"这段**降级逻辑被真跑到**，测的不是 mock 自己。MCP 层用本机自研的 `MCPServer` 当假 server（真协议真子进程，但不碰网络）。真连外部 SaaS 的用例标 `external`，**默认跳过**。

**Q5：覆盖率多少？**
核心链路加权 **74.5%**（PRD 要求 ≥60%）。但全项目只有 **51%** —— 差异来自评测链路（`eval_runner` / `judge_service` / `eval_report_service`）和可观测取数通道**目前是 0%**。**它们不是"测过了"，是"还没测"**，已经登记为待办。
