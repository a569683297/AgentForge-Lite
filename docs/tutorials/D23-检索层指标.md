## §2 核心概念讲解

### 2.1 先看清"评测有三层"，才能理解为什么要下沉

一次 RAG 评测其实是一条**三层流水线**，每层都会失真：

```
  ① 检索层     问题 → retrieve() → 排好序的片段列表
                   ↓  这一层错了，后面全错
  ② 生成层     LLM 读片段 → 写出答案
                   ↓  这一层是随机的（同问题两次答案不同，D21 实测 10.0%）
  ③ 判定层     judge 拿参考答案打分
                   ↓  这一层也有噪声（D20 实测 ε = 0.95%）
  ─────────────────────────────────────────────
  答案级指标（准确率）= 三层噪声叠加后剩下的那一点信号
```

**名词注解**：
- **RAG**（Retrieval-Augmented Generation，检索增强生成）：先从知识库检索相关片段、再让 LLM 依据片段回答。本项目就是这条路（`问 → 检索 → 拼进 prompt → 回答`）。
- **答案级指标**：只看"最终答案对不对"（准确率 / 正确性均分），不关心错在哪一层。
- **检索层指标**：只看"检索有没有把正确的文档捞回来"，不看 LLM 怎么写。

D22 的做法是答案级：跑生成 → judge 打分 → 98% / 98% / 98%，一条差异都没有。
但"没有差异"有三种可能，答案级**分不出来**：

| 可能 | 表现 |
|---|---|
| (a) 三个配置确实一样好 | 真实结论 |
| (b) 都在天花板（题太简单） | 指标量不出差异 |
| (c) 判定层坏了（假失败把差异吃掉） | D23 前两步已排除 |

D23 前两步修好了 (c)；**本文这一步是去验证 (b)** —— 而且用了最直接的办法：
**把②③两层整个拆掉**，只留①。

### 2.2 gold 文档（标准答案文档）

**gold**（ground truth，标准答案）：这道题的答案**应该来自哪几篇文档**。

本项目里就是 `eval_cases.doc_ids`（UUID 数组），出题时逐条标注。例如：

| 题 | 依据文档 |
|---|---|
| A01「员工累计工作满 1 年但不满 10 年的，年假有几天？」 | `annual-leave` 1 篇 |
| B02「请假对绩效考核有什么影响？」 | `annual-leave` + `performance` 2 篇 |

**两条纪律**：

1. **gold 只用于判分统计，绝不能当检索过滤条件**。一旦拿它过滤检索（"只在这两篇里搜"），等于开卷考试还给页码 → 检索难度归零，A/B/C 的差异被整体抹平，评测结论从根上失效。
2. **不是所有题都有 gold**。50 条题里只有 **35 条**能算：

| 类别 | 数量 | 有没有 gold | 为什么 |
|---|---|---|---|
| 单文档问答（`doc_qa`）非负例 | 25 | ✅ | 答案出自某一篇 |
| 跨文档推理（`cross_doc`） | 10 | ✅ | 答案出自两篇 |
| **负例**（`is_negative`） | 5 | ❌ | 正确答案是"知识库里没有"，**按定义就没有依据文档** |
| **工具类题**（`tool_call`） | 10 | ❌ | 判定依据是"有没有调对工具"，与检索质量无关 |

→ **15 条被排除，不是"算不出"，是"按定义没有正确答案文档"**。分母口径必须写到报告里。

### 2.3 Hit@k（命中率）

**定义**：top-k 结果里**至少有一条**来自 gold 文档集合 → 记 1，否则 0。对全部题取平均。

**为什么需要"文档级去重"**（本步最容易写错的地方）：

一篇文档会切成很多片（本项目 `CHUNK_SIZE=300` 字/片，8 篇切出 51 片）。
同一篇文档可能一次命中好几片 → 如果不去重，**一篇文档就能把 top-5 占满**。

去重 = 每篇文档只记它**最早出现的名次**：

```
命中片段（按名次）:  [片1(annual-leave), 片2(annual-leave), 片3(annual-leave), 片4(performance)]
不去重 → 4 条命中      → "命中率很高"
去重后 → {annual-leave:1, performance:4}  → 2 篇文档，且第二篇排第 4
```

**不去重会让两个指标朝相反方向错**（都不报错）：

| 指标 | 不去重会怎样 |
|---|---|
| `Hit@k` | **虚高** —— 自己跟自己重复计数 |
| `Hit@k(all)`（跨文档题的"两篇都捞到"） | **永远为假** —— 第二篇被第一篇自己的切片挤出了窗口 |

### 2.4 MRR（平均倒数名次）

**MRR**（Mean Reciprocal Rank）：第一篇 gold 文档排第几名，就记 `1/名次`，再对全部题取平均。

```
  第 1 名命中 → 1.000
  第 3 名命中 → 0.333
  没命中      → 0
```

它比 Hit@k 敏感：Hit@5 只问"在不在前 5"，MRR 还问"排多前"。

### 2.5 为什么必须新加 `MRR_last`（本步的核心发现）

**标准 MRR 在这份数据上恒等于 1.000** —— 因为 35 道题的**第一篇** gold 文档，
三个配置下**全部排在第 1 名**（实测 `35/35`，名次分布只有 `[1]` 一个值）。

原因很直接：语料只有 **8 篇**，而题面是**照着原文条款写**的（出题流程就是"先立语料 → 再从语料里挑事实出题"），
字面几乎重叠 → 任何检索方式都能把它排第 1。

**于是 MRR 完全没有信息量** —— 它已经没有上限可测了。

但跨文档题（B 类）有**两篇** gold，第一篇恒第 1 名，**第二篇不一定**：

```
B02:  A [1, 7]    B [1, 6]    C [1, 2]
      ↑第一篇恒第1名     ↑第二篇才是真正的质量差异
```

所以本步引入 **`MRR_last`**：**最后一片** gold 的倒数名次。
「第一篇第 1、第二篇第 7」的检索质量，显然不如「第 1、第 2」。

> 一句话：**MRR 量"最好的那一篇"，MRR_last 量"最差的那一篇"。**
> 跨文档题的质量由后者决定 —— 只捞到一篇，答案必然不全。

### 2.6 随机基线（random baseline）—— 回答"100% 有没有信息量"

**问题**：三配置 Hit@5 都是 100%。这是"检索很准"还是"语料小到谁都能进前 5"？

**负对照做法**：把「随便一篇**非 gold** 文档」当答案，看它能不能落进 top-k。

```
  随机基线@5 = 4.5%（A）/ 9.4%（B）/ 9.4%（C）
  真实 Hit@5 = 100%
```

→ 差 10~20 倍，**说明指标确实在区分"对的文档"和"别的文档"**，比对逻辑没坏。
→ 但**三配置之间完全一样** → 说明在这份语料上，三者确实没有分别。

**这是"负对照"的典型用法**：一个指标只有在"喂错东西时真的会掉下来"才可信。
`d23_metrics_verify.py` 的 E 段把它做成了断言：把 gold 换成**错的文档**，
Hit@5 必须从 100% 掉到 40% 以下（实测 **17.1%**）。

### 2.7 Wilson 置信区间

**置信区间**：样本只有 10 条题时，「8/10 命中」这个**点估计**并不精确 ——
换一批同分布的题可能得到 6/10 或 10/10。区间给出"真值大概落在哪"。

**Wilson 区间**是其中一种算法。为什么不用最简单的 `p ± 1.96·√(p(1-p)/n)`：
后者在 p 接近 0 或 1 时会算出**超过 [0,1] 的区间**（100% 命中时算到 105%），Wilson 不会。

实测：

| 配置 | 跨文档题「两篇都进 top5」 | Wilson 95% |
|---|---|---|
| `pure_vector` (A) | 8/10 = 80.0% | **[49.0%, 94.3%]** |
| `hybrid` (B) | 8/10 = 80.0% | **[49.0%, 94.3%]** |
| `hybrid_rerank` (C) | 10/10 = 100.0% | **[72.2%, 100.0%]** |

**两个区间重叠** → **不能下"重排更好"的结论**。
观测值 C 确实更好，但 10 条题的样本量**不足以排除运气**。

> ⚠ 一个容易搞混的点：检索层是**确定性**的（同一份语料重跑 100 次，结果逐字相同），
> 所以这个区间衡量的**不是"重跑会不同"**，而是**"换一批题结论还稳不稳"** ——
> 即**样本量不足**。两者都是"不确定性"，但来源完全不同。
> （同 D20「重复的是裁判还是输入」那条判据。）

### 2.8 为什么这一层本应有分辨力

| 层 | 有噪声吗 | 成本 |
|---|---|---|
| 检索层 | **无** —— 确定性，同输入同输出 | **零 token** |
| 生成层 | 有 —— 同问题两次答案不同（10.0%） | 花钱 |
| 判定层 | 有 —— ε = 0.95% | 花钱 |

**本步的核心优势**：只量检索层 → **不调 LLM、不调 judge、零 token**。
35 题 × 3 配置全部跑完的成本是 **电费**（A 2.6s / B 1.4s / C 35.1s，重排是大头）。

## §3 代码逐行解读

### 3.1 `scripts/d23_retrieval_metrics.py`（指标主脚本）

#### 模块 docstring（先说清定义再写码）

文件开头把**每个指标的定义**、**三个坑**、以及 **B 与 C 的对比为什么是干净的**全部写清。
这不是装饰：指标类脚本的 docstring 就是它的规格说明，读的人首先要知道"这个数是分母除谁"。

#### `wilson(k, n, z=1.96)` —— 置信区间

```python
lo = (center - margin) / d
hi = (center + margin) / d
return (max(0.0, lo), min(1.0, hi))     # ← 夹到 [0,1]
```

**`max(0.0, ...)` 是本次实测抓出来的一个真实缺陷**：
`k=0` 时 `center` 与 `margin` 在浮点上未必精确相等，相减会得到 `-2.8e-17` ——
**一个负的概率**。它打印出来是 `-0.0%`（看着无害），但它是错的数，
下游若拿它做区间比较就会出错。

抓出它的是 `d23_metrics_verify.py` 的 **A6 断言**（遍历 0/10~10/10，
断言"下界 ≤ 点估计 ≤ 上界且都在 [0,1] 内"）。
**第一次跑就红了** —— 这就是"写断言"的意义：这个缺陷靠肉眼看输出是发现不了的。

#### `load_cases(conn)` —— 顺带说出排除理由

```python
if item["doc_ids"]:
    usable.append(item)
else:
    reason = "负例（正确答案是拒答，没有 gold 文档）" if item["category"] == "doc_qa" \
        else "工具类题（判定依据是工具调用，与检索质量无关）"
    excluded.append({**item, "reason": reason})
```

**判据来自数据本身**（`doc_ids` 有没有值），不是 `category` 的名字 ——
"有 gold 才算得了"这件事，是数据说的，不是名字说的。
把排除理由**存下来**而不是就地丢掉，是为了让报告能打印"分母少了谁、为什么"。

#### `check_gold_alignment(conn, cases)` —— 坑①的硬闸

```python
return (len(gold_ids), len(found), sorted(str(x) for x in (gold_ids - found)))
```

**这个函数存在的唯一理由**：把「标注失效」和「检索坏了」区分开。

`doc_ids` 指向 `documents.id`，而**重建语料必然生成新 UUID**。
一旦语料被重建（`d21_seed` 重跑过），所有 `doc_ids` 集体指向不存在的 UUID
→ 所有题都变成"未命中" → **指标全 0%**。

这时看上去像"检索彻底坏了"，实际是**标注失效**。
不做这一步核验，你会去乱改本来正确的检索代码。

`run()` 里的硬闸：

```python
if missing or n_gold == 0:
    print("❌ gold 标注与当前语料对不上 —— ...")
    return 1                      # ← 拒绝出指标，而不是打印一堆 0%
```

**同 D22「指纹不等就拒绝出报告」**：数据不可信时不给数字，比给一个错的数字好。

#### `ranks_by_document(hits, chunk2doc)` —— 坑②+去重

```python
best: dict = {}
for rank, h in enumerate(hits, start=1):
    did = chunk2doc.get(h.get("chunk_id"))
    if did is not None:
        best.setdefault(did, rank)     # ← setdefault：保留**最早**出现的名次
return best
```

两个细节都是**错了不报错**的类型：

- `chunk2doc.get(...)` 而不是 `[...]` → 映射里没有的 chunk_id 跳过，
  宁可少一条，也不要因为一条脏数据让整轮崩。
- `setdefault(did, rank)` 而不是 `best[did] = rank` →
  后者会留下**最后一次**出现的名次 → 名次被系统性拉低 → `MRR_last` 偏低，**全程不报错**。
  `d23_metrics_verify.py` 的 **B6** 专门做了这个反面对照：
  `direct assignment` 得到 `D1=3`（错），`setdefault` 得到 `D1=1`（对）。

**为什么这一步必须能单测**：它是全脚本最容易写错、且错了最不容易发现的地方。
抽成纯函数才能喂人工数据进去断言。

#### `collect(config, top_k, cases)` —— 跑一个配置

```python
try:
    hits = await retrieve(c["question"], top_k=top_k, config=config)
except Exception as e:  # noqa: BLE001
    errors.append(f"{c['case_key']}: {type(e).__name__}: {e}")
    hits = []
```

单题失败**不中断整轮**（同 `eval_runner` 对生成失败的处置）：
"哪个配置跑不通"本身就是有价值的数据，扔掉它等于把"系统稳定性"从评测里删掉。

```python
for h in hits:
    retriever_tags[h.get("retriever") or "?"] += 1
```

**统计的是"实际走通的链路"，不是配置名**。这是 D19「降级必须可归因」的复用：
C 配置在重排失败时会退回融合序，并把 `retriever` 标成 `hybrid`。
如果只按配置名分组，**降级样本会被算成重排的成绩**，而代码不会有任何报错。

#### `metrics(block, corpus_size)` —— 每个指标都带分母

- `hit_any(k)`：`any(x <= k for x in gold_ranks)`
- `hit_all(k)`：`len(gold_ranks) == n_gold and all(x <= k ...)`
  —— 先判"gold 全在里面"再判"都在 top-k"，否则单文档题会被误算
- `mrr`：`1 / gold_ranks[0]`（第一篇）
- `mrr_last`：`1 / gold_ranks[-1]`（最后一篇）
- `random_base(k)`：非 gold 文档落进 top-k 的比例，**逐题算再平均**
  （不能把全部题的非 gold 名次拼成一个大池子 —— 那就变成"文档越多基数越大"，
   题间 gold 数不等时会失真）

#### `print_ceiling` / `print_cross_doc` / `print_conclusion` —— 结论由数据决定

三段结论文字全部写成 `if/else`，随数据变化（铁律 11：禁止硬编码结论）。
例如：

```python
if all(m["first_rank_one"] == m["n_cases"] for m in mets):
    print("  ⚠ **每一道题的第一篇依据文档，三个配置下都排在第 1 名**。")
    ...
else:
    print("  首篇名次并非全为 1 → Hit@k 仍有余量可测。")
```

`print_per_case` 里还**主动报出反向案例**：

```python
print(f"  {worst} vs {base}：变更靠前 {better} 条、变更靠后 {worse} 条")
```

只报"重排更好"的例子就是选择性汇报 —— 实测有 1 条题 C 反而比 A 差（B09）。

### 3.2 `scripts/d23_metrics_verify.py`（33 条断言）

指标算错了不会报错，只会让数字悄悄偏，所以必须用断言钉住。五段：

| 段 | 验什么 | 条数 | 要不要碰库 |
|---|---|---|---|
| **A** | Wilson 区间（含边界：0/10、10/10、5/10 对称、n=0） | 6 | 否 |
| **B** | 文档级去重（含"直接赋值会怎样"的反面对照） | 6 | 否 |
| **C** | `metrics()` 手算对照（3 道人工构造的题，每个指标都手算过） | 11 | 否 |
| **D** | 分母口径（35 / 15 / 25+10 / 语料 8）+ gold 对齐 | 7 | 是 |
| **E** | **负对照**：把 gold 换成错的文档，指标必须掉下来 | 3 | 是 |

C 段的手工数据与期望值（**每个数都是手算的，不是"跑出来看着对"**）：

```
X1 单文档题，gold 第 1 名，2 篇非 gold 在第 2、3 名
X2 单文档题，未命中，2 篇非 gold 在第 1、2 名
X3 跨文档题，gold 在第 1、4 名，2 篇非 gold 在第 2、3 名
corpus_size = 8

Hit@1 = Hit@5 = 2/3          （X2 未命中）
Hit@5(all) = 2/3             （X1 单篇命中；X3 两篇都在 top5）
MRR  = (1 + 0 + 1)/3    = 0.6667
MRR_last = (1 + 0 + 0.25)/3 = 0.4167   ← X3 取**最后一篇**的第 4 名
随机基线@5 = (2/7 + 2/7 + 2/6)/3 = 0.3016
```

**C7 是一条"设计意图"断言**：`MRR_last ≠ MRR` —— 证明引入它确实能看出标准 MRR 看不到的退化。

E 段（负对照）实测：

```
E1 真 gold：Hit@5 = 100.0%
E2 错 gold：Hit@5 =  17.1%    ← 必须 < 40%，否则说明比对逻辑恒真
E3 随机基线@5 =  4.5%
```

## §5 面试考点

**Q：你们的 RAG 评测为什么不用正确的答案率就够了，还要做检索层指标？**

> 因为准确率是三层噪声叠加后的结果：检索错了、生成随机、judge 有抖动，
> 三层混在一起，**"没差异"分不清是"配置一样"还是"指标量不出"**。
> 我们把中间两层整个拆掉，只量检索 —— 这一层是**确定性**的，同输入同输出，
> 而且**零 LLM 成本**，35 题三配置跑完只要 40 秒。
> 结果是：三层全部撞天花板（生成 98% / 判定 98% / 检索 100%），
> 于是**问题定位从"哪个配置好"变成了"任务难度不够"** —— 这是换指标换不出来的。

**Q：Hit@5 你们是 100%，这个数字有意义吗？**

> 单看没有意义，所以我们报了**随机基线**做负对照：随便挑一篇非 gold 文档，
> 只有 4.5%~9.4% 能进 top5。差十几倍说明指标确实在区分对错。
> 但三个配置之间完全一样，而且 35 题里**每一题的第一篇依据文档都排第 1 名** ——
> 这是因为语料只有 8 篇、题面又照着原文条款写。
> **所以 100% 不代表"检索完美"，代表"这份语料区分不开"。**

**Q：那你们怎么知道重排（rerank）到底有没有用？**

> 只在一处看到了梯度：**跨文档题的第二篇依据文档的名次**。
> 纯向量 `[4,7,6,3,3,3,3,2,3,3]`、混合 `[3,6,5,2,2,3,3,2,6,3]`、
> 重排 `[2,2,2,3,2,3,2,2,4,2]`。重排明显把第二篇往前拉。
> 但跨文档题只有 10 条，Wilson 95% 区间 A `[49%, 94%]` 与 C `[72%, 100%]` **重叠**，
> **样本量不足以确证**。而且逐题看有 1 条题重排反而变差 —— 重排不是单调变好。
> 要确证，得加跨文档题或加语料，而不是继续换指标。

## §7 踩坑记录

| # | 坑 | 后果 | 处理 |
|---|---|---|---|
| 1 | `wilson(0, n)` 的下界因浮点误差算成 `-2.8e-17` | 一个"负的概率"，打印是 `-0.0%`，下游比较会出错 | `max(0.0, lo)` / `min(1.0, hi)` 夹住；**由 A6 断言抓出**（第一次跑就红） |
| 2 | 一开始想**解析历史 `retrieved_chunks` 文本**来算指标 | 那是给 judge 看的**渲染文本**（`[名次] 来源：文件名`），从渲染结果反推数据很脆；且它**没有 chunk_id** | 改为**重跑检索层**：直接拿 `chunk_id` → `document_id`，与 `doc_ids` 精确比对 |
| 3 | `gold_ranks` 里若含 `None`（文档已删） | `sorted()` 会 `TypeError` | `ranks_by_document` 里 `if did is not None` 直接过滤 |

| 5 | 差点把 B 与 C 的差异全归因给"重排" | 其实要先确认两者的**融合输入是否一样**；本项目两路各取 20 条，差别只在"融合后是否重排" → 归因干净 | 在 docstring 里写明这条链路对比，并统计 `retriever_tags` 证明没有大规模降级（实测 C **100% 走了重排**） |

## 附录 B：结论与下一步

**本步的收获不是"拿到了区分度"，而是把问题定位到了层**：

```
  生成层（答案级）   98% / 98% / 98%     ← 天花板
  判定层（修复后）   98% / 98% / 98%     ← 天花板
  检索层（本步）    100% / 100% / 100%   ← 天花板
```

三层全到顶 → 瓶颈**不在重排、不在评测器**，而在**任务难度**：

- 语料只有 8 篇、51 片
- 25/35 是单文档题，题面照着原文条款写 → 首篇 gold 恒排第 1 名
- 唯一还有梯度的跨文档题只有 10 条 → 区间重叠，结论下不了

**下一步的三条候选路**（见 [`评测总纲.md`](评测总纲.md) §3 待办）：

| 选项 | 做法 | 成本 | 本步之后的判断 |
|---|---|---|---|
| ① 把题加难 | 换掉太简单的题（尤其**加跨文档题**） | 要重出题 + 重新冻结指纹 → **ε 作废** | **证据指向这里** —— 唯一还有希望的方向 |
| ② `generation_runs` 提到 3 | 治生成侧抖动（每轮 ≈25 分钟/配置） | 花钱；**不增加分辨力** | 不解决"区分不开" |
| ③ 补检索层指标 | ← **本步已完成** | 零 token | 做完后证明：**检索层也是天花板**，已排除 |
