★ 名词先说清（后面全部要用）：
- **trace（追踪）** = 一次完整业务动作的记录（本项目 = "用户问一句、系统答完"这**一整轮**）。它是**容器**。

## §2 名词先注解（全部在此，不外链）

这一节的存在理由同 D26/D27：下面 §3 起会连续用到这些词。**不先定义就用，等于用一堆我不确定你熟不熟的东西解释新东西。**

### 2.1 今天新出现的

| 名词 | 它是什么 | 它解决什么问题 |
|---|---|---|
| **trace（追踪）** | 一次完整业务动作的记录（本项目 = 一整轮对话）。它是**容器** | 回答"这一轮里发生了哪些事、各花了多久" |
| **span / observation（跨度 / 观测）** | trace 里**一段具体工作**的记录（如一次 LLM 调用 / 一次检索）。它是**内容物** | 回答"这**一段**花了多久、输入输出是什么" |
| **根 span（root span）** | 埋在点（顶点）的那一个 span，**它自己就是那条 trace 的载体** | 没有它，每个 span 都是孤儿 → 各自一条 trace（§3） |
| **埋点树** | 一个 trace 下所有 span 按父子关系组成的树（本文起的名，方便指代） | "全链路可追踪"看的就是这棵树的形状 |
| **OTEL / OpenTelemetry** | 一套**通用的埋点标准**（span / trace / 父子 / contextvars 都是它定义的）。Langfuse 建在它上面 | 让"埋点"这件事不绑定某一家厂商；也解释了"父是谁自动算"的机制来源 |
| **`TracerProvider`** | OTEL 里"造 span 的工厂 + 分发器"：所有 span 由它产出，并交给挂在它上面的处理器 | 它是**挂内存 exporter 的入口**（§7.8 进程内取证靠它） |
| **span processor（处理器）** | 挂在 `TracerProvider` 上、负责"span 结束后怎么办"的组件 | Langfuse 默认挂的是**批量导出**（推给服务端）；我们另挂一个**内存**的（留在本地） |
| **`InMemorySpanExporter`** | OTEL 自带的一个"导出器"：把结束的 span **收到内存列表里**，不推网络 | 让验证脚本能**进程内**读回整棵树（不依赖网络与服务端延迟） |
| **`propagate_attributes`** | Langfuse 4.x 的**模块级函数**，用来给"当前这条 trace"贴属性（session_id / user_id / trace_name …） | 它替代了旧版（≤3.x）的 `update_current_trace`（本版本**没有**那个方法） |
| **观察类型（observation type / `as_type`）** | 每个 span 必须声明"自己是哪一类工作"（generation / tool / retriever / embedding / agent …） | ★ **它不是给人看的标签** —— 它**决定哪些字段能写进去**（§4.2） |
| **generation-like** | 观察类型里的**一类**：`generation` 与 `embedding` | 只有这类能带 **model 名 / token 用量 / 成本 / prompt / 首字延迟** |
| **span-like** | 另一类：`span` / `agent` / `tool` / `chain` / `retriever` / `evaluator` / `guardrail` | 这类**带不了**上面那些字段（传了也**静默丢弃、不报错**） |
| **P95（第 95 百分位）** | 把所有耗时从小到大排，排在 95% 位置的那个值 | 比"平均值"更能反映"最慢的那批有多慢"（平均值会被大量快请求拉平） |
| **最近秩法（nearest-rank）** | 求分位数的一种口径：直接取"确实存在的那条记录"的值（不插值） | 与 SQL 的 `percentile_disc` 一致 → 两个数据源**同构**（F11.7 要求） |
| **页码分页 / 游标分页** | 两种翻页方式：前者用 `page=1/2/3…`；后者用**上一页返回的一个游标串**接着翻 | Langfuse 的 v1 用页码、v2 用游标 → 两代 API 的翻页代码完全不同 |
| **429 / 限流（rate limit）** | HTTP 状态码 429 = "你请求太密了，先歇会儿" | 今天实测撞到过 → 决定了"读通道不能自动重试"（§6.3） |
| **降级（degrade）** | 某个依赖出问题时，**只让那部分功能变弱**，不拖垮整体 | PRD F8.5.4 要求"Langfuse 挂了只该指标报错"（§6.3） |

## §3 埋点树：为什么"全链路"以前做不到

### 3.1 病灶：每个 span 都是孤儿

先看**现状**（D28 之前）。我读了 Langfuse SDK 源码确认机制（不是推测）：

- `langfuse/_client/client.py` 第 **1124** 行：**调用者没给 `trace_context` 时**，直接走
  `self._otel_tracer.start_as_current_span(...)`。
  （`trace_context` = 一个"挂到指定 trace"的可选参数；传了它走另一条路 —— 不建真 span、只造一个"哑父"，
  细节见附录 A.5。本项目今天**不用**它。）
- OTEL 的语义是：**新 span 的父 = 当前上下文里正在活动的那个 span**。
- 而 `run_agent` 里**没有任何外层 span** 包着 `get_agent().ainvoke(...)`。

所以结论是：**以前每调一次 LLM，那个 generation 就自己变成根 span = 自成一条 trace**。
一轮对话如果 plan + answer 调了 2 次 LLM，Langfuse 上就是**两条互不相干的 trace** ——
你没法回答"这一轮里检索花了多久、工具花了多久"。

**实测钉死**（探针 `order_probe.py`）：不用根 span 时，两个 generation 的 `trace_id` 分别是
`f95d9d…` 和 `249920…` —— **两条独立 trace**。

### 3.2 修法：套一个根 span，让"当前活动 span"存在

```python
with trace_attrs(session_id=session_id, trace_name=SPAN_ROOT):   # ① 先贴 trace 属性
    with span(SPAN_ROOT, as_type="agent") as root_span:          # ② 再建根 span
        result = await get_agent().ainvoke(state, ...)           # ③ 图在里面跑
        root_span.update(output={...})
```

只要外层有 `with span(...)` 包着，**在它"活动期间"创建的所有 span 都会自动挂到它下面** ——
不再需要手动传 trace_id。

**实测钉死了两件"看起来会丢上下文"的场景仍然成立**（探针 `ctx_probe.py` + 编码后 C 段）：

| 场景 | 结果 |
|---|---|
| 跨 **LangGraph 节点**（节点函数是独立协程） | ✅ 三层 `trace_id` 完全相同 |
| 跨 `asyncio.gather` 的**并发分支** | ✅ 保持 |

原因是 OTEL 用 `contextvars` 实现，而 asyncio 创建子任务时会**复制**当前上下文。
→ **这也是"根 span 方案能成立"的全部地基**：如果上下文一跨节点就丢，整个方案不成立。

### 3.3 修好之后长这样（实测打印，不是示意图）

以下是从验证脚本 C 段**真实打印出来**的树（`run_agent` 跑一轮"公司的年假有几天？"，3.5s）：

```
run_agent                  type=agent         session=30fbabf5-…   ← 根（今天新加）
  agent-plan               type=generation    session=30fbabf5-…   ← D5 起就有
  tool:search_documents    type=tool          session=30fbabf5-…   ← 今天新加
    retrieval              type=retriever     session=30fbabf5-…   ← 今天新加（父）
      bm25                 type=retriever     session=30fbabf5-…
      vector_search        type=retriever     session=30fbabf5-…
        embedding          type=embedding     session=30fbabf5-…
      rerank               type=retriever     session=30fbabf5-…
  agent-answer             type=generation    session=30fbabf5-…
```

★ **这条树里最值钱的一格**：工具 span 的 `metadata.source`（§5 讲）—— 它回答的正是验收②。

⚠ 一处**刻意的范围选择**：根 span **到"取答案"为止、不含后面的写回会话记忆**。
理由：写回是副作用、不占用户等待时间；把它算进根 span 的 latency，会让"这一轮慢在哪"失真 ——
而 D28 之后这个 latency 是要被**当指标读的**（D35 的 `latency_p95`）。

⚠ 另一处：树里会不会多出一格跟 `tool:search_documents` 很像的？**会** ——
MCP SDK **自带埋点**，会多出一格 `MCP send tools/call <工具名>`。它和我们的 `tool:<名>` 是**父子**关系
（SDK 那格是内部的传输动作），**不是重复埋点**。

## §4 三条埋点纪律（每条都对应一个实测过的坑）

### 4.1 纪律一：埋点**不加 `try/except`**

直觉会写"埋点不能影响业务 → 用 try 保住"，但**实测证明不需要**：

- `langfuse` 4.15.1：`public_key` 为空时打印一行
  `Authentication error: ... Client will be disabled`，然后**照常返回一个 no-op 的 span 对象**
  （no-op = 空操作：这个对象什么都不做，调用它的方法不产生任何效果）；
- `start_as_current_observation` 与 `propagate_attributes` **都不抛异常**。

→ 所以业务代码里**不加 try/except**。加了反而**把"埋点静默失效"藏起来** ——
那正是 D12 孤儿切片的教训：用异常兜住的失败，看起来和成功一样。

### 4.2 纪律二：**类型决定"能带哪些字段"**（接口一样、行为不同）

这条是今天最反直觉的一手实证。实测（读 SDK 源码 `_client/span.py`）：

- 观察类型分**两个桶**：**generation-like = `{generation, embedding}`**；
  **span-like = `{span, agent, tool, chain, retriever, evaluator, guardrail}`**；另加 `event`。
- `span.py:165`（创建路径）与 `span.py:692`（更新路径）**同一个分支**：
  `if 类型 ∈ generation-like → create_generation_attributes(...)`；`else → create_span_attributes(...)`。
- ★ **`LangfuseGeneration.update` 与 `LangfuseSpan.update` 的签名完全一样**（都接受
  `model` / `usage_details` / `cost_details` / `prompt`）—— 但走 else 分支时**这些参数被静默丢弃**，
  **不报错**（`create_span_attributes` 根本没这几个形参）。

**对 D28 的直接含义**：

| 格 | 类型 | 能不能带 model / token |
|---|---|---|
| `embedding` | generation-like | ✅ **能** —— 实测带上了 `model=BAAI/bge-small-zh-v1.5`（B6 断言） |
| `tool:*` / `retriever` | span-like | ❌ **带不了** —— 所以验收②的"来源标识"**只能写进 `metadata`** |

→ 一句话：**"看签名以为能带，看结果才知道没带上，而且没有报错提醒你。"**
（与"标签 ≠ 行为"同型；面试可讲。）

### 4.3 纪律三：`with` 的**范围**就是**被计时的范围**

`span()` 是个上下文管理器（`@contextmanager`）—— **退出 `with` 时 SDK 自动 `end()` 并记录 latency**。
所以：

- **包太窄** → 漏掉真实耗时；
- **包太宽** → 把不相关的等待算进来（例如根 span 若包住写回，就会把"用户没在等的时间"算进去）。

配套的两条**具体取舍**（都写进了代码注释）：

1. **`embed_texts()` 不包，只包 `embed_query()`** —— 因为 `embed_texts()` 也被**入库路径**调用（那不是检索）。
   只包后者，顺带把"用户查询的向量化"（单条、每次检索都发生）与"文档入库的向量化"（整篇、批量）
   在 Langfuse 上分成两格 —— 两者耗时口径完全不同，**混一格会让 P95 变成一个没有意义的平均数**。
2. **`rerank` 包住"三条降级路径"** —— 重排是整条链路里最贵的一段（20 候选 @300 字 ≈ 750~820ms），
   也是唯一会降级的分支。把降级也 `update(level="WARNING", status_message=...)`，
   "降级可归因"就落到了 trace 上；否则"最近怎么都不重排了"在 Langfuse 上**看不见** ——
   而 P95 反而会因为**跳过重排而变好看**（一个朝错误方向优化的信号）。

### 4.4 ★ 顺序是硬约束：`propagate_attributes` 必须在根 span **之外**

官方 docstring 原文照抄：**"Pre-existing spans will NOT be retroactively updated"**（已建好的 span 不会被追溯更新）。

**实测证实**（探针 `tree_probe.py` / `order_probe.py`）：

| 顺序 | 根 span 有 session/user？ | 结论 |
|---|---|---|
| **A**：`propagate_attributes` 包在根 span **外面** | ✅ 有 | **推荐写法**（本项目采用） |
| **B**：进入根 span 之后**立刻**调 | ✅ 有 | 也可用 |
| C：完全不调 `propagate_attributes` | ❌ `None` | 属性缺失 |

⚠ **顺序 C 的失败形态最难查**：根 span 先建、propagate 后调 → **根 span 自己 `session=None`，
而它的子 span 有值** —— 一种"看起来设了、其实只设了一半"的状态。

## §5 来源标识：从 `source` 到 `mcp_server_name`

### 5.1 地基 D27 就打好了

「能指出某次调用来自 harness」这个能力，**D27 已经埋下了地基** —— `registry.register()` 新增的
`source` 字段。**注册表现在自己知道每个工具的出身**，D28 只需在生成工具 span 时把这个值抄进 `metadata`。

### 5.2 一处口径映射（PRD 要的字段名与 D27 存的不是一回事）

| 出处 | 要什么 |
|---|---|
| PRD **F8.4** 原文 | span metadata 需含 **`mcp_server_name`** 与 **`tool_name`** |
| D27 代码 | 只存了 **`source`**（实测值：`local` / `inventory` / `harness`） |

**实测过的关键事实**（`app/tools/registry.py:31,44-46`）：`source` 对 MCP 工具**就是 server 名**，
本地工具是 `"local"`。所以映射规则（**不改 D27 的字段**）：

```
mcp_server_name = source if source != "local" else None
tool_name       = 工具名
```

**为什么本地工具要映射成 `None` 而不是写 `"local"`**：本地工具**不属于任何 MCP server**，
写 `"local"` 等于**谎称**它是某台 server 的工具。PRD F8.4 要的是"这一次是外部 server 的调用，不是自研工具"。

### 5.3 ⚠ 绝不能靠"工具名"猜来源（四条理由）

1. **工具名可以随便起** —— server 想叫什么就叫什么，完全可能出现一个叫 `search_documents` 的工具；
2. **撞名时当前实现是 `raise ValueError` 抛错**（不是静默覆盖），但抛在 `discover_and_register` 的循环中间
   （D27 登记的走读发现），**前面的工具已经进表了**；
3. ★ **反过来也不行**：名字带前缀（如 `harness_`）**只说明"命名时加过前缀"，不说明"注册动作真的来自那台 server"** ——
   这条一句话就把"**名字的长相**"和"**注册的事实**"切开了，也正是 `source` 字段非存在不可的理由；
4. **故障时分不清该重启谁** —— 这是 `source` 字段注释里就写明的理由。

→ 判据：**"来自哪"必须是注册时记下来的结构化事实，不是运行时从字符串里二次推断。**

### 5.4 未知工具返回 `"unknown"`，不是 `"local"`

`registry.get_tool_source(name)` 单独给一个函数（而不是让调用方遍历 `describe_tools()`），两个理由：

1. 遍历等于每次重新构造整个列表；
2. **注册表才是"工具元信息的唯一出处"**，查出身这种事不该在调用点重造一遍。

⚠ 未知工具返回 **`"unknown"`** 而**不是** `"local"`：调用方会拿这个值去填 span 的 metadata，
把"没有这个工具"谎报成"本地工具"，会在 Langfuse 上留下**一条看起来正常的假调用记录** ——
而真实情况是"**LLM 编了个不存在的工具名**"。排障时这两者必须能区分。

## §6 取数通道：为什么必须补 + 三个设计约束

### 6.1 一句话理由：**Langfuse 有自己的数据库，项目 PG 里没有这些数据**

| 数据 | 现在 Agent 能分析吗 | 为什么 |
|---|---|---|
| 评测准确率、切片质量、对话量 | ✅ 能 | 在**项目 PG** 里，SQL 可查 |
| **延迟 P95、token 成本、各段耗时、MCP 调用成功率** | ❌ **不能** | 在 **Langfuse 里**，而**没有回流通道** |

「接口接了 Langfuse 看板」**不等于**"Agent 能用这些数据" ——
**看板是给人看的，回流是给 Agent 用的**。这就是腿 B 存在的全部理由。

### 6.2 两条 REST 通道，结构完全不同（实测）

| | v1 `/api/public/observations` | v2 `/api/public/v2/observations` |
|---|---|---|
| token 用量 | ✅ `usageDetails={input:2834, output:70, total:2904}` | ❌ **结构上没有** |
| metadata / model 名 | ✅ 有 | ❌ 无（只有 modelId / 价格） |
| 分页 | 页码式（`meta.page` / `totalPages`） | **游标式**（`meta.cursor`） |
| 官方状态 | ⚠️ 响应带 `_deprecation`：**2026-11-16 移除** | ✅ 推荐 |

v1 的 `_deprecation` 原文：**"On Langfuse Cloud, Langfuse v3 is deprecated and this endpoint
will be removed on November 16, 2026. … Use GET /api/public/v2/observations instead."**
且旧版 **"may have data delays of several minutes"**（新数据可能几分钟才读得到）。

**为什么当前仍然用 v1**：v2 **拿不到 token 用量**（键集里根本没有 `usageDetails`），
而"token 成本"正好是 F8.5 要的一半数据 —— 用 v2 等于这一半永远没有。
🚩 **未结清**：2026-11-16 前必须重估。届时 token 指标要改走 `/api/public/v2/metrics`，
那是**聚合接口而不是明细接口**，口径会变，**不是"换一个 URL"那么简单**。

### 6.3 三个设计约束（PRD §9.12.3 / F8.5.4）

| # | 约束 | 今天怎么落实的 |
|---|---|---|
| ① | **返回结构与 SQL 源同构**（同一个 dict schema） | `_aggregate()` 返回 `[{name, value, count}]`，上层不感知数据来自哪 |
| ② | **只读、不双写落库**（权威存储是 Langfuse） | 走 HTTP 只读，绝不写回 PG |
| ③ | **不可达时只降级该指标**（不阻断主流程） | 单独异常类型 `LangfuseUnavailableError`（上层可只降级这一项） |

### 6.4 ★ 撞到限流后定的两条策略

**实测撞到过 429**（不是理论风险）：密集拉取返回

```
429 {"code":"rate_limited","message":"Rate limit exceeded for GET /api/public/observations.
     Use GET /api/public/v2/observations?... for high-volume reads."}
```

—— 服务端这句话**又一次**指向 v2（与 `_deprecation` 同一个方向）。

**当前处理：不自动重试，一律抛 `LangfuseUnavailableError`。** 两个理由：

1. 重试只会加剧限流，把"读不到"变成"**更久地读不到**"；
2. "这一项暂时不可用"本来就是设计要能表达的状态（F8.5.4 只降级该指标）。

**减小调用量的手段**（D35 用）**：60s 缓存（已实现）+ 更窄的时间窗 + 按需单指标查询**，
而不是"一次把一个月的数据全拉回来再本地过滤"。

## §7 代码逐行解读

> 只讲**决策点**，不复述显然的代码。按文件顺序：观测层 → 取数层 → 三个埋点插入点 → 验证脚本 → 负测试。

### 7.1 `app/services/observability.py`（新，190 行）—— 观测层唯一出口

与 `llm_gateway` 是「LLM 调用的唯一出口」同构。三条设计理由（每条对应一个实测坑）：

1. **整个进程只能有一个 Langfuse 实例（复用，绝不新建）** —— 实例内部持有一个 OTEL TracerProvider +
   批量导出线程。**建两个 = 两条独立导出管道**：同一段工作上报两次、线程与连接翻倍，
   而且两边**都看起来正常**。所以这里 `from app.services.llm_gateway import langfuse`，
   而不是再 `Langfuse(...)` 一次。（A3 断言钉的就是这个：`obs.langfuse is langfuse`。）
2. **span 命名规范必须有唯一权威出处** —— PRD §18 遗留问题 #5 点名"`latency_p95` 的 span 命名约定未统一"，
   要求 D28 定下来。六个 `SPAN_*` 常量是**唯一出处**，埋点侧与 D35 的聚合侧都从这里取；
   否则聚合时**某处拼错只会静默少一行**，不报错。
3. **埋点不能阻断业务，但不靠 try/except** —— 见 §4.1。

**关键函数**：

- `tool_span_name(tool_name)` → `"tool:<工具名>"`。为什么带前缀：**工具名是用户可自定义的**，
  完全可能出现一个叫 `vector_search` 的工具，那时它和检索那一格**同名**，`group by name` 会把两个东西
  混成一组 —— 而 D35 的 `latency_p95` 正是按 name 分组。**前缀把"工具层"和"检索层"在名字层面就分开。**
- `span(name, as_type, **kwargs)` —— 上下文管理器。两个"不用你操心"的机制已实测（§3.2 / §4.3）。
- `trace_attrs(*, session_id, user_id, trace_name, metadata, tags)` —— 给当前 trace 贴属性。
  **传 `None` 的项会被跳过（不下发）**：`propagate_attributes` 把 `None` 当成"要设成 None"，
  而我们要的语义是"这项不管" —— 两者不是一回事。
- `current_trace_id()` —— 给验证脚本取证用（生产代码不需要手读它：父子由上下文自动维护）。

**文件末尾**还专门解释了**为什么多一个 `retrieval` 父 span**（超出 PRD 的建议清单）：
一次检索可能只走其中一部分（`pure_vector` 只有 `vector_search`；BM25 路可能无 token 直接返回空；
rerank 可能超时降级）。有父节点时，它的 latency **就是这次检索的总耗时**，
`output` 里记着实际走了哪几步 —— 既能看到单段、也能直接读一格看整体。

### 7.2 `app/services/langfuse_client.py`（新，350 行）—— 腿 B 读通道

⚠ **名字歧义先说清**（本项目最容易混的一处）：`llm_gateway` 里的 `langfuse` = **写通道**（SDK 实例）；
本文件的 `LangfuseClient` = **读通道**（HTTP 只读）。**一个写、一个读，互不相干**，文件名相似只是巧合。

四个决策（每个都对应一个实测或一条原则）：

1. **用 v1 而不是官方推荐的 v2** —— 见 §6.2。
2. **字段映射表 `_FIELD_PATHS`** —— 语义层写 `usage.totalTokens`，REST 实际是 `usageDetails.total`。
   **不映射会静默拿到 `None`**（PRD 例子里写的 `usage.totalTokens` 直接拿去取就会踩这个）。
3. **只缓存成功结果** —— 失败也缓存的话，一次网络抖动会被放大成"接下来 60 秒都读不到"。
4. **`query()` 留空壳抛 `NotImplementedError`** —— `MetricSpec` 属语义层（D35），
   硬造一个等于埋一个必改的债；但也**不能悄悄返回空**（空会被上层当成"该指标为 0"）。

**`_percentile` 用最近秩法**（不插值）：与 D35 的 SQL 源 `percentile_disc` **一致**（F11.7 要同构）。
⚠ 样本量很小时（<20）P95 基本等于最大值，报数时要带上样本数。

**`_to_iso` 的坑**：只给日期时终点要补 `T23:59:59Z`，否则 `toStartTime=2026-10-04` 会把当天
**整天的数据都排除掉**（终点被当成当天零点 → 范围变空集）—— 而返回的是 **200 + 空数组，不报错**。

**`get_langfuse_client()`** —— 模块级单例（工厂 + 缓存），凭据**只从 `settings` 读**（PRD §8.2 红线 4：
业务代码不得直连 `os.environ`）。

### 7.3 `app/tools/registry.py`（+21 行）—— 加一个 `get_tool_source()`

见 §5.4。核心是"未知工具返回 `unknown`，不谎报 local"。

### 7.4 `app/services/agent_service.py`（+118 / −54）—— 根 span + 工具 span

三处值得单独说：

- **根 span 的范围刻意到"取答案"为止、不含写回**（§3.3）—— 写回不占用户等待时间，
  算进去会让"这一轮慢在哪"失真。
- **工具名在 `try` 外面先取**：取值用 `.get` 链而不是 `tc["function"]["name"]` ——
  名字提到 `try` 外之后，就必须自己保证它不会抛（原代码的取名在 `try` 内，结构异常会被吞成"解析失败"；
  **换个位置而不换写法，就会把一个可恢复的失败升级成节点崩溃**）。
- **工具 span 失败时 `level="ERROR"`**：只写日志的话，"这台 server 的工具最近一直失败"在 Langfuse 上
  看不见 —— 而它恰恰是运维最该看见的。

### 7.5 `app/services/retrieval_service.py`（+140 / −103）—— 检索父 span + 向量 / BM25 两格

⚠ **那 140 行插入大部分是缩进**（整个函数体包进 `with`），不是 140 行新逻辑。

- `retrieve` 包 `retrieval` 父 span（§7.1 末说了为什么加它）。
- `search` 包 `vector_search`；它的子节点是 `embedding`（`embed_query` 建的）——
  于是"向量这一段"能拆成"算向量"+"查库排序"两块。
- `search_keywords` 包 `bm25`；**无有效 token 那一支也 `obs.update(...)`** ——
  它会让融合退化成向量单路，而"这次混合检索为什么只有一半"**在结果里看不出来**（结果照样返回）。
- 各格只记**条数**、不记 content：切片正文最长 300 字 × top20，全塞进 span 会把 trace 撑大且无增量信息。

### 7.6 `app/services/embedding_service.py`（+25 / −3）—— 只包 `embed_query`

见 §4.3 第 1 条。这一格是**唯一能带 model 名**的（generation-like），
实测带上了 `model=BAAI/bge-small-zh-v1.5` —— 让"换 embedding 模型之后 P95 变了吗"变成能按模型分组的问题。
`output` 只记**维度**而不是向量本身（512 个浮点数塞进 trace 既大又无增量信息，
但"维度对不对"是个真实排障信号：换模型忘了重建索引时维度会不匹配）。

### 7.7 `app/services/rerank_service.py`（+86 / −49）—— 包三条降级路径

见 §4.3 第 2 条。`output` 记**分数区间**（它是"重排到底有没有把分数拉开"的直接证据）；
⚠ 记的是**本次**区间，不跨次求平均（D18 实测重排分是 logit、**跨 query 不可比** ——
logit = 模型输出的原始分数，未归一化到 0~1，所以不同 query 之间的分值不能直接比较）。

### 7.8 `scripts/d28_verify.py`（新，706 行）—— ★ 最重要的设计是"进程内取证"

**七段各答一个问题**：

| 段 | 答什么 |
|---|---|
| A 结构 | 观测层的命名规范 / 取数层的字段映射，是不是真的在位 |
| B 检索树 | 一次 `retrieve()` 建了几格、是不是**同一条 trace**、父子对不对 |
| C 对话树 | 真跑一轮 `run_agent`：根 span 在不在、session 落没落上、generation 挂哪 |
| D 工具 | 工具 span 的 metadata 能不能回答"调了哪个工具 / 属于哪台 server" |
| E ★ 验收② | 真调 harness 的工具，那格 span 真的标着 harness 吗 |
| F 腿 B | 取数通道：真拉回、字段映射、聚合、60s 缓存、不可达只升明确错误 |
| G 自证 | 断言用的属性键真的存在吗（否则"全绿"可能只是空集合恒真） |

★ **关键取证手法（本脚本最重要的设计）**：

```python
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter
exporter = InMemorySpanExporter()
langfuse._resources.tracer_provider.add_span_processor(SimpleSpanProcessor(exporter))
# 跑被测代码 → exporter.get_finished_spans() 拿到 name / trace_id / span_id / parent / attributes
```

**为什么不用 REST 读回**：① 官方对 v1 observations 的原文警告是 "may have data delays of several
minutes" —— 用它做验收断言会变成"**看运气**"（第一版就是这么红的）；② 网络抖动会让"埋点对不对"
这个**纯逻辑问题**变得不可判定。内存 exporter 读的是**同一份 span 数据**（同一个 TracerProvider），
只是不经网络 —— 所以它证明的是"**埋点结构**"，网络那一段由 F 段**单独证**。

**G 段自证**回答三个问题：① 断言用的**属性键真的存在吗**（打印真实键名 + 断言后缀匹配）；
② 对照集**非空**吗；③ 本脚本有没有**硬编码真工具名**（AST 扫字符串常量 ∩ 运行时真工具名 = 必须为空）。
→ ③ **当场抓到一条**：A 段里写了 `tool_span_name("search_documents")` 当样例 ——
**自证机制的价值就在这里，它抓的是我自己。**

**两条纪律**：① 必须用 `-m` 跑（否则 `import app` 失败）；② 开关**由命令行强制决定**，不依赖 `.env`
（`.env` 里 `MCP_HARNESS_ENABLED` 默认 false，若不管它，`--with-harness` 会被**静默压掉** → E 段跳过 → 看起来像通过）。

### 7.9 负测试：证明"49/49 全绿"不是"永远全绿"

做法（铁律 9 附则）：**往被测对象里注入一处已知会破坏该断言的改动，跑一次，看它是否如期报红，然后还原并复跑。**

本次注入：让 `registry.get_tool_source()` **恒返回 `"local"`**。

| 步骤 | 结果 |
|---|---|
| 注入后跑 `--with-harness` | **44 / 失败 5 / 共 49**，`EXIT=1`；5 条如期红：**A7 / D6 / D7 / E3 / E4** |
| 关键对照 | **D3「本地工具 source=local」仍然 PASS** → 证明注入只打中该打中的那条链，不是一片乱红 |
| 还原后复跑 | **49 / 失败 0**，`EXIT=0`；grep 确认注入行零残留 |

→ 这一跑同时证明三件事：① 那几条断言不是摆设；② 它们**互相独立**（不会一个坏连坐一片）；
③ **退出码真的会随失败变化**。

## §8 SDK 实测事实（langfuse 4.15.1）

`langfuse` 版本 **4.15.1**（`uv.lock` 实读）。用 `inspect.signature` 把 API 实测了一遍：

| 事实 | 内容 |
|---|---|
| ❌ **网上常见但本版本不存在** | `start_as_current_span` / `start_span` / **`update_current_trace`** —— **三个名字全都不存在** |
| ✅ trace 级属性的真实入口 | **模块级 `langfuse.propagate_attributes(user_id=, session_id=, metadata=, tags=, trace_name=, ...)`** |
| ✅ `as_type` 原生取值 | `generation` / `embedding` / `span` / **`agent`** / **`tool`** / `chain` / **`retriever`** / `evaluator` / `guardrail` |
| ✅ 还有 | `update_current_span` / `get_current_trace_id()` / `score_current_trace()` / `observe` 装饰器 |
| ✅ `TraceContext` | `{trace_id, parent_span_id?}` —— 跨进程 / 跨线程挂到同一条 trace 用（今天子进程只吐 JSON-RPC 文本，用不上，是 D29+ 的扩展点） |
| ⚠ **实例上没有 `propagate_attributes`** | `hasattr(Langfuse, "propagate_attributes")` 为 **False** —— 它是**模块级函数**，只能 `from langfuse import propagate_attributes`。写成 `langfuse.propagate_attributes(...)` 会 `AttributeError` |

## §10 踩坑记录

### ① ★ 验证脚本绕过被埋点的那一层（**同一天在同一份脚本里犯了两次**）

**现场**：埋点写在 `agent_service.execute_node` 里（"Agent 决定调工具"那一步）。
验证脚本要证"MCP 工具的 span 标着 source"，却直接调了注册表的 `execute_tool(...)` ——
**跳过了 `execute_node`**，于是 span 根本没建。脚本报的是
`[FAIL] MCP 工具的 span 标着 source=... | source=None`，**字面上看像埋点代码错了**。

**第二次形态（更值得记）**：发现 D 段错了、改完之后，**E 段有同一个错却没跟着改** ——
**修法只补了被看见的那一处**。（与 skill 铁律 8 附则六「修法只补被投诉的那一级」是同一条纪律的**第 2 次命中**。）

→ **判据**：写完一条断言先问 —— *"我调的这个函数，真的会经过我要证的那段代码吗？"*
**做法**：**从最外层的真实入口驱动**（本例用 `execute_node` / `run_agent`），
而不是从"离被测代码最近的那个函数"驱动。

### ② 时间窗太窄 → 断言变成"看运气"

F 段第一版只查"今天"+limit 50，拉到 **16 条**且**不含 generation** → F3/F5 红。
成因：官方对 v1 observations 明说"**可能有几分钟数据延迟**"，"刚跑完的 span 什么时候能读到"不确定。
→ 改成**一周 + limit 300**：本段要证的是"取数与聚合的**能力**"，用已落定的历史数据最稳。

### ③ ★ 撞 429 限流把脚本整崩（健壮性缺陷）

限流一抖，F-③ 那段**没包 try** → **整个脚本崩掉**，后面 F4~F10、G 段**全部跑不到**，
输出看起来像"断在半路"。→ 修法两条：① F-① 带一次重试（等 5s）；
② F-③ **复用 F-① 的缓存窗口、不再发新请求**（"第一次真发能拉到"由 F-① 证，
"重复调用不再发"由 F-③ 证 —— 两件事分开证，合起来才是完整的缓存语义）。
（与 D27 用 try 包住 `TestClient` 同一条规矩：**缺前提就跳过并报红，不要崩**。）

### ④ 假名 vs 真工具名：自证机制抓到我自己

A2 断言本意是验 `tool_span_name` 加前缀，我顺手写了 `tool_span_name("search_documents")` ——
**那是运行时真工具名** → G3（零硬编码自证）**如期报红**。→ 改成假名 `"demo"`。
**自证机制的价值就在这里 —— 它抓的是我自己。**

### ⑤ `uv run python /tmp/xxx.py` 的 `sys.path[0]` 是脚本目录

跑**项目外**的探针时 `ModuleNotFoundError: No module named 'app'`。
修法：**`PYTHONPATH=. uv run python /tmp/xxx.py`**。
（与 MEMORY §3.1 的 `-m` 那条互补：`-m` 管**项目内**脚本，`PYTHONPATH` 管**项目外**脚本。）

### ⑥ `query()` 是 async —— 不 `await` 就只是一行都不跑

F10 第一版写 `client.query(...)` 得到的是一个 coroutine 对象：函数体一行没跑、断言自然不成立，
还会留下 "coroutine was never awaited" 警告。→ 必须**真 `await`**。
（与"命令错冒充对象坏"同型：探针自己写错，看起来却像被测代码有问题。）

### ⑦ 本项目老坑复用

- **`uv` 不在非交互 shell 的 PATH**（报 `command not found`、退出码 127）→ 用绝对路径 `~/.local/bin/uv`。
- **机检假阳性不许照修**（本项目反复出现，第 N 次）：机检只负责报警，不负责判决（见附录 D）。

### A.1 Q1 · 埋点树

- **L1**（出处 §7.5 + §3.3）：一次 `retrieve()` 会建 **5 格**：
  **`retrieval`（父）** → 子 **`bm25`**、**`vector_search`**、**`rerank`**；
  其中 **`vector_search` 下面再挂 `embedding`**。
  实测树（C 段打印，`retrieval` 是这一棵子树的根）：
  ```
  retrieval
    ├─ bm25
    ├─ vector_search
    │    └─ embedding
    └─ rerank
  ```
  ⚠ 走哪几条子段**取决于检索配置**（`pure_vector` 只有 `vector_search`；`bm25` 可能无 token 直接返回空）。
- **L2**（出处 §7.1 末）：因为一次检索**可能只走其中一部分**，而且**会降级**。
  有了 `retrieval` 这一格，它的 **latency 就是这一次检索的总耗时**（不用在面板上手工把几条拼起来），
  它的 `output` 里记着**实际走了哪几步** → D35 的 `latency_p95` 既能按 name 看单段，也能直接读这一格看整体。
- **L3**（出处 §7.1 末）：因为 `retrieval` 是**嵌套计时** —— 它的耗时**已经包含**了子 span 的耗时。
  把父与子相加 = **重复计算**（会把总时长算大一倍甚至更多）。

### A.2 Q2 · 埋点的安全性

- **L1**（出处 §4.1）：**实测证明不需要**。`langfuse` 4.15.1 在 `public_key` 为空时只打印一行
  `Authentication error: ... Client will be disabled`，然后**照常返回一个 no-op 的 span 对象**；
  `start_as_current_observation` 与 `propagate_attributes` **都不抛异常**。
  **加了 try/except 反而会把"埋点静默失效"藏起来**（用异常兜住的失败，看起来和成功一样）。
- **L2**（出处 §4.2）：因为 **`tool` / `retriever` 属 span-like 类型，带不了 `model` 那几个字段**
  —— `LangfuseSpan.update` 与 `LangfuseGeneration.update` **签名一样**，但走 span-like 分支时
  `create_span_attributes` 根本没这几个形参 → **传了会被静默丢弃、不报错**。
  而 `embedding` 属 generation-like，所以**能**带 model。
  → 结论：**span-like 的格表达来源只能靠 `metadata`**。
- **L3**（出处 §4.4）：官方硬约束 —— **"Pre-existing spans will NOT be retroactively updated"**。
  实测：根 span 先建、`propagate_attributes` 后调 → **根 span 自己 `session=None`，而它的子 span 有值**
  —— 一种"**看起来设了、其实只设了一半**"的状态，最难查。
  → 正确写法：`propagate_attributes` **包在根 span 外面**（推荐）或刚进根 span 时立刻调。

### A.3 Q3 · 来源标识

- **L1**（出处 §7.4 / §5.2）：**三个字段** —— `tool_name`（调了哪个具体工具）、
  `mcp_server_name`（它属于哪台 server，本地工具为 `None`）、`source`（来源标识：`local` / `inventory` / `harness`）。
- **L2**（出处 §5.4）：因为调用方会拿这个值去填 span 的 metadata。把"**没有这个工具**"谎报成"本地工具"，
  会在 Langfuse 上留下**一条看起来正常的假调用记录** —— 而真实情况是"**LLM 编了个不存在的工具名**"。
  排障时这两者必须能区分。
- **L3**（出处 §5.3）：**名字带前缀只说明"命名时加过前缀"，不说明"注册动作真的来自那台 server"** ——
  名字是"长相"，`source` 是"事实"，两者不是一回事。
  （配套理由：工具名可以随便起 / 撞名会抛错 / 故障时分不清该重启谁。）

### A.4 Q4 · 取数通道

- **L1**（出处 §6.2）：因为 **v2 拿不到 token 用量**（键集里根本没有 `usageDetails`），
  而"token 成本"正好是 F8.5 要的一半数据 —— 用 v2 等于这一半永远没有。
  （v1 的 `_deprecation` 已写明 **2026-11-16 移除** → 期限已登记。）
- **L2**（出处 §7.2 决策②）：**要显式映射字段名**。语义层写的是 `usage.totalTokens`，
  而 REST 实际返回的是 `usageDetails.total` —— 靠 `_FIELD_PATHS` 把前者翻成后者的路径。
  **不映射会静默拿到 `None`**（不是报错，是悄悄没值）。
- **L3**（出处 §6.4）：两个理由 —— ① **重试只会加剧限流**，把"读不到"变成"**更久地读不到**"；
  ② "**这一项暂时不可用**"本来就是设计要能表达的状态（F8.5.4 只降级该指标）。
  → 一律抛 `LangfuseUnavailableError`，让上层只降级这一项。

### A.5 移出考题、只作为讲解的点（B 方案）

D28 第一轮（原理环节）的三问，因当时**指不回文档**被移出考题、改成讲解 —— 一并在此留档，
它们是**真知识**，只是当时还没写进讲解：

1. **根 span 怎么建**：入口是 `with langfuse.start_as_current_observation(name="run_agent", as_type="agent")`；
   在 `with` 里创建的所有 span 自动挂到它下面。
2. **`trace_context` 那条路**：传 `trace_context={"trace_id": ...}` 会**不建真 span**，而是造一个
   `NonRecordingSpan`（"哑父"，只揣 trace_id/span_id、自己不落记录），用途是**跨进程 / 跨线程**拼一条 trace。
   （今天不用它；子进程只吐 JSON-RPC 文本。）
3. **工具 span 该写哪些字段**：`as_type="tool"` + `name=tool:<工具名>` +
   `metadata={tool_name, mcp_server_name, source}` —— 因为 `tool` 属 span-like，**只能带 input / output / metadata**。
