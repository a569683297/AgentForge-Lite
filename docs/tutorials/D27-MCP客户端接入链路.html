D27 · MCP 客户端接入

从「工具跑在我自己的进程里」到「工具跑在另一个进程里」—— AgentForge-Lite，2026-10-03 · M5 第 3 天

这张图回答一个问题：MCP 客户端接入，到底在我这条已有的链路上加了什么、没加什么？

前置两天：D25 学协议（三方角色、报文长什么样）→ D26 写 server（一台能独立跑、能被陌生调用方驱动的库存服务）。 D27 是反过来的一天：我不再是"写服务的人"，而是"写调用方的人" —— 让 Agent 变成客户端。

§0 先注解名词（后面全部用得到，按首次出现顺序）

名词一句话定义（它是什么、解决什么问题）
Host（宿主） 装着模型、决定"哪些工具能被模型看见"的那个程序。在本项目里 = FastAPI 这个进程（app/main.py 起的服务）。它有放行权与否决权。
Client（客户端） 一个只负责搬运的通道对象：1 个 Client 恰好连 1 个 Server。它不决策、不执行，只把调用送过去、把结果带回来。在本项目里 = 我这次要写的 app/services/mcp_client.py 里的那段连接。
Server（服务端） 装着工具的独立进程，四件事：启动常驻 / 接线（读 stdin 写 stdout）/ 报目录（tools/list）/ 校验调度（tools/call）。D26 的 mcp_servers/inventory_server.py 就是一台。
Tool Registry（工具注册表） 项目里的工具总目录：app/tools/registry.py 的一个全局字典 _registry，键 = 工具名、值 = 函数 + 描述 + 参数 schema。Agent 引擎只认它，不认工具从哪来。
stub（存根） 一个本地占位函数：自己不干活，只把收到的调用转发到远端、再把结果带回来。类比前端：const api={getUsers:p=>fetch('/users',p)} —— 名字和签名在本地，实现在对端。
命名空间（namespace） 给名字加前缀分组，避免两套东西撞名。这里解决的是：两台 server 都可能有叫 get / list 的工具，而注册表重名会直接抛错。
toolset（工具集） 服务端把工具按用途分组的篮子（Harness 有 42 个，如 pipeline / execution）。全开 = 几百个工具挤进 prompt；裁剪 = 只留这次的场景要用的。
Modern / Legacy 两代协议 两套"开场方式"：Legacy 先发 initialize 握手（谈定 2025-11-25）；Modern 无握手、版本走每条报文的 _meta（谈定 2026-07-28）。本项目走高层 Client，默认 mode="auto" → 落在 Modern 代（D26 抓包实测）。

§1 今天真正要加的只有一件事：第二条进注册表的路

路径 A · 静态注册（D8 就有了，今天的基线）

1
写一个工具文件
app/tools/current_time.py，函数体写在本进程内。
2
加一个装饰器
@register(name=…, description=…, parameters=…) —— 名字、描述、schema 全部由我手写。
3
在 app/tools/__init__.py import 一次
装饰器只在模块被导入时执行；没人 import，注册表里就没有它。
4
进了同一个字典 _registry
时机 = 进程启动时（import 期），来源 = 我自己写的函数。

→ 加一个工具的成本：改代码 + 重启进程。

路径 B · 动态发现（D27 新增，MCP 的意义所在）

1
启动子进程
subprocess 拉起 server（自研的 inventory_server.py，或 Harness 的 npx harness-mcp-v2）。
2
问它「你有什么」
发 tools/list → 拿回一份目录：每个工具的名字、描述、参数 schema 都是它给的，不是我写的。
3
为每个工具现造一个 stub
名字加前缀（命名空间）→ registry.register(...) 注册进同一个 _registry。
4
Agent 引擎零改动
get_tools_schema() 遍历的还是那个字典 → 新工具自动出现在 LLM 的工具清单里。

→ 加一个工具的成本：在 server 那边加。我这边一行不改、不重启 —— 这就是 PRD 里说的「接新 server 不改 Agent 代码」。

对比项路径 A 静态路径 B 动态（MCP）
注册时机进程启动时（import 期）运行期（连上之后）
函数体在哪本进程内另一个进程里
名字/描述/schema 谁写我手写server 的 tools/list 给
注册进哪同一个 _registry（→ 下游 plan / execute 节点完全不用知道区别）
加工具要不要改我这边要（改文件 + 重启）不要
调用怎么发生Python 直接调用（微秒级）跨进程 JSON-RPC 往返（毫秒级）
一句话记住两条路的区别：不是"名字从哪来"，而是 "函数体在哪、什么时候被发现"。
⚠️ 但"接新 server 不改 Agent 代码"这条结论，靠的不是"函数体在别处"。 "函数体不在本进程"只说明 代价从哪来（必须跨进程往返，微秒 → 毫秒）； 能不能不改代码，取决于契约够不够窄：
  • 注册表只要求「三样描述信息 + 一个可调用对象」：_registry[name] = {function, description, parameters}
  • 下游 plan / execute 只认 get_tools_schema() 与 execute_tool(name, args) —— 两个函数、两个签名
  • 而且它从不检查 function 到底是本地的真函数，还是一个只会转发报文的代理
→ 只要 stub 满足这份契约，上游（LLM）和下游（引擎）都看不出区别。 "注册表是一个运行期也能写的进程内字典"才是这条结论真正的支点。

§2 stub 为什么必须存在：Python 的函数调用不跨进程

远端工具的真实函数住在子进程里，我这边拿不到它的函数对象 —— import 不到、也调用不了。 两个进程之间唯一的通道，就是子进程的 stdin 和 stdout 两根管子。 所以本地必须放一个"替身"，它的职责只有三件：

stub 的三件事

  1. 冒充：用 server 给的名字 / 描述 / schema 注册，让 LLM 以为这是个普通工具
  2. 打包：把参数包成一条 JSON-RPC 报文 tools/call，写进子进程的 stdin
  3. 等回：在 stdout 上等同一个 id 的响应，取出文本层返回

对上已有的契约

execute_tool(name, args) -> str —— 注册表要求 handler 收 dict、回字符串。 stub 正好满足它：对内像本地函数，对外是一次远程调用。

注意 execute_tool 出错时返回的是错误字符串而不是抛异常（源码设计如此）—— stub 也要遵守这条：把远端错误翻译成一段文字还回去，让模型看得见、能自己改。

§3 一次调用的完整往返（含两条进程边界）

1
用户提问
「哪些物料库存低于 20？」→ POST /api/chat
2
plan 节点取工具清单
get_tools_schema() ← 现在里面多了带前缀的库存工具（Agent 引擎的代码一个字没改）
3
LLM 决定调哪个工具
返回 tool_calls: [{name:"inventory_query_inventory", arguments:{...}}]
4
execute 节点 → execute_tool() → 查到 stub
到这一步为止，和 D10 的知识库检索工具走的是同一段代码。
5
★ 进程边界 1：stub 把报文写进子进程 stdin
{"jsonrpc":"2.0","id":N,"method":"tools/call","params":{"name":…,"arguments":{…}}}
6
子进程内部（D26 讲过的七步）
读 stdin → 看 method → 查自己的工具表 → schema 校验参数 → 执行真函数 → 包成 content + structuredContent
7
★ 进程边界 2：响应回到 stub 的 stdout
带同一个 id，所以并发多路调用也不会串（id 是配对的钥匙）
8
结果当字符串返回 → 以 tool 消息写回 → 回到 plan 节点
LLM 读到工具结果 → 生成最终回答
这条链路的价值在于"没变的部分"：plan / execute / 消息写回 / 引用收集 —— 一条都没动。 新增的只有第 4→7 步之间那一小段（stub + 两根管子）。这就是分层：工具的来源换了，Agent 的骨架没换。

§4 四个工程细节：能跑 ≠ 能用

#问题对策（今天要做成代码的部分）
1子进程是常驻的，谁管它的生死？ 启动 / 健康检查 / 崩溃重启（退避） / 退出清理，防子进程泄漏。
依据（D26 实测）：server.run() 不是永不返回 —— stdin 收到 EOF 就正常退出，生命周期归 Host 管。
2首次启动慢（要拉 npm 包 / 下模型） 预热脚本 + 锁版本 + 国内必须走镜像 registry.npmmirror.com（直连 npmjs 实测超时）。
3写操作有风险（create / update / delete / execute） 服务端 HARNESS_READ_ONLY=true 屏蔽一切写操作；另有 HARNESS_AUTO_APPROVE_RISK 设"人工确认阈值"。
口径更正（D25）：「只读」不在 PAT 上 —— 个人 PAT 继承账号全权、创建时没有只读档。
4工具数膨胀会塞满上下文 按需裁剪 toolset（Harness 有 42 个）。官方理由：工具数膨胀会降低 LLM 选型准确率。

⚠️ 补一条机制：server 挂了，注册表里的 stub 不会消失

_registry 是一个内存字典，而 registry.py 里根本没有回收逻辑 （没有 unregister、没有"健康检查后再摘除"）。子进程死掉只是让那根管子断了， 字典里的键值对原样留着 → get_tools_schema() 照样把它报给 LLM， LLM 依然以为这个工具可用、会继续尝试调它。

"挂了"要分两种，形状完全不同：

怎么挂的调用时会发生什么
① 进程没了（崩溃 / 被 kill） 往已经死掉的子进程 stdin 写 → 写失败（管道已断）→ 被 execute_tool 的 except 接住 → 变成一段错误字符串喂回 LLM
② 进程还活着但卡住 写入成功，但等不到响应 → 超时才是命门。没有超时机制，整个 Agent 循环会被一起挂住 —— 这比报错严重得多

→ 这是 D24 那条「覆盖面型静默失效」的又一个实例：注册表声称的能力 ≠ 真实能调通的能力。 而现有的关注点（工具清单齐不齐、schema 对不对）没有一条在检查"报出来的工具是不是真能调通"。 修法与 D24 同源：新增一个维度（健康检查 / 来源标注），不是收紧原有断言。

⚠️ 以上全部是源码推演，尚未实测（路径 B 还没写）。今天编码时会用真实场景验一次（杀掉子进程再调）， 验完才升格为结论。

⚠️ 补一条机制：命名空间不加前缀会怎样 ——「静默覆盖」比「抛错」难查得多

register 现在是重名直接 raise ValueError（registry.py 48–49 行）， 且发生在进程启动时 —— 这是快速失败，问题会自己喊出来。 假设把它改成「后注册的覆盖先注册的」，同一件事就换了一副面孔：

层次真正会发生什么
① 能力静默消失
（最根本的一层）
 键相同 → 整条记录被顶掉，被覆盖那台 server 的工具从 _registry 里彻底没了。 get_tools_schema() 只报存活的那一个 → LLM 连它存在都不知道，根本不会去调它。 → 所以第一层后果不是「调用了、返回错结果」，而是「这个能力不存在了，而且没有任何人告诉你」。
② 调了也拿到不搭的东西 两边名字同、语义不同时（inventory 的 get = 查物料 / harness 的 get = 查资源）， LLM 拿 A 域的问题去调 B 域的同名工具 → 返回语义对不上的结果。这是第二层，不是第一层。
③ 谁活下来由顺序决定
（最毒的一层）
 取决于 import 顺序 / 启动顺序 / 连接快慢（动态发现时还受网络影响） → 同一份代码在不同机器、不同次启动，活下来的可能不是同一个工具 → 本地复现不了。
④ 为什么「无法排查」 日志里只有工具名，而名字又相同 → 分不清这次调用到底打到了哪台 server。 （_registry 现在存的是 {function, description, parameters}，没有 source 字段 —— 这正是今天要「让注册表记住来源」的直接动因。）

★ 对照：抛错的世界与覆盖的世界，差别不在「有没有 bug」，而在「bug 会不会自己喊出来」。 → 与 D24「覆盖面型静默失效」同源。

顺带钉一个口径：加前缀只动「名字」这一个字段。 description 与 parameters 都是 server 给的原文、原样透传。 「在描述里补上来源」是我额外要做的另一个动作（因为名字变了、描述里得留线索）， 不是加前缀的必然结果 —— 这两件事是两步，别混成一步。

今天的验收里有一条卡在时限上：「/api/tools 能看到 Harness 的 11 个工具」需要 PAT 仍然有效， 而 Harness 的 TRIAL 账号 2026-10-06 07:59:59 到期（今天 10-03）。 → 所以 Harness 那一半要么今天排进去，要么先把账号问题解决掉，不能拖到 D28。

§5 两条"默认值/边界"必须先说清（D26 的教训）

① 本项目落在哪一代协议

走高层 Client，它默认 mode="auto"：先探 server/discover，成功就不再发 initialize → 谈定 Modern（2026-07-28）。

⚠ 这句话必须带主语：「默认走哪一代，取决于用哪一层客户端」。低层 ClientSession.initialize() 与 mode="legacy" 才走握手代。

② 子进程的生死

server.run() 阻塞着，但不是永不返回：客户端一断开 → stdin EOF → 它正常退出（D26 实测 0.94s）。

→ 「常驻」是我们这边不断开造成的，不是 server 自己赖着不走。所以清理逻辑必须写在我们这边。
