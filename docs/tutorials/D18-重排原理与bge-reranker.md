## 2. 核心概念讲解

### 2.1 RRF 之后为什么还不够

D17 我们已经能把两路合成了一个排序。但 RRF 有一个**结构性**盲区：

> **它的输入只有名次，对文档内容一无所知。**

后果用一个构造的例子说（📌 标注：**这是构造的，不是我们语料上的实测** —— 我们只有
4 篇语料，向量路自己就能把正确答案排第一，D17 已实测过）：

查询「报销标准是多少」，正确答案是 **D**，但有两篇文档参与竞争：

| 文档 | 向量路名次 | BM25 路名次 | RRF 分 |
|---|---|---|---|
| **D**（真的写了金额标准） | rank3 | rank3 | `1/63 + 1/63` = 0.031746 |
| **E**（只讲审批流程，没写金额） | rank1 | rank2 | `1/61 + 1/62` = 0.032522 |

**E 赢。** 而 RRF **没有任何办法发现这件事** —— 它看到的就是两组名次，两组名次都说 E 更靠前。

它要发现"E 其实压根没写金额标准"，唯一的办法是**把 query 和这两篇文档放在一起读一遍**。
这正是重排要做的事：**在最终的前 20 名上，用"会读内容"的模型重新判一次。**

### 2.2 唯一的新概念：交互深度换计算量

| | **bi-encoder**（向量检索在用的） | **cross-encoder**（重排要用的） |
|---|---|---|
| 输入 | query 一条序列 / document 一条序列 | **[query, document] 拼成一条**序列 |
| 输出 | 两个向量 | **一个标量** |
| query 与 doc 何时交互 | **只在最后一步**（算一次余弦） | **每一层、每对 token 之间** |
| doc 的表示依赖 query 吗 | **不依赖** → 可预先算好存库 | **依赖** → 不能缓存 |
| 一次查询要跑几次模型 | 1 次（query）+ N 次点积 | **N 次完整前向**（N = 候选数） |
| 能建 ANN 索引吗 | 能（HNSW / IVF） | **不能** |
| 擅长 | 召回（快、宽、会漏） | 精排（慢、准、只排少量） |

**一句话**：cross-encoder 更准，但它**不能单独当检索用** —— 因为每个文档的分数都依赖 query，
"文档向量"这个东西在它这里根本不存在，也就无从建索引。

> 这也解释了为什么两种**分词/编码**路线要分开看：bi-encoder 里 doc 侧可以离线批量算，
> cross-encoder 里 doc 侧必须**等 query 到了才能算**。

### 2.3 为什么必须是"两阶段"（不是"换个更强的模型"）

这不是风格选择，是被数量级逼出来的。设语料 **N = 10000 篇**：

| 方案 | 一次查询的计算量 | 量级 |
|---|---|---|
| 只用向量检索 | 1 次 query 编码 + 一次 ANN 搜索 | **毫秒级** |
| 只用 cross-encoder | **10000 次完整前向**（每篇都要跟 query 拼起来跑一遍） | **分钟级** |
| **两阶段（标准做法）** | 1 次 ANN + **20 次** cross-encoder 前向 | 毫秒级 + 可接受开销 |

> **用便宜的、能预计算的、会漏的（bi-encoder）把 N 缩到 20；
> 再用贵的、准的、不能缓存的（cross-encoder）把这 20 排好。**

"重排"（re-rank）这个名字的字面意思就是：**它不负责「找」，只负责「重新排」。**

### 2.4 分数是什么 —— 三个坑

cross-encoder 输出的是 **logit（未归一化实数）**，不是概率、不是相似度。
据 BAAI 模型卡，bge-reranker 系列用二分类（相关 / 不相关）目标训练，所以分数**可正可负**。
本机实测（`d18_rerank_probe.py` ⑤ 段，query = `年假有几天`）：

```
1. 制度综合（含年假）   score=+2.9621
2. 考勤管理            score=-0.9890
3. 运维发布规范        score=-10.1957
```

由此三个坑：

1. **不可跨 query 比较** —— 同一篇文档换个 query 分数完全变。所以**不能用绝对阈值过滤**
   （`if score < 0.5: 丢` 是错的：一个高分查询可能 20 条全在 3.0 以上，另一个查询全在 -2.0 以下，
   阈值根本没有统一含义）。
2. **不可与 cosine / BM25 分数相加** —— D17 刚讲完"cosine 有界、BM25 无界"，
   重排分是**第三个量纲**。所以重排是**替换**掉原分数，不是加权叠加。
3. **但同一次查询内可比** —— 同一个 `(query, 候选列表)` 里，分数大小等价于相关性顺序。
   这就够了：我们只需要**排序**，不需要绝对阈值。

### 2.5 RRF 与重排，别混（最容易讲错的一处）

| | RRF 融合（D17） | cross-encoder 重排 |
|---|---|---|
| 输入 | 两路的**名次** | 融合后 20 条的**内容** |
| 看内容吗 | ❌ 完全不看 | ✅ 逐对读 |
| 输出 | 新的名次 | 新的**分数** → 再排名次 |
| 计算 | 纯算术（微秒级） | N 次模型前向（**实测 800 ms 量级**） |
| 位置 | 阶段 1 的收尾 | 阶段 2 的全部 |
| 能纠正什么 | 两路**分歧** | 两路**一致但不相关** |

**最后一行是关键区分**：RRF 能仲裁分歧，但纠正不了"两路一起错"；重排能读内容，所以能。
两者是流水线上下两道，**不是替代关系**。

### 2.6 完整链路（PRD §9.3 原文）

```
query → 向量检索（pgvector cosine top20）
      → BM25 关键词检索（倒排走 tsvector/GIN，BM25 分在应用层自算；top20）
      → RRF 融合（k=60）→ top20
      → bge-reranker 重排 → top5      ← D18 学的是这一步，D19 落地
      → 组装 prompt（片段+引用编号）
```

`RETRIEVER_CONFIG = pure_vector | hybrid | hybrid_rerank` —— 三态可切，
供 D23 的消融实验复用（这也是为什么 D19 要顺手做配置化）。

### 3.1 为什么这个脚本需要存在（而不是跑完就扔）

D18 一开始所有实测都在 `/tmp` 里。问题很具体：

- 我在 `/tmp` 测出「2.8 ms/篇」，**这个数是错的**（用了 12 token 的短句）——
  如果没有把脚本入库，D19 做延迟预算时会**没有任何依据去质疑它**
- 延迟数据必须能**重跑**，因为机器负载会变（§7 坑 1），一次性的数字无法判定是否被污染

所以入库的收益不是"保存脚本"，而是**把"这次测量是在什么条件下做的"固定下来**。

### 3.2 段落结构（对应它回答的四个问题）

| 段 | 回答什么 | 关键手段 |
|---|---|---|
| ① token 换算 | 一篇切片到底多少 token？ | 同一个 tokenizer 实测 5 档长度 |
| ② 延迟 | 候选数 / 切片长度怎么影响耗时？ | 4 档长度 × 3 档 top-k，每档重复取**最小值** |
| ③ 会话配置 | 有没有免费开关？ | 3~4 种 session 配置横向对照 |
| ④ 批推理 | batch_size 是杠杆吗？ | 读签名 + 比较 20 与 64 |
| ⑤ 语义 sanity | 它真能把"该排第一的"排第一吗？ | 3 篇内容互异的切片，看排序与分数形态 |

### 3.3 两处刻意的设计（都是踩过坑才加的）

**① 每个段落都打 `load_tag()`**

```python
def load_tag() -> str:
    """当前 load average / 逻辑核数 —— 延迟数字的解读前提。"""
    la = os.getloadavg()[0]
    return f"load={la:.2f}/{os.cpu_count()}核"
```

理由见 §7 坑 1：同一份代码两次跑差 1.8 倍，**差异不来自代码而来自 CPU 争用**。
不带 load 的延迟数字**不可解释**，只能当上界。

**② 测量段落同时打印**逐次原始值**，不只报最小值**

```python
ts = [_time(...) for _ in range(repeat)]
print(" / ".join(f"{t:.1f} ms" for t in ts) + f" → 中位 {...}")
spread = (max(ts) - min(ts)) / min(ts) * 100
print(f"抖动幅度 = (max-min)/min = {spread:.1f}%  （>50% 说明机器在被抢核…）")
```

只报 `min()` 会把一次 966 ms / 一次 1512 ms 的实验粉饰成"742 ms，很稳定"。
**把抖动本身也打出来**，读数字的人才能判断这组数可不可信。

**③ 结论全部由实测推导，不写死**（这条是事后补的，见 §7 坑 3）

```python
nt300, r300 = measured[300]
nt75, r75 = measured[75]
print(f"  实测换算：{nt75} tok → top20 {r75[2]:.1f} ms；{nt300} tok → top20 {r300[2]:.1f} ms"
      f"（token 比 {nt300 / nt75:.2f}× → 耗时比 {r300[2] / r75[2]:.2f}×）")
```

## 4. 类比迁移表

| 概念 | 前端/工程里的类比 | 对应关系 |
|---|---|---|
| bi-encoder（双塔，分开编码） | 给每篇文章预先建好**索引文件**，搜索时只比对索引 | 可离线批量、可建索引 |
| cross-encoder（交叉编码） | 每次搜索都**现场把 query 和文章一起交给专家读一遍** | 不能预先算、不能建索引 |
| 两阶段检索 | CDN 命中率 + 回源精算 | 先用便宜的方式缩范围，再用精确但贵的方式定夺 |
| RRF 只看名次 | 只看两个评委给的**排名**，不看打分表 | 去掉量纲，只要序 |
| 重排替换分数 | 复评**重新打分**，而不是把两轮分数相加 | 量纲不同不能相加 |
| logit 分数（可正可负） | 没有归一化的原始分，不是百分比 | 不能设绝对阈值 |
| `load_tag()` | 压测报告里必须写明的**机器规格与并发数** | 没有前提的数字没有意义 |

## 5. 面试考点

**Q：你的 RAG 链路为什么要有重排？已经有 RRF 融合了。**
> 因为 RRF 只看名次、不看内容。它能处理两路**分歧**，但处理不了两路**一致但不相关** ——
> 比如两路都把一篇讲"审批流程"的文档排在讲"金额标准"的文档前面，RRF 看到两组名次一致，
> 只会把错误放大。重排把 (query, 文档) 拼成一条序列逐对读，才有能力区分"字面/语义都像"和"真的回答了问题"。

**Q：为什么不直接用重排做检索？它更准。**
> 因为它不能建索引。文档的分数依赖 query，所以"文档向量"不存在，也就没有 ANN 索引可建。
> 1 万篇要跑 1 万次完整前向 —— 分钟级。两阶段的本质是：用便宜且能预计算的把 1 万缩到 20，
> 再用贵但准的把这 20 排好。

**Q：重排打分的阈值怎么定？**
> 不定绝对阈值。它是 logit，可正可负（实测同一批候选里有 +2.96 也有 -10.20），
> 而且**不可跨 query 比较** —— 换个问题同一篇文档分数完全不同。
> 所以我们只按**名次**截断（top5），不按分数过滤。

**Q：RRF 的分数和重排的分数能相加吗？**
> 不能。这是第三种量纲：cosine 有界 [0,1]，BM25 无上界（本语料 2~3），重排是 logit（可负）。
> RRF 之所以能融合前两者，正是因为它**把分数扔了只留名次**；重排则是**替换**原分数。

**Q：重排的延迟怎么控制？你试过哪些优化？**
> 实测生产尺寸（300 字 / 223 token）top20 重排约 **750–820 ms**（机器 load ≤10 时抖动 <10%），
> 这是链路里最大的串行成本。三条"看起来该有效"的优化我都试过，全部无效：
> 换线程数（4/10 都更慢）、换 CoreML 执行器（慢 7 倍，图被切碎且每 pair 一次独立前向）、
> 批推理（`batch_size` 默认 64，20 条本来就在同一批里）。
> **唯一有效的旋钮是减少候选数**，耗时与候选数近似线性，20→10 省约一半。

**Q：怎么保证 BM25 的中文检索可用？**（D16 的延续，重排会放大分词错误）
> 倒排用 `tsvector` + GIN，BM25 打分在应用层自算（`ts_rank` 拿不到 `df/N/avgdl`，IDF 算不出来）。
> 中文必须走应用层 jieba + `simple` 配置，且**索引侧与查询侧必须同一个分词器**——
> 这是单点函数保证的，不是文档约定。

**2.** 文档 A 在向量路排第 1、BM25 完全没召回；文档 B 在两路都排第 3。
   谁的 RRF 分高？这说明 RRF 偏向什么？它**纠正不了**哪一类错误？

**3.** 重排分数能不能这样写：`if score < 0.5: 丢弃这条`？为什么？
   如果真要丢掉"明显不相关的"，应该拿什么当判据？

**4.** 如果语料从 1 万篇涨到 100 万篇，两阶段架构里**哪一段的成本会变**，哪一段基本不变？为什么？

**5.** 我实测了三种"看起来该有效"的提速手段（线程数 / CoreML / 批推理），全部无效。
   请逐个说明原因。**然后回答**：剩下的有效旋钮是什么，代价是什么？

<details>
<summary>参考答案</summary>

**1.** 因为 cross-encoder 的输入是 `[query, document]` 拼接后的**一条序列**，输出是一个标量。
   文档的表示**依赖 query** —— 换个问题，同一篇文档要重新跑一遍。
   而 ANN 索引（HNSW / IVF）的前提是"每个文档有一个**独立于查询**、可以预先算好的向量"，
   这个前提在 cross-encoder 里根本不成立。bi-encoder 之所以能建索引，
   正是因为它把 query 和 doc **分开**编码，doc 向量可以离线批量算好入库。

**2.** B 高。B = `2/(60+3) = 2/63 ≈ 0.03175`，A = `1/61 ≈ 0.01639` —— B 是 A 的约 1.94 倍。
   说明 RRF 偏向"**被多条列表同时提名**"的文档，而不是"在某一路里排第一"的文档
   （哪怕 B 在两路里都只是第 3，A 在其中一路是第 1）。
   它纠正不了的是"**两路一致但都不相关**"—— 因为 RRF 看不到内容，两路名次一致时它只会顺着名次排。

**3.** 不能。它是 logit，**可正可负**（实测同一批候选里有 `+2.9621`，也有 `-10.1957`），
   而且**不可跨 query 比较**：换一个问题，同一篇文档分数完全变，
   所以 0.5 在不同查询里含义完全不同（一个查询可能全部 > 3.0，另一个全部 < -2.0）。
   真要做"丢掉明显不相关的"，只能：① 按**名次**截断（top-k）；② 或者用**同一次查询内**的
   相对量（如"只保留分数 ≥ 本次 top1 分数的某个比例"，且比例要靠评测调），
   而不是一个跨查询的绝对阈值。

**4.** 阶段 1（ANN 检索）成本随 N **对数增长**（HNSW 约 O(log N)），基本可控；
   阶段 2（重排）成本**只取决于候选窗口大小**（如 20），与 N **无关** —— 这是两阶段架构
   最值钱的性质：**把"全库规模"换成"固定窗口"**。
   真正会随 N 线性增长的是**索引构建与存储**（离线、可并行），不在查询路径上。

**5.**
   - **换线程数**：`threads=4` → 905.8 ms（1.09×）、`threads=10` → 929.4 ms（1.12×），都**更慢**。
     我们每个 pair 是一次**独立小前向**，并行收益小于线程调度开销 —— CPU 上小 batch 的常态。
   - **换 CoreML 执行器**：慢了约 7 倍。它只能接管 641 个节点里的 405 个，图被切碎；
     而"每个 pair 一次独立前向"意味着**每次前向都要付一次分区与跨设备搬运开销**。
   - **批推理**：`rerank()` 的 `batch_size` 默认 **64**，而候选窗口只有 20 ——
     **20 条本来就已经在同一个 batch 里**，所以它不是"缺失的杠杆"，是本来就没浪费。
   - **剩下的唯一旋钮：减少候选数**。实测耗时与候选数近似线性（top20 / top5 = 4.41×），
     20→10 约省一半。代价是**召回面收窄** —— 重排只能在候选集里重排，进不了候选的正确文档
     永远没机会。所以这个数不能随便砍，要用 D20–D24 的评测来定。

</details>

## 7. 踩坑记录

### 坑 1：延迟数字被 CPU 争用污染（1.8 倍），而我差点就这么汇报了

同一台机器、同一份代码、同一档输入（300 字 / 223 token / top20），**四次测量**：

| 轮次 | load average | top20 @300字 | 同批抖动 |
|---|---|---|---|
| ①（机器空闲） | 未记录 | **729.6 ms**（719.5 / 709.0 / 743.8） | ~5% |
| ②（两个重排进程并发） | **14.75 / 10 核** | **1369.6 ms**（966.4 / 1469.2 / 1512.5） | **56%** |
| ③（受控复测） | 6.94 | 754.5 ms（741~789） | 6% |
| ④（脚本正式运行） | 9.20 | 812.2 ms（821.4 / 821.3 / 843.0） | 2.6% |

**差值不是代码问题，是 CPU 争用**：onnxruntime 默认开满核，谁在旁边抢核，延迟就被放大。

判断依据是一个细节：**四档长度（75/150/300/450）同时等比放大 ~1.8 倍** ——
这种"全局等比放大"是资源争用的特征（真 bug 通常只影响某一条路径）。

**➜ 落地的教训**：**延迟数字必须连同当时的 load average 一起报**，否则不可解释、
不可比、不可复现。这条已写进脚本（每个段落都打 `load_tag()`）和协作规则。

> 附带一条：发现污染是因为**第一批和第二批差 1.9 倍**。如果我只跑过一次，
> 就会把一个差一倍的数当成事实。**关键性能数字至少要独立测两次。**

### 坑 2：用十几字的短句测出「2.8 ms/篇」，差了 250 倍

第一次后台下载完模型时的自测：喂两句十几字的中文，得到「首次推理 13 ms」「20 篇 56 ms（2.8 ms/篇）」。

**这个数是假的** —— 但脚本没错，是**测试对象选错了**：那两句只有 **12 token**，
而生产切片是 `CHUNK_SIZE = 300` 字 → **223 token**，差 **18 倍**。

**关键认知：决定推理成本的是 token 数，不是"篇数"。**
按真实尺寸重测后差异是 **250 倍**（2.8 ms → 700+ ms）。

**➜ 教训**：性能测试的输入必须**与生产同尺寸、同形态**。这是铁律 9
「测首次成本要保证未被使用过」的同类 —— 都是"被测对象的前提没对齐"。

### 坑 3：结论硬编码在 print 里 —— 同一个毛病**第三次**犯

脚本 ② 段原本写死一句「生产尺寸（300 字）下 top20 ≈ 690~740 ms」。
可当机器负载高时，它上面打印的行是 **1369.6 ms** —— **数据与结论互相矛盾，脚本照念不误**。

同样的问题在 ③ 段更严重：加了 `--no-ep` 跳过 CoreML 后，
脚本**照样**打印「CoreML 慢约 7 倍」—— 那是**没测出来的东西，却被当成结论汇报**。

这个坑的历史：**D13**（构造的对照表证不了结论）、**D16**（E 段打印"区分度放大"却照念"被压缩"）、
**D18**（本次）。三次都是"把结论写成 print 字面量"，而不是从数据推导。

**➜ 修法**：所有结论改成从当次实测值推导；**没测的分支明确打"未测，不下结论"**。
这条已经写进协作规则（铁律 11），但显然规则不够 —— 真正的解法是
**写 print 结论时先问自己："这行字里的数字，是上面哪个变量算出来的？"** 答不上来就是硬编码。

### 坑 4：`asyncio.run` 写在协程里（自造的运行时错误）

延迟脚本第一版把"从数据库读切片"写成一个普通函数、内部 `asyncio.run(...)`，
然后在一个 `async def main()` 里调它 → `RuntimeError: asyncio.run() cannot be called from a running event loop`。

**➜ 教训**：一个进程里**事件循环只能有一层**。要读库就在同一个 async 上下文里 `await`，
不要为了"看起来方便"在协程内部再起一个 loop。

### 坑 5（环境）：`huggingface.co` 直连不通

```
huggingface.co         → HTTP 000（不通）
hf-mirror.com          → HTTP 200 ✅
storage.googleapis.com → 可达
```

必须 `os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")`，
且**要在 import 之前**。1.04 GB 模型走镜像 2m17s 下完，落盘 2154 MB（含 f32/fp16 两份），
加载 634~1024 ms。

## 附录 A：实测数据汇总

### A.1 token 换算（`①` 段实测）

| 切片字符数 | tokens | token/字 |
|---|---|---|
| 75 | 59 | 0.79 |
| 150 | 111 | 0.74 |
| 300 | 223 | 0.74 |
| 450 | 327 | 0.73 |
| 600 | 439 | 0.73 |

**中文约 0.73 ~ 0.79 token/字** —— BPE 会把常见词合并，所以不是 1:1。

### A.2 延迟：切片长度 × 候选数（load = 9.20 / 10 核）

| 切片 | tokens | top5 | top10 | top20 | 单篇 @20 |
|---|---|---|---|---|---|
| 75 字 | 59 | 50.1 ms | 96.8 ms | 211.6 ms | 10.58 ms |
| 150 字 | 111 | 88.4 ms | 175.5 ms | 370.5 ms | 18.52 ms |
| **300 字（生产尺寸）** | **223** | **184.0 ms** | **390.0 ms** | **812.2 ms** | **40.61 ms** |
| 450 字 | 327 | 297.6 ms | 617.9 ms | 1268.8 ms | 63.44 ms |

- token 比 3.78× → 耗时比 **3.84×**（近似线性）
- 候选数比 4×（top5→top20）→ 耗时比 **4.41×**（近似线性）

### A.3 会话配置对照（top20 @ 300 字）

| 配置 | 耗时 | 相对基准 |
|---|---|---|
| **默认（0 改动）** | **831.4 ms** | **1.00×** |
| threads=4 | 905.8 ms | 1.09× |
| threads=10 | 929.4 ms | 1.12× |
| CoreML 执行器（另一轮测） | 5060.4 ms | **≈7×** |

### A.4 批推理

```
rerank 签名: (query, documents, batch_size: int = 64, **kwargs) -> Iterable[float]
```

`batch_size` 默认 **64** > 候选窗口 **20** ⇒ 20 条本来就在同一批里，**不是缺失的杠杆**。

### A.5 语义 sanity check

```
query = '年假有几天'
  1. 制度综合（含年假）   score=+2.9621   (300 字 / 223 tok)
  2. 考勤管理            score=-0.9890   (219 字 / 168 tok)
  3. 运维发布规范        score=-10.1957  (255 字 / 180 tok)
```

含"年假"的那篇排第一 ✓；同时直接演示了**分数可正可负**（这是 §2.4 三个坑的原始证据）。

### A.6 诚实边界（必须一起读）

- `⑤` 段的三篇文档是**我合成的**，不是库里的真实语料
- 真实语料目前只有 **1 篇文档 / 3 个切片**（62~73 字），D16/D17 的验证脚本各自清理了测试数据
- 所以这批数据的价值是给出「**token 数 → 延迟**」的换算关系，
  **不代表线上表现**；D19 做端到端延迟验证时可能需要先造一批真实尺寸的语料
- ② 段用的 20 篇是**同一份文本复制 20 份** —— 只用于测时间，**排序结果无意义**（分数必然相同）
