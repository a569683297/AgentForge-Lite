## §1 核心原理：评测必须拆成两阶段

> **两阶段** = 先生成（跑被测系统）、再打分（judge），中间把答案落库。
> 而不是"跑一条、立刻打一条"。

### 1.1 为什么不能合在一起

D20 实测出的硬事实：

> **"3 次重复"重复的是 judge（裁判），不是生成。**
>
> 同一条 B01 题、同配置、两次独立运行 → 459 字判**对** / 511 字判**错**；
> 而 judge 内部各自 5 次打分完全一致（`[2,2,2,2,2]`）。

**重复打分对"这次答案本身就没生成好"完全无效。**

如果生成与打分写在一个循环里（跑一次 → 打一次），代码结构上就**表达不出**
"重复只打在裁判上"这件事 —— 你只能写出一个笼统的 `repeat=3`，
而它对两个完全不同的抖动来源一视同仁。

拆开之后，两个次数各有独立的名字与参数：

| 参数 | 含义 | 对抗什么 |
|---|---|---|
| `generation_runs` | 同一道题让**被测系统**跑几次 | **生成侧抖动**（答案本身是随机变量） |
| `runs_per_case` | 同一份答案让 **judge** 打几次 | **裁判侧抖动**（量具有误差） |

### 1.2 拆开还省一大笔钱

| | 单次耗时 | 50 条 × 3 配置 |
|---|---|---|
| 生成（检索 + 重排 ~760ms + LLM 几秒） | 5~10 s | 150 次 ≈ **15~25 分钟** |
| 打分（judge 调 deepseek） | ~1 s | 450 次 ≈ **6 分钟** |

如果不拆、把"3 次重复"套在整条链路上：`150 × 3 = 450` 次**生成** ≈ 45~75 分钟。
花 3 倍钱，买到的还是同一份答案打 3 次 —— **重复错了对象**。

### 1.3 流水线

```
① 冻结校验   两个指纹（题 + 语料）与库中一致 —— 不一致就拒绝跑
      ↓
② 建 run     先建 eval_runs 拿 run_id（汇总分留空）
      ↓
③ 生成       每条题 × generation_runs 次
             每次**全新 session**、persist=False
      ↓
④ 打分       每份答案 × runs_per_case 次 → 取中位数
      ↓
⑤ 归因       纯函数推导 failure_reason（不让 judge 自由发挥）
      ↓
⑥ 落库 + 汇总  明细写 eval_case_results；汇总回填 eval_runs
```

### 1.4 两个写死在代码里的前提

**前提 ①：每条题用全新 session。**

`persist=False` 只保证"不写"，**不保证"读不到别人写的"**。
`run_agent` 的 ① 会去读 Redis 热窗口 —— 如果复用 session，
第 2 题会读到第 1 题的问答，答案就真的变了。
所以 runner 每条题都 `uuid.uuid4()` 新建 session。

这是"关掉写入不影响答案"这个论断的**前提条件**，不是顺手为之：
关掉写入之所以安全，是因为读写都发生在**同一次运行内**且读在写之前；
一旦跨题复用 session，"读到自己刚写的东西"就成了可能。

**前提 ②：生成串行、打分并发。**

生成里包含重排（本地 ONNX，CPU 密集）与 embedding。并发会抢核 ——
D18/D19 实测过 load 一高延迟就飘（751ms → 1.4s），而延迟本身也是这次要记录的数据。
打分是"等外部 HTTP"，天然适合并发（`settings.judge_max_concurrency = 4`）。

## §2 数据层

### 2.1 三张表的关系

```
eval_cases         一行 = 一条评测用例（题面 + 参考答案 + 依据）
     │
     │  被引用（不建外键 —— 见 2.6）
     ↓
eval_runs          一行 = 一次评测运行（配置 + 汇总分 + 用哪版题、哪版语料）
     │
     │  run_id 外键 ON DELETE CASCADE
     ↓
eval_case_results  一行 = 某次运行里、某道题的**某一次生成**及其打分结果
```

一句话类比：`eval_runs` 是"班级平均分"，`eval_case_results` 是"每个学生每道题的得分"。
只有平均分，你答不出"是几何题差还是代数题差"。

### 2.2 明细表的粒度：为什么是"**一次生成**"而不是"一道题"

`generation_runs > 1` 时，一道题会有多份答案。如果把多份压成一行：

- 看不出这份题到底飘不飘 —— 而这正是 D22 要量的东西
- `runs_per_case` 次打分只有一组原始分数，多个答案的分数会互相污染

所以粒度取**最细**：一道题生成 N 次 → **N 行**。
"这道题的结论"由聚合得出（`GROUP BY case_key` + 多数投票）；
"生成侧抖动" = 同一个 `case_key` 的 N 行里 `passed` 的分布。
**一行只存一次生成，才能同时支持这两件事。**

### 2.3 哪些字段必须存

| 字段 | 为什么不能省 |
|---|---|
| `answer` | 报告里"失败案例各取 3 条"直接取它 |
| `retrieved_chunks` | judge 的 `faithfulness` 维度是拿**片段**当对照物（不是参考答案）。不存下来就没法复现或重判 |
| `tool_calls` | 算 `tool_miss` 的**唯一输入**。而"该不该调工具"从答案文本里看不出来 |
| `judge_raw` | 各次打分的原始输出。D20 的教训是"报平均分等于在比噪声更小的差异" —— 存下每一次才能事后算抖动 |
| `judge_runs` | 实际成功次数。`< runs_per_case` 说明有调用失败，这条数据不满次数 |

**如果没有 `tool_calls` 与 `retrieved_chunks`，明细表就只剩一堆分数** ——
与只有 `eval_runs` 没有本质区别，下钻能力归零。

### 2.4 `category` 冗余存一份：代价与它的保险

PRD F7.10 的固定查询是 `SELECT category, AVG(score_faithfulness) ... GROUP BY category`。
冗余之后免掉 join，代价是"两处可能不一致"。

**代价必须有人看着**，所以验证脚本有一条断言钉住它：

```
C6 明细的 category 与评测集一致（冗余列不漂移）
```

否则按类别聚合出来的分布是错的，而**没有任何报错**。

反之，`config_name` **故意不冗余**：它是 run 的属性，一台 run 只有一个值，
冗余反而多一处可能写歪的地方，而 join 一次的成本可忽略。

### 2.5 迁移：`create_all` 不给已存在的表加列

D22 需要给 `eval_runs` 加两列（`corpus_fingerprint` / `generation_runs`）。

而 `Base.metadata.create_all(checkfirst=True)` 的行为是"**表存在就整张跳过**"——
不补外键、**不加列**、不改类型，一声不吭。

于是"给 eval_runs 加了列"这件事在 ORM 里成立、在库里不成立，而应用照常启动。

所以 `scripts/d22_migrate.py` 的能力 = `create_all`（建新表）+ **显式 ALTER**（改旧表）：

```python
_ALTERS = [
    ("eval_runs", "corpus_fingerprint", "VARCHAR(64)"),
    ("eval_runs", "generation_runs", "INTEGER"),
]
```

实际输出（第一次跑）：

```
[1/5] 建缺失的表      本次新建：['eval_case_results']
[2/5] 给已存在的表补列  本次新增列：['eval_runs.corpus_fingerprint', 'eval_runs.generation_runs']
[3/5] 回读库结构        三张表列数与类型全部匹配
[4/5] ORM ↔ 库 交叉核对  三张表一致
[5/5] 外键与级联        run_id → eval_runs（ON DELETE CASCADE）
```

第二次跑会打出 `（无，表已存在）` 与 `（无，列已存在）`——
**"这次加了几列"这个数字本身就是幂等性的证据**。

### 2.6 两个刻意的"没有外键"

`eval_case_results.case_key` **不建外键**指向 `eval_cases.case_key`。

理由：评测明细是**历史记录**。题目被重写或删除后，历史分数仍应可读。
外键会拦住评测集重建 —— 而重建评测集是经常发生的事（`d21_seed` 每次都清空重写）。
**为了让历史保持可读，宁可牺牲引用完整性**，代价是"明细可能指向已不存在的题"，
这由 C5 断言（明细的 case_key 能在评测集里找到）在**每次验证时**检查。

## §3 打分层

### 3.1 为什么要给 Gateway 加"锁通道"

**背景**：`scripts/d20_judge_probe.py` 当时**自己发 httpx**，绕过了 `llm_gateway`。

**为什么绕**：Gateway 的 `_call_with_failover` 语义是"主通道失败 → 静默切备用"。
judge 若走它，会出现"一部分样本是 deepseek 打的、一部分是中转 GPT 打的"，
**而报告上只写一个 judge 名字** → 分数不可比、且没有任何报错。

**但绕过违反了 PRD §8.2 的架构红线**："业务代码不得绕过 Gateway 直连 SDK"，
绕了就没有 Langfuse 追踪、没有 token 统计。

所以 D22 给 Gateway **加了锁定通道的能力**，而不是让调用方自己发请求：

```python
chat(..., provider="deepseek")    # 只用该通道，失败就抛，绝不偷偷换
chat(..., allow_failover=False)   # 不指定通道时，只用主通道
```

这是"**降级是有代价的**"这条认识的具体落地：
降级让"用了哪个通道"这件事**从数据里消失**。

### 3.2 锁定模式不包装异常（一个不显眼但重要的细节）

多通道降级失败时，Gateway 抛 `RuntimeError("所有 LLM 通道均失败: ...")`。

但**锁定模式不能这样包装**，因为包装会把 `httpx.HTTPStatusError` 变成 `RuntimeError`，
调用方（judge 的重试逻辑）就没法判断"这个错重试有没有意义"：

| 异常 | 该不该重试 |
|---|---|
| 429 限流 | **该** —— 等一会儿就有额度 |
| 503 / 超时 | **该** |
| 401 鉴权失败 | **不该** —— 重试 100 次都是同样的错，只会把延迟放大 3 倍 |
| 400 参数错 | **不该** |

包成 `RuntimeError` 后这四种长得一模一样 → **信息在包装时被丢掉了**。
所以锁定模式直接 `raise last_error`（保留原始类型）。

### 3.3 聚合口径：中位数 ≥ 阈值 ≡ 多数投票

D20 定的规则是"3 次多数投票"（每次二值化为通过/不通过，再取多数）。
`judge_service.aggregate` 的做法是"取三维度分数的**中位数**，再按阈值二值化"。

两者**数学上等价**（阈值是单点、比较是单调的）：

```
中位数 ≥ 4  ⟺  至少半数以上的次数 ≥ 4  ⟺  多数投票通过
```

取中位数的额外好处是**同时得到分数值**（报告要报均分），而多数投票只给 0/1。

**为什么不用平均分**：平均分对极端值敏感。3 次里出现一次离谱的 0 分（judge 抽风），
平均分被拉到 2.67，而中位数仍是 4 —— **判定结论完全不同**。

### 3.4 打分全失败 → 抛错，不落库

```python
if outcome.all_failed:
    raise RuntimeError(...)   # 中止本轮评测
```

理由：把打分失败落库成"答错"，会让**量具故障伪装成系统缺陷** ——
而两者的修法完全不同（一个修 judge 通道，一个改检索/prompt）。
这正是 D21 那条教训的形态：静默地把一种情况算成另一种。

只失败**一部分**时保留（用成功的几次算），但 `judge_runs` 会如实记下次数，
验证脚本据此能看出"这条数据不满次数"。

## §4 归因层

### 4.1 `failure_reason` 为什么必须机械推导

> **`failure_reason`（失败归因）**：一个短字符串，说明这道题**为什么**没通过。
> 它存在的唯一目的是让报告能做"失败模式聚类" ——
> 即"这次失败里，有几条是没检索到、有几条是编造"。

最自然的写法是让 judge 在 JSON 里多吐一个 `"failure_reason": "..."` 字段。
**这条路是错的**，三个理由，每一个单独都足以否决：

| 问题 | 具体表现 |
|---|---|
| **同义异形** | 5 次调用写出"检索未命中"/"资料缺失"/"没找到相关内容"/"知识库无此信息" → 聚类时被算成 **4 类** → 报告里的失败模式分布是**假的**，且没有任何报错 |
| **不可复现** | 同一份答案重跑一次，judge 换一种措辞 → 同一份报告两次不一样 |
| **不可测** | 自由文本没法写断言（"这条应该是 hallucination" 无法机检）|

同族先例（本项目真发生过）：D14 的 `messages.tool_calls` 被 SQLAlchemy 存成
JSON 字面量 `null` 而非 SQL NULL → **同一语义有两种表示** → `IS NULL` 恒为假，
整片逻辑静默失效。

**判据（一句话）**：

> **能用纯函数从已有数字推出来的东西，不要让模型再生成一遍。**

可执行自检（`d22_verify.py` B1 在做）：
**同一份答案重复推导 10 次，结果必须完全相同。**

### 4.2 六个取值

| 值 | 含义 | 触发条件 |
|---|---|---|
| `system_error` | 没跑成 | 生成阶段就失败（LLM 全通道挂 / 超时 / 异常） |
| `tool_miss` | 没调对工具 | C 类题 `expected_tool` 明确，实际未调用或调了别的 |
| `hallucination` | 编造 | `faithfulness ≤ 2` |
| `incomplete` | 答不全 | `completeness ≤ 2` |
| `wrong_answer` | 答错 | `correctness ≤ 2` 或遗漏 |
| `None` | 通过 | `passed = True` |

### 4.3 优先级：上游原因优先于下游表现

```
system_error → tool_miss → hallucination → incomplete → wrong_answer
```

"没调工具"是**根因**，"答错了"是它的**结果**。若一律记成 `wrong_answer`，
"工具选择错误"这个失败模式就被藏起来了 —— 而它恰恰是 C 类题存在的意义。

**两个刻意的设计决定**：

1. **C 类题 `tool_miss` 有否决权**：答案侥幸对了也算不通过。
   C 类题测的是工具调用能力，答案对不是它要测的东西。
2. **先判 `faithfulness` 再判 `completeness`**：编造比漏答严重。
   编造是"引入了不存在的事实"（会误导用户）；漏答只是"说得不全"。

### 4.4 `expected_tool` 的三种语义

| 取值 | 含义 | 判定 |
|---|---|---|
| `None` | **未约束**（A/B 类题） | 调不调都算过 |
| `"__none__"` | **显式要求不调工具** | 调了就是错 |
| `"xxx"` | 必须调用到它 | **调了别的也算不满足** |

第三种值得展开：用 `in` 而不是 `==` 比较（一步题里可能先调 `search_documents`
再调别的，只要目标工具在序列里出现过就算命中）。而"调了别的工具"算不满足，
是因为 C 类题测的是"**选对**工具"，不是"有调工具"。

## §5 编排层

### 5.1 生成阶段（串行，每条全新 session）

```python
for case in cases:
    for generation_index in range(generation_runs):
        session_id = uuid.uuid4()
        try:
            result = await run_agent(session_id, case.question, persist=False)
        except Exception as exc:
            ...  # 记为 run_failed，不中断整轮
```

**生成失败不中断整轮评测**：记为 `run_failed`，由归因函数判成 `system_error`。
这本身是有价值的数据（"几个配置里有没有哪个跑不通"），
把它扔掉等于把"系统稳定性"从评测里删掉。

### 5.2 打分阶段（并发）

```python
tasks = [[asyncio.create_task(_judge_with_semaphore(...)) for _ in range(runs_per_case)]
         for row in answers]
```

⚠ 这里有一处**我写错又改回来**的地方（见 §8 踩坑①）：

```python
# 错的：
all_results = await asyncio.gather(*tasks)
started = time.perf_counter()        # ← 计时起点在区间之后 → 算出 0.0s
```

### 5.3 配置切换的陷阱：赋值绕过 validator

`retrieve()` 从 `settings.retriever_config` 读配置，所以切换配置只需改这个值。
但：**pydantic 的 `BaseSettings` 默认不校验赋值**（`validate_assignment=False`）。

```python
settings.retriever_config = "hybrid_rerankk"   # 多打一个 k
# ↑ 不会报错！那个 field_validator 只在构造 Settings 时跑，管不到赋值
```

后果：检索会静默走默认分支，**那一列的配置就是假的**。

所以 `run_evaluation` **自己显式校验**，不指望配置层的 validator：

```python
if config_name not in RETRIEVER_CONFIGS:
    raise ValueError(...)
```

并且跑完**必须恢复**（`try/finally`）—— 否则后续手动对话会莫名其妙
用了最后一档配置，而那不会有任何提示。验证脚本 C1 断言钉住这一点。

### 5.4 两个口径（必须分开说清）

| 指标 | 分母 | 为什么 |
|---|---|---|
| `accuracy` | **题数** | PRD 的 "+10%" 说的是**题目**的百分比（50 条里多对 4 条）。按行算的话 `generation_runs` 一变分母就变，"+10%" 立刻不可解释 |
| 三维度均分 | **明细行数** | 它衡量"系统产出的东西平均质量如何"，天然是逐次生成的粒度 |

⚠ **两者分母不同，不能互相印证**。报告里必须分别写明 ——
这是 D20 留下的教训（不同口径的数字不能并列比较）。

`summarize_results` 是这两个口径的**唯一定义出处**（纯函数、可单测），
并且**同时接受 dict 与 ORM 对象**（见 §5.5）。

### 5.5 汇总的两条路径必须给出同一个数字

同一个 `summarize_results` 被用在两处：

- `run_evaluation` 跑完当场算（手里是 dict）→ 写回 `eval_runs.accuracy`
- `GET /api/eval/runs/{id}` 读历史时重算（手里是 `EvalCaseResult` 对象）

两处**必须一致**，否则"报告里的准确率"与"接口读出来的准确率"会不同，
而这是最难发现的一类错（两份数字都"有来源"）。

所以用 `_field(row, key)` 抹平两种输入，并且验证脚本有一条断言：

```
D5 从库重算的准确率 == 跑完当场算的准确率
```

## §6 三个决策怎么落进代码

### 决策 1：生成要重复 → 参数做进主干，默认 1，用探针数据决定

**落地**：`generation_runs` 是 `run_evaluation` 和命令行的一等参数（不是后加的）。

理由：D22 的验收点（单条可评分 + 明细有行）**不依赖**这个数，
但 runner 的**主干结构**依赖它 —— 参数必须先有，哪怕默认是 1，
否则 D23 要改主干。

**默认 1 而不是 3**：如果生成抖动只集中在少数题上，×3 是花 3 倍成本买一点点方差下降。
`scripts/d22_generation_jitter_probe.py` 量出散布后由 D23 决定（见 §7）。

### 决策 2：指纹要覆盖语料 → 独立成列 + seed 前置校验

**落地**：

1. `eval_runs` 加 `corpus_fingerprint` 列（**独立一列，不与 dataset 指纹合并**）。
   理由：两者独立变化，合在一起时"变了"**无法归因**（是题被改了还是语料被换了？）
2. `compute_corpus_fingerprint(chunks_by_file)`：按文件名排序后各文件切片序列的 sha256
3. `d21_seed` 加**前置校验**：源文件侧按同样的 `split_text` 算一遍，与库里比对，
   不一致就报错并要求 `--force`

**覆盖面 = 正文内容 + 切片方式**：

| 动作 | 指纹 |
|---|---|
| 正文改一个字 | **变** |
| 改 `CHUNK_SIZE` 并重建 | **变**（这是要的：切片方式变了检索结果就变） |
| 重建语料（新 UUID） | **不变**（UUID 不进指纹） |

⚠ 第 3 行是 D21 的"好消息"，但**同一行代码反过来读就是"语料换了也不报警"** ——
这正是决策 2 要修的那个盲区。同一性质的两种读法。

**实测（改语料不 `--force`）**：

```
跳过 绩效考核与晋升管理办法.md   已存在（6 片，1528 字）   ← 整篇跳过，一行写库动作都没有
...
[OK] 源文件指纹 == 库中指纹：a7797b06…          ← 题没改，指纹当然不变
```

三处都不出声：语料没更新、指纹不报警、D 段断言只在被改的那句正好被某条 evidence
引用时才会红。**加上前置校验后就变成了一条明确的报错。**

### 决策 3：6 个值 + 纯函数推导规则表

**落地**：`app/services/failure_taxonomy.py`，见 §4。
`sequence_ok` 按建议**先不建**（今天没有 multi_step 类题，
建一个永远为 NULL 的列会让 `SELECT sequence_ok` 看起来像"实现了但都不通过"，
同族：D14 的 JSON null 让 `IS NULL` 恒假）。

验证脚本 A5 断言**它不存在** —— 把"我们刻意没建"变成机检事实，
防止后来有人"顺手补上"。

## §7 探针：生成侧抖动

> 数据见 `docs/tutorials/D22-生成抖动探针结果.md`（本篇只讲方法与结论）。

### 7.1 为什么必须实测

D21 观测到 B01 一次判对、一次判错。但**一个案例推不出分布** ——
可能就是这一条题特别飘。

如果只有少数题飘 → `generation_runs=3` 是花 3 倍成本买一点点方差下降；
如果大面积飘 → 不重复生成的话，D23 的 A/B/C 差异会被随机性淹没。

**两种情况的决策相反，所以必须先量。**

### 7.2 方法：三层，缺一层结论就会错

```
① 每道题生成 N 次            → 拿到 N 份**不同的答案**（这才是生成侧抽样）
② 每份答案打 M 次分，取多数   → 压掉**裁判侧**噪声
③ 比较 N 份答案的"多数结论"   → 剩下的变化只可能来自生成
```

⚠ **第 ② 步不能省**：省掉它，裁判的抖动会被误记成生成的抖动，
**夸大生成侧**，于是你会得出"要重复生成 5 次"这种过度投入的结论。

⚠ **反面**：也不能把 N 份答案**合在一起**打分取多数。那等于把"5 份不同答案"
当成"同一份答案的 5 次测量"，把生成侧抖动**抹掉**成裁判侧抖动 ——
方向相反的同一个错误。

### 7.3 对象选 `cross_doc`（往最坏处取样）

跨文档题需要两篇文档的信息拼起来才能答对，最容易出现"这次检索到 A、下次检索到 B"。
如果连它都不怎么飘，别的类更不用担心。

⚠ 这与 D21 的 ε 重测**取样策略相反**：那次是分层抽样（量"整卷"），
这次是往最坏处取样（量"最坏情形"）—— **因为问题不同，所以方法不同**。

## §8 踩坑

### ① 计时起点又写错了（方向相反的同一条坑）

小规模探路跑出来的输出：

```
[打分] 24 次成功（期望 24 次，其中 0 份未生成）耗时 0.0s
                                                      ↑ 24 次 HTTP 调用耗时 0 秒
```

原因：`started = time.perf_counter()` 写在了 `await asyncio.gather(...)` **之后**。

这与 D20 那条坑是**同一个错误的两个方向**：

| | 起点位置 | 后果 |
|---|---|---|
| D20 | 在并发锁**外面** | 排队时间混进单次耗时 → 0.84s 报成 11.74s（**差 14 倍**） |
| D22 | 在 `gather` **之后** | 耗时算成 0.0s |

两种都不会报错，只会给出一个"看起来很正常"的假数。
**这条纪律我刚写进 skill 就又踩了一次** —— 说明"写进规范"不等于"写到手上"。

**能发现它的唯一原因**是输出里带了这个数字：`耗时 0.0s` 显然不对。
如果当初没打印它，这个错误会一直留着（而它不影响任何功能）。

### ② `Bash` 的 `grep` 在本项目下又返回空

多次发生（D20 起记录在案）。查文件内容**一律用检索工具**。

### ③ 记忆文件超限被截断

`MEMORY.md` 超过 4000 字符限制，注入时被截断（头部出现 `ACTION REQUIRED`）。
已重整压缩到 3358 字符。

**这件事本身是个提醒**：长期记忆也会"静默失效"——
它不像报错那样显眼，只是**悄悄少了一段**，而那段可能正是关键的约束。

## §10 自测题

> **本节是 D22 自测题的唯一权威。**
> 开工前那份 [`D22-决策材料.md`](D22-决策材料.md) §4 的 6 题考的是"**量之前要先想清的事**"
> （抖动分三层 / 为什么必须机械推导 / 门槛数怎么来的），与本节**不重复**，两批都可做。
> 正文回复里的"成组提问"就是本节这 3 题 —— **以后不另行出题**。
> （起因：初稿时正文一套、本文件一套，两批题对不上，用户不知道该做哪批。
> 一个判断不能有两份权威 —— 这正是 D22 代码里反复强调的那条，我自己先犯了。）

### 怎么答：三级阶梯

每题都拆成 **L1 → L2 → L3**：

| 级 | 在问什么 | 答不出来意味着 |
|---|---|---|
| **L1 认出来** | 这题说的是哪个已写下的东西？能指着代码/表格说"就是它" | **我的讲解有洞**，直接说，别硬扛 |
| **L2 说因果** | 为什么必须这么写？换成另一种写法会怎样 | 概念没串起来，回看对应小节 |
| **L3 推边界** | 换一个没写过的输入，会发生什么 | 正常。L3 本来就是"衍生"能力，答不全是常态 |

**规则：L1 一定能在讲解正文里找到出处。找不到就是漏讲了，那是我的问题。**

---

**Q1（两个"重复次数"为什么不能合并）**

背景：`generation_runs`（每题让被测系统**生成**几次）与 `runs_per_case`（每份答案让 judge **打**几次）
是两个独立参数。

- **L1**：这两个参数各自对抗的是**哪一层**的随机性？（抖动分三层，见决策材料 §1）
- **L2**：如果合成一个 `repeat=3`（整套流程跑 3 遍），D23 报告里哪个数字会变得**无法解释**？
- **L3**：合成之后，花的钱大约变成原来的几倍？多花的钱买到了什么新信息？

---

**Q2（工具调用的三种语义）**

背景：`failure_taxonomy.tool_call_ok(expected_tool, actual_tools)` 内部用 `in` 比较。

- **L1**：`expected_tool` 取 `None` / `"__none__"` / `"search_documents"` 时，分别**在要求什么**？
- **L2**：某题 `expected_tool="search_documents"`，实际只调了 `list_documents`。算不算过？为什么这样定？
- **L3**：若删掉 `"__none__"` 哨兵、改成"`None` 表示要求不调工具"，哪一类题会立刻判错？错成什么样？

---

**Q3（面试题：你降的到底是什么噪声）**

面试官问："你说评测用 3 次多数投票降噪，**降的是什么噪声**？
生成那一步如果换个随机种子答案就变了，你这 3 次投票管用吗？"

- **L1**：这 3 次重复的是"**生成**"还是"**打分**"？（一句话）
- **L2**：为什么它救不了生成侧抖动？用 D20 的哪条实测证据说？
- **L3**：生成侧抖动靠什么解决？代价是什么？

### 附一：作废题一道（出题事故，说明在此）

本节初稿还有一道题：*"`_registration_row` 里 `_question` 和 `reference` 两个键为什么先挂上、落库时再剥掉？"*

**作废，两个原因**：

1. **`reference` 的挂载在正文讲解里没写**（只讲了 `_question`）。
   考一个没讲过的细节 = 出题事故，**不是答题人的问题**。
2. **题面表述与代码不符**：`_registration_row` 用的是**白名单挑选**（只列出它要的键），

   —— 排除的依据是"不在白名单里"，不是前缀。
