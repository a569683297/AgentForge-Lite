2026-10-02 · mcp 2.2.0 / Python 3.12 · 所有结论均由本机实测得出，取证脚本与日志在 /tmp/d26_probe/
这张图解决什么疑问？
D25 已经弄清「谁负责什么」：模型选工具 · Host 放行 · Client 搬运 · Server 执行。 今天往下一层：Server 拿到一次 tools/call 之后，它内部做了哪几件事，才把一个调用变成一次 Python 函数执行？ 顺带把一个"人人都说但没人验过"的说法当场验掉（§4）。

§1 先补两个名词（本图首次出现，先注解再用）

名词它是什么 / 解决什么问题在本项目里长什么样
stdio
standard input / output，标准输入输出		 进程天生自带的一对数据通道：stdin（读）与 stdout（写）。 不占端口、不走网络，两个进程靠"一个写另一读"对话。MCP 用它做最省事的本地传输。 Client 与 Server 是父子进程：Client 写子进程的 stdin，读子进程的 stdout
JSON-RPC 一种"调用约定"：每条消息都是一个 JSON，里面写清我要调用谁（method）、参数是什么、这次请求的编号（id）， 对方回一条同 id 的 JSON。解决"两个进程怎么把函数调用说清楚"这件事。 MCP 的每一条报文都是它。initialize / tools/list / tools/call 都是 method 的取值
fd
file descriptor，文件描述符		 操作系统给每个进程的一张小表，每一行是"一个可读写的东西"的编号。约定：0 = stdin，1 = stdout，2 = stderr。 程序里的 print() 最终就是往 1 号写。 §4 的判决证据就是比较 fd 1 与 fd 2 指向的是不是同一样东西
schema
inputSchema / outputSchema，模式		 一份"参数说明书"：这个工具要什么参数、什么类型、哪个必填。它的作用是让调用方不用读源码就知道怎么调 —— 模型就是靠读它来决定传什么参数的。 本项目不手写它：由 Python 函数签名自动生成（见 §5）

§2 Server 的最小骨架：只有三件事

一个 MCP Server 从头到尾只有三段，多出来的都是细节：

from mcp.server import MCPServer          # ← ① 建盒子

server = MCPServer("inventory")

@server.tool()                            # ← ② 往盒子里放工具
def query_inventory(min_stock: int | None = None) -> list[dict]:
    """查询库存商品。"""                    #    这行 docstring 会被当成工具描述
    ...

if __name__ == "__main__":
    server.run(transport="stdio")          # ← ③ 开张营业（此处开始阻塞）
①
建盒子 —— MCPServer("inventory")
只是造了个对象，还没连任何人。name 是第一个位置参数（实测签名确认）。
②
放工具 —— @server.tool() 装饰器
装饰器在函数定义的那一刻就把工具写进盒子里的一张字典。 这是"登记"，不是"调用" —— 函数体此刻一行都没跑。
③
开张 —— server.run(transport="stdio")
从这里开始阻塞：一直读 stdin、处理、写 stdout，直到 stdin 被关闭才返回。 实测：Client 断开后 server 进程正常退出（存活 0.94s）。生命周期由 Host 掌管 —— D25 讲的那条在这里落地。
给前端背景的类比：server.run() 之于 MCP Server，正如 app.listen() 之于 Express / http.createServer().listen() 之于 Node。 之前全是"配置"，它才是"开始接客"。区别只有一个：HTTP 服务监听端口，stdio 服务监听管道。

§3 一次 tools/call 在 Server 内部走的路

D25 讲的是"层与层之间谁把东西交给谁"。现在把 Server 这个进程切开，看它内部：

1
从 stdin 读到一行 JSON
形如 {"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"query_inventory","arguments":{...}}} —— 一行就是一条完整消息（这叫 newline-delimited JSON）。
2
看 method 是什么，决定走哪条分支
initialize → 回自己的能力；tools/list → 回工具清单；tools/call → 往下走。
3
拿 params.name 去字典里查
Server 内部维护一张字典：工具名 → 工具对象（工具对象上挂着那个真正的 Python 函数）。 所谓"路由"，就是一次字典查表。查不到 → 返回"工具不存在"，但不抛异常（见下方 §5 末）。
4
用 inputSchema 校验参数
类型不符就直接拒绝，根本不会进入你的函数体。 实测：给一个要 str 的参数传 123，Server 回 rejected arguments: ['text']。
5
调用真正的 Python 函数
到这一步才执行你写的业务代码。函数的返回值就是工具的返回值。
6
把返回值包成"双层结构"
同一个结果发两份：content（给人/模型读的自然语言）+ structuredContent（给程序读的结构化值）。见 §5 真实报文。
7
写回 stdout，带上同一个 id
Client 靠 id 把"回复"对上"请求"。一次调用至此往返完毕。
一句话记住这个进程：它是个常驻的、只会读写管道的循环 —— 读一行 → 看方法 → 查表 → 校验 → 执行 → 包结果 → 写一行。没有端口、没有 URL。

§4 今天最值钱的一节往 stdout 打印会不会毁掉协议？

写 server 的人一定会想在工具里 print() 调试。而"stdout 是协议通道，打印会污染协议"是一句流传很广的话。 我们把它当场验了，结论跟"流传的说法"不完全一样。

实验设计（对照法：只改一个变量）

  • A 干净版：工具内不打印。
  • B 吵闹版：与 A 逐字相同，只多一行 print("DEBUG: ...", flush=True)。
  • 若两者行为有差 → 成因只能是那一行 print。
  • 同时挂一个 stdout 监听中继（tee），把 Server 的 stdout 逐行原样抄进日志（不截断），并对每一行判一次"是不是合法 JSON"。

结果

A 干净版
initialize ✅   tools/list ✅   tools/call ✅
B 吵闹版
initialize ✅   tools/list ✅   tools/call ✅

两者都成功 —— print 没有造成任何可观测故障。协议流日志里，两个版本都只有 3 行、行行是合法 JSON， 那行 DEBUG 一行都没进协议流。它去了哪？去终端了。

追它去了哪：投三枚可区分的标记

光看"没坏"不够 —— 得知道是谁把它挡下的。于是在工具函数里用三种方式各投一枚标记：

标记投法落点（实测）
MARKER-M1-PRINTprint(...)（Python 层）终端 stderr，协议流里无
MARKER-M2-SYS-STDOUTsys.stdout.write(...)（Python 层，绕过 print 包装）终端 stderr，协议流里无
MARKER-M3-OS-WRITE-FD1os.write(1, ...)（fd 层，直接写描述符 1）终端 stderr，协议流里无

连 fd 层直写都被改道了 —— 这说明不是 Python 层的包装在挡，而是fd 本身被换了指向。同一时刻量到的 fd 事实：

{
  "fd1_ino": 845803477511856773,
  "fd2_ino": 845803477511856773,      ← 与 fd1 完全相同
  "fd1_mode": "0o10660",
  "fd2_mode": "0o10660",
  "fd1_same_as_fd2": true
}
判决：MCPServer.run() 在启动时把 fd 1 改道到了 fd 2（两者指向同一个对象）。 → 用户代码里写到 stdout 的任何东西，实际都流向了 stderr，因此落不到协议通道上。

但别急着记成"随便打印没事" —— 三条边界

#要点
1这是 SDK 的保护，不是协议的许可。协议的规定是"stdio 通道上只能有协议消息"。 换一个 SDK、换一个语言实现、或自己手写 stdio server，就没有这层保护 —— 那时 print 真的会毁掉会话。
2"没坏"属于"没测出坏"，不等于"设计上安全"。本实验只覆盖了 mcp 2.2.0 + MCPServer + 工具函数内打印这一种情形， 并且在 Client 端做的是高层调用（ClientSession）。更底层或别的实现下会不会坏，本次没测。
3副作用仍在：调试输出会混进 stderr。因为 fd1 与 fd2 已合流， Server 的 stderr 现在是"业务噪音 + 真正的错误日志"混在一起 —— 排查问题时要能区分，别把调试文本当成故障。
这条为什么值得单独讲？ 因为它是一个"差点被当成常识直接讲出去"的例子。我原本准备的说法是"print 会污染协议"——听起来完全合理、人人都这么说。 跑完发现：在当前 SDK 下它被主动挡住了。
→ 规矩：凡"会导致 X 故障"这类断言，先问"我在这个版本上真见过它发生吗"。没见过的，就写成"风险存在，但当前实现有防护"， 而不是当成结论复述。转述一个未经自己验证的故障，比不转述更危险 —— 它带着别人的权威感。

§5 装饰器替你做了哪些事（真实报文，一字未改）

下面这段是 §4 实验里 B 吵闹版的 tools/list 原始响应（从协议流日志里逐字复制）：

{"jsonrpc":"2.0","id":2,"result":{"tools":[
  {
    "name":"echo",
    "description":"原样回显传入的文本。",
    "inputSchema":{
      "properties":{"text":{"title":"Text","type":"string"}},
      "required":["text"], "type":"object", "title":"echoArguments"
    },
    "outputSchema":{
      "properties":{"result":{"title":"Result","type":"string"}},
      "required":["result"], "type":"object", "title":"echoOutput"
    }
  }
]}}

而工具函数只写了这样几行 —— 上面那一大坨全是自动生成的：

@server.tool()
def echo(text: str) -> str:
    """原样回显传入的文本。"""
    return f"echo:{text}"
报文里的字段它从哪来
name: "echo"函数名
description函数的第一行 docstring —— 模型靠这句判断"什么时候该用它"
inputSchema参数签名 + 类型标注。text: str → {"type":"string"}； 带默认值的参数会变成 anyOf:[..., null]
outputSchema返回类型标注。-> str → {"result": {"type":"string"}}
title: "echoArguments"工具名 + Arguments / Output 自动拼接（注意：是直接拼接，不是转驼峰）

调用一次 tools/call 后，返回也是双层的（同样是原始报文，逐字复制）：

{"jsonrpc":"2.0","id":3,"result":{
  "content":[{"text":"echo:hi","type":"text"}],     ← 给模型读的自然语言
  "structuredContent":{"result":"echo:hi"},          ← 给程序读的结构化值
  "isError":false
}}
函数只 return "echo:hi" 了一个字符串，SDK 自动把它包成 content（文本块）与 structuredContent: {"result": ...} 两份 —— 这正是 D25 说的"工具返回值是双层的"在服务端的落地形态。

顺带一条：initialize 的响应里能看到 Server 自报的三样

{"result":{
  "protocolVersion":"2025-11-25",                    ← 谈定的协议版本
  "capabilities":{
    "tools":{"listChanged":false},                   ← 我提供工具
    "resources":{"listChanged":false,"subscribe":false},  ← 我提供资源（D25 讲的三原语之一）
    "prompts":{"listChanged":false}                  ← 我提供提示模板
  },
  "serverInfo":{"name":"noisy","version":""}
}}

这段报文本身就是"D25 说的三原语（Tools / Resources / Prompts）"在服务端的真实样子： Server 在握手时把"我会这三样里的哪些、会不会主动通知变更"报给 Client。 本项目只用 Tools，所以三样里只有它是我们真正在用的。

关于 isError（D25 已测，这里补一句服务端视角）： 参数校验失败、工具名不存在 —— 这两种错都不抛异常，而是装在一条正常的 result 里、把 isError 置为 true 返回。 这是有意的设计：错误要能被模型看见，模型才有机会自己修正参数重试一次。 所以 Client 端的 call_tool 不抛异常 —— 判断成功与否要看返回对象的 is_error 字段， 不能用 try/except 包着调用就当验过了。

§6 验收项「服务独立可调」到底在验什么

PRD 给 D26 的验收是四个字，容易看轻它。它的真实含义是：

「独立」指怎么证
不依赖 Agent —— 不需要 LLM 决定调不调它 拿一个最简客户端直接连上去，跑通三件事：
initialize 握手 → tools/list 拿到工具清单 → tools/call 真的取回数据。
（Client 里不出现任何"库存"业务逻辑，也不出现 LLM）
不依赖 FastAPI —— 不需要先启动本项目后端
不依赖数据库 —— 数据是进程内的 mock
为什么这条验收值得认真做？因为它是"解耦"这个词的可运行证据。 "我的工具是个 MCP Server"这句话，如果不能撇开 Agent 单独跑起来，那就只是一句说法 —— 它仍然只是 Agent 代码里的一个普通函数，套了个 MCP 的壳。

反过来说：能被别人独立调用 = 它是真 Server。这正是 D25 那条判据（"需要被启动吗？被连接吗？被问『你有什么』吗？"）在 D26 的落地检验。
