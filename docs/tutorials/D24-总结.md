## §2 核心概念讲解

### 2.1 先定位：报告在评测体系里的位置

本项目的评测是**三层**的，每层的"量具"不同：

| 层 | 量什么 | 要花钱吗 | 当日工具 |
|---|---|---|---|
| **检索层** | 有没有把正确的文档捞进 top-k | ❌ 零 token（纯 SQL + 本地嵌入） | `d23_retrieval_metrics.py` |
| **生成层** | 把捞到的材料组织成答案的能力 | ✅ 调 LLM | `d22_run.py`（`generation_runs` 控制） |
| **裁判层** | 答案对不对（LLM-as-judge 打分） | ✅ 调 LLM | `judge_service`（`runs_per_case` 控制） |

> **LLM-as-judge**（大模型当裁判）：用一个大模型按 rubric（评分细则）给答案打分，代替人工评分。
> 它解决"人评 50 条题太累、且每次标准不一样"的问题；代价是它自己也会抖，所以要**先校准它**（D20 的 ε）。

**报告生成在这三层之外，属于"呈现层"** —— 它的输入是已经落库的 `eval_case_results` 明细，
输出是一份 Markdown。**它一个 token 都不花，也一个数字都不产生。**

> ⚠ 这句话是设计约束，不是修辞：**报告里的每个数都必须能在库里找到出处**。
> 一旦报告自己"算"了一个新指标（比如自己定义个"综合得分"），
> 它就变成了**第二个真相来源**，与库里的口径迟早对不上（这就是 D23 花两轮修掉的「双权威」病）。

### 2.2 PRD §9.5 规定的报告结构，以及它为什么是这个顺序

```
总体对比表 → 每类明细 → 失败案例（各取 3 条）→ 结论与建议
```

这个顺序是**由粗到细再回到总**，每一步回答一个不同的问题：

| 段 | 回答的问题 | 读者拿到它之后会问的下一个问题 |
|---|---|---|
| §1 总体对比表 | 三个配置**总的来说**谁好？ | "好在哪些类问题上？" |
| §2 每类明细 | 差异**集中在哪一类**？ | "具体是哪几条错了？为什么错？" |
| §3 失败案例 | 错**长什么样**？ | "那我该怎么办？" |
| §4 结论与建议 | 该怎么办？ | （回到 §1 复核） |

> 这三跳与 D36 的「Agentic BI 下钻链」是同一套思路：
> **汇总分不可下钻就等于没有解释力**。这也是 PRD v4.1 专门补 `eval_case_results`
> 明细表的原因 —— 没有它，"每类明细"和"失败案例"**这两段都产不出来**。

### 2.3 两个口径：按题 vs 按行（**报告里最容易骗人的地方**）

同一个 run，准确率有两个完全不同的算法：

| 口径 | 分母 | 算法 | 它回答的问题 |
|---|---|---|---|
| **准确率（按题）** | **题数** | 每条题先在自己的多次生成里**多数投票**，再算通过题数 / 总题数 | "这批题答对了多少" |
| **三维度均分（按行）** | **有分数的明细行数** | 每次生成的答案各算一份，求平均 | "产出的平均质量" |

> **多数投票**：同一条题生成 3 次，有 2 次判"通过"就算通过。它解决的是"单次生成可能是运气"。
> 平局（3 次里 1 过 1 不过 1 缺）记为**不通过** —— 把平局算通过等于**往有利方向兜底**。

**为什么必须分开说**：PRD S2 验收点是「混合+重排 vs 纯向量 **≥ +10%**」，
这个 +10% 说的是**题目**的百分比（50 条题里多对 5 条）。
若拿"按行"的均分去对"按题"的门槛，结论会不可解释。

本次报告里的真实数字：

```
准确率     98.00%  = 49/50 题      ← 分母是「题」
正确性均分  4.925   = 分母是 40 行  ← 不是 50！
```

**那 10 行去哪了？** 工具类题（`expected_tool` 非空）**不判内容**：
D23 定了"这一类只判有没有调用正确的工具"，所以它们的三列 `score_*` 是 **NULL**、不参与求平均。

> ⚠ **这是本项目第 4 次踩同一个族系的坑**（D20「分母悄悄变小」→ D21「把判定次数读成题数」→
> D23「工具题豁免后分母变了」→ 本次）。**修法**：把分母变成一个**可引用的字段**
> （`scored_rows`），让报告里"40（共 50 行）"两个数都印出来。
> 只印一个数的时候，读者永远不知道它是哪一个。

### 2.4 可比性守卫：为什么必须是**异常**，不是警告

报告的**全部意义**是"同一份考卷、同一份教材，只换检索配置，分数怎么变"。所以三个 run 必须：

| # | 条件 | 不满足意味着 | 报告会怎么错 |
|---|---|---|---|
| ① | 配置齐全（恰好 3 个） | 对比表缺列 | 读者以为只跑了两个配置 |
| ② | `dataset_fingerprint` 逐字相同 | 换过题 | 分数差里混进"题目变了" |
| ③ | `corpus_fingerprint` 逐字相同 | 换过语料 | 同上 |
| ④ | 题号集合完全相同 | 用过 `--limit` / `--category` | **分母不同，百分比不可比** |

> **指纹**：把一组内容（题目 + 语料切片）按稳定规则算出的哈希值。
> 它解决的问题是"我怎么证明考卷没被人偷偷改过" —— 改一个字，指纹就变。
> 本项目有两张网：`dataset_fingerprint`（考卷）与 `corpus_fingerprint`（教材），D22 补上后者。

**为什么不是打一行警告**：这类错误**没有任何症状** —— 表格照排、百分比照算、脚本正常退出。
唯一能发现它的方式是**主动去比**。而"打一行警告"在实践中的结局是两种：
**没人看**，或者**被当成噪音后关掉**。

D23 就踩过一次真实的：当时拿 run 1 与 run 4/5/6 做对照，
而 run 1 **只跑了 C01~C04（8 行）**、run 4/5/6 跑了全部 10 条 C 类题 ——
**两次覆盖的题目集合不同**，那个"前后对比"没有任何含义。

→ 所以这里**抛 `ReportGuardError`**，而且**抛它自己的类型**：
调用方要能区分"数据不可比（该去查数据）"与"程序出错（该去查代码）"。
包装成 `RuntimeError` 等于**把可判断的信息变成不可判断**（铁律 12 附则三）。

### 2.5 抖动三层，以及本日最核心的发现：**答案指纹**

> **抖动**：同样的输入跑两次，结果不一样。它不是 bug，是 LLM 的固有属性。

D22 把抖动分成三层，**三层应对方式完全不同**：

| 层 | 本质 | 怎么应对 |
|---|---|---|
| ① **裁判侧** | 重复测量**同一个值**（答案被钉住） | 多数投票 / 置信区间 —— **有效** |
| ② **生成侧** | 给**随机变量**抽样（每次答案都不同） | 只能重复生成，投票**无效** |
| ③ **不是抖动** | 输入被换过（语料/题/配置） | **指纹前置拦截** —— 不做统计 |

一句话自检：**"我重复的是裁判，还是输入？"**

**本日发现的坑，是第 ② 层伪装成了"配置差异"**：

报告里本来会出现这样两行（直接抄库里的 `failure_reason`）：

```
- pure_vector    ：wrong_answer 1 条
- hybrid         ：wrong_answer 1 条
- hybrid_rerank  ：incomplete   1 条
```

读者会自然地读成「**配置不同 → 失败模式不同**」。**这是错的。**

回库把三份答案取出来比指纹后发现：

| 配置 | 答案 sha256（前 12 位） | 字数 | 归因 |
|---|---|---|---|
| `pure_vector` | `32d4d63c0783` | 651 | `wrong_answer` |
| `hybrid` | `448154b3f899` | 484 | `wrong_answer` |
| `hybrid_rerank` | `5c0405241aa9` | 529 | `incomplete` |

**三份答案逐字不同**，连开头都在第 4 个字就分岔（「根据公司**制度**」vs「根据公司**规定**」）。
也就是说：**三个配置拿到的是三次不同的生成结果**，那个"归因差异"来自**生成侧抖动**，
与检索配置无关。

> **`sha256`**（安全散列算法）：把任意长度的内容压成一个固定长度的"指纹"。
> 内容改一个字，指纹就完全不同 → 用它判"两份答案是不是同一份"。
> ⚠ **不能用"字数相同"代替**：字数相同而内容不同的答案在 LLM 输出里极常见，
> 而这两件事的后果完全不同。

**修法**：报告里新增 §4.3，把"同一条题在多个配置下都失败"的情形挑出来，
**显式比较答案指纹**，并给出结论分支：

- 指纹**相同** → 同一份答案被重复测量，归因差异来自**裁判侧**，可用投票降噪
- 指纹**不同** → **生成侧抖动**，该题的失败**不能归因于检索配置**

**这一段的形态最值得记住**：它**看起来完全正常** —— 表里有数据、归因字段有值、百分比算得对，
而且它**恰好出现在最容易被引用的一格**（失败模式分布）。
唯一能发现它的动作是**把被比较的两个答案取出来比指纹**，而不是读判定结果。

### 2.6 为什么"失败案例各取 3 条"会取不满

PRD 要求"失败案例各取 3 条"。本次实测：

- 50 题 × 3 配置 = 150 条判定，**只失败 3 条**（而且是**同 1 道题 B01** 在三个配置下各失败一次）
- 所以每个配置只能取到 **1 条**

**取不到 3 条不是一个要遮掩的缺陷，它本身就是结论** ——
它直接证明"这批评测集对当前系统的难度过低"。

→ 报告里的写法是 **`⚠ 该配置共失败 1 条，不足 3 条，以下是全部。`**
关键是把两件事**在文字上分开**：**"只有 N 条"** 与 **"截断到 N 条"**。

> 同族的表述纪律：摘要里报的是"**3 条判定失败，涉及 1 道题**"——
> "3 条"与"3 道"是两个数。D21 正是把"45 次判定"读成了"45 条题"，
> 结论方向没错，但**证据基础被夸大了 5 倍**。

## §3 代码逐行解读

### 3.1 `app/services/eval_report_service.py`（约 790 行）

#### ① 模块级常量：为什么这些字符串要抽出来

```python
REQUIRED_SECTIONS: tuple[str, ...] = (
    "## 1. 总体对比表",
    "## 2. 每类明细",
    "## 3. 失败案例",
    "## 4. 结论与建议",
)
FAILURE_CASES_PER_CONFIG = 3
S2_MIN_GAIN_PP = 10.0
PASS_THRESHOLD = 4.0
```

- `REQUIRED_SECTIONS` 是 PRD §9.5 的四个必需章节。**验证脚本按它逐节检查** ——
  所以这些标题字符串**只能在这里出现一次**。若在 `render_report` 里再手写一遍，
  两处就会各自演化，验证脚本检查的不再是报告真正用的那组标题（**双权威**）。
- `FAILURE_CASES_PER_CONFIG = 3`：报告正文里有句"不足 3 条"。
  那个"3"若写成字面量，改取数逻辑时**正文不会跟着变**。
- `PASS_THRESHOLD = 4.0`：PRD F7.5 的"正确性 ≥4/5 记为对"。**它决定报告里所有数字的含义**，
  所以必须印在报告里（附录 A）—— 读者不知道门槛就无法解释得分。
- `S2_MIN_GAIN_PP`：PRD S2 的 +10%，**它决定"是否达标"那一句的判定**。

#### ② `ReportGuardError`：一个专门的异常类型

```python
class ReportGuardError(RuntimeError):
    """数据不满足"可比"的前提（指纹不一致 / 题号集合不同 / 配置不全）。"""
```

继承 `RuntimeError` 而不是 `Exception`：语义上它属于"调用方用错了数据"。
**关键是它有独立类型** —— 见 §2.4。

#### ③ `load_latest_runs()`：取数条件必须能"随重跑自洽收缩"

```python
stmt = (
    select(EvalRun)
    .distinct(EvalRun.config_name)
    .order_by(EvalRun.config_name, EvalRun.id.desc())
)
```

`distinct on`（PostgreSQL 语法：**每个分组只保留第一行**）
配合 `order_by(..., id desc)` = **每个配置取最新那一轮**。

**为什么不用 `where generation_runs = 1`**：D23 踩过这个坑 —— 那个条件在第一轮恰好命中 3 条，
**重跑之后就变成 6 条**，把已声明作废的旧轮混进了统计，而且**不报错、不崩溃、数字看着也正常**。

本项目 `eval_runs` 里现在同时躺着：
- `run 1`：只跑了 8 行（小样本试跑）
- `run 4/5/6`：**D23 修复前**的轮次，已声明作废
- `run 9/10/11`：修复后重跑，**有效**

`distinct on` 恰好只取最后一批 —— 这是个**结构上就正确**的条件，不依赖我记得去改 WHERE。

#### ④ `check_comparable()`：五道闸门，每道对应一个具体的错误解读

```python
names = [r.config_name for r in runs]
if sorted(names) != sorted(RETRIEVER_CONFIGS):
    raise ReportGuardError(f"配置不全：拿到 {names}，期望 {sorted(RETRIEVER_CONFIGS)}。...")
```

每个 `raise` 的 message 都写清了**"不满足会导致什么"**，不是"校验失败"。
理由：这份异常会打到终端上，是排查时唯一的线索。写 `assert failed` 等于什么都没说。

```python
key_sets = {r.config_name: frozenset(...) for r in runs}
common = frozenset.intersection(*key_sets.values())
if any(s != common for s in key_sets.values()):
```

> ⚠ **这里原本写的是 `set.intersection(*key_sets.values())`，是个真 bug，见 §7 踩坑①**：
> `set.intersection` 是**未绑定方法**，descriptor 会检查第一个实参是不是 `set` 实例，
> 而 **frozenset 不是 set 的子类** → `TypeError`。必须写 `frozenset.intersection`。

#### ⑤ `summarize_results` 复用而不是重算

```python
from app.services.eval_service import _field, summarize_results
```

**准确率的定义只有一处**（在 `eval_service.summarize_results` 里），报告只调用它。
这是"一个判断只能有一个出处"的直接应用：
若这里再写一遍"通过题数 / 总题数"，将来那个函数改了（比如平局规则从"不过"改成"过"），
**报告不会跟着变**，而两处都"有来源"—— 这是最难发现的一类不一致。

`_field(row, key)` 是个小工具，同时支持 **dict** 与 **ORM 对象**：

```python
return row.get(key, default) if isinstance(row, dict) else getattr(row, key, default)
```

为什么要两者都支持：同一个汇总函数被用在两处 —— runner 跑完当场算（手里是 dict）、
API 读历史运行重算（手里是 ORM 对象）。**两处必须给出同一个结果**。

#### ⑥ `mean_scores()`：把分母变成一个**可引用的字段**

```python
summary = summarize_results(rows)
return {
    ...
    "scored_rows": summary["scored_rows"],   # ← 真实分母
    "total_rows": summary["total_rows"],     # ← 总行数（不是分母）
}
```

两个都返回，报告里写成 `40（共 50 行）`。**只返回一个的时候，读者永远不知道它是哪一个。**

#### ⑦ `group_by_category()`：为什么不用现成的 SQL 聚合

代码库里已经有 `eval_service.aggregate_by_category(run_id)`，但报告**没用它**：

```python
"""
⚠ 为什么不直接用 eval_service.aggregate_by_category：那是 SQL 侧的行级聚合，
  它给的是"哪一类平均分更差"；报告要的是"哪一类通过率更低"，
  两者的 passed 口径不同（行级 vs 题级）。同一张表里混两种口径，
  读者会拿行级通过数去对题级通过率 —— 这是 D20「两个口径不能互相印证」的翻版。
"""
```

→ 报告内部**统一走题级**，需要行级明细时另开一列并标名。

#### ⑧ `answer_signature()` 与 `cross_config_failure_view()`（本日新增的核心）

```python
def answer_signature(text) -> str:
    return hashlib.sha256(str(text or "").encode("utf-8")).hexdigest()[:8]
```

取前 8 位十六进制（32 bit）足够区分"是不是同一份答案"（碰撞概率可忽略），
且比 64 位更易读。

```python
by_case.setdefault(str(_field(row, "case_key")), {})[r.config_name] = row
```

逐步看：遍历所有配置的失败行 → 按题号归组 → 每个题号下记"哪个配置失败了、失败的那行长什么样"。

```python
sigs = {cfg: answer_signature(_field(row, "answer")) for cfg, row in per_config.items()}
out.append({
    "same_answer": len(set(sigs.values())) == 1,
    ...
})
```

`len(set(...)) == 1` 就是"所有配置的答案指纹都一样" → `same_answer=True`。
这一个布尔值决定了报告里走哪个结论分支（§2.5 那两条）。

#### ⑨ `failing_rows()`：同时返回"取到的"和"总数"

```python
def failing_rows(rows: list, limit: int) -> tuple[list, int]:
    fails = [x for x in rows if not bool(_field(x, "passed"))]
    return fails[:limit], len(fails)
```

**为什么返回两个值**：若只返回列表，报告写成"失败案例（各取 3 条）"下面只挂 1 条，
**读者无从判断是"只有 1 条"还是"被截断了"**。

#### ⑩ `_cell()`：`None` 不能渲染成 `0`

```python
def _cell(value, ndigits: int = 3) -> str:
    if value is None:
        return "—"
```

工具类题的 `score_*` 是 NULL。**渲染成 `0.000` 会让人得出"工具类题的答案质量是 0 分"
这个完全错误的结论** —— 实际是"这一类不按这三个维度评价"。
用 `—` 让"不适用"与"得了 0 分"在视觉上分开。

#### ⑪ `_table()`：必须转义单元格里的 `|`

```python
def esc(c):
    return str(c).replace("|", "\\|").replace("\n", " ")
```

答案文本、judge 理由里常常带 `|` 或换行。**不转义的话表格会被从中间截断**，
而且是**静默**的（Markdown 照样渲染，只是少了半张表）。

#### ⑫ `render_report()`：纯函数 + 结论全部分支

```python
def render_report(runs, rows_by_run, *, generated_at=None) -> str:
    """
    ⚠ `generated_at` 显式传入而不是内部 `now()`：
      否则同一个函数两次调用会给出不同的文本，验证脚本无法断言"确定性"。
    """
```

**把时间作为参数注入**，换来一条可断言的性质：**同一输入两次渲染逐字相同**。
这是验证脚本 A1 那条断言的基础。

结论段的分支（**没有一句硬编码的判定**）：

```python
identical = len({round(summaries[r.id]["accuracy"], 6) for r in ordered}) == 1
...
    if identical:
        ...  "本轮消融**未测出配置差异**"
        ...  "**未达标**"
        out.append("⚠ **这个 0 差异不能解读为「重排无用 / 混合检索无用」**，理由有三条...")

```

> 自检口诀：**指着每个结论里的数字问"这个数是哪个变量算出来的"**，答不上来就是硬编码。

#### ⑬ `attach_report_path()`：返回值是"更新了几行"

|---|---|---|

**① `check()` 不用 `assert`**

```python
def check(label: str, cond: bool, detail: str = "") -> None:
    global PASS, FAIL
    ...
```

用 `assert` 会在第一条失败时中断，**后面的断言一条都不跑**。
用计数式出口，则"**全部断言都跑完再给汇总结论**"——
排查时最怕的就是"修了一个又冒出三个"。

**② B 段为什么必须是负面测试**

守卫最容易写成"看着像检查、实际永远通过"：条件写反、或异常被上层 `except Exception` 吞掉。
所以 B 段**主动制造六种坏数据**，断言每一种都抛 `ReportGuardError`：

```python
def expect_reject(label, rs_, rw_):
    try:
        rs.check_comparable(rs_, rw_)
    except rs.ReportGuardError as e:
        check(label, True, f"→ 已拒绝：{str(e)[:52]}…")
        return
    check(label, False, "→ ❌ 没拒绝（守卫失效，后面的绿灯都不可信）")
```

而且 B 段**第一条是 `B0`：正常数据必须先通过**——
否则后面的"拒绝"可能只是因为那份数据本来就不过（**假通过**）。

**③ C 段为什么要用"另一条独立 SQL"**

```sql
with per_case as (
    select case_key, count(*) n, count(*) filter (where passed) ok
    from eval_case_results where run_id = :rid group by case_key
)
select count(*) filter (where ok * 2 > n) from per_case
```

这是在 SQL 里**重新实现了一遍题级多数投票**，不复用 `summarize_results`。
若复用，那它只能证明"函数调了两次结果一样"，**证明不了报告里的数是对的** ——
分母口径写错时两边会一起错。

**④ F 段为什么必须**双向**断言**

```python
check("F2b 答案相同时**不出现**「逐字不同」的结论（否则就是看到了不存在的事实）",
      "逐字不同" not in md_same)
check("F3b 答案不同时明确写出「不能归因于检索配置」", "不能归因于检索配置" in md_diff)
```

只测一个方向（"答案不同 → 说要归因抖动"）的话，另一半永远为真 = **假通过**。
构造两份假数据（一份答案相同、一份不同），**两个方向都要对**。

## §5 面试考点

**Q1：你的评测报告是怎么生成出来的？**
> 三层解耦：评测跑完把**逐条明细**写进 `eval_case_results`（这一层是 D22 建的），
> 报告生成是**独立的呈现层** —— 它只读明细、零 LLM 调用、零 token，
> 所以报告可以随时重新生成，且**报告里的每个数都能在库里找到出处**。
> 报告结构按需求文档固定四段：总体对比表 → 每类明细 → 失败案例 → 结论与建议。

**Q2：消融实验的结果是什么？**
> **没有测出差异** —— 三个配置在 50 条题上都是 98%（49/50），
> 需求文档要求的"混合+重排 vs 纯向量 ≥ +10%"**未达标**。
> 但我做了**归因**，而不是含糊过去（三条证据）：
> ① 检索层指标全部撞天花板（`Hit@1/5/10` 全 100%、`MRR` 恒 1.000、35 题的首篇正确文档都排第 1）；
> ② 题目本身区分能力不足（每个主题语料里只有一篇文档）；
> ③ 量具没坏（随机基线只有 4.5%~9.4%，且 33 条验证断言全绿）。
> 结论是"**在当前这份评测集上三配置不可区分，瓶颈是任务难度**"，
> 并给出了可量化的改进判据（让 gold 文档的融合名次落进 6~20 区间，实测当前 0/35）。

**Q3：报告里最容易出错的地方是什么？**
> 两处，都是"不报错"的：① **分母**——工具类题不判内容、分数是 NULL，
> 所以三维度均分的真实分母是 40 行而不是 50 行，我把两个数都印出来；
> ② **把生成侧抖动当成配置差异**——我实测发现唯一那条失败题在三个配置下的答案**逐字不同**
> （sha256 各异），所以"归因不同"根本不能归因于配置。
> 我为这一条专门在报告里加了答案指纹对比段。

**Q4：怎么保证报告没写错？**
> 报告不自我声称可信，有**独立验证脚本 60 条断言**，分六段：
> 纯函数确定性 / 守卫负面测试 / **数字与另一条独立 SQL 交叉核对** /
> 失败案例规则 / 落盘回写 / 答案一致性双向。
> 最关键的是 B 段和 C 段：B 段**故意做坏数据**验证守卫真会拒绝（不做这个，
> 守卫可能永远通过而我不知道）；C 段用**独立实现**重算一遍，避免"两边一起错"。

**Q5（追问）：为什么不直接把评测结果打印出来？**
> 因为报告要能**被仲裁**。打印是一次性的，报告是**可复现的交付物**：
> 它带 run_id、评测集与语料指纹、judge 与次数，
> 别人可以拿这些信息把同一个结论重跑一遍；路径还会回写进 `eval_runs.report_path`，
> 从数据库就能找到"这一轮的报告在哪"。

## §7 踩坑记录

### ① `set.intersection(*frozensets)` → `TypeError`（**最值得记的一个**）

```python
# ❌ 原写法
only = {k: sorted(v - set.intersection(*key_sets.values())) for k, v in ...}
# TypeError: descriptor 'intersection' for 'set' objects doesn't apply to a 'frozenset' object
```

**原因**：`set.intersection` 是**未绑定方法**，作为 descriptor 会检查第一个实参是否为 `set` 实例，
而 `frozenset` **不是** `set` 的子类（两者是平级的）。

**为什么它特别危险**：这一行**只在"题号集合确实不同"时才会执行**
（集合相同就短路进不了这个分支）。也就是说 ——
**它恰好在最需要守卫的那一刻才崩**：本该"拒绝出报告"，结果程序 TypeError 崩了。

**是负面测试 B3 把它打出来的**。正面路径永远碰不到这一行。
→ 这正是"必须做负面测试"最有力的例证：**守卫的代码路径，正常数据永远不会走。**

### ② 中文串里混进 ASCII 双引号（本轮又犯）

```python
# ❌
out.append(f"> ⚠ ...这不是"报告写少了"，")
# ✅
out.append(f"> ⚠ ...这不是「报告写少了」，")
```

f-string 内层用 ASCII 双引号会直接 `SyntaxError`（3.12 之前）。
**修正动作**：写完立刻 `ast.parse` 复查 —— 本轮就是靠它当场抓到的。

### ③ 死代码 + 撒谎的注释

初版里有两处：
```python
out.append(_table(...) if False else "")     # 死代码，只为占一行
def _cell(value, ...):
    """表格单元格：None 显示为 `—` 并加脚注标记"""   # ← 实际没加脚注
```

**注释描述了一个不存在的实现**，比没有注释更糟 —— 它让后来的人以为已经做了。
→ 修正：死代码删掉、注释改成与实现一致（并说明**为什么**用 `—`）。

### ④ 把"生成侧抖动"当成"配置差异"（本日最有价值的发现）

如 §2.5 所述：报告初稿会把三配置的 `failure_reason` 并列，
读者会读成"配置不同 → 失败模式不同"，而真相是**同一条题的三次生成本身不同**。

**这个错不是靠"把断言写得更严"发现的** —— 它属于铁律 12 附则「**覆盖面型静默失效**」：
原来的断言全绿，因为**没有任何一条断言在检查"被比较的两个东西是不是同一个"**。
→ 修法是**新增一个维度**（答案指纹），而不是收紧原有断言。

### ⑤ 数据源与规划不一致（**遗留问题**）

报告用的 run 9/10/11 是 `generation_runs = 1`（修复后的**诊断轮**）。
而评测总纲 §3 第 ③ 项规划的是 **D23 正式消融 = `generation_runs = 3`** ——
**那一轮至今没跑**。

影响：`generation_runs=1` 时同一条题只生成一次，**生成侧抖动无法被多数投票吸收**，
这正是 §2.5 那个发现能出现的原因。
报告里已**如实标注**了"每条题生成 1 次"与"该指标需多次生成才有意义"。

→ **待办**：跑 D23 正式消融（3 配置 × 50 题 × `generation_runs=3`，预计 45~80 分钟）
后再重生成报告。**结论预期不变**（检索层已 100%，三配置拿到的检索结果相同），
但报告的严谨性会提高。

直到今天做全量回归才暴露。这是「**验证脚本自身陈旧**」，不是代码退化 ——
两者在日志里长得一模一样（都是一条 FAIL），**必须靠 git 历史区分**。

病根是**硬编码总列数**：它把断言拍成了一张一次性快照，而 schema 是会**合法增长**的。
改成两条，各守一件事：

  这才是我当时真正想守的东西 —— 没人偷偷删列 / 改名 / 换语义。
- **A8b**（总数，13）：仍然冻住总数，但**故意**让它将来会红。

> **这里的取舍值得说清**：A8b 明知会被未来的扩表打红，为什么还留?
> 因为「打红」在这里是**功能**不是**缺陷** —— 它强迫下次扩表的人来这一行
> 显式确认"我确实改了 schema"，而不是让一个陈旧断言在无人察觉中一直红下去
> （D22 到 D24 之间发生的正是后者）。
> 反过来说，如果当初只写 A8b 不写 A8，那"有人删了 `score_faithfulness`"
> 和"有人加了 `report_path`"会被报成**同一种红**，反而更难查。

修完 `d21_eval_verify` 变成 **63/63**（62 + 新增 A8b）。

**推广规则**：凡是断言「结构恰好长这样」，都要拆成
「**旧有的东西还在吗**（子集，永久有效）」+「**总数变了没有**（等值，故意易红）」两条。
只写后者 = 断言会随合法变更失真；只写前者 = 删列改名查得出、但悄悄多出一列查不出。
