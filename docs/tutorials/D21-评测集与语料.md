## §2 核心概念讲解

### 2.1 「先立语料、再出题」—— 一条不可逆的顺序

**问题**：D22 要跑消融实验（ablation，即"把某个组件拆掉，看分数掉多少"），
需要 50 道有标准答案的题。这 50 道题从哪来？

**直觉做法（错的）**：先想 50 个"看起来像样的业务问题"，比如
"员工年假有几天？""出差住宿费报销多少？"，然后去找语料。

**为什么错**：想出来的问题会**带着脑子里默认的数字**。
比如你写参考答案"年休假 5 天"，但入库那份语料里写的是"7 天"——
这题**永远答不对，而且不会报任何错**。它在 D23 的报告里只会表现成
"某个配置特别差"，你会去怀疑重排、怀疑融合、怀疑 prompt，就是不会怀疑题目本身。

**正确顺序**：

```
① 先立语料（真实尺寸的中文文档入库、切好片）
        ↓   ← 题只有在语料已经躺在库里时，才"有依据可查"
② 再从语料里挑事实出题（参考答案逐字对标原文）
        ↓
③ 落库 + 算指纹（写完即冻结）
```

**判据一句话**：**每一道题的正确答案，必须能在语料里指出它出自哪一段。**
指不出来，这题就是"幻觉的标尺"——它会把 judge 的分数带偏，而你不会知道。

→ 落到代码：`scripts/d21_corpus.py` 先定义 8 篇文档，
`scripts/d21_cases.py` 里每条题的 `evidence` 字段写的就是"原文里那句话"，
而 `scripts/d21_eval_verify.py` 的 **D 段（依据机检）**会拿这句话回去搜语料，搜不到就报错。

### 2.2 评测集的三类题

`category` 有三档，不是随便分的，它们**测的是系统的三种不同能力**：

| category | 中文 | 测什么 | 数量 |
|---|---|---|---|
| `doc_qa` | 单文档问答 | **检索 + 抽取**：答案在一篇文档里，看能不能找对、抄准 | 30（含 5 负例）|
| `cross_doc` | 跨文档推理 | **多跳检索**：答案要**同时用两篇文档**才能拼出来 | 10 |
| `tool_call` | 工具调用 | **Agent 决策**：这题该不该调工具、调哪个 | 10 |

**为什么 B 类最难出、也最有价值**：它不是"查一段抄回来"，而是
"查 A 篇拿到一个条件，再拿这个条件去 B 篇查规则"。
比如：**年休假怎么算 → 结果影响绩效评级**，
这需要系统先检索到 `annual-leave`（年休假办法），再检索到 `performance`（绩效考核办法），
两篇的条款**串起来**才能回答。

**为什么必须有 C 类**：前两类测的都是"RAG 检索对不对"。
但一个 Agent 平台的核心差异在"**它知不知道什么时候不该检索、什么时候该调工具**"。
C 类里有题是 `expected_tool = "__none__"`——**明确要求不调用任何工具**，
测的是"乱调工具"这个失败模式。

---

### 2.3 负例（negative case）

**定义**：语料里**根本不存在答案**的题。它的**正确行为是拒答**（说"知识库里没有这方面的规定"）。

**为什么要专门设**：这是唯一能测出**幻觉**（hallucination，即模型一本正经地编造不存在的内容）的题型。
别的题答错只是"没答对"；负例题答错是**编了一段不存在的规定出来**——
在真实业务里这是能造成损失的那种错。

**为什么 `reference`（参考答案）不能留空**：
这是最容易踩的坑。有人想"既然答案是'没有'，那参考答案就写 N/A 或者留空吧"。
**不行** —— judge（评判模型）判分靠的是"拿被测答案与参考答案比"，
参考答案空着，judge 就**没有标尺**，它会怎么判完全随机。

**正确写法**：把参考答案写成一句**可判定的陈述**，例如：

> 知识库中没有关于"员工子女教育补贴"的规定，正确做法是明确告知用户无法从现有制度中找到依据。

这样 judge 就能判："被测答案说了'没有' → 对；被测答案编了补贴金额 → 错。"

→ 本项目 5 条负例的关键词在整份语料里**确实搜不到**，这一点由
`d21_eval_verify.py` 的 **D3** 断言守着（搜得到就说明它根本不是负例）。

---

### 2.4 `evidence`（判定依据）—— 让参考答案变成可机检的

**定义**：一条题"凭什么这么说"的凭据。它有三种形态，覆盖三类题：

| 形态 | 写法 | 用在 | 机检方式 |
|---|---|---|---|
| 正向原文片段 | 直接抄原文一句 | A 类（除负例） | 回语料里搜，必须逐字命中 |
| 跨文档 | `片段一 \| 片段二` | B 类 | 第 i 段必须落在第 i 个 `doc_slug` 里 |
| 负例 | `[不存在] 关键词` | A 类负例 | 关键词在**整份语料**里搜不到 |
| 工具 | `[工具] 工具名` | C 类 | 工具名必须等于 `expected_tool` |

**为什么需要它**：没有 `evidence`，"参考答案是不是编的"只能靠人肉复查 50 条——
而人肉复查的失败模式是"我第一次写的时候是核对过的"，之后每次改题都不一定再核。

**`evidence` 让这件事变成一个断言**。本项目里这条断言第一次跑就抓到了一个真实错误（见 §7 踩坑①）。

---

### 2.5 内容指纹（content fingerprint）—— 解决"偷偷改题再重跑"

**定义**：把评测集的全部内容**归一化**成一串字节，再算 **sha256** 哈希
（sha256 = 一种单向摘要算法，输入任何长度的内容，输出固定 64 个十六进制字符；
内容改一个字符，输出就完全不同，且无法从输出反推输入）。这串值就是"指纹"。

**它解决的具体危害**（这不是理论风险，是几乎一定会发生的行为）：

```
跑完评测 → 看一眼哪条挂了 → 顺手把 prompt 改一改（或者把那条题改简单点）
        → 重跑 → 分数涨了 → 以为效果提升了
```

**实际发生的是"把评测集背下来了"** —— 这叫**数据泄漏 / 过拟合评测集**
（overfitting，即针对具体题目做优化，而不是真的提升了能力）。
口头约定"我们不改题"**无法证明**这件事没发生；指纹可以。

**本项目怎么用**：
- 出题脚本 `d21_cases.py` 里算出**源文件指纹**
- 落库后从数据库读回来再算一次，**两者必须相等**（`d21_seed.py` 第 [3/3] 步的硬断言）
- `/api/eval/dataset` 把指纹**暴露成一个可以外部读到的值**
- D23 的报告里写的就是这个指纹；对不上 → **那份报告作废**

→ 少了最后一步"可对照的出口"，指纹就是算了个寂寞。**光有指纹、没地方读，等于没有冻结。**

---

### 2.6 为什么 `id` / `created_at` / `doc_ids` 不进指纹 ⭐

这是今天**最容易写错、且写错了不会报错**的一处。指纹的输入必须**只包含影响判分的内容**。

| 字段 | 是否进指纹 | 理由 |
|---|---|---|
| `case_key` / `category` / `difficulty` / `is_negative` / `question` / `reference` / `evidence` / `doc_slugs` / `expected_tool` | ✅ 进 | 任何一个改了，都是**实质改题** |
| `id` | ❌ 不进 | 自增主键，重新写入就变，与内容无关 |
| `created_at` | ❌ 不进 | 写入时间，与内容无关 |
| **`doc_ids`** | ❌ **不进** | 见下 |

**`doc_ids` 为什么是关键的坑**：它是**文档的 UUID**
（UUID = 全局唯一标识符，128 位，每次重新入库都会生成新的）。

如果把它算进指纹，会发生：
1. 改了一句语料 → 重跑 `d21_seed` → 8 篇文档拿到**全新 UUID** → 指纹变
2. 明天又重建一次、题目**一个字没改** → 指纹**又变**
3. D23 报告里写着"指纹 A"，实际读出"指纹 B" → 报警
4. 于是你开始**忽略这个报警**（报警疲劳）
5. 到真正有人改题那天，报警响了你也不看了 —— **冻结机制彻底失效**

→ 所以指纹里用的是 **`doc_slugs`**（业务名：`annual-leave`、`infosec`……）。
slug 是**我们自己起的稳定名字**，重建语料它不会变。

**今天实测验证了这一点**（不是推理，是跑出来的）：
全量回归跑完后，7 个历史脚本把语料删光了；重跑 `d21_seed` 重建，
**新的 8 个 UUID 与之前完全不同，而指纹仍精确等于 `a7797b06…90afe`**。
如果 `doc_ids` 进了指纹，这里必然报"评测集被改过"的假警。

### 2.7 `case_key` vs 自增 `id`：为什么两个都要

`id` 是 `BIGSERIAL`（数据库自增整数），`case_key` 是 `A01` / `B07` / `C10` 这样的**业务键**。

**为什么报告、命令行、失败定位都用 `case_key` 而不是 id**：
`id` 每次重建都会变（清空重写 → 从 1 重新开始）。如果报告里写"第 5 条题挂了"，
下次重建后"第 5 条"可能就是完全另一道题。

→ **需要的是"不随重建变化的名字"**。`case_key` 是我们手工指定且唯一的（数据库上有 `UNIQUE` 约束守着）。

**顺带一个反向取舍**：`documents` 表用的是 UUID（防枚举），`eval_cases` 用的是自增整数。
**这不是前后不一致**：自增 ID 的风险是"可枚举、泄露总量"，那是**面向用户的数据**才需要防的；
评测集是内部研发资料，而报告/命令行里要大量写"第几条题"——**可读性优先**。

---

### 2.8 `__none__` 哨兵：为什么不复用 `NULL`

C 类题里"**明确要求不调用任何工具**"这一种，`expected_tool` 该写什么？

**直觉做法（错的）**：写 `NULL`。
**为什么错**：`NULL` 在别处已经表示"**这个字段没填**"（A/B 类题根本不涉及工具）。
两种语义完全不同，混在一起 → "该不该调工具"变成一个**要靠 `category` 二次推断**的隐式信息。

→ 用一个**显式的哨兵值**（sentinel value，即"用一个特殊值代表某种特定含义"）：
`EXPECTED_TOOL_NOT_CALLED = "__none__"`。

**同族问题**在 D19 出现过：`similarity=None` 被当成"相关度 0"渲染出来。
**一个字段承担两种含义**是这个项目里反复出现的坑。

### 2.9 ε 的两种"0"（承接 D20）

D20 定的指标 **ε（读作 epsilon，希腊字母）＝ 单次判定不一致率**：
同一份答案重复打分，单次结论与"最终结论"（5 次多数投票）不一致的比例。

**D21 重测时，ε 还是 `0.0000`，但成因与 D20 完全不同** —— 分清这两者比数字本身重要：

| | D20 第 1 轮 | D21 重测 |
|---|---|---|
| 阈值带（correctness = 4）占比 | **0 / 50 = 空** | **5 / 50 = 10%（不空）** |
| ε | 0.0000 | 0.0000 |
| 成因 | 没有样本落在可翻转区间 → **结构性锁死为 0** | 样本**太简单**（45/50 次判定是满分 5 分）+ 打分高度自洽 |
| 修法方向 | 改 rubric + 加**难度梯度样本** | 加**更难**的样本 + 用**保守口径**报门槛 |

**阈值带**（threshold band）是什么：二值化的判定线是"correctness ≥ 4 记对"，
那么在 4 分**两侧**的区间（3.5~4.5）就是"危险区"——
**只有落在这里的样本才可能翻转**。落在 2 分或 5 分的样本离判定线太远，怎么抖都翻不过来。

**结论**：**`0.0000` 不是"非常稳定"，是"这次量具没量到东西"。**
→ 规矩：**任何点估计为 0 的比例型指标，必须同时报"分母是否有效"**（这里是阈值带条数），
并附一个**保守口径**（Wilson 置信区间上限）。
点估计给的是"看起来多稳"，上限给的是"**最坏能有多不稳**"。

本项目两轮实测：

| 口径 | 数值 | 换算成 50 条题的门槛 |
|---|---|---|
| A 点估计 | ε = 0.00% | **0.00 条 → 不可用** |
| B 保守（Wilson 上限） | ε = 7.14% | 噪声地板 6.63 条 / **单次打分门槛 11.42 条** / **3 次投票后 3.79 条** |

**对 PRD 验收线的含义**：PRD 的验收线是"+10% 相对提升"，在 50 条上 ≈ **4 条题**。
- 对**口径 A**：4 条 > 0 条门槛 → "显著"→ **这是荒谬结论**，因为门槛本身是假的
- 对**口径 B**：4 条 < 11.42 条 → **单次打分判不出**；
  但 3 次投票后门槛降到 3.79 条 → **投票后可判定**

→ 这一条**用数据证明了 D20 定的"要 3 次重复"是必要的**，不是保险起见。

### 2.10 生成侧抖动 ≫ judge 侧抖动（D21 最重要的发现）

D20 定的"3 次重复"，**重复的是 judge 打分**。D21 实测发现：

| | 第 1 次运行 | 第 2 次运行 |
|---|---|---|
| B01（跨文档题）的**系统答案** | 459 字 | 511 字 |
| judge 5 次打分 | `[4,4,4,4,4]` → **判对** | `[2,2,2,2,2]` → **判错** |

**同一条题、同一个系统、同样的配置、两次独立运行**，judge **各自内部完全一致**
（5 次全同），但**两次的判定结果相反**。

**说明了什么**：
- judge 本身**没有问题** —— 它每次都很自洽，误差不是它带来的
- 真正的抖动在**生成侧**：LLM 生成的答案**本身就是随机变量**
- **judge 重复 n 次，救不了"这次答案本来就没生成好"** ——
  因为重复测量只能压掉"同一份答案被重复测量"的噪声，
  压不掉"答案本身在变"这一层

**一句话自检**：**"我重复的是输入还是裁判？"** 两者不同，不能互相顶替。

→ D22 要做的决策：**生成要不要也重复 N 次**（成本是 N 倍）。
本日不做，只记录。

## §3 代码逐行解读

### 3.1 `app/models/eval.py`（新建，180 行）

两张表的 ORM 定义（ORM = 对象关系映射，把 Python 类映射成数据库表）。

**为什么字段比 PRD 多了五个**：PRD §10 的原始定义只有"题面 + 参考答案 + 类别"，
不足以支撑"可机检的评测集"。多出来的五个字段，每一个都对应一条纪律：

| 字段 | 类型 | 为什么需要它 |
|---|---|---|
| `case_key` | `String(16)` UNIQUE | 稳定业务键。`id` 会变，"第 5 条题"这个说法不可靠 |
| `evidence` | `Text` | 判定依据。没有它无法机检"参考答案是不是编的" |
| `doc_slugs` | `ARRAY(Text)` | 依据文档的**业务名**。指纹**只能用 slug，不能用 UUID** |
| `is_negative` | `Boolean` | 是否负例。不能靠人去读 `reference` 判断，程序必须能直接识别 |
| `difficulty` | `String(8)` | 预设难度。D22 要做**分层抽样**和"分类别出分" |

**逐行要点**：

```python
id: Mapped[int] = mapped_column(BigInteger, primary_key=True, autoincrement=True, ...)
```
`Mapped[int]` 是 SQLAlchemy 2.0 的类型标注写法，**不只是给编辑器看的**——
SQLAlchemy 会读它来决定列类型（TS 类比：有点像 TypeORM 的 `@Column()` 装饰器 + 类型标注，
但 Python 这边注解**真的参与运行时**）。

```python
case_key: Mapped[str] = mapped_column(String(16), unique=True, index=True, ...)
```
`unique=True` 落到数据库上就是 **UNIQUE 约束**（不是应用层的 if 判断）。
区别很重要：约束是**数据库强制**的，任何写入路径都绕不过去；
应用层判断只要有一条路径忘了写，重复数据就进去了。

```python
doc_ids: Mapped[list[uuid.UUID] | None] = mapped_column(ARRAY(Uuid), nullable=True, ...)
doc_slugs: Mapped[list[str]] = mapped_column(ARRAY(Text), server_default="{}", ...)
```
`ARRAY(Uuid)` 是 PostgreSQL 特有的**数组类型**（标准 SQL 没有）。
`server_default="{}"` 是"数据库层面的默认值"——
⚠ 它在 `ARRAY` 列上到底被处理成什么，**只有回读 `information_schema.columns` 才知道**，
不能靠猜（见 §7 踩坑②）。

> `doc_ids` 的注视里写死了本条纪律：**"绝不可作为检索过滤条件 ——
> 那等于开卷考试还给页码，A/B/C 的差异会被抹平"**。
> 评测题本来就标注了"答案在哪几篇文档"，一旦拿它去过滤检索，
> 检索难度归零、三个配置的表现全都变成满分。`doc_ids` 只用于**判分与统计**。

```python
EXPECTED_TOOL_NOT_CALLED = "__none__"
```
模块级常量，不写在类里 —— 因为它要同时被 ORM、schema、验证脚本、D22 的 runner 引用。

### 3.3 `app/services/eval_service.py`（新建，211 行）

**分工**：与 `retrieval_service` / `document_service` 保持一致 ——
本模块只管评测集的**数据**，**不跑评测、不打分**（那是 D22/D23 的事）。

#### ① 归一函数 `_normalized_payload(raw)`

```python
get = (lambda k, d=None: raw.get(k, d)) if isinstance(raw, dict) else \
      (lambda k, d=None: getattr(raw, k, d))
```
**一行里做的事**：根据 `raw` 是"字典"还是"ORM 对象"，选一个**统一的取值函数**。
- `raw.get(k, d)` —— 字典取值，取不到返回默认值 `d`
- `getattr(raw, k, d)` —— 对象属性取值，没有该属性返回默认值 `d`

**为什么要这样设计**：指纹会被算**两次**——
写入前用"出题脚本里的字典"算一次，之后用"从数据库读回来的 ORM 对象"算一次。
**两条路径必须产出完全一样的字典**，否则"源文件 == 库中"这条断言就永远红。

TS 类比：像一个 `normalize(input: PlainObject | Entity)` 的函数，
内部用 `'get' in input ? ... : ...` 分支，对外只暴露一种形状。

```python
"slugs": sorted(get("doc_slugs") or []),
"tool": get("expected_tool") or "",
```
两处**归一化**，各解决一个假报警：
- `sorted(...)` —— `doc_slugs` 本身是"文档集合"，**顺序不该影响指纹**
  （A+B 与 B+A 是同一套依据）
- `or ""` —— `None` 与 `""` 必须归成同一个值。否则一旦有人把 `None` 写成 `""`，
  内容其实没变，指纹却变了 → 假报警

#### ② 指纹计算 `compute_dataset_fingerprint(cases)`

```python
payload = [_normalized_payload(c) for c in cases]
payload.sort(key=lambda item: item["key"])            # ① 固定顺序
blob = json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(",", ":"))  # ②
return hashlib.sha256(blob.encode("utf-8")).hexdigest()
```

**三行各解决一个"假报警"**（少一个就会出问题）：

| 步骤 | 防的是什么 |
|---|---|
| `sort(key=key)` | 数据库返回的行序**不保证稳定**，顺序一变指纹就变 |
| `sort_keys=True` | JSON 对象**键序**不参与语义，不该影响指纹 |
| `separators=(",", ":")` | 去掉 JSON 里的空格，避免"格式化差异"被当成内容差异 |

`ensure_ascii=False` 让中文不被转义成 `\uXXXX`（只是省字节，对结果一致性无影响，
因为转义方式是确定的）。
`hexdigest()` 输出 64 个十六进制字符。

**为什么用 sha256 而不是 `hash()`**：Python 内置 `hash()` 有**随机盐**，
同一个进程重启后结果就变（这是防哈希碰撞攻击的设计）。
指纹必须**跨进程、跨机器稳定**，所以必须用密码学哈希。

#### ③ `fingerprint_from_db()`

```python
async def fingerprint_from_db() -> tuple[str, int]:
    async with async_session_factory() as session:
        rows = list((await session.scalars(select(EvalCase))).all())
    return compute_dataset_fingerprint(rows), len(rows)
```
返回**元组 `(指纹, 条数)`**：只对指纹、不对条数是不够的 ——
万一落库时少写了一条，指纹也会变（因为少了内容），但"具体少了几条"是另一个有用信息。
`list(...)` 是必要的：`scalars()` 返回的是迭代器，不消费就什么都没读。

#### ④ 写入 `seed_cases(cases, slug_to_doc_id)`

```python
rows: list[EvalCase] = []
missing_slugs: set[str] = set()

for case in cases:
    slugs = list(case.get("doc_slugs") or [])
    doc_ids = [slug_to_doc_id[s] for s in slugs if s in slug_to_doc_id]
    missing_slugs.update(s for s in slugs if s not in slug_to_doc_id)
```
**关键设计**：`if s in slug_to_doc_id` 这个过滤条件看起来是"防御性编程"，
**但它是在制造静默失败** —— slug 翻译失败时 `doc_ids` 会**少一个元素**，
而不是报错。所以紧接着的 `missing_slugs.update(...)` 把失败的那些记下来，
在循环外统一抛异常：

```python
if missing_slugs:
    raise RuntimeError(f"以下 slug 在语料里找不到对应文档：{sorted(missing_slugs)}")
```
**这是"把静默失败变成显式失败"的标准做法**：不阻止失败，但让失败**发出声音**。

```python
    rows.append(EvalCase(
        ..., doc_ids=doc_ids or None, doc_slugs=slugs,
        expected_tool=case.get("expected_tool"), ...))
```
`doc_ids or None`：空列表 → `None`。这是"空数组"与"没有依据文档"的归一 ——
语义上 A 类负例题确实可能没有依据文档。

```python
async with async_session_factory() as session:
    await session.execute(delete(EvalCase))
    session.add_all(rows)
    await session.commit()
```
**"先清空再写"而不是"逐条 upsert"**（upsert = 有则更新、无则插入）：
重跑 seed 时，如果上次有、这次没有的题（比如删掉了 A31），upsert 会把它**留下**，
于是**库里的评测集与源文件不再一致**，而指纹只反映库里的内容 ——
报告会拿到一个"包含幽灵题"的评测集。
清空重写让**库始终等于源文件**，这条不变量是后面所有断言的前提。

#### ⑤ 读取三兄弟

```python
async def list_cases(category=None, limit=200, offset=0):    # 按 case_key 排序列出
async def count_cases(category=None) -> int:                 # 计数

#### ⑥ `dataset_stats()`

`.get(key, 0) + 1` 是 Python 里"计数器"的惯用写法（TS 里习惯写

> **代价**：**它是编的**。报告里必须如实声明"合成语料，非真实企业制度"。

**跨文档钩子**（写语料时就埋好，这是 B 类题的全部依据）：

```

差旅(2)    ──报销款项何时到账──→        财务付款(8)
培训(7)    ──外部培训期间差旅按谁的标准──→ 差旅(2)
采购(3)    ──采购付款由谁审批──→        财务付款(8)
信息安全(4)──员工账号与权限回收──→      IT 服务台(6)
培训(7)    ──外部培训的审批层级──→       采购(3) 的额度分级（对比题）
```

**条款写成"一行一条、不换行"**：
`split_text` 是按**字符**切的，**不认段落**。每条款独立成行有两个好处：
① 抽取 `evidence` 时，一条证据正好落在一行内，能**逐字比对**
② 单条条款不会被切成两半（条款长度都 < 300）

**实测尺寸**：`CHUNK_SIZE=300` / `CHUNK_OVERLAP=50` → step=250，
每篇实际 **1371~1745 字**，8 篇合计 **51 片**。

**为什么专门记这个数**：D19 的断言 B1 要求"切片数 > 20"，
否则"top20 → 重排 → top5"这条链路**根本装不满候选窗口**（`RERANK_CANDIDATE_K = 20`）。
51 片不仅满足，还让检索变成"从 51 片里选 5 片"，比刚好 20 片更接近真实难度。

**`full_text(lines)`** 把条款列表拼成一个字符串（`"\n".join(lines)`）供入库。

actual = {r.column_name for r in (await conn.execute(text(...))).all()}
if declared != actual:
    raise RuntimeError(f"...ORM 多出 {sorted(declared-actual)}，库里多出 {sorted(actual-declared)}")
```
**交叉核对"ORM 声明 == 库里实际"**。
这条能抓到"**模型改了但忘了跑迁移**"这类问题 —— 它是**静默**的：
应用照常启动，只是那个新字段永远读出来是 `None`。

### 3.12 `scripts/d21_epsilon_recheck.py`（新建，389 行）

**目的**：D20 的 ε 是在**21 份手写样本**上测的；现在换成
"**从 50 条真实评测集里分层抽样 + 真跑系统**"，得到的 ε 才对 D22/D23 有意义。

#### 常量

```python
RUNS = 5                    # 每个样本重复打分几次（5 次才够估比例）
PASS_THRESHOLD = 4          # correctness >= 4 记"对"（PRD F7.5）
EVAL_SET_SIZE = 50          # 与评测集规模一致，用于把 ε 换算成"条数门槛"
VOTE_RUNS = 3               # D20 定下的"3 次多数投票"
MIN_MISMATCH_FOR_POINT_ESTIMATE = 5     # 观测到的不一致少于 5 次 → 点估计不可用
DISCRIMINATION_ALERT_SHARE = 0.7        # 满分占比 > 70% → 区分度预警
PRD_IMPROVEMENT_CASES = 4               # PRD 的 +10% 在 50 条上 ≈ 4 条
```

**`MIN_MISMATCH_FOR_POINT_ESTIMATE = 5` 是今天加的最重要一条**：
"观测到 0 次不一致"**只能说明 ε 很小，推不出 ε = 0**。
拿 0 当门槛会得出"**任何差异都显著**"的荒谬结论。
所以**不一致次数不足 5 次时，直接宣布点估计不可用**，只认保守口径。

#### `noise_floor_from_epsilon(epsilon, size)`

**噪声地板**（noise floor）＝"纯噪声情况下，两次测量的差异**期望有多大**"，单位是**条数**。
公式来自二项分布：两次测量各翻不翻车是两个独立事件，差异条的期望 ≈ `size × 2ε(1−ε)`。

⚠ **它与 ε 不是同一个量**（D20 文档曾把两者混着叫，已修正）：
**ε 是比例（0.95%），噪声地板是条数（2.9 条）**。

#### `gate_after_voting(epsilon, runs=3, size=50)`

**多数投票后门槛**：3 次投票需要 **≥2 次**同向翻转才会改变结论，
概率 ≈ `C(3,2)·ε²(1−ε) + C(3,3)·ε³`。用 `math.comb` 写成通用形式。
实测：单次门槛 11.42 条 → **投票后降到 3.79 条**。

#### `sample_cases()` —— 分层抽样

```python
SAMPLING_PLAN = ...   # doc_qa easy 2 / medium 2 / hard 1 / 负例 1 /
                      # cross_doc medium 1 / hard 1 / tool_call easy 2
```
**为什么分层抽样而不是随机抽 10 条**：
随机抽 10 条**很可能全落在 `doc_qa/easy`**（这一类占比最大），
于是测出来的 ε 只反映"最简单的那一档"。
分层抽样保证每一档都有代表。

#### `run_system(cases)` —— 真跑

```python
每条**全新 session**
```
**为什么每条题要新 session**：会话记忆会带着上一题的内容进下一题，
**污染**答案（同 D11 踩过的"会话 ID 写死 → 读到上一轮历史"）。

#### `cleanup_sessions(session_ids)`

**清理 Redis 窗口 + PG 记录**。
为什么必须清：这些是**评测产生的垃圾会话**，留着会混进"真实用户会话"的统计里。

#### `report_epsilon(samples, grouped, title)` —— 四段输出

1. **逐条明细**：`A01 doc_qa corr=[5,5,5,5,5] → 判定 对`
2. **correctness 分档直方图** + **阈值带占比**
3. **ε（点估计）+ 95% Wilson 区间**
4. **口径 A / 口径 B 两行对比** + 对 PRD 验收线的含义

**Wilson 区间**（Wilson score interval）：
比例型指标的置信区间算法，比"正态近似"在**小样本 + 极端比例（接近 0 或 1）**时可靠得多。
**为什么必须用它**：观测到 0 次不一致时，正态近似的标准差是 0、区间退化成 `[0, 0]`——
**看起来"绝对确定"，实则完全没有信息**。Wilson 给出的是 `[0%, 7.14%]`，这才是诚实的表达。

#### `main()` 四步

```
[1/4] 分层抽样
[2/4] 真跑系统（每条新 session）
[3/4] judge 重复打分 → 算 ε
[4/4] 参考答案自评（全部 50 条，单次打分）
```

**第 4 步"参考答案自评"是什么**：
把**我们自己的参考答案**当成"被测答案"喂给 judge 打分。
- 如果参考答案自己都拿不到 ≥4 分 → judge 的 **rubric 有问题**（标尺本身是歪的）
- 如果全部 ≥4 分 → **评测集质量下限通过**

**实测**：50 条全部 ≥4 分，单次 HTTP 往返中位 0.71s。

**为什么这一步必须做**：它是唯一能区分
"**系统答得差**"与"**参考答案写得没法判**"的手段。
不做这一步，一次低分你永远不知道该去修系统还是修题。

## §4 类比迁移表

| 今天的新东西 | 你已经会的（TS / React / 前端） | 关键差异 |
|---|---|---|
| `Mapped[int]` + `mapped_column` | TypeORM / Drizzle 的列定义 | Python 这边**类型注解参与运行时**，不只是编译期 |
| `Literal["a","b"]` | `type X = 'a' \| 'b'` | 几乎一样；差别是 FastAPI 会**自动**把它变成 422 |
| `BaseModel` / `ConfigDict` | Zod schema | Pydantic 多了 `from_attributes`（能从对象读，不只从对象字面量） |
| `EvalCaseDetailOut(EvalCaseOut)` | `interface B extends A` | 一样的继承语义 |
| `hashlib.sha256` 内容指纹 | 前端构建产物的 hash 文件名 | 同一套思想：**内容变了才变** |
| `sorted(...)` 后再哈希 | 对象做 key 前先 `JSON.stringify` 稳定化 | 一样：**顺序不是内容** |
| `server_default="{}"` | 数据库 `DEFAULT` 子句 | 一样；坑在于"字符串会被当成 SQL 表达式" |
| `information_schema` 回读自查 | `PRAGMA table_info` / 迁移 diff | 一样：**别信 ORM，信数据库** |
| `delete_all_documents()` 的隐患 | 测试里直接 `TRUNCATE` 共享库 | 一样：**共享数据源上的清理必须自限范围** |
| Wilson 置信区间 | 前端埋点"转化率 3/100 的置信区间" | 一样的思想；小样本/极端比例才见真章 |
| 分层抽样 | A/B 测试按用户分层 | 一样：**防止某一类占满样本** |

## §5 面试考点

**Q：你们的评测集是怎么建的？**
> 先立语料、再出题，顺序不能反。反过来会造出"参考答案里的数字在语料里根本不存在"的题——
> 这种题**永远答不对且不报错**，只会污染评测结果。
> 语料是 8 篇合成企业制度文档（51 个切片），题是 50 条：
> A 类单文档 30（含 5 条负例）、B 类跨文档 10、C 类工具 10。

**Q：怎么保证评测集不被偷偷改？**
> 内容指纹。把影响判分的字段归一化后算 sha256，落库前算一次、从库读回来再算一次，
> **两者必须相等**；同时 `/api/eval/dataset` 把指纹暴露成**可外部对照的出口**。
> 关键在于**哪些字段不进指纹**：`id` / `created_at` / `doc_ids` 都不进 ——
> 尤其 `doc_ids` 是文档 UUID，重建语料就会换，算进去会导致"题目一个字没改也报改版"，
> 然后**报警疲劳**，冻结机制就废了。

**Q：负例怎么设计？**
> 语料里**根本不存在答案**的题，正确行为是**拒答**。
> 关键在于 `reference` **不能留空或写 N/A** —— judge 判分是拿被测答案和参考答案比，
> 参考答案空着 judge 就没有标尺。要写成**可判定的陈述**：
> "知识库中没有关于 X 的规定，正确做法是明确告知用户找不到依据"。

**Q：评测的噪声怎么处理？**
> 分两层，**不同层要用不同办法**：
> - **judge 侧抖动**：重复打分 + 多数投票。实测 ε ≈ 7.14%（保守口径），
>   单次打分门槛 11.42 条、3 次投票后降到 3.79 条 ——
>   这就是"要 3 次重复"的数据依据。
> - **生成侧抖动**：这个**投票救不了**。实测同一条题、同配置两次独立运行，
>   答案 459 字 vs 511 字，judge 内部各自 5 次完全一致，但一次判对、一次判错。
>   **重复测量只能压掉"同一份答案被重复测量"的噪声，压不掉"答案本身在变"**。
>   要对付它只能**重复生成**，成本是 N 倍。

**Q：为什么 `doc_ids` 不能当检索过滤条件？**
> 评测题本来就标注了"答案在哪几篇文档"，拿它去过滤检索等于**开卷考试还给页码**——
> 检索难度归零，三个检索配置（纯向量 / 混合 / 混合+重排）的表现会**全部变成满分**，
> 消融实验从根上失效。`doc_ids` 只用于**判分与统计**。

**Q：为什么评测集用自增 id，文档表用 UUID？**
> 不是前后不一致，是**取舍对象不同**。
> 自增 id 的风险是"可枚举、泄露总量"，那是对**面向用户的数据**才需要防的。
> 评测集是内部研发资料，而报告/命令行/复现说明里要大量写"第几条题"——
> **可读性优先**。同时用 `case_key`（A01/B03）做**稳定业务键**，
> 因为自增 id 每次重建都会变。

## §7 踩坑记录

### 踩坑① 出题时把 evidence 标错了文档 —— 被 D 段断言抓出来

**现象**：B07（跨文档题）的第二段证据标在 `finance-payment` 名下，
但那句话**实际出自 `procurement`**（两段同源）。
→ **这题根本不是"跨文档题"**，照此跑评测，B 类的成绩**全程是假的**
（被判对的其实是单文档检索）。**脚本不会报任何错。**

**是谁抓到的**：`d21_eval_verify.py` 的 **D 段"依据机检"**。
第一次跑验证是 **56/58，2 项红** —— 就是它。

**修法**：把 B07 第二段证据改成真正出自 `finance-payment` 的一句
（"公司设定每月 10 日和 25 日两个集中付款日"）。

**教训**：**"我出题的时候是对的"不是证据，"把题拿回语料里验一遍"才是。**
凡人工构造的数据集，必须配一段"回原始数据核对"的机检断言。

---

### 踩坑② 迁移脚本里我自己写错了期望类型 —— 被回读自查抓出来

**现象**：`EXPECTED_COLUMNS` 里把 `category` 的期望写成 `("text", "text")`，
实际建出来是 `character varying` / `varchar`（`String(16)` 映射成 varchar 而非 text）。

**是谁抓到的**：**回读 `information_schema.columns` 再和期望比**这一步。

**教训**：**期望值是我自己写的，写错了脚本会"如实"地认为结构不对或对。**
所以核对必须有一个**独立来源** —— `information_schema` 的真实回读优先于我的期望。

---

### 踩坑③ 7 个历史脚本会删光长期语料 —— 今天才发现

**现象**：引入长期语料后才发现，7 个历史验证脚本调用 `delete_all_documents()`：

```
d9_retrieval_verify / d10_tool_verify / d10_agent_rag_verify /
d11_citation_verify / d11_http_verify / d12_documents_verify / d14_sessions_verify
```

在 D21 之前这是安全的（数据本来就是临时造的），但**跑一次全量回归就会删光 51 片语料**，
而脚本本身**不会报任何错**（它们测的就是"删干净"）。

**今天的对策**：回归跑完 → 重跑 `d21_seed` 重建 → 验证**指纹不变**。
这也顺便**反证了"UUID 不进指纹"的设计是必要的**：
重建必然换 UUID，如果纳入指纹就会假报警。

**正确修法（待做）**：清理函数**按范围自限**（如 `delete_documents_by_prefix`），
禁止在**共享库**上用"删全表"当清理手段。

### 踩坑④ ε 又是 0.0000，但成因与 D20 完全不同

见 §2.9。**两次都印 `0.0000`，修法方向却相反**。
"数字本身没错，但它回答的不是你想问的问题" —— 与 D18"12 token 测出 2.8ms"同族。

---

### 踩坑⑤ 生成侧抖动 ≫ judge 侧抖动

见 §2.10。**这是 D20 方法论的一个缺口**，D22 要决策"生成要不要也重复"。

### 小结：今天五条坑里，有三条的成因是同一个

| 坑 | 失败模式 |
|---|---|
| ① B07 证据标错文档 | 人工数据**没有回原始数据核对** |
| ② 期望类型写错 | 期望值来自**我脑子里**而不是独立来源 |
| ③ 脚本删光语料 | 破坏性操作的**作用域没有自限** |

共同点：**不报错、不崩溃，只是"存得/做得和你以为的不一样"**。
这正是铁律 12「静默失效」的三种形态。

## 附录 B：五处"为什么不是更简单的写法"

| 更简单的写法 | 为什么不用 | 代价 |
|---|---|---|
| 指纹直接把 ORM 对象 `json.dumps` | ORM 对象带 `id` / `created_at` / `doc_ids` → 假报警 | 多写一个归一函数 |
| 用 `doc_ids`（UUID）而不是 `doc_slugs` | 重建语料就换 UUID → 报警疲劳 → 冻结失效 | 多维护一份 slug 映射 |
| 列表接口直接返回全部字段 | 答案页泄漏到前端 → 不再是盲测 | 多一个 `EvalCaseOut` + 详情接口 |
| `expected_tool` 用 `NULL` 表示"不该调工具" | `NULL` 已表示"没填"，两种语义混用 | 一个哨兵常量 |
| 逐条 upsert 而不是清空重写 | 删掉的题会留下 → 库里与源文件不一致 | 每次重建（50 条，可忽略） |
| 清理用 `delete_all_documents()` | 会删光共享库里的长期语料 | 要写按范围限定的删除（**待做**）|
