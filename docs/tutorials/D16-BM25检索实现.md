## 2. 核心概念讲解

### 2.1 三层分工：一句话各管什么

| 层 | 一句话职责 | 它决定的事 | 在哪执行 |
|---|---|---|---|
| ① 切词 | 把字符串变成词 | **什么算一个词**（词表） | 应用层 Python（jieba） |
| ② 筛候选 | 用倒排索引捞出"可能相关"的切片 | **谁能参与排名** | 数据库 SQL（走 GIN） |
| ③ 打分 | 套 BM25 公式给候选排序 | **谁排在前面** | **我们自己写的 SQL** |

⚠️ 两个容易说错的地方：

- ② **不做相关性判断**。它只判断"这个切片里有没有出现查询词"，有就进候选、没有就出局。
  真正决定"多相关"的是 ③（靠 IDF 把"的"这类词的贡献压到接近 0）。
  准确分工是：**② 负责「不漏」，③ 负责「排准」**。
- ③ 虽然写在 SQL 里，但它是**我们的代码逻辑**，不是数据库的内建能力 ——
  见 §2.6。

### 2.2 第②层为什么不改变结果（这是本节最反直觉的一处）

结论：**筛候选只影响成本，不影响结果。**

严格推导：

```
BM25 分数 s(D) = Σ_{q∈Q} IDF(q) × [ f(q,D)×(k1+1) ] / [ f(q,D) + k1×(1-b+b×|D|/avgdl) ]

① 若 D 不含任何查询词 → 每一项的 f(q,D) 都是 0 → 每一项都是 0 → s(D) = 0
② IDF(q) = ln(1 + (N-df+0.5)/(df+0.5))，当 df ≤ N 时括号内 > 1 → IDF(q) > 0
   → 候选集内的切片至少有一个 f > 0 → s(D) > 0
③ 于是「候选集外的分数恒为 0」且「候选集内的分数恒 > 0」
   → 候选集外的切片必然排在候选集内之后
   → 取 top_k 时，结果与"扫全表给每个切片打分"**完全一致**
```

所以 GIN 倒排在这里的角色是**纯加速**：不必给那 9000 个零分切片算一遍分。

### 2.3 为什么候选筛选必须是 OR（正确性问题，不是风格问题）

由 §2.2 的第 ③ 条反过来推：

| 连接词 | 候选集定义 | 与「分数可能非 0」的关系 | 后果 |
|---|---|---|---|
| **OR**（`年假 \| 报销`） | 至少命中一个查询词 | **恰好等价** | 候选集不多不少，结果不变 ✅ |
| AND（`年假 & 报销`） | 全部命中 | 严格更小 | 会踢掉"只命中部分词"的切片 —— 而它们**分数非 0**，本该参与排名 → **静默篡改排序** ❌ |

**"静默"是关键**：不报错、不崩溃，只是答案变差。

### 2.4 第③层的输入是两类数据，来源不同

| 类别 | 具体量 | 从哪来 | 覆盖范围 |
|---|---|---|---|
| **行级** | `f`（词频）、`dl`（文档长度） | 被 ② 筛出来的那几行 | 候选集 |
| **全库级** | `N`、`avgdl`、`df` | 统计整张表 | **整个语料** |

**为什么全库量不能只算候选集**：候选集不是随机子集，它是**"与查询相关"的子集**，
里面的切片天然更容易包含查询词 → 同一个词在候选集里显得更常见 → 权重被改变。

⚠️ 本节有一处**我讲解时讲错了、被实测纠正**，见 §7 坑 6。**以实测为准**：

| 口径 | N | df(报销) | IDF(报销) | IDF(灰度) | 词间区分度 |
|---|---|---|---|---|---|
| 全库 | 6 | 3 | 0.6931 | 1.5404 | 2.222 |
| 候选集 | 4 | 3 | 0.3567 | 1.2040 | **3.376（放大，非压缩）** |

实测结论（E1 + E2）：候选集口径让 IDF 整体变小、区分度**放大** 1.153，而**排序完全没变**。
所以站得住的危害不是"排序会变"，而是**原则性**的：
**IDF 本应是词的固有属性（全语料稀有度），改用候选集算，它就变成了"本次查询的函数"** ——
同一个词换个查询、候选集一换，权重就变，排序依据不再稳定，也无法跨查询横向比较。

### 2.5 长度归一化（"为什么长文档天然占便宜"）

**问题**：两篇文档都只含 1 次"年假" ——

- 短文档：`年假 天数 按 工龄 计算`（5 个 token）
- 长文档：一份 300 token 的手册全文，"年假"顺带提了一句

直觉上短文档更相关（整篇都在讲它），但公式里两者 `f` 相同、IDF 相同 → **算出来一模一样**。
这就是"长文档占便宜"：文档越长，越容易**不小心中**查询词。

**类比**：一杯 500ml 水放 5 勺糖，和一杯 100ml 水放 5 勺糖 —— 糖的总量相同，浓度差 5 倍。
BM25 要比较的是**浓度**，不是总量。

**机制**（分母里那一段）：

```
f + k1 × (1 - b + b × dl/avgdl)
              ↑          ↑
          不打折部分   按长度打折部分
```

关键是 `dl/avgdl` —— **不是文档长度的绝对值，而是"本文档长度 ÷ 语料平均长度"**。
这个换算就是"归一化"三个字：把长度换算成"相对平均长度的倍数"，
让不同长度的文档站在同一条起跑线上比较（就像前端用 `rem` 相对根字号，而不是写死 `px`）。

| `dl/avgdl` | 含义 | 分母 | 结果 |
|---|---|---|---|
| **= 1** | 长度正好等于平均 | `f + k1` | **基准，不奖不罚**（`b` 取任何值都成立） |
| **> 1** | 比平均长 | 变大 | 分数被**压** |
| **< 1** | 比平均短 | 变小 | 分数被**抬** |

`b` 控制折扣力度：`b=0` 时 `1-b+b×x ≡ 1`（完全不看长度）；`b=1` 时完全按长度比例调。
**`1-b`（默认 0.25）是刻意留下的"长度中立"余量** —— 因为"长文档更全"有时确实更相关
（问三个问题时，往往就是那篇长手册能覆盖全），不能把长全压死。

⭐ **一个必须点出来的联系**：`avgdl` 是**语料平均长度** —— 也就是说
**长度归一化用的基准线本身就是个全库统计量**。所以第 ③ 层依赖全库的量不止 IDF 一个：

| 量 | 用在哪 | 为什么必须是全库 |
|---|---|---|
| `df` | IDF | 不然"稀有度"被候选集改变 |
| `N` | IDF | 与 df 必须同口径 |
| `avgdl` | 长度归一化 | 不然"长/短"的基准线随查询漂移 |

三个量都躺在那一条 SQL 的 CTE 里 —— 这就是"**BM25 是语料级算法**"的完整含义，
也是它跟向量检索最根本的差别（向量每篇独立编码，加一百篇也不影响已有向量）。

### 2.6 `tsvector` 是索引、BM25 是公式 —— 落点在哪

D13 反复强调过这句话，今天的代码把它变成了可以指出来的两行：

- `content_tsv`（`tsvector` + GIN）**只出现在 `WHERE` 里**（筛候选），**从不参与打分**
- BM25 的 `f` 是**从 `content_tokens` 这个纯文本列里数出来的**，压根不经过 `tsvector`

**这正好说明索引与打分是可以解耦的两个东西**：同一个候选集，换个公式照样能排；
同一套公式，换个索引结构（比如 `text[]` + GIN 数组索引）也照样能用。
面试可以直接说：**"倒排索引用 `tsvector` + GIN，BM25 分是我们自己用 SQL 实现的。"**

### 3.1 `app/services/tokenizer.py` —— 为什么必须只有一个出口

D13 §2.5 提过这条风险，D16 探针 v3 把它变成了**看得见的后果**：
只要索引侧与查询侧的 token 对不上，检索就**静默失效**（不报错、只是永远查不到）。
唯一可靠的防法就是物理上只有一个函数。

清洗分两步，**顺序不能反**：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| ① | 剥掉 token 内部的 tsquery 元字符 | jieba 会把标点切成独立 token（`'A&B公司'` → `['A','&','B','公司']`），而 `& \| ! ( ) : < > ' \ *` 这 10 个字符会让 `to_tsquery` **直接抛语法错**（对用户就是 500） |
| ② | 丢弃不含实义字符的 token | 纯标点 token 对检索零价值，还会污染 `df` 统计 |

**为什么顺序不能反**：先剥再判，`'a&b'` 会变成 `'ab'`（有实义、保留）；
先判再剥，`'a&b'` 因为"含字母"而被保留下来，**带着 `&` 进 tsquery 就炸了**。

```python
def _clean_token(raw: str) -> str | None:
    token = _UNSAFE_CHARS.sub("", raw)
    if not _HAS_WORD.search(token):
        return None
    return token
```

**另一条容易被"优化"掉的规则：不去重。**

```python
def tokenize(text: str) -> list[str]:
    ...
    for raw in jieba.lcut(text):
        cleaned = _clean_token(raw)
        if cleaned:
            tokens.append(cleaned)   # 重复的 token 要保留！
    return tokens
```

重复次数就是 BM25 的词频 `tf` —— 去重会把 `f` 恒定为 1，整个 TF 部件直接失效。

**`build_or_tsquery()` 为什么放在 tokenizer 而不是 retrieval_service**：
它成立的前提是「token 已经过清洗」。和 `tokenize()` 是同一份契约的两端，
分到两个文件里，将来有人绕过清洗直接拼 tsquery 就会 500。

### 3.2 `app/models/document_chunk.py` —— 为什么 `content_tsv` 是生成列

```python
content_tokens: Mapped[str | None] = mapped_column(Text, nullable=True, ...)

content_tsv: Mapped[str | None] = mapped_column(
    TSVECTOR,
    Computed("to_tsvector('simple', content_tokens)", persisted=True),   # STORED
    nullable=True,
)
```

如果用**普通列**：每次写入都要记得同步更新，漏一次就是静默不一致
（倒排索引里的 token 和 `content_tokens` 对不上，检索不出来但毫无报错）。
生成列把「`tsv` 恒等于 `to_tsvector(tokens)`」交给数据库保证，应用侧永远不写它。

⚠️ **但要清楚它只能保证"第二段一致性"**：

```
content ──(应用侧 jieba)──> content_tokens ──(数据库生成列)──> content_tsv
         ↑ 第一段：靠 tokenizer.py 单点保证     ↑ 第二段：靠生成列保证
```

`NULL` 语义也实测确认过：**未回填的行（`content_tokens IS NULL`）→ `content_tsv` 也是 NULL**，
不会静默变成空 `tsvector`，所以 `WHERE content_tokens IS NULL` 可以当"未分词"的判据用。

GIN 索引：

```python
Index("idx_chunks_tsv", "content_tsv", postgresql_using="gin"),
```

### 3.3 `scripts/d16_migrate.py` —— 为什么不能只改模型

**铁律 10**：`Base.metadata.create_all(checkfirst=True)` 见到表已存在就**整张跳过** ——
不补列、不改类型、不建索引。D12 曾因此让 `document_chunks` 长期没有外键。
所以这里用**显式 DDL**，并且做完立刻回读库结构自查。

三个动作 + 一个必须做的补账：

```
① ALTER TABLE ... ADD COLUMN IF NOT EXISTS content_tokens TEXT
② ALTER TABLE ... ADD COLUMN IF NOT EXISTS content_tsv tsvector
       GENERATED ALWAYS AS (to_tsvector('simple', content_tokens)) STORED
③ CREATE INDEX IF NOT EXISTS idx_chunks_tsv ... USING GIN (content_tsv)
④ 回填：把 content_tokens IS NULL 的历史切片逐行分词写回
```

**④ 为什么不能省**：DDL 只是把列建出来，历史切片的 `content_tokens` 还是 NULL ——
**它们永远搜不到**。「列加了但数据是空的」比「不加列」更危险：前者看起来一切正常。

自查用 `information_schema.columns` + `pg_indexes` **回读真实结构**，
而不是相信"语句没报错"（`IF NOT EXISTS` 在列已存在时是**静默跳过**的）：

```python
EXPECTED_COLUMNS = {
    "content_tokens": ("text", "NEVER"),
    "content_tsv": ("tsvector", "ALWAYS"),
}
```

整个迁移包在一个事务里（`async with engine.begin()`）—— 任何一步自检失败就抛异常，
DDL 一起回滚，不留半成品。（PostgreSQL 的 DDL 是事务性的，这点和 MySQL 不同。）

### 3.4 `retrieval_service._BM25_SQL` —— 逐 CTE

| CTE | 作用 | 关键点 |
|---|---|---|
| `corpus` | 语料统计 `N` / `avgdl` | 只统计 `status='ready'` 且 `content_tokens <> ''` 的切片 |
| `candidates` | ② 筛候选 | `content_tsv @@ to_tsquery('simple', :tsq)` 走 GIN |
| `q` | 查询词序列 | `unnest(string_to_array(:terms, ' '))` |
| `tf` | 每个 (候选, 查询词) 的 `f` 与 `dl` | 直接数 token 串 |
| `df` | 每个查询词的 `df` | **与 `corpus` 同口径**（全库、只看 ready） |
| `scored` | 套公式求和 | 逐词 `IDF × 饱和后的 TF`，再 `sum()` |

三个必须记住的点：

```sql
-- ① 浮点参数一律显式 CAST（D13 坑 1）
/ (tf.f + CAST(:k1 AS double precision)
         * (1 - CAST(:b AS double precision)
              + CAST(:b AS double precision) * tf.dl / corpus.avgdl))
```

不加 `CAST`，PostgreSQL 会把 `:k1` 推断成 **integer** —— `1.2` 被静默截断成 `1`、
`0.75` 截断成 `0`，而 **`b=0` 等于把长度归一化整个关掉**。语句不报错、照样跑完，只是排序悄悄变错。

② `N` / `avgdl` / `df` 的口径必须一致，且覆盖**整个语料**（见 §2.4）。

③ 候选筛选用 OR（见 §2.3）—— `:tsq` 由 `build_or_tsquery()` 拼成 `'年 | 假 | 报销'`。

**排序里那个 `cd.id ASC`**：分数相同时的兜底排序。没有它，同分文档的顺序由数据库决定，
验证脚本会出现"这次跑和上次跑结果不一样"的鬼故事（铁律 9 里那条"先怀疑进程外状态"的同类问题）。

日志里带了候选数：

```sql
count(*) OVER () AS candidate_count   -- 窗口函数在 LIMIT 之前求值
```

`LIMIT` 之前求值 → 拿到的是**候选总数**，用来观察 OR 的召回宽度（实测：查"报销"候选=3）。

### 3.5 `retrieval_service.search_keywords()`

```python
tokens = tokenize(query)
if not tokens:
    logger.info("BM25 检索跳过：query=%r 清洗后无有效 token", query[:20])
    return []
```

**这个提前返回为什么必要** —— 这里有一处**臆测被实测推翻**（见 §7 坑 4）：
我原本注释写"空 tsquery 会匹配所有"，实测是 `to_tsquery('simple','')` → `''`，
`@@` 结果是 **False（查不到）**。所以空串不会造成错误结果，只是白跑一次数据库往返、语义也不清晰。

返回契约与向量检索**有意不同**：

```python
{
    "content": ..., "source": ..., "page_ref": ...,
    "score": round(float(row.score), 4),     # 不是 similarity
    "retriever": "bm25",                     # 标明这一路是谁产的
}
```

- `score` 而不是 `similarity`：BM25 分数**无上界**（可 > 1），与 cosine 的 `[0,1]` 不是一个量纲。
  混用同一个键名，会在 D17 做 RRF 时埋雷（融合时容易误以为两者可直接比较/相加）。
- `retriever`：调试与消融实验（D23）归因用。

## 4. 类比迁移表

| D16 的新东西 | 你已会的（前端 / TS） | 对应关系 |
|---|---|---|
| `tokenizer.py` 单点分词 | 项目里唯一的 `dayjs` 实例 / 唯一的 axios 封装 | 多个出口 = 格式不一致 = 静默 bug |
| `content_tsv` 生成列 | Vue 的 `computed` / DB 的 generated column | 派生值不让人手写，消灭"忘记同步"这一类 bug |
| GIN 倒排索引 | `Map<token, Set<docId>>` | 就是你熟的那个倒排表，由数据库持久化 |
| ② 筛候选 vs ③ 打分 | SQL `WHERE` 先过滤、再 `ORDER BY` 排序 | **先缩小集合，再排序** —— 只是"缩小"的依据是倒排表 |
| `score` 无上界 vs `similarity` 在 [0,1] | 不同单位的值不能相加 | 融合前必须统一到"排名"上（这就是 RRF 用 rank 不用分数的原因） |
| 迁移脚本 + 结构自查 | 手写 migration 而不是靠 ORM 自动同步 | `create_all` 不是迁移工具（D12 教训） |

## 5. 面试考点

**Q1：你们的 BM25 是怎么实现的？**
> 倒排索引用 PostgreSQL 的 `tsvector` + GIN，**BM25 打分是我们自己用 SQL 实现的** ——
> `N` / `df` / `avgdl` 三个语料级统计量用 CTE 现算。
> PostgreSQL 内建的 `ts_rank(tsvector, tsquery)` **不是 BM25**：它只接收这两个入参，
> 拿不到 `df` / `N` / `avgdl`，**IDF 在数学上就算不出来**；而且默认参数下没有长度归一化。

**Q2：中文怎么处理？**
> 应用层 jieba 分词 + 数据库侧用 `simple` 配置。因为 PostgreSQL 内置分词器对中文无效
> （整句会退化成一个 token，实测查"智能"不命中）。
> **索引侧和查询侧必须是同一个分词器**，否则 token 对不上、检索静默失效 ——
> 我们把分词收敛成单点函数 + 迁移脚本可重跑 + 一致性断言三层来兜。

**Q3：关键词检索和向量检索怎么配合？**
> 不是二选一，是互补：向量擅长"意思相近"，对精确字面不敏感；BM25 反过来，字面不命中就是 0 分。
> 今天我们实测过一个例子：查「报销」，BM25 把高频词文档排第一、向量把语义最像的排第一，**首位就不同**；
> 而查「灰度回滚」时向量会返回 3 条（把完全无关的长文档也排进去了），BM25 只返回 1 条。
> 两路命中集合不同，才值得用 RRF 融合（D17）。

**Q4：为什么候选筛选用 OR 不用 AND？**
> 这不是召回率取舍，是正确性问题。BM25 中不含任何查询词的文档分数**恒为 0**，
> 所以"至少命中一个查询词"这个条件与"分数可能非 0"是**等价的** ——
> OR 筛出来的候选集不多不少，结果与扫全表完全一致，只是省掉算零分的成本。
> 换成 AND 会踢掉"只命中部分词"的文档，而它们分数非 0、本该参与排名，等于**静默篡改排序**。

**Q5：长度归一化在做什么？**
> 压掉"长文档天然占便宜"。长文档有更多机会不小心中查询词，
> 所以用 `dl/avgdl`（相对平均长度的倍数）做调节：比平均长的扣分、比平均短的加分、
> 正好等于平均长度的不奖不罚。`b` 控制力度，默认 0.75 ——
> 那个 `1-b=0.25` 是刻意留的余地，因为"长文档更全"有时确实更相关。
> 注意 `avgdl` 也是**全库统计量**，所以 BM25 里依赖语料的量其实有三个：`N`、`df`、`avgdl`。

<details>
<summary>参考答案要点</summary>

1. ①切词=词表、②筛候选=谁能参与排名、③打分=谁排前面。②在数据库里（GIN），③是我们写的 SQL（不是 PG 内建函数）。
2. 不含查询词的切片每项 `f=0` → 分数恒 0；候选集内至少一项 `f>0` 且 IDF>0 → 分数恒 >0。所以候选集外必然排在后面，top_k 结果不变。
3. AND 要求全部命中，会踢掉只命中部分词的切片 —— 它们分数非 0、本该参与排名。危害静默：不报错、不崩溃，只是答案变差。
4. 三个：`N`（IDF 的语料总量）、`df`（IDF 的稀有度）、`avgdl`（长度归一化的基准线）。`avgdl` 算全库量是因为归一化比较的是"相对平均长度的倍数"，基准线一变所有文档的系数都变。
5. 系数 = 1（不奖不罚，`b` 取任何值都成立）。`b=0` 完全不看长度；`b=1` 完全按长度比例调节。
6. 生成列让数据库保证 `tsv ≡ to_tsvector(tokens)`，应用侧不可能写歪。它保证**第二段**（tokens→tsv）；**第一段**（content→tokens）靠 `tokenizer.py` 单点保证。
7. 不回填，历史切片的 `content_tokens` 是 NULL → 永远搜不到。**不报错**，只是查不到 —— 比"不加列"更危险，因为看起来一切正常。
8. BM25 分数无上界、cosine 在 `[0,1]`，不同量纲。RRF 只用**排名**不用分数，但接口上要能区分来源与量纲，混用同键名会在融合时埋雷。

## 7. 踩坑记录

### 坑 1（探针 v1，事务污染 → 一半结论是假的）
第一版探针逐条测 `to_tsquery` 的语法风险，第一条 `foo(bar)` 报错后，asyncpg 的**事务进入 aborted 状态**，
后续 6 条全部返回 `InFailedSQLTransactionError` —— 看起来"7 个查询串会炸"，
实际只有第一条是真报错，其余是**污染出来的假象**。
**教训**：测"每一轮都可能失败"的东西，每轮失败后必须显式 `rollback`，
否则后面的"结论"全是上一个错误留下的残影。
（这是铁律 9 那条"先怀疑进程外状态"的同族问题。）

### 坑 2（探针 v1，冷启动计时测成 0）
为了测 jieba 冷启动成本，我在**第三个**探针函数里做的计时 —— 但 jieba 在**第二个**探针里
就被 import 并调用过了，词典早建好了，于是测出 `首次 lcut：0.000s`（假的）。
真实成本其实打在 jieba 自己的日志里：`Loading model cost 0.275 seconds`。
**教训**：测"首次成本"必须保证被测量对象**在本进程里从未被使用过**；
计时起点要在任何 import 之前。

### 坑 3（我自己的 docstring 里的 `\`）
`tokenizer.py` 的 docstring 里为了列举危险字符写了 `\`，触发
`SyntaxWarning: invalid escape sequence '\ '`。
**修法**：docstring 声明成 raw string（`r"""..."""`）。
注意**第三方包的同类警告修不了**（jieba 自己就有三处），那是它的历史遗留，与我们无关。

### 坑 4（未验证的断言写进注释：空 tsquery 会"匹配所有"）
在 `build_or_tsquery()` 的 docstring 里我写下"空串送进 `to_tsquery` 会解析成空查询，
行为不是'查不到'而是'匹配所有'" —— 这是**臆测**。实测：

```
to_tsquery('simple', '')            → ''        （不报错，空查询）
to_tsvector(...) @@ 空查询           → False     （查不到，不是匹配所有）
```

**教训**：写进代码注释的每一句"行为描述"都是一条断言，同样要实测。
臆测和真理在注释里长得一模一样，几个月后连自己都会信。

### 坑 5（E 段把"结论"硬编码在 print 里 —— 又犯了铁律 11）
验证脚本的 E 段，我一边打印出"候选集口径把区分度**放大**了 1.153"，
一边在下面硬编码一段"区分度一旦被**压缩**，排序就更接近纯词频排序……"。
**打印的数据和结论相反，脚本照样念完** —— 这正是 D13 踩过的坑（铁律 11 明令禁止"结论硬编码"），
我自己写下的规矩自己又破了。已改成 `if/else` 由数据决定用词。

### 坑 6（原理课预判被实测推翻：是"放大"不是"压缩"）
讲解第③层时我判断"候选集算 `df` 会让 IDF 被**系统性低估**、区分度被**压缩**"。
实测（E1/E2）：

| 口径 | N | df | IDF(报销) | IDF(灰度) | 区分度 | 排序 |
|---|---|---|---|---|---|---|
| 全库 | 6 | 3 | 0.6931 | 1.5404 | 2.222 | `[other, tf10, short, long]` |
| 候选集 | 4 | 3 | 0.3567 | 1.2040 | **3.376** | **完全相同** |

- 方向**反了**：是放大、不是压缩
- 而且**排序根本没变** —— 说明"改口径更差"在这个数据规模上**不成立**

修正后的结论（站得住的版本）：
**IDF 本应是词的固有属性（全语料稀有度），改用候选集算就变成"本次查询的函数"** ——
同一个词换个查询、候选集一换权重就变，排序依据不稳定、也无法跨查询横向比较。
这是**原则性**的理由，不是"实测更差"的理由。
**教训**：结构性推理可以用来说明"为什么这么设计"，但不能当成"实测结论"讲出去；
一旦有了数据，以数据为准，并且**把推翻过程留在文档里**。

## 附录 A：端到端运行链路（实测）

```
① 入库（写路径）
   POST /api/documents → process_upload → _ingest_segments
     content ──jieba 分词──> content_tokens（存库）
                  └─ 数据库自动派生 ──> content_tsv（生成列）

② 检索（读路径）
   search_keywords("报销")
     ├─ tokenize("报销")            → ['报销']
     ├─ build_or_tsquery(['报销'])  → '报销'
     └─ SQL
          corpus      N=6, avgdl=...
          candidates  content_tsv @@ to_tsquery('simple','报销')  → 3 条候选
          df          报销 → df=3
          scored      IDF × 饱和TF ÷ 长度归一化 → 求和
        → ORDER BY score DESC, id ASC LIMIT 3
```

实测输出（D16 验证脚本）：

```
查「报销」→ ['d16-bm25-verify-tf10', 'd16-bm25-verify-short', 'd16-bm25-verify-long']
            （不含 'other' —— 它不含"报销"，被 ② 挡在候选集外）

长度归一化（tf 均为 1，唯一变量是长度）：
  short(dl=3)  score=1.095  >  long(dl=93)  score=0.3657     ← b=0.75 生效
词频饱和（tf 1 → 10，长度相近）：
  score 比值 = 1.305  （k1=1.2 时理论上限 k1+1 = 2.2）          ← k1 生效
```

两路检索对比（D17 的基线）：

| 查询 | BM25 | 向量 |
|---|---|---|
| `报销` | `['tf10', 'short', 'long']` | `['short', 'tf10', 'long']` ← **首位不同** |
| `灰度回滚` | `['other']`（只 1 条） | `['other', 'long', 'tf10']`（把无关长文档也排进来） |
| `上线前要做什么` | `['other']` | `['other', 'short', 'long']` |

**这两个例子正好是 RRF 存在的理由**：
「报销」一词上，BM25 偏爱高频、向量偏爱语义 → 排序分歧；
「灰度回滚」上，向量对字面无关的文档也给了分，BM25 精确定位到 1 条。

验证脚本结果：**26/26 通过**；全量回归 15 个脚本全绿。
