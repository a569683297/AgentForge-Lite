## §1 病：judge 拿"出题说明"当答案

### 1.1 现象

`tool_call` 类题（C01~C10）的 `eval_cases.reference`（参考答案）长这样：

```
C01  "应当调用 search_documents 工具完成该请求。理由：答案在知识库制度文档里，必须先检索"
C05  "应当调用 current_time 工具完成该请求。理由：问的是当前时刻，属于实时信息，知识库里没有"
C08  "不应当调用任何工具，直接回答即可。理由：闲聊兼能力询问，没有需要外部信息的成分"
```

**10 条题的 reference 全部是这个形态，没有一条写了答案内容。**

> `reference` = 参考答案，judge 判分时用来比对的标准答案；`eval_cases` 表里的一列。

### 1.2 铁证

C05 的完整对照：

| 项 | 内容 |
|---|---|
| 题面 | 「现在几点了？」 |
| `reference` | "应当调用 `current_time` 工具完成该请求。……" |
| **系统实际行为** | **调用了 `current_time` ✓，回答"现在是 2026 年 9 月 29 日 09:33:27。"✓** |
| **judge 判定** | **0 分** |

理由原文（judge 自己写的）：*"参考答案要求调用检索工具，待评答案直接给出了住宿费标准，未按要求执行"*。

**系统做得完全正确，被判失败。**

### 1.3 更关键的一点：判错了还是判不准？

查库里历史数据时发现一个比"判错"更严重的事实：

| 时机 | 题目 | judge 给的分 |
|---|---|---|
| D22 验收（`run_id=1`） | C01~C04 | **全部 5.0 分**，accuracy 100% |
| D23 诊断（`run_id=4/5/6`） | C01~C04 | **多处 0 分** |

**同样的题、同样的 `reference`、同样的 judge，两次的理解相反。**

这说明不是"judge 偶尔判错"，而是——**这个字段对 judge 而言，语义本身就是歧义的**。
一句"应当调用 X 工具"既可以读成"这题的要求是调 X"（→ 看行为），
也可以读成"标准答案是这句关于 X 的话"（→ 比文本）。judge 每次随机挑一种读法。

> 这就是为什么修法不能是"给 judge 换个更清楚的 prompt 措辞"——
> 措辞清楚解决不了"这一列同时承担两种含义"这个结构问题。

## §2 为什么它藏了这么久

三条结构性原因，每一条都单独成立：

**① 稳定的假失败比随机噪声更危险。**
C05~C08 在**三个配置下一致失败**，看起来像一个可靠信号（"系统在这类题上确实不行"）。
随机噪声至少会自己抖出来被人看见；稳态的偏差会被人当成事实记下来。

**② D22 的验收恰好避开了。**
`d22_verify.py` 的小规模实跑参数是 `category=tool_call, limit=4` —— 跑的正是 C01~C04，
而那一次 judge **全给了 5 分**，验收 60/60 全绿。**同一段代码、同一批题，换个时间跑就红**。

**③ 数据形状完全正常。**
C 类题 `reference` 平均 48 字（A 类 36、B 类 72），既不离群也不异常。
任何"看统计量"的检查都抓不到它——**只能读内容**。

**教训**：验收脚本全绿 ≠ 契约成立。D22 的 60 项断言验的是
"明细有行 / 字段能读回 / 分数落库了"，**没有一条验"分数是不是对的"**。
它验的是**机制**，不是**语义**。

## §3 为什么选乙而不是甲

两个候选方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲** | 把 C 类题的 `reference` 改写成真正的答案内容 | C05~C07 问"现在几点"，**答案不固定**，写不出可核对的标准答案；且改数据 → **评测集指纹变** → D21 校准的 ε 作废，要重新校准 |
| **乙** | **C 类题只判工具调用**（走 `tool_call_ok`），`reference` 不再给 judge 当答案 | 需要在判定层开一条"不判内容"的路径 |

选乙的三个理由：

**① 它符合 C 类题存在的意义。**
C 类题考的是"**会不会选对工具**"，不是"答得对不对"。答得对不对由 A/B 类题覆盖——
这是分工，不是漏测。

**② 修复前是半吊子，乙补上了对称的那一半。**
`derive_case_outcome` 原本已经写了这条：
*"C 类题 tool_miss 有否决权：答题侥幸对了也算不通过"*。
既然**"答案对"救不了 tool_miss**，那**"答案错"也不该拖垮 tool 对了的题**。
原来的实现只给了否决权，没给对称的通过权。

**③ 一个不显眼但很实在的收益：不用重算指纹与 ε。**
指纹（`dataset_fingerprint`，评测集的内容哈希）**覆盖了 `reference` 这一列**。
甲要改它 → 指纹变 → 所有引用旧指纹的地方作废 → D21 那轮 ε 校准（含第 1 轮作废重做）
要重来一遍。**乙不动任何数据行 → 指纹不变 → ε 继续有效。**

> 代价诚实记录：C 类题的 `reference` 仍然是"一个字段两种语义"
> （内容题是答案、工具题是出题说明）。它靠**代码分路 + 列注释 + 验收断言**防呆，
> 没有从数据上根除。要根除就得付甲的代价。

## §4 修复的核心设计：一个开关 + 唯一判据

改动的中心是一个判断：

> **这道题要不要判内容？** ⟸ 判据 = `expected_tool` 有没有被标注。

| `expected_tool` | 语义 | 判定路径 |
|---|---|---|
| `None` | 未约束工具（A/B 类题） | **内容题**：看分数 |
| `"__none__"` | 显式要求不调工具（C08~C10） | **工具题**：只看工具 |
| `"search_documents"` | 必须调用到它（C01~C04） | **工具题**：只看工具 |

### 为什么这个判断必须**只写一次**

这个判断同时被两个地方需要，而它们在两个文件里：

| 谁 | 拿它决定什么 |
|---|---|
| `eval_runner.score_answers` | **要不要给这题发 judge 请求**（发不发钱） |
| `failure_taxonomy.derive_case_outcome` | **拿不拿分数当判据**（认不认结果） |

如果两处各写一遍 `expected_tool is not None`，那么将来只要有一处被改成别的写法
（比如 `category == "tool_call"`），就会出现**静默分裂**：
runner 照常花钱打分、判定函数却不看那批分数——**花了钱、落了库、一个都没用上，
且不会有任何报错**。

这正是本项目反复踩的那条坑（同一判断两处写 → 两份真相）。
所以判据封成一个函数 `is_tool_only()`，两边都调它。

> **`开关字段`**：一个字段的"有没有值"被用来控制程序走向，而不是只当作数据。
> 它的风险是"看数据时看不出来它还是个开关"——所以必须写进列注释。

## §5 逐行：`failure_taxonomy.py`（判定层）

### 5.1 新增 `is_tool_only()`

```python
def is_tool_only(expected_tool: str | None) -> bool:
    return expected_tool is not None
```

三行。它的价值不在实现，在**它是唯一出处**（理由见 §4）。

### 5.2 `derive_case_outcome()` 加了分路

改动前后对比：

```
【改前】                           【改后】
if run_failed: → system_error      if run_failed: → system_error
if 分数缺失: → raise ValueError     if 工具不对:   → tool_miss
if 工具不对: → tool_miss            if is_tool_only: → 通过（不看分数）
if correctness >= 4: → 通过         if 分数缺失: → raise ValueError
if faithfulness <= 2: → 编造        if correctness >= 4: → 通过
if completeness <= 2: → 不完整      if faithfulness <= 2: → 编造
→ 答错                              if completeness <= 2: → 不完整
                                    → 答错
```

两处顺序变化，各有原因：

**① 分数缺失检查挪到了 `is_tool_only` 之后。**
否则不打分的工具题会被那句 `raise ValueError` 拦下——而它**本来就不该有分数**。
这就是"允许传 None"和"缺分数是错误"必须分开的原因。

**② `tool_miss` 仍然排在分数之前，而且排在 `is_tool_only` 之前。**
否决权对工具题和内容题都生效（内容题若被约束了工具，也要先看工具）。

### 5.3 一个刻意的保留

内容题缺分数**仍然抛 ValueError**。这条防线没被拆掉——
新增的 B16 断言专门钉住它（见 §9）。分路不等于放水。

## §6 逐行：`eval_runner.py`（编排层）

### 6.1 `score_answers()` 跳过工具题

```python
for row in answers:
    if row["run_failed"]:
        tasks.append([])                              # 没跑出答案 → 不打分
        continue
    if failure_taxonomy.is_tool_only(row["expected_tool"]):
        tasks.append([])                              # 工具题 → 不打分
        skipped += 1
        continue
    tasks.append([...create_task(judge)...])
```

两个细节：

- **用空 list 占位而不是 `continue`**：下面的 `zip(answers, grouped)` 要按**位置**对齐，
  少一个元素会让后面每一行都错位一格。错位不会报错，只会让每道题的分数**张冠李戴**。
- **`skipped` 计数并打印**：不打分是个"少做了事"的动作，
  必须让它出现在日志里（"0 次调用"如果不解释，会被读成"跑挂了"）。

### 6.2 结果处理从两分支改成三分支

```python
if row["run_failed"]:      → system_error，分数全 None
elif not results:          → 工具题：不传分数，走工具判定
else:                      → 内容题：聚合 → 判分
```

改前的写法是"run_failed 单独一套 + 其余一套"，第二套里硬编码调用了
`judge_service.aggregate(results)`——工具题的 `results` 是空的，会直接崩。
三分支之后每种情况各说各话，不再共用一段假装通用的代码。

## §7 逐行：口径层（`eval_service` / `api` / `schemas`）

工具题不贡献分数，于是 **`rows`（明细行数）不再等于"三维度均分的分母"**。

改前的代码其实**没错**（`mean_of` 会 `if v is not None` 跳过 NULL，
SQL 的 `AVG` 也自动跳过），错的是**分母是隐含的**：
报告里很容易写出"平均正确性 4.2 分（共 150 行）"——**那个 150 是错的，真实分母只有 120**。

这正是 D20 那条教训的又一次变体：**分母悄悄变小，而没人看得见**。

三处改动，让分母变得**可被引用**：

| 文件 | 改动 |
|---|---|
| `eval_service.summarize_results` | 返回里新增 `scored_rows`（有分数的行数） |
| `schemas/eval.py` | `EvalRunDetailOut` 新增 `scored_rows` 字段，说明里写明它是均分的分母 |
| `api/eval.py` | 详情接口填充它；docstring 从"两个口径"改成"三个口径" |

## §8 逐行：`d23_migrate.py`（把语义写进库）

### 8.1 明明没改表结构，为什么需要迁移

这次**没加列、没改类型**，改的是**列的语义**。而这次 bug 的根因恰恰是
"语义只存在于生产者的注释里，消费者不知道"——所以语义不能只写在 Python 里，
**必须让库自己能回答"这列是什么意思"**（`\d+ eval_cases` 就能看到）。

用 `COMMENT ON COLUMN`（给列写说明，存在数据库里，不是代码里）落地。

### 8.2 两个设计要点

**① 不写第二份注释文本。** 期望值全部从 ORM 元数据读：

```python
column = model.__table__.c.get(column_name)
out[key] = column.comment or ""
```

脚本只负责搬运。如果在这里再抄一遍注释，就变成同一句话两个出处——
改一处忘一处，正是本项目反复修的那个病。

**② 幂等证据 = "本次更新 N 列"，第二次跑必须是 0。**
先查当前值（从 `pg_description` 读，独立于 ORM），只有不同才 `COMMENT ON`。
打印那个 N 是**唯一能证明它真的做了事**的东西——否则一个空跑的循环
（循环体里啥也没干）也会打印"迁移完成"。

> **幂等**：同一操作执行多次，结果与执行一次相同。它是"可安全重跑"的保证，
> 也是这类脚本的自检手段——如果第二次跑还说"更新了 8 列"，说明第一次根本没生效。

### 8.3 作用域：只同步 8 列

```python
TARGETS = { ("eval_cases","reference"): "…", ("eval_cases","expected_tool"): "…", … }
```

**不做全表列注释大扫除。** 理由（D21 的清理作用域教训）：
迁移脚本的作用域必须与"这次改了什么"严格对齐。
顺手同步别的列 = 一次看不见的作用域外溢，跑完没人知道它还动了什么。

### 8.4 实测

```
[同步] 本次更新 8 列注释（目标 8 列）
[核对] 8 列注释全部与 ORM 一致
✅ 完成
--- 第二次跑 ---
[同步] 本次更新 0 列注释（目标 8 列）
✅ 幂等
```

`[核对]` 那一步是**回库查一遍**，不是信 `sync()` 的返回值。
判据始终是：**"我调了个函数"不是证据，"我回库里查了一遍"才是证据。**

## §9 逐行：`d22_verify.py`（两条路径都得有人验）

### 9.1 为什么必须改验收脚本

`d22_verify.py` 的实跑参数原本是 `category="tool_call"`——**正是被改的那一类**。
工具题不再打分后，原来两条断言必然为假：

| 断言 | 内容 | 改后 |
|---|---|---|
| C9 | `judge_runs` 都等于 3 | ❌ 工具题恒为 0 |
| C10 | `judge_raw` 是列表且长度 == `judge_runs` | ❌ 工具题是 NULL |

**处理方式不是删断言，而是分两轮：**

| 段 | 类别 | 验什么 |
|---|---|---|
| C/D 段 | `doc_qa`（4 题 × 2 生成 × 3 打分） | 打分链路：多次打分、原始分数落库 |
| **C2 段（新）** | `tool_call`（2 题 × 1 生成） | 新契约：不判内容、不调 judge |

只验其中一条，另一条坏了也不会被发现。

### 9.2 C2 段的 10 条断言

| # | 验什么 |
|---|---|
| T1 | 明细 2 行（2 题 × 1 生成） |
| T2 | `judge_runs` 全为 0 |
| T3 | 三个维度分数全为 NULL |
| T4 | `judge_raw` 为 NULL |
| **T5** | **`passed` == `tool_call_ok(expected_tool, tool_calls)`（逐行回库核对）** |
| T6 | 失败原因只可能是 `tool_miss` 或通过 |
| T7 | `judge_raw` 是真 SQL NULL（不是 JSON 字面量 `null`——D14 的坑） |
| T8 | 汇总里 `scored_rows=0` 而 `total_rows=2`（两个分母被分开了） |
| T9 | 准确率仍算得出（分母是题数，不受"不打分"影响） |
| T10 | 本段自建的 run 已自行清理（作用域自限） |

**T5 是整段最重要的一条**：它拿库里的行**重新算一遍**纯函数，比对 `passed`。
"跑通了"不等于"结论对"——只有回库核对才算验过。

### 9.3 B 段（纯函数）新增 6 条

| # | 验什么 |
|---|---|
| B11 | 工具题不传任何分数也合法 |
| **B12** | **工具题分数全 1 也通过** ← D23 修掉的假失败的最小复现 |
| B13 | `__none__` 题也走同一条路径 |
| B14 | 工具题的否决权仍然生效（不传分数也能判出 `tool_miss`） |
| B15 | 开关就是 `expected_tool` 有没有标注 |
| **B16** | **内容题缺分数仍然抛错** ← 修复的护栏：分路不能把防线一起拆了 |

### 9.4 E 段的一处顺带加强

E10 原本只验"按 `doc_qa` 过滤返回空"（负向证据）。类别调换后改成
"按 `tool_call` 过滤返回空" + **新增 E10b**"按 `doc_qa` 过滤返回全部"。
两条一起才说明接口真的在**按值筛**，而不是"恰好返回空列表"。

**T5 与 T8 是这次修复的核心证据**：

后者证明"分母被显式化了"（不是靠隐含）。

## §11 历史数据：作废，但不删

`run_id=4/5/6`（诊断那三条）里 C 类题的判定**是坏的**（假失败 13 条）。
处理方式：**不重算、不删除，标注作废**。

理由：

- **不重算**：那条 run 的汇总分（`eval_runs.accuracy`）已经落库。
  只改明细不改汇总 = 同一件事有两份数字，且**两份都"有来源"**，这是最难发现的一类错。
- **不删**：它是"量具不合格时会量出什么"的现场证据。
  仓库里已有先例——`D20-探针结果-第1轮.md` 的 ε 作废后同样保留原文。

**引用规则**：报告与总纲引用 A/B/C 成绩时，**只能用修复后重跑的 run**。

## 附录 B：一条可迁移的判据

> **字段的语义不能只写在生产者的注释里，消费者也要显式知情。**

这次的现场是：`_tool_case()` 的 docstring 明明写着"reference 说明期望行为"，
但下游 `build_prompt` 并不知道，于是把它标成【参考答案】发了出去。
**生产者的注释不构成契约。**

推广到别的场景：只要一个字段被两个角色以不同方式理解，
就应该在**字段自己身上**（列注释 / schema 说明 / 唯一判据函数）写清楚，
而不是指望"读代码的人会看见那句注释"。
