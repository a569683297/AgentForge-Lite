# 启动与更新操作手册（本地 + 远程）

> **本文是什么**：AgentForge-Lite 的「日常怎么启动、改了代码怎么更新」操作入口。
> 覆盖三件事：**本地启动**（使用/开发两种模式）、**本机 8080 更新**、**外网服务器更新**。
>
> **所有命令均于 2026-10-16 在本机与服务器实测通过**（记录见文末附录）。
> 部署环境从零搭建（买服务器 → 装 Docker → 上传 → 首次构建）见《部署手册-IP直连版-2026-10-15.md》；本文只管"搭好之后怎么用"。

---

## 0. 先懂一个概念：为什么 8080 改了代码不会自动变

**一句话**：`8080` 是**构建快照**，`5173` 是**实时源码**。

| 入口 | 是什么 | 改源码后 |
|---|---|---|
| `localhost:8080` | nginx 容器吐的**打包成品**（`npm run build` 的产物冻在镜像里） | ❌ 不动——必须**重新构建镜像**才变 |
| `localhost:5173` | vite dev **实时读源码**（热更新，改一下浏览器立刻刷新） | ✅ 秒变 |

类比你熟的流程：`vite dev`（开发服务器）vs `npm run build` 出来的 `dist` 部署到 nginx——
**改了源码不重新 build，8080 永远停在旧包**。这不是 bug，是"构建快照"的天性。

> 术语注解：**构建快照** = 打包那一刻冻结的静态文件集合；**热更新（HMR）** = 开发服务器监听源码变化，自动在浏览器里局部替换刷新，无需手动构建。

**所以要记住的操作口诀**：
- 开发、改代码 → 看 **5173**（实时）
- 演示、给别人看 → 看 **8080**（成品）→ 改完代码记得重建（见 §1.4）

## 1. 本地启动

### 1.1 全容器模式（日常使用 / 演示，一条命令）

```bash
cd /Users/779369901qq.com/workspace/bs/AgentForge-Lite
make up          # = docker compose up -d --build；起 db / redis / api / web 四个容器
```

启动后访问：

| 地址 | 内容 |
|---|---|
| <http://localhost:8080> | **前端界面**（从这里开始） |
| <http://localhost:18000/api/health> | 后端健康检查 |
| <http://localhost:18000/docs> | 接口文档（Swagger） |

**演示/首次使用前的初始化**（可选，但演示前强烈建议）：

```bash
make seed      # 灌 3 份示例文档进知识库（已就绪会自动跳过，幂等）
make warmup    # 预热外部 MCP 工具（首次要下载 npx 包，约 2-3 分钟；不跑则演示时当场卡）
```

**常用管理命令**：

```bash
make down      # 停容器（数据保留在卷里，重启不丢）
make ps        # 看容器状态
make logs      # 跟踪全部容器日志（Ctrl+C 退出）
make test      # 跑 pytest
make verify    # 跑全量回归脚本（日志落 logs/）
```

### 1.2 开发模式（写代码，改哪哪生效）

三个进程分开跑（终端 1 / 终端 2），依赖服务用容器：

```bash
# 依赖服务：只用容器里的 db + redis（若全容器模式已在跑，这步可跳过）
docker compose up -d db redis

# 终端 1：后端 —— 宿主机直接跑，代码热重载
cd /Users/779369901qq.com/workspace/bs/AgentForge-Lite
uv run uvicorn app.main:app --reload --port 8000

# 终端 2：前端 —— vite dev
make web-dev     # = cd frontend && npm run dev → http://localhost:5173
```

**开发时访问 <http://localhost:5173>**（前端 vite 会把 `/api` 代理到 `8000`）。

> ⚠️ **必须写 `localhost:5173`，不要写 `127.0.0.1:5173`**：vite 只监听了 IPv6 的 localhost，
> IPv4 的 `127.0.0.1` 会"拒绝连接"（2026-10-16 实测踩坑，查了半天）。

> **两个后端实例互相独立**（这是设计，不是冲突）：
> - `:8000` 宿主机 uvicorn —— **14 个工具**（含 harness 系列，需要宿主机 Node 用 npx 拉起）
> - `:18000` 容器 api —— **4 个工具**（容器里没有 Node，`MCP_HARNESS_ENABLED=false`）
>
> 演示"外部系统互操作"用 8000；容器形态 18000 是已知边界（README §4.3 / §8）。

> 术语注解：**热重载（--reload）** = uvicorn 监听 .py 文件变化自动重启服务；**代理（proxy）** = vite dev 把 `/api/xxx` 的请求转发给 8000 的后端，避免浏览器跨端口请求。

### 1.3 常用命令速查表

| 命令 | 干什么 |
|---|---|
| `make up` / `make down` | 起 / 停 全部容器（保留数据） |
| `make restart` | 重建并重启 |
| `make ps` / `make logs` | 容器状态 / 日志 |
| `make warmup` / `make warmup-dry` | 预热 MCP 工具 / 只查配置（秒级） |
| `make seed` / `make seed-clean` | 播种示例文档 / 删除它们 |
| `make test` / `make verify` | pytest / 全量回归脚本 |
| `make web-dev` / `make web-build` | 前端 dev（5173）/ 生产构建 |
| `uv run uvicorn app.main:app --reload --port 8000` | 本机跑后端（8000） |

### 1.4 改了代码，怎么让 8080 出新版

```bash
cd /Users/779369901qq.com/workspace/bs/AgentForge-Lite

# 只改了前端（frontend/）：
docker compose build web && docker compose up -d web

# 只改了后端（app/ scripts/ 等）：
docker compose build api && docker compose up -d api

# 两边都改了 / 不确定：全量（等同 make up 的构建部分）
docker compose up -d --build
```

**怎么确认更新真的生效**：

```bash
# 看 8080 页面引用的产物文件名有没有变（构建 hash 会变）
curl -s http://localhost:8080/ | grep -o 'assets/[^"]*'
# 或直接刷新浏览器页面看效果
```

## 2. 远程更新（外网服务器 118.89.150.64）

> 服务器目录：`/home/ubuntu/AgentForge-Lite/`；SSH 密钥：本机 `~/.ssh/agentforge_deploy`。

### 2.1 标准流程（改了任何东西都用这条，全量版）

```bash
# ① 在 Mac（项目根）——增量同步代码，秒级
cd /Users/779369901qq.com/workspace/bs/AgentForge-Lite
rsync -avzP -e "ssh -i ~/.ssh/agentforge_deploy" \
  --exclude '/.git' --exclude '/.venv' --exclude 'node_modules' \
  --exclude '/models' --exclude '/logs' --exclude '.pytest_cache' \
  --exclude '__pycache__' --exclude '*.pyc' --exclude '.DS_Store' --exclude '.coverage' \
  ./ ubuntu@118.89.150.64:/home/ubuntu/AgentForge-Lite/

# ② 在服务器——先停再构建起（避免内存叠加）
ssh -i ~/.ssh/agentforge_deploy ubuntu@118.89.150.64
cd ~/AgentForge-Lite
docker compose down && docker compose up -d --build && docker compose ps
```

### 2.2 轻量流程（只改一部分时，不停其他容器、中断最小）

```bash
# ── 只改了前端（本次 2026-10-16 实操用的就是这条）──
# ① 只同步 frontend/
rsync -avz --delete -e "ssh -i ~/.ssh/agentforge_deploy" \
  --exclude node_modules --exclude dist \
  frontend/ ubuntu@118.89.150.64:~/AgentForge-Lite/frontend/

# ② 服务器只重建 web
ssh -i ~/.ssh/agentforge_deploy ubuntu@118.89.150.64 \
  'cd ~/AgentForge-Lite && docker compose build web && docker compose up -d web'

# ── 只改了后端：把 ① 的 frontend/ 换成 app/（改了 scripts/ 同理），② 的 web 换成 api ──
```

> 术语注解：**rsync** = 增量同步工具，只传"有变化的部分"（本次前端只传了 ~20KB）；
> `--delete` = 让远端删除本地已不存在的文件（保持两边一致）；`-e "ssh -i ..."` = 走这条 SSH 密钥免密连接。

### 2.3 四个注意点（都是真实踩过的坑）

1. **排除项必须"锚定"**：`'/models'` `'/logs'` **要带斜杠**——不带斜杠会在任意层级匹配，
   会把 `app/models/`（ORM 代码包）一起排掉，容器直接崩（`ModuleNotFoundError: No module named 'app.models'`）。
2. **`.env` 会被覆盖**：标准流程会把**本机 `.env` 同步上去盖掉服务器的**。
   若服务器上单独改过 `.env`，同步时加 `--exclude '.env'`；只想更新前端时本就不会碰它。
3. **验证是否生效**：
   ```bash
   curl -s http://118.89.150.64:8080/ | grep -o 'assets/[^"]*'   # 产物 hash 变了 = 新版
   ```
4. **服务器重启后站点打不开**：db/redis 容器**没配开机自启**（设计如此），手动恢复：
   ```bash
   ssh -i ~/.ssh/agentforge_deploy ubuntu@118.89.150.64
   cd ~/AgentForge-Lite && docker compose up -d
   ```

### 2.4 服务器内存提醒（4G 机器）

- 构建/跑重任务时如果和 api 容器（重排模型 ~2.2GB）叠加，会挤爆内存——
  标准流程的"先 `down` 再构建"就是为了避免这一点。
- 跑评测等重任务前先确认可用内存：`free -h`（详见《部署手册》§9 故障排查）。

## 3. 故障速查（只看启动与更新相关）

| 现象 | 原因与处理 |
|---|---|
| 8080 还是旧版页面 | **没重建镜像**（§0 概念）；跑 `docker compose build web && docker compose up -d web` |
| `127.0.0.1:5173` 打不开 | vite 只监听 IPv6 → 改用 `localhost:5173` |
| 8080 / 18000 端口被占 | 本机有别的服务；改 docker-compose.yml 的 ports 左侧 |
| 页面能开、提问报错 | `.env` 的 `DEEPSEEK_API_KEY` 没填/无效 → 检查后 `make restart` |
| `make up` 后 api 一直 unhealthy | `make logs` 看 api 日志；常见是 `.env` 缺失导致连不上库 |
| 外网 8080 打不开但服务器内 `curl localhost:8080` 通 | 腾讯云防火墙没放行 8080（部署手册 §1.2） |
| 外网 api 反复重启日志报 `No module named 'app.models'` | rsync 排除模式没锚定（§2.3-1），修复后补传文件并重建 api |
