## Q1 · 一条 FAIL：真回归，还是旧账？（本阶段最有价值的一题）

> 背景名词：**回归（regression）** = 改完新功能后重跑既有测试，确认"没把原来好的弄坏"。
> 一条 FAIL 出现时，有两种完全不同的可能：**① 你的改动真弄坏了什么（真回归）**；
> **② 这条断言本来就是错的/过期的（旧账）**——D24 时期这叫"**验证脚本自身陈旧**"。

**L1**：S4 跑 5 个评测脚本时，`d23_metrics_verify` 报了 32/33（D5 失败：`语料文档数 12`，
期望 `== 8`）。你手上第一反应该是"模型切换改坏了什么吗？"——**用什么动作能在一分钟内
把它定性**是"真回归"还是"旧账"？（提示：这条断言是"什么时候、为什么"写下的？）

**L2**：定性为旧账后，修法是 `corpus_size == 8` → **`>= 8`**。为什么不是改成 `== 12`？
`>= 8` 保留了什么防线、放弃了什么防线？

**L3**：这个坑为什么**必须靠 git 历史判别**？（提示：现代码、库、断言三者里，哪个"看起来
都是对的"？）另外——如果将来有人"修复"这条断言时顺手把它**删掉**（理由是"它误报过"），
会丢掉什么？

<details><summary>参考答案</summary>

**L1**：动作 = **`git log -S "corpus_size == 8" -- scripts/d23_metrics_verify.py`**（追这行
断言的引入/修改历史）+ `git log -- scripts/d23_metrics_verify.py`（脚本整体最后一次动）。
追出来：该断言自 **D23（`6919f39`）引入后从未改过**，而语料在那个时间点之后**扩张过两次**
（10-09 D35 补 3 篇 → 11 篇；10-11 演示上传 1 篇 → 12 篇）→ **`== 8` 从 10-09 起就已经
必然失败**，今天的改动只是"第一次把它跑出来"而已。
一句话判据：**断言的"年龄"早于"环境变化"→ 旧账；断言要求的行为与本次改动的代码直接
相关 → 真回归。**

**L2**：`== 12` 是**把当前快照写死**——下次再补素材/再上传演示文档它就又红了，同一个坑
踩第二次。`>= 8` 保留的防线：**"语料被误删"仍会红**（掉到 8 篇以下），这正是原断言真正
有价值的一半（守住"D21 基础语料在库"）。放弃的防线：不再约束"上限"——但"语料变多"本来就
不是故障（D35 补素材、演示上传都是**既定行为**），不需要防。
判据：**断言的语义要跟着"什么是故障"走，而不是跟着"当时的数字"走。**

**L3**：因为三方**各自看都正常**——库里的 12 篇是对的（用户上传的素材）、新代码没碰语料、
断言只是"如实"打印 12；**没有任何一方"报错"**，它们只是"不再互相匹配"。只有拿 **git
历史**把"断言写下的时刻"和"环境变化的时刻"排到同一条时间线上，才能看出"谁过期了"。
（对比 L2 的反实例：删掉断言 = 把"误报"和"防线"一起扔了——**它误报过，但它也抓真问题**；
正确动作是**修口径**（`== 8` → `>= 8`），不是**删断言**。）

依据位置：操作现场在本次对话；结论已登记在 `docs/tutorials/README.md`「历史教程的过时点」
表末两行 + 说明段（"同族第二例"）。
代码定位：`scripts/d23_metrics_verify.py` 的 D5（含为什么是 `>=8` 的注释）。
</details>

## Q2 · 语料"同源"：为什么变了必须登记？

> 背景名词：**语料指纹** = 给全库文档切片算的一个哈希值，用来回答"**现在库里的教材
> 还是不是当初那本**"。**同源** = 报告/对照实验与当前库基于**同一批**文档（D39 的
> 前提 1 就是这个）。**`check_comparable()`** = 出报告前的守卫，三条校验之一是
> "三个 run 的语料指纹逐字相同"。

**L1**：这次 S4 发现当前库是 `1f67b67b…`（12 篇 / 312 片），而 10-10 消融报告写的是
`d1c88a2f…`（11 篇 / 82 片）。这个变化本身是"故障"吗？那它为什么必须**登记**？
`check_comparable()` 的守卫为什么拦不住这一类问题？

**L2**："正式消融报告与当前库不再同源"的**具体危害**是什么？把危害说成一句面试时
能讲的话（提示：想想"教材换了一本、考卷没换"这个比喻里，分数差变成了什么）。

**L3**：这次登记还发现第二层影响：**D39「同源」前提**也受了影响（Dify 侧灌的是 11 篇，
本项目现在 12 篇）。如果你负责 D39，实施前的处理路径有哪几种？各有什么代价？

<details><summary>参考答案</summary>

**L1**：不是故障——它是**合法演化的结果**（10-11 有意的演示上传，跟"误删"完全两码事）。
但必须登记，因为它**改变了所有引用数字的语境**：任何"拿旧报告说事"的地方（简历、
面试演示、下一次评测对比）默认的前提是"报告和库同源"，而事实上不再同源。
`check_comparable()` 拦不住的原因：它校验的是"**三个 run 之间**的指纹一致"（防"同一
批对比实验内部数据不齐"），**管不到"报告与当前库是否同源"**——后者是**跨时间**的问题，
只能靠**人**在报告里/日志里登记。（这正是 D35 那次"教材换了没人出声"的同型问题。）

**L2**：一句版："报告里的成绩差异，本来只归因于**检索配置**；现在库变了，差异里**混进了
'教材变了'这个新变量**——归因不再成立，且**不报错**。"
更完整一点：**任何"拿这批数字做决策"的动作**（选型、对比、写进简历的量级判断）都建立
在一个**不再成立的等价关系**上——数字本身没变、口径没变，但**分母/底料的所指变了**。

**L3**：至少三种路径（没有唯一正确答案，关键是说出代价）：
- **① 删掉第 12 篇（主系统原型文档）** → 回到 11 篇，与 D36 报告/Dify 侧重新同源。代价：删掉了一份演示素材；且有"删数据"的不可逆风险（需备份）。
- **② 补灌 Dify 侧**（把第 12 篇也灌进 Dify）→ 两边都是 12 篇、重新同源。代价：Dify 侧块数与 AgentForge 片数本来就"非逐片一致"（82 vs 88 块的经验），同源是"文档级"不是"切片级"；且 D39 对照实验需要重新核对基线。
- **③ 不追求全库同源，把 D39 的对照范围限定在"双方共有的 11 篇"** → 不删也不补。代价：对照结论的适用范围要写明"不含第 12 篇"，且要防它被检索命中（第 12 篇在库 = 评测/对照可能命中它，成绩不可解释）。

依据位置：`docs/tutorials/评测总纲.md` §4.5 / §4.5.1（两次登记的全文）+ 附录 C 指纹表。
</details>

## Q3 · 回归的"覆盖面"：为什么是这两批脚本？

> 背景：S4 的脚本回归跑了两批 —— **评测类 5 个**（`d21_delete_scope 27 + d21_eval 63 +
> d22 77 + d23_metrics 33 + d24_report 60 = 260`）与**对话链路 6 个**（`d7 网关 / d6 图 /
> d8 记忆 / d10 Agent+RAG / d11 HTTP / d14 会话`）。

**L1**：这两批各自的**问题**是什么？（提示：模型切换这次改动的"影响面"覆盖了哪些层？
哪一批测"链路行为"，哪一批测"数据与口径"？）

**L2**："`model_id` 不传 = 旧行为逐字节不变"——这句话在 S4 是**怎么被证实的**？
（提示：这 11 个脚本里，有几个传了 `model_id`？）为什么"逐字节不变"这个承诺要立得这么重？

**L3**：跑完回归后，还做了一步"**回库核对**"（查库里是不是恰好 12 篇 / 312 片）。
这一步防的是什么？为什么"12 个脚本全绿"**不能替代**这一步？

<details><summary>参考答案</summary>

**L1**：S2 改动的影响面 = `llm_gateway`（降级/调用）+ `agent_service`（双入口）+
`api/chat`（错误翻译）+ 记忆/会话链路（顺带被 touched 的行为）→ 所以**对话链路 6 个**
每个都"从某个角度真跑一轮/多轮对话"（网关降级、图路径、记忆滑窗、工具决策、HTTP 边界、
会话落库），覆盖"行为层"。
评测类 5 个不跑对话、只校验**数据与口径**（删除作用域 / 评测集与语料对齐 / 判定链路 /
指标函数 / 报告守卫）——它们要回答"**评测这套账本还是不是原样**"（评测体系是冻结的
资产，改对话链路绝不能悄悄污染它）。两批合计 260 + 对话链路全部通过。

**L2**：证实方式 = **这 11 个脚本全部不传 `model_id` 跑通**（它们写于模型切换之前，
调用方式是历史形态）→ 等于用**真实的历史调用方**验证了"默认路径没被改动波及"。
（加上 pytest 里**传与不传都覆盖**的用例、和 `d22_run --dry-run` 指纹一致的校验。）
承诺要立重的原因：**评测体系（D20-D24 的消融/报告）依赖"对话行为在冻结后不变"**——
如果默认路径被悄悄改了，**旧报告与新运行不再可比**（仪器被换了，刻度全废）。
"不传 = 旧行为"就是"**新功能的加入方式是无损的**"这句话的可执行版本。

**L3**：回库核对防的是"**脚本全绿但库被弄脏/弄空**"——脚本自身的清理可能有副作用
（D21 前车之鉴：7 个脚本删全库、51 片语料被删光，而脚本**不会报错**，因为它们测的
就是"删干净"）。"11 个脚本全绿"不能替代它的原因：**每个脚本只验证它自己关心的事**
（自己的断言范围），**没有一个脚本负责回答"整个库的终态是不是对的"**。
回库核对把"清理做对了"变成一个**可观测的整体状态**（恰好 12 篇 / 312 片），
而不是"我改了这里那里"的清单——**清单永远可能漏一项，状态不会**。

依据位置：本次对话的批次 A/B 现场；D21 教训见 `README.md` 第 440/450 行附近
（"跑一次全量回归就把 51 片语料删光"）与 `D21` 的删除作用域修复记录。
</details>

## Q4 · Langfuse 抽查：为什么要"造一轮真的"？

> 背景名词：**抽查（spot check）** = 从观测系统里抽取样本，核对"记录的内容与事实
> 是否一致"。**三源互证** = 用三个**互相独立**的观测点分别取证，交叉确认同一事实。

**L1**：S4 的抽查做法是**临时建一个自定义模型（指向假端点）→ 真调一轮 → 查 Langfuse
→ 删掉**。为什么不省事一点，直接翻 10-13 验收时期的历史 trace 就行？

**L2**：这次用了三个证据源：① Langfuse 的 trace（`agent-plan` generation，
`model=fake-model`）；② 响应里的 `model_used` 归因；③ 假端点自己的 `GET /last`
（`{"model": "fake-model", "stream": false}`）。各自的"视角"是什么？为什么
**一个源不够**？

**L3**：抽查完为什么要**删掉**临时模型？（提示：想一想如果留着会发生什么——
下次别人看 `GET /api/models` 时、以及 D39/演示时。）

<details><summary>参考答案</summary>

**L1**：三点：
- **时效**："现在这套代码 + 现在这套环境"能不能正确落到 Langfuse —— 历史 trace 证明的
  是"10-13 那个版本可以"，之后代码/配置可能漂移（这次抽查正好覆盖了 S4 的代码状态）；
- **完整性**：历史 trace 是别人跑的，你不知道当时用了什么参数、有没有其他变量；
  自己造的一轮**变量全在手里**（模型指向假端点 → 记录里必须出现 `fake-model`，这是一个
  **可判决的预期**：出现=记对了，不出现=埋点丢字段）；
- **可控性**：假端点回包固定（`pong`、usage 1/1），**任何偏差都能立刻归因**到链路上。

**L2**：三个视角：
- ① Langfuse = **观测系统内部**（埋点层）的视角——它证明"埋点结构正确、字段值正确"；
- ② 响应 `model_used` = **业务出口**的视角——用户实际能看到的那份归因数据；
- ③ 假端点的 `/last` = **网络层/被调用方**的视角（独立进程）——证明"请求**物理上**
  真的带着 `model=fake-model` 打到了它"。
一个源不够：①若埋点写错（比如硬编码），它会自说自话；②若后端把"用户选了什么"直接
抄进归因（而不是"实际执行者"），它也会显示 fake-model，但没证明请求真的发出去了；
③是**外部证人**——它记录的是"我收到了什么"。**三者同一才排除"系统内部自洽但实际
没发生"**。（D26/D27 的老教训："自己填进去的值"是循环证据。）

**L3**：不删的后果：
- `GET /api/models` 里会多一个**指向 127.0.0.1:18923 的假模型**——但假端点进程一旦停了，
  这个模型就是"看起来能用、一测就失败"的脏数据；它还会出现在**下拉框**里被误选；
- D39/演示时，库里的状态与文档记录不一致（又是一次"未登记的变更"——正是 Q2 的坑）；
- 判据：**抽查是"运行期的临时状态"，跑完必须回到"声明过的稳态"**。"造数据 → 验证 →
  清理 → 核对清理结果"是一个完整动作（这次清理后列表只剩 2 个内置模型，已核对）。

依据位置：本次对话的抽查现场（trace 详情 + `/last` 输出 + 删除后列表核对）；
同类原则见 `README.md` 铁律"回归脚本可能带破坏性副作用"一段。
</details>
