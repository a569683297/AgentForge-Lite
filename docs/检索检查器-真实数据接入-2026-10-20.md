# 检索检查器：接入真实数据（2026-10-20）

> 一句话：这一页以前画的是 20 条手写数字，现在画的是**库里真实文档的真实检索过程** ——
> 候选池 20 条、融合名次、重排前后的名次变化、以及有没有命中标准答案文档。

## 1. 改之前是什么

`RetrieverPage.tsx` 读 `frontend/src/mock/index.ts` 里的 `MOCK_RETRIEVAL`：

- 20 条全是 `Array.from` 生成的假数据，文件名是轮换的 4 个
- 「检索」按钮**没有 `onClick`**
- top-k 选择器 `value={5}` 是**硬编码常量**，连 `onChange` 都没有
- 输入框只改 `useState`，没有任何请求
- 页头挂着一枚「示例数据」徽章

后端侧也没有任何检索接口：`app/api/` 全目录 grep 不到 retrieval / search 路由。

所以这不是"接一下就行"的事 —— **页面和接口两头都不存在**。

## 2. 这一页到底要回答什么

设计文档（`DESIGN.md §8.4` / `IMPL-SPEC.md §5.7`）给了四条：

1. 每次检索返回 top-k（默认 5），每条带来源文档名和名次
2. **重排前后并排显示**（候选池 20 → 最终 5，这是一次真正的取舍）
3. 分数必须标明是 logit，不是概率
4. 命中 gold 用色点，不用整行染色

把四条翻译成一句人话：**要能回答"为什么是这 5 条、凭什么"。**

评测只能告诉你"Hit@k 掉了 8 个点"，不能告诉你掉在哪一步 —— 是向量路没找到、
是 BM25 召回了但被融合压下去、还是重排把对的那条挤掉了。这一页补的就是这个。

两条文档没明说、但落地时必须处理的需求：

- **金标准（gold）从哪来**：自由输入的问题没有标准答案文档。只有关联到评测题才有。
- **非重排配置怎么显示**：`pure_vector` / `hybrid` 根本没有重排，"重排后"那一列不能是空的。

## 3. 真实链路有什么、缺什么

`retrieval_service.py` 能给出：`content` / `source` / `page_ref` / `similarity` /
`rrf_score` / `vector_rank` / `bm25_rank` / `bm25_score` / `rerank_score`。

三个缺口：

| 缺口 | 症状 | 本项目的解法 |
|---|---|---|
| `retrieve()` 只返回最终 top_k，候选池 20 条没有出口 | 画不出左列 | API 层复刻 hybrid_rerank 分支：`hybrid_search(q, 20)` → `rerank(q, fused, 5)`（两个都是公开函数） |
| `rerank()` 只返回 `paired[:top_n]`，被淘汰的 15 条 logit 算完即丢 | 说得出"没进前 5"，说不出"掉到第 12" | 给 `rerank()` 加 `return_all`（默认 `False`，主链路零影响） |
| gold 只存在 `eval_cases`，`documents` 表没有 slug 列 | 色点无从判断 | 按 `case_key` 查 `doc_ids`，用 chunk → document_id 映射比对 |

## 4. 接口

### `GET /api/retriever/options`

```json
{ "configs": ["pure_vector", "hybrid", "hybrid_rerank"],
  "default_config": "hybrid_rerank", "max_top_k": 20, "default_top_k": 5 }
```

为什么单开一个接口而不是前端写死：配置名对 `RETRIEVER_CONFIGS`、
`max_top_k` 对候选池宽度、默认值对 `settings` —— 三处都有硬约束的另一端。
前端硬编码一份，后端改一处，页面就会拿一个不存在的配置名去请求，
收到 400 而不是"选项里没有它"。

### `POST /api/retriever/search`

```jsonc
// 入参
{ "query": "年假有几天？", "top_k": 5, "config": "hybrid_rerank", "case_key": "A01" }

// 出参（节选）
{
  "requested_config": "hybrid_rerank",
  "effective_config": "hybrid",          // 实际走通的路径（降级时不是请求的那个）
  "reranked": false,
  "degrade_reason": "重排未生效（超时 / 推理异常 / 分数条数不匹配）…",
  "score_kind": "rrf_score",
  "candidate_k": 20,
  "timings": { "retrieve_ms": 100, "rerank_ms": 3008, "resolve_ms": 20, "total_ms": 3130 },
  "candidates": [
    { "pool_rank": 1, "chunk_id": "12", "doc_id": "…", "source": "员工带薪年休假…md",
      "content": "…", "score": 0.0328, "rrf_score": 0.0328, "similarity": 0.87,
      "vector_rank": 1, "bm25_rank": 3,
      "rerank_rank": 1, "final_rank": 1, "rerank_score": 6.953, "is_gold": true }
  ],
  "gold": { "case_key": "A01", "doc_slugs": ["annual-leave"], "has_gold": true,
            "expected_count": 1, "hit_count": 1, "hit": true, "hit_rank": 1, "mrr": 1.0 }
}
```

错误码：`400` 配置非法（正常被 pydantic 的 422 提前拦下，只有脚本调用会走到）、
`404` 题号不存在、`422` 参数越界、`200` + `candidates=[]` 表示知识库为空（**不是错误**）。

## 5. 四个关键设计决策

### 5.1 三个名次必须分开，不能合成一个 `rank`

| 字段 | 含义 | 谁在用 |
|---|---|---|
| `pool_rank` | 候选池名次（融合序） | 左列的行序 |
| `rerank_rank` | **重排后的完整名次**（1..20） | 箭头 `↓7`、`↑3` |
| `final_rank` | 最终 top-k 名次（只有前 k 条有） | 右列的行序 |

合成一个的后果不是报错，而是右列悄悄变成 20 行 —— 页面看上去更"完整"，
但"从 20 里挑 5"这个过程就再也看不出来了。`test_final_rank_only_covers_top_k` 钉住它。

### 5.2 四种分数各自独立成字段，不合并成 `score`

余弦 ∈ [0,1]、BM25 无上界、RRF 是 `1/(60+名次)` 累加（0.016~0.033）、logit 跨查询不可比。

原先 mock 里"重排前也显示 logit"是**错的** —— logit 是 reranker 算出来的，
只有重排之后才有。真接上去，左列数字会从 `1.92` 变成 `0.0249`，
不解释的话看起来像坏了，其实是换了量纲。

左列标题写 `RRF 融合分`、右列写 `重排 logit`，两者都不是"分数"两个字能概括的。

### 5.3 gold 是三态，不是布尔

| 值 | 含义 | 页面表现 |
|---|---|---|
| `null` | 没选评测题 | 不画色点（画灰点会被读成"全都没命中"） |
| `false` | 有 gold，但这条不是 | 灰点 |
| `true` | 命中 | 绿点 + 左边框 |

另外：50 条题里只有 35 条有 `doc_ids`。**负例**（正确答案是"库里没有"）与
**工具题**（判定依据是"有没有调对工具"）按定义就没有依据文档，
它们的 hit/MRR 算出来必然是 0，算进去等于凭空拉低检索指标。页面会明写原因。

### 5.4 gold 判定用文档级去重（与 D23 一致）

一篇文档切 300 字一片，能切出几十片。同一篇命中的多个切片只记**最早名次**：

```
命中片段（按最终名次）: [d1第1, d1第2, d2第3]
不去重 → hit_count = 3    → 分母只有 2 篇，却"命中 3 篇"
去重后 → hit_count = 2，最早第 1 名，MRR = 1.0
```

不去重会让 Hit@k 虚高，而且跨文档题的"两篇都捞到"永远为假
（第二篇被第一篇自己的切片挤出窗口）。`test_gold_dedupes_by_document` 钉住它。

## 8. 一个真实的部署问题（必须知道）

容器内重排 20 条候选耗时 **2.4~3.0 秒**，而 `rerank_timeout_s` 默认 **3.0 秒** ——
**贴着超时线跑，偶发降级**。实测 8 次里 2 次降级。

为什么会慢：`D18` 记录的 750~820ms 是本机原生跑的成绩；容器里走的是 Docker Desktop
的 Linux VM + arm64 ONNX，慢 3 倍左右。

这不是页面引入的问题 —— **真实对话同样受影响**：重排一旦超时，
Agent 拿到的就是融合序而不是精排序，而用户（和评测）看不出区别，
只是 Hit@k 悄悄变差。

页面这次把它变成了**可见的**：`degrade_reason` 会明写"右列退回融合序，分数不是 logit"。
以前这条信息只在日志里，没人看。

三条路可选，本次**没有擅自改**：

1. 调大 `RERANK_TIMEOUT_S`（比如 8）—— 代价是真实对话最坏等 8 秒
2. 减小候选池（20 → 10）—— 代价是重排能纠正的空间变小
3. 给 api 容器更多 CPU / 换更小的 reranker 模型

## 9. 仍然没做的

- **点不到 Trace 页**：这一页发起的检索有独立的 `retriever_inspect` span，
  但页面没有"跳到这条 trace"的链接（`trace_id` 没回传）
- **不能对比两次检索**：改了 top-k 或配置只能重新跑，看不到"上一组 vs 这一组"的并排
- **正文只显示命中片段**，不能顺带看它所在的整篇文档（那是知识库页的事）
- **case_key 之外的 gold 形态**：只支持评测题，不支持用户手动标注"我认为应该命中哪篇"
