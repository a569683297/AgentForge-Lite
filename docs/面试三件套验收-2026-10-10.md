## §2 第一件 · 评测报告

### 2.1 交付物

| 项 | 值 |
|---|---|
| 报告文件 | [`docs/eval-report-2026-10-10.md`](eval-report-2026-10-10.md)（D36 正式消融，`generation_runs=3`） |
| 生成器 | `app/services/eval_report_service.py` + 入口 `scripts/d24_report.py`（**零 LLM 调用**，只读 `eval_runs` / `eval_case_results`） |
| 涉及 run | `26`（pure_vector）· `27`（hybrid）· `28`（hybrid_rerank） |
| 消融自变量 | 只有 `settings.retriever_config` 一个（其余全同：同一 judge、同一 rubric、同一阈值、同一评测集、同一语料） |

### 2.2 S1 评测集规模（实测）

原句：`≥ 50 条（3 类）`。实测取自 `/api/eval/dataset`：

```
total = 50
by_category = { doc_qa: 30, cross_doc: 10, tool_call: 10 }
by_difficulty = { easy: 21, medium: 22, hard: 7 }
negative = 5        # 「文档中无答案」的负例，测幻觉控制
covered_slugs = 8    # 覆盖 8 个主题文档
```

→ **50 条 / 3 类 → 达标。**

### 2.3 S2 与 S3（实测）

| 配置 | run | 准确率（按题） | 通过/总题数 | 结论 |
|---|---|---|---|---|
| `pure_vector`（向量 top5） | 26 | **98.00%** | 49/50 | — |
| `hybrid`（BM25+向量 RRF top5） | 27 | **98.00%** | 49/50 | — |
| `hybrid_rerank`（RRF top20 → 重排 top5） | 28 | **98.00%** | 49/50 | — |

- **S3**：98.00% ≥ 88% → **✅ 达标**。
- **S2**：`hybrid_rerank` − `pure_vector` = **+0.00 个百分点** → **❌ 未达标**。
- ⚠ **按题相同 ≠ 按行相同（本轮最好的一个反例）**：**按题**三配置完全一致（98.00%，逐题判定 50/50）；
  但**按行**的正确性均分是 **4.925 / 4.933 / 4.942**（单调递增）。
  → 拿"均分一路上升"去讲「重排略好」，就是**把行级抽样差异当成了题级结论**。
  **两个口径各自都对，互相印证就错**（本节 §2.4 的 S5 也出现过同型现象）。
- ⚠ **这个 0 差异不能读成「重排无用」** —— 三条理由（可复核）：
  1. **检索层已撞天花板**：三配置的 `Hit@1/Hit@5/Hit@10` 全 **100%**、`MRR` 恒 **1.000**（35 道可算题）；
     配置之间**没有可改进的空间**——不是重排没起作用，是**没有一道题给过它发挥机会**。
  2. **评测集区分能力不足**：题由制度条款轻度改写，语料中**每个主题只有一篇文档** →
     「找对文档」对三种配置都不构成挑战。
  3. **量具坏的这种可能已排除**：随机基线 `Hit@5` 只有 4.5%~9.4%，`d23_metrics_verify.py` 33/33 全绿。
- → **正确的说法**：「在当前这份评测集上，三个检索配置**不可区分**；瓶颈是**任务难度**，不是检索配置。」
- **可量化的改进判据**：让 gold 文档在**融合序**里的名次落进 **6~20** 区间（唯一能区分 B 与 C 的区间）→ **实测当前 0/35**。

### 2.4 S5 引用覆盖率（**本轮首次实测**）

原句：`≥ 90% 答案含引用且可定位`，验证方式 = **评测报告**。
⚠ 查证发现：**D24 那份报告并没有覆盖 S5**（全仓 grep「引用覆盖率」只在 PRD 与资产清单里出现）
→ 这是本轮补上的一个**取证缺口**。

**本仓自测口径**（必须写明，否则数字对不上）：

| 项 | 定义 |
|---|---|
| 分母 | **内容题**明细行（`doc_qa` + `cross_doc`）；`tool_call` 类题不产生引用，排除 |
| 「含引用」 | `answer` 里出现 `[n]` 形式的引用标记 |
| 「可定位」 | 出现的**每个** `n` 都落在 `1..sources_count` 内（越界的会进 `/api/chat` 的 `invalid_citations`，定位不到） |
| 符合 | 含引用 **且** 可定位 |

**实测**（直查 `eval_case_results`，run 26/27/28 的 360 条内容题行）：

| run | 内容题行 | 含引用 | 可定位 | 达标率 |
|---|---|---|---|---|
| 26 `pure_vector` | 120 | 119 | 119 | 99.17% |
| 27 `hybrid` | 120 | 119 | 119 | 99.17% |
| 28 `hybrid_rerank` | 120 | **120** | **120** | **100.00%** |
| **合计** | **360** | **358** | **358** | **99.44%** |

**越界引用（定位不到的）行数 = 0** → **99.44% ≥ 90% → ✅ 达标**。

> 复现脚本见 §7。⚠ 全批 360 行中有 **2 行「无引用」**（run 26/27 各 1 行，**同一道跨文档题**：
> 答案以叙述为主未挂编号），**不是系统性缺陷**；run 28 同题给出了引用 → **三配置间 1 行的差别本身也是生成侧抖动的表现**（§6.6）。

### 2.5 ⚠ 语料指纹变更登记（**D35 起的一笔未登记账，本轮结清**）

| 指纹 | 报告（旧）声明 | 当前库实测 |
|---|---|---|
| 评测集（题） | `a7797b06…b90afe` | `a7797b06…b90afe`（**未变**，仍是 50 题） |
| 语料 | `5783a666…bbdcc9`（8 篇 / 51 片） | `d1c88a2f…e833ff`（**11 篇 / 82 片**） |

- **差额 = 31 片**，正是 **D35 补的三份演示素材**（`data/sample_docs/` 3 文件 / 9+9+13 片）。
- ⚠ **这笔变更此前从未被登记**：D35 教程、10-09 工作日志、项目记忆里「指纹」一词**零命中**
  → 旧报告与当前库**不再同源**，而**没有任何地方写着这件事**。
- **本轮处理**：D36 的正式消融（run 26/27/28）**跑在当前库上**，其 `corpus_fingerprint` 已是
  `d1c88a2f…`；新报告自动记录新指纹 → **报告与库重新同源**。
- **登记去向**：本节 + D36 教程「口径变更」段 + `docs/tutorials/README.md` 的「历史教程过时点」表。

> **为什么必须这么较真**：`eval_report_service.check_comparable()` 的三条守卫里，
> 第二条就是「语料指纹逐字相同」。指纹变了而没人登记，等于**教材换了一本、考卷没换**——
> 分数差里混进了「教材变了」这一项，**归因不再成立**，而且**不会报错**。

## §3 第二件 · Langfuse 追踪演示（S6）

### 3.1 结论

| 项 | 判定 |
|---|---|
| 追踪**通道**可用（数据能读回来） | ✅ 已取证（§3.2） |
| 追踪**在实时写入** | ✅ 已取证（§3.2） |
| 一次对话的**完整调用树**被记录 | ✅ 已取证（7 种 span，§3.2） |
| 「**100%** 对话可追踪」这个**目标值** | ⚠ **未完全验证** —— 见 §3.3 |

### 3.2 实测证据

1. **实时写入**（2026-10-10 14:03，本会话实测）：
   拉 `/api/public/observations`（窗口 = 当天），返回的 50 条 observation
   **全部**是 `eval-judge` （type=`GENERATION`）——正是**当时正在后台跑的正式消融**产生的。
   → 说明追踪**不是历史存量，是活的**。
2. **完整调用树**（本会话早前实测，100 条 obs）：覆盖 **7 种 span** ——
   `run_agent`（根）· `agent-plan` · `agent-answer` · `retrieval` · `vector_search` ·
   `embedding` · `tool:search_documents`。
   → 一轮对话从**入口 → 规划 → 检索 → 生成 → 工具**全链路都有 span，**不是只记一条**。
3. **结构性保证**：根 span `run_agent` 包住整轮 Agent 调用（`agent_service.py` 的 `root_span`），
   所以**每次 `run_agent` 必然产生一条 trace** —— 这是「100% 对话可追踪」的设计依据。

### 3.3 ⚠ 本轮发现：取数通道撞上云端限流（**如实记录**）

用 D28 的取数通道（`app/services/langfuse_client.py`）读当天全量时，**第一次就被 429 挡住**：

```
Langfuse 返回 429: {"message":"Rate limit exceeded for GET /api/public/observations.
  Use GET /api/public/v2/observations?fromStartTime=<from>&toStartTime=<to>
  for high-volume reads.","code":"rate_limited", ...}
```

- **含义**：本项目取数通道用的是**旧端点** `/api/public/observations`，Langfuse 已对它限流，
  官方在报错里直接给出替代品 `v2/observations`。
- **影响面**：不影响追踪**写入**（写入正常）；影响**大窗口回读**（≥ 200 条时就可能被挡）。
  → 对演示无碍（演示只读小窗口），对「按天做数据分析」是**已知限制**。
- **处理**：本轮**只记录、不改代码**（改端点属新功能，撞 PRD L1524 红线 #3「D19 后冻结后端新功能」）。
  登记为**偏差候选**，留给 M8 语义层（PRD F11 / S15）那一步一并处理——那一步本来就要按天取数。
- ⚠ **未验证项**：「100% 可追踪」在 Langfuse 不可达时会怎样（上报是 fail-open 还是 fail-closed）
  **本轮没有验证** —— 不写结论。

→ 这是「外部工具真的被调用了」的**最强证据类型**：**输出内容与外部系统的真实状态一致**。

## §5 顺带结清：D36 修掉的缺陷 —— `/api/chat` 漏传 `tool_calls`

> 本节只记**证据与判定**；改动细节（为什么这么改、踩了什么坑）在 D36 教程。

### 5.1 症状与根因

| 项 | 内容 |
|---|---|
| **症状** | `POST /api/chat` 的响应里 `tool_calls` **恒为 `[]`**，而同一轮 Langfuse / PG 里**明明有工具调用** |
| **根因** | `app/api/chat.py` 构造 `ChatResponse(...)` 时**漏传 `tool_calls=result.tool_calls`**；该字段 `default_factory=list` → **静默兜成 `[]`**，**不报错、不崩溃** |
| **性质判定** | **修 bug，不是新功能** → 不撞 PRD L1524 红线 #3（「D19 后冻结后端新功能」） |

### 5.2 六步证据链（怎么定位到的）

| # | 动作 | 结果 |
|---|---|---|
| ① | 核字段名 | `ChatResult.tool_calls` / `ChatResponse`（继承）**都存在**，不是命名问题 |
| ② | 直接 POST `/api/chat` | 键名齐全，`tool_calls = []`、`sources = 0` |
| ③ | 查 Langfuse observations | **有 `tool:harness_describe`（type=TOOL）** → 工具**真被调了** |
| ④ | 查 PG `messages`（chat 全量落库） | **4 次 chat 全部有 tool_calls**（`harness_status+harness_list` / `harness_list` / `harness_describe` ×2），标准 OpenAI `function.name` 格式 |
| ⑤ | 手写脚本复现 `run_agent` 的提取逻辑 | `tool_names = ['harness_describe']` → **服务层提取正确**，排除服务层 |
| ⑥ | 读 `app/api/chat.py` | ★ **根因**：`ChatResponse(...)` 漏传 `tool_calls` |

> **方法论**：②③④⑤ 是「**逐层排除**」——先证「工具有被调」，再证「服务层提取对」，
> 最后**只剩出口那一层**。这样定位到的根因**不需要猜**。

### 5.3 影响面（实测）

| 受影响 | 说明 |
|---|---|
| **前端实时对话的「工具卡片」** | 永远不显示（`ChatPage.tsx:77` `tools: toolCallFactory(response.tool_calls)`，**完全依赖这个字段**） |
| **但历史消息路径不受影响** | `/api/sessions/{id}/messages` 读 PG，PG 里有值 → 表现为「**实时看不到、刷新后出现**」，**最容易被误判成前端 bug** |
| **演示脚本第 4 段** | 打 ✅ 却显示「（无）」——**假绿**（判据只看前置是否装载，不看 `tool_calls` 是否非空） |
| **S10 的验收证据** | 「工具可被发现**并成功调用**」的**演示脚本这一侧读不到工具调用** → 证据受损 |
| **评测** | ✅ **不受影响** —— 评测直调 `run_agent`（不经 HTTP） |

### 5.4 修法与验证（都做完并实测通过）

| # | 动作 | 验证 |
|---|---|---|
| 1 | `chat.py` 补 `tool_calls=result.tool_calls` + 更新 docstring + 加「这一行不能省」注释 | ✅ |
| 2 | 新增防回归用例 `tests/integration/test_api_endpoints.py::test_chat_forwards_every_chatresult_field_to_http`（**哨兵值法**） | ✅ **故意易红验证**：临时撤掉那行 → 用例**确实变红**（`assert [] == ['SENTINEL_TOOL']`）；恢复 → 12 passed |
| 3 | `scripts/demo.sh` 第 4 段改**分层判据** | ✅ `bash -n` 过；判据逻辑 4 例单测全符合（harness→✅ / 本地工具→⚠ / 空→❌ / 缺键→❌） |
| 4 | 端到端：`POST http://localhost:8000/api/chat` | ✅ 返回 `tool_calls = ['harness_describe']`（**这一发本身就是 S10 的强证据**） |

### 5.5 ⚠ 为什么「键集合比对」这类断言**抓不到**这个 bug（值得记住）

给返回模型加字段时，漏传的字段会被默认值**静默补齐**，而
**pydantic / FastAPI 序列化会带上默认值** → 漏传的字段**在 JSON 里照样出现**（只是值为默认）。
所以「断言响应键集合 == 模型字段集合」对这个 bug **恒真**，抓不到。
→ **正确做法：哨兵值法**（让桩返回每个字段的哨兵值，再断言能原样读回）。
