## 第 1 题：为什么指纹要算原始字节，而不是解析后的文本？

**答：因为「解析」这一步本身会失败，也会变。**

### 1.1 算解析文本，failed 记录永远拿不到指纹

去重的前提是「上传时就能算出一个指纹，拿去和库里比对」。

如果指纹来自解析文本，那么计算顺序是：

```
收到字节 → 解析 → 得到文本 → 算 sha256 → 查重
```

而解析恰恰是最容易出错的一步：坏 PDF、加密 PDF、扫描件（提取不到文字）、DOCX 结构异常。

```
收到字节 → 解析 ✗ 抛异常 → 后面三步全部不执行
```

结果：这条记录 `status=failed`，`content_hash` 是 NULL。用户拿同一个文件再传一次 ——
新请求同样在解析阶段失败，同样算不出指纹，**永远匹配不上那条 failed 记录**。

于是每重试一次就多一条 failed 记录，库里堆的全是同一份文件的尸体。
而「失败后重传」正是要解决的两个场景之一，算文本等于把它从根上废掉。

算原始字节则没有这个问题：`sha256(bytes)` 在解析**之前**就能算完，
坏文件、加密文件、扫描件一样有指纹，一样能命中历史记录。

### 1.2 解析器的输出不稳定，指纹会漂移

解析文本是**代码的产物**，不是文件的属性：

- 今天 `_parse_docx` 只读 `document.paragraphs`，明天修好表格解析（块 3 就要做），同一份 DOCX 会解析出更多文字
- `pypdf` 升级后，同一份 PDF 的换行、空格、页眉页脚处理都可能变
- 切片参数（chunk_size / overlap）一变，拼回去的文本也不一样

只要其中任何一项变了，同一份文件在升级前后算出的 hash 就不同 → 去重失效，
用户会看到「这份文档明明传过，怎么又进去了」。

原始字节是文件的物理属性，不会因为我的代码改动而变化。

### 1.3 反面场景：算文本还会**误判**重复

现在 DOCX 表格是丢的（已实测：3×2 表格一个字都不剩）。
如果算解析文本，两份**表格内容完全不同**的文档（比如两个部门的报销标准），
正文一模一样、只有表格不同 → 解析文本完全相同 → hash 相同 → 第二份被判定为「已存在」直接拒收。

这是比「漏判」更糟的错误：漏判只是多存一份，误判是**用户的文件根本进不来**，而且提示"该文档已在知识库中"，用户无从理解。

### 1.4 代价，以及为什么可以接受

用字节做指纹，代价是：**同一份内容用 Word 重新导出一次（字节变了、文字没变），会被当成两份文档。**

接受这个代价的理由：

1. 重新导出在你的工作流里通常意味着「改过内容」，本来就该作为新版本入库
2. 反过来（内容真变了但字节没变）在物理上不可能发生 —— 字节相同必然内容相同，这是 sha256 的性质
3. 真正的「同一份文件」场景（拖两次、双击上传按钮、刷新页面重传）字节是完全一致的，100% 能识别

一句话：**宁可多存一份真文档，不可错拒一份新文档。**

## 第 2 题：failed 复用为什么要带 `WHERE status='failed'`？

**答：因为「读到的状态」和「写的时候的状态」之间有时间差，条件更新是唯一能把这两步合成原子的写法。**

### 2.1 不用 CAS 会发生什么

CAS（compare-and-swap，比较并交换）在这里就是「把读到的旧状态写进 UPDATE 的 WHERE 里，
只有状态还没被人改过，更新才生效」。

假设两个请求同时到达（前端双击、两个标签页、用户手快点了两次重试）：

```
请求 A：SELECT → 查到 id=X，status=failed
请求 B：SELECT → 查到 id=X，status=failed      ← 两条都读到了同一个旧状态
请求 A：UPDATE documents SET status='processing' WHERE id=X   → 影响 1 行，成功
请求 B：UPDATE documents SET status='processing' WHERE id=X   → 影响 1 行，成功
```

单看 UPDATE，两条都「成功」了 —— 因为 `WHERE id=X` 对当前状态**没有任何要求**。
真正的后果是两个后台任务并行跑同一份文档：

| 后果 | 具体表现 |
|---|---|
| 切片写两遍 | 两个任务各自从 `chunk_index=0` 开始插入，同一份文档出现两套编号重叠的切片 |
| `chunk_count` 互相覆盖 | A 写 40，B 写 40，最后是 40 —— 但表里实际有 80 行 |
| 检索出重复片段 | top_k=5 可能被同一段内容占掉 2-3 个名额，挤掉其他文档 |
| embedding 白算一遍 | CPU 密集任务翻倍，把正常检索请求也拖慢 |

注意这里**没有任何报错**。这才是它危险的地方：状态是 ready、切片数看着正常、日志里两条「入库完成」，
只有检索质量悄悄变差了。

### 2.2 加了 CAS 之后

```sql
UPDATE documents
   SET status='processing', error_message=NULL, chunk_count=0, filename=:name
 WHERE id = :id AND status = 'failed'
```

这条语句是**单条 SQL**，PostgreSQL 执行时对该行加行锁。两个请求的时序变成：

```
A：UPDATE ... WHERE id=X AND status='failed'  → 拿到行锁，影响 1 行
B：UPDATE ... WHERE id=X AND status='failed'  → 阻塞，等 A 的锁
A：COMMIT                                      → 释放锁
B：解除阻塞，重新检查 WHERE（READ COMMITTED 的语义）→ 此时 status 已是 processing
                                                → 条件不成立 → 影响 0 行
B：rowcount == 0 → 判定「别人先抢了」→ 返回 409「正在处理中」
```

**关键点：影响行数就是这把锁的返回值。** 1 表示抢到，0 表示没抢到。
应用层不需要额外查询、不需要分布式锁，也不存在「检查完再更新」的窗口。

### 2.3 为什么不用 `SELECT ... FOR UPDATE`

也可以，但要写成「同一事务里先锁行、再判断、再更新、最后提交」四步，
任何一步写错（比如 SELECT 在事务外、或者中途 commit 了）锁就白加了，而且这种错**不会报错**。

单条条件 UPDATE 只有一句 SQL，没有「锁的持有范围」可以写错 —— 少一个犯错的地方。

### 2.4 一个前端类比

这就是前端乐观更新里的版本号校验：

```ts
if (row.version === expectedVersion) update(row)   // 版本对不上就放弃
```

区别只是：前端靠单线程天然串行，服务端靠数据库的行锁保证原子性。

## 第 3 题：已经有应用层查重了，为什么还必须有唯一索引？

**答：应用层查重是「先查再插」（check-then-act），查和插之间有一个时间窗，任何并发请求都能从这个窗口钻进去。**

### 3.1 窗口在哪

```
请求 A：SELECT ... WHERE content_hash='h'  → 没有
请求 B：SELECT ... WHERE content_hash='h'  → 没有      ← 两个都在这时查完
请求 A：INSERT (hash='h')                  → 成功
请求 B：INSERT (hash='h')                  → 成功        ← 应用层查重完全没起作用
```

失效的时间窗 = **从 SELECT 返回到 INSERT 提交之间的这段时间**。
不是「理论上可能」，而是只要两个请求间隔在几十毫秒内就必然发生 —— 而几十毫秒正好是
一次网络往返 + 一次解析前的耗时量级。

这个窗口在真实场景里天天出现：

- 前端按钮没禁用，用户连点两下
- 用户开了两个标签页传同一个文件
- 网关超时后客户端自动重试（原请求其实已经成功）
- 将来 `uvicorn --workers 4` 或多副本部署 —— 两个请求可能落在**不同进程**，进程内的锁完全无效

### 3.2 唯一索引做了什么

```sql
CREATE UNIQUE INDEX uq_documents_content_hash ON documents (content_hash);
```

插入时数据库自己判重：第二个 `INSERT` 直接抛 `IntegrityError`（PostgreSQL 错误码 23505，
唯一约束冲突）。应用层捕获它 → `rollback` → 重新 `SELECT` → 走「已有记录」的分支。

这样就变成**两层防线**，职责不同：

| 层 | 作用 | 失败时的表现 |
|---|---|---|
| 应用层 SELECT | 给出友好提示（"已在知识库中"）、决定是复用还是拒绝 | 并发时可能漏判 |
| 数据库唯一索引 | 保证**物理上不可能**出现两条相同 hash | 抛异常，由应用层兜住 |

### 3.3 为什么不用 Redis 锁

- 进程内的 `asyncio.Lock` 只在单进程有效，多 worker 部署立刻失效
- Redis 锁要处理过期时间、续租、锁丢失（GC 停顿导致锁提前过期）—— 是一个独立的分布式系统问题
- 而唯一索引**零额外组件、零过期时间、永远正确**，它本身就是数据库对「唯一」这件事的定义

Redis 适合做「减少无谓竞争」的优化（比如按 hash 加 30 秒短锁，让第二个请求快速失败），
但它不能替代唯一索引作为正确性保证。

### 3.4 一个必须知道的细节

PostgreSQL 的唯一索引**允许多个 NULL**（因为 `NULL <> NULL`）。

这不是缺陷，正好是我们需要的：历史数据的 `content_hash` 全是 NULL（原始文件从没存过，补不出来），
它们之间不会互相冲突，也不会阻塞新数据。代价是**老文档不参与去重** —— 这个事实必须承认，不能假装能回填。

## 附：块 1 的实现契约

### A. 上传入口的状态分支

| 命中记录的状态 | 行为 | HTTP |
|---|---|---|
| 没有记录 | 新建 `processing`，派后台任务 | 202 |
| `ready` | 拒绝，提示"已在知识库中" | 409 |
| `processing` | 拒绝，提示"正在处理中" | 409 |
| `failed` | CAS 抢锁 → 重置字段 → 派后台任务 | 202 |
| `failed` 但 CAS 失败（别人先抢） | 拒绝，提示"正在处理中" | 409 |

### B. 复用 failed 记录时要重置的字段

| 字段 | 重置为 | 原因 |
|---|---|---|
| `status` | `processing` | |
| `error_message` | `NULL` | 不清掉，前端会一直显示上一次的错误 |
| `chunk_count` | `0` | 防御性重置（失败时本应为 0） |
| `filename` | 本次文件名 | 同一内容可能以不同名字上传，展示用最后一次的 |
| `created_at` | **不动** | 它是"首次上传时间"，重试不该改写历史 |
| `updated_at` | `now()` | 状态机的时间戳，块 2 的超时回收要用它 |
| 旧切片 | `DELETE` | 理论上失败时同事务已回滚，这里是防御性清理 |

### C. 指纹字段

- 列名 `content_hash`，`CHAR(64)`，可空（历史数据）
- 值 = `sha256(原始字节).hexdigest()`，小写十六进制
- 唯一索引 `uq_documents_content_hash`

### D. 验证清单

1. 同一份文件连传两次 → 第二次 409，库里只有 1 条记录、1 套切片
2. 把一条记录手动改成 `failed` 再传同一份文件 → 复用原 id，不新增记录，`error_message` 被清空
3. 两个协程同时对同一条 failed 记录发起重试 → 恰好一个 `retried`、一个 `duplicate_processing`（CAS 生效）
4. 历史数据（`content_hash IS NULL`）多条共存 → 唯一索引不报错
5. 迁移脚本可重复执行（幂等），且回读 `information_schema` / `pg_indexes` 自查通过

## 块 3 实施记录：DOCX 表格解析（2026-10-20）

### 问题回顾

旧实现只有一行关键代码：

```python
lines = [p.text.strip() for p in document.paragraphs]
```

`document.paragraphs` 只返回**正文直接段落**。表格里的段落在
`table.rows[].cells[].paragraphs` 另一棵树上，因此表格内容一个字都进不来。
文档仍然 `ready`、`chunk_count` 也正常 —— 用户不会怀疑解析，只会怀疑 RAG 效果。

### 改法

不再用 `document.paragraphs`，改成按 **body 的 XML 子节点顺序**遍历：

| 子节点 | 处理 |
|---|---|
| `w:p` | 普通段落 |
| `w:tbl` | 表格 → 每行一条 `单元格 \| 单元格` |
| `w:sdt` | 内容控件的外壳，钻进 `w:sdtContent` 继续遍历（企业模板的填写区常用） |

顺序为什么必须保住：`一、标准如下表` → 表格 → `以上自 2026 年 1 月起执行`。
顺序错了，模型会把结论和它对应的表格对不上号。

表格渲染的三个细节：

1. **合并单元格**：`row.cells` 会把同一个格子重复返回 N 次（横向合并几列就几次），
   按底层 `tc` 元素身份去重，否则入库成「住宿 | 住宿 | 每晚 600 元」。
2. **空行**：整行无文字直接跳过，避免切片里堆出一排 ` | `。
3. **单元格内的嵌套表格**：递归展开成行、用分号连接（单元格自己也是一棵块级树）。

| `tests/unit/test_document_parser.py` | 新增 5 条：顺序保留、纯表格文档、合并单元格去重、空表格不产噪声、嵌套表格 |

### 仍然没覆盖的（如实记录）

- **页眉 / 页脚 / 脚注 / 批注**：同样不在 body 直接子节点里，本轮没做（属于块 4 的输入范围，不是表格问题）。
- **超长表格被切片器从行中间切断**：`split_text` 按字符数切，可能把一行 `住宿 | 600` 切成两半。
  表格本身能进库了，但极端长表格的**行完整性**没有保证。
