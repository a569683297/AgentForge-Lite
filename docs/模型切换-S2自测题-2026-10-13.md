## Q1 · 锁定语义（本日核心）

> 背景名词：**锁定（lock）** = 用户显式选定某个模型后，这次调用"必须是它"——
> 失败就报错，**不允许**偷偷换成别的。与之相对的是**降级（failover）**：
> 主通道失败时静默切备用通道（"降级"是默认链路的既有行为）。

**L1**：请求带了 `model_id` 但该模型不存在（已被删除 / 名字写错），网关会怎么处理？
——报错，还是回退到主通道（默认的 deepseek）？

**L2**：`_resolve_channels` 里，`provider=...`（judge 评测用）和 `model_id=...`（用户选定）
都走"锁定"分支，但前者失败抛 `RuntimeError`、后者抛 `ModelResolutionError`。
为什么同一个"锁定"要用**不同**的异常类型？

**L3**：默认链路（不传 `model_id`）里主通道失败会自动降级到备用。
现在用户**显式选定**了 deepseek（它恰好就是主通道），deepseek 挂了之后会发生什么？
——降级到备用，还是报错？为什么这两个场景的行为不一样？

**L4**：如果锁定模式失败时"自动降级到备用、但响应里如实报告用了备用"，
从纯功能角度是不是也行？为什么我们刻意不做？

<details><summary>参考答案（先自己答完再看）</summary>

- **L1**：报错。解析失败抛 `ModelResolutionError` → 非流式 422 / 流式 error 帧。
  **绝不能回退主通道**：回退会让"我选的 A"悄悄变成"实际用了 B"，
  而响应里的 `model_used`（归因）是要给用户看的 —— 归因不能是谎话，
  所以"选错了"必须显式失败，让用户重新选。
- **L2**：因为**调用者的处置策略不同**：
  - `provider` 是**服务端内部**调用（评测 judge），失败属于"系统运行问题"，
    调用方（judge 重试逻辑）需要拿到原始异常类型判断"重试有没有意义"
    （429 该重试、401 不该）；`RuntimeError` 合适。
  - `model_id` 来自**用户输入**，失败是"用户选了个不存在的东西"——
    路由层要把它翻译成 **422**（"你的输入有问题"），而不是 500（"服务端故障"）。
    异常类型就是路由层分叉的依据（`except ModelResolutionError`），
    否则路由只能靠字符串匹配错误信息，脆弱且会漂。
- **L3**：**报错（不降级）**。差别在"谁的意志"：
  - 默认链路没人在意用哪个通道，"别让用户等不到回答"是最高优先 → 降级是对的；
  - 显式选定 = 用户的明确意志，此时"用哪个模型"本身就是需求的一部分，
    偷偷换掉 = 违背用户意志且归因撒谎 → 宁可报错让用户知道。
    这正是需求稿 §4.3「显式选择 = 锁定不降级」的由来。
- **L4**：功能上"能跑"，但语义上不行 —— 同一个"我选了 A"的请求，
  有时得到 A 的回答、有时得到 B 的回答，且用户要**读完响应里的归因才知道**。
  这会把"选择"变成"建议"：锁定语义的全部价值就是"选定的确定性"。
  失败要显式，这样用户能自己决定"那我换一个"——决定权在用户，不在系统。

代码定位：`app/services/llm_gateway.py` → `_resolve_locked_model` / `_resolve_channels` / `_call_with_failover` 末尾。
</details>

## Q2 · 归因（model_used）

> 背景名词：**归因（attribution）** = 在本轮回答上记录"这是谁答的"，
> 供界面显示（"本轮由 DeepSeek 回答"）与事后排查。

**L1**：`model_used` 的三个字段 `id` / `name` / `model` 分别是什么？
为什么 `id` 要和请求里的 `model_id` **同口径**（内置名 / UUID）？

**L2**：默认链路发生降级时（主通道失败 → 备用应答），`model_used` 记录的是主通道还是备用？
为什么记"配置上本应是谁"是错的？

**L3**：这个数据为什么必须走**响应里的结构化字段**（`ChatResult.model_used` / done 帧），
而不能只在日志里打一行？

<details><summary>参考答案（先自己答完再看）</summary>

- **L1**：`id` = 配置里的身份（内置通道名 `"deepseek"` 或自定义模型 UUID）——
  与请求 `model_id` 同口径，前端才能拿它对齐"当前选中态"（打勾对得上）；
  `name` = 界面上怎么称呼（"DeepSeek" / 用户给自定义模型起的名字）；
  `model` = 发给端点的**真实模型标识**（如 `"deepseek-chat"`）——机器事实，
  不受显示名影响。
- **L2**：**备用**。归因的语义是"实际用了什么"（事实），不是"配置上本应用什么"（意图）。
  记错的后果：D22 时代"降级让用了哪个通道从数据里消失"的旧病复发 ——
  排查"这批回答质量差"时看归因全是主通道，而实际一半是备用答的，结论全错。
- **L3**：因为它是**数据**（可被前端渲染、可被评测聚合、可被未来功能消费），
  而日志是"给人偶然翻的文本"。数据要结构化、进类型系统（pydantic 模型），
  漏传会被哨兵测试抓住；日志漏了没有任何人会发现。
  （本次实测的证明：哨兵元断言 `covered == set(ChatResult.model_fields)`
  在加 `model_used` 时当即报红——日志做不到这种守卫。）

代码定位：`app/schemas/chat.py` → `ModelUsed`；`app/services/agent_service.py` → `plan_node` 转存 / `run_agent` ⑨ / done 帧。
</details>

## Q3 · 错误翻译（422 / error 帧）

> 背景名词：**SSE 帧**（Server-Sent Events）——服务器单向持续推流的一条条消息；
> 本项目的对话流式出口用它做"打字机"效果。**error 帧** = 帧协议里
> `{"type": "error", "message": ...}` 这一种，表示链路上出了错。

**L1**：同一个"模型不存在"，非流式和流式出口分别以什么形态返回给前端？
为什么流式不能用 422？

**L2**：流式的 error 帧为什么必须存在？
——如果异常就让连接"无声断掉"（不发明文、直接结束），前端会发生什么？

**L3**：流式端点里我们给 `ModelResolutionError` 单独写了一个 `except` 分支，
而且只记 `logger.warning`（其他异常记 `logger.exception`）。
为什么"用户选错模型"不该记成 exception？

<details><summary>参考答案（先自己答完再看）</summary>

- **L1**：非流式 → **HTTP 422**（`detail` 是原始可读原因）；流式 → **error 帧**。
  流式不能用 422 的原因：**HTTP 状态码在开流那一刻就已经发出去了（200）**——
  SSE 是"先回响应头、再持续发内容"，等模型解析失败发生时，`200 OK` 已经在路上，
  改不了。此后一切错误只能以**帧**的形式传递（SSE 协议的固有限制）。
  这也是为什么前端**不能只看状态码**，必须监听 error 帧。
- **L2**：如果没有 error 帧、让流无声断掉：前端的读取循环会正常结束
  （`read()` 返回 done），前端以为"回答完了"——但 done 帧从没到过，
  屏幕上留下半截气泡、URL 不跳转、用户不知道发生了什么。
  **"失败"被伪装成了"完成"**——比报错更糟。有了 error 帧，前端有据可依：
  显示错误、允许重试。
- **L3**：日志的 `level` 是**分流信号**：`exception`（ERROR 级）意味着"服务端出了
  需要排查的问题"，运维会拉告警、查堆栈。而"用户选了个不存在的模型"是**正常业务**
  的一部分（就像密码输错）——把它记成 ERROR 会在日志里制造"服务在持续报错"的假象，
  把真实故障淹没在噪音里。所以：warning 级 + 用户可读的一句话，足够。

代码定位：`app/api/chat.py` → `chat()` 的 `except ModelResolutionError` /
`chat_stream()` 的 `except ModelResolutionError` 分支。
</details>

## Q4 · 代理策略归一（本次补的一个真实坑）

> 背景名词：**环境代理** = 操作系统环境变量里的 `HTTP_PROXY` / `HTTPS_PROXY`
> （本机是 `127.0.0.1:56908` 的科学上网工具）。**httpx** = 本项目用的 Python
> HTTP 客户端，默认 `trust_env=True`（信任环境变量里的代理设置）。

**L1**：把 Ollama（`http://host.docker.internal:11434/v1`）录入自定义模型后，
如果网关的 HTTP 客户端仍按默认"信任环境代理"，会发生什么？为什么？

**L2**：修复方式是"**本机/内网地址直连、外网端点跟随环境代理**"。
为什么不做成"全部直连"？也不做成"全部跟随"？

**L3**：S1 已经修过探测路径的同款问题，S2 才发现对话路径也踩坑。
这次把策略抽成唯一出处 `build_outbound_client`。**如果将来你要加第三个
"调用 LLM 端点"的模块，你应该怎么做？**这题考的是"从事故中提炼规程"。

<details><summary>参考答案（先自己答完再看）</summary>

- **L1**：请求会被环境代理接走，而代理**不认识 `host.docker.internal` 这个域名**
  （它是 Docker 容器网络里访问宿主机的特殊域名，只在容器/宿主机网络里有意义）。
  结果：连接失败或代理返回怪异的错误码（502 之类）——
  **错误指向代理，而真实病因是"代理就不该出现在这条链路上"**。
  实测证据：同一台机器上请求 `127.0.0.1:9`（没开的端口），
  默认客户端拿到的是**代理的 502**（本机端口没开不可能返回任何 HTTP 响应，
  只有中间层能应答）；直连客户端拿到的是 `ConnectError`（真实的"连不上"）。
- **L2**：因为两类流量的**正确默认行为不同**：
  - 本机/内网（localhost / 127.0.0.1 / host.docker.internal / *.local）：
    走公共代理毫无意义（代理也到不了你本机的服务），只会引入假错误 → **直连**；
  - 外网端点：代理可能是用户**有意的网络策略**（科学上网、公司网关）——
    你要尊重它，替用户决定"直连外网"可能让本来能用的配置失效 → **跟随环境**。
  一刀切任何一边都会造成"一半场景正确、另一半莫名失败"。
- **L3**：**不复制代码，直接 import `build_outbound_client`**（策略的唯一出处）。
  并从这次事故提炼规程：**横切策略（代理、超时、重试、日志）必须只有一个出处**——
  "两个地方各写一份"的下场就是这次：S1 修了一半、S2 才发现另一半，
  修完还要回来补文档。"修了一个点之后，问自己：**同一个模式还有几处？**"

代码定位：`app/services/model_service.py` → `build_outbound_client`（策略唯一出处）；
两个使用方：`_probe_chat_endpoint`（探测）与 `app/services/llm_gateway.py` 的
`_call_once` / `_call_once_stream`（对话）。
</details>
