**新名词先注解**（本文首次出现处给定义，读者不必回头查）：

| 名词 | 一句话注解 |
|---|---|
| **SSE** | Server-Sent Events，服务端**单向持续推送**文本给浏览器的机制（逐字打字机效果靠它） |
| **pgvector** | PostgreSQL 的向量扩展插件，让数据库能按"语义相近程度"排序 |
| **tsvector** | PostgreSQL 的**全文检索**数据类型，把文本切成词后建倒排索引 |
| **BM25** | 经典关键词相关性打分公式（考虑词频/文档长度/词稀有度） |
| **RRF** | Reciprocal Rank Fusion，把**多路检索的名次**融合成一个列表（只取名次、不问分数） |
| **reranker（重排）** | 用一个"精算模型"对候选片段重新打分排序，比向量检索准但更慢 |
| **LangGraph** | LangChain 出的**图式编排框架**：节点=处理步骤，边=跳转规则 |
| **ReAct** | Reason+Act，让模型"想一步→做个动作→看结果→再想"的循环范式 |
| **MCP** | Model Context Protocol，让 Agent 用统一协议接入外部工具的开放标准 |
| **npx** | Node 生态的"临时下载并运行某个包"的命令 |
| **PAT** | Personal Access Token，个人访问令牌（服务端靠它认人） |
| **span / trace** | span=一次操作（一次检索/一次 LLM 调用）；trace=一次请求串起来的所有 span |
| **ORM** | 用 Python 类代替写 SQL 来操作数据库表的中间层 |
| **function calling** | 让 LLM 按约定格式**声明要调哪个函数、带什么参数**的标准机制 |
| **Langfuse** | 开源的 LLM 应用**可观测平台**：把每次调用的输入输出、token、耗时记成可查的 trace |
| **GIN 倒排索引** | PostgreSQL 的一种索引类型，适合"一个词出现哪些文档里"这类多值字段的快速筛候选 |
| **ContextVar** | Python 的"上下文局部变量"，同一段代码在不同请求里能拿到各自的值（并发安全） |

## 2. 五层各自"负责什么 / 不负责什么"

解耦的**可检验判据**不是"分了目录"，而是**每一层都有一个对外唯一出口** —— 出口只有一个，才谈得上替换。

| 层 | 负责 | **不**负责 | **对外唯一出口** |
|---|---|---|---|
| ① 界面 | 呈现、交互、SSE 接收（规划中） | 任何业务判断 | `frontend/src/api/*`（7 个模块） |
| ② 接口 | 补默认值、调服务层、记进出日志 | 业务逻辑、参数校验（交 pydantic/422） | FastAPI `router` |
| ③ 编排 | 决定"下一步调工具还是作答" | 具体怎么查、怎么调模型 | `run_agent()` |
| ④a 工具 | 注册与执行、记出身（`source`） | 知道谁调它 | `execute_tool()` / `get_tools_schema()` |
| ④b 检索 | 检索链路（向量/关键词/融合/重排） | 决定用哪种配置 | `retrieve()` |
| ④c 记忆 | 热窗口 + 长期摘要 | 生成回答 | `get_window()` / `append_turn()` / `maybe_summarize()` |
| ⑤ 基础设施 | 模型调用、存储、追踪、外部接入 | 知道调用它的业务含义 | `llm_gateway.chat()` / MCP `manager` |

★ **这张表最值钱的一行是"不负责"那一列**。分层失效从来不是"文件放错目录"，而是某一层开始替别人做决定 ——
比如让 Agent 引擎自己拼 SQL、或让接口层自己判断要不要检索。

## 3. 七条架构红线（PRD §8.2 原文 1–7 条，附"不遵守会怎样"）

| # | 红线 | 违反后的真实后果 |
|---|---|---|
| 1 | 业务代码不得绕过 Gateway 直连 SDK | 那次调用**在 Langfuse 上不存在** —— token 统计与延迟数据出现无法解释的缺口 |
| 2 | Agent 不得直接调函数（必须经 Registry） | 加工具要改 Agent 引擎（D8 之前的耦合）；且 LLM 的能力清单与实际可用工具**两处维护、必然漂移** |
| 3 | 评测模块与业务解耦（输入=配置+评测集，输出=报告） | 评测会污染会话数据（D22 的 `persist=False` 就是这条的落地） |
| 4 | 任何外部凭据不得进入代码/数据库/日志，只从 `.env` 读 | 密钥进日志 = 一条 `repr(settings)` 就明文打印 4 个密钥（D34 实测抓到过） |
| 5 | MCP 工具不得写死在代码中，必须运行时动态发现 | 加一台 server 要改代码 → 失去 MCP 的全部意义（D27 实证：接入 Harness **Agent 引擎零改动**） |
| 6 | 结构化查询不得由 LLM 直接生成 SQL，必须经语义层模板渲染 | 从"查错数"升级为"**删库**"；且答案无法复现 |
| 7 | Langfuse 只作只读数据源，不双写落库 | 两份追踪数据必然漂移，且生命周期纠缠（追踪可清理、业务数据不可） |

## 4. 一次问答的端到端数据流

**入口 → 步骤 → 返回**。共 8 段，段号与 `agent_service.run_agent` 的注释编号**一一对应**（便于对照源码）。

### 4.1 全景（30 秒版）

```
浏览器 ──POST /api/chat──▶ ②接口层 ──run_agent(session_id, message)──▶ ③编排层
                                                                            │
         ┌──────────────────── ⓪ 重置引用收集器 ──────────────────────────┤
         │ ① 读历史（Redis 优先 / PG 兜底） ①.5 读长期摘要（PG）           │
         │ ② 组状态 → ③ 跑图：plan ⇄ execute（可多轮）                     │
         │ ④ 取最终回答 ⑤ 取来源表 ⑥ 校验引用越界 ⑥.5 取工具调用序列      │
         └────────────────────────────────────────────────────────────────┘
                                    │
                        ⑦ 写回 Redis 热窗口（仅 user + 最终回答）
                        ⑧ 写回 PG 全量（含 assistant(tool_calls) 与 tool 消息）
                        ⑧.5 摘要压缩检查（到阈值才触发）
                                    │
        ②接口层 ◀──ChatResult─── ⑨ 返回 {answer, sources, invalid_citations, tool_calls}
        浏览器 ◀── JSON {session_id, answer, sources, invalid_citations}
```

### 4.2 逐段说明（含代码位置）

| 段 | 做什么 | 代码位置 | 关键设计点 |
|---|---|---|---|
| ⓪ | 重置引用收集器 | `core/citation.py: reset_sources()` | ContextVar 复制的是**绑定**不是对象内容，不重置会读到上一请求的残留 |
| ① | 读会话热窗口 | `memory_service.get_window()` | Redis 优先，未命中/不可用走 PG 兜底 |
| ①.5 | 读长期摘要 | `session_service.get_summary()` | 首次对话时返回 `None` → system prompt 里**跳过这一段**，不留空壳 |
| ② | 组装 AgentState | `agent_service.py: AgentState` | `{messages, step_count, summary}`；摘要**单独走字段**，不塞进 messages（否则伪装成真实对话轮次、干扰引用编号判断） |
| ③ | 跑 LangGraph 图 | `get_agent().ainvoke(state, config={"recursion_limit": 12})` | 见 §4.3 |
| ④ | 取最终回答 | 从后往前找**第一条 content 非空**的 assistant 消息 | 中间的 assistant 消息可能只带 `tool_calls`、content 为空 |
| ⑤ | 取来源表 | `core/citation.py: get_sources()` → `SourceItem` | 结构通道（不是从回答文本里正则抠） |
| ⑥ | 校验引用越界 | `core/citation.py: check_citations()` | 幻觉引用检测：回答里写了 `[7]` 但只有 5 条来源 → 告警 |
| ⑥.5 | 取本轮工具调用序列 | `new_messages[len(history):]` | ★ 评测判"C 类题有没有选对工具"的**唯一依据**（`tool_miss`）——答案可能答对却完全没查库 |
| ⑦ | 写回 Redis | `memory_service.append_turn()` | 只存 user + 最终回答，**不存中间工具消息** |
| ⑧ | 写回 PG 全量 | `session_service.append_messages()` | 失败**不阻断**对话（已等到回答，抛 500 只会白跑），但必须留 ERROR 日志 |
| ⑧.5 | 摘要压缩检查 | `memory_service.maybe_summarize()` | 排在 ⑧ 之后 —— 触发判据要从 PG 数轮数，不等落库就永远差一轮 |
| ⑨ | 返回 | `ChatResult{answer, sources, invalid_citations, tool_calls}` | 工具序列随返回一起出，供前端工具卡片与评测共用 |

★ **观测层的范围刻意到 ⑥.5 为止，不含 ⑦⑧**：写回是副作用、不占用户等待时间；
把它算进根 span 的 latency，会让"这一轮慢在哪"失真 —— 而这个 latency 之后是要被**当指标读**的。

### 4.3 图内部：plan ⇄ execute 的循环

```
               ┌──────────────────────────────────────────┐
START ──▶ plan │  一次 LLM 调用（走 Gateway，带 tools schema）│
               │  输出可能是：① 含 tool_calls = 要去查       │
               │              ② 不含 tool_calls = 就是最终答案│
               └──────────────┬───────────────────────────┘
                              │ should_continue()
              ┌───────────────┴────────────────┐
              ▼                                ▼
       有 tool_calls                      无 tool_calls
              │                                │
              ▼                                ▼
     execute_node（逐个执行工具）            END（plan 的输出直接给用户）
     结果以 role="tool" 消息写回
              │
              └──────────▶ 回到 plan（基于结果作答，或继续下钻）
```

**两处容易讲错、也最常被追问的地方**：

1. **没有独立的 answer 节点**。D14 之前是 `plan → (execute | answer)`，两个节点各调一次 LLM；
   实测发现**不需要工具时 plan 已经把答案说完了**，条件边还会再走 answer 又生成一遍 ——
   一轮白烧一次调用，PG 里留下两条内容相近的 assistant 消息。
   修法：把回答规范**并进 plan 的 prompt**，无 tool_calls 时直接 END。
   代价（如实说）：**"决策"和"作答"合并到一个节点**，所以 Langfuse 上靠节点名已分不出这两件事，
   改用 `trace_name` 区分（`agent-plan` / `agent-answer`，判据="这一轮是否已拿到工具结果"）。

2. **LangGraph 的 recursion_limit 必须显式传**。不传则用库默认值 25，而本项目定为 **12**。
   ⚠ 历史上这里只在注释里写着"=10"，代码里从未真正传过 —— **注释与行为不符**，实际生效的是默认值。
   现在显式声明，不让它跟着库默认值漂。

### 4.4 工具执行的两种"出身"

Agent 调工具时，**只认工具名，不关心它住哪** —— 这正是路径 B 能零改动接入的原因。
但人必须能分辨，所以注册表给每个工具记了 `source`：

| 工具 | 名字实例 | `source` | 函数体在哪 |
|---|---|---|---|
| 内置 | `current_time` | `local` | 本进程（真函数） |
| 自研检索 | `search_documents` | `local` | 本进程（真函数） |
| 自研 MCP | `inventory_query_inventory` | `inventory` | 另一个 Python 子进程（**代理 stub**） |
| 外部 MCP | `harness_*`（11 个） | `harness` | `npx` 拉起的 Node 子进程 → 云端 API（**代理 stub**） |
| 🅳 M8 | `query_metric` | `local` | Agentic BI 入口（语义层模板渲染） |

**两个必须说清的实现细节**：

- **`source` 对 MCP 工具就是 server 名**；本地工具**不该谎称**来自某台 server，所以映射成 `None`。
- **未知工具返回 `"unknown"`，不是 `"local"`**：把"没这个工具"谎报成"本地工具"，
  会在 Langfuse 上留下一条**看起来正常的假调用记录** —— 而真实情况是"LLM 编了个不存在的工具名"。
  排障时这两者必须能区分。
- **命名前缀规则是显式配置**，不是猜的：`inventory` 那台远端叫 `query_inventory`，
  加前缀成 `inventory_query_inventory`；`harness` 的工具**自带** `harness_` 前缀，**不再叠加**（`namespace=""`）。

### 4.5 检索层：三条腿 + 一个门面

```
retrieve(问题)   ← 全项目检索的唯一对外入口        app/services/retrieval_service.py
  │
  ├─ pure_vector   → search(top5)                       无融合、无重排
  ├─ hybrid        → hybrid_search(top20→top5)           融合后直接取 5
  └─ hybrid_rerank → hybrid_search(top20) → rerank → top5
                                 ↑ ⚠ 融合窗口是 20 不是 5

hybrid_search(问题)   ← 并发两路（asyncio.gather）
  ├─ search(问题, top_k=20)             向量路：embedding <=> 问题向量（pgvector 余弦距离）
  ├─ search_keywords(问题, top_k=20)    关键词路：content_tsv 走 GIN 倒排筛候选 → BM25 打分排序
  └─ fuse_rrf(...)                      RRF 只取**名次**融合 → 一个有序列表
```

**为什么必须保留"三条腿"而不是只留最好的那条**：PRD §9.5 的消融矩阵要求
**同一个评测集跑三遍**（A 纯向量 / B 混合 / C 混合+重排）。如果直接用重排替换掉 `search()`，
**B 配置就永久消失**了 —— "重排到底有没有用"这个问题以后再也答不出来。

**为什么两条路都要有**：向量擅长"意思相近"，对**精确字面**不敏感；
问"E104 型号""3.5% 提成比例"这类问题时，向量可能把语义相近但字面无关的片段排前面，而 BM25 恰好相反
（字面不命中就是 0 分）。**命中集合不同，才值得融合**。

### 4.6 观测层：一次对话 = 一条 trace

| span 名（常量） | 类型 | 覆盖范围 |
|---|---|---|

## 8. 演示第 1 段（30 秒）讲稿

> 演示脚本（`scripts/demo.sh`）的第 1 段就念这段。**先讲分层，再讲最值钱的那一处解耦。**

```
AgentForge 是一个企业 Agent 运行时平台，分五层：

界面层是 React + TS 的七个页面；
接口层是 FastAPI，只做补默认值和转发，不含业务判断；
编排层是 LangGraph 的 ReAct 图 —— 一个 plan 节点负责决策、一个 execute 节点负责执行工具，
  两者组成循环，支持多步下钻；
下面是四个平级能力层：工具注册表、RAG 检索、记忆、以及所有模型调用的唯一入口 LLM Gateway；
最底下是基础设施：PostgreSQL + pgvector、Redis、Langfuse、以及两台 MCP Server。

这套架构最值钱的一点是「工具注册表 + MCP 客户端」这一层：
工具不是写死在代码里的，是运行时动态发现的。所以我把接一台**外部企业系统**——
Harness 的官方 MCP Server，11 个工具——接进来的时候，Agent 引擎一行代码都没改。
工具的两种出身，真函数和跨进程的代理，从 LLM 那一侧看毫无区别。
```
