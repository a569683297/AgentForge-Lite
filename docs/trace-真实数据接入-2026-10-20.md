## 一、起点：原来那一页是假的

`TracePage.tsx` 之前读 `frontend/src/mock/index.ts` 的 `MOCK_TRACES`，页面标题旁挂着
「示例数据」徽章，刷新按钮没有 onClick。`mock/index.ts` 第 5 行的注释写得很直白：

> `MOCK_TRACES` —— Trace 页：**后端完全没有 trace 查询接口**（span 在 Langfuse，无 REST 出口）

所以"接入真实数据"要补的不是前端，是后端缺的那条查询链路。

## 二、数据源选型：为什么是 v2 observations

Langfuse 有三条能读到 span 的路，实测结果：

| 端点 | 字段 | 限流 | 时效 | 命运 |
|---|---|---|---|---|
| `/api/public/observations`（v1） | 全（含 metadata / usageDetails） | **5 次/分钟** | 有分钟级延迟 | `_deprecation`：**2026-11-16 移除** |
| `/api/public/traces` | 全（一次返回整棵树） | 未观测到 | 文档说约 10 分钟延迟 | meta 里 `sunsetAt: 2026-11-16` |
| `/api/public/v2/observations` | 缺 metadata / usageDetails | 未观测到限流头 | **实时**（官方称唯一实时读路径） | 官方指定的替代品 |

选 v2 的三个理由：

1. **不踩下线**。前两个都在 2026-11-16 同一天消失，只有 27 天。
2. **不和指标抢配额**。v1 的 5 次/分钟要供 `token_cost` / `latency_p95` 用，
   Trace 页是会被反复点开的页面，挤进去必然把指标打成 degraded。
3. **支持 `?traceId=` 精确过滤**（实测一条 `run_agent` 的 4 个 span 一次返回），
   画一棵树只需 1 次请求，不需要"先查列表再翻页拼树"。

代价：v2 不带 `metadata` 与 `usageDetails`。所以这一页**看不到**「工具属于哪台
MCP server」和 token 数 —— 那两项由 `/api/metrics` 回答，不在这里重复。

## 三、数据流（入口 → 步骤 → 返回）

列表：

```
浏览器 GET /api/traces?hours=24&limit=20
  → trace_service.list_traces
      ① 算窗口：[now-24h, now]（UTC）
      ② fetch_v2_observations(from, to, limit=200)   ← 负缓存 → 缓存 → 单飞 → HTTP
      ③ 按 traceId 分组，每组压成一行摘要（根名 / 开始时刻 / 跨度 / span 数 / 有无错误）
      ④ 按开始时间倒序，取前 limit 条
  ← {degraded, reason, truncated, traces[]}
```

详情：

```
浏览器 GET /api/traces/{trace_id}
  → trace_service.get_trace
      ① fetch_v2_observations(trace_id=...)     ← 一次拿全，不分页
      ② _build_spans：parentObservationId 建父子表 → 先序遍历 → depth + 相对毫秒
  ← {degraded, total_ms, spans[]}（数组顺序即渲染顺序）
```

前端两级视图各一次请求，点过的 trace 进 `Map` 缓存，来回比对不再打 HTTP。

## 四、接口契约

`GET /api/traces?hours=24&limit=20`

| 字段 | 含义 |
|---|---|
| `degraded` / `reason` | 读通道不可用；此时 HTTP 仍是 **200**，`traces` 为空 |
| `truncated` | 窗口内 span 超过单次上限（200），只统计了最近一批 |
| `traces[]` | `trace_id` / `name`（根 span 名）/ `session_id` / `start_time` / `duration_ms` / `span_count` / `has_error` |

`GET /api/traces/{trace_id}`

| 字段 | 含义 |
|---|---|
| `total_ms` | 整条 trace 的墙钟跨度，瀑布图横轴上限 |
| `spans[]` | `name` / `type` / `depth` / `start_ms` / `end_ms` / `duration_ms` / `status` / `model` |

`start_ms` / `end_ms` 是**相对本次 trace 起点**的毫秒，不是时间戳。瀑布图横轴只关心
"谁先开始、持续多久"，绝对时刻留在 `start_time` 里。

trace 不存在或超出 Langfuse 保留期 → **404**（用户问题，与降级区分开）。

---

## 五、三个刻意的设计

**1. 降级不是 500。** `degraded=true` + 人话原因，HTTP 200。观测数据是旁路，
它的不可用不该让整页变成错误页 —— 与 `/api/metrics` 的 degraded 同一条规矩。

**2. 孤儿节点当根，不丢弃。** 父节点被时间窗或 limit 截掉时，那个 span 仍要画出来
（`depth=0`）。丢掉的表现是「明明 6 个 span，页面只画 4 个」且不报错。

**3. v2 的缓存三件套与 v1 完全独立。** 不复用 `_cache` / `_inflight` / `_blocked`：
两者的键语义不同（时间窗 vs traceId），混用会让"缓存命中"变成巧合，而这类 bug
的表现是「页面画的树和选中的那条 trace 对不上」。更实际的理由是：v1 是指标的命脉，
Trace 页不能挤占它的配额计数。

## 七、已知限制（都是真的，不是待办）

1. **跨窗口边界的 trace 会缺前半截**。按时间窗取数，23:59:58 开始的那条在
   "最近 1 小时"里可能只剩后半段，表现为根缺失、`span_count` 偏小。不报错。
2. **单次最多 200 条 span**。7 天窗口实测触顶（`truncated=true`），耗时数字偏小。
3. **看不到 token 与工具来源**（v2 不带 `usageDetails` / `metadata`）。
4. **依赖 Langfuse Cloud**。凭据失效或断网时整页降级 —— 因为 span 从来不落项目库。
   若要彻底摆脱这个依赖，得改埋点做双写（新增本地 trace 表），那是另一个工程。
