## 上传大小限制现状盘点（用户提问触发，实读 + 实测）

### 两层限制（不一致）
- **应用层（设计值）**：`app/services/document_parser.py:28` `MAX_FILE_SIZE = 20MB` → 超限 400 + 中文说明。
- **网关层（8080 部署路径）**：`frontend/nginx.conf` **未配 `client_max_body_size`** → nginx 默认 **1MB** → 超限 **413**（英文默认错误页）。
- **前端**：`KnowledgePage.tsx` 无 size 预校验（只有 `accept` 扩展名过滤）；413 时 nginx 返回 HTML 非 JSON → client.ts 取不到 `detail` → 用户见 "Request failed with status code 413" 英文。

### 实测证据（本机，全部清理无残留）
- 1.5MB / 1.1MB 过 8080 → **413**；0.9MB 过 8080 → 202 入库；2MB 直连 8000 → 202（对照：瓶颈在 nginx 不在后端）；21MB 直连 8000 → 400「文件过大（21.0MB），上限 20MB」。
- 测试文档（2MB/0.9MB 两份）已删除，回库 **12 篇/312 片** 恢复原状。
- 为什么一直没发现：M6 期间上传的都是小文件（<1MB），从未触发 nginx 默认值。

### 修复建议（待用户拍板，未动工）
- `nginx.conf` 的 `location /api/` 块加 `client_max_body_size 24m;`（略大于 20MB，把否决权留给后端——超 20MB 时用户拿到中文 400 而非英文 413）。
- 可选：前端加 `file.size` 预校验（立即中文提示，不必等网络往返）。

## 「100MB 上限」影响分析（用户提问，实测 + 外推，未动工）

### 实测基线（2MB 中文文本=69 万字，直连 8000，本机 10 核/32GB）
- 上传+202 响应 **0.02s**；**2839 片 / 后台处理 27.0s**（≈105 片/s）。
- 处理期间发 chat：**0.8s，与空闲基线一致**（无可见劣化；快问快答不触发检索）。
- 测试文档已删，回库 **12 篇/312 片**。

### 100MB 外推（★线性外推估算，未实测 100MB）
- 100MB 中文文本 ≈ 3500 万字符 ÷ 250 字/片 → **≈ 14 万片**；处理时长外推 **~22 分钟+**（写库事务/内存压力超线性，实际大概率更长）。
- 内存峰值粗估 **3GB 量级**（主项：`vec.tolist()` 后 14 万条 512 维 Python float list ≈ 2.2GB；次项：切片文本+分词+ORM 对象）。
- 链路风险点全在：`data = await file.read()`（全量进内存）→ `embed_texts`（一次性 14 万条）→ 单事务写 14 万行。均为「为小文件设计」的模式。

### 影响面定性
- **不受影响**：小文件路径逐字节不变；现有语料/评测/对话零影响；pytest 用 `MAX_FILE_SIZE` 常量引用（`test_document_parser.py:49,54`），改值自动跟随不破测试。
- **必须配套**（否则 8080 半通）：nginx `client_max_body_size` 不提就还是 1MB 截断；建议前端加 size 预校验。
- **外网部署后才会碰到**：axios 20s timeout（100MB÷2MB/s=50s）、nginx `client_body_timeout` 60s 默认。
- **扫描件 PDF 场景**：现有解析器对无文本层 PDF 直接 failed（"未提取到任何文本"）——**提升上限 ≠ 支持**该场景（需 OCR，另属大工程）。
- **同源纪律**：大文件入库=语料指纹变化 → 又触发「评测同源」登记要求（第三次同型风险）。

### 推荐（分两步，待拍板）
① 立即：nginx 对齐设计值（1MB → 20MB+），治当前缺口；
② 100MB 真支持：需「大文件处理改造」（流式读取/分批 embed/分批 commit/进度反馈/超时可配），属新里程碑——先改造再提上限，否则"能收下但处理不动"（20min+ 无进度 + 进程重启丢任务窗口放大 50 倍）。
