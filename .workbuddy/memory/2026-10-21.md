## 上线后用户实测报的两个 bug（已修）

**现象**：点登录不跳转、F5 才进得去；进去后发不了消息。
**注意**：这两条在 432 条后端测试 + 17 个接口探针全绿的情况下依然存在 —— 都是**纯前端集成层**的问题，测试覆盖不到。

### bug ① 登录态写进了存储，但没通知视图

- 根因：`App.tsx` 用 `useState(() => getSession())`，初始值函数**只在首次挂载执行一次**；
  `saveSession()` 改的是 `lib/auth` 的模块变量 + localStorage，App 毫不知情。
  → `authenticated` 仍为 false → 路由守卫把刚跳过去的 `/chat` 又推回 `/login?next=/chat`。
  → 刷新能好，是因为 App 重新挂载、初始值函数重跑了一次。
- 修法：`lib/auth.ts` 加订阅器（`subscribeSession` + `emit()`），`App.tsx` 改用
  `useSyncExternalStore(subscribeSession, getSession, getSession)`。
- **为什么必须订阅而不能在登录页 setState 往上抛**：5 个写入点里有两个在**组件树之外**
  （axios 拦截器的静默刷新、强制下线），那里调不到 setState。
- **硬约束**：`getSnapshot` 在值没变时必须返回同一对象（`Object.is`），否则无限重渲染。
  `current` 是模块级变量、只在写入时换引用 —— 满足，且已用测试钉住。
- 顺带修：`emit()` 原本裸循环，一个订阅者抛错会中断通知链 + 把异常冒泡给 `saveSession()`，
  让登录页误判"登录失败"（而凭证已落盘）。改成逐个 try/catch。
- 附带：加了 `storage` 事件监听，多标签页登录态同步。

### bug ② 流式对话用裸 fetch，绕过了 axios 拦截器

- 根因：流式必须用 `fetch`（浏览器端 XHR 拿不到流式响应体），而 **fetch 不经过 axios 拦截器**
  → Authorization 头没加、401 不会自动刷新。后端老实回 `401 {"detail":"请先登录"}`。
- 迷惑性：轮询类接口（axios）全绿，只有这一条通道坏；报错文案指向"身份"不像"通道"。
- 修法：`api/client.ts` 新增 `authedFetch`，行为与拦截器逐条对齐
  （① 先 ensureFreshToken ② 401 → `refreshOnce()`（**复用同一个单飞 Promise**）→ 重放一次
  ③ 刷新失败 forceLogout）。三个细节：重放前 `first.body.cancel()`；每次重发重新读 token；只重放一次。
- 实测：不带 token → 401 `{"detail":"请先登录"}`；带 token → 200 + `data: {...}` 正常推流。

### 新增前端测试（25 条，vitest 22 → 47）

`src/lib/auth.test.ts`(17) / `src/lib/authStore.test.tsx`(3，真渲染复现 bug ①) / `src/api/client.test.ts`(5，守 bug ②)。
两条都做了反向验证：换回修复前的写法，分别红 3 条 / 2 条。

**通用教训**：「写进了存储」≠「视图知道了」；「某个 HTTP 客户端配了拦截器」≠「所有出站请求都带了凭证」。
两者都是**看起来自动、其实显式**的地方，只在多写入点/多通道时才暴露。

### 三条硬结论

1. **画像是 fail-open，认证是 fail-closed**。判据：这层是不是业务前置条件。
   画像读不到 = 这次没个性化；认证读不到 = 不能确定你是谁。
2. **抽取必须异步**（`asyncio.create_task`），摘要必须同步。判据：结果会不会被下一步立刻读到。
   后台任务必须**保存强引用**（`_BACKGROUND` set），否则可能被 GC 回收 —— 症状是"有时抽有时不抽"，
   日志里什么都没有。
3. **LLM 抽取失败要写冷却时间**。不写 → 下一轮立刻重试 → 一次故障放大成"每轮一次失败调用"。

### 踩的坑

- **类体字段遮蔽**：`UserProfileFact` 有字段 `text`，类体内 `server_default=text("0.7")`
  的 `text` 已变成 MappedColumn → `TypeError: 'MappedColumn' object is not callable`。
  修：`from sqlalchemy import text as sa_text`。类体是普通作用域，这个坑会重复出现。
- **jieba 复合词**：查询「前端」匹配不到事实「前端开发相关的第 N 条事实」——
  jieba 把「前端开发」切成一个词。只做完全相等会让画像在最常见问法上静默失效。
  修：加包含关系兜底，但**限制 token 长度 ≥ 2**（单字是任何词的子串，放进来等于匹配失效）。
  这是写测试时发现的，不是看代码看出来的。
- **`SAWarning: nested transaction already deassociated`**：迁移脚本手写 begin_nested +
  commit，插入失败后事务失联。改用 `async with conn.begin_nested()`。

## 用户反馈「新开窗口画像没被召回」——根因不是没注入，是兜底只给 1 条（已修）

- 现场：账号 `569683297@qq.com`，画像 2 条（`是开发工程师` / `希望被称呼为梦`，conf 均 0.95），
  显式字段全空。问「我叫什么」→ 答「我这边没有你的名字信息」。
- 探针结论：`render_for_prompt` **有**返回内容 —— 注入了，但只注入了「是开发工程师」。
  查询分词 `['我','叫','什么']` 与两条事实余弦都是 0 → 走零相关兜底 →
  旧实现 `_by_confidence(1)` 按 id 取第一条 → 名字被丢。
- 修法：兜底从「1 条」改为「按 confidence 取满 `top_k`（=4，事实不足则全带）」，
  空查询与零相关合并成同一条 `_by_confidence(limit)`。
- 教训：**"零相关"不等于"每条都同样无关"**，它只说明匹配没给出信号；
  没信号时唯一可用的排序依据是 confidence，应当用它填满预算，而不是凭空只挑一条。
  这正是"注入成功了一半"型故障 —— 日志全绿、页面有数据，只有回答不对。
- 反证：把兜底改回 `_by_confidence(1)` → 3 条用例同时红（含 `test_name_fact_survives_zero_relevance_query`）。
- 容器实测（重建后）：问「你记得我叫什么」→「梦。」；「我是做什么的」→「你是开发工程师。」；
  问天气时不主动复述画像（提示词约束生效）。
- 顺带记录两个**正常**时间差（文档 §6.7）：当轮说"叫我阿梦"当轮问名字答不出（抽取在回答之后）；
  刚改显式字段在同一轮追问用旧值（画像每轮开始前读一次）。
