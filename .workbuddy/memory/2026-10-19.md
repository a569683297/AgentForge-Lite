## 诊断：分析页 Token 消耗 / 各阶段延迟 P95 展示失败

结论：Langfuse v1 `/api/public/observations` 限流（实测响应头 `x-ratelimit-limit: 5`、`retry-after: 56`，即 5 次/分钟），
而一次分析页加载要打 6 次（token_cost 3 页 + latency_p95 3 页 × PAGE_SIZE=100 / limit=300），必然超限 → 429 → 两指标 degraded。

关键实测数据（7 天窗口 2026-10-13~19）：
- `totalItems=3146`、`totalPages=32`，分页为**新→旧降序**（page1=10-16，page32=10-12）
- limit=300 只覆盖最新 ~9.5% 数据 → token sum 低估、P95 样本偏向 10-16 批量评测流量（口径隐患，非报错原因）

代码层根因：
1. `langfuse_client._fetch_observations` 缓存键 `(from_ts,to_ts,limit)` 两指标相同，但**无 single-flight**；前端 `Promise.all` 并发 → 双方同时 miss，各拉 3 页（本可共享为 3 次）
2. `main.tsx` 有 `StrictMode`，dev 下 effect 双跑 → 12 次请求（生产构建不双跑）
3. 失败不缓存、429 无退避 → 刷新即重新打满额度
4. 降级文案直接透出 Langfuse 英文原句并截断 60 字符

修复方向（待用户确认后动手，未改代码）：
- 短期：single-flight 合并并发 + 429 读 `retry-after` 做 30~60s 负缓存 + 降级文案翻译
- 结构：后端加 `/api/metrics/overview` 一次返回全部指标（服务端串行复用一份 observations）
- 根本：改 v2 `/api/public/v2/metrics` 聚合接口（v1 端点 2026-11-16 下线；token 字段是否支持需查文档验证，勿猜）

## 审查：RAG 文档上传的重复/失败处理（15:30，仅审查未改码）

结论：**两类场景均无处理逻辑**。核查范围 `app/api/documents.py`、`app/services/document_service.py`、`app/models/document.py`、`app/models/document_chunk.py`、前端 `KnowledgePage.tsx` / `api/documents.ts`。

- 去重：`documents` 无 content_hash 列、无唯一约束（除主键）；`filename` 注释明确"不再是身份标识"。每次 POST 都新建 UUID 记录 → 切片/embedding 重算 → 检索 top_k 被同一内容重复占位。`document_service.py:19` 注释已意识到该风险，但当时只用异步降低发生概率，未消除。
- 失败重传：有 failed 状态 + error_message（截断 500 字符），但**无 retry 接口**；只能重新上传生成新记录，旧 failed 记录留在库里需手删。
- 硬约束：**原始文件不落盘**（`data: bytes` 仅在内存中传给 BackgroundTasks，Document 无 file_path 字段）→ 进程重启后服务端无物可重试，这是"服务端重试不可能"的根因。
- 隐性缺口：processing 无超时回收/启动对账（`api/documents.py:56` 自认进程重启会卡死）；前端轮询只要有一条 processing 就永不停。
- 并发：前端 `handleUpload` 无 loading 防抖，连点两次即两份重复文档。

补法（分层，待用户确认再动手）：hash 去重（P0）、原始文件留存 + retry 接口（P0）、processing 超时回收（P1）、Redis 按 hash 加锁防并发（P1）、可重试错误自动退避（P1）。
